# 论文定位、任务边界与术语

本目录负责回答：第一篇论文到底讲什么、边界在哪里、哪些话能写、哪些话不能写。当前只保留三个长期入口：本文件、[claim_evidence_map.md](./claim_evidence_map.md) 和 [paper_outline.md](./paper_outline.md)。

## 1. 一句话主线

给定控制系统自然语言需求 `NL` 与初始状态机 `STM_0`，本文研究是否可以通过无人化、结构化反馈驱动的检查、诊断、场景、仿真与修正循环，得到相对于 `STM_0` 更可检查、更可执行、更语义一致的候选状态机 `STM_k`。

## 2. 为什么不是 `NL -> STM` 生成论文

直接从自然语言生成状态机已经是拥挤方向。若继续主打 `NL -> STM`，论文会被拉回提示词、模型选择、direct baseline 公平性和生成质量硬对比，而不容易突出本项目真正积累起来的诊断、仿真、修正反馈和运行审计能力。

真实使用场景中，已有或可构造的初始状态机往往不是完全不可用，而是存在结构、语义、guard / action、行为场景或可执行性缺陷。更稳的研究问题是：**给定 `NL` 与 `STM_0`，系统能否自动发现缺陷、提出修正、检查回归、接受或回滚候选，从而得到更好的 `STM_k`。**

## 3. 核心缺口

| 既有工作常见能力 | 本文关注的缺口 |
|---|---|
| 生成类似状态机 / UML / SysML / 行为模型的制品 | 生成后制品是否可机检、可执行、可诊断、可修正常缺少闭环 |
| 使用提示词或 agent 分阶段生成模型 | 结构化反馈是否能稳定减少缺陷、避免回归、记录失败模式仍需实证 |
| 使用自然语言或示例辅助建模 | 初始模型与需求之间的语义漂移、guard / action 错误、场景行为缺陷需要可审计修复协议 |
| 一次性人工审查或工具检查 | 缺少“诊断 -> 修正 -> 回归 -> 接受 / 回滚”的无人化循环与归因台账 |

## 4. 方法洞察

本文的关键不是提出一个新 DSL，也不是换更强模型重新生成状态机，而是把初始状态机规范化为可机检、可执行的状态机制品，使系统可以自动产生结构化反馈，并将反馈纳入修正循环：

```text
<NL, STM_i> -> 诊断 / 场景反馈 -> 候选修正 -> 回归检查 -> 接受 / 拒绝 / 回滚 -> STM_{i+1}
```

该循环必须记录 rejected repair、振荡、不收敛、语义漂移和 转换器 attribution，不能只报告成功样例。

## 5. 任务定义

输入为自然语言需求 `NL` 与初始状态机 `STM_0`。输出为自动反馈驱动修正循环后的候选状态机 `STM_k`，以及每轮诊断、反馈、候选修正、接受、拒绝和回滚证据。

```text
输入：<NL, STM_0>
输出：<STM_k, 诊断台账, 场景台账, 修正台账, 接受/拒绝/回滚台账>
```

### 5.1 方法内范围

| 阶段 | 是否属于方法内 | 说明 |
|---|---:|---|
| 对 `STM_i` 做解析、语义、设计、场景诊断 | 是 | 产生结构化反馈 |
| 基于反馈生成候选修正 | 是 | 可以由 LLM 或确定性策略参与，但必须受冻结输入和检查门约束 |
| 对候选重新执行诊断、场景和回归检查 | 是 | 决定接受、拒绝或回滚 |
| 记录 rejected repair、振荡、不收敛 | 是 | 失败也是结果的一部分 |
| 在 `max_iterations` 或停止条件内选择当前最佳候选 | 是 | 不允许人工临时介入修正 run |

### 5.2 方法外范围

| 阶段 | 定位 | 记录要求 |
|---|---|---|
| `NL -> STM_0` 提示词生成 | seed construction | 记录提示词、模型、配置和来源；不作为主贡献 |
| prior artifact 转换为内部表示 | 转换器 / seed preparation | 记录转换损失、人工补全和归因；不计入修正循环收益 |
| 学生 / 人工初始建模 | seed source | 记录任务说明、参与者角色、允许工具与数据边界 |
| reference / adjudication | evaluation audit | 人类可参与，但不属于修正运行内方法 |

## 6. 人类角色边界

| 人类活动 | 允许性 | 是否属于修正运行内无人化循环 |
|---|---:|---|
| 设计 benchmark / seed registry | 允许 | 不属于 run 内 |
| 制作参考裁决 / 人工审计 | 允许 | 不属于 run 内 |
| 在某轮修正失败后手工改 `STM_i` 再继续 | 不允许 | 会破坏无人化修正定义 |
| 事后分析失败模式 | 允许 | 作为 evaluation / threats |

## 7. 停止、拒绝与回滚

候选修正不能只要“看起来更好”就接受。最低策略：

1. 若引入新的阻塞级诊断，拒绝候选。
2. 若冻结场景或回归检查退化，拒绝候选。
3. 若基于 NL 的裁决判定语义退化，拒绝候选。
4. 若多轮在同类候选间振荡，记录 oscillation 并停止或回滚到当前最佳。
5. 若超过 `max_iterations` 或预算，记录 non-convergence，不手工补救。

## 8. 贡献草案

| 贡献草案 | 当前证据状态 | 后续证据门 |
|---|---|---|
| 定义 `<NL, STM_0> -> STM_k` 的反馈驱动状态机修正任务 | 已由本文件冻结任务边界 | 写作时必须引用 seed、转换、评价门与真实修正证据，不可扩大为 `NL -> STM` |
| 提出无人化修正运行协议 | 当前仅定义边界 | 后续必须有真实循环、repair ledger、回归与接受 / 拒绝证据 |
| 操作化 Better STM，区分转换收益与修正收益 | 已由 Better STM 定义和评价门冻结 | 后续必须有同一 `STM_0` 对比、场景、诊断和裁决证据 |
| 将 prior artifact 重排为 seed source、转换压力、错误类型和有限对照 | 已有 seed / baseline registry | 后续正式实验前需冻结 eligibility |

## 9. 推荐术语

| 语义 | 中文推荐写法 | 英文必要写法 |
|---|---|---|
| 论文主任务 | 反馈驱动状态机修正 | feedback-driven state-machine repair / refinement |
| 状态机表示 | 语义增强、可机检、可执行状态机制品 | semantically enriched, machine-checkable state-machine artifact |
| 检查反馈 | 轻量形式化 / 静态诊断、语义诊断、场景仿真反馈 | lightweight diagnostics / scenario feedback |
| 修正循环 | 诊断-修正-回归-接受/拒绝/回滚协议 | diagnose-repair-regression loop |
| 结果目标 | 相对更优 STM | relatively better STM |

`fcstm` / `pyfcstm` / DSL 只可在方法实现、复现说明和 artifact appendix 中低调出现；不得进入标题、摘要或贡献列表。

## 10. 禁止或需降级的表达

| 高风险表达 | 安全替代 |
|---|---|
| 首个 / 最强 `NL -> STM` 方法 | 本文研究给定初始状态机后的反馈驱动修正任务 |
| 提出新 DSL | 使用语义增强、可机检、可执行的状态机制品作为实验载体 |
| 完整形式化验证 / model checking 保证正确 | 使用轻量形式化 / 静态诊断和场景仿真反馈发现并约束缺陷 |
| 自动修正一定提升质量 | 在预注册评价门下检验是否产生相对更优候选，并报告失败和不收敛 |
| baseline 不需要比较 | baseline 重排为 seed source、转换压力、有限对照和 related work |
| run record 是方法贡献 | run record 是内部实验审计和复现证据链，不写成论文贡献 |

## 11. 未闭合风险

| 风险 | 后续闭合方式 |
|---|---|
| 哪些 seed 可进入正式主实验仍需资格冻结 | R7 eligibility / protocol |
| 修正循环是否稳定有效尚未实证 | R6/R8 真实修正循环 |
| Better STM 是否成立尚无主结果 | 真实 `STM_0` vs `STM_k`、场景、诊断与人工/结构化裁决 |
| 转换和修正贡献容易混淆 | 三阶段归因：原始制品 -> 规范化 `STM_0` -> `STM_k` |

更多主张与证据门见 [claim_evidence_map.md](./claim_evidence_map.md)。
