Abstract — Product Families are gaining interest because of 
the increasing demand for customiza ble products. However, 
testing a Product Family is a difficult task, in special, for 
dependable products, in whic h the exception handling must 
also be well tested. Model-base d testing (MBT) can be useful 
for testing Product Families, in which a behavior model can be 
obtained from the requirements; this model being used for 
automatic test case generation. The use of MBT, however, 
requires a good modeling expertise from practitioners, as they 
are mainly used with informal, textual descriptions of the 
requirements. In this paper, we show how to apply a use-case 
modeling approach that allows the automatic extraction of a 
state machine model for a product. Use cases are described in a 
restricted format that comprises not only the representation of 
commonalities and variabilities but also the specification of 
exception handling for fault-tolerant behavior. 
Keywords—use case; state  machine; product family; 
exception handling 
I. INTRODUCTION  
The term Product Family (PF) or Software Product Line 
(SPL) refers to a set of similar software products that share a 
common set of features. These products are developed from 
a common set of core assets in a prescribed way [1] . The 
development of a PF presents some new challenges for 
Software Engineering. First, it was necessary to define two 
processes: Domain Engineering (DE)  and Application 
Engineering (AE) . The former is concerned with the 
definition of common and vari able parts, as well as the 
design of an adaptable architecture and the development of 
reusable components. The AE, on the other hand, is 
concerned with the development of an individual  product. 
The user selects the required features that were defined 
during the DE process. Based on the selected features, the 
architecture is tailored for the product, and the necessary 
reusable components are selected. Another challenge is 
relative to testing: how to be certain that requirements are 
satisfied by a given new product ? [2] Since there is a high 
number of potential products in a PF, there is also a need to 
automate product testing.  
Model-based testing (MBT) can be very useful for PF 
testing, in which that MB T provides a technique for 
generation of test cases using models extracted from 
software artifacts [3] . One key advantage of MBT is that test cases can be systematically gene rated from requirements 
represented by the model, in that way, automating test case 
design. A key element for the use of a MBT approach is the 
model used for software behavior description (e.g. finite state 
machines). MBT requires solid modeling expertise from 
developers in order to build models that can be processed by 
a tool. Since our goal is on test models from use cases 
representing product-speci fic behavior, the question is how 
to allow users that are not fami liar with modeling to derive 
test models for a product that takes into account the 
exception handling mechanisms? 
Use cases (UCs) are used to elicit and document 
customer requirements.  Deriving Analysis Models from UCs 
is traditionally a manual process, guided by some heuristics 
[4]. However, there are some proposals to help the automatic 
model derivation from use cases, such as class models [5]  or 
state machine models [6][7] , but they consider only the 
development of single systems and do not take into account 
explicitly the exception handling mechanisms. 
In this paper, we present an approach to extract state 
machine models, more specifically, Extended Finite State 
Machines (EFSMs), representing product-specific behavior. 
The extraction is based on use case descriptions developed 
during the Requirements phase. These use cases must be 
described using a structured language notation. We also 
added exceptional and variation flows; the former are used to 
handle exceptional behavior in the software systems whereas 
the variation flows are used to handle variability when 
specifying a PF. As a proof-of-concept, we are implementing 
a prototyping tool, MA RITACA, which applies natural 
language processing techniques to extract the initial version 
of a product behavior model.  
The remainder of the paper is organized as follows. 
Section II presents some related works. Section III shows the 
artifacts used in our testing-orien ted modeling approach. 
Section IV approach to generate state machine from use case 
descriptions, followed by a br ief description of the tool in 
Section V. Finally, Section VI concludes the paper.

got inspiration from  the FeDRE (Feature-Driven

specification of PF [12] . Although this approach is only 
concerned with the requirements phase, and not with testing,

developers as well as for testers. Our contribution to the PF 
testing domain is the automat ic generation of a product test

III. TEST ARTEFACTS  
Our goal is a model-based test case generation method 
for product-specific testing. The method is based mostly on 
Unified Modeling Language (UM L) notations, given their 
popularity in practice. More specifically, it uses, from UML: 
use cases, class diagrams, and state machine models. In 
addition, the method also uses non-UML models to specify 
variability. One of such models is the Feature model  (FM) 
[13], which is used to represent common and variable 
features in SPLs. The FM is a diagram showing the features, 
their relationships as well as  the constraints among them. 
The Product map (PM) and Traceability matrix  (TM) [12] 
were also adopted in our method. The PM relates products to 
features, indicating which features are used by the products 
that are foreseen. The TM relates features to use cases. It is 
not only useful during the deve lopment of a new product, as 
it shows which use cases are required by which features, but 
also helps when requirements evolve, as each change in the 
FM will be traced to the use cases and vice-versa. In the 
following, we describe in more details the Use Case 
modeling, as it is key for state machine model extraction. 
In UML a Use Case Model is composed by a Use Case 
Diagram (UCD) and a Use Case textual specification 
(UCTS)  [14].  Use cases describe an external view of the 
system, i.e., they show how the system interacts with its actors, which can represent people, external systems or 
hardware devices [4]. When Use Cases are utilized to model 
PF, it is common to extend them to  cope with variability. In 
the UCD, the Use Cases can be  labeled with stereotypes such 
as [15]: <<kernel>> for those that are common to all 
products of the PF; <<optional>> for those required for some 
products but not all, and <<alternative>> when different 
versions of a use case are required by different products.  
The UCD is complemented with the UCTS, which 
describes each Use Case (UC) in the diagram in a textual 
form. UML provides no specific notation for specifying 
UCTS, so it is common practice to adopt some template. The 
one we adopt is based on RUCM approach  [10] because it 
uses a restricted format to write UCTS in order to facilitate 
automated UC analysis necessary to extract the behavior 
models. RUCM was intended for a single system, thus, we 
extended it to cope with variab ility. We also made explicit 
the specification of exceptional behavior [16] .  
Fig. 1 shows an example of a use case documented 
according to this structured notation. The example describes 
the Open the Door  use case of a Microwave oven system 
[15]. The fields: brief description, precondition, primary and 
secondary actors, dependency and generalization are not 
further explained here, for the sake of space; they are 
common to many templates and the description given in the 
table is enough to understand their meaning. The fields Use 
Case Type  and Associated Feature  are intended to handle 
variability when specifying a PF. The Use Case Type  
specifies whether the use case is kernel (mandatory), 
optional, or alternative [15]. The Associated Feature  field 
specifies the name of the feature(s) associated with the use 
case. The Feature Cardinality  specifies, (for alternative 
features) whether it can have one or more variation points in 
the use case. Variability can also  be specified inside a UC, 
using variation points, which identify locations in which 
variation occurs. For the moment,  this is the kind of 
variability considered by the use of variation flows. In the 
remainder of this section, we focus the discussion on the 
description of the use case flows, as they are essential for 
model extraction. 
Getting inspiration from [7] , we describe a UC as a tuple 
<Header, Pre, Flows > in which Header was described 
above. Pre is a set of pre-conditions and Flows  refer to the 
set of UC’s flows. Each flow in Flows  is also represented by 
a tuple < Type, Steps, Post >. Type  contains the type of the 
flow, which can be one of the following: (i) basic  (or main) 
flow represents the “normal flow” of steps for a use case. A 
use case can only have one basic flow; (ii) alternative flow , 
representing conditional steps that are performed in place o f 
one or more steps in another flow (designated as reference 
flow, or RF), after which the UC c ontinues to be executed; 
(iii) exceptional flow , representing error conditions, and are 
further divided into recoverable  and failure flows [16]. Both 
flows specific what the system does when a failure occurs in 
a RF step. The difference between them is that after a 
recoverable flow execution continues, whereas in a failure 
flow execution is aborted; (iv) variant  flows specify steps 
executed for selected features of a PF. Non-basic flows can 
also be categorized as specific  (refers to a single step in a

flow specification ends with a set of post-conditions ( Post) 
that must hold when the flows terminate. 
Steps  represent a set of steps in the flow and are also 
represented by a tuple < SNumber, Cond, Oper >. SNumber  
is the step number. The steps in a flow are numbered 
sequentially; this implies that each step is completed before 
the next one is started. Cond  is a set of conditions that must 
hold for the step to be possible; it may be empty. Conditions 
are expressed using RUCM keywords: IF-THEN-ELSE-
ELSEIF-ENDIF  or VALIDATES THAT.  In order to 
consider variability when specifying a PF, we further 
introduced the keyword IF-OPTION-THEN-ELSE-
ELSEIF-ENDIF , to specify an alternative or optional 
feature in a UC that must be selected for a given variation 
flow to be considered. Fig.1, line 35 shows an example of 
utilization of this keyword. Oper  is an action which 
describes an interaction between : (i) the primary actor and 
the system (e.g. Fig. 1, line 13) ; (ii) the system with itself 
(e.g., modifying its internal state, as in Fig. 1, line 14) or (iii) 
the system with an actor (e.g., sending a result to an actor). 
RUCM proposes restriction rules  on the use of natural 
language, such as: actions should be written in the present 
tense; verbs should be in active voice, among others [5]. In 
order to ease the processing by a tool, we also add that 
actions should have the form “The <actor> does something” 
or “The system does something”.  
The exception flows are triggered when there is a 
violation of the condition associated with the VALIDATE 
THAT  keyword. Recoverable  flows terminate with a 
RESUME STEP  keyword. This indicates that the exception 
flow goes back to the reference flow, meaning that exception 
handling is well succeeded. A failure  flow, on the other 
hand, terminates with an ABORT  keyword indicating that 
the system execution can no longer continue. 
IV. APPROACH TO GENERATE STATE MACHINE FROM USE 
CASE DESCRIPTION  
 Our approach aims to generate a state-machine model 
representing sequential dependencies among UCs [6][2]. In 
general, these dependencies are not exp licitly identified in 
textual descriptions. They can be made explicit using pre- 
and post-conditions. The model to  derive is a subset of UML 
in the form of an extended finite state machine, which can be 
defined as M = < V, in itial, start, final, I, O, CV, T>. V is a 
finite set of vertices, with initial and final  representing the 
initial pseudo-states and fi nal state respectively. The start  
state is proposed by Yue et al . [8] to represent the starting 
state. Except for initial and final , all the other states are 
represented by invariants, which are the pre- and post- 
conditions of the UC. Two states w ith the same invariants are 
considered identical. I is a finite set of input events, which 
are represented by UC, as those generally are caused by a 
request from an actor. O represents a finite set of output 
actions, representing either an included or extended use case 
or else the outputs generated from  the system to an actor. CV 
represents a finite set of context variables used in state 
invariants or in guards. T represents a finite set of transitions. By default, there is an initial transition from the initial 
pseudo-state to the start state, as UML requires that every 
state diagram should have su ch a transition. This transition is 
not triggered by an even t, but can have an action associated 
with it. There is also a final transition, to the final state. The 
other transitions represent possible flows among the UCs. 
Fig. 1.  Use case Open the door  
Since states represent pre- and post- conditions, there are 
as many post-conditions (states) and transitions as flows for 
a given UC. The guards differentiate the transitions from the 
origin to a destination state for a given UC. Guards 
correspond to the Cond  set that precedes each non-basic 
flow. In that way, exception flows are represented by a 
transition whose guard corresponds to the case in which the 
condition specified  with the VALIDATE THAT  keyword 
is not satisfied, combined with an y other conditions in the 
flow. The destination state of the transition(s) corresponds 
to the exception flow  post-condition(s). An ABORT  leads 
to a final state. For a PF, it is necessary to consider the 
variation flows. Variation flows are characterized by the IF-
OPTION-THEN-ENDIF keyword in a flow of a UC, that 
we designate here as UCv. When the feature (indicated after 
the OPTION  word) is selected for the product being 
modeled, a new state is created with the variation flow’s 
post-condition. Then, a new transition is added from the 
origin state of UCv to the newly created states. The guard of 
this transition corresponds to the step’s Cond set.  
It is worth noting that the extracted state machine 
contains only simple states, i .e., it has no regions and no

V. SUPPORTING TOOL  
In order to show the feasib ility of the approach, we are 
implementing a prototype  tool, MARITACA (state 
MAchine geneRatIon from TextuAl use CAses). Based on 
our previous experience with  TXT2SMM prototype [17], 
which extracts state machine models from a narrative text, 
MARITACA applies Natural Language Processing (NLP) 
techniques, more specifically, a Part-of-Speech tagger, 
which processes the words in a text and attaches to each a 
tag according to its grammatical category (noun, adjectives, 
verbs and so on). The tagg ed text is used to extract patterns, 
that is, word sequences that can be assigned to elements of 
the state machine: triggers, guards and variables. The 
assignment of the extracted patterns to these elements is 
based not only on grammatic al information but also on the 
template structure. Moreover, the MARITACA tool, using 
the information available in the traceability matrix [12], let 
users select the desired features for a given product. Then 
the tool selects the use cases to analyze based on this 
information. A sketch of the initial extraction from 
MARITACA is presented in Fig 2.

VI. CONCLUSIONS AND FUTURE WORK  
We present the generation of state machine models from 
use cases in the context of model-based test case generation 
for a PF. The state machines are product-specific and 
represent control dependencies among UCs. Our work aims 
at helping not only testers bu t also domain and requirements 
analysts in the specification of PFs. A prototype tool is 
under development, to support th e approach. The tool uses a 
set of rules and natural language processing techniques to 
extract the state machine from the restricted description of 
UCs. This paper presents an ongoing work, and hence, 
improvements to the tool are envisaged, as well as the 
application of the method to real world product families.
