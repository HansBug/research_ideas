## 2. 关键定义与术语

为了让 method section 起稿时口径统一，先把后续高频术语固定下来：

1. **Agent Loop**（本研究新造的复合概念）
   - rationale：现有 LLM-based modeling 论文 [llms_emp / structure_event] 普遍是 single-prompt 或 two-step prompting，少有显式把 deterministic verifier 和 LLM judge 同时接入闭环的 architecture。
   - 操作化：由 $k$ 个 LLM agent（`SpecExtractor`、`Modeler`、`Repair`）和 $m$ 个 feedback source（`ParseFeedback`、`SemanticFeedback`、`SimFeedback`、`JudgeFeedback`）组成的迭代图，迭代上限 $N=3$。
2. **Feedback Source**（领域已有定义 + 改动）
   - 既有定义（reflexion / self-refine 系列）：单一 evaluator 输出 reward 或 critique。
   - 本研究改动：每个 source 输出**结构化字段**而非自然语言批评，且 source 之间通过 fixed schema 合并，便于 Repair agent 定向修复。
3. **Speculative Validation**（直接借用 `pyfcstm` 文档表述）
   - 定义来自 `pyfcstm.simulate` 文档：执行 transition 前先模拟看能否到达 stable stoppable state，否则回滚。
   - 在本研究中作为 SimFeedback 的核心 mechanism，是 Umple/SCXML 等通用 statechart runtime 不直接提供的差异化点。
4. **Intrinsic Metrics**（本研究新造定义）
   - rationale：[sources/](../sources/) 的控制系统样本没有 canonical reference STM，传统 component-level F1 无法计算。
   - 操作化：`ParseRate`、`SemValidRate`、`SimRate`、`ReachabilityRate`、`JudgeScore` 共 5 个不依赖 reference 的可计算指标。
   - sprint 阶段用法：Path 2 的主决策信号。
   - 待方向定后补：用手工 reference 子集做 intrinsic-F1 Pearson 相关性验证（calibration），把 intrinsic 升级为有可信度桥的 evaluation 协议。

## 3. 方法骨架

### 3.1 整体架构

```text
NL requirement (from sources/ STM.md §2)
      |
      v
  [SpecExtractor]  ----+    LLM agent (Claude Opus 4.7)
      |                |    out: structured spec
      v                |        (states / events / vars /
  [Modeler]            |         transitions / hierarchy)
      |                |    LLM agent
      v                |    out: pyfcstm DSL text
  current_model        |
      |                |
      v                |
  +---+---------------+----------------+
  |   Feedback Sources (parallel)      |
  |  - ParseFeedback   (deterministic) |
  |  - SemanticFeedback (deterministic)|
  |  - SimFeedback     (deterministic, |
  |        speculative + witness)      |
  |  - JudgeFeedback   (LLM judge from |
  |        project_ex1 ExpertReview)   |
  +---+--------------------------------+
      |
      v
  structured_feedback (JSON, merged)
      |
      v
  [Repair]    LLM agent
      |       in: (current_model, feedback)
      v       out: new pyfcstm DSL text
  next_model  --> 回到 Feedback Sources, iterate N=3 rounds
      |
      v
  final_model + execution_trace + judge_record
```

### 3.2 三类反馈源的具体接入点

| Feedback Source | pyfcstm 入口 | 输出 schema 核心字段 |
| --- | --- | --- |
| Parse | `pyfcstm.dsl.parse_with_grammar_entry(dsl, "state_machine_dsl")` | `{ok, line, col, expected_tokens, got, snippet}` |
| Semantic | `pyfcstm.model.parse_dsl_node_to_state_machine(ast)` | `{ok, missing_states, dangling_transitions, undefined_vars, type_mismatches}` |
| Sim | `pyfcstm.simulate.SimulationRuntime(sm).run_until_stable()` + topology API | `{ok, unreachable_states, deadlocks, witness_paths, safety_limit_hits}` |
| Judge | `project_ex1.src.expert_review.agent.ExpertReviewAgent` | `{rubric_scores: {coverage, fidelity, structure, executability, safety}, evidence_spans, overall}` |

### 3.3 与 Umple 的差异化在 paper 中的呈现位置

差异化不在 §2 related work 中正面 PK，而在 §3 method 的 design rationale 子节里**自然落地**：

1. SimFeedback 的 witness path / speculative validation 是 pyfcstm runtime 直接给的，Umple 要外接 NuSMV/Alloy 才能做等价检查（成本明显更高）。
2. 因此选 pyfcstm 不是"我们的 DSL 比 Umple 强"，而是"在 agent loop 反馈密度场景下，pyfcstm 的工具链更接近 zero-glue feedback"。
3. 落到一句话定位：

> We chose `pyfcstm` as the target formalism not because it generalizes Umple, but because its runtime exposes parse / semantic / simulation / reachability signals through a single Python API, which makes per-iteration feedback in an LLM agent loop cheap and uniformly structured.

完整 Umple rebuttal 口径继续以 [2026-04-14 讨论稿](./2026-04-14-23-03-54-AI-讨论-pyfcstm作为LLM建模论文目标形式的必要性与Umple-rebuttal口径.md) §7 为准。

## 4. 实验 protocol（Decision-Sprint 版）

### 4.1 决策准则（**参考信号 + 用户拍板**，Claude 不自动判定）

sprint 末 Phase 6 时，Claude / agent **不擅自决策**；而是把 Path 1 / Path 2 的全部 raw 数据 + 下表信号判定整理成完整汇报，**最终方向由用户拍板**。

下表的阈值（+10pp / +20pp）是 sprint 开工前的**先验经验值**，仅作为信号强度 anchor，**不作为自动判定逻辑**：

| 情景 | Path 1 信号 (F1 lift) | Path 2 信号 (intrinsic lift) | 信号倾向（供参考） |
| --- | --- | --- | --- |
| S1 硬刚信号强 | $\ge +10$pp | $< +15$pp | 倾向硬刚 |
| S2 差异化信号强 | $< +5$pp | $\ge +20$pp | 倾向差异化 |
| S3 双强 | $\ge +10$pp | $\ge +20$pp | 倾向差异化（external validity tie-breaker） |
| S4 其他（含双弱、双中、临界） | — | — | 信号不显著，需用户结合 paper 卖点 / 投稿目标 / 后续工作量综合判断 |

其中 lift 定义：

1. Path 1 lift = `agent_loop A4 macro-F1` $-$ `single-prompt A0 macro-F1`
2. Path 2 lift = 5 个 intrinsic 指标的均值 lift（`A4 mean(5 metrics)` $-$ `A0 mean(5 metrics)`，按百分点）

**Phase 6 完整汇报必须给到用户的信息**（Claude 整理但不下结论）：

1. Path 1 raw 表：7 类组件 P/R/F1 lift $\times$ 每个 case + macro-F1 lift
2. Path 2 raw 表：5 个 intrinsic lift $\times$ 每条 sources/ 样本 + JudgeScore lift
3. 信号判定：按上表把当前数据归到 S1/S2/S3/S4 哪一类
4. Claude 的方向建议 + rationale（写明依据，不强推）
5. 若选某一路后续 1-2 个月工作量预估对比表（含手工 reference 标注 / 剩余 ablation / cross-vendor 等推迟项各自的代价）
6. 已知 raw 数据的 confounders（GPT API 失败 fallback 样本、超 token limit 截断样本、parse error 直接 0 分的样本等）

**关键观察（决定 Path 2 学术合法性的 4 条）**：

1. **6 个 baseline 中，3 个已有 in-loop feedback**（#2 llms_emp / #3 IEC 61499 / #6 ttool-ai）。"我们 first to do in-loop feedback" **不成立**。
2. **没有任何 baseline 同时做 (a) parse + (b) semantic + (c) runtime simulation + (d) reachability witness + (e) LLM judge 五路并列的反馈**。llms_emp 只 a+b（grammar/semantics rule-based check），ttool-ai 主要 a+b，IEC 61499 主要 c（simulation）但需人介入，Llama3 Umple 主要 c（execution）但只是 pass@k。
3. **没有任何 baseline 做 reachability witness in loop**。这是 pyfcstm `topology` 子包独有的能力。
4. **只有 IEC 61499 做控制系统且有 simulation feedback**，但它需要**人类评论介入**进行迭代精化。**fully automated control system NL-to-STM with multi-source verifier feedback 是空白**。

### 4.5 我们的核心创新点（v3 新增）

基于 §4.4 全景分析，我们与 baseline 的真正差异化在以下 6 点。Path 1 / Path 2 共用此 framing，paper §1 contributions 直接复用：

1. **In-loop multi-source deterministic verifier feedback**：把 pyfcstm 的 parse + semantic + simulation + reachability witness 作为 **4 路并列的 ground-truth 反馈源**接入 generation loop。覆盖 syntax / semantics / executability / coverage 4 个正交维度。其他 baseline 要么只做 1 路（llms_emp 的 grammar）、要么只做 post-hoc（ttool-ai 的 TTool simulator）。
2. **Fully automated no-human-in-the-loop**：IEC 61499 论文的迭代精化需要人类评论介入；ttool-ai 的评分含教师 rubric；我们的 agent loop fully automated 跑完 $N=3$ 轮。
3. **Reachability witness as structured prompt input**：pyfcstm `topology` 子包提供。witness 不只是 boolean "状态 X 不可达"，还含**从 initial state 到达失败原因的具体 transition 链**，作为 prompt 输入告诉 LLM 怎么修。这是其他 baseline 都不做的。
4. **Speculative validation from runtime**：pyfcstm `SimulationRuntime` 在 execute transition 前 speculatively validate 能否 reach stable stoppable state，否则回滚。其他 baseline 的工具链（PlantUML / Umple / Mermaid / TTool）不直接给。
5. **LLM-as-judge as in-loop semantic feedback (not standalone evaluator)**：借 [project_ex1](../../project_ex1_llm_judge_for_stm/) 的 `ExpertReviewAgent` 作为 5 维 rubric semantic feedback，与 deterministic verifier 并列。所有 baseline 都不把 LLM judge 用作 in-loop feedback（ttool-ai 的反馈是 JSON/syntax，不是 LLM judgment）。
6. **Reference-free intrinsic + judge evaluation protocol**：所有 baseline 评测都假设 ground truth STM 存在。控制系统真实场景下不存在 canonical reference STM（同一需求可对应多个等价 STM），ref-based F1 在 construct level 就不成立。我们提出 5 个 intrinsic 指标 + judge rubric，**这一条本身可作为独立 contribution 发表**。

### 4.6 5 个 Intrinsic 指标定义

1. `ParseRate` = 通过 `pyfcstm.dsl.parse_with_grammar_entry` 的样本比例
2. `SemValidRate` = 通过 `pyfcstm.model.parse_dsl_node_to_state_machine` 的样本比例
3. `SimRate` = `SimulationRuntime` 至少能执行 1 个完整 cycle 且不触发 safety limit（1000 steps / 64 stack depth）的样本比例
4. `ReachabilityRate` = 模型所有定义状态中非 unreachable 状态比例的样本均值
5. `JudgeScore` = `ExpertReviewAgent` rubric 总分（0-1）

2. 三件套环境变量：`LLM_ENDPOINT` + `LLM_API_KEY` + `LLM_MODEL`（详见仓库根 `.env`，已 gitignore）
3. **切换模型只改 LLM_MODEL + 重新 source .env，代码不动**
4. **代码绝不直接读 .env 文件**，只从 `os.environ` 读；运行前必须 shell `source .env`
5. method/gpt_client.py 是 sprint 中唯一允许实例化 OpenAI client 的位置；所有 agent / baseline replication 都 inject 这个 client，不重复造轮子

成本估算：

1. 单次 A4 full loop $\approx$ 1 spec + 1 model + (parse + sem + sim + judge) $\times$ 3 + 1 repair $\times$ 2 $\approx$ 10 LLM calls
2. Sprint 总 calls $\approx$ (16 + 40) $\times$ ((1 baseline call) + (10 A4 calls)) / 2 = 56 $\times$ 5.5 $\approx$ 308 主线 calls
3. **token 不缺，不熔断**；checkpoint 落盘避免长跑中断丢数据

### 4.8 Sprint 阶段不做的事（**显式声明**）

1. **不复现** llms_emp 两阶段框架 / ttool-ai 自动反馈循环 / IEC 61499 仿真精化等 in-loop feedback baseline（sprint 只与 structure_event Hybrid 对照；其他作为方向定后 paper 阶段补充工作）
2. Ablation 表 5 配置（A0/A1/A2/A3/A4）不全跑，**只跑 A0_strong 和 A4_ours**；A1/A2/A3 留给方向定后 paper 阶段做 ablation
3. 手工 reference 标注（原 Track B 10 条）**推迟**；如果决策走差异化，再用 4-5h 标注
4. Cross-vendor sanity (Opus 4.7) **推迟**
5. Pearson(intrinsic, F1) calibration 分析**推迟**（依赖 Track B）
6. $N=3$ vs $N=5$ ablation **推迟**
7. sources/ 30 条全量扩展 **推迟**（sprint 20 条够出决策信号）

## 6. 关键风险与回退

| 风险 | 触发条件 | 回退动作 |
| --- | --- | --- |
| pyfcstm 仓库 main 与 PyPI 版本不一致 | `pip install pyfcstm` 装上的 API 与 main 分支不同 | 改用 `pip install -e ~/oo-projects/pyfcstm/` 直接装 main 源码 |
| `SimulationRuntime` 需要 abstract handler 才能跑 | smoke 时报缺 handler | 用 mock handler 全返回 no-op，sim 仅检 reachability 不验业务逻辑 |
| LLM 完全写不出合法 pyfcstm DSL | Phase 1 smoke A0 ParseRate $< 30\%$ | few-shot 加到 5 个 example；仍不行把 DSL 简化子集写进 prompt 作为 grammar reference |
| sources/ 20 条选样过偏 | 全是简单 FSM 或全是 HSM | 提前按 3 桶分层抽样硬约束（FSM 6 / EFSM 8 / HSM 6），且**全部限定 T0** |
| Path 1 baseline T0 子集 $< 5$ 条 | structure_event 8 cases 中无时间约束样本不足 | 补 llms_emp stm 38 的 T0 子集；若仍不足 5 条，扩 llms_emp 全 98 条中可类比 stm 任务的 T0 样本 |
| ex1 ExpertReviewAgent 接入有 schema breaking | adapter 写半天还跑不通 | A4 暂用简化版 judge（单 prompt rubric scorer），完整 ExpertReviewAgent 留给方向定后 |
| LLM_ENDPOINT 失败 / rate limit | Phase 4/5 跑实验时大量 5xx | 改 .env 中 `LLM_MODEL` 到次选模型（如 gpt-5.4），重新 `source .env` 后继续；记录哪些样本用了 fallback；**不在同一 sprint 内换 vendor**（避免数据干扰决策信号） |
| `.env` 未 source / 环境变量缺失 | 跑实验时 KeyError on `os.environ["LLM_ENDPOINT"]` | shell 跑 `source .env` 后重新执行；这是 Phase 0 自检必须 verify 的 |
| 决策准则 S4 双弱 | Path 1 lift $< +5$pp **且** Path 2 lift $< +15$pp | 按 §4.1 用户决定：**选 lift 稍高的一路起稿**，paper claim 收紧 + ablation 深做以补偿 |
| 30h 跑不完决策 | Phase 6 进入时已经 28h | `DIRECTION.md` 决策报告必交，`OUTLINE.md` 退化为关键字段填空，commit 保资产 |

## 10. 两路并行开发模式（v2 新增）

为了让 Path 1 (硬刚) 和 Path 2 (差异化) 真正能并行推进，sprint 实施采用 **git branch 隔离 + 共同基础在 main 上稳定** 的双轨开发模式。

### 10.1 共同基础（main 分支）

main 分支提供两路共享的：

1. `method/` 目录骨架（`agents/` / `feedback/` / `loop.py` / `schema.py` / `prompts/`）
2. pyfcstm 反馈源 wrappers（`feedback/parse.py` / `semantic.py` / `sim.py`）
3. ex1 judge adapter（`feedback/judge.py`）
4. 三个 agent prompt + Python wrapper（`agents/spec_extractor.py` / `modeler.py` / `repair.py`）
5. 数据准备脚本（sources/ T0 筛选 + 3 桶分层；structure_event T0 筛选；llms_emp stm T0 子集筛选）
6. GPT API client 封装（`method/gpt_client.py`）

这些工作两路都要用，因此**先在 main 上做好 Phase 0-3，再 fork 两个 branch 各自推 Phase 4-7**。否则两个 branch 会重复造同一个轮子，最后还要解 merge conflict。

### 10.2 Path 1 branch (`dev/path1-hard-comparison`)

专注硬刚路线的 evaluation：

1. 实验脚本 `method/run_path1.py`
2. 结果落 `reproduction/results/sprint_path1/`
3. 决策报告 `paper_v1/PATH1_REPORT.md`
4. 详细指引见 [paper_v1/PATH1_HARD_COMPARISON_GUIDE.md](../paper_v1/PATH1_HARD_COMPARISON_GUIDE.md)

### 10.3 Path 2 branch (`dev/path2-differentiation`)

专注差异化路线的 evaluation：

1. 实验脚本 `method/run_path2.py`
2. 结果落 `reproduction/results/sprint_path2/`
3. 决策报告 `paper_v1/PATH2_REPORT.md`
4. 详细指引见 [paper_v1/PATH2_DIFFERENTIATION_GUIDE.md](../paper_v1/PATH2_DIFFERENTIATION_GUIDE.md)

### 10.4 决策合流

两个 branch 跑完后**分别提 PR 但不合并**；由用户在合并前对两路 raw 数据做综合判断，选定方向后：

1. 选中路线的 branch 合并到 main
2. 未选中路线的 branch 保留作为 paper rebuttal 时 "we also tried X" 的证据
3. main 上启动正式 paper 阶段工作

### 10.5 新 session 接管点

任何新 Claude / codex session 进入对应 branch 后，按以下顺序读 file：

1. 本文件 [2026-05-26-15-30-00-AI-讨论-第一篇论文agent-loop闭环2日冲刺计划.md](./2026-05-26-15-30-00-AI-讨论-第一篇论文agent-loop闭环2日冲刺计划.md)（meta-level 路线规划与决策准则）
2. 对应路线指引 [PATH1_HARD_COMPARISON_GUIDE.md](../paper_v1/PATH1_HARD_COMPARISON_GUIDE.md) 或 [PATH2_DIFFERENTIATION_GUIDE.md](../paper_v1/PATH2_DIFFERENTIATION_GUIDE.md)
3. `method/STATUS.md`（如果已开工，查当前进度）
4. `reproduction/results/sprint_pathX/`（如果有部分结果，查已完成的样本）
