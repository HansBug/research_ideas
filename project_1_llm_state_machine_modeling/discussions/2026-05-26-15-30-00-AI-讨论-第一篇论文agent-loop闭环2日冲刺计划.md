## 2. 关键定义与术语

为了让 method section 起稿时口径统一，先把后续高频术语固定下来：

1. **Agent Loop**（本研究新造的复合概念）
   - rationale：现有 LLM-based modeling 论文 [llms_emp / structure_event] 普遍是 single-prompt 或 two-step prompting，少有显式把 deterministic verifier 和 LLM judge 同时接入闭环的 architecture。
   - 操作化：由 $k$ 个 LLM agent（`SpecExtractor`、`Modeler`、`Repair`）和 $m$ 个 feedback source（`ParseFeedback`、`SemanticFeedback`、`SimFeedback`、`JudgeFeedback`）组成的迭代图，迭代上限 $N=3$。
2. **Feedback Source**（领域已有定义 + 改动）
   - 既有定义（reflexion / self-refine 系列）：单一 evaluator 输出 reward 或 critique。
   - 本研究改动：每个 source 输出**结构化字段**而非自然语言批评，且 source 之间通过 fixed schema 合并，便于 Repair agent 定向修复。
3. **Speculative Validation**（直接借用 `pyfcstm` 文档表述）
   - 定义来自 `pyfcstm.simulate` 文档：执行 transition 前先模拟看能否到达 stable stoppable state，否则回滚。
   - 在本研究中作为 SimFeedback 的核心 mechanism，是 Umple/SCXML 等通用 statechart runtime 不直接提供的差异化点。
4. **Intrinsic Metrics**（本研究新造定义）
   - rationale：[sources/](../sources/) 的控制系统样本没有 canonical reference STM，传统 component-level F1 无法计算。
   - 操作化：`ParseRate`、`SemValidRate`、`SimRate`、`ReachabilityRate`、`JudgeScore` 共 5 个不依赖 reference 的可计算指标。
   - sprint 阶段用法：Path 2 的主决策信号。
   - 待方向定后补：用手工 reference 子集做 intrinsic-F1 Pearson 相关性验证（calibration），把 intrinsic 升级为有可信度桥的 evaluation 协议。

## 3. 方法骨架

### 3.1 整体架构

```text
NL requirement (from sources/ STM.md §2)
      |
      v
  [SpecExtractor]  ----+    LLM agent (Claude Opus 4.7)
      |                |    out: structured spec
      v                |        (states / events / vars /
  [Modeler]            |         transitions / hierarchy)
      |                |    LLM agent
      v                |    out: pyfcstm DSL text
  current_model        |
      |                |
      v                |
  +---+---------------+----------------+
  |   Feedback Sources (gated cascade) |
  |  - ParseFeedback   (deterministic) |
  |  - SemanticFeedback (deterministic)|
  |  - SimFeedback     (deterministic, |
  |        speculative + scenariogen  |
  |        self-managed 6-mutation     |
  |        coverage as bug probes)    |
  |  - [JudgeFeedback   — sprint 跳过, |
  |        Phase H, hook 已留]        |
  +---+--------------------------------+
      |
      v
  structured_feedback (JSON, merged)
      |
      v
  [Cascaded Repair]   LLM agent
      |       4 个 fix sub-prompt
      |       (parse/sem/sim/judge占位)
      v       按 earliest-failing channel 路由
  next_model  --> 回到 Feedback Sources, iterate N=3 rounds
      |
      v
  final_model + execution_trace
```

### 3.3 与 Umple 的差异化在 paper 中的呈现位置

差异化不在 §2 related work 中正面 PK，而在 §3 method 的 design rationale 子节里**自然落地**：

1. SimFeedback 的 witness path / speculative validation 是 pyfcstm runtime 直接给的，Umple 要外接 NuSMV/Alloy 才能做等价检查（成本明显更高）。
2. 因此选 pyfcstm 不是"我们的 DSL 比 Umple 强"，而是"在 agent loop 反馈密度场景下，pyfcstm 的工具链更接近 zero-glue feedback"。
3. 落到一句话定位：

> We chose `pyfcstm` as the target formalism not because it generalizes Umple, but because its runtime exposes parse / semantic / simulation / reachability signals through a single Python API, which makes per-iteration feedback in an LLM agent loop cheap and uniformly structured.

完整 Umple rebuttal 口径继续以 [2026-04-14 讨论稿](./2026-04-14-23-03-54-AI-讨论-pyfcstm作为LLM建模论文目标形式的必要性与Umple-rebuttal口径.md) §7 为准。

## 4. 实验 protocol（Decision-Sprint 版）

### 4.1 决策准则（**参考信号 + 用户拍板**，Claude 不自动判定）

sprint 末 Phase 6 时，Claude / agent **不擅自决策**；而是把 Path 1 / Path 2 的全部 raw 数据 + 下表信号判定整理成完整汇报，**最终方向由用户拍板**。

下表的阈值（+10pp / +20pp）是 sprint 开工前的**先验经验值**，仅作为信号强度 anchor，**不作为自动判定逻辑**：

| 情景 | Path 1 信号 (F1 lift) | Path 2 信号 (intrinsic lift) | 信号倾向（供参考） |
| --- | --- | --- | --- |
| S1 硬刚信号强 | $\ge +10$pp | $< +15$pp | 倾向硬刚 |
| S2 差异化信号强 | $< +5$pp | $\ge +20$pp | 倾向差异化 |
| S3 双强 | $\ge +10$pp | $\ge +20$pp | 倾向差异化（external validity tie-breaker） |
| S4 其他（含双弱、双中、临界） | — | — | 信号不显著，需用户结合 paper 卖点 / 投稿目标 / 后续工作量综合判断 |

其中 lift 定义：

1. Path 1 lift = `agent_loop A4 macro-F1` $-$ `single-prompt A0 macro-F1`
2. Path 2 lift = 5 个 intrinsic 指标的均值 lift（`A4 mean(5 metrics)` $-$ `A0 mean(5 metrics)`，按百分点）

**Phase 6 完整汇报必须给到用户的信息**（Claude 整理但不下结论）：

1. Path 1 raw 表：**5 类组件** P/R/F1 lift $\times$ 每个 case + overall-F1 lift（v4 修订：5 类组件而非 7 类，去 parallel_regions / history_states）
2. Path 2 raw 表：**4 个 intrinsic** lift $\times$ 每条 sources/ 样本（v4 修订：4 intrinsic 而非 5，去 JudgeScore — sprint 跳 Phase H）
3. 信号判定：按上表把当前数据归到 S1/S2/S3/S4 哪一类
4. Claude 的方向建议 + rationale（写明依据，不强推）
5. 若选某一路后续 1-2 个月工作量预估对比表（含手工 reference 标注 / 剩余 ablation / cross-vendor 等推迟项各自的代价）
6. 已知 raw 数据的 confounders（GPT API 失败 fallback 样本、超 token limit 截断样本、parse error 直接 0 分的样本等）

**关键观察（决定 Path 2 学术合法性的 4 条）**：

1. **6 个 baseline 中，3 个已有 in-loop feedback**（#2 llms_emp / #3 IEC 61499 / #6 ttool-ai）。"我们 first to do in-loop feedback" **不成立**。
2. **没有任何 baseline 同时做 (a) parse + (b) semantic + (c) runtime simulation + (d) reachability witness + (e) LLM judge 五路并列的反馈**。llms_emp 只 a+b（grammar/semantics rule-based check），ttool-ai 主要 a+b，IEC 61499 主要 c（simulation）但需人介入，Llama3 Umple 主要 c（execution）但只是 pass@k。
3. **没有任何 baseline 做 reachability witness in loop**。这是 pyfcstm `topology` 子包独有的能力。
4. **只有 IEC 61499 做控制系统且有 simulation feedback**，但它需要**人类评论介入**进行迭代精化。**fully automated control system NL-to-STM with multi-source verifier feedback 是空白**。

### 4.5 我们的核心创新点（v4 修订 — 基于 pyfcstm main 分支真实能力 deep-dive）

> **v3 → v4 修订依据**：原 v3 §4.5 误以为 pyfcstm 有 `topology` 子包（实际只在 dev 分支才有），且完全没体现 pyfcstm/solver/ 内置 Z3 求解能力。2026-05-26 派 general-purpose agent 完成 pyfcstm main 分支 deep-dive 后纠正。

#### 4.5.1 pyfcstm 真实差异化能力清单（7 条 method differentiator，对比 Umple/PlantUML/Mermaid/SysML）

1. **Speculative DFS validation + safety limits + structured `SimulationRuntimeDfsError`**：runtime 自身在每个 cycle 入口对候选 transition 做轻量模型检查，bounded by 1000 步 / 64 层 / 结构+值签名剪枝；`SimulationRuntimeDfsError` 的 docstring 直接枚举 LLM 常见的病态 STM 模式（`pyfcstm/simulate/runtime.py:_validate_transition` / `_run_cycle_on_context`）
2. **Z3-backed solver layer (`pyfcstm/solver/`)**：在 model 层之内（无需 codegen）做 guard 可满足性、effect 符号执行、多解枚举（`solver/expr.py:expr_to_z3` + `solver/operation.py:execute_operations` + `solver/solve.py:solve`）
3. **Language-independent expression IR + 9 种 expr style + Jinja2 模板代码生成**：同一个 `Expr` 对象 4 件事（evaluate / round-trip / Z3-translate / 9-lang render，含 DSL/C/CPP/Python/Java/JS/TS/Rust/Go）
4. **DSL-native AOP + forced fault paths**：aspect actions `>> during before/after` 从 root→leaf→root cascade 每 cycle 注入；forced transition `!` 在模型层递归展开到所有 descendant substate（一行 declarative fault-recovery escape）
5. **Abstract action + ReadOnlyExecutionContext + `@abstract_handler`**：DSL 级声明 abstract 占位 + Python 反射注入 handler + frozen context + 两档错误处理（`raise / log` 把异常落到 `error_info` / `abstract_handler_errors`）
6. **4 种 event scope + DSL-native modular import**：local `::` / chain `:` / parent-relative `.` `..` / root-absolute `/` + `import "./sub.fcstm" as Sub { def * -> Sub_*; event Sub.x -> .x; }` 在模型层完整 inline + 循环引用检测 + 变量四种 mapping 模式
7. **Cycle-based execution + frame mode + history buffer + hot start**：与控制系统 tick 范式直接对应；hot start API 支持 scenario-specific 调试

完整 deep-dive 见 agent 研究报告（2026-05-26）。

#### 4.5.2 4 条 paper §1 contribution（**v4.1 修订**：原 v4 含 C5 "Four-level event scoping + DSL-native module composition"，用户反馈"太侧重工程，不构成 paper-level method contribution"，已删除。Path 1 / Path 2 共用 source of truth）

**C1 — In-loop deterministic feedback via speculative validation**

pyfcstm `SimulationRuntime` 每 cycle 入口的 deepcopy-snapshot speculative DFS validation，把"model check"从 offline batch 工件变成 **online repair signal**。任何会让 STM 陷入 dead-end（composite state init 全 guard false / pseudo state 链不停 / guard 互锁）的转换会被 reject + rollback，且 `SimulationRuntimeDfsError` 直接抛出可被 LLM agent 消费的诊断信息。Umple 的 generate-then-execute 不在 runtime 层做 dead-end 检测。

**C2 — Language-independent expression IR enables symbolic reasoning without code generation**

pyfcstm 的 `Expr` IR (`pyfcstm/model/expr.py`) 同时 evaluable / round-trippable / Z3-translatable / 9-lang renderable。agent loop 不离开 DSL 工具链就能拿到 **guard SMT satisfiability + symbolic effect propagation** 作为 feedback signal — Umple 的 host-language-bound guards 做不到这点。

**C3 — DSL-native aspect AOP + forced fault paths align with control-system idioms**

aspect actions `>> during before/after` 与 forced transitions `!` 是 Umple / PlantUML 没有 DSL 级对应物的原语，分别对应控制系统的"横切关注点 / 每周期 invariant 注入"和"强制安全失效路径"。

**C4 — Abstract action + read-only context decouples symbolic STM from physical effectors**

DSL 级 abstract action 占位 + Python 反射注入 handler + frozen context 让 LLM 在生成阶段不需要决定 deployment target；handler 在 runtime 注册，异常落到 structured field 供 agent 消费。Umple 的 lifecycle hook 是 host-language-bound，没有 DSL 级抽象层。

> **已删除的 C5**：原 "Four-level event scoping + DSL-native module composition support multi-channel control plants"（event scope 4 种语法 + modular import + 变量映射）虽然是 pyfcstm 真实差异化能力（见 §4.5.1 #6），但更偏 DSL 工程化能力而非 paper-level method contribution，已从 paper §1 contributions 列表中删除。其支撑的 multi-channel / multi-axis 控制器场景将在 paper §3.x example 子节中作为 pyfcstm 表达力 demonstration 出现，不进 §1 contributions。

#### 4.5.3 4 条 contribution 共同的 framing 句

> baseline (Umple/PlantUML/Mermaid/SysML) 的 STM 工具链把"语法 + 代码生成"做到了第一类公民，但**没有把 STM 当作可符号求解、可在 generation loop 中提供 grounding 的中间对象**。pyfcstm 把 (a) speculative validation runtime + (b) Z3 solver layer + (c) 跨语言表达式 IR + (d) DSL-native AOP/forced/abstract 等原语 **全部做在 DSL 工具链本体内**，使得 LLM agent loop 拿到的 feedback 不只是 "syntax error / unreachable state" 这种 boolean signal，而是 **runtime trace + DFS validation diagnosis + SMT satisfiability evidence + structured grounding** 这样的 multi-source 反馈。这是 paper 的 method core。

### 4.6 5 个 Intrinsic 指标定义

1. `ParseRate` = 通过 `pyfcstm.dsl.parse_with_grammar_entry` 的样本比例

3. `SimRate` = `SimulationRuntime` 至少能执行 1 个完整 cycle 且不触发 safety limit（1000 steps / 64 stack depth）的样本比例
4. `ReachabilityRate` = 模型所有定义状态中非 unreachable 状态比例的样本均值
5. `JudgeScore` = `ExpertReviewAgent` rubric 总分（0-1）

**统一 LLM 接入标准（v3 新增）**：

1. 所有 LLM 调用（含 baseline Hybrid 复现 + 我们的 agent loop spec/model/repair/judge/NL summary）走 **OpenAI-compatible proxy** `LLM_ENDPOINT`

3. **切换模型只改 LLM_MODEL + 重新 source .env，代码不动**
4. **代码绝不直接读 .env 文件**，只从 `os.environ` 读；运行前必须 shell `source .env`
5. method/gpt_client.py 是 sprint 中唯一允许实例化 OpenAI client 的位置；所有 agent / baseline replication 都 inject 这个 client，不重复造轮子

成本估算：

1. 单次 A4 full loop $\approx$ 1 spec + 1 model + (parse + sem + sim + judge) $\times$ 3 + 1 repair $\times$ 2 $\approx$ 10 LLM calls
2. Sprint 总 calls $\approx$ (16 + 40) $\times$ ((1 baseline call) + (10 A4 calls)) / 2 = 56 $\times$ 5.5 $\approx$ 308 主线 calls
3. **token 不缺，不熔断**；checkpoint 落盘避免长跑中断丢数据
