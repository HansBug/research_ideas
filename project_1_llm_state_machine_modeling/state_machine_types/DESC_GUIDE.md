# `state_machine_types/` 的 `desc.md` 编写规范

本文档用于规范 `project_1_llm_state_machine_modeling/state_machine_types/*/desc.md` 的写法。它服务于 `project_1` 的“状态机类型谱系”建设，目标不是写泛泛的论文摘要，而是产出一份能直接回答“这个形式主义是什么、能做什么、怎么构造、有什么生态、适合什么需求”的单篇分析。

## 1. 使用前提与阅读顺序

开始编写单篇 `desc.md` 前，必须先完成以下阅读顺序：

1. [README.md](./README.md)
2. [GUIDE.md](./GUIDE.md)
3. [SUMMARY.md](./SUMMARY.md)
4. 当前论文目录下的 `bibtex.bib`
5. 当前论文目录下的 `paper_content.txt`
6. 必要时核对 `paper.pdf`

## 2. `desc.md` 的核心目标

每篇 `desc.md` 至少需要回答以下问题：

1. 这篇论文聚焦的状态机族形式主义到底是什么。
2. 它的核心功能和表达对象是什么。
3. 它支持哪些关键特性，例如层次、并发、时间、数据、连续动态、随机性。
4. 它通常通过什么方式构造和承载，例如图形、DSL、XML、JSON、元模型或代码。
5. 它对应的基础设施成熟度如何。
6. 它更适合哪些场景，对需求输入有什么前提。
7. 它和 `project_1` 的“需求到状态机自动建模”主线是什么关系。

本 collection 对单篇 `desc.md` 还有一条额外收束：

1. 主体必须围绕**模型本体**与**标准/基础设施**展开。
2. 方法路线类论文只在能稳定佐证“该形式主义能做什么、如何构造、依赖什么基础设施”时才值得入库。
3. 若论文主要价值只是某个算法、流程或应用案例，而不是形式主义本身，则不要硬写成 `desc.md`。

## 3. 何时使用 `desc.md`

以下情况默认使用 `desc.md`：

1. 奠基定义论文。
2. 单一形式主义的语义说明或教程论文。
3. 围绕某一形式主义的标准、交换格式、DSL、元模型或工具链论文。
4. 主要贡献仍然落在单一形式主义，而不是跨多个形式主义比较的论文。
5. 方法路线论文，但它能够明显补出单一形式主义的能力边界、构造方式、标准载体或基础设施条件。

以下情况默认不使用 `desc.md`：

1. survey、review、mapping study、taxonomy 这类跨多个形式主义的综述条目。
2. 主贡献在跨形式主义比较，而不是单一形式主义本身的论文。
3. 应用/案例论文，即使其中使用了某种状态机模型，但正文不解释该模型本体。
4. 主要创新在算法、验证、综合或转换方法，但对形式主义本体、构造方式和基础设施没有新增可用证据的论文。

这些条目应改用 [SURVEY_GUIDE.md](./SURVEY_GUIDE.md) 生成 `survey.md`。

补充一条硬约束：

1. 若一篇候选论文不能稳定回答“它是什么、能做什么、怎么构造、依赖什么基础设施”中的核心问题，就不应正式立成 `desc.md` 条目。

## 4. 标题与总格式

### 4.1 文件标题

文件开头默认使用一级标题：

```markdown
# 中文标题 / English Title
```

规则如下：

1. 优先使用“中文标题 / 英文标题”的双语格式。
2. 若论文没有官方中文标题，可以给出克制、准确的中文翻译。

### 4.2 一级章节顺序

除非材料极端特殊，默认一级章节顺序应为：

1. `## 基本信息`
2. `## 简报`
3. `## 形式主义定义与核心对象`
4. `## 关键特性`
5. `## 构造方式与承载格式`
6. `## 配套基础设施`
7. `## 适用场景与需求前提`
8. `## 与相邻形式主义的关系`
9. `## 与本研究的关系`
10. `## 重要的相关工作`
11. `## 文献分类总结`

## 5. `## 基本信息` 的固定写法

该章节默认使用短条目列表，至少包含以下字段：

1. `标题`
2. `中文标题`
3. `作者`
4. `发表`
5. `DOI`
6. `链接`
7. `形式主义`
8. `主类`
9. `描述客体`
10. `所属领域`
11. `论文角色`

紧接着必须显式写出两项获取信息：

1. `工具/实现获取方式`
2. `标准/格式获取方式`

若原文没有明确给出公开工具、标准或仓库入口，必须如实写“原文未提供”。

## 6. `## 简报` 的固定写法

简报是高密度概览区，必须至少回答以下五个问题：

1. 这个形式主义主要描述什么对象。
2. 它最核心的表达能力是什么。
3. 它通常如何构造和落地。
4. 它依赖什么关键工具或标准。
5. 它最适合什么场景。

如果原文含有大量方法流程、实验设计或应用案例，这一章只保留与形式主义能力和基础设施直接相关的部分，不展开无关细节。

该章节推荐使用如下固定小结构：

1. 一段总述
2. `- 形式主义定位：`
3. `- 构造方式简述：`
4. `- 基础设施与场景简述：`
5. 一个短链路示意图，例如：

```text
需求要素 -> 形式主义对象 -> 承载格式 / 工具链 -> 分析 / 执行 / 验证场景
```

## 7. `## 形式主义定义与核心对象` 的固定写法

该章节默认至少包含以下二级标题：

1. `### 定义对象`
2. `### 核心抽象`
3. `### 语义边界`

若原文提供正式定义，应优先保留至少一个关键公式，例如：

```markdown
$$
M = (S, E, T, \ldots)
$$
```

这一章的核心任务不是复述摘要，而是讲清：

1. 状态、迁移、事件、动作、时钟、token、连续变量等核心对象分别是什么。
2. 该形式主义到底是离散、时间、混成、并发还是接口/契约导向。
3. 它和普通 `FSM` 相比，究竟多了哪些结构。

## 8. `## 关键特性` 的固定写法

该章节必须至少包含一个“能力特征速览”表。默认推荐如下维度：

| 维度 | 支持情况 | 说明 |
|---|---|---|
| 状态 / 模式 |  |  |
| 事件 / 触发 |  |  |
| 守卫 / 数据 |  |  |
| 层次 |  |  |
| 并发 / 同步 |  |  |
| 时间约束 |  |  |
| 连续动态 / 随机性 |  |  |
| 可执行 / 可验证性 |  |  |

如果某一维度不适用，也要明确写“不适用”或“原文未涉及”，不要留空。

## 9. `## 构造方式与承载格式` 的固定写法

这是本论文集的重心之一，必须显式回答以下问题：

1. 该形式主义主要是图形化、文本化，还是两者并存。
2. 是否存在明确的 DSL、XML、JSON、元模型、交换标准或代码表示。
3. 若论文只给抽象语法而不给具体文件格式，也必须明确写出。
4. 若该形式主义常见地依附某个标准或工具载体，也要写清。

推荐至少包含以下二级标题：

1. `### 建模入口`
2. `### 机器可处理承载方式`
3. `### 交换与互操作`

## 10. `## 配套基础设施` 的固定写法

该章节至少应从以下维度盘点：

1. 建模/编辑工具
2. 解析/交换/元模型支持
3. 仿真/执行支持
4. 验证/分析支持
5. 代码生成/转换支持
6. 标准化或社区生态

若原文没有覆盖某一部分，应明确写“原文未说明”，不要用常识补齐。

若当前条目来自方法路线论文，应显式注明这些基础设施信息是论文直接给出的，还是论文所依赖的外部标准/工具前提；不能把方法实现细节误写成形式主义自身的通用基础设施。

## 11. `## 适用场景与需求前提` 的固定写法

该章节默认至少包含以下二级标题：

1. `### 适用场景`
2. `### 需求前提`
3. `### 不适用或高成本场景`

其中 `### 需求前提` 必须尽量回答：

1. 需求是否需要显式状态/模式划分。
2. 是否依赖事件触发。
3. 是否需要守卫、数据变量或动作效果。
4. 是否需要时间约束。
5. 是否需要并发、同步、资源竞争或连续动力学信息。

## 12. `## 与相邻形式主义的关系` 的固定写法

该章节的目标是帮助后续形成类型谱系，而不是单篇孤立解读。

默认至少比较以下两类内容中的若干项：

1. 与 `FSM / Statechart / Timed Automata / Petri Nets / Hybrid Automata` 等相邻家族的差异。
2. 与更简单或更复杂形式主义相比，它增加了什么，又牺牲了什么。

若原文没有直接比较，也应基于原文可追溯信息保守总结，而不是自由发挥。

## 13. `## 与本研究的关系` 的固定写法

该章节默认至少包含以下二级标题：

1. `### 对 Project 1 的价值`
2. `### 作为目标形式主义还是中间表示`
3. `### 对需求到模型生成的启发`
4. `### 现实限制`

这里必须显式回答：

1. 该形式主义是否适合作为 `project_1` 的直接输出对象。
2. 如果不适合作为最终输出，它是否适合作为中间表示。
3. 它对输入需求质量提出了什么要求。
4. 它是否已经具备足够成熟的验证或执行基础设施。

## 14. `## 重要的相关工作` 的固定写法

该章节必须基于原文的相关工作与参考文献来写，不能编造。

默认按以下几类组织：

1. `### 奠基或前身工作`
2. `### 同类型或同家族工作`
3. `### 标准 / 格式 / 工具链工作`
4. `### 与本研究关系最紧的工作`

## 15. `## 文献分类总结` 的固定写法

章节结尾必须给出一组可直接映射到 [SUMMARY.md](./SUMMARY.md) 的压缩字段，至少包含：

1. `主类`
2. `描述客体`
3. `所属领域`
4. `形式主义`
5. `论文角色`
6. `核心功能`
7. `关键特性`
8. `构造方式`
9. `基础设施`
10. `适用场景`
11. `需求前提`
12. `状态`

## 16. 与 `SUMMARY.md` 的对齐关系

后续单篇 `desc.md` 与 [SUMMARY.md](./SUMMARY.md) 的关系固定如下：

1. `主类` 对应总表中的 `主类`。
2. `描述客体` 对应总表中的 `客体`。
3. `所属领域` 对应总表中的 `领域`。
4. `形式主义` 对应总表中的 `形式主义`。
5. `论文角色` 对应总表中的 `论文角色`。
6. `核心功能 / 关键特性 / 构造方式 / 基础设施 / 适用场景 / 需求前提 / 状态` 分别对应总表中的同名列。

换言之：

1. `SUMMARY.md` 负责压缩汇总。
2. `desc.md` 负责把单一形式主义讲清楚。
3. 若条目主体无法稳定映射到“核心功能 / 关键特性 / 构造方式 / 基础设施 / 适用场景 / 需求前提”这些核心字段，应降为候选而不是勉强入库。
