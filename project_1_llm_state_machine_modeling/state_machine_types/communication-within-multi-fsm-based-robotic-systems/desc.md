## 简报

这篇论文的价值不在于又定义一个通用自动机家族，而在于把“机器人由多个通信子系统组成”这件事固定成一套可落地的方法：规格阶段用 embodied agent 描述控制、感知和执行子系统，运行阶段把它转成共享白板通信的 `LLFSM` 集合。这样，每个子系统都保留自己的 `FSM` 行为逻辑，而跨子系统的数据交换和解耦则交给 whiteboard。论文的重点不是单机大状态图，而是“多 `FSM` 系统如何可靠通信并自动落成控制器”。

- 形式主义定位：面向机器人子系统分解、通信和代码生成的 `LLFSM + whiteboard` 执行架构，而不是单个 mission supervisor。
- 构造方式简述：先按 embodied agent 将系统拆成控制、虚拟受体、虚拟执行器等子系统，再为每个子系统写 hierarchical `FSM` 与行为 transition function，最后生成 `LLFSM` 和 whiteboard 共享内存通信实现。
- 基础设施与场景简述：依托 `gusimplewhiteboard`、`LLFSM`、自动代码生成和分布式 UDP/TTA 共享机制，服务多子系统机器人控制。

```text
机器人规格需求 -> embodied agent + subsystem FSMs -> transition function / terminal condition -> LLFSM + whiteboard -> 可执行控制器
```

## 形式主义定义与核心对象

### 定义对象

论文中的核心对象包括：

1. embodied agent `a_j`：完整机器人或计算代理的规格单位。
2. control subsystem `c_j`：负责行为选择和总体协调。
3. virtual receptors `r_{j,k}`：聚合传感器输入。
4. virtual effectors `e_{j,n}`：把控制命令变成真实执行器可接受的形式。
5. hierarchical FSM `{}^sF_{j,v}`：描述每个子系统活动的状态机。
6. behaviour sub-FSM `{}^sB_{j,v,\omega}`：描述某一状态下具体行为的周期计算。
7. whiteboard：子系统之间共享对象和消息的通信媒介。
8. `LLFSM`：运行阶段承载各子系统行为的逻辑标记有限状态机实现。

### 核心抽象

原文对 embodied agent 和行为函数给出了较明确的结构，这里保守整理为：

$$
a_j = (c_j, \{r_{j,k}\}, \{e_{j,n}\}, \{R_{j,l}\}, \{E_{j,m}\})
$$

上式中的符号逐项解释如下：

1. `c_j` 是控制子系统。
2. `r_{j,k}` 是虚拟受体，用于聚合来自真实传感器的数据。
3. `e_{j,n}` 是虚拟执行器，用于向真实执行器下发控制命令。
4. `R_{j,l}` 是真实受体，也就是实体传感器。
5. `E_{j,m}` 是真实执行器。

每个子系统 `s \in \{c,e,r\}` 的活动由 hierarchical `FSM` 表示：

$$
{}^sF_{j,v} = (Q_{j,v}, q^0_{j,v}, \Delta_{j,v}, B_{j,v})
$$

上式中的符号逐项解释如下：

1. `Q_{j,v}` 是子系统状态集合。
2. `q^0_{j,v}` 是初始状态。
3. `\Delta_{j,v}` 是带谓词条件的状态迁移集合。
4. `B_{j,v}` 把每个状态映射到相应 behaviour sub-FSM。

论文还明确给出了行为周期函数的输入输出关系：

$$
{}^sf_{j,v,\omega} : ({}^sS^i_{j,v}, x{}^sS^i_{j,v}) \mapsto (y{}^sS^{i+1}_{j,v}, {}^sS^{i+1}_{j,v})
$$

上式中的符号逐项解释如下：

1. `{}^sS^i_{j,v}` 是子系统在离散时刻 `i` 的内部记忆。
2. `x{}^sS^i_{j,v}` 是该时刻从其他子系统或环境获得的输入缓冲。
3. `y{}^sS^{i+1}_{j,v}` 是下一拍写入输出缓冲的数据。
4. `{}^sS^{i+1}_{j,v}` 是更新后的内部记忆。

### 一个最小例子与通俗解释

论文以一个简化的 table tennis ball-collecting robot 作为例子。直观上可以把它想成：

1. 感知子系统负责判断球是否被看见、位置在哪里。
2. 控制子系统根据白板上的球位姿和当前任务阶段决定“去找球”“靠近球”还是“收球”。
3. 执行子系统接收控制命令，驱动车轮或收集机构动作。
4. 各子系统不直接彼此硬连接，而是通过 whiteboard 共享对象。

通俗地说，这种方法像“多个小状态机围着同一块共享白板协同工作”：每个状态机只关心自己的节拍和内部逻辑，通信则统一走白板，从而减少子系统间硬编码耦合。

### 运行 / 接受 / 转移语义

行为循环可保守写成：

$$
\mathrm{step}_{j,v,\omega}^i = \bigl({}^sf_{j,v,\omega}, {}^sf^\varepsilon_{j,v,\beta}, {}^sf^\tau_{j,v,\xi}\bigr)
$$

上式中的符号逐项解释如下：

1. `{}^sf_{j,v,\omega}` 是本拍的 transition function。
2. `{}^sf^\varepsilon_{j,v,\beta}` 是错误条件。
3. `{}^sf^\tau_{j,v,\xi}` 是终止条件。

基于论文描述，其行为终止条件可保守整理为：

$$
\mathrm{continue}({}^sB_{j,v,\omega}) \iff \neg {}^sf^\varepsilon_{j,v,\beta} \land \neg {}^sf^\tau_{j,v,\xi}
$$

上式中的符号逐项解释如下：

1. 若错误条件和终止条件都未满足，则子系统继续执行当前行为。
2. 一旦任一条件满足，主 `FSM` 恢复活动并选择下一个状态。

whiteboard 上的通信可保守表达为：

$$
W_{i+1} = \mathrm{write}(W_i, y{}^sS^{i+1}_{j,v})
$$

上式中的符号逐项解释如下：

1. `W_i` 是时刻 `i` 的 whiteboard 内容。
2. `y{}^sS^{i+1}_{j,v}` 是子系统本拍计算出的输出对象。
3. whiteboard 存的是可共享对象，而不是直接点对点的函数调用。

### 语义边界

这套方法的边界也很明确：

1. 它解决的是“多子系统机器人如何规格化通信与执行”，不是模型检查理论。
2. `FSM` 语义强调离散节拍、状态和行为函数，连续控制留给子系统内部算法。
3. whiteboard 关注通信共享，不承担复杂知识推理语义。
4. 它更适合模块化机器人控制器，而不是极端轻量、单脚本式的应用。

### 关键性质与判定边界

| 问题 / 性质 | 形式化写法 | 原文意义 |
|---|---|---|
| agent 骨架 | `$a_j = (c_j, \{r_{j,k}\}, \{e_{j,n}\}, \{R_{j,l}\}, \{E_{j,m}\})$` | 机器人被拆成控制、感知、执行与实体接口几类子系统。 |
| 子系统行为 | `${}^sF_{j,v} = (Q_{j,v}, q^0_{j,v}, \Delta_{j,v}, B_{j,v})$` | 每个子系统都由层次状态机驱动。 |
| 行为周期函数 | `${}^sf_{j,v,\omega} : ({}^sS^i, x{}^sS^i) \mapsto (y{}^sS^{i+1}, {}^sS^{i+1})$` | 每一拍根据输入和内部记忆计算输出与下一状态。 |
| 通信共享 | `$W_{i+1} = \mathrm{write}(W_i, y{}^sS^{i+1})$` | 子系统通过 whiteboard 解耦交换数据。 |

## 关键特性

| 维度 | 支持情况 | 说明 |
|---|---|---|
| 状态 / 模式 | 强支持 | 每个子系统由 hierarchical `FSM` 驱动。 |
| 事件 / 触发 | 支持 | 状态迁移由谓词条件、错误条件和终止条件共同决定。 |
| 守卫 / 数据 | 强支持 | transition function、输入缓冲、输出缓冲和内部记忆都是核心概念。 |
| 层次 | 强支持 | 每个状态都可绑定 behaviour sub-FSM。 |
| 并发 / 同步 | 强支持 | 多子系统并行运行，通过 whiteboard 协调。 |
| 时间约束 | 弱支持 | 有离散采样周期，但没有时钟自动机式显式时钟语义。 |
| 连续动态 / 随机性 | 不支持 | 连续控制和概率行为不在本体核心。 |
| 可执行 / 可验证性 | 强执行、弱形式验证 | 规格可转成 `LLFSM` 控制器代码；形式验证不是重点。 |

### 形式化问题与性质

1. 这篇论文真正补出的不是“又一个 FSM”，而是“如何把多 FSM 机器人规格稳定落成可执行架构”。
2. whiteboard 与 `LLFSM` 的组合把子系统通信和子系统行为两条线拆开了。
3. 相比直接在 `ROS` 节点间硬连，这种规格先行的方法更强调架构清晰性和自动生成。
4. 论文把 distributed whiteboard 的 UDP/TTA 共享机制也纳入了实现考虑，说明其目标是工程落地而非纯概念图。

## 构造方式与承载格式

### 建模入口

建模入口主要包括：

1. 先把机器人分解为 embodied agent 的控制、感知、执行等子系统。
2. 为每个子系统建立 hierarchical `FSM`。
3. 为每个状态定义 behaviour sub-FSM、transition function、terminal condition 和 error condition。
4. 在实现阶段把规格映射到 `LLFSM + whiteboard` 结构。

### 机器可处理承载方式

原文直接给出的承载方式包括：

1. embodied-agent 规格结构。
2. 子系统 `FSM` 与 behaviour sub-FSM。
3. `LLFSM` 执行模型。
4. `gusimplewhiteboard` 中存放的共享 `C++11` 对象。
5. 分布式场景下基于 UDP 和 TTA 的共享算法。

### 交换与互操作

互操作重点在：

1. whiteboard 用共享对象而不是点对点消息强绑定。
2. 同一 whiteboard 机制既支持本地共享内存，也支持分布式广播共享。
3. 生成出来的控制器把通信路径和行为逻辑都固定到了同一执行骨架中。

## 配套基础设施

- 建模/编辑工具：论文强调基于 embodied-agent 规格和自动生成流程，图形界面不是重点。
- 解析/交换/元模型支持：`gusimplewhiteboard` 负责共享对象传递，支持本地和分布式共享。
- 仿真/执行支持：`LLFSM` 负责子系统行为执行，whiteboard 负责通信。
- 验证/分析支持：论文主要强调架构清晰、可生成和可维护，形式验证未展开。
- 代码生成/转换支持：原文明确说明可从规格转换到由 whiteboard 和 `LLFSM` 组成的可执行控制器代码。
- 标准化或社区生态：依赖作者团队工具线，公开行业标准和广泛互操作规范较弱。

## 适用场景与需求前提

### 适用场景

适合需要明确划分控制、感知、执行和通信职责的多子系统机器人控制器，尤其是要强调架构解耦、代码生成和通信共享的系统。

### 需求前提

1. 系统能够自然分解成多个 communicating subsystems。
2. 子系统活动能够按离散采样周期表达为状态 + 行为函数。
3. 跨子系统通信适合通过共享对象抽象，而不是复杂事务协议。
4. 团队愿意先做规格建模，再生成控制器实现。

### 不适用或高成本场景

如果系统极小、通信关系很少、或团队已经完全接受直接中间件编程，那么 embodied-agent 规格与 whiteboard 架构会显得偏重；它更适合中大型机器人系统的结构化设计。

## 与相邻形式主义的关系

相对单一 mission supervisor 型状态机，它强调“多个子系统各有状态机”；相对 `ROS` 节点图，它补了更强的形式化结构与自动生成入口；相对 `Interface Automata`，它关注的不是抽象兼容性，而是机器人内部通信和执行架构。

## 与本研究的关系

### 对 Project 1 的价值

这篇论文补出了一个很有价值的工程事实：状态机不一定只是一张总控图，也可以是“多个局部状态机 + 通信白板”的组合架构。

### 作为目标形式主义还是中间表示

它更像一种工程化目标载体和实现架构，而不是跨领域统一中间表示；但其“子系统拆分 + 状态机局部化 + 共享通信”思想对中间表示设计很有启发。

### 对需求到模型生成的启发

1. 需求抽取时不仅要抽状态，还要抽子系统边界和通信路径。
2. 一个复杂系统不必强行扁平化成单个大状态机。
3. 若目标是自动生成控制器，实现载体里应显式保留采样周期、输入缓冲、输出缓冲和终止条件。

## 重要的相关工作

- `LLFSM`：承担执行语义和代码生成落地职责。
