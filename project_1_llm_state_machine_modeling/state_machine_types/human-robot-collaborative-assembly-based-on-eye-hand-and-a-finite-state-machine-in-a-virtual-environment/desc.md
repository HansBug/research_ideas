## 简报

这篇论文的核心价值，不在于重新提出一种通用自动机理论，而在于把协同装配里的“粗粒度意图选择”和“细粒度末端微调”压成一条明确的状态机交互链。作者把 `Leap Motion` 手势、`Tobii` 视线、`PRM` 自动抓取路径和虚拟环境中的机器人末端控制接在一起，让用户只在最必要的环节提供提示，其余部分由机器人自动完成。

- 形式主义定位：面向虚拟装配与协同机器人操作的 `FSM` 交互控制器，其中状态机负责在 `识别 -> 指示 -> 抓取/搬运 -> 映射微调` 之间切换。
- 构造方式简述：以手势类别、眼-手共指对象和机器人当前状态为输入，通过 `Simulink FSM` 决定是否进入自动抓取流程或映射控制流程。
- 基础设施与场景简述：依托 `Leap Motion`、`Tobii`、`Unity`、`Simulink`、`UDP` 和 `PRM`，服务虚拟装配、协同抓取和人机共装场景。

```text
装配任务 -> 眼-手共指目标 -> FSM 切换交互阶段 -> PRM 自动抓取/搬运 -> Mapping 模式细调装配
```

## 形式主义定义与核心对象

### 定义对象

论文中的关键对象包括：

1. 用户手势集合 `G = {G_1, \ldots, G_9}`，其中实际交互主要依赖 `G_1` 到 `G_4`。
2. 视线-手指联合选择事件，用于确定被抓取对象和目标放置位置。
3. `FSM` 状态集合，负责切换 `Recognize`、`Indication`、`Capture`、`Mapping` 等交互阶段。
4. `PRM` 规划器，用于在虚拟环境里生成无碰撞抓取和搬运路径。
5. `Unity` 场景与 `Simulink` 机器人模型，用于承载状态机和机器人执行逻辑。
6. 眼-手映射控制器，用于在 `Mapping` 状态下把人手空间位姿映射到机器人末端。

### 核心抽象

原文没有给出显式数学元组，这里根据文中对 `FSM`、眼-手触发、自动抓取和映射控制的描述，保守整理该交互模型为：

$$
\mathcal{H} = (S, s_0, G, E, O, P, T, \Pi, \mu)
$$

上式中的符号逐项解释如下：

1. `S = \{\text{Recognize}, \text{Indication}, \text{Capture}, \text{Mapping}\}` 是交互状态集合。
2. `s_0 = \text{Recognize}` 是初始状态，表示系统先识别手势并等待用户进入有效交互。
3. `G` 是手势事件集合，论文主要使用 `G_1` 指示、`G_2` 进入映射、`G_3` 退出映射、`G_4` 松开夹爪。
4. `E` 是视线/手指共指触发事件集合，用于确认对象和目标位置。
5. `O` 是候选装配对象集合，例如积木块。
6. `P` 是目标放置位置集合。
7. `T` 是状态转移关系。
8. `\Pi` 是 `PRM` 自动规划与抓取执行模块。
9. `\mu` 是把手的空间状态映射到机器人末端位姿的映射控制模块。

根据论文对 Figure 7 的说明，可把核心状态转移保守写成：

$$
T:\; S \times (G \cup E) \rightarrow S
$$

以及如下典型转移规则：

$$
\begin{aligned}
T(\text{Recognize}, G_1 \land E(o,p)) &= \text{Indication} \\
T(\text{Indication}, \mathrm{select}(o,p)) &= \text{Capture} \\
T(\text{Capture}, \mathrm{reach}(o,p) \land G_2) &= \text{Mapping} \\
T(\text{Mapping}, G_3) &= \text{Recognize}
\end{aligned}
$$

上式中的符号逐项解释如下：

1. `o \in O` 是被选中的装配对象。
2. `p \in P` 是目标放置位置。
3. `G_1 \land E(o,p)` 表示用户用手势和视线同时确认对象与目标点。
4. `\mathrm{select}(o,p)` 表示系统完成对象/目标触发确认。
5. `\mathrm{reach}(o,p)` 表示机器人已经完成自动抓取和搬运，抵达目标附近。
6. `G_2` 表示用户把系统切到映射微调模式。
7. `G_3` 表示用户结束映射控制，系统回到识别态。

### 一个最小例子与通俗解释

论文中的最小工作流可以概括为：

1. 用户用 `G_1` 指向某个积木，同时视线也盯住同一个积木和目标区域。
2. `FSM` 进入 `Indication` 状态并确认“抓哪一块、放到哪里”。
3. `PRM` 自动规划机器人从当前位置到抓取位姿、再到目标位姿附近的路径。
4. 到达后，用户用 `G_2` 把系统切到 `Mapping`，直接用手的位姿细调末端。
5. 用户完成细调后用 `G_3` 退出映射；若需要松爪则用 `G_4`。

通俗地说，这个模型像一个“协作接力器”：人先负责指出意图，机器人负责完成长距离、低层次、易碰撞的自动搬运，最后再把精细放置权交还给人。它比纯遥操作少了大量连续按键，比纯自动规划又保留了人类对最后装配细节的控制。

### 运行 / 接受 / 转移语义

原文的运行逻辑可以保守整理为“状态机 + 自动规划 + 映射控制”的串联语义：

$$
(s_t, g_t, e_t) \xrightarrow{T} s_{t+1}
\xrightarrow{\;\Pi \text{ or } \mu\;} u_t
$$

上式中的符号逐项解释如下：

1. `s_t` 是当前交互状态。
2. `g_t` 是当前手势输入。
3. `e_t` 是当前视线/共指触发输入。
4. `s_{t+1}` 是状态转移后的下一个交互阶段。
5. `u_t` 是机器人执行动作。
6. 若 `s_{t+1} = \text{Capture}`，则动作由 `PRM` 规划模块 `\Pi` 生成。
7. 若 `s_{t+1} = \text{Mapping}`，则动作由手-末端映射模块 `\mu` 生成。

因此，这个系统不是“每个状态都手动控制”，而是状态机会把不同阶段路由给不同执行器：自动阶段交给 `PRM`，微调阶段交给映射控制。

### 语义边界

这个模型的边界很清楚：

1. 它是一个协同装配交互状态机，不是一般意义上的形式化验证状态机语言。
2. 它依赖虚拟环境、视线追踪和手势识别，不适合脱离这些感知前提单独存在。
3. 自动抓取阶段的几何与碰撞语义主要由 `PRM` 和场景模型承担，而不是 `FSM` 自己承担。
4. 它没有显式时间约束或安全逻辑证明，重点是交互分工与效率提升。

### 关键性质与判定边界

| 问题 / 性质 | 形式化写法 | 原文意义 |
|---|---|---|
| 交互骨架 | `$\mathcal{H} = (S, s_0, G, E, O, P, T, \Pi, \mu)$` | 系统由交互状态、眼手事件、自动规划和映射控制共同构成。 |
| 状态转移 | `$T: S \times (G \cup E) \rightarrow S$` | 手势和视线事件决定当前进入自动还是映射阶段。 |
| 自动阶段 | `$s_{t+1}=\text{Capture} \Rightarrow u_t=\Pi(o,p)$` | 自动抓取/搬运由 `PRM` 完成。 |
| 微调阶段 | `$s_{t+1}=\text{Mapping} \Rightarrow u_t=\mu(\text{hand pose})$` | 放置细调依赖手位姿到末端位姿的映射。 |

## 关键特性

| 维度 | 支持情况 | 说明 |
|---|---|---|
| 状态 / 模式 | 强支持 | 论文明确给出 `Recognize / Indication / Capture / Mapping` 四类核心状态。 |

| 层次 | 弱支持 | 不是层次状态机，主要是扁平交互阶段切换。 |
| 并发 / 同步 | 弱支持 | 眼和手需要协同触发，但没有并发状态区域。 |
| 时间约束 | 弱支持 | 仅有视线/手势持续时间判定，没有显式时间状态机语义。 |

### 形式化问题与性质

1. 论文真正解决的是“怎样把人类的低负担意图输入接进机器人装配流程”，而不是单独优化手势识别或路径规划。
2. `FSM` 的作用是把自动流程和手动微调明确分层，避免整条装配链都落成连续遥操作。
3. 眼-手联合选择让“对象是谁、目标在哪”成为清晰的离散触发条件，从而适合状态机编排。
4. 这种状态机特别适合“机器人完成粗动作，人类完成最终对位”的协作流程。

## 构造方式与承载格式

### 建模入口

建模入口主要包括：

1. 用 `Leap Motion` 采集手姿和指向信息。
2. 用 `Tobii` 采集视线目标。
3. 在 `Simulink` 中实现 `FSM` 和机器人控制逻辑。
4. 在 `Unity` 中承载虚拟装配场景。
5. 用 `PRM` 生成自动抓取与搬运轨迹。

### 机器可处理承载方式

原文直接给出的承载方式包括：

1. `Simulink` 中的 `FSM` 状态切换逻辑。
2. `Unity` 场景里的虚拟装配对象与机器人。
3. `UDP` 用于 `Simulink` 和 `Unity` 间传输状态/动作数据。
4. 手势分类神经网络与指向/视线触发算法。
5. `PRM` 轨迹规划器。

### 交换与互操作

互操作重点在：

1. 手势识别模块把 `Leap` 数据转换成离散手势类别。
2. 视线和手指方向共同决定对象/目标选择事件。
3. `FSM` 把交互状态路由到自动规划或映射控制。
4. `Unity` 和 `Simulink` 通过 `UDP` 同步机器人状态与场景表现。

## 适用场景与需求前提

### 适用场景

适合需要“人指意图 + 机器人自动搬运 + 人做最终微调”的协同装配、抓取搬运、虚拟调试和数字孪生装配训练场景。

### 需求前提

1. 任务对象和目标位置能够在虚拟场景中被离散化识别。
2. 用户可接受视线追踪和手势输入作为主交互通道。
3. 自动阶段能够用 `PRM` 或等价规划器完成抓取与搬运。
4. 最终装配仍需要人类在末端姿态上做细粒度修正。

### 不适用或高成本场景

如果装配任务几乎全是连续力控制、接触反馈和精密工艺，缺少触觉/力反馈的 `VR + FSM` 模式就会有明显局限；如果对象识别和目标定位高度不稳定，状态机切换也会被上游感知误差拖垮。

## 与相邻形式主义的关系

相对纯示教器或按键遥操作，它把“自动搬运”单独抽出来，因此明显减少用户持续操控负担；相对纯自动规划，它保留了 `Mapping` 阶段的人类精细调整；相对 `SMACH`、`RAFCON` 这类机器人任务状态机，它更强调眼-手共指的人机交互触发，而不是单纯任务编排。

## 与本研究的关系

### 对 Project 1 的价值

这篇条目补出了一个非常实际的模式：状态机不一定直接描述被控设备内部逻辑，也可以作为“交互阶段组织器”，把人类输入、自动规划和末端修正接成一个闭环。

### 作为目标形式主义还是中间表示

它更适合作为特定协作装配系统中的目标执行载体，而不是通用中间表示。

### 对需求到模型生成的启发

1. 需求里的“用户确认目标”“自动执行粗动作”“人工完成细调”非常适合分解成离散状态。
2. 生成状态机时，既要生成状态与转移，也要同步生成哪些阶段由规划器执行、哪些阶段由映射控制执行。
3. 面向协作装配的状态机往往需要把人机分工本身编码进模型，而不是只写机器人动作序列。

## 重要的相关工作

- 传统按键式或示教器遥操作：是论文实验中直接对照的基线。
- `PRM` 轨迹规划：承担自动抓取与搬运的关键路径生成职责。
- 视线追踪 / 手势识别 `HRI` 方法：为该状态机提供离散触发事件来源。
