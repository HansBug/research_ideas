## 简报

这篇论文的重点不是发明新的 PLC 语言，而是指出 `SFC` 虽然在 `IEC 61131-3` 里有标准语法，却长期缺少无歧义、可落地的统一语义。作者给出的解决方案是：用一个可参数化的形式语义把步骤、并行、层次、动作限定词和时间扩展都纳入同一套执行模型，并允许针对不同商业工具实例化。

- 形式主义定位：`PLC` 工业控制语境里的图形化顺序控制载体。
- 构造方式简述：步骤、转移、动作块和限定词共同构成图；一次 `PLC` cycle 内依序执行动作、求值守卫、选择转移并更新活动步骤。
- 基础设施与场景简述：直接服务 `IEC 61131-3` 工具链、工业自动化和安全相关 `PLC` 软件分析。

```text
工业顺控需求 -> SFC step / transition / action blocks -> 参数化 cycle semantics -> PLC 执行 / 工具适配 / 形式分析
```

## 形式主义定义与核心对象

### 定义对象

论文要解决的问题是：同样一个 `SFC` 图，在不同 `PLC` 编程工具里可能被解释成不同的运行结果，因此必须把语法、动作限定词、优先级和历史行为统一进一个形式化模型。

### 核心抽象

论文把一个 `SFC` 定义为：

$$
\mathcal{S} = (X, Q, A, q_0, T, block, <, \prec, h)
$$

上式中的符号逐项解释如下：

1. `X` 是变量集合。
2. `Q` 是步骤集合。
3. `A` 是动作集合，其中动作也可以是嵌套的 `SFC`。
4. `q_0` 是初始步骤。
5. `T \subseteq (2^Q \setminus \{\emptyset\}) \times G \times (2^Q \setminus \{\emptyset\})` 是转移集合。
6. `block : Q \to 2^B` 把动作块标到步骤上。
7. `<` 是动作执行次序。
8. `\prec` 是冲突转移优先级。
9. `h \in \{0,1\}` 表示是否带 history。

单个系统状态不是普通的变量赋值，而是一个配置：

$$
c = (\sigma, ready_Q, active_Q, active_A, stored_A)
$$

其中：

1. `\sigma` 是变量状态。
2. `ready_Q` 是控制当前位置，即 ready steps。
3. `active_Q` 是本轮真正执行动作的 active steps。
4. `active_A` 是当前活动动作。
5. `stored_A` 是被 `S` 限定词保留下来的 stored actions。

### 一个最小例子与通俗解释

可以把一个简单的液位控制器写成：

1. 初始步骤 `Idle` 关联动作 `closeValve`。
2. 按下 `START` 后转到 `Fill`，并执行 `openValve`。
3. 当 `levelHigh` 为真时，从 `Fill` 转到 `Drain`。
4. `Drain` 执行 `openOutlet`，直到 `levelLow` 成立再回到 `Idle`。

通俗解释是：`SFC` 像“工业控制里的有动作步骤图”。每个 `PLC` 周期都先跑当前活动步骤的动作，再看哪些转移满足守卫，再按优先级决定下一轮哪些步骤继续活跃。

### 运行 / 接受 / 转移语义

论文把 `SFC` 的执行定义成一个转移系统：

$$
E(\mathcal{S}) = (C, c_0, \to)
$$

其中：

1. `C` 是所有可能配置的集合。
2. `c_0` 是初始配置。
3. `\to` 是一个 `PLC` cycle 级别的状态迁移关系。

使能转移集合被定义为：

$$
enabled = \{ (\chi, g, \chi') \in \bar{T} \mid \chi \subseteq active_Q \land c \models g \}
$$

其中：

1. `\chi` 是某条转移的源步骤集合。
2. `\chi'` 是目标步骤集合。
3. `c \models g` 表示当前配置满足守卫 `g`。

下一轮 ready steps 的更新写成：

$$
ready_Q' = (ready_Q \setminus source(taken)) \cup target(taken)
$$

这里：

1. `taken` 是在 `enabled` 中按优先级 `\prec` 选出的真正触发转移集合。
2. `source(taken)` 表示这些转移的源步骤。
3. `target(taken)` 表示这些转移的目标步骤。

动作执行顺序则依赖 `<`。若当前活动动作是 `a_1 < \cdots < a_m`，则变量更新满足：

$$
\sigma' = (a_m \circ \cdots \circ a_1)(\sigma)
$$

这正是论文强调的关键点：`SFC` 语义里不仅要知道“有哪些步骤激活”，还要知道“动作按什么顺序执行”和“哪些动作会被 `S/R/P0/P1` 这类限定词保留或重置”。

### 语义边界

这套统一语义的边界很清楚：

1. 它面向 `PLC cycle` 级执行，而不是一般异步进程语义。
2. 它把 `SFC` 看成带动作限定词、优先级和层次的工业程序语言。
3. 它的主要任务不是追求最抽象的理论最简模型，而是覆盖现实工具里的行为差异。

### 关键性质与判定边界

论文的关键贡献不是某个复杂度定理，而是：

1. 把工具差异压缩进参数 `<`、`\prec`、`h` 和 timed extension。
2. 显式区分 `ready` 与 `active`，从而支持嵌套 `SFC` 的恢复行为。
3. 给 timed `SFC` 留出统一扩展入口，支持 `si.T` 这类活动时长测试。

## 关键特性

| 维度 | 支持情况 | 说明 |
|---|---|---|
| 状态 / 模式 | 强支持 | 步骤是 `SFC` 的基本控制位置。 |
| 事件 / 触发 | 部分支持 | 主要通过守卫和 `PLC` cycle 触发，而非独立消息事件系统。 |
| 守卫 / 数据 | 强支持 | 守卫直接读变量和步骤活动性。 |
| 层次 | 强支持 | 动作可以嵌套 `SFC`，并显式讨论 history。 |
| 并发 / 同步 | 强支持 | 并行步骤和并发分支是标准特性。 |
| 时间约束 | 强支持 | 论文专门给出 timed extension 和定时动作限定词。 |
| 连续动态 / 随机性 | 不支持 | 目标是 `PLC` 离散控制程序。 |
| 可执行 / 可验证性 | 强支持 | 统一语义直接服务形式分析和工具适配。 |

### 形式化问题与性质

| 问题 / 性质 | 形式化写法 | 原文意义 |
|---|---|---|
| `SFC` 本体 | `$\mathcal{S} = (X, Q, A, q_0, T, block, <, \prec, h)$` | 把变量、步骤、动作、转移和优先级都放进一个统一对象。 |
| 运行配置 | `$c = (\sigma, ready_Q, active_Q, active_A, stored_A)$` | 一次执行不仅有变量值，还有 ready/active/stored 三层控制信息。 |
| 执行系统 | `$E(\mathcal{S}) = (C, c_0, \to)$` | 一个 `PLC` cycle 对应转移系统中的一步。 |
| 使能转移 | `$enabled = \{(\chi,g,\chi') \in \bar{T} \mid \chi \subseteq active_Q \land c \models g\}$` | 只有源步骤都 active 且守卫为真时转移才使能。 |
| 步骤更新 | `$ready_Q' = (ready_Q \setminus source(taken)) \cup target(taken)$` | 触发转移会移除旧步骤并激活目标步骤。 |
| 动作组合 | `$\sigma' = (a_m \circ \cdots \circ a_1)(\sigma)$` | 动作顺序 `<` 直接影响变量更新结果。 |

## 构造方式与承载格式

### 建模入口

建模入口是 `IEC 61131-3` 的图形化 `SFC`：步骤、转移、守卫和动作块共同组成程序。

### 机器可处理承载方式

原文没有提出新的文件格式，而是围绕 `IEC 61131-3` 语法和商业工具实现来定义形式语义。

### 交换与互操作

论文的互操作策略不是发明交换标准，而是给不同工具语义提供统一参数化语义底座，便于比较、仿真和验证。

## 配套基础设施

- 建模/编辑工具：面向 `PLC` 的 `SFC` 编程环境。
- 解析/交换/元模型支持：依托 `IEC 61131-3` 语法，本论文补的是语义层而非新元模型。
- 仿真/执行支持：以 `PLC` cycle 为基本执行单位。
- 验证/分析支持：正是论文的核心目标，用于形式分析与工具语义对齐。

## 适用场景与需求前提

### 适用场景

适合装配线、化工过程、电力控制等 `PLC` 顺序控制逻辑，以及任何使用 `SFC` 作为工程主语言的工业系统。

### 需求前提

1. 控制过程可被拆成步骤、守卫和动作块。
2. 系统遵循 `PLC` 周期扫描式执行。
3. 需要解释不同工具对 `SFC` 模糊语义的差异。

### 不适用或高成本场景

若系统核心是连续动力学、复杂开放交互协议或一般软件对象生命周期，`SFC` 往往过于面向工业顺控。

## 与相邻形式主义的关系

相对 `Grafcet`，`SFC` 更贴近 `PLC` 工具语境；相对 `Petri Net`，它保留了图结构直觉但把动作限定词和工程执行周期放到中心；相对 `Statecharts`，它更工业、也更强调步骤扫描与工具语义。

## 与本研究的关系

### 对 Project 1 的价值

`SFC` 是控制系统里最典型的行业目标载体之一，尤其适合从步骤化、顺序化需求直接落到工程实现。

### 作为目标形式主义还是中间表示

在工业自动化场景里它完全可以是目标形式主义；在更一般的控制系统研究里，也可作为局部顺控子系统的目标后端。

### 对需求到模型生成的启发

当需求文本本身就是“先做 A，再满足条件进入 B，并行执行 C/D，等待计时器后切换”这种顺控语言时，直接生成 `SFC` 往往比生成一般层次状态机更自然。

### 现实限制

`SFC` 的表达边界强依赖 `PLC` 周期和动作限定词语义，对非工业控制软件未必合适。
