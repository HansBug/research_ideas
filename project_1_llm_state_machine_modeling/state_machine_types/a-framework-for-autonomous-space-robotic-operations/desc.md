## 简报

这篇论文的核心不是单独提出一个新的自动机理论，而是把空间机器人“规划 - 验证 - 执行 - 复盘”整条作业链压缩到 `ARGO` 工具箱里，其中最关键的行为执行骨架是 `Cortex` 的层次 `FSM`。论文把命令脚本和自治行为统一处理为同一种 `FSM/HFSM` 对象：脚本描述预先验证过的操作序列，行为描述针对通信延迟、传感器事件或故障条件的本地反应逻辑。这样，空间机械臂和行星车既可以执行预编排任务，也可以在通信延迟或黑障期间依靠本地状态机完成分支、循环与异常应对。

- 形式主义定位：面向空间机器人任务脚本与本地自治的一体化 `HFSM` 工具链，而不是纯 teleoperation 界面。
- 构造方式简述：用图形状态、transition guards、triggers、sub-FSM、输入输出参数和 `JAVA` 代码片段构造脚本与行为库，再由 `Cortex` 自动生成实现。
- 基础设施与场景简述：依托 `Cortex`、`RGCS`、`Remote/Log` toolboxes、虚拟环境与在线监控，覆盖轨道操控、星表巡视和长时延深空操作。

```text
空间作业需求 -> command script / autonomous behavior -> Cortex HFSM + code generation -> ARGO toolboxes -> 规划 / 验证 / 执行 / 回放
```

## 形式主义定义与核心对象

### 定义对象

论文把 `ARGO` 的行为执行核心分成两层：

1. command script：面向某次具体操作的状态机脚本。
2. autonomous behavior：面向预定义事件和条件的可复用行为库。
3. state：代表一个待执行命令、动作块或子行为。
4. transition：由 guard 和 trigger 联合决定的状态切换。
5. sub-FSM：把复杂状态展开为更低层任务分解。
6. toolbox composition：把 `Cortex`、`RGCS`、`Remote`、`Log`、仿真环境等按任务需要装配。

### 核心抽象

原文把脚本和行为都统一为有限状态机对象，这里按其 guard/trigger/层次接口的描述，保守整理单个 `Cortex` 行为为：

$$
M = (S, s_0, \Sigma, T, I, O, H)
$$

上式中的符号逐项解释如下：

1. `S` 是状态集合，每个状态通常对应一个空间机器人命令、动作块或子行为。
2. `s_0 \in S` 是初始状态。
3. `\Sigma` 是 trigger 集合，例如周期 `CLOCK`、传感器事件、操作员输入或前一命令完成信号。
4. `T \subseteq S \times G \times \Sigma \times S` 是转移集合，其中 `G` 是 guard 条件集合。
5. `I` 是输入参数集合，例如姿态、传感器值、目标角度或任务上下文。
6. `O` 是输出参数集合，例如命令结果、遥测更新或子行为返回值。
7. `H : S \to \{\bot\} \cup \mathcal{M}` 表示层次映射；若 `H(s)=M'`，则状态 `s` 细化成一个 sub-FSM。

单步转移可保守写成：

$$
(s, \iota) \xrightarrow{\sigma} s' \iff \exists (s, g, \sigma, s') \in T,\ g(\iota)=\mathrm{true}
$$

上式中的符号逐项解释如下：

1. `s`、`s'` 是当前状态和后继状态。
2. `\iota \in I` 是当前输入上下文，包含遥测、环境信息或操作员输入。
3. `\sigma \in \Sigma` 是触发转移评估的事件。
4. `g` 是该转移的 guard 条件，只有在当前上下文里为真时转移才能发生。

### 一个最小例子与通俗解释

论文在 `Cortex` 示例里给了一个很直观的转向状态机：`Starting_Motion -> Turning -> Stopping_Motion`。

1. `Starting_Motion` 负责让移动底盘开始运动。
2. `Turning` 在进入状态时记录当前方位角，并持续检查转角是否达到目标。
3. `Stopping_Motion` 负责在达到目标角度后停车。
4. 若 `Turning` 内部逻辑过于复杂，还可以把它展开成 sub-FSM。

通俗地说，`ARGO / Cortex` 像是“能出代码、能监控、能回放的空间机器人脚本车间”：你画状态机、填 guard 和动作，工具帮你生成真正能跑在远端机器人上的行为代码，并把在线监控和事后回放都接上。

### 运行 / 接受 / 转移语义

脚本与行为在 `ARGO` 中本质上都由事件驱动的 `FSM` 执行，可保守整理为：

$$
\mathrm{run}(M,\sigma_t,\iota_t) =
\begin{cases}
s_{t+1}, & \text{若某条 guard 满足并触发转移} \\
s_t, & \text{否则保持当前状态}
\end{cases}
$$

上式中的符号逐项解释如下：

1. `\sigma_t` 是时刻 `t` 触发的事件。
2. `\iota_t` 是该时刻的遥测、环境或操作员上下文。
3. `s_t`、`s_{t+1}` 分别是当前和下一状态。
4. 若没有任何 guard 成立，状态机继续停留在当前状态。

层次化执行可进一步整理为：

$$
\mathrm{exec}(s) =
\begin{cases}
\mathrm{exec}(H(s)), & H(s) \neq \bot \\
\mathrm{do\_action}(s), & H(s) = \bot
\end{cases}
$$

上式中的符号逐项解释如下：

1. `H(s)` 是状态 `s` 的可选 sub-FSM。
2. 若 `s` 细化成子状态机，则先执行子行为。
3. 若 `s` 是叶子状态，则直接执行该状态关联的动作代码。

### 语义边界

`ARGO / Cortex` 的边界比较清楚：

1. 它提供的是空间机器人操作框架，不是严格形式验证理论。
2. 它强调“图形建模 + 代码生成 + 在线监控 + 回放”，而不是新的时钟或连续动力学语义。
3. 决策依赖预先建好的 guards、triggers 和行为库，面对完全未知任务时仍需上层规划。
4. 它适合高成本、长链路、需要严密运维流程的空间任务，不追求极简轻量运行时。

### 关键性质与判定边界

| 问题 / 性质 | 形式化写法 | 原文意义 |
|---|---|---|
| 行为骨架 | `$M = (S, s_0, \Sigma, T, I, O, H)$` | `Cortex` 用统一的状态机对象承载脚本和自治行为。 |
| 事件驱动切换 | `$(s,\iota)\xrightarrow{\sigma}s'$` | 转移受 trigger 和 guard 共同控制。 |
| 层次展开 | `$\mathrm{exec}(s)=\mathrm{exec}(H(s))$` | 高层任务可分解为可复用的 sub-FSM。 |
| 代码生成与监控 | `$\mathrm{Gen}(M)\to \mathrm{JAVA}$` | 图形状态机不是文档，而是可编译、可上线、可回放的软件工件。 |

## 关键特性

| 维度 | 支持情况 | 说明 |
|---|---|---|
| 状态 / 模式 | 强支持 | 命令脚本和自治行为都建成 `FSM/HFSM`。 |
| 事件 / 触发 | 强支持 | 以 trigger 驱动 guard 评估和转移。 |
| 守卫 / 数据 | 强支持 | transition guards、输入输出参数和状态动作代码都是一等对象。 |
| 层次 | 强支持 | 支持 sub-FSM、模块化复用和任务分解。 |
| 并发 / 同步 | 中等支持 | 工具箱组合支持分布式和多平台连接，但论文重点不在并发语义本体。 |
| 时间约束 | 弱支持 | 论文强调长时延通信场景，但不提供内建时钟自动机语义。 |
| 连续动态 / 随机性 | 不支持 | 连续控制与动力学仍在底层机器人软件中处理。 |
| 可执行 / 可验证性 | 强执行、弱形式验证 | 自动代码生成、监控、事件记录和仿真很强；时序逻辑级验证尚未提供。 |

### 形式化问题与性质

1. `ARGO` 把“脚本”和“行为”统一成同一种 `FSM` 工件，减少了空间操作中规划与自治实现的割裂。
2. `Cortex` 明确支持 transition priority，因此在多条 guard 可同时满足时仍能固定决策顺序。
3. 工具箱架构允许把同一命令/遥测接口无缝切到仿真环境、真实设备和日志回放环境。
4. 对空间操作来说，真正关键的不是“能不能画状态机”，而是“能不能把状态机纳入高成本运维流程”。

## 构造方式与承载格式

### 建模入口

建模入口主要包括：

1. 用 `Cortex` 图形界面创建 states、sub-FSM、junctions 和 transitions。
2. 给状态填入动作代码，给转移填入 guard 表达式和 trigger 逻辑。
3. 为 sub-FSM 声明输入、局部变量和输出参数。
4. 通过 toolbox 组合把行为执行、地面监控、日志和仿真环境接起来。

### 机器可处理承载方式

原文直接给出的承载方式包括：

1. 图形 `FSM/HFSM` 模型。
2. 状态动作与转移 guard 的 `JAVA` 代码片段。
3. 自动生成并编译的 `JAVA` 源码。
4. `Remote Toolbox` 支撑的命令/遥测数据库与分布式接口。
5. 基于 `XML`、Eclipse、`UML` 的软件工程载体。

### 交换与互操作

互操作重点在：

1. `Remote Toolbox` 统一连接仿真、真实设备和日志回放。
2. `RGCS` 自动识别可用命令和遥测项并快速组装地面界面。
3. 同一行为模型既可用于离线验证，也可用于在线执行与监控。

## 配套基础设施

- 建模/编辑工具：`Cortex GUI` 支持图形化编辑 `FSM/HFSM`。
- 解析/交换/元模型支持：`Remote Toolbox` 管理命令、遥测、日志和分布式连接。
- 仿真/执行支持：`ARGO` 把虚拟环境、真实设备和 post-flight analysis 放进同一流程。
- 验证/分析支持：支持 extensive simulation、在线监控、事件记录和 step-by-step playback；高级形式验证尚未集成。
- 代码生成/转换支持：`Cortex` 自动生成并编译 `JAVA` 源码。
- 标准化或社区生态：依赖通用软件工程标准和加拿大航天局内部工具链，开放标准化程度有限，但任务流程集成度高。

## 适用场景与需求前提

### 适用场景

适合轨道机械臂、在轨服务、行星车、长时延地外机器人等需要把命令脚本、本地自治、地面监控和离线验证统一起来的任务。

### 需求前提

1. 任务能够分解为离散命令和可复用自治行为。
2. 决策逻辑可以表示为 guards、triggers 和层次任务分解。
3. 系统需要在高延迟、低带宽或间歇通信环境下局部自治。
4. 团队愿意把行为工程纳入严格的规划、验证、上线和回放流程。

### 不适用或高成本场景

如果任务只需轻量脚本自动化、几乎没有通信延迟、也不需要复杂运维链路，那么 `ARGO` 的工具箱完整性可能反而显得过重；它更适合高代价、高风险、长周期的空间作业。

## 与相邻形式主义的关系

相对纯 teleoperation 框架，`ARGO` 明确把脚本和自治行为统一进 `HFSM`。相对 `PLEXIL` 这类计划执行语言，它更强调图形行为编辑、地面控制站和全流程运维集成。相对 `RoboChart` 这种验证导向 DSL，它更偏任务工程和空间运维，而不是形式语义证明。

## 与本研究的关系

### 对 Project 1 的价值

这篇论文说明，面向高成本任务的状态机载体不能只考虑“表达行为”，还要考虑“如何接入规划、验证、执行与复盘流程”。这正对应 `project_1` 后续关心的目标载体选型问题。

### 作为目标形式主义还是中间表示

它更适合作为空间机器人任务层的目标执行载体，而不是跨领域统一中间表示；但其 `HFSM + codegen + monitor` 组合很适合为中间表示设计提供约束。

### 对需求到模型生成的启发

1. 需求生成出的状态机若要落地，最好同时有图形编辑、自动代码生成和在线可观测性。
2. 行为库和脚本不必分属两套体系，可以统一成同一种层次状态机工件。
3. 长时延场景下，需求建模时应显式区分“必须由本地自治完成的决策”和“仍可由地面介入的决策”。

## 重要的相关工作

- `ROSA`、`IIRO`：是论文明确提到的加拿大航天局前序地面控制/监督自治路线。
- `CLARAty`、`FIDO`、`CAMPOUT`：是 NASA/JPL 面向高自治空间机器人的近邻架构。
- `MARCO`、`FAMOUS`、`DREAMS`：代表欧洲空间机器人 teleoperation 与 ground control 路线。
