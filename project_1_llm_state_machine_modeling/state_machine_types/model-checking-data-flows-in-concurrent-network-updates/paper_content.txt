Abstract. We present a model checking approach for the verication of
data ow correctness in networks during concurrent updates of the net-
work conguration. This verication problem is of great importance for
software-dened networking (SDN), where errors can lead to packet loss,
black holes, and security violations. Our approach is based on a specica-
tion of temporal properties of individual data ows, such as the require-
ment that the ow is free of cycles. We check whether these properties
are simultaneously satised for all active data ows while the network
conguration is updated. To represent the behavior of the concurrent
network controllers and the resulting evolutions of the congurations,
we introduce an extension of Petri nets with a transit relation, which
characterizes the data ow caused by each transition of the Petri net.
For safe Petri nets with transits, we reduce the verication of temporal
ow properties to a circuit model checking problem that can be solved
with eective verication techniques like IC3, interpolation, and bounded
model checking. We report on encouraging experiments with a prototype
implementation based on the hardware model checker ABC.
1 Introduction
Software-dened networking (SDN) [33,7] is a networking technology that sep-
arates the packet forwarding process, called the data plane , from the routing
process, called the control plane . Updates to the routing conguration can be
initiated by a central controller and are then implemented in a distributed man-
ner in the network. The separation of data plane and control plane makes the
management of a software-dened network dramatically more ecient than a
traditional network. The model checking of network congurations and concur-
rent updates between them is a serious challenge. The distributed update process
can cause issues like forwarding loops, black holes, and incoherent routing which,
from the perspective of the end-user, result in performance degradation, broken
connections, and security violations. Correctness of concurrent network updates

has previously been addressed with restrictions like consistent updates [39]: ev-
ery packet is guaranteed during its entire journey to either encounter the initial
routing conguration or the nal routing conguration, but never a mixture in
the sense that some switches still apply the old routing conguration and others
already apply the new routing conguration. Under these restrictions, updates to
network congurations can be synthesized [13,32]. Ensuring consistent updates
is slow and expensive: switches must store multiple routing tables and messages
must be tagged with version numbers.
In this paper, we propose the verication of network congurations and con-
current updates between them. We specify desired properties of the data ows
in the network, such as the absence of loops, and then automatically check, for
a given initial routing conguration and a concurrent update, whether the spec-
ied properties are simultaneously satised for all active data ows while the
routing conguration is updated. This allows us to check a specic concurrent
update and to thus only impose a sequential order where this is strictly needed
to avoid an erroneous conguration during the update process.
Our approach is based on temporal logic and model checking. The control
plane of the network can naturally be specied as a Petri net. Petri nets are
convenient to dierentiate between sequential and parallel update steps. The
data plane, however, is more dicult to specify. The standard ow relation of a
Petri net does not describe which ingoing token of a transition transits to which
outgoing token. In theory, such a connection could be made with colored Petri
nets [22], by using a uniquely colored token for each data ow in the network.
Since there is no bound on the number of packets, this would require innitely
many tokens and colors to track the innitely many data ows. To avoid this
problem, we develop an extension of Petri nets called Petri nets with transits ,
which augment standard Petri nets with a transit relation . This relation species
the precise data ow between ingoing and outgoing tokens of a transition. In Petri
nets with transits, a single token can carry an unbounded number of data ows.
We introduce a linear-time temporal logic called Flow-LTL to specify the
correct data ows in Petri nets with transits. The logic expresses requirements
on several separate timelines: global conditions, such as fairness, are expressed
in terms of the global timeline of the system run. Requirements on individual
data ows, such as that the data ow does not enter a loop, on the other hand,
are expressed in terms of the timeline of that specic data ow. The next op-
erator, for example, refers to the next step taken by the particular data ow,
independently of the behavior of other, simultaneously active, data ows.
Concurrent updates of software-dened networks can be modeled as safe Petri
nets with transits. We show that the model checking problem of the innite state
space of Petri nets with transits against a Flow-LTL formula can be reduced to
the LTL model checking problem for Petri nets with a nite number of tokens;
and that this model checking problem can in turn be reduced to checking a
hardware circuit against an LTL formula. This ultimately results in a standard
verication problem, for which highly ecient tools such as ABC [2] exist.

7 Implementation Details and Experimental Results
We implemented our model checking approach in a prototype tool based on the
toolAdam [16]. Our tool takes as input a Flow-LTL specication and a Petri net
with transits, and carries out the transformation described in Sec. 6 to obtain
an LTL formula and an Aiger circuit. We then use MCHyper [18] to combine the
circuit and the LTL formula into another Aiger circuit. MCHyper is a verication
tool for HyperLTL [11], which subsumes LTL. The actual model checking is
carried out by the hardware model checker ABC [2]. ABC provides a toolbox
of state-of-the-art verication and falsication techniques like IC3 [5]/PDR [12],
interpolation (INT) [34], and bounded model checking [3] (BMC, BMC2, BMC3).
We prepared an artifact to replicate our experimental results [21].

Switch Failure (SF) ( Parameter: nswitches): From a sequence of nswitches
with the ingress at the beginning and the egress at the end, a failing switch is
chosen at random and removed. Then, data ows are bypassed from the prede-

node no matter of the update (connectivity).
Redundant Pipeline (RP) ( Parameters: n1switches in pipeline one / n2
switches in pipeline two / vversion): The base version (B) contains two dis-

length. For this and the next two versions, it is required that each data ow
reaches the egress node (connectivity) and is only forwarded via the rst or the

that can concurrently remove the rst node of any pipeline and return the data

Returning the data ows violates packet coherence. Mutex version (M): A mutex
is added to the update version such that at most one pipeline can be broken.
Updates can happen sequentially such that data ows are in a cycle through
the ingress. Correct version (C): The requirements are weakened such that each
data ow only has to reach the egress when updates do not occur innitely often.
Routing Update (RU) is a case study based on realistic software-dened net-

guration, we build a sequential update in reverse from egress to ingress. The
update overlaps with the initial conguration at some point during the update

8 Related Work
There is a large body of work on software-dened networks, see [28] for a good
introduction. Specic solutions that were proposed for the network update prob-
lem include consistent updates [39,8] (cf. the introduction), dynamic schedul-
ing[23], and incremental updates [25]. Model checking, including both explicit
and SMT-based approaches, has previously been used to verify software-dened
networks [6,31,30,43,1,36]. Closest to our work are models of networks as Kripke
structures to use model checking for synthesis of correct network updates [13,32].
While they pursue synthesis , rather than verication of network updates, the ap-
proach is still based on a model checking algorithm that is called in each step
of the construction of a sequence of updates. The model checking subroutine of
the synthesizer assumes that each packet sees at most one switch that was up-
dated after the packet entered the network. This restriction is implemented with
explicit waits, which can afterwards often be removed by heuristics. Our model
checking routine does not require this assumption. As it therefore allows for more
general updates, it would be very interesting to add the new model checking al-
gorithm into the synthesis procedure. Flow correctness also plays a role in other
application areas like access control in physical spaces. Flow properties that are
of interest in this setting, such as \from every room in the building there is a
path to exit the building", have been formalized in a temporal logic [42].
There is a signicant number of model checking tools (e.g., [40,41,24]) for
Petri nets and an annual model checking contest [27]. In this contest, however,
only LTL formulas with places as atomic propositions are checked. To the best of
our knowledge, other model checking tools for Petri nets do not provide places
and transitions as atomic propositions. Our encoding needs to reason about
places and transitions to pose fairness conditions on the ring of transitions.
9 Conclusion
We have presented a model checking approach for the verication of data ow
correctness in networks during concurrent updates of the network conguration.
Key ingredients of the approach are Petri nets with transits, which superimpose
the transit relation of data ows onto the ow relation of Petri nets, and Flow-
LTL, which combines the specication of local data ows with the specication

--- Page 16 ---
16 B. Finkbeiner et al.
of global control. The model checking problem for Petri nets with transits and
Flow-LTL specications reduces to a circuit model checking problem. Our pro-
totype tool implementation can verify and falsify realistic concurrent updates of
software-dened networks with specications like packet coherence.
In future work, we plan to extend this work to the synthesis of concurrent
updates. Existing synthesis techniques use model checking as a subroutine to
verify the correctness of the individual update steps [13,32]. We plan to study
Flow-LTL specications in the setting of Petri games [17], which describe the
existence of controllers for asynchronous distributed processes. This would allow
us to synthesize concurrent network updates without a central controller.

A Encoding of Concurrent Updates for SDN
In this section of the appendix, we outline how updates to a congured network
topology can be encoded into Petri nets with transits. First, we recall network
topologies, network congurations, and concurrent updates. Second, we encode
a network topology as data plane into Petri nets with transits. Third, we en-
code a corresponding network conguration and a concurrent update to this
conguration into usual Petri nets (without transits).
A.1 Network Topology, Congurations, and Updates
Anetwork topology Tis given as a nite, connected, undirected graph T=
(Sw;Con) with the non-empty set of switches Swas vertices and the non-empty
set of connections ConSwSwas edges. The conguration of a network
topology is dened by a static NetCore [20,35] program with the following syntax:
ingress = Ingr;
forwarding;
egress = Egr;
such that IngrSwis the non-empty set of ingress switches where packets en-

to which packets should be forwarded. It is required that Ingr\Egr =;.
forwarding is a list of forwarding rules of the form x.fwd(y); with x;y2Sw.
Such a rule denes that switch xforwards packets to switch y. Each switch oc-
curs at most once on the left hand side of the list of forwarding rules, making
the forwarding decision of switches deterministic . If a switch is not congured,
then all packets are dropped at that switch.
Aconcurrent update to the forwarding rules is given by the following syntax:
switch update ::= upd(x.fwd(z)) (x;z2Sw)
sequential update ::= (update >>update >>...>>update )
parallel update ::= (update ||update ||...||update )
update ::= switch update jsequential update jparallel update
where, for eciency reasons, each switch is updated at most once.
Update statements of the form upd(x.fwd(z)) dene that a given cong-
uration is altered by changing the forwarding rule x.fwd(y) tox.fwd(z) or
by adding x.fwd(z) to the given conguration if switch xis not congured in
forwarding . The rst case updates the forwarding rule of switch xfrom switch y
to switch zwhereas the second case congures the switch xto now forward pack-
ets to switch z(instead of dropping the packets). The sequential update denes a
sequence of updates, where the next update is only carried out after the current
update is nished. The parallel update denes that all updates can happen in
parallel and no assumptions about their order can be made.
