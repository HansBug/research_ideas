## 简报

这篇论文的价值不在于再发明一个状态机，而在于把工业上广泛使用的 `Stateflow` 明确解释成一种“顺序化、命令式的图形状态机语言”。论文最关键的判断是：`Stateflow` 虽然表面上像 `Statecharts`，但它真正的行为来自严格的静态排序、顺序执行和事件处理规则，而不是经典层次状态机里的并发语义。

- 形式主义定位：`Matlab/Simulink` 里的工业级状态机/流程图混合载体。
- 构造方式简述：状态、junction、内部/外部 transition、事件、动作和层次组合被线性化成有序列表后执行。
- 基础设施与场景简述：直接依托 `Stateflow` 仿真、代码生成和嵌入式控制建模生态，适合离散控制器与连续被控对象联合建模。

```text
控制逻辑与事件需求 -> Stateflow chart -> 顺序化 operational semantics -> 仿真 / 代码生成 / 形式分析
```

## 形式主义定义与核心对象

### 定义对象

原文关注的是 `Stateflow` 这种工业图形语言怎样被严格形式化，特别是：

1. 层次状态与 flowchart junction 怎样统一描述。
2. 事件、守卫、动作和转移优先级怎样决定一次 step 内的执行结果。
3. 所谓“并行子图”在 `Stateflow` 里其实如何按固定顺序执行。

### 核心抽象

论文先把 `Stateflow` 的一个安全子集线性化。其核心组合对象为：

$$
C = Or(s_a, p, T, SD) \mid And(b, SD)
$$

上式中的符号逐项解释如下：

1. `Or(s_a, p, T, SD)` 表示一个 `OR` 组合，包含当前活动状态 `s_a`、路径 `p`、默认转移 `T` 和状态定义表 `SD`。
2. `And(b, SD)` 表示一个 `AND` 组合，其中 `b` 表示该并行组合当前是否激活。
3. `SD` 是状态定义列表，把状态名映射到具体状态定义。

单个状态定义写成：

$$
sd = ((a_e, a_d, a_x), C, T_i, T_o, J)
$$

其中：

1. `(a_e, a_d, a_x)` 分别是 entry、during、exit 三类动作。
2. `C` 是该状态内部的组合结构。
3. `T_i` 是内部转移列表。
4. `T_o` 是对外转移列表。
5. `J` 是 junction 到转移列表的映射。

一条转移被表示为：

$$
t = (e_t, c, a_c, a_t, d)
$$

其中：

1. `e_t` 是转移事件，可以为空事件。
2. `c` 是守卫条件。
3. `a_c` 是一旦转移有效就立即执行的动作。
4. `a_t` 是只有真正走通该转移后才执行的尾部动作。
5. `d` 是目标，可以是路径 `p`，也可以是 junction `j`。

### 一个最小例子与通俗解释

论文给出的最直观例子是带 `START` 和 `LAP` 按钮的秒表：

1. `Reset` 与 `LapStop` 属于停止大状态。
2. `Running` 与 `Lap` 属于运行大状态。
3. `START` 控制“停止/运行”切换，`LAP` 控制显示是否冻结。
4. `TIC` 事件驱动内部 flowchart 增加 `cent/sec/min`。

通俗解释是：`Stateflow` 像“带层次状态的流程图解释器”。每来一个事件，解释器会按固定顺序检查当前状态、junction 和 transition，谁先匹配、谁先执行，不留真正的并发歧义。

### 运行 / 接受 / 转移语义

论文用结构操作语义描述事件处理：

$$
e, D \vdash_P P \to D', P', tv
$$

上式中的符号逐项解释如下：

1. `e` 是当前处理的输入事件。
2. `D` 是环境，保存变量取值和当前 instant 内被抛出的输出事件。
3. `P` 是当前正在执行的 `Stateflow` 语法对象。
4. `D'` 是更新后的环境。
5. `P'` 是执行后的新程序状态。
6. `tv` 是转移值，用来向外层报告是否发生了转移。

转移值集合写成：

$$
tv \in \{ Fire(d, a), End, No \}
$$

其中：

1. `Fire(d, a)` 表示某条转移已经触发，并携带目标 `d` 与待执行动作 `a`。
2. `End` 表示 flowchart 到达终止 junction。
3. `No` 表示当前路径未触发可用转移。

单条转移的核心规则可压缩为：

$$
(e = e_t \lor e_t = \varnothing_e) \land \llbracket c \rrbracket_{e,D} = \mathrm{true} \Rightarrow e, D \vdash t \to D', Fire(d, a_t)
$$

这里：

1. `\varnothing_e` 表示空事件。
2. `\llbracket c \rrbracket_{e,D}` 表示在事件 `e` 和环境 `D` 下求值守卫 `c`。
3. `D'` 是执行立即动作 `a_c` 后得到的新环境。

论文还强调 transition list 是顺序求值的，第一条可触发转移就会被采用；即便是 `And` 组合，其“并行”子图也按照静态已知顺序逐个执行。

### 语义边界

这套语义明确告诉我们：`Stateflow` 的本质不是“真正并发的层次状态机”，而是：

1. 强依赖顺序化优先级和 `12 o'clock rule` 的工业图形语言。
2. 通过 junction 和 transition list 把 flowchart 与 statechart 混在一起的命令式系统。
3. 更适合做控制器行为描述，而不是表达开放式并发协议。

### 关键性质与判定边界

论文最重要的性质不是复杂度定理，而是两个工程结论：

1. 许多 `Stateflow` 语义都可在操作语义层被精确重建，从而支撑静态分析和模型检查。
2. `AND` 组合在语义上仍是顺序执行，因此很多“并发”问题其实退化成确定的求值顺序问题。

## 关键特性

| 维度 | 支持情况 | 说明 |
|---|---|---|
| 状态 / 模式 | 强支持 | 层次状态、活动状态和默认路径都是核心对象。 |
| 事件 / 触发 | 强支持 | 转移事件和本地事件驱动整个执行。 |
| 守卫 / 数据 | 强支持 | 条件、动作和环境更新都显式进入语义。 |
| 层次 | 强支持 | `Or` / `And` 组合和 interlevel transitions 是主体内容。 |
| 并发 / 同步 | 部分支持 | 图上有并行结构，但语义上按静态顺序执行。 |
| 时间约束 | 部分支持 | 论文面向离散事件处理，本身不引入显式时钟自动机语义。 |
| 连续动态 / 随机性 | 不支持 | 连续部分由 `Simulink` 其他部件承载，不在本语义核心内。 |
| 可执行 / 可验证性 | 强支持 | 原文用该语义支撑解释器、静态分析和模型检查原型。 |

### 形式化问题与性质

| 问题 / 性质 | 形式化写法 | 原文意义 |
|---|---|---|
| 组合结构 | `$C = Or(s_a,p,T,SD) \mid And(b,SD)$` | `Stateflow` chart 由层次 `OR` 组合与顺序化 `AND` 组合构成。 |
| 状态定义 | `$sd = ((a_e,a_d,a_x), C, T_i, T_o, J)$` | 每个状态都绑定 entry/during/exit 动作、内部组合和转移表。 |
| 转移对象 | `$t = (e_t, c, a_c, a_t, d)$` | 事件、守卫、动作和目标共同决定一条 `Stateflow` 转移。 |
| 事件处理关系 | `$e, D \vdash_P P \to D', P', tv$` | 处理一个事件会同时更新环境、控制状态和转移值。 |
| 转移值 | `$tv \in \{Fire(d,a), End, No\}$` | 区分成功转移、终止 junction 和失败路径。 |
| 触发条件 | `$(e=e_t \lor e_t=\varnothing_e) \land \llbracket c \rrbracket_{e,D}$` | 只有事件匹配且守卫为真时转移才会生效。 |

## 构造方式与承载格式

### 建模入口

建模入口是 `Stateflow` 图形 chart：状态、junction、内部/外部 transition、事件和动作共同构成控制器。

### 机器可处理承载方式

原文没有定义脱离 `Matlab/Simulink` 的独立交换格式，而是直接以 `Stateflow` 图形语言和其仿真语义作为机器可处理承载。

### 交换与互操作

`Stateflow` 的互操作强依赖 `Matlab/Simulink` 生态。原文主要解决“怎样把 chart 解释清楚”，不是“怎样跨工具交换”。

## 配套基础设施

- 建模/编辑工具：`Stateflow` 图形编辑器。
- 解析/交换/元模型支持：论文给出了可操作语义驱动的线性化表示，但未提出开放交换标准。
- 仿真/执行支持：直接复用 `Matlab/Simulink` 的 simulation semantics。
- 验证/分析支持：原文用该语义支撑解释器、静态分析、模型检查和测试生成原型。
- 代码生成/转换支持：依托 `Matlab` 工具链已有代码生成能力。
- 标准化或社区生态：工业采用面广，但语义长期以工具行为为准而非正式标准为准。

## 适用场景与需求前提

### 适用场景

适合嵌入式控制器、混成系统中的离散控制部分、汽车/航电等模型驱动开发场景。

### 需求前提

1. 需求中存在清晰的模式、事件和切换条件。
2. 系统可以接受由工具规定的严格优先级和顺序执行规则。
3. 控制逻辑要与 `Simulink` 连续模型和代码生成工具链协同。

### 不适用或高成本场景

若需求重点是开放并发、分布式交互或跨工具可移植交换，`Stateflow` 的封闭生态和顺序化语义会带来较高成本。

## 与相邻形式主义的关系

相对经典 `Statecharts`，`Stateflow` 更工程化、更依赖工具定义的执行顺序；相对 `SCXML`，它更强调与 `Simulink` 协同而不是开放交换；相对 `Ptolemy` 或 `Modelica` 状态机载体，它更强绑定 `Matlab` 生态。

## 与本研究的关系

### 对 Project 1 的价值

它提供了一个非常典型的工业目标载体：需求生成出的状态机若要进入现有工程链，`Stateflow` 是现实世界里的高频落点之一。

### 作为目标形式主义还是中间表示

更适合作为工程目标载体，而不是跨工具中立的中间表示。

### 对需求到模型生成的启发

如果需求最终要喂给 `Simulink/Stateflow` 工具链，那么生成阶段必须考虑顺序化优先级、junction 结构和安全子集约束，不能只生成抽象的层次状态图。

### 现实限制

它的形式语义依赖工具真实行为，开放交换格式和跨平台可移植性较弱。
