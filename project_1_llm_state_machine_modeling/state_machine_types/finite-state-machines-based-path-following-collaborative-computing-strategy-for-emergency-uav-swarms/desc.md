## 简报

这篇论文把“无人机沿路径飞行、网络拓扑随时间变化、机载资源又彼此异构”三个问题压到一个统一状态机模型里。作者不是只把 `FSM` 当成任务调度标签，而是构造了 `Extended Finite State Machine Space-time Graph (EFSMSG)`，把每架 `UAV` 的资源状态、跨时隙连接关系和任务 `DAG` 映射统一到一个延迟优化问题中。

- 形式主义定位：面向应急 `UAV` 群协同计算的扩展状态机-图模型，其中状态机负责描述机载资源状态与状态转移，图结构负责描述跨时隙通信。
- 构造方式简述：先建立路径跟随的空间时间图 `SG`，再给每架 `UAV` 添加 `FSM` 资源状态，最后把任务 `DAG` 映射到 `EFSMSG` 上求最小处理时延。
- 基础设施与场景简述：依托 `MATLAB` 仿真、`CSABPSO`、任务 `DAG`、时隙化 `UAV` 编队拓扑和异构机载计算资源，服务应急救援低时延任务卸载场景。

```text
应急任务 DAG -> UAV 状态机 + 空间时间图 -> EFSMSG -> 映射优化 -> 最小时延协同计算
```

## 形式主义定义与核心对象

### 定义对象

论文中的关键对象包括：

1. 单机 `UAV` 的有限状态机资源模型。
2. 路径跟随条件下的空间时间图 `SG`。
3. 结合状态与拓扑的 `EFSMSG`。
4. 任务 `DAG` `\Phi = (\Psi, \Gamma)`。
5. 子任务到 `UAV` 状态节点的映射矩阵。
6. 跨时隙缓存与链路延迟。
7. 用于求解最小时延映射的 `CSABPSO` 算法。

### 核心抽象

论文给出单架 `UAV` 的状态机模型为：

$$
S_{\mathrm{UAV}} = \{Q, E, \delta, q_0, O\}
$$

上式中的符号逐项解释如下：

1. `Q` 是该 `UAV` 的有限状态集合，对应不同机载资源或处理阶段。
2. `E` 是触发条件集合。
3. `\delta` 是状态转移关系。
4. `q_0` 是初始状态。
5. `O \subseteq Q` 是终止状态集合。

原文进一步把路径跟随网络与资源状态结合成加权图：

$$
G_p =
\begin{bmatrix}
G_p^1 & G_p^{1,2} & \cdots & \infty \\
\infty & G_p^2 & \cdots & \infty \\
\vdots & \vdots & \ddots & G_p^{n-1,n} \\
G_p^{n,1} & \infty & \cdots & G_p^n
\end{bmatrix}
$$

上式中的符号逐项解释如下：

1. `G_p^k` 是第 `k` 个时隙内的状态-资源加权子图。
2. `G_p^{k,k+1}` 是相邻时隙间的通信/缓存连接。
3. 整个矩阵把“同一时隙内状态转移”和“跨时隙数据传输”放进一个统一图结构。

任务模型用 `DAG` 表示：

$$
\Phi = (\Psi, \Gamma)
$$

其中：

1. `\Psi = \{\phi_1, \ldots, \phi_q\}` 是子任务集合。
2. `\Gamma` 是子任务间依赖关系。

论文把问题转成映射优化：

$$
X^\ast = \arg \min T(X)
$$

上式中的符号逐项解释如下：

1. `X` 是子任务到 `UAV` 状态-时隙节点的映射矩阵。
2. `T(X)` 是由通信时延和计算时延共同构成的总处理时延。
3. `X^\ast` 是最优映射策略。

### 一个最小例子与通俗解释

论文用图像处理任务说明模型的工作方式。最小例子可以理解为：

1. 某架 `UAV` 先处在 `Search` 状态，发现目标后进入 `Photograph`。
2. 图像并不一定在同一架 `UAV` 上完成所有处理步骤，而是可能跨多个 `UAV` 和多个时隙分摊。
3. 每个子任务例如 `Grayscale`、`Binarization`、`Denoising` 都必须映射到具备对应处理状态的节点。
4. 如果当前链路断开，数据会在当前 `UAV` 缓存到下一时隙，再继续传输或计算。

通俗地说，这个模型像一个“会随队形移动的分布式流水线”：状态机告诉你每架无人机现在会什么、能切到什么状态，空间时间图告诉你现在和下一时隙谁能连上谁，任务 `DAG` 决定每一步计算该落到哪里。

### 运行 / 接受 / 转移语义

状态机与任务映射的运行语义可压缩为：

$$
\phi_i \xrightarrow{B,Z} \left(u_d^k, f_l\right)
\xrightarrow{\delta \text{ or link}} \left(u_h^w, f_{l'}\right)
$$

上式中的符号逐项解释如下：

1. `\phi_i` 是某个子任务。
2. `B` 是子任务到状态节点的映射。
3. `Z` 是子任务边到 `EFSMSG` 路径的映射。
4. `(u_d^k, f_l)` 表示第 `k` 个时隙、第 `d` 架 `UAV` 的某个状态节点。
5. `\delta` 表示同一 `UAV` 内的状态转移。
6. `link` 表示跨 `UAV` 或跨时隙传输。

此外，论文明确给出映射矩阵约束：

$$
x(\phi_i, u_d^k) \in \{0,1\},
\qquad
\sum_{u_d^k \in U_T} x(\phi_i, u_d^k) = \rho_i + 1
$$

这里：

1. `x(\phi_i, u_d^k)` 表示子任务是否映射到某个状态-时隙节点。
2. `\rho_i` 是子任务跨越的时隙数。

### 语义边界

这个模型的边界主要是：

1. 它是“资源与链路调度状态机”，不是低层飞控状态机。
2. 它依赖已知或可预测的路径跟随轨迹与时隙划分。
3. 它强调延迟优化，不直接讨论飞行安全控制或任务成功率之外的物理约束。
4. 它更接近分布式计算图模型，而不是传统控制软件里的事件驱动状态图。

### 关键性质与判定边界

| 问题 / 性质 | 形式化写法 | 原文意义 |
|---|---|---|
| 单机资源状态机 | `$S_{\mathrm{UAV}} = \{Q, E, \delta, q_0, O\}$` | 每架 `UAV` 的机载资源与处理阶段由有限状态机刻画。 |
| 时空加权图 | `$G_p$` | 同时表示时隙内状态关系和跨时隙通信关系。 |
| 任务模型 | `$\Phi = (\Psi, \Gamma)$` | 整体任务被写成依赖 `DAG`。 |
| 优化目标 | `$X^\ast = \arg \min T(X)$` | 本质问题是最小化子任务映射后的总时延。 |

## 关键特性

| 维度 | 支持情况 | 说明 |
|---|---|---|
| 状态 / 模式 | 强支持 | `UAV` 处理资源被显式写成状态集合。 |
| 事件 / 触发 | 强支持 | 任务发现、处理成功、链路可用等都可触发状态/路径变化。 |
| 守卫 / 数据 | 强支持 | 资源能力、链路延迟、跨时隙缓存和任务依赖共同决定可行映射。 |
| 层次 | 弱支持 | 更像“状态机 + 图”的组合，不是层次状态机。 |
| 并发 / 同步 | 强支持 | 多架 `UAV` 和多时隙协同是模型核心。 |
| 时间约束 | 强支持 | 时隙结构和总时延优化是主体。 |
| 连续动态 / 随机性 | 弱支持 | 飞行连续动力学被路径跟随前提抽象掉了。 |
| 可执行 / 可验证性 | 强仿真、弱工程验证 | `MATLAB` 仿真完整，但缺少工程级实现细节。 |

### 形式化问题与性质

1. 论文把“状态机”从传统控制逻辑扩展到“机载资源能力描述”，这是本条目最值得保留的点。
2. `EFSMSG` 的关键贡献是把状态转移和通信拓扑合并成单一优化图，而不是分开建模。
3. 任务 `DAG` 到 `EFSMSG` 的映射让状态机成为协同计算问题的直接求解载体。
4. 这说明应用型状态机并不一定描述设备模式，也可以描述“资源状态 + 服务可用性”。

## 构造方式与承载格式

### 建模入口

建模入口主要包括：

1. 先用空间时间图 `SG` 固定路径跟随网络。
2. 为每架 `UAV` 建立资源状态机 `S_{\mathrm{UAV}}`。
3. 把状态节点嵌入时隙化图中形成 `EFSMSG`。
4. 把应急任务写成 `DAG`，再求最优映射矩阵。

### 机器可处理承载方式

原文直接给出的承载方式包括：

1. `FSM` 状态集合和状态转移。
2. 加权邻接矩阵形式的 `EFSMSG`。
3. 子任务 `DAG` 与映射矩阵 `X`。
4. `CSABPSO` 粒子群优化表示。

### 交换与互操作

互操作重点在：

1. 任务 `DAG` 子任务必须映射到拥有对应处理状态的 `UAV`。
2. 若链路中断，数据可在当前 `UAV` 缓存并跨时隙继续转发。
3. 传输与计算都体现在同一加权图中，因此可统一计算总时延。

## 适用场景与需求前提

### 适用场景

适合应急救援、灾害观测、低时延图像处理、飞行中协同卸载等“路径已知但资源异构”的多 `UAV` 任务。

### 需求前提

1. `UAV` 编队具有可预期的路径跟随行为和时隙划分。
2. 任务能够写成具依赖关系的 `DAG`。
3. 各 `UAV` 的处理状态和资源能力可枚举。
4. 优化目标以通信/计算时延最小化为主。

### 不适用或高成本场景

如果 `UAV` 轨迹完全不可预测、链路极端不稳定、或者任务目标主要是安全控制而不是协同计算，这个模型就不合适；若需要解释复杂飞控逻辑，它也过于抽象。

## 与相邻形式主义的关系

相对传统 `SFC` 或静态服务链调度模型，它显式考虑了路径跟随导致的动态拓扑；相对普通 `FSM`，它把时空图和状态机融合；相对纯任务 `DAG` 调度模型，它又补上了“哪些节点在什么时隙具备何种处理状态”的可行性约束。

## 与本研究的关系

### 对 Project 1 的价值

这篇条目说明状态机不仅能描述控制器行为，也能描述“资源状态和服务过程”，这对后续把复杂需求压成可求解中间表示很有启发。

### 作为目标形式主义还是中间表示

它更适合作为分布式协同计算问题的中间表示，而不是最终交付给控制软件工程师的执行状态图。

### 对需求到模型生成的启发

1. 需求里的“谁能做什么、何时能做、做完后如何转交”很适合落成状态机资源模型。
2. 生成状态机时不一定只生成控制模式，也可以生成任务/资源映射约束。
3. 对多主体系统，状态机和图模型可以联立而不是二选一。

## 重要的相关工作

- `SFC` 与静态协同卸载研究：是论文明确对比的上一代路线。
- `task DAG` 应急图像处理模型：为 `EFSMSG` 提供典型任务载体。
- `CSABPSO`：是该状态机图模型的关键求解器。
