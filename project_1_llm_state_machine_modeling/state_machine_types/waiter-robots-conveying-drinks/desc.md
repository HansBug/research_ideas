## 简报

这篇论文的重点不是一般路径规划，而是一个很具体的问题：**机器人在餐厅里送饮料时，如何在不洒出的前提下仍然保持可接受的运行效率**。作者把 step-velocity、ramp-velocity 和 S-velocity 当作三类可切换运动行为，再用 `SMACH` 把“空载返回”“送餐”“送饮料”这些场景压成不同状态与转移。

- 形式主义定位：面向餐厅服务机器人的运动策略状态机，核心是根据载荷与任务语义切换合适速度曲线。
- 构造方式简述：通过 `Dock` 选择策略，通过各类 `Cruise`、`smooth throttle`、`smooth brake` 状态生成期望速度。
- 基础设施与场景简述：依托 `ROS navigation`、`move_base`、`AMCL`、速度编码器和障碍感知，服务餐饮场景中的送餐、送饮料和回位。

```text
订单/载荷类型 -> Dock 选择 motion strategy -> Cruise / throttle / brake -> 速度指令 -> waiter robot 导航执行
```

## 形式主义定义与核心对象

### 定义对象

论文中的关键对象包括：

1. `VelProSMACH_V2` 状态机。
2. `Dock` 状态，作为策略切换中心。
3. 多个 `Cruise` 状态，用于不同速度档位的巡航。
4. `smooth throttle` 与 `smooth brake` 非反应式状态。
5. step / ramp / S-velocity 三种速度曲线。
6. 任务输入、当前速度、剩余距离、障碍物距离和定位信息。

### 核心抽象

按论文结构，可将其保守整理为：

$$
\mathcal{W} = (Q, q_0, \Sigma, \delta, V, \Lambda)
$$

上式中的符号逐项解释如下：

1. `Q` 是状态集合，如 `Dock`、`Cruise`、`smooth\ throttle`、`smooth\ brake`、terminal docking。
2. `q_0` 是默认普通导航状态。
3. `\Sigma` 是输入事件集合，包括任务类型、载荷类别、goal proximity、obstacle proximity 和当前 twist command。
4. `\delta` 是状态转移函数。
5. `V` 是可选速度生成策略集合，即 step、ramp 和 S-velocity。
6. `\Lambda` 是各状态对应的速度生成与切换逻辑。

论文给出的 S-curve 速度生成核心公式为：

$$
v_i = v_{i-1} + dv_i
$$

$$
dv_i = dv_{i-1} + |j| \operatorname{sgn}(j)
$$

上式中的符号逐项解释如下：

1. `v_i` 是当前离散时刻的速度命令。
2. `v_{i-1}` 是前一时刻速度命令。
3. `dv_i` 是当前时刻的速度增量。
4. `dv_{i-1}` 是上一时刻速度增量。
5. `j` 用来区分 S 曲线的 concave / convex 段。
6. `\operatorname{sgn}(j)` 在加速和减速阶段分别控制 jerk 方向。

状态转移可保守写成：

$$
q_{t+1} = \delta(q_t, \sigma_t, \hat{v}_t, d_t, o_t)
$$

上式中的符号逐项解释如下：

1. `q_t` 是当前运动策略状态。
2. `\sigma_t` 是任务/载荷语义，例如“空载”“送餐”“送饮料”。
3. `\hat{v}_t` 是当前速度级别。
4. `d_t` 是到目标的剩余距离。
5. `o_t` 是障碍物和局部导航相关观测。

### 一个最小例子与通俗解释

最小例子可以直接用“送一盘饮料到桌边”：

1. 系统收到任务，`Dock` 判断当前载荷属于液体饮品。
2. 因为液体对起停 jerk 敏感，状态机从默认 step-velocity 切到 S-velocity 策略。
3. 机器人在 `Cruise` 状态中按剩余距离和障碍情况决定是进入 `smooth throttle` 还是 `smooth brake`。
4. 在加速/减速窗口内，这两个状态是非反应式的，保证 S 曲线不会被中途打断。
5. 接近目标时，状态机进入 terminal docking，用更小步长靠近桌边。
6. 送达后若要空载返回，`Dock` 再切回默认的 step-velocity 策略。

通俗地说，这个模型像“餐厅驾驶模式切换器”。同一台机器人在不同任务下不是一套通用速度，而是像汽车切换到不同驾驶模式。

### 运行 / 接受 / 转移语义

其运行语义可保守写成：

$$
(q_t, x_t) \xrightarrow{\Lambda(q_t)} v_t \xrightarrow{\mathrm{publish}} q_{t+1}
$$

上式中的符号逐项解释如下：

1. `q_t` 是当前运动状态。
2. `x_t` 是 `AMCL`、twist、目标位置和障碍物信息等观测。
3. `\Lambda(q_t)` 表示当前状态绑定的速度生成逻辑。
4. `v_t` 是当前周期发布的速度命令。
5. `q_{t+1}` 是依据速度、距离和场景逻辑切换后的下一状态。

对 `Dock` 状态，可进一步理解为一个策略选择器：

$$
\Lambda(\mathrm{Dock}) : \sigma_t \mapsto V
$$

即把任务语义映射到合适的速度曲线类型。

### 语义边界

这个模型的边界包括：

1. 它只管“如何移动更稳”，不重新发明全局导航。
2. 状态机依赖 `ROS navigation` 提供路径与局部避障底座。
3. `S-velocity` 的 jerk 参数需要针对机器人硬件标定。
4. 非反应式加减速窗口会带来响应迟滞，不适合极端动态环境。

### 关键性质与判定边界

| 问题 / 性质 | 形式化写法 | 原文意义 |
|---|---|---|
| 多策略状态机 | `$\mathcal{W} = (Q, q_0, \Sigma, \delta, V, \Lambda)$` | 运动控制不再是一条固定速度曲线，而是可切换策略集合。 |
| S 曲线速度更新 | `$v_i = v_{i-1} + dv_i$` | 当前速度由上一时刻速度与增量递推得到。 |
| S 曲线加速度更新 | `$dv_i = dv_{i-1} + |j| \operatorname{sgn}(j)$` | 通过受控 jerk 生成平滑起停。 |
| 状态转移依赖任务与环境 | `$q_{t+1} = \delta(q_t, \sigma_t, \hat{v}_t, d_t, o_t)$` | 载荷类型、剩余距离和障碍共同决定策略切换。 |

## 关键特性

| 维度 | 支持情况 | 说明 |
|---|---|---|
| 状态 / 模式 | 强支持 | `Dock`、多种 `Cruise` 和平滑加减速状态都很明确。 |
| 事件 / 触发 | 强支持 | 订单类型、goal proximity、障碍邻近和 move base 命令都会触发转移。 |

| 并发 / 同步 | 弱支持 | 重点是单机器人运动策略切换。 |

| 连续动态 / 随机性 | 中等连续、无随机 | 连续速度变化很重要，但高层状态机仍是离散的。 |

### 形式化问题与性质

1. 论文回答的是“任务语义如何选择运动曲线”。
2. `Dock` 作为 strategy hub，是该条目最值得抽象的状态机对象。
3. `smooth throttle / brake` 的非反应式窗口体现了应用型状态机的一个常见取舍：稳定性优先于即刻响应。
4. 实验上，S-velocity 将平均 docking radius 从 `329.6 mm` 降到 `233.8 mm`，并把洒出次数从 `20/20` 降到 `0/20`。

## 构造方式与承载格式

### 建模入口

建模入口主要包括：

1. 先识别服务场景中的几类载荷和对应速度需求。
2. 把 step、ramp、S 三种曲线抽成可切换行为策略。
3. 用 `Dock` 管理高层策略切换。
4. 用 `Cruise`、`smooth throttle`、`smooth brake` 管理局部速度调节。
5. 最后把状态机接到 `move_base` 和速度发布节点上。

### 机器可处理承载方式

原文直接给出的承载方式包括：

1. `VelProSMACH_V1.py` 与 `VelProSMACH_V2.py`。
2. `SMACH` 状态机图。
3. 基于 Python 值增量操作的 S-velocity 生成逻辑。
4. 与 `ROS` twist command、`AMCL` 和导航节点相连的状态输入输出。

### 交换与互操作

互操作重点在：

1. `Dock` 读取订单/载荷语义并决定策略。
2. `Cruise` 读取 `move_base` 指令、当前位置和障碍距离决定提速/减速。
3. 状态机输出新的 twist command 给底层导航。
4. 若整合点餐系统，还可由订单系统直接决定使用 strategy 1/2/3。

## 适用场景与需求前提

### 适用场景

适合餐厅、酒店、医院配餐等需要移动机器人在“空载快速移动”和“载液平稳移动”之间切换的场景。

### 需求前提

1. 任务类型或载荷类型可被明确分类。
2. 机器人已有稳定导航底座。
3. 速度曲线与 jerk 对任务成败有显著影响。
4. 可以接受为平稳性牺牲一部分响应速度和总时长。

### 不适用或高成本场景

若环境极其动态、需要毫秒级重规划，或者机器人负载变化太复杂无法简单分类为三种策略，这种手工设计的多速度状态机会较快失去优势。

## 与相邻形式主义的关系

相对普通 `move_base` 导航，它多了一层任务语义驱动的速度策略切换；相对行为树，它更强调离散状态与 jerk-limited 运动曲线绑定；相对通用 `SMACH` 任务流，它更专注于一个很窄但很关键的“运动风格监督器”。

## 与本研究的关系

### 对 Project 1 的价值

它很好地展示了自然语言里的“送饮料要稳、送餐可稍快、回位最快”这种业务语义，如何被压成显式状态和速度策略。

### 作为目标形式主义还是中间表示

对服务机器人而言，它可以直接作为可执行目标监督器；对更大系统来说，它也可作为导航模块内部的中间控制层。

### 对需求到模型生成的启发

1. 需求中的载荷类型、舒适性目标和场景语义适合直接转成状态机模式名。
2. LLM 生成状态机时不应只抽“到达/避障”，还应识别“运动风格切换”。
3. 低层速度曲线参数可以挂在状态上，而不是散落在控制脚本里。
4. 应用型状态机的优劣往往可由具体性能指标直接验证，如 spill ratio 和 docking radius。

### 现实限制

该模型对硬件标定、餐厅空间尺度和 `ROS` 导航配置较敏感，跨平台时需要重新调 S-curve 参数。
