ABSTRACT Real-time audio/video transmission through Internet media is an important part of
communication. Due to bandwidth limitations and a noisy environment, delivery of multimedia content to
a remote location is not 100% guaranteed. These limitations are the basic cause of missing packets which
affect the Quality of Service (QoS). A protocol for the recovery of lost packets is described in [Maxemchuk,
Nicholas F., K. Padmanabhan, and S. Lo. ‘‘A cooperative packet recovery protocol for multicast video.’’
Network Protocols, 1997. Proc. of 1997 International Conference on. IEEE]. This protocol claims significant
improvement in QoS. We formally specify the protocol in a network of timed automata. By model-checking
(A mathematical technique), we find that packet recovery is not always there. In this article, We report
such scenarios of malfunctioning in the protocol when the size of multimedia contents is known (e.g.,
live video/audio broadcasting) and middle-level servers have different rates of data sending and receiving.
We formulate the effect of inter-packet delay and transmission speed difference on a buffer.

I. INTRODUCTION
There is a massive increase in video communication over
the Internet because of the high data rate [1]. The primary
concern is quality of service (QoS), particularly in critical
systems [2],[3],[4], and [5], where a little mistake may cause
big problems. Heterogeneity in communication networks
reduces QoS in multimedia communication. There are several
challenges in designing communication protocols to achieve
a good QoS, for example, bandwidth limitation, massive
network traffic, packet congestion, and many more. Packet
loss in communication is a significant factor for QoS. Packet
Loss Ratio (PLR) must be less than 1% for achieving good
QoS in video conferencing [6].

III. COOPERATIVE PACKET RECOVERY PROTOCOL
A source, a server, a client and some receivers are the basic
structural components of the protocol. The basic architecture
of the packet recovery protocol is shown in Figure 1. In this
protocol, the source broadcasts packets for the client and the
server. The server is called the ‘‘retransmit server’’ because
it transmits a packet if the client requests a lost packet. All
packets have their sequence numbers in which the source
broadcasts them. The server receives packets from the source
and stores them in its buffer. According to the protocol [7],
it is least likely that the server misses a packet sent by
the source. The client also receives packets from the source
and stores them in the proper place in its buffer. If the
client receives a packet with a higher sequence number than
expected, then it sends a NACK request to the server to
recover the missing packet(s). After receiving packets from
the source in a proper sequence, the client broadcasts packets
to the receivers in a proper sequence. According to [7],
the basic architecture was practically implemented between
Indian Hill, Chicago and Murray Hill, New Jersey as shown
in Figure 1. Live multimedia transmission was started from
Indian Hill for the Murray Hill viewer.
The basic architecture is further extended into a large
network. There is a number of receivers located in different
areas, so there is a number of clients for each area, as shown
in Figure 2. In extended architecture, the server is modified to
cater to multiple clients instead of a single client. The server
receives multiple NACK requests from the clients and stores
them in a queue and responds to them in the same sequence.
There are two different architectures based on the
communication channels between the server and clients.

We use the UPPAAL toolset for the formal specification
of the protocol. UPPAAL is a model-checking toolset for
the verification of distributed real-time systems. There is a
graphical user interface to specify a process formally. We can
verify the functional requirements by behavioral simulation
of concurrent processes. There are two essential elements,
a location and an edge (so-called transition), to specify
states and actions, respectively. A circle represents a location;
if it is initial state, it is a double-lined circle. A state
can also be committed if the actions from this state are
without interleaving the action from other states that are not
committed. In other words, actions from a committed state
get priority w.r.t. non-committed states. So, an action from
a committed state/location must be taken to avoid deadlock.
The purpose of an edge is to take some action where taking
action can be conditional, i.e., a guarded action. During an
action, values, and communication can be updated between

ARCHITECTURES
As discussed in Section III, two architectures are proposed for
the extended version of the protocol [7]. The architectures are
shown in Figures 2and3. We verify both architectures of the
protocol. Specification difference between both architectures
is given below;
A. ARCHITECTURES 1
In architecture 1, a unicast channel is used to send repair
packet(s) from the server to the client. Repair packets are
only sent to the requested client. For this purpose, we send
the client ID with the packet. We perform the following set of
actions to model this behavior,
•The client sends its process ID with the NACK
request (sendNack[cid] [packet2Recover]) when the
client needs to recover a packet.
•The server receives packets from the client with client-
ID (sendNack[cid][lostpacket]) and stores packets in the
packet-ID and client-ID in the nack-ID buffers.
•Repair packets are sent to the requested client with
client-ID via sendRepairpkt [id][lostPacket] channel.
•The client receives a repair packet with client’s ID so the
requested client can only receive the repair packet.
The number of NACK requests is greater in this model
because the server independently deals with NACK requests
from all clients. For example, if two clients send NACK for
the same packet, the server sends repair packets one by one.
B. ARCHITECTURES 2
In architectures 2, a broadcast channel (sendRepairpkt
[lostPacket]) is used to send repair packets from the server to
the client. The server sends a repair packet to all clients when
any client sends a NACK request. The number of NACK
requests is less than architecture 1 because the server sends

IX. LIMITATION AND CHALLENGES
The limited size of the computer’s main memory is the main
limitation in the model checking using the UPPAAL toolset.
The system model generates an ample state space. It causes
a state space explosion problem, a big challenge to modeling
a system. In this article, we verify the extended architecture
of cooperative recovery protocol. We design a system model
with two clients (Client(0) and Client(1) and three receivers
(Receiver(0), Receiver(1) and Receiver(2) for each client
because of limited main memory. We verify the system model
for the limited size of packets and limited buffer size in the
clients and the server. The functional properties of the system
models are not affected by these limitations because limited
data and buffer size, along with few numbers of clients and
receivers, can reflect the whole behaviour of the protocol.
X. CONCLUSION
In the cooperative packet recovery protocol, Nicholas F.
Maxemchuk et al. claim QoS improvements in multicast
communication. They introduce a server, a closed link with
the source. This server stores packets in its buffer and recovers
a packet if the packet is reported as lost. We formally
verify their claim by specifying the protocol for four basic
components (Source, Server, Client, and Receivers) using
the UPPAAL toolset. We extract the protocol’s functional
requirements and formalise them [7]. We verify the system
model for these formalise function requirements and report
the scenarios where these requirements are unsatisfied by
using a message sequence chart. We design a mathematical
model to determine the size of the active part of the buffer in
communication. We also express the effects of inter-packet
delay and speed difference on the active part of the buffer
using MATLAB graphs.
