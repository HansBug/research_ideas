gr1c: a tool for interactive and incremental
reactive synthesis
Scott C. Livingston
January 21, 2024
Abstract
gr1c is an open source tool suite for GR(1) synthesis and related ac-
tivities. Development is motivated by current research in formal methods
for robotics, including motion planning with temporal logic specifications.
It has several novel features beyond a fast implementation of basic GR(1)
synthesis. Users can interact with binary decision diagrams (BDDs) and
make live queries to intermediate values of a µ-calculus fixed-point com-
putation, which in turn provide the basis for strategy automaton con-
struction. Another novel feature is the ability to load an existing strategy
and modify parts of it following changes to the original specification. Be-
sides visual formats intended for human review, gr1c can produce output
in standard formats, including JSON, that enable integration with other
tools. To support verifying results, output can be in Promela, which al-
lows model checking by Spin.
1 Introduction
The primary distinction of formal synthesis from other problems in control the-
ory is the specification of desired behavior in a formal language such as linear
temporal logic (LTL). In this work, we are concerned with reactive synthesis for
the fragment of LTL called generalized reactivity rank 1, or GR(1) [7]. Speci-
fications in GR(1) have solutions that produce trajectories of infinite duration
and that are defined by discrete steps taken in turn with an adversarial envi-
ronment. Intuitively, the problem is to find a strategy that guarantees a set
of goals will be reached repeatedly, assuming that the environment repeatedly
satisfies a set of its own goals. Precisely, the specification is

Despite its apparent simplicity, many different kinds of LTL formulae can be
rewritten in the GR(1) template. Application to more general dynamical sys-
tems (e.g., having dense time) is achieved by constructing discrete abstractions
that model the original system in a way where synthesis can be applied, e.g.,
through bisimulation [1].
In this paper, we provide a brief introduction to gr1c , a tool suite for
GR(1) synthesis and related activities. The source code is available at https:

2 Related work
gr1c was first released in the year 2012. Before it, the first implementation of
GR(1) known to the authors was in Java with JTLV [11], [12]. This tool had the
advantage of being easy to distribute because it required only an appropriate
version of the Java VM installed. However, it was released as an opaque JAR
file and eventually not maintained. For research that requires modifying the
basic fixed-point process, something new was required. Thus motivated, and to
overcome performance and usability concerns with that first implementation,
gr1c was created.
Since the beginning, gr1c has been developed to support integration with
other software, in particular the Temporal Logic Planning toolbox, Tulip [4].
Tulip is written in Python and supports expressing and solving formal synthesis
problems with hybrid systems. Internally, Tulip passes part of a problem to
GR(1) solvers, such as gr1c , and incorporates the resulting strategy into the
solution of the original problem. More recently, the default solver in Tulip is
omega , a Python package that can do GR(1) synthesis and more [5]. Documen-
tation is available at http://tulip-control.org
Perhaps the most similar tool is Slugs [3]. Unlike gr1c , which is written in
standard C and emphasizes performance, Slugs is written in C++ and prior-
itizes easy extension. The Slugs distribution includes plugins that implement
algorithms from the authors’ research, such as adding costs or producing reports.

1. compute the winning set, i.e., the set of states from which there is some
strategy that guarantees satisfaction of the specification;

Completing the first step and checking whether initial states are contained in
the winning set, without constructing an explicit strategy, is known as checking
realizability . Most of the computation is performed in terms of sets of states
using binary decision diagrams (BDDs) [2]. The winning set is found by iterating
aµ-calculus formula until a fixed point is reached [8]. Currently, the only
supported external package of BDD operations is CUDD (CU Decision Diagram)
[13]. Work is in progress to support other BDD packages.
The sets created during fixed-point iterations are known as sublevel sets .
With these, a strategy is constructed by successively moving into inner subsets
until a goal state is reached and, then, repeating this for the next system goal.
Note that the environment may take different actions at each state, so the
(system) strategy must have an action to take in response for each. Moving into
the next sublevel set is not necessarily possible at a given time, but because
of the environment liveness assumption, eventually it will be. This setting is
illustrated in Figure 1.
3.2 Syntax example
Problems are specified in a plaintext file format. Variables are declared as
Boolean or as having domains of ranges of integers. LTL operators □,□, and⃝
are written as [],<>, and ’(primed variable), respectively. Initial constraints,
transition rules, and goals are written in separate blocks with names ENVINIT ,
etc.
For example, the following specification defines two variables, where xis
uncontrolled and is assumed to repeatedly toggle True andFalse . The synthesis
problem is to repeatedly have ybeTrue when xis, while also repeatedly have
ybeFalse .

4 Interactivity
If started with the command-line flag -i,gr1c will compute the sublevel sets
from the fixpoint computation of the winning set and then start a prompt for in-
teractively probing the data structures, modifying the specification, and finding
feasible environment and system actions from any given state.
For example, the following session uses the first specification above.
>>> var
x (0), y (1)
>>> numgoals
2
>>> printgoal 0
(y&x)
>>> printgoal 1
(!y)
>>> sysnext 1 1 1 1
0
---
The first four commands are self-explanatory. The final command, sysnext ,
gets all feasible next system states that make progress (in terms of winning
sets) toward the goal !yfrom state 1 1(xandyboth True ). Other commands
are available to investigate intermediate values (as outlined in Section 3.1 and
Figure 1). Enter help to get a summary of all available commands.
A Python wrapper for interactive sessions is included in Tulip. Finally, there
is optional linking with GNU Readline for an enhanced prompt with command
history, etc.

6 Model checking
While algorithms for formal synthesis produce controllers that are “correct-by-
construction,” in practice there can be errors in the implementations of solvers
that result in controllers that are not correct. These errors can go unnoticed
because nontrivial specifications have complex solutions that are difficult to
inspect. This practical issue is especially relevant in research, where new code
6

--- Page 7 ---
is written but often not subject to rigorous review, in contrast to algorithms
written in papers. To protect against this, gr1c can express strategies in the
Promela language of Spin [6], thereby facilitating model checking.
7 Conclusion
Now more than 11 years old, development and growth of gr1c is ongoing. Most
uses of gr1c have been in research. Future work will also be in practical appli-
cations by leveraging the generality, speed, and quality of its implementation.
