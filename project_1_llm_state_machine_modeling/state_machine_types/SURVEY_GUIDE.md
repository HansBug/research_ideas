# `state_machine_types/` 的 `survey.md` 编写规范

本文档用于规范 `project_1_llm_state_machine_modeling/state_machine_types/*/survey.md` 的写法。它服务于 `project_1` 的“状态机类型谱系”建设，目标不是写泛泛综述摘要，而是把一篇 survey/review/mapping study 中对多个状态机族形式主义的分类框架、比较维度、生态观察和研究缺口整理成可直接用于扩库和选型的文档。

## 1. 使用前提与阅读顺序

开始编写单篇 `survey.md` 前，必须先完成以下阅读顺序：

1. [README.md](./README.md)
2. [GUIDE.md](./GUIDE.md)
3. [SUMMARY.md](./SUMMARY.md)
4. 当前论文目录下的 `bibtex.bib`
5. 当前论文目录下的 `paper_content.txt`
6. 必要时核对 `paper.pdf`

## 2. 何时使用 `survey.md`

以下情况默认使用 `survey.md`：

1. 论文标题或正文明确属于 `survey`、`review`、`mapping study`、`taxonomy`、`state of the art`。
2. 论文主要贡献是跨多个状态机族形式主义进行系统比较。
3. 论文核心价值是给出分类轴、比较框架、生态版图或研究缺口，而不是定义单一形式主义。
4. tutorial、retrospective 或 handbook 章节虽不自称 survey，但正文主要组织多个形式主义的比较时，也应归入 `survey.md`。
5. 方法路线类综述只有在能反向导出“应继续补哪些模型本体、标准或工具线”时，才值得正式收录。

以下情况默认不使用 `survey.md`：

1. 单一形式主义的 tutorial 或标准说明。
2. 主要仍在讲一个形式主义，只在 related work 中顺带比较其他类型的论文。
3. 纯应用/案例综述，若它主要描述领域落地经验，而不能稳定回溯到形式主义本体或基础设施。
4. 纯方法路线综述，若它主要讲流程或算法，而不能导出值得继续补入的模型本体 / 标准 / 工具线。

这些条目应改用 [DESC_GUIDE.md](./DESC_GUIDE.md) 生成 `desc.md`。

## 3. `survey.md` 的核心目标

每篇 `survey.md` 至少要回答以下问题：

1. 这篇综述覆盖了哪些状态机族形式主义，没有覆盖哪些。
2. 它采用什么分类轴组织这些形式主义。
3. 它如何比较各类形式主义的能力边界、构造方式和工具生态。
4. 它指出了哪些代表性基础论文、标准或工具线。
5. 它对 `project_1` 的形式主义选型与后续扩库有什么直接价值。
6. 它的主对象到底是模型本体、方法路线、标准/基础设施，还是应用/案例。

这里额外固定一条硬约束：

1. `survey.md` 不只是综述摘要，还必须能直接指导下一轮补什么条目。
2. 如果没有抽出可追踪的代表原始文献、标准或工具线，该 `survey.md` 默认不算完成。
3. 如果没有明确判定 `对象类型`，该 `survey.md` 默认不算完成。
4. 本 collection 优先收 `🧱` 与 `🏗️` 类型综述；`🛠️` 只作为辅助导航，`🧪` 原则上不扩张。

## 4. 标题与总格式

### 4.1 文件标题

文件开头默认使用一级标题：

```markdown
# 中文标题 / English Title
```

### 4.2 一级章节顺序

除非材料极端特殊，默认一级章节顺序应为：

1. `## 基本信息`
2. `## 综述范围与结论`
3. `## 覆盖的形式主义版图`
4. `## 分类轴与比较框架`
5. `## 构造方式与表示格式版图`
6. `## 基础设施与生态版图`
7. `## 适用场景与需求映射`
8. `## 对本研究的启发`
9. `## 应追踪的代表原始文献`
10. `## 文献分类总结`

## 5. `## 基本信息` 的固定写法

该章节至少包含以下字段：

1. `标题`
2. `中文标题`
3. `作者`
4. `发表`
5. `DOI`
6. `链接`
7. `综述主题`
8. `对象类型`
9. `覆盖时间范围`
10. `覆盖主类`

紧接着必须写出：

1. `补充材料/数据获取方式`
2. `原文是否给出系统比较表`

## 6. `## 综述范围与结论` 的固定写法

该章节必须用较高密度的方式讲清三件事：

1. 这篇综述到底比较了哪些家族。
2. 它主要从哪些维度比较。
3. 它得出的最关键结论是什么。

推荐至少包含：

1. 一段总述
2. `- 覆盖范围：`
3. `- 主要比较轴：`
4. `- 对本 collection 的直接价值：`

## 7. `## 覆盖的形式主义版图` 的固定写法

该章节必须至少包含一张覆盖表。推荐字段如下：

| 主类 | 形式主义 | 覆盖深度 | 文中角色 | 关键说明 |
|---|---|---|---|---|

其中：

1. `覆盖深度` 可写 `重点 / 一般 / 顺带提及`。
2. `文中角色` 可写 `定义对象 / 对比对象 / 应用对象 / 背景对象`。

## 8. `## 分类轴与比较框架` 的固定写法

该章节必须显式抽出原文使用的分类轴，例如：

1. 离散 vs 时间 vs 混成
2. 状态驱动 vs token 流驱动
3. 图形化 vs 文本化
4. 可执行 vs 可验证 vs 可交换
5. 单体建模 vs 组合/接口建模

如果原文没有直接给表，也要把它的比较逻辑压缩整理出来，但必须有原文依据。

## 9. `## 构造方式与表示格式版图` 的固定写法

这是本论文集特别关注的章节，至少要回答：

1. 各类形式主义主要通过图形、DSL、XML、JSON、元模型还是代码落地。
2. 原文是否比较了交换格式、标准化程度或机器可处理表示。
3. 哪些形式主义在构造方式上最利于自动生成。

推荐至少包含一张对照表：

| 形式主义 | 图形表示 | 文本/DSL | XML/JSON/元模型 | 标准/交换格式 | 说明 |
|---|---|---|---|---|---|

## 10. `## 基础设施与生态版图` 的固定写法

该章节至少从以下维度进行盘点：

1. 建模/编辑工具
2. 仿真/执行工具
3. 验证/分析工具
4. 转换/代码生成工具
5. 标准与社区生态

推荐至少包含一张对照表：

| 形式主义 | 典型工具/平台 | 支持能力 | 生态成熟度 | 备注 |
|---|---|---|---|---|

如果原文没有系统给出工具生态，应明确写“原文未系统比较”。

## 11. `## 适用场景与需求映射` 的固定写法

该章节至少回答以下问题：

1. 哪类形式主义适合事件驱动控制。
2. 哪类形式主义适合时间约束。
3. 哪类形式主义适合并发同步。
4. 哪类形式主义适合连续/混成动态。
5. 它们分别对需求输入提出什么前提。

推荐至少包含一张映射表：

| 形式主义 | 适用场景 | 需求前提 | 不适合的情况 |
|---|---|---|---|

## 12. `## 对本研究的启发` 的固定写法

该章节默认至少包含以下二级标题：

1. `### 对 Project 1 目标形式主义选型的启发`
2. `### 对中间表示设计的启发`
3. `### 对后续扩库方向的启发`
4. `### 原文未覆盖但本研究仍需补的空白`

## 13. `## 应追踪的代表原始文献` 的固定写法

survey 条目不能只停留在“读完综述就结束”。这一章必须把后续值得拆成单篇 `desc.md` 的原始文献线索整理出来。

推荐至少包含以下字段：

| 年份 | 形式主义 / 方向 | 代表原始文献 | 推荐原因 | 后续动作 | 优先级 |
|---:|---|---|---|---|---|

其中 `后续动作` 可写：

1. `优先补单篇 desc`
2. `先找标准/工具论文`
3. `暂记为背景`

其中 `优先级` 默认用 emoji 单列表示，正式写表时单元格只写一个 emoji，例如 `🔴 / 🟠 / 🟡 / ⚪`，中文释义在表前或表后统一解释，不要写成 `🔴 高优先级` 这种形式。

补充约束如下：

1. 该表属于文献跟进表，默认必须包含 `年份` 列。
2. 除非该目录另有 override，否则该表默认按 `年份升序` 排列。
3. 跟进条目优先回填“模型本体”与“标准/基础设施”线；方法路线条目只在能为这些主线提供佐证时再纳入。

## 14. `## 文献分类总结` 的固定写法

章节结尾必须给出一组可直接映射到 [SUMMARY.md](./SUMMARY.md) 综述总表的压缩字段，至少包含：

1. `综述主题`
2. `对象类型`
3. `覆盖主类`
4. `覆盖的形式主义`
5. `是否覆盖构造方式/基础设施`
6. `主要价值`
7. `状态`

## 15. 与 `SUMMARY.md` 的对齐关系

后续单篇 `survey.md` 与 [SUMMARY.md](./SUMMARY.md) 的关系固定如下：

1. `综述主题` 对应综述总表中的 `综述主题`。
2. `对象类型` 对应综述总表中的 `对象类型`。
3. `覆盖主类` 对应综述总表中的 `覆盖主类`。
4. `覆盖的形式主义` 对应综述总表中的 `覆盖的形式主义`。
5. `是否覆盖构造方式/基础设施` 对应综述总表中的同名列。
6. `主要价值` 和 `状态` 分别对应综述总表中的同名列。
7. `## 应追踪的代表原始文献` 中整理出的条目，应同步回填到 [SUMMARY.md](./SUMMARY.md) 的“由综述引出的待跟进原始文献”章节。

换言之：

1. `SUMMARY.md` 中的综述总表是压缩版全局入口。
2. `survey.md` 是该综述对类型版图、比较轴和后续扩库线索的展开版。
3. survey 的真正完成态不是“写完概述”，而是“已经把后续可跟进的条目导流出来”。

## 16. 综述对象类型判定规则

单篇 `survey.md` 必须显式判定一个 `对象类型`，默认从以下四类中四选一：

| Emoji | 对象类型 | 判定标准 |
|---|---|---|
| 🧱 | 模型本体 | 主体在讲形式主义定义、语义、变体、表达力、可判定性边界 |
| 🛠️ | 方法路线 | 主体在讲建模、验证、综合、转换、形式化方法路线 |
| 🏗️ | 标准/基础设施 | 主体在讲标准、交换格式、元模型、API、工具互操作、生态基础设施 |
| 🧪 | 应用/案例 | 主体在讲某领域中的应用、案例、工业采用或经验总结 |

执行细则如下：

1. 只能选一个 emoji，不得并列写多个。
2. 优先看正文主体和作者试图回答的问题，而不是只看题目关键词。
3. 若一篇 survey 同时覆盖模型与方法，但主要在回答“怎么验证/怎么形式化”，判为 `🛠️`。
4. 若同时覆盖模型与工具，但主要在回答“如何标准化承载/交换/集成”，判为 `🏗️`。
5. 若主要在整理某类 automata/petri net/state machine 的分支谱系，则判为 `🧱`。
6. 即使对象类型判成 `🛠️`，也只有在它能继续导流出值得补入的模型本体、标准或工具线时，才应在本 collection 中正式保留。
7. 对象类型若判成 `🧪`，默认应先审查其是否真正服务本 collection 的类型谱系目标；若不能，原则上不收。
