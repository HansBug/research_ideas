# 确定性成分在 LLM 流程中的角色分类学

> ⭐ **本文件是一份方法论定义,不是调研结论。** ⛔ 它定义一套角色划分与判定协议,供 [`tool_roles.md`](./tool_roles.md) 对语料逐项分类时引用,也供 M1 方法重构时定位设计动作。
>
> **来源**:2026-08-13 用户提出五角色划分,⭐ 主 session 补三处改动后冻结。⛔ **本文件冻结后不得为了让某个案例好归类而改判据** —— ⭐ 归不进去的案例记入 §7 待分类,而不是放宽定义。

---

## 1. 这套划分要解决什么问题

⭐ 讨论「LLM 流程里该不该接确定性工具」时,一个反复出现的混乱是:**同一个问题的两侧引用的证据其实在说不同的事。**

⚠️ 实测的三次混乱:

1. ⭐ 有人说「确定性检查器比 LLM 自评好」,⛔ 那是在说**谁裁决**;有人说「确定性工具能提高发现能力」,⭐ 那是在说**什么信号种下发现**。⛔⛔ **两者的因果方向相反**,而它们常被当成同一条主张。
2. ⭐ 三个独立团队报告「往发现阶段注入规则使召回**重新分配而非增加**」,⛔ 而另一篇把 MBD 诊断注入发现阶段并声称有效。⛔ 表面矛盾,⭐ **实际是两个不同角色**。
3. ⭐ 我们自己的流水线「接了 pyfcstm 诊断」⭐ 同时「prompt 禁止据诊断形成需求」—— ⛔ 若只问「接没接」,这两句话无法同时表述。

⭐⭐ **所以需要的不是「有没有确定性工具」这个二值问题,而是「它的输出作用于模型决策过程的哪一个部件」。**

---

## 2. 组织原则

⭐⭐⭐ **判据轴只有一个:该确定性成分的输出,作用于模型决策过程的哪一个部件。**

| 作用于 | 角色 |
| :-- | :-- |
| 模型的**信息状态**(它知道什么) | 信息探索 |
| 信息的**呈现形态**(什么容易被看见、什么装得进上下文) | 表示变换 / 定域 |
| 模型的**目标与约束集**(什么算合格) | 规则建立 |
| 某个命题的**真值** | 求值 |
| **被判对象本身** | 执行操作 |

⭐ 时序位置(前置 / 后置)是这个轴的**推论**而非独立轴:前三个必然前置,后两个必然后置。

⛔⛔ **「提供反馈」不是本轴上的一个值。** ⭐ 它是 **求值 + 处置** 的复合 —— 见 §4。

## 3. 五个角色的判定判据

### 3.1 信息探索

**它让模型知道了它原本不知道的事。**

⭐ **判定动作**:问「若撤掉这个成分,模型还能从现有输入推出这条信息吗?」⛔ 推不出 → 信息探索。

⭐ 典型形态:仿真 / 执行的结果 · 模型诊断(MBD、conflict set、hitting set)· 外部检索到的文档片段 · 一个模型本来要自己重建的配置事实 · 另一个模态里才有的信息(图里有而正文没有的迁移)。

⚠️ **不是信息探索的**:把已在输入里的东西换个格式(→ 表示变换)· 告诉模型该遵守什么(→ 规则建立)。

### 3.2 表示变换 / 定域

**不增加信息,改变可见性与上下文占用。**

⭐ **判定动作**:同 §3.1 的问题,⭐ **推得出 → 表示变换**。⛔ 即它的全部输出在原输入里都已隐含。

⭐ 典型形态:解析成 AST 后抽原子逐个送 · 按章节树切窗 · 列出已声明的元素名 · 把最短路结果当检索键 · 归一化空白与压缩表格。

⭐⭐ **它为什么值得单列**:它**不改变模型的目标,也不给新事实**,但它决定**模型在有限上下文里看到什么**。⭐ 语料里它常被误读成信息探索(「我们把结构信号喂进去了」),⛔ **而它对发现能力的作用机制与信息探索不同** —— 它只能让本来看得见的东西更容易看见,⛔ 不能让看不见的变得看得见。

### 3.3 规则建立

**设定模型的目标与约束集:什么该做、什么不能做、什么算合格。**

⭐ **判定动作**:问「这个输出是关于**制品的事实**,还是关于**该怎么做的规定**?」⛔ 后者 → 规则建立。

⭐ 典型形态:规则目录注入 prompt · 词表附带「必须逐字使用」条款 · schema 的字段约束进 prompt 说明 · 「输出必须满足以下 6 条」。

⛔⛔ **已知风险(有三个独立团队的负面报告,见 [`tool_roles.md`](./tool_roles.md))**:⭐ 规则建立与自然语言规约**是同一类东西** —— 两者都是「该关注什么」的规定,⛔ 所以它们**竞争注意力**。⭐ 观察到的后果是召回**重新分配而非增加**。

### 3.4 求值

**计算某个命题的真值,不改变被判对象本身。**

⭐⭐ **「外部」的可操作判据**:⛔ 不用「系统视角」这种描述,⭐ 用 **「它有没有改变被判对象本身」**。⭐ 写日志、写审计、写 run record → **没改** → 属求值侧;⭐ 改模型文件、改代码、发请求 → **改了** → 属执行操作。

⭐ 典型形态:model checker · SMT / SAT · 编译器(只判能不能编译)· 差分 oracle · 谓词求值 · schema 校验。

### 3.5 执行操作

**改变被判对象本身。**

⭐ 典型形态:agent 调用工具修改模型文件 · 自动重构 · 自动打补丁并落盘。

⭐ **它与求值的边界**就是 §3.4 那条判据。⚠️ 一次工具调用可以**同时**占两个角色(改完再判),⭐ 那种情况按 §6 拆开记。

## 4. ⭐⭐ 求值的第二维:**处置**

⭐ 求值只产出一个真值。**真值拿去干什么,是一个独立的维度**,而它决定了流程的形状。

| 处置 | 含义 | 语料实例 |
| :-- | :-- | :-- |
| ⭐⭐ **记录** | **真值本身就是产物** —— 不回灌、不拦截、不丢弃 | ⭐ 我们的 19 条谓词求值(为假 = 一条发现) |
| **回灌** | 把失败信息送回生产者要求修订(**软**) | 通常叫 reviewer |
| **拦截** | 不许进结果集,但不要求重做(**硬**) | 通常叫 gate |
| ⭐ **丢弃** | **整份产物扔掉、重新采样** | ⭐ LLM-FSM 三道门**全是**这个,⛔ 没有一道是「打回修订」 |
| ⭐⭐⭐ **封存** | ⭐⭐ **真值算出来了,但被刻意从 LLM 的上下文里扣掉**;⛔ 只有「可执行 / 不可执行」这一位放出去,⭐ 真值到流程后段才解封 | ⭐⭐ **我们的 `precheck_and_seal`** —— ⛔ 语料里**无第二例** |

⭐⭐⭐ **为什么必须单列这一维**:

1. ⭐ 「gate」与「reviewer」在文献里被当成两种东西,⛔ **实际是同一次求值的两种处置** —— 把它们并列成角色会掩盖「它们共享一次求值」这个事实。
2. ⭐⭐ **「记录」这个处置在通常的划分里没有格子**,⛔ 而它是我们的核心设计:真值不用于控制流程,**它就是论文的结论**。
3. ⭐ **「丢弃」不等于「拦截」**。⭐ 前者放弃这次采样并重采,后者只是不收这一条。⛔ 语料里有工作用「丢弃」换掉了整套修订机器(产出率 1,500 → 1,000),⭐ 那是一个明确的设计权衡而不是省事。
4. ⭐⭐⭐ **「封存」在通常的划分里也没有格子**,⛔ 而它是本仓库唯一一处、且由类型系统保证的机制 —— 见 §4.1。

### 4.1 ⭐⭐⭐ 「封存」为什么必须单列

⭐ 它与「记录」的区别不在最终去向(两者最终都进产物),⭐ 而在**循环期间 LLM 能不能看到真值**:

- **记录** = 真值算出来直接落进产物,⛔ 不涉及「LLM 看不看得到」这个问题(⭐ 因为没有后续 LLM 步骤)
- ⭐⭐ **封存** = **有后续 LLM 步骤,而真值被刻意扣住不让它看**

⭐⭐ **为什么要扣**:若审查者看得到真值,它就能反向调整断言去凑出「为假」——⛔ **那是一个直接的作弊通道**。⭐ 扣住真值使审查只能针对**可执行性与形式**,不能针对结果。

⭐⭐⭐ **实现层面它是类型系统保证的,不是约定**(⭐ 本仓库实例):放给审查者的类 `AssertionExecutionPublic` 的字段只有 `status: Literal["executable", "invalid", "blocked"]` 与 `error` —— ⛔ **它结构上没有 `truth_value` 这个字段**;真值只存在于另一个类 `AssertionResult` 上,⭐ 而后者经 `SealedAssertionReceipt`(只含 `sealed_hash` / `result_count` / `sealed_payload_ref`)间接引用。

⭐ 配套还有一处刻意的路由选择,源码注释逐字:

> `blocked means a prerequisite did not hold, so this assertion was never run. It is not an execution failure and **must not send the script back for repair -- the prerequisite's own False is the finding**.`

⭐⭐ **即:前置条件为假时,它被路由进产物(记录)而不是修订回路(回灌)** —— ⭐ 这是「记录 vs 回灌」的一次显式取舍,而不是漏做。

## 5. ⭐⭐⭐ 核心原则:**角色是「工具输出 + prompt 框定」的联合属性**

⛔⛔ **角色不是工具的属性。** ⭐ 同一份确定性输出,框定方式不同就落在不同角色上,效果也不同。

⭐ 两个实测实例(都在本仓库自己的代码里):

| 工具输出 | 内容本身是 | prompt 的框定把它变成 | 后果 |
| :-- | :-- | :-- | :-- |
| 已声明元素清单 | ⭐ **表示变换**(列出输入里已有的名字) | ⛔ 附加「必须逐字使用;不在此列的名字不存在」→ **规则建立** | ⭐ 防住了拼错导致断言真空的事故,⛔ 但不指向缺陷位点 |
| 工具诊断 | ⭐⭐ **信息探索的材料** | ⛔⛔ `orientation evidence only` + `never turn a tool warning into a requirement` + `diagnostics alone are not sufficient evidence` → **零角色** | ⛔ 可以看,⛔ 但不能据它形成义务、不能单独当证据 |

⭐⭐⭐ **设计含义**:动作不是「接不接这个工具」,而是 **「把它的输出框定成哪个角色」**。⛔ 一个已接入但被框成零角色的工具,在流程里等于不存在 —— ⭐ 而这种情况**光看依赖列表和架构图看不出来**,必须读 prompt。

## 6. 分类协议

⭐ 对语料逐项分类时,按以下顺序执行。

### 6.1 单位:**一次(成分 × 位置)**,不是一篇论文

⛔ 一篇工作通常有多个确定性成分,且**同一个成分可以在不同阶段占不同角色**。⭐ 分类的单位是 **(成分, 它输出到哪一步, 该步怎么框定它)** 三元组。

### 6.2 必填字段

| 字段 | 说明 |
| :-- | :-- |
| 成分 | ⛔ 具体到工具名 / 算法名,⛔ **不许写「静态分析」这类笼统词** |
| 它算出什么 | ⛔ 具体到产物形态(「哪 2 个 gateway」而不是「问题位置」) |
| 输出到哪一步 | ⭐ 哪个 LLM 调用,或「不进 LLM」 |
| prompt 怎么框定 | ⭐ 逐字引文优先;⛔ 无引文则标 S/I |
| 角色 | ⭐ §3 的五个之一,⛔ 或「零角色」/「不进 LLM」 |
| 处置(仅求值) | ⭐ §4 的**五个**之一:`记录` / `回灌` / `拦截` / `丢弃` / `封存` |
| 有无量化 | ⭐ **有该成分 vs 无该成分**的受控对照 + 两侧数字;⛔ 无则明写「无对照」 |
| 证据级别 | M / S / I |

### 6.3 ⛔ 三条硬纪律

1. ⛔⛔ **「不进 LLM」必须与「进 LLM 但被框成零角色」区分开。** ⭐ 前者是架构选择,⭐ 后者是 prompt 选择,⛔ **两者的修法完全不同**。
2. ⛔ **评测端的确定性工具不占任何角色。** ⭐ 只用于给方法打分的工具在流程之外,⛔ 记为「评测端」并单独统计。
3. ⛔ **不许为了让案例好归类而改判据。** ⭐ 归不进去的记入 §7。

## 7. 已知的边界情形与待分类

⭐ 本节记录判据无法唯一裁定的形态。⛔ **它会增长,这是正常的** —— ⭐ 一个不记边界情形的分类学是假的。

| # | 形态 | 为什么难判 | 当前处置 |
| :-: | :-- | :-- | :-- |
| **1** | ⭐ 一个成分**先改后判**(修补丁并落盘、再跑 oracle) | ⭐ 同时占执行操作与求值 | ⭐ **拆成两条记**,各自填表 |
| **2** | ⭐ 确定性信号被压成**标量当训练奖励** | ⛔ 它不进上下文,⭐ 模型推理时看不到 | ⭐ 记 **「训练端」**,⛔ 不占前置角色;⭐ 单独统计 |
| **3** | ⭐ 确定性判定结果**回灌给人**而不是 LLM | ⛔ 有反馈但接收者不是模型 | ⭐ 记 **「人在回路」**,⛔ 不占角色 |
| **4** | ⭐ 词表既列名字又附「必须逐字」条款 | ⭐ 同时是表示变换与规则建立 | ⭐ **按主导效果记,并注明双重性**(§5) |
| **5** | ⭐ 检索(embedding / BM25)取回的片段 | ⚠️ 是「新信息」还是「已有信息的重新呈现」取决于**语料是否在原输入里** | ⭐ 语料**在**原输入内 → 表示变换;⭐ 语料**在原输入外** → 信息探索 |
| **6** | ⭐ 多次采样 + 投票 / 共识 | ⛔ 没有工具算出任何关于制品的事实,⭐ 只是聚合 LLM 自己的输出 | ⭐ 记 **「聚合」**,⛔ 不占角色 |

## 8. ⭐ 已知的角色 × 效果对应(⛔ 证据薄,⭐ 逐条带分母)

⚠️ **本节是当前证据状态的快照,⛔ 不是结论。** ⭐ 完整逐项分类见 [`tool_roles.md`](./tool_roles.md)。

| 角色 | 对**发现能力**的已知效应 | 分母 |
| :-- | :-- | :-- |
| **信息探索** | ⚠️ **加法未测**。⭐ 唯一做了这个形态的工作**消融装置在 artifact 里、正文一字未提**。⭐ 有**两条减法证据**(去掉信息 → 召回下降)与**一条不同构的加法数**(+8.7pp,⛔ 不同批、且测的是产出正确性不是发现) | 1 篇形态 + 2 条减法 + 1 条异构加法 |
| **表示变换** | ⚠️ **无对照**。⭐ 语料里 3 处使用,⛔ 无一处量化 | 3 处使用 / 0 对照 |
| **规则建立** | ⛔⛔ **三个独立团队报负面**:召回**重新分配而非增加**;⭐ 其中一个团队的对策是**带规则跑一遍、不带规则跑一遍取并集** | 3 个独立团队 |
| **求值 · 记录** | ⭐ 我们自己;⛔ 语料里无第二例 | 1 |
| ⭐⭐ **求值 · 封存** | ⭐⭐ **我们自己,⛔ 语料里无第二例**。⚠️ **无对照** —— ⛔ 从未测过「封存 vs 不封存」;⭐ 它的正当性是**防作弊通道**这个解析论证,不是实测收益 | 1 |
| **求值 · 回灌** | ⚠️ 方向不一;⭐ 最强的负面是一处**接了真 sound oracle 却 6 格里 5 格撞满 20 轮不收敛**,根因记为**反馈不可执行**(只给「哪条性质没满足」,不给反例路径、不定位元素) | 见 `tool_roles.md` |
| **求值 · 拦截** | ⭐ 方向为正,⛔ 但最常引的那条「0%」是**定义出来的**(变体的接受判据就是那道检查) | — |
| **求值 · 丢弃** | ⚠️ **无对照**,⭐ 但有一处明确的设计权衡记录(产出率换掉整套修订机器) | 1 |
| **执行操作** | ⚠️ 语料里 1 处,⛔ 且**每格只跑一次、无方差** | 1 |

⭐⭐⭐ **当前最要紧的空缺:信息探索在发现方向上的加法没有任何人测过。** ⭐ 这既是风险(我们没有先例可引),也是机会(它是一个真空白)。
