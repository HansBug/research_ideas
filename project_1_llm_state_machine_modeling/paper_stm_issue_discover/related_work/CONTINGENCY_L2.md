## 2. ⭐ 分档前必须先定死的一件事：出处在为**什么东西**背书

**这是决定落在哪一档的最大单一变量，比检索投入更重要。** v25 四条全灭不是因为查得不够，是因为**问错了问题**。

### 2.1 v25 的失效机制，拆成一句话

v25 向 UML 索取的是「**模型必须满足 X**」这种**义务命题**，而 UML Clause 14 对绝大多数此类问题的回应只有三种：陈述操作语义（不是义务）、显式保留二义（拒绝表态）、或**明确允许我们称之为缺陷的东西**。所以 A2 零依据、A3 规范表态与之相反、A1 的存在性半段落在规范拒绝表态处、A4 类别错位。

### 2.2 而【仓库裁定】早已把三类来源分了工

[method_provenance_policy.md](../discover_matrix/docs/protocol/method_provenance_policy.md) §一.2 的三列表**已经**规定了每类来源各自负责什么：

| 来源类 | 该表逐字写的职责 |
| :-- | :-- |
| **现实需求** | 「哪些义务值得被断言：可达、驻留、事件响应、效果方向、覆盖」 |
| **技术文档 / 规约** | 「每条义务能被**怎样**机械化，以及边界在哪（如闭词表为何是 19 条）」 |
| **学术文献** | 「判据本身的正确性依据，以及为什么某种操作化是伪代理」 |

⭐ **v25 让 UML 去干第一列的活，而口径把 UML 派在第二列。** 19 条谓词不是合式性公理，是**主张形状（claim shape）**：某条谓词求值为假之所以是缺陷，义务来自 **NL 需求那一句**，不来自标准。标准要背书的是「这个主张形状在 $M = (S, E, V, Tr, A)$ 上定义良好、其求值程序忠实于该形式主义的公认语义」。

### 2.3 由此得到 L2 Q1 的**两栏**问法（⛔ 不是一栏）

| 栏 | 问的是 | 谁背书 | 落级 |
| :-- | :-- | :-- | :-- |
| **P · 求值程序正当性** | 「按这个形式主义的公认语义，这样求值对不对？」 | UML / PSSM / SCXML / FCSTM 语法与投影规则 | (a)(b)(c) 可达 |
| **O · 义务正当性** | 「NL 点名了它，模型就有义务体现它——这条凭什么？」 | 需求工程通则、功能安全标准的追溯性要求、控制系统建模指南、`sources/` 领域实践 | 主要 (b)-弱 与 (d) |

⛔ **两栏必须在 `predicate_provenance.md` 里分列，不得合并成一个「出处级」。** 合并会造成两种错误各出一次：把 P 栏的 (c) 级说成「UML 要求模型这么做」（= v25 的 A4 类别错位），或者因为 O 栏挂不上就把整条判 (f)（= 白扔掉一个成立的 P 栏依据）。

### 2.4 ⛔ 反向护栏：这个拆法**不得**被用来洗白弱证据

拆两栏是为了问对问题，不是为了多挂几条。三条硬约束：

1. ⛔ **P 栏满级不等于该谓词「有出处」。** 论文正文若要说「这条规则从领域归纳而来」，靠的是 **O 栏**；P 栏只支撑「我们的求值没写错」。两者在正文里必须分开成句。
2. ⛔ **O 栏的 (d) 级必须给具体篇目 + 逐字片段**（伞 PR §4.6 已明令）。`sources/*/STM.md` 的「原文摘录」节自带页码与行号，没有理由省。
3. ⛔ **不得用 P 栏的强度去描述 O 栏。** 例如：PSSM 定义了事件消费语义（P 栏可到 (c)），但 PSSM **没有**说「NL 点名的刺激必须被某个配置消费」——后者是 O 栏，PSSM 不背书。

### 7.1 PSSM（Precise Semantics of UML State Machines）——本轮最值得先摸的方向

⭐ **全库确实从未读过**：本轮 `grep -ril "PSSM|Precise Semantics of UML State"` 全仓只命中 **3 个文件**（[../TODO.md](../TODO.md)、`state_machine_types/SUMMARY.md`、`state_machine_types/embedded-uml-model-execution-.../desc.md`），且均为提及，无任何提取物。

| 摸到的线索 | 对 L2 的意义 |
| :-- | :-- |
| PSSM 是 **fUML 的扩展**，定义 UML 状态机的**执行语义**；正式版 1.0 已发布（alpha 2016-12 / beta 2017-02）。入口：[omg.org/spec/PSSM/About-PSSM](https://www.omg.org/spec/PSSM/About-PSSM/)、[PDF](https://www.omg.org/spec/PSSM/1.0/PDF) | ⭐ 6 条仿真谓词的 **P 栏**最正当出处。⚠️ 但它是**执行语义**，落 **(c) 级**——与 v25 A4 同一类别 |
| 覆盖 run-to-completion、event pool、**deferred event pool**（有序、无变体点）、**completion event**（作用域限于产生它的 StateActivation）、`getNextEvent` 调度 | 直接对应 `event_consumed`（事件是否被消费）、`stays_in`（未触发迁移的事件被丢弃、丢弃不改变配置）、`occupancy_after`（RTC 步内的配置演化） |
| 含 **103 个 conformance test case**，可用于检查执行工具的一致性 | ⭐ 这是一个**意料之外的可用物**：它给「我们的仿真求值是否忠实」提供了一个**外部可执行判据**，比引一段散文强得多 |
| ⚠️ 已有学术工作对 PSSM 提出批评：Software Quality Journal 2023 的评估研究指出测试只在模型层进行、RTC 步与事件池内容不在机器可读测试套件内；[arXiv:2309.14884](https://arxiv.org/pdf/2309.14884) 专门审视 doActivity 语义的模糊处 | ⚠️ **双刃**：这些批评本身是可引的 (c) 级文献，但也说明「PSSM 说了算」这句话不能说满 |
| ⚠️ 有报告称 PSSM 自带的 `Join 003` 样例**违反** UML 2.5.1 的 `join_segment_guards` 约束 | ⛔ **一个直接的 v25 式警告**：标准自身的配套物也会与标准正文冲突。取一手 PDF 逐字核，⛔ 不要引二手描述 |
| ⚠️ 另有一篇综述 [arXiv:2407.17215](https://arxiv.org/pdf/2407.17215)《Formalizing UML State Machines for Automated Verification — A Survey》（1997–2021），逐字指出 OMG 规范以自然语言写就、其歧义会引入不一致 | ⭐ **单位收益可能最高的一篇**：一篇枚举语义变体点的综述，既能为多条谓词的 P 栏提供锚点，又能**量化「标准在哪些地方不表态」**——那正是 (e)(f) 级的正当理由来源。⚠️ 但它同时削弱「UML 说了算」的口吻 |

⛔ **边界门检查**：PSSM 覆盖 region / orthogonal 并发语义，**那部分界外**。按伞 PR §4.0.2「同一篇规范可以部分可用」，引用必须落到**顺序状态机**的具体章节，⛔ 不得整篇引。

**我的判断**：PSSM 大概率能把 6 条仿真谓词的 **P 栏**做到 (c)，⛔ 但**几乎肯定做不了 O 栏**——它规定的是「符合规范的引擎如何执行」，不是「模型必须满足什么」。**所以 PSSM 提高的是档 A 的 (a)(b)(c) 计数上限，⛔ 不改变 §3.1 里以 O 栏计的「已挂条数」。** 这一点必须在开跑前对执行者讲明，否则会出现「查了一天 PSSM、已挂条数一条没涨」的挫败与误判。

### 7.2 控制系统建模规约里，`cardinality` 这类谓词有没有对应说法

| 摸到的线索 | 对 L2 的意义 |
| :-- | :-- |
| **IEC 61131-3 SFC**：每个 SFC 要求**恰好一个** `INITIAL_STEP`（文法 `step-element ::= [ INITIAL_STEP \| STEP ] step-name ...`，图形上双线框）；同一图内**步名不得重复**；步与转换必须交替 | ⭐ **正对着 `initial_target` 被 UML 拒绝的那半边**——UML 显式允许没有默认入口，而 SFC **要求**有初始步。这是本轮最有价值的单条线索 |
| IEC 61131-3 第二版 Figure 18 给出 **ill-formed 示例**："unsafe" SFC 与 "unreachable" SFC | 对应 `reaches`；且「标准自己画出反例图」是比散文更强的表态形式 |
| 规范条文位置（供取一手用）：步 = 二版 Table 40/43、三版 Table 54/57；转换 = 二版 Table 41、三版 Table 55。⚠️ 当前版本为 **IEC 61131-3:2025（第 4 版，2025-05-22）** | ⛔ PLCopen FAQ 明确声明非规范性，⛔ 不得当条文引 |
| **MAAB / MAB 建模指南 db_0137**（"States in state machines"）：OR（互斥）分解下**至少两个状态**，单状态被判为不正确；MAB v6 另有 "Number of States per Stateflow Container" | ⭐ 这是唯一摸到的、**直接约束状态计数**的成文规则，对 `cardinality` 的 O 栏最相关 |
| Stateflow 语义：state 即 operating mode；OR 分解 = 互斥模式，AND 分解 = 并发 | ⭐ 「模式↔状态」这条映射本身是 `state_declared` / `cardinality` 的 O 栏素材 |

⛔ **三条必须一并记住的减分项，⛔ 不要在兴奋中略过**：

1. ⛔ **SFC 是另一种数学对象。** 它是 token/step 语义，并行分支下多步可同时活跃。伞 PR §4.6 已限定「只取 SFC **顺序**部分」，⚠️ 但即便顺序部分，「借它的规范强度给 $M$ 上的谓词」**正是 v25 A3 死掉的那个动作**（把讲 choice 伪态的话借给普通 State）。⭐ 建议：**SFC 只作 (d) 级**（领域实践中「初始步必须唯一存在」是通行义务），⛔ **不作 (b) 级**，除非能论证顺序 SFC 与 $M$ 的对应是保义务的。
2. ⛔ **MAB 是厂商指南，不是国际标准。** 且 db_0137 给的是**下界（≥2）**，而 `cardinality` 断言的是 **NL 说的那个确切数**。它能支撑的只是「状态计数是一个被成文规范承认的建模质量维度」，⛔ **支撑不了任何具体计数**。级别上限 (d)，⛔ 不是 (b)。
3. ⚠️ **AND 分解界外。** 引 Stateflow 时只能引 OR 分解部分。

**我的判断**：`cardinality` 的 O 栏**最可能落 (d)**，来源是 `sources/` 的领域实践（§1.4 已实测到 "three operating layers" 这类逐字形态）加 MAB db_0137 作旁证。⛔ **落 (b) 的概率很低**，不要为了让表好看而强推。

### 7.4 ⭐ 为什么我给的概率是「预算内查得到什么」，不是「客观上存不存在」
