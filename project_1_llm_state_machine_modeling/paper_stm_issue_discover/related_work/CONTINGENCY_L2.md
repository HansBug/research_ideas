### 两种证据的区别（⛔ 这是本裁定的全部内容）

| | 要证明的命题 | 论文里的句子 |
| :-- | :-- | :-- |
| ⛔ **符合性（本文件原先的主轴）** | 「谓词 X 的定义**依从**标准 Y §Z」 | 「我们遵循 …」 |
| ⭐ **普遍性（现行唯一主轴）** | 「检查 X 这件事在领域文献与工程实践里**反复出现、确有需求**」 | ⭐ 「这类检查在 … 中反复出现，我们把主流的这些归纳成一套闭合词表」 |

⛔ **我们不作任何符合性主张。** 因此：⛔ 不必声明依从 UML / PSSM / SCXML 任何一家，⛔ 也不得引 pyfcstm 充当语义权威——引它等于把「与某个实现一致」变成新的义务，而仿真语义**不是本文的核心贡献，无须多说**。

### ⛔ 一条防止过度执行的细分：**标准不是不能引，是不能这样引**

⚠️ 本裁定**不禁止**引 UML / IEC / ISO 等规范材料。⭐ **同一份文件，取什么主张决定它落在哪条轴上**：

| 从 UML 良构性规则里取什么 | 落哪条轴 | 后果 |
| :-- | :-- | :-- |
| ⛔ 「我们的 `state_declared` **依从** UML §14.x」 | 符合性 | ⛔ 制造了一个对齐义务，⛔ 而我们不作这个主张 |
| ⭐ 「**声明性检查是 UML 良构性规则里的常规项之一**」 | ⭐ **普遍性** | ⭐ 只作证「这类检查是公认需要的」，⛔ 不承诺任何一致性 |

⛔ **所以判据不是「材料是不是标准」，而是「我们从它那里取的是一条要求，还是一个存在性事实」。** 取「某标准把这类检查列为常规项」是**普遍性证据**，合法且有力；取「某标准要求模型必须满足 X，所以我们的谓词有依据」是**符合性论证**，⛔ 不要。

⚠️ 被作废的 (d2) 之所以作废，不是因为它引了规范，⭐ 而是因为它引的规范**讲的是另一个数学对象**（SFC 的 token/step 语义不是 $M$），于是唯一能让它成立的方式就是补一段「对应保不保义务」的符合性论证——⛔ 而那段论证在普遍性轴上既不需要也不可用。

⚠️ 这一段是 2026-08-11 的自我更正——本裁定块的初稿曾断言「$n$/$f$ 量错了东西」与「六级的序要反转」，⛔ **两条都是错的**，起因是只做了关键词检索而没有通读 §2。逐字证据在这里：

## 2. ⭐ 分档前必须先定死的一件事：出处在为**什么东西**背书

**这是决定落在哪一档的最大单一变量，比检索投入更重要。** v25 四条全灭不是因为查得不够，是因为**问错了问题**。

### 2.1 v25 的失效机制，拆成一句话

v25 向 UML 索取的是「**模型必须满足 X**」这种**义务命题**，而 UML Clause 14 对绝大多数此类问题的回应只有三种：陈述操作语义（不是义务）、显式保留二义（拒绝表态）、或**明确允许我们称之为缺陷的东西**。所以 A2 零依据、A3 规范表态与之相反、A1 的存在性半段落在规范拒绝表态处、A4 类别错位。

### 2.2 而【仓库裁定】早已把三类来源分了工

[method_provenance_policy.md](../discover_matrix/docs/protocol/method_provenance_policy.md) §一.2 的三列表**已经**规定了每类来源各自负责什么：

| 来源类 | 该表逐字写的职责 |
| :-- | :-- |
| **现实需求** | 「哪些义务值得被断言：可达、驻留、事件响应、效果方向、覆盖」 |
| **技术文档 / 规约** | 「每条义务能被**怎样**机械化，以及边界在哪（如闭词表为何是 19 条）」 |
| **学术文献** | 「判据本身的正确性依据，以及为什么某种操作化是伪代理」 |

⭐ **v25 让 UML 去干第一列的活，而口径把 UML 派在第二列。** 19 条谓词不是合式性公理，是**主张形状（claim shape）**：某条谓词求值为假之所以是缺陷，义务来自 **NL 需求那一句**，不来自标准。标准要背书的是「这个主张形状在 $M = (S, E, V, Tr, A)$ 上定义良好、其求值程序忠实于该形式主义的公认语义」。

### 3.6 ⛔ P-驳斥档（横切，⛔ 与 A/B/C 不在同一根轴上）

⛔ **上一版的风险模型漏掉了一整类后果。** A/B/C/C′ 全部回答同一个问题——「**主张能说多强**」；⛔ 它们没有一档回答另一个问题——「**结果可能是错的**」。⚠️ §2.3 明明提出了 P 栏的问法「按这个形式主义的公认语义，这样求值对不对」，⛔ **但没有任何一档以「P 栏为否」作为触发**。⛔ 而 §3.4 把 C-2 定义成「与**现有措辞**相反」，其补救是**改措辞**；⛔ **若分歧落在求值程序上，改措辞什么也修不了。**

#### 触发条件

⛔ **一手规范与我们的求值程序在「顺序状态机」语义上存在实质分歧。** 典型形态（⛔ 均落在界内，⛔ 不是并发/时间那些界外项）：

1. **RTC（run-to-completion）步的边界与我们的仿真器不一致**——例如规范要求一个 RTC 步内完成的迁移链，我们分成了多步（或反之），⛔ 那么 `occupancy_after` 在「之后」这个词上算的就不是同一个时刻。
2. **事件池语义不一致**——事件的入池/取出/丢弃时机、`getNextEvent` 的调度约束。⛔ 直接影响 `event_consumed` 与 `stays_in`。
3. **deferred event 语义不一致**——被 defer 的事件既未消费也未丢弃，⛔ 若我们的求值把它算成「已丢弃且配置不变」，`stays_in` 与 `event_consumed` 同时错。
4. **completion event 语义不一致**——完成事件的产生时机与作用域（PSSM 限定于产生它的 StateActivation）。⛔ 影响 `reaches` 与 `terminates` 的可达路径。

## 4. ⭐ 贯穿各档的不对称：最容易挂的谓词恰恰最不用

### 7.2 控制系统建模规约里，`cardinality` 这类谓词有没有对应说法

| :-- | :-- |
| **IEC 61131-3 SFC**：每个 SFC 要求**恰好一个** `INITIAL_STEP`（文法 `step-element ::= [ INITIAL_STEP \| STEP ] step-name ...`，图形上双线框）；同一图内**步名不得重复**；步与转换必须交替 | ⭐ **正对着 `initial_target` 被 UML 拒绝的那半边**——UML 显式允许没有默认入口，而 SFC **要求**有初始步。这是本轮最有价值的单条线索。⛔ 定级见下方「关于 SFC 定级的修正」 |

| **MAAB / MAB 建模指南 db_0137**（"States in state machines"）：OR（互斥）分解下**至少两个状态**，单状态被判为不正确；MAB v6 另有 "Number of States per Stateflow Container" | ⭐ 这是唯一摸到的、**直接约束状态计数**的成文规则，对 `cardinality` 的 O 栏最相关 |
| Stateflow 语义：state 即 operating mode；OR 分解 = 互斥模式，AND 分解 = 并发 | ⭐ 「模式↔状态」这条映射本身是 `state_declared` / `cardinality` 的 O 栏素材 |

⛔ **三条必须一并记住的减分项，⛔ 不要在兴奋中略过**：

1. ⛔ **SFC 是另一种数学对象。** 它是 token/step 语义，并行分支下多步可同时活跃。伞 PR §4.6 已限定「只取 SFC **顺序**部分」，⚠️ 但即便顺序部分，「借它的规范强度给 $M$ 上的谓词」**正是 v25 A3 死掉的那个动作**（把讲 choice 伪态的话借给普通 State）。⛔ 定级见下方修正。
2. ⛔ **MAB 是厂商指南，不是国际标准。** 且 db_0137 给的是**下界（≥2）**，而 `cardinality` 断言的是 **NL 说的那个确切数**。它能支撑的只是「状态计数是一个被成文规范承认的建模质量维度」，⛔ **支撑不了任何具体计数**。⛔ 定级见下方修正。
3. ⚠️ **AND 分解界外。** 引 Stateflow 时只能引 OR 分解部分。

#### ⛔ 关于 SFC 与 MAB 定级的修正：两者都落 **(d2)**，⛔ 不是 (d)

⚠️ **上一版把 SFC 判成「只作 (d) 级，不作 (b) 级」。⛔ 方向对，但级别错。** (d) 在上一版是个笼统档，而 §2.5 已经把它拆开了——⛔ **(d) 是频次命题**（「领域里 K/N 份这么做」），⛔ **而 IEC 61131-3 是规范条文**（样本量 1，但带规范强度）。⛔ 把一条 IEC 条文标成 (d)，**对上低估了它的规范强度、对下高估了它的领域覆盖面**——⛔ 读者会以为「这条义务在领域里被广泛观察到」，而实际证据是「一份国际标准这么规定」。⛔ 这两句话的可辩护性完全不同。

| 对象 | ⛔ 正确级别 | 降级理由属哪一类 | ⛔ 计入已挂的条件 |
| :-- | :-- | :-- | :-- |
| **IEC 61131-3 SFC** 的 `INITIAL_STEP` 条文 | **(d2)** | ⛔ **对象理由**——SFC 是 token/step 语义，⛔ 不是 $M = (S, E, V, Tr, A)$ | 必须写出「顺序 SFC → $M$ 的对应，以及该对应**是否保**『初始步唯一存在』这条义务」的论证。⛔ 论证在则计入 $n$；⛔ 不在则只作旁证 |
| **MAB / MAAB db_0137** | **(d2)** | ⛔ **权威性理由**——厂商指南，⛔ 不是国际标准机构 | 同上，且⛔ 还要写明「它给的是下界 ≥2，⛔ 支撑不了 NL 说的那个确切数」 |

⭐ **这条修正很值钱，⛔ 别把它当格式问题**：`initial_target` 恰恰是 **UML 明确拒绝背书、而 SFC 明确要求**的那一条，⛔ 且它占可挂支撑的 **47.7%**（185 条，§1.2）。⛔ **它挂在 (d) 还是 (d2)、论证在不在，直接决定 $f$ 越不越过 40% 与 60% 那两道门**——⛔ 也就直接决定落 A、B 还是 C。⛔ 所以「顺序 SFC → $M$ 是否保义务」这个论证是本轮**单点收益最高的一件事**，⛔ 必须优先做、⛔ 且必须写成可被第三方检验的形式，⛔ 不得写成一句「我们认为是保的」。

### 7.4 ⭐ 为什么我给的概率是「预算内查得到什么」，不是「客观上存不存在」

档 A 的 15% 看起来低，理由是三条**结构性**的，与努力程度无关：

1. **(a) 级供给是硬性稀缺的。** v25 已穷举 Clause 14 的 5 组 OCL 与 5 处 ill-formed 语句，最终只找出**一条**真正可用（`outgoing_from_initial`）。这个搜索**已经做过了**，重做不会变多。
2. **O 栏在设计上就不该由建模语言回答。** §2.2 的三列表把「哪些义务值得断言」派给「现实需求」，而不是规约。所以「多数谓词的 O 栏挂到 (a)(b)(c)」这件事**本身就与口径的分工相悖**——它罕见不是因为查得不够。
3. **时间预算 12 小时，其中还要留出 C1 逐字核验。** 取 OMG UML 2.5.1 PDF + PSSM + IEC 61131-3 三份一手规范并逐条核对，本身就吃掉大半预算；v25 那次**只核 4 条公理**就动用了一位独立核对者取 18 MB PDF 逐字核。⭐ **§0.2 的取件共享协议正是针对这一条写的**——⛔ 与 L1 各取一份会把这个已经紧张的预算再砍一半。

⛔ **而「至少一条现有措辞被标准表态否定」⛔ 不是概率，⛔ 是既成事实。** ⚠️ 上一版把它写成「在档 C 的 30% 里单独估到 ≥50%」，⛔ 那个写法错了——v25 已经证实了两条（`initial_target` 的存在性半边、`guard_distinguishable` 的 ill-formed 措辞），⚠️ **2026-08-11 复核确认它们仍在 `predicates.py` 的 `proves` 字段里逐字写着**。⛔ **所以 C-2 标记的概率是 1，⛔ 不是 50%**；⛔ 这也正是 §3.1 必须把它从档位判据里挪出来、降为横切标记的原因（否则 $P(C) = 1$）。⛔ **本轮对这两条的任务是核实与量化，⛔ 不是发现**；剩下的真正未知量只有两个：⛔ 还会不会**新增**第三条 C-2，以及 `initial_target` 最终掉不掉档（后者通过 $f$ 直接决定档位）。
