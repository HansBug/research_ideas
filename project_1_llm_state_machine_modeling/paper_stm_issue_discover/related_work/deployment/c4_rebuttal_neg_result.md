# C4 · 反驳：§12「负结果的形态与两端选型」

> **靶子**：[SUMMARY.md](./SUMMARY.md) §12（§12.1–§12.6）。**独立形成判断**，未读 `c1_*` / `c2_*` / `c3_*`。上下文只取 [small_model_papers.md](./small_model_papers.md) §4.6 与 [verification_log.md](./verification_log.md)。
>
> **审稿人立场**：这一节的算术我复算了，方向是对的；但它用**两个不同来源的证据各撑半边**，然后把两半拼成一个论文级主张，而两半各自都撑不起自己那一端。下面三条按严重度排。**第一条我判无解，建议放弃该主张形态。**

## 0. 先把 KV cache 那一算做完：⛔ 它救不了 §12.2，也推不翻它

委托里问：长上下文的 KV cache 会不会把「8 卡节点能跑 671B」推翻？**我算完的答案是不会，而且差得很远。** 但这一算顺手证伪了表里的另一格，而那一格恰好是 §12.3「唯一能救小模型的场景」所倚靠的那一格。

**公式**（行内，可复算）：每 token 的 KV 字节数 $= 2 \times L \times H_{kv} \times d_{head} \times b_{kv}$，其中 $L$ 为层数、$H_{kv}$ 为 KV 头数、$b_{kv}$ 为每元素字节数（BF16 取 2）。**MLA 例外**：K 与 V 共用一份压缩潜向量，不乘 2，每 token 为 $L \times (r_{kv} + d_{rope}) \times b_{kv}$。

**上下文长度取值**：`splitter` system prompt 实测 **95,589 字符**（§12.6 已给），语法手册 + 英文 + JSON 混合，按 3.2–3.8 字符/token 折算约 **25K–30K token**；加 user prompt 与 trace JSON，工作上下文按 **32K** 计，悲观上界按 **128K** 计。**流水线的多阶段不在显存里累加**（每阶段的 cache 用完即释放），且这是**单人交互工具，batch = 1**——这两点合起来使 KV 项比直觉小得多。

| 模型（真实架构，可核） | 每 token KV（BF16） | 32K 上下文 | 128K 上下文 | 权重（4-bit） | KV 占权重比（32K） |
| :-- | --: | --: | --: | --: | --: |
| DeepSeek-V3/R1 671B（MLA，61 层，$r_{kv}=512$ + rope 64） | **68.6 KiB** | **2.25 GB** | 9.0 GB | ~369 GB | **0.6%** |
| Qwen3-235B-A22B（GQA，94 层，4 KV 头 × 128） | 188 KiB | 6.2 GB | 24.6 GB | ~130 GB | 4.7% |
| gpt-oss-120b（GQA，36 层，8 KV 头 × 64；半数层滑窗 128） | ≤72 KiB | ≤2.4 GB | ≤9.4 GB | ~64 GB | 3.7% |
| 对照：2023 年 MHA 7B（32 层，32 头 × 128，无 GQA） | **512 KiB** | 16 GB | 64 GB | ~4 GB | **400%** |

**结论一**：671B 在 32K 上下文、batch 1 下，KV 只占权重的 **0.6%**；即便按 128K × **8 路并发**算也只有 **72 GB**，与权重合计 **441 GB < 640 GB**，仍在一台 8×80G 节点内。**§12.2 的最后一行结论不动，连一格数字都不用改。** 若再把 KV 量化到 FP8（生产常规），还要再减半。

**结论二（这一条 §12 没写，但它是「为什么 KV 不咬人」的真正原因，值得写进论文）**：KV cache 与权重同量级是一个**2023 年的小 dense MHA 直觉**——上表末行 7B/MHA 在 32K 下 KV 是权重的 4 倍。而 MLA 与「少 KV 头 GQA」正是为压掉 KV 而设计的，且**恰好只有最大的那批 MoE 模型采用**。所以：**规模越大，KV 的相对负担越轻。** 这不是削弱 §12.3，是**加强**它——包络越往上走，长上下文的额外代价越可以忽略。

**结论三（就地更正一格）**：⛔ **「工程师现有终端（24 GB）→ 4-bit 上限 ~44B」这格在有真实上下文时是错的。** 复算：`Qwen3-32B`（dense，64 层，8 KV 头 × 128）每 token KV = **256 KiB**，32K 上下文即 **8.6 GB**；权重 4-bit ≈ 18 GB，合计 **26.6 GB > 24 GB**，**一张 24 GB 卡在 32K 上下文下连 32B dense 都装不下**，更不用说 44B。同卡的现实上限是 **~14–20B**（`Qwen3-14B` 4-bit 8 GB + 32K KV 5.2 GB = 13 GB，宽裕；`gpt-oss-20b` MXFP4 13 GB + 32K KV 1.5 GB = 15 GB，宽裕）。⚠️ **方向仍对我方有利**（终端场景更紧，§12.3 那条「唯一能救它的场景」更站不住），**但这格数字必须改**，因为 §12.3 正是靠它把救援场景压到 4–8B 的；改完之后那条救援场景的上限从「消费卡能吃 44B」变成「消费卡能吃 14–20B」，而这直接撞上 R2 第 2 点。

**证据等级**：架构参数（层数 / KV 头数 / head_dim / MLA 秩）为公开模型卡与 config 口径，**M**（可逐项核）；折算与占比为**我方算术，I 级，公式已给可复算**；32K 这个上下文取值由 95,589 字符换算得来，**I**。

**给作者一句话**：KV cache 这条路不用再想了，写一句脚注挡掉即可（「按 MLA/GQA 实测每 token ≤188 KiB，32K 上下文下 KV 占权重 ≤5%，不改变包络结论」）。**别把它当限定写长**，它反而是你的论据。

## R1（最致命）· ⛔ 「有效区间 ⟂ 部署包络」这个二段式，两端各由不同来源撑一半，⛔ 而两半都撑不起自己那一端；**判无解，建议放弃该主张形态**

### 反驳

§12.4 要报的那句话是一个**二段推理**：

- **前提 A**：这类多阶段脚手架的**有效区间在 ~20B 以下**。
- **前提 B**：真实私域部署包络允许 **120B–671B**。
- **结论 C**：故在实际部署条件下，这类方法拿不到设计时假定的增益。

问题不在结论，在于**A 与 B 来自两个完全不同的证据体系，且这个 story 的作者对两端各自都没有生产能力**：

**B 是我方的显存算术（I 级，可复算，我已复核并加强）。** 这一端是干净的。

**A 是第三方 5 个数据点。** 而这 5 个点撑不起「~20B」这个数，理由有四条，任一条单独就足以让审稿人划掉这个阈值：

1. **跨家族插值。** 5 个点来自 **3 个家族**：Llama-3.1（8B，+35）· Qwen2.5（7B +24 / 32B +2）· GPT-OSS（20B +15 / 120B +3）。**Qwen 家族的膝点落在 7B–32B 之间，GPT-OSS 家族的膝点落在 20B–120B 之间**——两条曲线的膝点区间**根本不重叠**。把它们摊到同一条参数量 x 轴上读出一个「~20B」，是把三条不同的曲线当成一条。**而且没有任何一个家族在 20B–32B 之间有点**，这个区间里一个测量都没有。
2. **已知反转直接反对该机制。** `Qwen2.5-32B` 的 Basic = **382**，低于 `GPT-OSS-20B` 的 **424**——它**能力更低而收益更小**（+2 vs +15）。「收益随能力衰减」这个机制在这两点上是**反的**。真正的解释变量更可能是**训练配方 / 是否 reasoning-tuned**，而那不是参数量的函数。一旦解释变量不是参数量，「有效区间在 ~20B 以下」这句话**连量纲都不对**——它把一个非参数量的现象钉在参数量轴上。
3. **膝在统计上不存在。** [small_model_papers.md](./small_model_papers.md) §4.6 自陈 Llama 的 342 是**三跑取最好**，均值 336.0、$\sigma = 5.3$。若 $\sigma \approx 5$ 通用，两个独立测量之差的 $\sigma_{diff} \approx 7.5$。于是：+35 → **4.7σ** · +24 → **3.2σ** · +15 → **2.0σ** · +2 → **0.3σ** · +3 → **0.4σ**。也就是说：**只有 ≤8B 档稳稳非零**；20B 勉强 2σ；32B 与 120B 与零不可区分。而定义那个「膝」的 **+15 与 +2 之差（13）只有 1.7σ**——⛔ **审稿人一句话就能说：你的拐点在噪声里。**
4. **1 任务 · 1 流水线 · 1 篇 preprint（arXiv，无 venue 标注）。** 有效区间是一个**关于方法类的定量论断**，用一篇未评审 preprint 的单任务消融表去钉它，等级不够。

### 为什么致命（具体到哪条主张失效）

**§12.4 的那段引用块整段失效**，因为它的前半句（「我们测出有效区间在 ~20B 以下」）**不是我们测的**——它是 VerIbmc 测的，测的是别人的三阶段流水线在形式化验证不变式生成上的表现。⛔ 用第一人称「**我们测出**」陈述一张第三方表，这不是措辞问题，是**把他人结果据为己有**；而如果改成第三人称转述，那么前提 A 就成了「已有一篇 preprint 报告 …」，**二段推理的第一段立刻降到只能支持一个 hypothesis，撐不起 §12.4 那种结论句**。

更要紧的是：**这个前提我方原理上无法自证。** 要自己钉住「有效区间的位置」，需要在 **≥5 个规模档 × ≥2 个家族**上跑同一套八阶段流水线的 Basic vs Naive 对照，每档至少 3 轮以估 $\sigma$。而 §12.5 只给**两档**。两个点定不出一条曲线的膝点位置——**两个点只能定一条直线，而直线没有膝。** 这不是预算问题，是**该主张形态与可执行实验之间的结构性不匹配**。

### 证据

- VerIbmc 逐模型表、89 题能力差、Llama 三跑均值 336.0/σ=5.3：[small_model_papers.md](./small_model_papers.md) §4.6（该文件自陈「部分正文」，**S 级**）。
- 家族归属与 Basic 绝对值的反转（382 < 424）：同表逐行可读，**M 级**（表内数字）。
- σ 推算与 1.7σ：**I 级，我方算术**，前提是「σ≈5.3 可推广到其余四行」——⚠️ 原表只给了 Llama 一行的 σ，**这个推广本身未经证实**；但注意方向：若其余行 σ 更大，结论更强；若更小，作者有义务给出，而原文没给。
- 「我们测出」这一措辞：[SUMMARY.md](./SUMMARY.md) §12.4 引用块逐字。

### 建议处置

⛔ **无解，建议放弃「有效区间 ⟂ 包络」这个二段式主张。** 不是降档，是换形态。理由如上：前提 A 需要一条曲线，而任何可执行的实验设计只给得出两个点。

**可行的替代形态（用你真正拥有的资产）**：把 contribution 从**判决**（「这类方法在实际条件下没用」）换成**机制**（「这类方法的 token 预算花在哪、信号在哪一阶段丢掉」）。你手上有 [small_model_papers.md](./small_model_papers.md) §4.9 点名的那个空缺形状：**324 格全量 × 逐阶段降级诊断 × 逐格 token 记账 × 588 位逐位判定**。那份东西能支持的最强主张是：

> 在同一模型、同一批需求上，八阶段脚手架相对朴素单提示的净效应为 **−15.82pp**，且我们能逐阶段定位增量为负的具体位置（reviewer 第 3–5 轮恰好零位、79% token 覆盖净变化≈0、`precheck_and_seal` 0 token 性价比最高）。

这句话**不需要前提 A**，不需要任何跨规模曲线，也不需要「~20B」这个数。**它是自证的，而二段式不是。** 参数量那一端只保留一句 Limitations（「已有 preprint 报告脚手架收益在更弱模型上更大，方向与我们一致，但其规模阈值不可移植」），并**只作方向性提示，不写数字**。

## R2 · ⛔ 两端选型的两个端点，⛔ 一个自相矛盾、一个横跨唯一有意义的边界；按现设计跑完，588 位人工判定换不到新信息

### 反驳

**上端（~120B）与 §12.3 自相矛盾。** §12.3 的整个论点是「**部署包络越宽松，越该用大的**」，包络上限自算为 **~1164B 总参**。那么包络论证的**代表点**必须是「包络内最好的模型」——按 §12.2 自己的表，是 **397B（4-bit 218 GB）或 671B（4-bit 369 GB）**，两者都进得了一台 8 卡节点。⛔ **而 §12.5 挑了 ~120B，比自己算出的包络上限低了一个数量级，理由（§12.6）是「单卡 80G 4-bit 装得下」。** 这是**用手上的卡决定包络代表点**，恰恰把 §12.3 的因果方向调转过来了：论证说「有服务器所以该用大的」，选型说「我只有一张卡所以用 120B」。审稿人会一句话点掉：**你的上端不是部署包络下的实际选择，是你的硬件下的实际选择。**

**且上端很可能已经跑过了。** 前沿闭源臂（`gpt-5.5` / `claude-opus-4-7`）在能力上是「包络内最好开放权重模型」的**上界代理**，而它的 Δ = **−15.82pp** 已在 588 位上测完。那么 120B 开放权重臂带来的**唯一新信息**是「开放权重同类模型上也这样」——这是**稳健性检查**，不是新发现。⛔ **为一个稳健性检查再花一整轮 588 位人工判定，性价比不成立**（该项目自陈人工判定是最贵的投入，见 [../../TODO.md](../../TODO.md) P0 条对基线成本的评估）。

**下端（8–20B）横跨唯一有意义的那条边界。** 按 R1 第 3 点的 σ 拆解，**唯一稳稳非零的档是 ≤8B**，20B 只有 2.0σ。所以：选 8B 大概能看到 Δ>0，选 20B 有可观概率拿到 Δ≈0。⛔ **而「8–20B」这个写法没有钉死档位。** 一旦下端也拿到 Δ≈0，你得到的**不是**「区间存在但落在包络外」（那是 §12.4 想要的话），而是「**我们在任何规模上都没找到增益**」——⛔ 那句话的默认读法是**实现失败**，不是负结果，而审稿人会优先取这个读法（理由见 R3）。**两端都为零的风险没有被 §12.5 登记为风险。**

**而 24 GB 那一格一改，下端的部署叙事也要重写。** §12.3 承认「唯一能救小模型的场景」是「只能跑在工程师现有终端上」。按 §0 结论三：24 GB 卡在 32K 上下文下的现实上限是 **~14–20B**，不是表里写的 44B。而 §12.6 自陈 `splitter` system prompt 是 **95,589 字符（≈25–30K token）**。⛔ **也就是说，唯一有部署意义的那个 niche，其显存刚好被这条流水线自己的 prompt 预算吃掉一大块**——下端臂如果要挂「跑在工程师终端上」这个叙事，就必须同时说明 32K 工作上下文在 24 GB 上怎么放，而现在这两件事在文档里是分开写的、没有对账。

### 为什么致命

失效的是 **§12.5 整张表的第三列**（「它回答什么」）。上端那格声称「真实部署包络下的实际选择」——按 §12.3 自己的标准，**120B 不是那个选择**；下端那格声称「脚手架增益是否真的存在，这是方法唯一可能赢的地方」——**在 20B 档它有约一半概率答「不存在」，而那个答案会被读成方法失败而不是负结果。** 两格都答不了它声称要答的问题，则「两端之差就是那个负结果的量」这句话失去指称对象。

### 证据

- §12.2 表（1164B 上限、397B/671B 的 4-bit 可容性）、§12.3 表、§12.5 表、§12.6 的排除理由与 95,589 字符：[SUMMARY.md](./SUMMARY.md) 逐字，**M**（文档内事实）。
- 588 位 = v46 判定位总数、人工判定为最贵投入：[../../story/terminology_policy.md](../../story/terminology_policy.md)、[../../TODO.md](../../TODO.md) P0 条，**M**。
- σ 拆解与两端皆零的风险：**I，我方推算**（依赖 R1 第 3 点那个 σ 推广假设）。
- 24 GB 格的复算：**I**，见 §0 结论三。

### 建议处置

**接受并重设计，三条改动**：

1. **上端改成包络内最大可容的开放权重**（4-bit 下的 397B 或 671B 级），并把「为什么不是 120B」写清楚。若算力上确实做不到，则**明说前沿闭源臂即该端的能力上界代理、120B 臂降为附录稳健性检查**，⛔ **不为它单开一轮 588 位判定**——复用同一批需求、只报机械指标（断言数、覆盖率、ref 翻转率），把人工判定省下来。
2. **下端钉死在 ≤8B**，如需斜率再加一档 20B；且**每档 ≥3 轮**，先用自己的数据估 $\sigma$，⛔ **不要沿用第三方的 σ**。
3. **事前登记「两端皆零」这个分支怎么写**。按 `CLAUDE.md` §3.5.1，判据必须在看到结果之前落盘。现在 §12 只登记了「两端之差就是负结果的量」这一个分支，**这是一个只登记了有利分支的事前登记**。

## R3 · ⛔ 负结果的**单位**与**先例**都错位：⛔ 没有被推翻的信念就没有负结果；且 §12.1 刚接受的私域前提，把「212×」那条腿自己拆了

### 反驳

**(a) 先例不同类，§12.4 第 3 点的类比不成立。** Chou–Aydemir–Dalpiaz（REFSQ 2026）测的是**别人的 / 通用的**方法（LLM vs 一个十年前的规则式工具），它推翻的是一个**社区实际持有的信念**——「LLM 在这类任务上应该能打赢规则式基线」。那是一个 field-level finding：任何人读完都要修改自己的先验。⛔ **而本文测的是作者自己独有的八阶段流水线。社区里没有任何人持有「这套脚手架在 671B 上有用」这个信念，因为在本文之前没有人提出过它。** 推翻一个只有作者自己持有过的假设，得到的不是负结果，而是**一份未成功的系统报告**。两者在 CCF-A 的可发表性上不是同一档，§12.4 把它们当成同类是这一节最大的乐观。

**(b) 要升格成 class-level 结论，缺的东西是结构性的。** §12.4 那句话的主语是「**这类**多阶段脚手架」。要让它成立，需要：(i) 干预可被独立读者识别为该类的合格实例；(ii) $n > 1$ 个实例。现在是 $n = 1$、由作者自己设计、自由度最大。⛔ 审稿人的默认解释一定是「**你的流水线不好**」而不是「这个类不行」——而且这个默认解释在本仓库里**有现成的弹药**：[SUMMARY.md](./SUMMARY.md) §6 第 2 条已自陈契约门 / 致命门可能吃掉正确产出。⚠️ 注意，§6 只把这件事当成**归因**威胁（「−15.82pp 能不能归因于多阶段干扰」）；**对 class-level 主张它是更重的威胁**，因为那些门是**这一份流水线的特有物，不是这个类的属性**。也就是说：即便门误伤量算清楚了、−15.82pp 归因成立，它成立的对象仍然只是**这份实现**。**class-level 那句话在证据链上没有通路。**

**(c) §12.1 的前提把成本那条腿自己拆了（§12 完全没意识到）。** §12.1 把私域部署提升为**既成事实前提**——很好，那是用户裁定。⛔ **但自建部署下 token 的边际成本是电费与 GPU 小时，不是 API 报价。** 于是：

- **「212× 成本」这根棒子在你刚刚接受的前提下自动软化。** 一个把工具跑在自家节点上的单位，不会因为 token 数多 212 倍就否决它——它关心的是**墙钟与节点小时**，而那两者与 token 数**不成比例**：prefill 与 decode 的吞吐差一到两个数量级，多阶段流水线的 token 里有多大比例是 prefill、有多大比例是 decode，直接决定节点小时比是 212× 还是 10×。
- **更要紧的是 prefix 复用。** 那个 **95,589 字符（≈25–30K token）的 system prompt 在每次调用中逐字相同**。自建栈的 prefix cache（以及 hosted API 的 prompt caching）会把它的 prefill 摊掉；而 212× 这个数如果是**按裸 token 计数**算出来的，它就把这份常量 prompt 在 3621 次调用里**重复计了 3621 遍**。⚠️ **本轮未核 212.6× 的算法是否已计入 caching / prefix 复用**——但这是审稿人一定会问的第一个成本问题，而它可能把这根棒子削掉一半以上。

### 为什么致命

失效的具体主张有三处：**§12.4 引用块里的「这类方法」**（(b) 使它无通路）· **§12.4 好处第 3 点「有目标 venue 的先例」**（(a) 使 Dalpiaz 只剩「该 venue 接受不利结果」这个弱先例，⛔ 不是「同形态先例」）· **论文摘要级的「成本高 212 倍」**（(c) 使它在 §12.1 的前提下自我削弱，且计数口径可疑）。三处一起失效之后，§12.4 剩下的可写内容只有「我们建了一个东西、它比朴素基线差 15.82 个点」——⛔ **那是系统报告 + Limitations，撑不起一篇 CCF-A。**

### 证据

- Dalpiaz 那篇的结论形态：[SUMMARY.md](./SUMMARY.md) §4.1 / §12.4 第 3 点转述，**S**（本目录转述，未一手核）。

### 建议处置

1. **Dalpiaz 降档**：只引作「目标 venue 接受得出不利结论的实证论文」这一**弱**先例，⛔ **删掉「这个形态最好的先例」这一表述**——它不是同一形态。
