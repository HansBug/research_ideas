# N1a · 工业应用场景的叙事与学术口径

> **本文件的职责**：把导师给的工业应用场景**写成可引、可辩护的学术表述**——用什么措辞、引谁、放论文哪一节、审稿人会问什么、以及不能说什么。
>
> **不在职责内**：判断这条路线能不能赢、方法有没有效果、该选哪个模型。那些归 M1 / N1b / R1。修订过程与已作废的越界产出见 [revision_log.md](./revision_log.md)。

## 0. 起点：导师的两句话

> **实际工业应用是不可能把真实项目材料放到商业大模型上去用的**
>
> **而工业应用场景中，很难去部署大规模的模型，没有专业的算力基础设施**

这两句是**前提**，不是待证命题。本文件负责把它们落成学术口径。

## 0b. 实验能力上限（2026-08-13）

**用户交底：本项目可用 4×H200 做实验。这只说明我们能跑多大的模型，没有其他含义**——它**不是**论文叙事的一部分，**不是**部署条件陈述，**不进** motivation。

**唯一用途**：给 N1b 的选型划可行域。4×H200 = 4 × 141 GB = **564 GB 标称**；权重预算 $564 \times 0.92 - 20 - 12 \approx 487$ GB（0.92 为 vLLM 默认 `gpu_memory_utilization`，20 GB 为 30K 上下文 KV 上界，12 GB 为激活 + CUDA graph + NCCL）。对应 4-bit 可容约 **854B 总参**。

实测体积对照（[open_weight_model_compute.md](./open_weight_model_compute.md) 的 HF 逐文件合计）：**可跑** `Qwen3.5-397B-A17B` 4-bit 224 GB（8-bit ~421 GB 亦可）· `DeepSeek 671B` 级 4-bit ~382 GB · `gpt-oss-120b` 64.6 GB；**跑不了** `DeepSeek-V3/V3.2` 原生 FP8 689.5 GB · `DeepSeek-V4-Pro` 1.6T · `Kimi-K3` 2.8T。

**一条随之作废的我方越界结论**：此前据「单卡 24 GB」推出的「必须小模型」「缺口闭合」整套分析，**其前提是我方自行构造的，不成立**——且用户已指出，判断「这条路能不能赢」本就不在本 PR 职责内。详见 [revision_log.md](./revision_log.md)。

**论文里的硬件披露与本节无关**：论文只需说「本地单节点部署」并给必要的复现参数（模型 + 量化档 + 上下文长度 + 采样参数），**不必点卡型**。

### 0b.1 可行域（核验完成，详见 [h200x4_envelope.md](./h200x4_envelope.md)）

⛔ **本节只回答「哪些模型跑得动」，不回答「该选哪个」。** 用户 2026-08-13 明确：4×H200 只是**我们能做实验的规模上限**，「**更大的模型我也没法做了，仅此而已，不是一定要顶着最强的上，至于到时候选择什么，根据情况而定**」。选型归 N1b。

⭐ **而「顶着最强上」恰恰被本轮数据否掉了**：总分最高的那几个在**幻觉净分**上灾难性（见下），而那一项直接对应本方法的核心失败模式。**按总分挑最强是错的挑法。**

**容量上限随约束层级变化（三层，只报第一层是失真的）**：

| 约束层 | 该层的容量上限模型 | AA Index v4.1.1 | 件与实测体积 | 归属 |
| :-- | :-- | --: | :-- | :-- |
| 只按容量 | `GLM-5.2` | **52.64** | `nvidia/GLM-5.2-NVFP4` **464.8 GB** | ⛔ **社区/三方**（Z.ai 自己没发 4-bit） |
| ＋须模型作者件 | `DeepSeek V4-Flash-0731` | 51.77 | **166.9 GB**，MIT，**余量 320 GB** | 官方作者件 |
| ＋格式须 Hopper 原生且官方点名 4×H200 | `MiniMax M2.7` | 38.87 | 原生 FP8 **230.1 GB** | 官方作者件 |

**本表 AA 分数已逐条回查：全部为 AA 实测**（详见 [aa_measured_vs_estimated.md](./aa_measured_vs_estimated.md)）——布尔位 `intelligence_index_is_estimated = false` 且 v4.1.1 的 9 项成分齐全，payload 值 `GLM-5.2` 52.6383 · `V4-Flash` 51.7704 · `M2.7` 38.87 · `Opus 5` 63.0532 · `Qwen3.6-27B` 37.7025。

⛔ **此前我在此处加的警报是错的**：「38 条里 26 条是估计值」是 §0b.4 那张**2025 世代表自己的统计**，与本表**几乎不重叠**（前者集中在 DeepSeek V3.x / Nemotron / 旧 MiniMax 等较早模型）——**不同分母，推不出本表有估计值**。已撤。

与 Claude Opus 5 (max) **63.05** 的差：**10.41 / 11.28 / 24.18 分**，比值 **0.835 / 0.821 / 0.616**。对照 ≤32B 档的 `Qwen3.6-27B`（37.70，比值 0.598）——**放到 4×H200 使总分差距减半，但第三层几乎回到小模型水平**。⛔ 这三个数只说明**可行域内总分能到什么量级**，⛔ 不构成选型建议。

**逐维度的方向与总分相反，这条比总分重要**：

- **AA-LCR（长文档推理）：装得下的模型反超前沿**——MiniMax M3 **80.3** vs Opus 5 **75.7**（+4.6）· GLM-5.2 76.7（+1.0）· V4-Flash 74.3（比值 0.982）。⚠️ 但 AA-LCR 在 Index 里只占 **6%**。
- ⛔ **AA-Omniscience 净分（幻觉）：全维度最差**——Opus 5 **+37.1** vs GLM-5.2 **+4.4**（比值 **0.119**）；而总分第 2 的 V4-Flash 是 **−14.3，符号相反**。⛔ 该项权重 **12%**，是 AA-LCR 的**两倍**，且**直接对应本方法的核心失败模式（多报）**。⛔ **故「按总分挑最强」是错的挑法。**
- 其余：HLE 0.749 · GPQA-D 0.960 · Terminal-Bench 0.874 · $\tau^3$-Banking 0.822。
- ⛔ **IFBench 无法用于新模型**：v4.1 已因饱和将其移出 Index，**2026-07-09 后发布的模型（含 Opus 5、Kimi K3）一律无分**。故 §7 那条「IFBench ≈0.97」只对**当时有分的 ≤32B 与前沿模型对**成立，不可外推到本表。

**4-bit 量化退化：证据充分**（12 模型 / 48 组跨档对照）——671B 级掉 **0–3%**，且**规模越大越鲁棒**（1.6B 激活 −6.53% → 550B −1.49%）。唯一一条 4-bit × 长上下文对照（Hy3 作者件）是 AA-LCR **73.4 → 71.6**；我们的 30K 落在 RULER **>99.5% recovery** 带内。⛔ **真正的雷是 KV cache 量化**：`W4KV8` 无损而 **`W8KV4` 掉 20+ 点**。⛔ **结构化输出 × 量化档在公开文献里零数据**（真实空白，非漏检）——**只能自测**。

**4 卡工程可行性：三层全过，但有一个硬风险**——整除、专家并行、互联全过关（384 专家可被 4 整除），4-way NVLink + 564 GB 是 NVIDIA 自己命名的产品形态；官方实例逐字核过：GLM-4.5 card 确有 `H200 x 4`（FP8），⚠️ 但**满 128K 要 8 卡**，且前置含 batch ≤ 8 与**主机内存 ≥ 1T**；唯一 400+ GB 的官方 4×H200 实例是 **GLM-4.7-FP8**（`vram_minimum_gb: 430`）。⛔ **最大风险：NVFP4 / MXFP8 内核是 Blackwell 原生，而 H200 是 Hopper**——`Motif-3-NVFP4` **整体失效**（card 明写需 Blackwell）；MiniMax M3 的 MXFP8 存在**未裁定的两源冲突**。

**两条否定结论（自查得出，使「装不下」的判定在全部已知路径上成立）**：DeepSeek **102 个仓库穷举，零 4-bit** · **对已是 4-bit 的模型再量化不缩小**——`nvidia/Kimi-K2.6-NVFP4` 与原生 INT4 同为 595.2 GB，`nvidia/DeepSeek-V4-Pro-NVFP4` **反而从 864.7 涨到 913.1 GB**。

### 0b.2 实验可行性：推理性能与并发（详见 [h200x4_inference_perf.md](./h200x4_inference_perf.md)）

⛔ **本节纯属实验可行性，与学术口径无关。**

**用户的假设方向反了**：`DeepSeek V4-Flash` 是四个候选里**最快、余量最大**的那一个；不适合的是 `GLM-4.7-FP8`，不可行的是 `GLM-5.2-NVFP4`。

| 候选 | KV/token | 最大并发@30K | 端到端墙钟（3621 次调用） | 判定 |
| :-- | --: | --: | :-- | :-- |
| `DeepSeek V4-Flash`（MLA-like，L=43） | **48.4 KiB** | **228.8** | **4.05 / 7.13 h** | 最优 |
| `MiniMax M2.7`（纯 GQA，L=62，Hkv=8） | 248.0 KiB | 36.4 | 11.75 / 12.89 h | 可行 |
| `GLM-4.7-FP8`（GQA，**L=92**，Hkv=8） | **368.0 KiB** | **6.8**（口径修正后 12.8） | 9.66 / 23.99 h | ⛔ 不适合 |
| `GLM-5.2-NVFP4`（MLA+DSA，L=78） | 87.8 KiB | 15.6 | ⛔ **拒绝估算** | ⛔ 不可行 |

**判据是激活参数，不是总参数**——按 config 推算 M2.7 **9.8B**（官方 10B ✓）· V4-Flash 16.0B · GLM-4.7 **~32B** · GLM-5.2 **~39B**。⭐ 文献里「大 MoE 低并发慢」的自变量是**激活参数**，⛔ 而这四个里**总参数与激活参数的排序是反的**。`GLM-4.7` 在并发（官方自己写 `batch ≤ 8`）与激活（3.3 倍）**两项同时最差**；`GLM-5.2` 被格式否掉（其 recipe 逐字 `Test Hardware: NVIDIA B200`，NVFP4 在 Hopper 无原生张量核，**Marlin 回退省显存不省速度**）。

**唯一卡数完全对齐的实测**：MiniMax-M2.5 FP8 on **4×H200 SXM**，32K 档 TTFT **1.3 s**（1 req）→ 5.2 s（8 req）；单用户生成 **81 / 47 / 25 tok/s**（1/8/18 req）；`Capacity: 18 requests`。⭐ 且是**关闭 prompt caching、关闭投机、满精度 KV** 测的，即**下界**。

**主 session 补测的一项（编排层真实并发）**：`launch_cells_serial.sh` 的并发是命令行参数 `MAX`，闸门为 `while [ "$(jobs -rp|wc -l)" -ge "$MAX" ]`；每格内部是**顺序多阶段**，故在飞 LLM 请求数 ≈ 运行中的格数。**从 run record 实读：峰值在飞 = 6，21 次记录全为 6。** 推论：**并发 6 对除 `GLM-4.7` 外的所有候选都远未触及 KV 上限**，故瓶颈是**单序列 decode 吞吐**而非 KV 容量——与上面的激活参数判据一致。

**两条对我方前提的纠正（从 3637 份 run record 全量聚合，非估算）**：

1. ⛔ **输入被我低估**——实测均值 **36.4K tok/次**、总 **132.4M**（我此前按 108.6M 估）。
2. ⛔ **「prefill 是主要成本」是错的**——**decode 占墙钟 51%–89%**（六档里五档 >68%）。故优化顺序是**投机解码 > 提并发（= 省 KV）> prefix caching > prefill 算力**。

**prefix caching 的真实收益（实测而非估算）**：3637 次调用里每个角色的 `system_prompt_sha256` **只有唯一取值**（逐字节相同），全实验**只有 5 个前缀**，合计 **48.9M tok = 总输入的 36.9%**。但乘上 prefill 只占墙钟 11%–49% → ⛔ **端到端只省 4.2%–17.4%（0.5–0.7 h）**。⛔ 那个常被引的「TTFT 降 7 倍」是**单请求冷热对比，不适用**；受控并发 A/B 的真实数是 vLLM **+13.3% 吞吐**。**该开（vLLM 默认就开），但不是成败关键**——我此前判断它「可能决定墙钟是 5 小时还是 3 天」，**那个判断错了**。

**「哪一档最常见」——初稿的一刀切「查无来源」被改为分层表述**：

- ⛔ **企业侧仍然查无严谨统计**（第三次复核，结论不变）。
- ⭐ 但存在两条**真实、官方一手、机读可复算**的分布：**MLPerf Inference** 的 per-submission `accelerator_memory_capacity`（Apache-2.0，v6.0 共 24 家提交方）= **厂商送测侧上限**；**Hugging Face 297,135 人自报本地硬件**（官方博客 + Apache-2.0 数据集）= **个人开发者侧下限**——最流行的独立显卡是 **RTX 3060（4,737 人）**，数据中心卡合计仅占 top-100 报告的 **~7.7%**。
- ⭐⭐ **一条最有价值的推论**：**这三条来源的采样机制都系统性排除企业内网**（厂商自愿送测 / opt-in 个人 profile / 公网暴露面）⇒ **企业侧的空白是结构性的，不是等更多调查能填上的**。⭐ 这给 §1.3 的方法论正当理由补上了**机制解释**。
- ⛔ 确认不存在：Stack Overflow 调查**无硬件题**（2025 只有 LLM 使用题）· Ollama **无官方遥测**。

1. ⛔ **价格的主要发现是否定事实**：8 款专业 / 数据中心卡与 DGX / HGX **官方一律不公布价格**，路径统一是 "Find a Partner"。⚠️ 但 **nvidia.cn 对 RTX 5090 D v2 官方标价「￥16,499 元起」**——**同一厂商中英文站披露口径不同**。

### 0b.4 2025 世代开放权重全谱（详见 [open_weights_2025.md](./open_weights_2025.md)）

**135 个 HF 仓库条目**（106 基座 + 29 量化变体），22 厂商，参数量 0.27B–999.7B（跨 3700 倍），体积 0.5–1999.4 GB。**135/135 全部逐文件实测，零推算。**

**各档最强（2025 世代）**：

| 档 | 模型 | 体积 | 归属 |
| :-- | :-- | --: | :-- |
| **T1 / 24 GB** | `gpt-oss-20b` | **13.8 + KV 1.4 = 15.2 GB** | 官方件，原生 MXFP4 |
| **T1 / 84 GB** | `gpt-oss-120b`（117B / 5.1B） | **65.2 GB** | 官方件，**官方背书单张 80 GB H100**。同档 `Seed-OSS-36B` 72.3 GB 有 **512K 原生 context** |
| **T4b / T5** | `Kimi-K2-Thinking`（1T / 32B） | **594.2 GB** | **原生 INT4 QAT 作者件**——2025 世代唯一「1T 级 + 单节点装得下」的组合（同族 FP8 版 1029.2 GB 超 1024 GB 预算）。vLLM 官方 recipe 逐字 `8x H200/H20` ⇒ **INT4 QAT 在 Hopper 原生** |

**主要发现：Blackwell 格式判据几乎不打击 2025 世代。** 2025 世代 **NVFP4 官方件仅 1 个**（`Mistral-Large-3-2512-NVFP4`）· **MXFP8 为 0 个** · MXFP4 4 个（gpt-oss 四型）。⇒ 那条打掉 2026 世代容量排序前三名的判据，**在 2025 世代几乎无杀伤**。

**MXFP4 的裁定本轮从源码闭合**：vLLM 逐字 `SM90 falls through to … Marlin`、`the fallback dequantizes only the weights`，act dtype 硬返回 BF16 ⇒ **能跑、省显存、不省算力**。⛔ 但「Hopper 无 FP4 张量核」这句**在 NVIDIA 官方文档里找不到显式否定句**，依据只有引擎行为侧——**引用时须如此表述**。

**生态成熟度：我的假设有反向失效模式。** 我此前判断「2025 世代生态更成熟」——⭐ 大体成立（`Qwen3` 是唯一同发 FP8 + AWQ + GGUF 三条线的厂商，GGUF 命中 336–632；`DeepSeek R1` 系 AWQ 192 + GPTQ 94；`Gemma 3` 是唯一发 QAT 件的），⛔ **但有三个反例、且两个独立引擎注册表一致**：`dots.llm1` 与 `MiniMax-M1/Text-01` 落在 vLLM 的 `_PREVIOUSLY_SUPPORTED_MODELS` 里（末版 v0.23.0）、SGLang 无模块——⛔⛔ **`MiniMax-M1` 是「曾支持后被移出」**。**故「老模型生态更成熟」不是单调的：模型会被引擎摘掉。**

**一条影响本目录其他表的发现**：⛔⛔ **AA Index v4.1.1 的 38 个条目里只有 12 个是 AA 实测，26 个是估计值**——而其页面**顶部写裸数字、只有 FAQ 才标 `(estimated)`**。⭐ 故 §0b.1 与 §7 里引用的 AA 分数**须逐条回查是否为实测**，⛔ 未查明前不得当实测引用。另 **10 个模型完全无 AA 条目**；`Mistral-Large-3` 是唯一「AA 有实测分但零个官方自报数字」的。

## 1. 场景叙事：两句话怎么写成学术表述

### 1.1 前提一：真实项目材料不外发

**可用的英文表述**：

> In industrial settings, project artifacts such as requirements documents and design models are typically **not permitted to leave the organization's boundary** for processing by third-party hosted models.

**依据形态是「观察到的产业实践」，不是法规强制**——这一点必须自觉，因为它决定了怎么引：

| 可引证据 | 逐字 / 要点 | 谁在用 |
| :-- | :-- | :-- |
| 三星禁用 ChatGPT 事件（CNBC） | 企业级禁令的公开事例 | **TOSEM 2025**（CCF A 刊）就是引它 |
| **ABB Spec2Control** | 自陈 "we cannot publish them"（控制叙述属专有） | 同域（NL → PLC 控制逻辑）自述实践 |
| **CCS 2024**（[arXiv:2405.06371](https://arxiv.org/abs/2405.06371)，27 人访谈，CCF A） | 记录「因保密改用本地 Llama」的真实实践 | 唯一的访谈级实证 |

**放论文哪一节**：Introduction 的 motivation 段（一到两句）+ Threats to Validity 里显式承认它是 **assumption** 而非已证事实。

⚠️ **写成法规强制会有风险**。法条层能支撑的只有「不能用**未获授权的**商用端点」（DFARS 252.204-7012 (a) + NIST SP 800-171 §3.1.20），**推不出「不外发」这条更强的实践**。

⚠️ **必须主动交代的同域反例**：ABB 那篇同时**用了 Azure AI Foundry 上的 GPT-5**。处置是限定场景——设备厂商的内部工具链 ≠ 型号研制单位的涉密制品。**藏着不说比说出来更危险**，因为它就在同一篇里。

### 1.2 前提二：算力有限、固定、专用

**这一句最容易写坏。** 关键是：**私域部署不等于「没有算力」，而是「算力有限、固定、不可弹性扩展」。**

**可用的英文表述**：

> On-premise deployment implies a **fixed, dedicated compute budget** rather than elastic cloud capacity: capacity is procured once for a specific environment, cannot be shared across isolated segments, and cannot be scaled on demand.

⚠️ **「工业单位没有算力基础设施」这个措辞有风险**——有官方级反证：**浪潮 NF5868G8 官方页 1536 GB、可单机部署 DeepSeek 671B**；新华三一体机官方页覆盖 14B–671B。而这类一体机**正是工信部文件推荐给「算力有难点」群体的形态**。

| 可引证据 | 能支撑什么 | ⚠️ 限定 |
| :-- | :-- | :-- |
| **工信部工信厅通信〔2026〕14 号** 逐字「针对中小企业在算力获取、应用落地和能力提升中的难点」，并推荐「训推一体机」「整合本地闲置、分散算力」 | **官方承认算力获取存在难点** | ⛔ 口径是**中小企业**——引用时必须带这个限定，**不得暗示它涵盖型号研制单位** |
| **NVIDIA 10-Q**（期止 2026-04-26，SEC EDGAR）逐字「No shipments of Data Center Hopper products to China occurred during the quarter」「effectively foreclosed from competing in China's data center compute market」 | **高端数据中心 GPU 的可得性受限**，是「算力有限」的一个成因 | ⚠️ 宜只作**成因**——用它论证某个具体显存天花板会站不住 |
| **Weyssow et al., TOSEM 2025** 把「单卡 24 GB」写进 §3 独立成节、§4 方法论开篇、模型池筛选、直到结论句 | **固定算力预算可以作为承重前提**——这是最强的形态先例 | — |
| **REFSQ 2026** 把预算收到 **6 GB** | 同上，且更窄 | — |

**放论文哪一节**：与前提一同段，或紧随其后；实验设置节再给出本文实际采用的预算数值。

### 1.3 两句话合起来的研究问题形态

> 在一个**不外发**、**算力固定**的部署条件下，开源模型能否达到商业 SOTA 的水平？

**这个形态的三个好处**：

1. **不需要「必须小模型」**——只需要「包络是固定的」，具体多大由实验设置给定。
2. **不需要论证任何具体天花板**——那是我方此前自造的负担。
3. **反例不构成反驳**——它是**部署条件**而非全称断言；某单位有大算力不影响「存在这一条件」。

⛔ **一条硬条件**：**不得同时兼享「工业界普遍状况」的修辞**。工业单位实际算力**查无严谨来源**（四大中文库全部不可用 · 国产一体机官方材料不公布显存与卡数 · 军工方向零篇可引学术文献）。**而「数据结构性不可得」本身，正是「为什么陈述条件而非调查现状」的方法论正当理由。**

## 2. 术语选择

| 术语 | 用不用 | 理由 |
| :-- | :-- | :-- |
| **on-premise deployment** | **首选** | 文献通用，含义准确（自有场地部署），不预设规模 |
| **self-hosted** | 可用 | 与前者近义，偏工程语境 |
| **private deployment / 私域部署** | 中文可用，英文慎用 | 英文里 "private" 易与 "privacy-preserving"（差分隐私等技术路线）混淆 |
| **air-gapped** | ⛔ 只在真气隙时用 | 它是强断言（物理隔离），我方无证据支撑该场景普遍存在 |
| **local LLM** | ⛔ 避免 | 歧义——可能被读成「跑在笔记本上」 |

⚠️ **本轮实证**：MDE/RE 侧 1,029 份摘要里，`self-hosted` / `air-gapped` / `locally deploy` / `data never leaves` / `sovereign` / `open-weight` **六类说法一次都没出现**。**故这些术语在目标社区尚未成为惯用语，首次使用需给出定义。**

## 3. 文献先例：引谁、怎么引

**承重先例（3 篇）**——它们把「固定算力预算」做成了贯穿全文的前提，是形态样板：

- **Weyssow et al., TOSEM 2025**：单卡 24 GB 贯穿 §3 / §4 / 模型池筛选 / ICL 样本数 / 结论句（逐字「QLoRA enables the fine-tuning of LLMs up to 34B parameters for less than 24GB of GPU memory」）。**最强样板**。
- **REFSQ 2026**：预算收到 6 GB。
- **ICSR 2025**（[arXiv:2504.07907](https://arxiv.org/abs/2504.07907)，真实工业伙伴）：逐字「We had no available resources to fine-tune the larger model」「there was no need for a large scale compute cluster」「consumer GPUs as affordable business hardware」。**唯一落在单位级的证据**，判半承重；⛔ 通篇不给 GPU 型号与显存。

**判定承重与否的可复用判据**（19 篇 100% 一致）：**承重时数字会遍布 Methodology / RQ / 结论；只在 Setup 出现一次的基本不承重。**

⚠️ **一条对目标社区的冷判断**：MODELS / RE / REFSQ / SoSyM / REJ 共 **1,455 条题录、31 venue-年份**里，只有 2 篇写出「因保密所以用本地模型」这条因果，**三篇全文到手全部判装饰、承重 0 条**。**故审稿人不会默认接受这条动机，首次提出须给足依据。** 相对地，SE 期刊侧（TSE / TOSEM / EMSE）有 7 篇承重（⚠️ 其中 5 篇仅摘要级判定）。

## 5. 风险清单

本节**不是禁令**——本轮只做调研，无权规定正文怎么写。它标的是**已知反证与薄弱处**，以及**若要写建议配什么条件**。分两层，因为两层性质不同。

### 5.1 事实层：与措辞无关，写了就是错的

| 项 | 事实 |
| :-- | :-- |
| 「Gemini 3.5 / 3.6 Pro」「Grok 5」「无后缀 GPT-5.6」「910C 有 xx GB」 | **这些对象不存在**：Gemini Pro 线停在 3.1 Pro Preview（此后只发 Flash 系）· xAI 已被 SpaceX 收购、旗舰是 Grok 4.6 · GPT-5.6 只有 Sol / Terra / Luna 三个后缀 · 「910C」从未出现在任何官方硬件规格表 |
| 引 Anthropic 那句时删掉 `only` | 完整句是「ITAR data **can only** be processed via AWS Bedrock」——删后语义改变。属引文完整性 |
| 混比不同 AA Index 版本 | v4.0 与 v4.1.1 差可达 8 分（`Qwen3.6-27B` 46 → 37.70） |
| 引 Terminal-Bench 分数不写脚手架名 | 同一模型换脚手架分数可差近 2 倍，不写等于不可比 |

### 5.2 风险层：可以写，但有具体反证——须知风险并考虑配什么条件

| 若要写 | 风险来自哪 | 建议配的条件 |
| :-- | :-- | :-- |
| 「工业保密**所以必须**私域部署」 | 法条判据是**系统资质**而非「私域」；且私域对商业秘密／研发数据层完全正当（自建不构成委托处理），三层图景压成一句会失真 | 写成「因此**倾向于**在自有边界内处理」，或明确限定到「涉密制品」这一层 |
| 「工业单位**没有**算力基础设施」 | 两条：官方统计口径是**中小企业**（型号研制单位不在该抽样框）· 且有官方级反证——浪潮 NF5868G8 官方页 1536 GB、可单机部署 DeepSeek 671B，而这类一体机**正是工信部推荐给「算力有难点」群体的形态** | 写成「算力**有限、固定、不可弹性扩展**」；若坚持原措辞，须**限定到具体组织层级**并预答一体机反例 |
| 「私域部署本身也不合规」 | 这是把「引不出」说成了「被禁止」——法条管资质与委托处理义务，不管部署在哪 | 若要提，写成「涉密场景下**私域不构成合规判据**，判据是系统资质」 |
| 兼享「工业界普遍状况」的修辞 | 该断言无法证实：工业单位实际算力查无严谨来源，且该空白是**结构性的**（三条真实分布的采样机制都排除企业内网） | 用「存在这一部署条件」代替「工业界普遍如此」。⭐ 而「数据结构性不可得」本身可作为**为什么陈述条件而非调查现状**的正当理由 |
| 「据我们所知不存在 X」 | 本轮覆盖不足以支撑全称否定（ICSE / ASE / ISSTA / FSE 正文覆盖为零；中文四大库不可用） | 写成「在本轮覆盖的 X 内未见」并附覆盖范围 |
| 「我们实测成本高 212 倍」 | `212×` 是**裸 token 计数的上限**：input 主导（`review_assertions` 一块 98% 是反复重读），且那份 95,589 字符 system prompt 逐调用相同却被各算一遍。本仓库 `run_telemetry.py` 自己写着「跨代比较应以 `output_tokens` 为准」 | 以 `output_tokens` 为主口径，裸 token 比作上限附注 |

## 6. 五问的最终答案（契约要求，逐问落档）

### Q1 · 功能安全标准里有没有禁止外发的条款

**没有**，且不是「查不到」而是**标准自陈排除**（空集式结论）：

- **IEC 61508-1:2010 §1.2 m)**：「does not specify the requirements for … security policies or security services」
- **ISO/SAE 21434:2021 §1 Scope**：「does not prescribe specific technology or solutions related to cybersecurity」
- EN 50716:2023 Introduction 措辞与 IEC 61508 同源，**不计为第三条独立证据**

覆盖 9 本标准（IEC 61508-1/-3 · ISO 26262-2/-6/-8 · ISO/SAE 21434 · IEC 62304 · DO-178C/-330 · EN 50128/50716）+ 4 份邻接文件。**ISO 26262-8 的 DIA 机制管的是责任划分而非数据驻留**，且 §5.2 NOTE 2 使该章对不担安全责任的供应商整章不适用。

### Q2 · 真正可引的依据在哪一族

分两层，**混谈是本轮最容易犯的错**：

| 层 | 最强依据 | 能支撑什么 |
| :-- | :-- | :-- |
| **法条层** | **DFARS 252.204-7012 (a)** 的 `Technical information` 定义逐字含 "specifications, standards… engineering data… data sets"，即需求文档与设计模型本身；配 **NIST SP 800-171 Rev 2 §3.1.20** DISCUSSION 逐字点名 "software as a service" | 「不能用**未获授权的**商用端点」——**可立** |

### Q4 · 「小模型 + 方法学补偿」怎么讲圆

从读到正文的九篇里抽出**六种彼此正交的手法**，其中三种对本文相关。逐条给出处与判定：

| 策略 | 样本与年份 | 对本文的可迁移性 |
| :-- | :-- | :-- |
| **A** 承认落后 + 立刻绑定约束条件 | VerIbmc（[arXiv:2606.16886](https://arxiv.org/abs/2606.16886), 2026, arXiv preprint 无 venue）· Tai et al.（[arXiv:2507.08627](https://arxiv.org/abs/2507.08627), 2025） | **最高**。要点是**差距的绝对值留在原地，改变的是分母**——不是「只差 10 题」而是「在单机、无外部调用的前提下差 10 题」。⛔ **但有一条生死线前提**：我们的 SOTA baseline 也必须是云端才行；若朴素单提示在小模型上也跑出高分，约束就不构成差异。**故必须补一格「朴素单提示 + 部署条件内模型」** |
| **B** 非劣性替代优越性 | Su & McMillan（Automated Software Engineering, 2024）· Caumartin et al.（SANER 2025） | ⚠️ **中**。**15.82pp 过不了任何非劣性检验**，除非找到差距落进噪声底的分层子集。且「未拒绝原假设」≠「证明等价」——要用**正式 TOST 并预先声明边界值 δ** |
| **C** 把被牺牲的一侧真跑出来报数 | Kumar & Chimalakonda（[arXiv:2412.15676](https://arxiv.org/abs/2412.15676), 2024，⚠️ 是否发表待核验） | **可用**。它是全批**唯一**这么做的（把集中训练上界跑出来后再说「However, we choose FL because it offers privacy」），也是最能挡住「你在藏结果」的做法 |

**证据细节（VerIbmc 那张表的口径）**：它对**同一套三阶段流水线**做 `Basic`（完整）vs `LLM-Only`（跳过符号先验）消融，故其 Δ 的物理含义是**「符号先验这一个阶段的贡献」**，任务是形式化验证的不变式生成（后端 ESBMC v8.2，模型本地跑于 4×A6000）。逐模型 Δ：8B **+35** · 7B +24 · 20B +15 · 32B **+2** · 120B **+3**。⚠️ 其中 `+35` 的被减数 342 取自**三次运行的最好一次**（均值 336.0，σ=5.3），故**该值落在采样方差的乐观端**。

**关于 $\Delta \gtrsim G$ 这个条件（⛔ 两处限定不可省）**：

1. ⛔ **它是我方推论，不是文献结论。** VerIbmc 没有提出它；我方据其数据构造——若要主张「小模型 + 方法 ≈ 大模型」，则方法增益 $\Delta$ 须覆盖裸能力差 $G$。作者因此用了策略 A 而非宣称打平。
2. ⛔ **但 $G \approx 89$ 这个取值有一处偷换，须纠正。** 我方原文把 $G$ 定义为「与**云端 SOTA** 的裸能力差」，取的数却是 `431 − 342`——而那两端是 **GPT-OSS-120B** 与 **Llama-3.1-8B**，**两个都是开放权重、都跑在本地 4×A6000 上**。⛔ **VerIbmc 那张表里根本没有云端前沿模型**，故 89 是**开放权重家族内部的跨度**，不是「到云端 SOTA 的差」。该篇与前沿的比较是**跟别的系统**比（Clause2Inv 356 · LORIS 351 · LaM4Inv 338，三者 "require state of the art expensive frontier models run on external servers"），⚠️ 且**那是另一个口径**（赢它的两个工具只吃单循环标量整数程序，SV-COMP 可比子集缩到 43 题），**431 与 356 不可直接比**。
3. ⛔ **我们需要的那个 $G$ 不在这张表里。** 本文主臂是 `gpt-5.5` + `claude-opus-4-7`（54 pair × 2 模型 × 3 轮 = 324 格），**两个都是闭源前沿**。「部署条件内模型 → 主臂模型」的差距只能从别处取——benchmark 侧给的是 **AA Index 37.7 vs 63.1 = 25.4 分**（≤32B vs 前沿）。⚠️ **解题数与 Index 分单位不同，不可互换。**
4. ⛔ **它只对已放弃的 parity 主张适用。** 本轮已把主张改为「部署条件内模型 + 方法 vs **同模型裸跑**」（见 §7），该主张只需 $\Delta > 0$，**不需要 $\Delta \gtrsim G$**。故不得再用「$\Delta \gtrsim G$ 过不了」去否定策略 A 与 C。

**一条从同表重算出的结构观察（我方新得）**：89 分跨度里 **82 分（92%）发生在 8B → 20B 之间**（342 → 424），而 **20B → 120B 只有 +7**（424 → 431）。即**绝大部分能力跨度落在部署包络之内**。推论：**在包络内挑对模型的影响，几乎等于整个 8B→120B 的全部差距**——故正确动作是「在包络内挑最强的」，而非「必须小」。⛔ 但同表也警告不能按参数量挑：**Qwen2.5-32B（382）比 GPT-OSS-20B（424）差 42 题**，包络内「越大越好」同样不成立。
