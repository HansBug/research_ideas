## 1. Thesis

给定一份自然语言需求 `NL` 与一份由 LLM 从该需求生成的状态机模型 `STM_0`，
**把「这个模型哪里不符合需求」变成一个可机械求值的问题**：
先把需求全覆盖地拆成一条条义务，再把每条义务转换成一个受限谓词逻辑上的断言，
在被评审模型上求值——为假者构成一条**带可执行判据与闭合证据链**的发现，
为真者构成**回归防护**。

一句话：**本文贡献的是一套谓词逻辑元模型与断言体系，而不是「我们发现了多少问题」。**

## 2. 解决什么问题

LLM 已经能从自然语言需求生成状态机式制品，但生成出来的东西**不能直接用**——
它可能漏掉需求点名的状态、把条件写成事件、把并列条件压成一个名字、
留下进不去的状态或没有默认入口的复合态。于是问题从「能不能生成」变成
**「怎么知道生成的这一份哪里不对」**。

这不是一个「跑个检查器」的问题，原因有三层：

1. **判据从哪来**：需求是散文，模型是图；「模型是否满足需求」不是一个现成的形式化判定问题，
   得先把散文里的义务抽出来，再决定每条义务用什么可判定的形式表达。
2. **表达什么才算表达对了**：同一条义务有多种操作化，其中一部分是**伪代理**——
   「某条迁移是否存在」冒充「某个状态是否可达」就是典型：边存在不等于可达（守卫可能恒假、
   源态可能不可达），边不存在也不等于不可达（可经其它路径）。形式相似而实质不同。
3. **行为性问题在图上没有定义**：PlantUML 是绘图记法，不定义执行语义——
   「从上电起 3 步内能否到达 X」在它上面不是难以回答，是问题本身没有定义。

## 3. 为什么这个问题有价值

三条，按对审稿人的说服力排序：

1. **它是 LLM 建模落地的必经关口。** 控制系统的状态机模型下游要接模型检查、
   测试生成、代码生成；一个「看起来像状态机」的制品进入下游，错误会被放大而不是被发现。
   而人工逐份复核 LLM 生成的模型，成本与直接手写模型相当——那样 LLM 就没有意义了。
2. **它的产出形态决定了下游能不能用。** 见 §4：现有 detection 方法给出的是「这里可能有问题」，
   而下游需要的是「这条需求的这一条义务，在这个元素上，以这种方式不成立」。
3. **它是可累积的。** 断言一旦成立就可以反复求值。模型改一次，整套断言重跑一次——
   这是「一次性评审」变成「持续防护」的分界。

## 4. 现有方法存在的问题

这一节是 Intro 的 motivation 核心，**用导师的原话组织**：

> 现有的很多 detection 方法报告错误，**缺少错误的上下文信息**，一方面需要人工进行繁重的复核，
> 另一方面也不便于进行错误修复后的回归确认。

拆成三条可写的 gap：

| Gap | 具体表现 | 后果 |
| :-- | :-- | :-- |
| **G1 判据不可复算** | 报告是自然语言判断，读者无法自己验证真假 | 每条都要人工回读需求与模型，复核成本与重新评审相当 |
| **G2 缺少定位与归因** | 只说「有问题」，不说是哪条需求的哪条义务、锚在哪个模型元素 | 无法确定改哪里；改完也无法确认改对了 |
| **G3 无法回归** | 报告是一次性的、不可重放 | 模型改动后要从头再评审一遍，且无从知道旧问题是否复现 |

⚠️ **补一条我们自己的观察，它比上面三条更根本**：直接把形式化工具裸给自主 agent，
效果很差。agent 会乱用工具、一个劲地摸索，把算力烧在探索工具接口而不是理解需求上；
而且这条路线吃大量基础设施而不产生对应回报。**这条观察是反面立论，指向 §5 的方法洞察。**

## 5. 我们的方法：核心洞察

### 5.1 受限谓词词表本身就是一次建模

**这是本文最核心的判断，也是导师认可的那条「业务建模的重要性」的落点。**

不给 LLM 一个通用工具箱让它自己摸索，而是**先把「一个状态机模型可能在哪些方面不符合需求」
这件事建模一遍**，结果是一个 19 个谓词的闭合词表。词表按求值机制分三族：

| 族 | 个数 | 回答什么 | 谓词 |
| :-- | --: | :-- | :-- |
| 结构 | 10 | 模型里写没写 | `state_declared`、`event_declared`、`variable_declared`、`edge_declared`、`containment`、`initial_target`、`effect_declared`、`action_declared`、`guard_distinguishable`、`cardinality` |
| 仿真 | 6 | 跑起来会怎样 | `reaches`、`occupancy_after`、`event_consumed`、`stays_in`、`terminates`、`variable_delta_after` |
| 有界模型检查 | 3 | 界内是否恒成立 | `invariant`、`response_within`、`persists_until` |

这个词表干了三件事，缺一不可：

1. **它是一次领域建模**——把控制系统需求里反复出现的义务模式（可达、驻留、事件响应、
   效果方向、覆盖）固化成有限个可判定形式。
2. **它约束了 LLM 的输出空间**——LLM 不再自由发挥，只做「把这条义务映射到哪个谓词、
   绑哪些元素」这一件事。
3. **它让测不了的东西显式暴露**——义务无法用这 19 个谓词表达时，系统必须记为覆盖缺口，
   不许换个近似谓词蒙混过去。

⛔ **词表的由来必须按这个口径表述**：从**现实需求、技术文档与规约、学术文献**三类领域资料
归纳而来，应用于 54 个案例，并据此指导 prompt 设计。**不表述为「从这批 pair 归纳」。**
工程上这是硬要求（每条规则挂可查证外部出处、动机与出处分开记录），见
[../discover_matrix/docs/protocol/method_provenance_policy.md](../../../discover_matrix/docs/protocol/method_provenance_policy.md)。

两个具体的挂钩示例，可直接写进论文：

- `stays_in` 的语义取自 UML 2.5.1 §14.2.3.9.1 的 run-to-completion 规则——
  一个在当前配置下不触发任何迁移的事件会被丢弃，而丢弃不改变配置。
  **所以「事件有没有被消费」与「机器有没有离开」是两个独立问题**，
  该谓词不能用前者近似后者。
- `persists_until` 取自时序逻辑中 until 的标准定义：`p U q` 只约束 `q` 首次成立**之前**的
  前缀，而「整个区间上 `p` 或 `q` 恒成立」是一个严格更强的不同公式；有界情形取弱形式，
  界内既未释放也未违反的运行不算反例。

### 5.2 断言由全覆盖的需求拆分转换而来，因而天然具备覆盖性

流程不是「让 LLM 读模型找问题」，而是**先读需求**：把需求原文全覆盖地拆成义务，
再逐条转换成断言。这条顺序有两个直接后果：

1. **覆盖性来自构造，不来自运气**——分母是需求的义务集，不是模型的可疑点集。
2. **每条发现天生带上下文**——它知道自己来自需求哪一句、绑在模型哪个元素、
   用哪个谓词以什么参数求值为假。§4 的三条 gap 由此同时被填。

### 5.3 阶段化 + 定向反馈的循环

八个阶段，每个产出阶段配一个审查者，不合格带**定向反馈**打回重写：

```
需求 + 模型 → ① 需求拆分 → ② 需求审查 ⟲ ①
            → ③ 断言转换 → ④ 静态预检 ⟲ ③ → ⑤ 断言审查 ⟲ ③
            → ⑥ 求值发布 → ⑦ 归因绑定 → ⑧ 结果裁决 → 发布 issue
```

⚠️ **循环发生在审查者与被审查者之间，不是重试**：审查者说清哪一条不合格、缺什么、
期望什么形状，被审查者据此修订。**这一点必须与「换个随机数再跑一次」明确区分**，
否则整个循环的贡献会被读成「多采样几次」。

⚠️ **⑥ 的求值不看需求也不看参考模型，只看被评审模型本身**，所以它的真值是客观的、可复算的。
求值层允许**拒答**：谓词无法给出可靠真值时返回拒答而不猜真假。

### 5.4 为真的那部分不是废料

求值为真的断言构成**回归防护**：它们记录了「这份模型在这些义务上是对的」。
模型改动后重跑，为真变为假即为回归。**这是同一套断言体系的第二个用途**，
也是它相对一次性 detection 报告的结构性差异。

⚠️ 这条目前是**方法性质的主张，不是实测结论**——v46 未统计防护面规模，见
[claim_evidence_map.md](./claim_evidence_map.md) 的 C5。

## 6. Contributions

导师定调（原话）：「**discover 部分单独成一篇文章**」「repair 不会简单的，特别是要高质量
repair」「这个逻辑进一步印证了**业务建模**在其中的重要性」。

**两条，按此排序：**

### C-I 谓词逻辑元模型与断言体系

一套面向状态机模型问题发现的**谓词逻辑元模型**：19 个谓词构成的闭合词表 + 一套把自然语言
需求义务转换为该词表上断言的方法。它的三个性质是贡献的实质：

1. **覆盖性来自构造**——断言由 NL 全覆盖拆分出的需求条目转换而来。
2. **判据可机械求值**——每条发现挂在一个可复算的谓词调用上；测不了的显式记为覆盖缺口。
3. **为真者构成回归防护**——同一套断言在模型改动后可重放。

⚠️ **贡献不是「发现了多少问题」。** 覆盖率是支撑这条贡献的证据，不是贡献本身。

### C-II 带上下文的发现，使人工复核与回归确认可行

现有 detection 方法报告错误但**缺少错误的上下文信息**，导致人工复核繁重、
且不便于修复后的回归确认。本方法给出的是**可执行判据 + 闭合证据链**：
每条发现可回溯到需求原句、模型元素、谓词调用与求值记录。

⚠️ 这条可以**捎带提一下**可用于修复，但不宜多提——这篇文章不做修复。

### 不能写成主贡献的

以下属方法支撑或评价纪律，**不得写成 contribution bullet**：

- 中间表示与 PlantUML → DSL 的转换桥（它自身还有已量化的损耗）；
- run record 与证据簿记；
- 缺陷台账与命中判定口径；
- 多报侧五类裁定流程；
- 「loop + verification feedback」这条旧定调（已被本节取代）。

## 7. 技术挑战

| 挑战 | 为什么难 | 本文怎么处理 |
| :-- | :-- | :-- |
| **义务的操作化可能是伪代理** | 同一条义务的多种形式化不等价（边存在 ≠ 可达） | 闭合词表 + 断言审查阶段 + 明令禁止的替换形态清单 |
| **行为性问题在绘图记法上无定义** | PlantUML 无执行语义 | 编译到带形式语义的 DSL 后求值 |
| **编译不是无损的** | 两种记法表达力不重合 | 把损耗单独量化为**表示债务**并如实报告，不藏、不计入误报 |
| **求不出来时不能猜** | 「求不出来当成假」会直接造出假发现 | 谓词可拒答；拒答连同原因记录并回灌 |
| **配额耗尽时不能整格崩** | 最容易耗尽配额的恰是缺陷最硬的样本 | 降级：封存已有产物落盘，未完成部分记为结构化诊断 |
| **多报侧不能简单读成误报** | 逐条读完后该读法是错的 | 五类裁定，逐簇给判据，并给两套分母 |

## 8. 证据现状

一次完整的全量实验已完成：**54 pair × 2 执行模型 × 3 轮 = 324 格**。
完整结果、展开分析与全部局限见自包含报告
[../../talks/2026-08-10-实验-v46全量矩阵双侧结论.md](../../../../talks/2026-08-10-实验-v46全量矩阵双侧结论.md)。
claim 与证据的逐条对应见 [claim_evidence_map.md](./claim_evidence_map.md)。

最需要注意的三条证据性质：

1. $\mathrm{hit@1} \le 60.4\%$ **只能作为上界**——两条通道会让它虚高，且命中侧的对称审计未做。
2. **没有外部对照**——本文只报绝对量。朴素基线是补对照的第一项。
3. **判定层是独立误差源**——单一判定者，无一致性系数。

## 9. Related Work 定位

三条轴，每条都要说清「他们做到哪、我们补什么」：

1. **LLM 生成行为模型 / 状态机**：产出候选制品，但不回答「这一份哪里不对」。
   本文的语料正来自这类工作，因此这条轴同时是 related work 与语料来源。
2. **形式化建模与验证工具（模型检查器、DSL、静态检查器）**：提供可判定语义与查询语言，
   是本文的求值机制来源。⛔ 但本文不主张任何工具或语言更好——它们是介质。
3. **LLM 辅助的缺陷检测 / 评审 / 规约生成**：与本文最近，**差异化落点正是 §4 的三条 gap**——
   报告缺上下文、复核成本高、不可回归。
4. **表示层引入的假象**：表示债务这一现象既有文献已有同构名字——CEGAR 的
   spurious counterexample、静态分析框架的 program representation fault、
   模型驱动工程的 semantics preservation。**我们的新处只在把它做成评测归因侧的可扣除量**，
   三点限定：不是过近似造成的伪反例、不是工具 bug、落点在评测归因而非建模或验证环节。

## 10. 可以说的话

- 我们研究「给定需求与一份从它生成的状态机模型，自动发现不符合之处」这一任务。
- 我们给出一个 19 谓词的闭合词表与一套需求义务到断言的转换方法，
  使每条发现都可机械求值、可回溯到需求原句与模型元素。
- 断言由需求全覆盖拆分转换而来，因而覆盖性来自构造；求值为真者构成回归防护。
- 可执行语义是必要的：按台账断言组的族构成，26%–43% 的已知缺陷需要行为证据表达（两口径）。
- 未被台账认领的产出逐条可裁定，其中最大一块不是模型缺陷也不是方法误判，
  而是评审入口的编译损失——这使「有些多报不是被评审对象的错」从一句 threats
  变成一个可扣除的量。

## 11. 要小心的话

- 「覆盖率」必须带 $\le$，且必须与算力代价一起给。
- 「必要性」只到这个强度：可执行语义必要；**有界模型检查的必要性本实验无法判定**——
  不是被证伪，而是这批语料没有提供足够深度的案例。
- 「回归防护」目前是方法性质，不是实测结论。
- 「表示债务占 46.5%」不宜外推——一条链、一个语料、一个检测器。
  论文里主张的应当是**审查动作**（评审入口若是中间表示，就必须做这项扣除），不是这个数字。

## 12. 不能说的话

| 禁止 | 为什么 |
| :-- | :-- |
| 本文做模型修复 / 修复效果如何 | 修复是后续论文；导师明确 discover 单独成篇 |
| 贡献是 feedback loop + verification feedback | 已被 2026-08-07 / 08-08 定调取代 |
| 贡献是 `fcstm` / `pyfcstm` / 某种建模语言 | 中间表示是介质 |
| 贡献是 ledger / audit / 证据簿记 | 属评价与可复现纪律 |
| 贡献是「发现了 N 个新缺陷」 | 相对台账的净增量只有 2 条，且都不稳定；当前价值在覆盖已知缺陷 |
| `hit@1 = 60.4%`（不带 $\le$） | 已知扣除项只给上界方向 |
| 多报侧的「误报率」 | 分母不同质，且最大一块不是误判 |
| 某个执行模型更适合这项任务 | 两模型差 4.4pp，小于可解读量级，且能力边界高度重合 |
| 谓词选型建议 | 谓词与缺陷类型共线，须先做词表消融 |
| 这些模型没有并发 / 时间问题 | 我们排除的是无法判断的部分 |
| 台账即缺陷全集 | 台账有已知缺口，24 个 case 有外部记录的语义问题而台账无对应条目 |

## 13. 审稿人风险与应对

| 风险 | 为什么要紧 | 应对 |
| :-- | :-- | :-- |
| 「这不就是让 LLM 报缺陷吗」 | 会把贡献读成 prompt 工程 | 强调闭合词表是一次领域建模、每条发现可机械求值、以及裸给工具的反面证据 |
| 「60.4% 是相对什么」 | 无外部对照 | 如实说明无对照，并把朴素基线列为第一项待补；同时给算力代价 |
| 「你们的分母是自己标的」 | 台账既是分母又是自家产物 | 交代标注过程（谁标、何时标、是否在看过方法产出之后标、与判定是否同一人），并给外部对照缺口分析 |
| 「多报这么多，precision 呢」 | 朴素读法会得出反向结论 | 五类裁定 + 两套分母 + 逐簇判据；说明最大一块是编译损失 |
| 「为什么要中间表示，直接在 PlantUML 上查不行吗」 | 这是方法必要性的要害 | PlantUML 无执行语义；行为证据承载的覆盖份额；同时如实给出编译损耗 |
| 「fork/join 那份需求呢」 | 可能被读成剔样本 | 在问题定义处一句话说清建模对象边界，语料自然落在界外；**不展开辩护** |
| 「谁判的命中」 | 判定层可信度 | 如实写单一判定者、无一致性系数、20 位无判据文字（15 位在命中侧），并列为待补 |
