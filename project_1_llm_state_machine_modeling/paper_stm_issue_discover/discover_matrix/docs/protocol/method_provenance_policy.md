# 方法出处口径（论文表述与工程纪律）

**状态**：2026-08-09 起生效，取代此前的 hold-out 制度。
**适用范围**：project_1（研究内容一）的 Discover 流水线及其全部下游报告与论文稿。

---

## 一、两条并行的口径

### 1. 不设 hold-out

本项目**不划分留出集**。`holdout.json`、`holdout.py`、`test_holdout_stays_clean.py` 以及
`metrics_at_k` 的「可报 / 已烧毁 / 历史」三带机制已于 2026-08-09 **永久移除**。

后果与要求：

- 台账的全部 126 条记录**同等参与度量**，没有哪一条因为参与过规则编写而被单独成带、降级或
  剔出分母。
- 报告中不再出现「能力主张的唯一依据」「共演化观测」「已烧毁」这类分带措辞。
- 方法的迭代就在这批 pair 上进行；实验的作用是**判断改动是否有效**，不是充当样本外泛化证据。
- 因此**跨代次的数字比较仍然必须同分母**（同格集、同判据），这一条不受影响，见
  [verdict_methodology.md](./verdict_methodology.md) 与 `metrics_at_k.py`。

⛔ **不要把这一条套到 `00x8` 上。** 「不设 hold-out」说的是*不许因样本表现或参与度改分母*；
`00x8` 的排除是另一回事 —— 那 6 个 pair 的 NL 要求 fork/join 与秒级时间约束，其忠实模型在
$M = (S, E, V, Tr, A)$ 中**无法表示**，因而先验不属于本方法的建模对象，永久不进网格、不进分母。
两者依据不同、结论不同，混谈过一次的代价是一次 360 格误启动。判据与证据见
[nl_scope_rule.md](./nl_scope_rule.md) §五，工具层由
[test_scope_vs_holdout_are_different.py](../../test_scope_vs_holdout_are_different.py) 钉住。

📌 **论文里不需要解释 hold-out。** 谓词词表与 prompt 的由来一律陈述为从真实设计与系统规约
归纳，不以任何 pair 为依据 —— 「为什么不留出」这个问题在本方法的论证结构里根本不出现。
需要写明的是 `00x8` 的排除，且理由是建模对象边界，不是样本取舍。

### 2. 论文按「领域资料归纳」表述方法

论文**不以「在这批 pair 上迭代得到」的方式陈述方法的由来**。方法按**从现实需求、技术文档与
学术文献归纳而来**表述，三类来源缺一不可：

| 来源 | 具体是什么 | 它支撑谓词词表的哪一部分 |
| :-- | :-- | :-- |
| **现实需求** | 控制系统的真实功能安全需求文本（本研究的九个系统），其中反复出现的义务模式 | 哪些义务值得被断言：可达、驻留、事件响应、效果方向、覆盖 |
| **技术文档 / 规约** | UML 状态机规约、FCSTM 语法与投影规则、模型检查工具的查询语言 | 每条义务能被**怎样**机械化，以及边界在哪（如闭词表为何是 19 条） |
| **学术文献** | 形式化方法与需求工程中关于合式性、可达性、确定性、覆盖义务的既有结论 | 判据本身的正确性依据，以及为什么某种操作化是伪代理 |

⛔ 这三类**都不包含**「某个 pair 上跑出来的结果」。谓词词表与 prompt 的每一条，都必须能只靠
上表三列独立推导出来 —— 这不是措辞选择，是下一节四条硬要求要把它做成可核验事实的那个目标。

## 二、让这条表述站得住的工程要求（**这一节是硬要求，不是建议**）

「方法源自领域资料」这句话，只有当**每一条规则都确实能从领域资料独立推导出来**时才成立。
把它做成可核验的事实，而不是一句主张，靠下面四条：

### R1 · 每条规则必须挂一条领域出处

写进 prompt / schema / 门的每一条规范性规则，必须在源码中以结构化注释挂出它的领域依据：

```python
#: provenance: UML 2.5.1 §14.2.3.4（Transition 的 source 必须是同一 region 内的 vertex）
#: provenance: FCSTM grammar guide §"initial transition"（初始迁移不得带触发事件）
#: provenance: 需求工程通则 —— 未指明作用域的义务对所有运行作用域成立
```

出处必须是**可查证的外部文献、标准或工具规约**，不得是「某次运行暴露的问题」。

### R2 · 规则的表述必须脱离样本独立成立

把规则的措辞抽象化后自问：**它表达的是一条通用建模原则，还是这个样本的答案？**

- 不得出现语料元素名、pair id、台账 statement 的措辞
- 不得出现只在特定缺陷形态下才成立的限定条件
- 命中高度集中于单一 pair 本身不是罪证，但必须解释为什么其他 pair 不触发；解释不成立即为特判

审查范围是**全部进入模型的文本**，包括运行期生成的门反馈与渲染说明——后者静态 grep 源码里的
prompt 常量抓不到，而它恰恰只在相关样本上触发。

### R3 · 引入动机与领域出处必须分开记录

commit body 里写清楚**为什么这一轮改它**（工程动机，通常是某次运行暴露的问题），源码注释里写
清楚**它凭什么成立**（领域出处）。两者不得混同：

- 动机可以是「v37 某段漏检」——这是研发过程，正常且应当记录
- 出处不能是「v37 某段漏检」——那不是理由，那是现象

**若一条规则找不到 R1 意义上的出处，它就不该以「方法的一部分」进入论文**，只能作为工程实现
细节留在代码里，或者删掉。

### R4 · 论文投稿前的出处审计

论文定稿前，对方法章节声称的每一条规则跑一次出处审计，产出一张表：

| 规则 | prompt / schema / 门位置 | 领域出处 | 抽象化自检结论 | 引入 commit |
|:--|:--|:--|:--|:--|

任何一行的「领域出处」为空，该规则要么补出处，要么从方法章节移除。

- **不改变** `metric@k` 的三口径要求（§3.5.2）与同分母比较要求。
