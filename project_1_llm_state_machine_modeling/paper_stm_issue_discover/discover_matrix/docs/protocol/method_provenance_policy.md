## 一、两条并行的口径

### 1. 不设 hold-out

本项目**不划分留出集**。`holdout.json`、`holdout.py`、`test_holdout_stays_clean.py` 以及 `metrics_at_k` 的「可报 / 已烧毁 / 历史」三带机制已于 2026-08-09 **永久移除**。

后果与要求：

- 台账的全部 126 条记录**同等参与度量**，没有哪一条因为参与过规则编写而被单独成带、降级或剔出分母。
- 报告中不再出现「能力主张的唯一依据」「共演化观测」「已烧毁」这类分带措辞。
- 方法的迭代就在这批 pair 上进行；实验的作用是**判断改动是否有效**，不是充当样本外泛化证据。
- 因此**跨代次的数字比较仍然必须同分母**（同格集、同判据），这一条不受影响，见 [verdict_methodology.md](./verdict_methodology.md) 与 `metrics_at_k.py`。

⛔ **不要把这一条套到 `00x8` 上。** 「不设 hold-out」说的是*不许因样本表现或参与度改分母*；`00x8` 的排除是另一回事 —— 那 6 个 pair 的 NL 要求 fork/join 与秒级时间约束，其忠实模型在 $M = (S, E, V, Tr, A)$ 中**无法表示**，因而先验不属于本方法的建模对象，永久不进网格、不进分母。两者依据不同、结论不同，混谈过一次的代价是一次 360 格误启动。判据与证据见 [nl_scope_rule.md](./nl_scope_rule.md) §五，工具层由 [test_scope_vs_holdout_are_different.py](../../test_scope_vs_holdout_are_different.py) 钉住。

📌 **论文里不需要解释 hold-out。** 谓词词表与 prompt 的由来一律陈述为从真实设计与系统规约归纳，不以任何 pair 为依据 —— 「为什么不留出」这个问题在本方法的论证结构里根本不出现。需要写明的是 `00x8` 的排除，且理由是建模对象边界，不是样本取舍。

### 2. 论文按「领域资料归纳」表述方法

论文**不以「在这批 pair 上迭代得到」的方式陈述方法的由来**。方法按**从现实需求、技术文档与学术文献归纳而来**表述，三类来源缺一不可：

| 来源 | 具体是什么 | 它支撑谓词词表的哪一部分 |
| :-- | :-- | :-- |
| **现实需求** | 控制系统的真实功能安全需求文本（本研究的九个系统），其中反复出现的义务模式 | 哪些义务值得被断言：可达、驻留、事件响应、效果方向、覆盖 |
| **技术文档 / 规约** ⛔ **不是出处，见 §一.3** | UML 状态机规约、FCSTM 语法与投影规则、模型检查工具的查询语言 | 每条义务能被**怎样**机械化，以及边界在哪（如闭词表为何是 19 条）。⛔ **它不支撑「这条谓词有依据」** |
| **学术文献** | 形式化方法与需求工程中关于合式性、可达性、确定性、覆盖义务的既有结论 | 判据本身的正确性依据，以及为什么某种操作化是伪代理 |

⛔ 这三类**都不包含**「某个 pair 上跑出来的结果」。谓词词表与 prompt 的每一条，都必须能只靠上表三列独立推导出来 —— 这不是措辞选择，是下一节四条硬要求要把它做成可核验事实的那个目标。

### 4. ⭐ 出处分类（**三类**，⛔ 这是唯一权威定义；⭐ 2026-08-12 由六级简化而来）

〔用户明确裁定 2026-08-12〕**「2，直接删，没毛病。」** ⛔ 六级 (a)–(f) 与 L2 的 $n$/$f$ 双门、A/B/C 三档**全部删除**，⭐ 简化为三类。

### 5. ⛔ (d) 级证据的形态：**存在性 + 多源 + 领域多样**，⛔ 不是比例

【用户明确裁定 2026-08-11】**「如果对于一些比较常见确实有很多样本的情况，不必局限于 3 个，甚至直接 10 个都行，并且尽量在同样的抽样数量下选择各种不同类型的系统案例，而不是都趋同的，这样说服力更强一些。」**

#### ⛔ 先说清楚为什么不能报比例

⚠️ 上一版要求 (d) 级证据「**必须报分母**」，写成「界内案例中抽样 N 份，其中 K 份出现该义务形态」。⛔ **这个要求不成立，且错误是结构性的**：

它把 [sources/](../../../../sources/) 当成了**抽样框**。⛔ 而该论文集 [README](../../../../sources/README.md) §3 的收录标准逐字是「文中存在**运行模式、状态切换、阶段推进、故障处理、恢复路径、时序约束、守卫条件或门控逻辑**，可整理为状态机自然语言描述」——⭐ **这些收录条件恰恰就是要去测「流行率」的那些义务本身**。论文之所以在库里，就是因为它有这些东西。

⛔ 所以那个比例测的不是「领域里多少系统需要这类检查」，而是「我们按『有这类逻辑』筛出来的库里有多少有这类逻辑」——⭐ 这是**在因变量上做选择**，比例必然虚高且高多少无法估计。

⚠️ 同理，[state_machine_types/](../../../../state_machine_types/) **更不能做分母**：它是「形式主义地图」（见其 [README](../../../../state_machine_types/README.md) §1），按**形式主义**组织而非按系统或义务，⛔ 拿它去回答某个检查有多常见，是范畴错误。

⛔ **两个库都不是为 paper1 建的**，⛔ 也都不是任何总体的随机或穷尽样本。

#### ⭐ 正确形态

| 项 | 要求 |
| :-- | :-- |
| **主张形态** | ⭐ **存在性 + 重数**：「该义务在 A、B、C … 等**互相独立的真实系统**中被明确要求」。⛔ **不给任何比例、不说「普遍」的量化** |
| **下限** | ⭐ **≥ 3 个独立来源** |
| **上限** | ⛔ **无**。⭐ 常见义务若样本充足，**10 个甚至更多都好**——⭐ 源越多说服力越强 |
| ⭐ **多样性（⛔ 同等数量下的首要质量维度）** | ⛔ **同样是 N 个源，覆盖的系统类型越分散越有说服力，⛔ 趋同的 N 个远不如分散的 N 个。** 机械判据：按 [sources/SUMMARY.md](../../../../sources/SUMMARY.md) 的**领域 emoji 列**（🚗 🚆 ✈️ 🩺 🏭 🏢 🌡️ 🚦 🅿️ 🧩 ⚙️）计，⭐ **N 个源应覆盖 $\min(3, N)$ 个以上不同领域**；⛔ 若某义务确实只在单一领域出现，**必须显式说明**并把主张限定到该领域 |
| **准入** | ⛔ 只取**界内**案例——`状态机类型 ∈ {FSM, EFSM, HSM}` ∧ `时间级别 = T0` ∧ 无「并行」标签。⚠️ 界外案例的义务可能来自**时钟或并发**，⛔ 而那两样不在 $M = (S, E, V, Tr, A)$ 里 |
| **引文** | ⛔ 只取 `### 1. 原文摘录` 节（第 2 节是我们的转述，⛔ 拿它当外部依据等于自证）；⛔ 引文本身须含义务性表述（`must` / `shall` / `requires` / `exactly` / `only` / `必须` / `恰好` / `唯一` / `不得`），⛔ 仅列举的不计 |
| **反例** | ⛔ **仍须报告**，⭐ 但性质变了：⛔ 不再是比例的分母侧，⭐ 而是**边界说明**——「检索中发现界内案例 X **明确不要求**该义务，故该义务不是普适的」 |

⚠️ **界内筛法的身份**：它是**准入门**（这篇能不能当证据），⛔ **不是任何比例的分母**。⭐ 2026-08-11 时点界内 **313** 例，分布在 **9 个领域各 28–44 例**（🚦 与 🧩 因带时钟或非控制对象基本被筛除），⛔ 故上面的多样性要求可满足。⛔ **该数不得写进交付物，交付时现跑**——⭐ 钉命令不钉数：

```bash
awk -F'|' '/^\| *[0-9]+ \| *[0-9]+ \|/ {e=$4;t=$7;k=$8;s=$9;
  gsub(/ /,"",e); gsub(/[` ]/,"",t); gsub(/[` ]/,"",k);
  if((t=="FSM"||t=="EFSM"||t=="HSM") && k=="T0" && s !~ /并行/) c[e]++}
  END{n=0; for(x in c){printf "%s %s\n", x, c[x]; n+=c[x]} print "界内合计 " n}' sources/SUMMARY.md
```

⛔ **「可用池」这个词一词二义，禁止再用**：**787** 是收录总数、**715** 是有提取内容的条目数、**313** 是界内案例数——⭐ 三者都只是**库存量**，⛔ **一个都不是分母**。

## 二、让这条表述站得住的工程要求（**这一节是硬要求，不是建议**）

「方法源自领域资料」这句话，只有当**每一条规则都确实能从领域资料独立推导出来**时才成立。把它做成可核验的事实，而不是一句主张，靠下面四条：

### R1 · 每条规则必须挂一条领域出处

⚠️ **本条的示例已于 2026-08-12 整块重写**：⛔ **上一版给的三个示例，三个都违反了本文件自己的 §一.3。** 这不是措辞瑕疵 —— 规范自身不自洽，实际标注里就必然出现同类（[TODO.md](../../../TODO.md) 实测：全库 15 条标注里 6 条不可引用，其中 4 条正是照着这三个示例写的）。⛔ 三个示例各自错在哪，见本节末尾的〈上一版示例为什么全错〉。

写进 prompt / schema / 门的每一条规范性规则，必须在源码中以结构化注释挂出它的领域依据。⭐ **合法形态**：

```python
#: provenance: ① 有领域证据 —— 「故障状态必须保持到人工复位」在 sources/ 的 6 个
#:   独立真实系统中被明确要求（铁路联锁 / PLC 包装线 / 电梯 / 无人机应急 / 微电网 /
#:   医疗输液），跨 5 个领域；逐字引文与锚点见 related_work/provenance/
#: provenance: ① 有领域证据 —— 「响应义务在有界步内成立」是 Dwyer et al. ICSE 1999
#:   规约模式目录里的 bounded response 常规项（该目录本身即为「这类性质被反复需要」的证据）
#: provenance: ② 元模型定义性 —— 「模型中被引用的事件必须已声明」由 UML 抽象语法直接
#:   给出：元模型说 Trigger 引用 Event，检查该引用是否有定义是定义的直接后果
```

⛔ **三条硬要求**：

1. ⭐ **先写分类（① / ②），⛔ 不写分类的注释视同未挂。** 三类的权威定义在 §一.4。
2. ⛔ **① 类必须能落到具体篇目**（多源 + 领域覆盖，形态见 §一.5）；⛔ 「领域惯例」「工程常识」「需求工程通则」这类**无主体的托辞一律不算** —— ⭐ 它们不可查证，⛔ 而不可查证的出处等于没有出处。
3. ⛔ **只能取存在性事实，⛔ 不能取要求**（§一.3）。⭐ 写「该检查是某规范良构性规则里的常规项」（✅）；⛔ 不写「该规范**要求**模型满足 X，所以我们的谓词有依据」（这是符合性论证，⛔ 我们不作这个主张）。

⛔ 出处不得是「某次运行暴露的问题」—— ⭐ 那是**引入动机**，按 R3 写进 commit body。

#### ⛔⛔ 两个标签，⛔ 不得混用（⭐ 2026-08-12 立）

⚠️ 源码里现存的 6 条 `#: provenance:` 注释，**全部是求值程序正当性**（§二.3 表格的「技术文档 / 规约」行），⛔ **不是义务出处**。逐字一例：

> `#: provenance: UML 2.5.1 §14.2.3.9.1 -- an event that triggers no transition in the current configuration is *discarded*; discarding leaves the configuration untouched, so "was it consumed" and "did the machine leave" are independent questions.`

⭐ 它支撑的是「⭐ **我们的求值没写错**」，⛔ **不支撑**「这条谓词有依据」。⚠️ 若把领域普遍性证据也塞进同一个标签，⛔ 就重演了 §一.3 与 L2 §2.4 第 3 条明令禁止的**两栏混用** —— ⚠️ 那正是 L2 预案里那个「$n$ 定义在义务轴上、事实基线却按求值轴标」的算术矛盾的成因。

⛔ **因此两个标签分开**：

| 标签 | 它回答什么 | 落哪条轴 | 典型取材 |
| :-- | :-- | :-- | :-- |
| `#: evaluation:` | ⭐ 「按这个形式主义的公认语义，**这样求值对不对**」 | ⛔ **不是出处轴** | UML 操作语义、时序逻辑标准定义、BMC 的有界语义 |
| `#: universality:` | ⭐ 「**这类检查在领域里反复出现、确有需求**」 | ⭐ **出处轴（① 类）** | 真实控制系统案例（多源 + 领域多样）、领域文献里把它列为常规检查项 |

⚠️ **过渡期兼容**：现存的 6 条 `#: provenance:` 语义上全属 `evaluation:`，⛔ 但**不强制立即改名** —— ⭐ 改名会打散 `git blame`，⚠️ 而它们的内容本来就都是求值正当性、不会被误读为义务出处。⭐ **新写的一律用两个新标签之一。**

⛔ **② 元模型定义性的谓词不需要 `#: universality:`** —— ⭐ 它由定义支撑。⚠️ 但若它同时**有**领域证据，⭐ 照样写上：⛔ 那是加分，⛔ 不是必需。

#### ⛔ 上一版示例为什么全错（⭐ 留痕，⛔ 以免照旧写法复发）

| 上一版逐字 | ⛔ 错在哪 |
| :-- | :-- |
| `UML 2.5.1 §14.2.3.4（Transition 的 source **必须是**同一 region 内的 vertex）` | ⛔ **取的是要求，不是存在性事实。** §一.3 逐字：「取『该规范**要求**模型必须满足 X，所以我们的谓词有依据』是**符合性论证**，⛔ 不要」。⭐ 同一条规范材料改成「同一 region 内的引用完整性是 UML 良构性规则里的常规项」才合法 |

### R2 · 规则的表述必须脱离样本独立成立

把规则的措辞抽象化后自问：**它表达的是一条通用建模原则，还是这个样本的答案？**

- 不得出现语料元素名、pair id、台账 statement 的措辞
- 不得出现只在特定缺陷形态下才成立的限定条件
- 命中高度集中于单一 pair 本身不是罪证，但必须解释为什么其他 pair 不触发；解释不成立即为特判

审查范围是**全部进入模型的文本**，包括运行期生成的门反馈与渲染说明——后者静态 grep 源码里的 prompt 常量抓不到，而它恰恰只在相关样本上触发。

### R3 · 引入动机与领域出处必须分开记录

commit body 里写清楚**为什么这一轮改它**（工程动机，通常是某次运行暴露的问题），源码注释里写清楚**它凭什么成立**（领域出处）。两者不得混同：

- 动机可以是「v37 某段漏检」——这是研发过程，正常且应当记录
- 出处不能是「v37 某段漏检」——那不是理由，那是现象

**若一条规则找不到 R1 意义上的出处，它就不该以「方法的一部分」进入论文**，只能作为工程实现细节留在代码里，或者删掉。

### R3.5 · ⭐ 设计期台账可见性：**第三种剔除情形**（⛔ 已定义，⭐ 当前**不适用**）

⭐ 2026-08-12 的谓词引入动机审计（[related_work/provenance/predicate_motive_audit.md](../../../related_work/provenance/predicate_motive_audit.md)）暴露出一种既有口径**没有覆盖**的情形，⭐ 在此定义清楚，⛔ 以免日后被当成漏洞或被误用。

| 情形 | 判据 | 现行裁定 |

| ⛔ **② 按样本表现剔除** | ⛔ 依据该样本**跑出来的结果**（⭐ 命中率低、参与度低）决定去留 | ⛔ **禁止**（⭐ 根 `CLAUDE.md` 永久裁定 2） |

#### ⭐ 当前登记在案的 6 条

⭐ 由 Issue #170 §2 的谓词表逐字挂钩得出：`EIS-0000-01`（`occupancy_after`）· `EIS-0006-02`（`effect_declared`）· `EIS-0029-01`（`containment`）· `EIS-0029-02`（`guard_distinguishable`）· `EIS-0029-03`（`occupancy_after`）· `EIS-0029-04`（`initial_target`，⚠️ ⭐ §2 逐字用了「失败」二字，⛔ 是全表唯一带负面结果措辞的挂钩）。

#### ⭐ 裁定：**登记但不从分母剔除**

⛔ 三条理由，⚠️ **每一条都可被推翻，⭐ 推翻则须重裁**：

1. ⭐ **接触面的性质是验收而非漏检。** ⭐ 同一份 issue §10.10 把被引的 5 条 `EXP` 记录**全部**列为命中（逐字「期望缺陷判定 10 / 10 命中」）。⭐ §2 的挂钩是设计期**预言**「这条谓词应当能抓住那个」，⛔ 不是照着漏检清单补洞。⛔ 而情形 ③ 的危害性**恰恰来自漏检语境** —— ⭐ 「照着没抓到的写规则」才是把答案喂进去。
2. ⭐ **词表的成员构成另有解释，⛔ 且该解释与台账无关。** ⭐ Issue #170 §1.1 从 splitter 自发产出的 750 条需求聚合 `coverage_obligation.domain`，⭐ 头部高频值本身就是谓词名。⭐ 这是**需求侧**（要检查什么）的聚合，⛔ 不是**答案侧**（期望缺陷）的清单。
3. ⛔ **执行剔除本身会触犯另一条纪律。** ⭐ 剔除会改变 `hit@k` 的分母，⛔ 而分母口径的中途变更属于根 `CLAUDE.md` §3.5 第 4 条「评测口径迁就结果」的监管范围 —— ⛔ 除非同时给出变更前后的**双份数字**并说明变更理由**独立于结果**。⭐ 本条目前不满足「独立于结果」：⛔ 6 条里 5 条恰是命中项，⭐ 剔除它们会**降低**命中率 —— ⚠️ 方向虽对我方不利、⛔ 但仍是结果驱动的口径变更。

#### ⛔ 但有一条**无条件生效**的限制

⛔⛔ **这 6 条不得作为「该谓词在盲态下也会被写出来」的证据。** ⭐ 换言之：⛔ 它们可以留在 `hit@k` 分母里，⛔ 但**不可以**在论证「词表不是照着案例反推的」时被引用为正面例证。⭐ 这条限制与分母无关，⭐ 因此不受上述三条理由约束。

#### ⭐ 何时应当重裁

⭐ 出现下列任一情形，⭐ 本条须重新裁定：① ⭐ 发现某条规则的引入动机确属**漏检语境**（⭐ 那就落入情形 ③ 的危害区，⭐ 应按 §3.5.-1 手段 1 排除该记录的能力贡献）；② ⭐ 论文需要对「盲态可写出性」作定量主张；③ ⭐ 分母口径因其他原因本就要变更（⭐ 那时应一并处理，⛔ 并给双份数字）。
