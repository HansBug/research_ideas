## 一、两条并行的口径

### 1. 不设 hold-out

本项目**不划分留出集**。`holdout.json`、`holdout.py`、`test_holdout_stays_clean.py` 以及 `metrics_at_k` 的「可报 / 已烧毁 / 历史」三带机制已于 2026-08-09 **永久移除**。

后果与要求：

- 台账的全部 126 条记录**同等参与度量**，没有哪一条因为参与过规则编写而被单独成带、降级或剔出分母。
- 报告中不再出现「能力主张的唯一依据」「共演化观测」「已烧毁」这类分带措辞。
- 方法的迭代就在这批 pair 上进行；实验的作用是**判断改动是否有效**，不是充当样本外泛化证据。
- 因此**跨代次的数字比较仍然必须同分母**（同格集、同判据），这一条不受影响，见 [verdict_methodology.md](./verdict_methodology.md) 与 `metrics_at_k.py`。

⛔ **不要把这一条套到 `00x8` 上。** 「不设 hold-out」说的是*不许因样本表现或参与度改分母*；`00x8` 的排除是另一回事 —— 那 6 个 pair 的 NL 要求 fork/join 与秒级时间约束，其忠实模型在 $M = (S, E, V, Tr, A)$ 中**无法表示**，因而先验不属于本方法的建模对象，永久不进网格、不进分母。两者依据不同、结论不同，混谈过一次的代价是一次 360 格误启动。判据与证据见 [nl_scope_rule.md](./nl_scope_rule.md) §五，工具层由 [test_scope_vs_holdout_are_different.py](../../test_scope_vs_holdout_are_different.py) 钉住。

📌 **论文里不需要解释 hold-out。** 谓词词表与 prompt 的由来一律陈述为从真实设计与系统规约归纳，不以任何 pair 为依据 —— 「为什么不留出」这个问题在本方法的论证结构里根本不出现。需要写明的是 `00x8` 的排除，且理由是建模对象边界，不是样本取舍。

### 2. 论文按「领域资料归纳」表述方法

论文**不以「在这批 pair 上迭代得到」的方式陈述方法的由来**。方法按**从现实需求、技术文档与学术文献归纳而来**表述，三类来源缺一不可：

| 来源 | 具体是什么 | 它支撑谓词词表的哪一部分 |
| :-- | :-- | :-- |
| **现实需求** | 控制系统的真实功能安全需求文本（本研究的九个系统），其中反复出现的义务模式 | 哪些义务值得被断言：可达、驻留、事件响应、效果方向、覆盖 |
| **技术文档 / 规约** ⛔ **不是出处，见 §一.3** | UML 状态机规约、FCSTM 语法与投影规则、模型检查工具的查询语言 | 每条义务能被**怎样**机械化，以及边界在哪（如闭词表为何是 19 条）。⛔ **它不支撑「这条谓词有依据」** |
| **学术文献** | 形式化方法与需求工程中关于合式性、可达性、确定性、覆盖义务的既有结论 | 判据本身的正确性依据，以及为什么某种操作化是伪代理 |

⛔ 这三类**都不包含**「某个 pair 上跑出来的结果」。谓词词表与 prompt 的每一条，都必须能只靠上表三列独立推导出来 —— 这不是措辞选择，是下一节四条硬要求要把它做成可核验事实的那个目标。

### 3. ⭐ 证据轴的澄清（2026-08-11 追加）：三类来源里，**只有第一类是出处**

【用户明确裁定 2026-08-11】**「L2 那边调研的时候就只需要那些文献能证明这些所有的谓词逻辑都是常见的、有需求的，因此我们归纳了主流的这些、定义了这套东西……我们没必要非得说我们依从了谁，更不要因此引出 pyfcstm。」**

⚠️ 上表三行**各自的职责本来就写清了**，但实践中被误读过一次（L2 预案把第二行当成了出处阶梯的顶层），故在此写死：

| 上表的行 | 它是不是「谓词的出处」 | 它实际回答什么 |
| :-- | :-- | :-- |
| **现实需求**（反复出现的义务模式） | ⭐ **是，且是唯一的出处轴** | 哪些义务值得被断言——即**这类检查常见且有需求** |
| **技术文档 / 规约** | ⛔ **不是出处** | 每条义务能被**怎样**机械化，边界在哪。⛔ 它支撑「我们的求值没写错」，⛔ 不支撑「这条谓词有依据」 |
| **学术文献** | ⭐ **是**（与第一行同轴） | 该检查在学术工作里同样反复出现；以及为什么某种操作化是伪代理 |

⛔ **因此本项目不作任何符合性主张**：不声明依从 UML / PSSM / SCXML 任何一家，⛔ 也不得引 pyfcstm 或任何工具实现充当语义权威——引它等于把「与它一致」变成一个本不必承担的义务。

⚠️ **规范材料仍然可引，但取什么决定它落在哪条轴上**：取「这类检查是该规范良构性规则里的常规项」是**普遍性证据**（合法）；取「该规范要求模型必须满足 X，所以我们的谓词有依据」是**符合性论证**（⛔ 不要）。⭐ 判据是把句子写出来看它承诺了什么——承诺「我们与谁一致」的一律不要。

⚠️ **对 R1 的连带影响**：R1 示例里的 `#: provenance: FCSTM grammar guide §"initial transition"` 这类写法，⛔ 不得用于**谓词的义务出处**；它只能作为实现约束留在代码里。R1 要求的「可查证的外部文献、标准或工具规约」，在**谓词出处**这一用途上收窄为**可查证的外部文献与领域材料**。

### 4. ⭐ 出处分级表（**六级**，⛔ 这是唯一权威定义，2026-08-11 按普遍性轴重写）

**被分级的对象**：19 条谓词，**每条一个等级**。⭐ 分级要回答的问题是——**「这类检查在领域里有多明显地反复出现」**，⛔ **不是**「哪份标准要求模型满足它」（§一.3 的证据轴裁定）。

| 级 | ⭐ 它证明的事（普遍性口径） | 典型取材 | ⛔ 不得据此说 |
| :-- | :-- | :-- | :-- |
| **(a)** | 该检查被写进了某规范的**硬性约束**（如 OCL）——⭐ 说明它常见到需要被机械强制 | UML 2.5.1 Clause 14 的 OCL | ⛔ 「我们依从该 OCL」 |
| **(b)** | 该检查在**规范正文里被明确提出**——⭐ 说明规范作者认为它值得写下来 | UML / PSSM / SCXML / IEC 正文 | ⛔ 「该规范要求模型满足它」 |
| **(c)** | 该检查是**操作语义的组成部分**（run-to-completion、事件消费等）——⭐ 说明它是执行模型的常规关注点 | PSSM、工具语义文档 | ⛔ 「我们的求值与该语义一致」 |
| ⭐ **(d)** | ⭐ **领域实践频次**——真实控制系统的建模文献与工程材料里**反复把它当作一条义务**，或该类缺陷**被真实记录过**。⭐ **这是本口径下的首选证据轴** | `sources/` 的界内案例（按 §边界筛法过滤）+ 软工侧 STM 文献 | ⛔ 只说「大家都这么做」而不报**分母**与**反证** |
| **(e)** | **元模型定义性**——元模型说这种元素存在，⛔ 但没说「模型必须声明它」 | UML 抽象语法 | ⛔ 把它当成出处 |
| **(f)** | **无外部依据** | —— | ⛔ 隐瞒；⛔ 也不删谓词（588 冻结） |

⛔ **三条硬约束**：

1. ⭐ **(a)(b)(c) 不高于 (d)。** ⚠️ 这张表的字母序**不是强度序**——在普遍性轴上，一份「界内 40 例中 23 例要求该义务」的调研**强于**「UML 某条提到过它」。⛔ 旧口径把 (a) 当顶层是符合性思维的残留。
2. ⭐ **从 (a)(b)(c) 只能取存在性事实**（「该检查是规范的常规项」），⛔ 不能取要求（「规范要求模型满足 X」）。⛔ 判据：把句子写出来看它承诺了什么——承诺「我们与谁一致」的一律不要。
3. ⛔ **(d) 必须给具体篇目 + 逐字片段 + 抽样分母 + 反证计数**，⛔ 只给命中数一律作废。

## 二、让这条表述站得住的工程要求（**这一节是硬要求，不是建议**）

「方法源自领域资料」这句话，只有当**每一条规则都确实能从领域资料独立推导出来**时才成立。把它做成可核验的事实，而不是一句主张，靠下面四条：

### R1 · 每条规则必须挂一条领域出处

写进 prompt / schema / 门的每一条规范性规则，必须在源码中以结构化注释挂出它的领域依据：

```python
#: provenance: UML 2.5.1 §14.2.3.4（Transition 的 source 必须是同一 region 内的 vertex）
#: provenance: FCSTM grammar guide §"initial transition"（初始迁移不得带触发事件）
#: provenance: 需求工程通则 —— 未指明作用域的义务对所有运行作用域成立
```

出处必须是**可查证的外部文献、标准或工具规约**，不得是「某次运行暴露的问题」。

### R2 · 规则的表述必须脱离样本独立成立

把规则的措辞抽象化后自问：**它表达的是一条通用建模原则，还是这个样本的答案？**

- 不得出现语料元素名、pair id、台账 statement 的措辞
- 不得出现只在特定缺陷形态下才成立的限定条件
- 命中高度集中于单一 pair 本身不是罪证，但必须解释为什么其他 pair 不触发；解释不成立即为特判

审查范围是**全部进入模型的文本**，包括运行期生成的门反馈与渲染说明——后者静态 grep 源码里的 prompt 常量抓不到，而它恰恰只在相关样本上触发。

### R3 · 引入动机与领域出处必须分开记录

commit body 里写清楚**为什么这一轮改它**（工程动机，通常是某次运行暴露的问题），源码注释里写清楚**它凭什么成立**（领域出处）。两者不得混同：

- 动机可以是「v37 某段漏检」——这是研发过程，正常且应当记录
- 出处不能是「v37 某段漏检」——那不是理由，那是现象

**若一条规则找不到 R1 意义上的出处，它就不该以「方法的一部分」进入论文**，只能作为工程实现细节留在代码里，或者删掉。

### R4 · 论文投稿前的出处审计

论文定稿前，对方法章节声称的每一条规则跑一次出处审计，产出一张表：

| 规则 | prompt / schema / 门位置 | 领域出处 | 抽象化自检结论 | 引入 commit |
|:--|:--|:--|:--|:--|

任何一行的「领域出处」为空，该规则要么补出处，要么从方法章节移除。
