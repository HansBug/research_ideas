# 那 7 条 `wellformedness` 漏检：**按构造不可发现，因为参考侧不在输入里**

## 三条独立事实合起来的结论

### 1. ⛔ 「字段自相矛盾」这条已被我自己的后续实测**削弱**

> **原论证**：7 条的 `layer_basis` 都写「不需要参考模型」，而**每条都填了 `reference_side`** ——
> 字段与字段自相矛盾，所以真实依据是「参考侧有而生成侧无」。
>
> **它隐含一个我没验证的前提**：`reference_side` 只在判定需要它时才填。
>
> **实测（11 个 grid pair 全部 37 条）**：
>
>     layer_basis 取值分布
>       20  NL 点名了那个缺失或错位的元素
>       12  模型自身即可判定，不需要 NL 也不需要参考模型
>        3  与 NL 的显式义务矛盾
>        2  生成方凭空多出，且造成可断言的负面后果
>
>     37 条里 **37 条都填了 `reference_side`**
>
> **所以它是无条件填写的标准字段，不管 `layer_basis` 说什么。** 它的存在**不构成**「判定依赖参考侧」
> 的证据 —— 更可能只是记录「参考模型在这一点上长什么样」作为背景。
>
> 📌 **我把一个格式化字段读成了依据声明。** 而这个矛盾恰好覆盖 `wellformedness` 全部 12 条、且只覆盖
> 这一层 —— 那个"只覆盖一层"的整齐分布让我更相信它是真矛盾，实际它只反映**这一层的 `layer_basis` 取值
> 恰好都是那一个**。
>
> 以下原文保留以便追溯：

7 条**每一条**都写着「模型自身即可判定，**不需要 NL 也不需要参考模型**」，而**每一条都填了
`reference_side`**，且那个字段正是判定所依据的对照：

| 记录 | `layer_basis` 声称 | 实际 `reference_side` |
| :-- | :-- | :-- |
| `EIS-0032-01` | 不需要参考 | 「参考：`state Operate { [*] --> Idle }`（一层子态，**有默认子态**）」 |
| `EIS-0047-02` | 不需要参考 | 「参考的每个区**都有自己的** `[*] --> X_inactive`」 |
| `EIS-0048-03` | 不需要参考 | 「参考：`state Fork2 <>;` Fork2 与目标是**兄弟**」 |
| `EIS-0048-01` | 不需要参考 | 「参考：`state fork1 <>;` fork 与两个目标是**兄弟**」 |
| `EIS-0047-01` | 不需要参考 | 「参考的三个区各有**独立命名**的状态」 |

**所以真实依据是「参考侧有而生成侧无」，不是「模型自身可判定」。**

### 2. UML 核对已证明「模型自身可判定」是假的

独立核对者取 OMG 官方 PDF 逐字核对：**UML 显式允许复合态没有默认入口**（§14.2.3.2 与 §14.2.3.4.5 列出
两种都合法的解读，其一是「该 Region 保持 inactive、复合态按简单叶态处理」）。

所以 `layer_basis` 的「模型自身即可判定」在规范层面**不成立** —— 判定它必须有一个外部对照。

### 3. ⛔ 而参考模型**不在仓库任何位置**

全仓搜索 `0048` 的 puml：只有两个文件，且**逐字节相同**（`sha256` 一致），都是**生成侧**（含
`state fork1 <<fork>> { ... }`，即台账记录的缺陷形态本身）：

    selected_seed_examples/llms_emp_feedback_final_0048/stm0.puml
    pipeline/representation/reports/llms_emp_r45_java_60/pairs/0048/plantuml.puml

台账的 `reference_side` 字段是**台账编写者从别处抄来的** —— 编写者有参考模型，**pipeline 没有**。

## 结论：不是能力问题，是输入缺失

那 7 条在当前实验设置下**按构造不可发现**：

    依据不是 UML                    （UML 核对已证）
    依据是「参考侧有而生成侧无」      （台账自己的字段表明）
    参考侧不在 pipeline 的输入里      （全仓搜索确认）

~~三条合起来 ⇒ 无论 prompt、谓词、公理怎么改，方法都不可能发现它们。~~

⚠️ **该结论现在只剩两条支撑**（事实 1 已削弱），因此**可能过强**：

- 仍成立：UML 不支持「模型自身可判定」（官方 PDF 核对）
- 仍成立：参考模型不在仓库（`sha256` 逐字节相同）
- **已削弱**：「真实依据是对照式」—— 依据可能是别的东西，而我还不知道是什么

**核心张力仍在**：`layer_basis` 声称「模型自身即可判定」，而 UML 说不能判定。**但这个张力现在指向一个
更难的问题** —— 若依据既不是 UML 也不（必然）是参考侧，那「可判定」的根据究竟是什么？

已把这条更正发给裁定者，并明确要求它不因我主动更正而放松审查 —— **相反，这说明我前一轮推理不可靠，
它应当对我给的其余转述持同样怀疑。**

## 这对分母的含义

7 条 × 2 臂 × 3 轮 = **42 个判定位**，占全分母 204 位的 **20.6%**。它们在 v24 上贡献 2 个命中位
（`0032-01` 1、`0048-01` 1，均为偶然）。

| 口径 | 判定位 | 命中 | `hit@1` |
| :-- | --: | --: | --: |
| 当前全分母 | 204 | 108 | **52.9%** |
| 剔除这 7 条后 | **162** | **106** | **65.4%** |

⚠️ **这个 +12.5pp 我不主张。** 理由与「移出 `wellformedness` 层」被否决时相同 —— 那次的否决理由是
「事实前提为假（上游已检出）」，而这次的前提是**真的**（参考侧确实不在输入里）。

**但前提为真不等于该剔除。** 剔除需要回答两个问题，而它们都不在我的裁量范围内：

1. **台账为什么写「不需要参考模型」？** 若那是编写者的判断失误，应改台账；若那是某种我不理解的口径，
   应先弄清。**在弄清之前剔除，是用我的解读覆盖台账。**
2. **参考侧不在输入里，是设计选择还是遗漏？** 若是设计选择（方法**应当**只从 NL + 生成模型工作），
   那这 7 条本就不该进分母；若是遗漏（参考侧本该给），那该补输入而非改分母。

📌 **这两个问题都该由外部裁定，不该由我在报告里单方面决定。** 已交裁定。
