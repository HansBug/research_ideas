# v25 三条通路的可行性核查：**三条全部不能按裁定原样实施**

裁定给 v25 定了三条独立通路。**逐条做可行性核查后，三条都被推翻，而理由各不相同。**

这不是裁定错了 —— 裁定基于当时可得信息是合理的。是**执行时的核查推翻了它的前提**，而三次核查各只花了
几次查询。

## 通路 1：公理源缺失（预期覆盖 6 条）→ **收益降到 0**

盲态推导交付 4 条公理。随后 **UML 原文逐字核对**（OMG 官方 PDF，796 页）：

| 公理 | 结论 |
| :-- | :-- |
| A2 | **零规范依据** —— §14.2.3.9 标题都是错的，穷举 5 处 ill-formed 语句 + 5 组 OCL 集零支撑 |
| A3 | "ill formed" **借错地方**；UML 恰用**与 A3 一字不差的例子**说明「如何处理」而非「判为非法」 |
| A1 | 「唯一」的**存在性**那半是规范**显式拒绝表态**处（列了两种都合法的解读，其一允许无默认入口） |
| A4 | **类别错位** —— 操作语义推论，非合式性约束 |

**关键后果**：A1 降级后只剩「入口若存在则至多一个且无条件」，**抓不到「入口不存在」** —— 而那正是那
6 条漏检的形态。

📌 那 6 条之所以是缺陷，**依据不是 UML**（UML 显式允许复合态没有默认入口），而是**参考模型有而生成模型
没有**、或 **NL 隐含了进入后应到哪**。那是另一类义务源，需重新设计。

## 通路 2：融合事件禁令（预期覆盖 1 条）→ **无谓词承载**

| 检查 | 结果 |
| :-- | :-- |
| `cardinality` 能否数事件 | **不能**（docstring 逐字「non-pseudo **direct substates**」） |
| `event_declared` 能否数 | **不能**（存在性谓词） |
| 数据层面可数吗 | **可以** —— 但 `structure.events()` 是 **facade 不是谓词** |

让断言脚本直接调 facade 会绕过 `_note` 记账、`_require_well_formed_names`、attribution 引用记录 ——
**而那些正是让发现可归因的机制**。

📌 **按裁定建议执行会更糟**：模型被允许报告融合是缺陷，但没有谓词能承载该断言 —— 要么臆造谓词调用
（幻觉），要么落成 `unsupported`。**现状至少产出一个诚实的 True。**

**顺带查出一个独立缺陷**：融合事件禁令写在 **5 处**，强度不一致且跨阶段矛盾 ——
`REQUIREMENT_REVIEWER`(L379) 允许要求拆开，`ASSERTION_CONVERTER`(L77/L146) 禁止。这条该修，且**不需要
新谓词**。

## 通路 3：锚点投降（预期覆盖 ≥2 条）→ **前提不成立，锚点一致性 96.8%**

裁定的证据是 `containment(parent="...0048.fork1", child="...0048.fork1.AutoFocus") is True`，读作「父作用域
从模型读了出来」。

**实测 v24 全 66 格**（按 `source_context.nl_parent` 逐条核对）：

    containment 断言        125
    ✅ 绑定的 parent = nl_parent   121（96.8%）
    ❌ 不一致                        2
    需求侧无 nl_parent               2

那 2 处不一致是**名字大小写 / 后缀差异**，不是从模型读父作用域：

    0032-gpt  REQ-011   NL=Operate   绑=OperateState
    0018-gpt  REQ-024   NL=Join2     绑=join2

📌 **所以那类断言为 True 不是锚点投降，是正确行为** —— `containment(Join2, Fork2)` 在 `0048` 上为 True
因为模型**确实**把 Fork2 放在 Join2 里，而 **NL 也要求如此**（原文逐字
`"In the Fork2 state, which is part of the Join2 substate"`）。

**而那 2 处真不一致恰好是「名字匹配不对称」的又一实例**（`Operate` vs `OperateState`）—— 与多报侧最大
一类**同一根因**。

## ⚠️ 我在这三次核查中的四次机械代理失灵

| 代理 | 给出的假象 | 真相 | 失效原因 |
| :-- | :-- | :-- | :-- |
| 格级共现 | 13 条里 11 条被门吃掉 | 逐条匹配后 0 条 | 格级 ≠ 逐记录 |
| 元素级重叠 | 语义最清楚的那条只得 1 分 | —— | **我把唯一鉴别 token 当噪声滤掉了** |
| `sed` 读函数 | 函数里没有 `raise` | 有两处 | **嵌套 `def` 处提前终止** |
| 邻近正则数 `nl_parent` | 填充率 **47.2%** | **100%** | 字段顺序/嵌套不满足邻近假设 |

**四次都不报错，都给出一个看起来合理的数。** 最后一次尤其危险：若不核对，我会带着「填充率只有 47%」
这个假前提去设计门 —— 而真相是 100%，且真正的问题根本不在填充率。

## v25 的实际可做项（三条通路之外）

1. **名字匹配不对称**（产出方按字面判缺失、判定方按归一化判）—— 多报侧最大一类，且通路 3 的 2 处真
   不一致也是它。**修它不需要新谓词，也不需要 UML 背书。**
2. **融合事件禁令的跨阶段矛盾**（5 处强度不一致）—— 不需要新谓词。
3. **重新设计义务源类型** —— 那 6 条 `wellformedness` 漏检的依据是「参考侧有而生成侧无」或「NL 隐含」，
   不是 UML 合式性。这是一次设计工作，不是加条目。

📌 **1 与 2 是本轮唯一两件"已核查可行且不需扩张"的事。**
