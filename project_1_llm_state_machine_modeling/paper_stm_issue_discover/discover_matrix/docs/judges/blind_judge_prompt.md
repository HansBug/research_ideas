# 盲判者指令（固定文本，跨判定者与跨代次一律使用本文件）

## 为什么这份指令必须落成文件

上一代次我做了两次盲判，**给的指令不同**：第一次我在 prompt 里自写了一套更严的口径且没让判定者读
`docs/protocol/hit_criterion.md`；第二次让读了，并讲解了第 ④ 种形态。

结果两次测出的偏倚方向不同（带相关 → 单向），而**那个差异不能归因于覆盖率提高** —— 它可能完全是我
改指令造成的。这是一个我自己引入的混杂，只能在报告里披露，无法事后消除。

所以：**指令固定在本文件，逐字使用，不再由我临场撰写。** 若需要修改口径，改本文件并记录改动，使
「哪一代次用的哪一版指令」可追溯。

## ⚠️ 改版即产生披露义务 —— 这条由两份运行前 review 独立指出

固定文件**不消除**混杂，只让它可追溯。**任何版本变更都使跨代次的盲判数不可直接比较**，因为判定装置
变了。

所以每次改版必须在报告里显式声明：本代次用的是哪一版、上一代次用的是哪一版、两者产出的数字**不做
直接对比**（或者，若一定要对比，先用新版重判旧样本）。

v1 → v2 就是一个实例：v2 是**看到上一代次结果之后**写的（改动日志自陈），所以 v2 产出的数字与 v1
产出的数字之间的任何差异，都无法归因于实验变化。**这条义务写在这里，而不是等发布核验来指出。**

## 指令正文（以下内容逐字交给判定者，仅替换 `{{SAMPLE_PATH}}`）

你是一个**独立的盲判者**。对样本中的每个判定单元逐一判断，输出结构化结果。

### 输入

只读 `{{SAMPLE_PATH}}`

**不要读**同目录下的 `key.json`、其它 `sample*.json`、`verdicts/`、`holdout.json`，
**整个 `docs/generations/` 目录**（历代报告、事前登记、往轮裁定全在里面，含
`docs/generations/v22/blind_readjudication.md`、`docs/generations/v23/overreport_adjudication.md`），
以及 `manual_review/`、`onepass_sample/`，也不要翻 `runs/`。
这些都会泄漏你被盲掉的信息。若不小心读了任何一个，在最终输出里如实说明。

## ⛔ 也不要读**本文件的「改动日志」一节**

本文件你必须读（它是你的指令），但**只读到指令正文结束为止**。「改动日志」是维护记录、**不属于指令**。

📌 这条与 `docs/generations/v25/retired_onepass_prompt.md` 同批加入，起因是 v24 发布核验在那份文件里查出一次**答案形状泄漏**：
其改动日志逐字写着某个具体命题「应判 `grounded-extra`（某位标注者的判定正确）」，而**禁读清单列了十来个
文件，独独漏了指令文件自身**。

本文件当前的改动日志**不含**具体判定（已核查），但结构缺陷相同 —— **在它被写进去之前先堵住。**

**可以读，且应当读**：`docs/protocol/hit_criterion.md` —— 它是本仓库预注册的命中判据，是你的判定标准来源。
它不含任何分组信息。

### 每个单元要做什么

每个 item 有 `expected_defect`（一条期望被发现的缺陷）与 `pipeline_output_per_round`（某条管线各轮
**已发布**的发现列表）。判断：**每一轮的已发布发现里，有没有一条与 `expected_defect` 语义同一？**

### 判定口径：严格按 `docs/protocol/hit_criterion.md`

该文件 §3 列出语义同一性成立的**四种**形态，四种都算命中：

1. **直接对应** —— 两个命题说同一件事，只是谓词不同
2. **合取项之一** —— 台账命题是 all(...)，产出证明其中一个合取项为假
3. **负向命题的正向对偶** —— 台账说「不应存在错的边」，产出说「应存在对的边」
4. **蕴含更根本的原因** —— 产出命题为假蕴含台账命题为假，且定位到更上游
   （该文件自带的先例：台账「攻击完成边应有变量下降」vs 产出「模型根本没声明那个变量」——
   无变量则不可能有下降）

§4 列出**不**成立的形态：不同缺陷共用状态名；更弱的命题（台账要求「边的目标是 X」，产出只证明
「这个状态存在」）；反向蕴含。

**两条告诫，请同等对待：**

- **第 ④ 种形态容易被误判为未命中** —— 产出定位到更上游的缺失元素时，它仍然蕴含台账命题。
- **① ～ ④ 四种形态同样容易被过度援引** —— 尤其 ③（负向对偶）与 ④（蕴含更上游）。**说不清「产出为
  假如何蕴含台账为假」这条逻辑链，就判未命中。** 元素重叠、区域相同、都提到同一个状态名，**都不是**
  蕴含关系。

两条并列不是修辞：只给前一条会把判定推向多算命中。

### 输出格式

```
unit_id | r1 | r2 | r3 | 形态 | 依据（≤45 字）
U001    | 1  | 0  | 1  | ④   | r1/r3 第2条：无该状态则台账义务不可能成立；r2 只提元素
```

**每个单元都要有一行**，`形态` 列填 ①②③④ 之一或 `—`（未命中）。不得省略、不得写「同上」。
若某单元的轮次数不是 3，按其实际轮次数出列。

最后给：

1. 判 1 的总数 / 总轮次位数
2. 你用第 ④ 种形态判 1 的单元清单，以及每个的蕴含链一句话
3. 最不确定的 5 个单元及原因
4. 若某条 `expected_defect` 在当前判据下**按构造不可判定**（例如它自己声明该缺陷无法用现有谓词
   表达），单独列出 —— 这类应计为不可判定而非未命中

### 注意

- 你的判定会与另一位独立判定者算一致性，**按自己的理解判，不要猜别人怎么判**。
- 单元之间独立判，不要因为「前面几个都是 1」而调整后面。
- 样本里没有任何分组标签，也不需要你猜 —— 猜它会破坏这次复核的全部意义。
