### EIS-0047-01 ✅

**问题类型**：`element`（单元素） · `state`（状态） · `other`（其他） · `language`（语言规则）
- `other` 说明：涉及多个：三套避撞控制因重名塌缩成一套，修复要重命名 / 补齐 6 个状态声明并重连初始边。
- 归类依据（原文逐字）：Idle / Braking / Clamping 在 Frontend 里首次声明后，RearEnd 与 Pedestrian 中的同名引用指向的是 Frontend 内的同一批状态

**问题描述**：PlantUML 状态名是全局标识：Idle / Braking / Clamping 在 Frontend 里首次声明后，RearEnd 与 Pedestrian 中的同名引用指向的是 Frontend 内的同一批状态，于是后两个复合状态实际为空、其初始迁移越界指向 Frontend.Idle（pyfcstm 明确报 "PlantUML initial target outside child scope: CollisionAvoidanceSystem.Frontend.Idle"，并生成 InvalidInitialtr_0005 / InvalidInitialtr_0009）。三个避撞控制塌缩为一个，直接违反 NL 第1、3句要求的三路控制，也是同一批迁移被重复声明三次的根因。

- **补充证据（与本条是同一个问题）**：作者把同一条三态回路原样复制进了三个兄弟复合态：L4-L7（Frontend）、L11-L14（RearEnd）、L18-L21（Pedestrian）三段除外层复合态名外**逐字相同**，状态名 `Idle` / `Braking` / `Clamping` 在三处复用。而 PlantUML 的状态名是全局的（官方 frontend 不保留 qualified name，不同 scope 的同名 state 会碰撞），故这三段解析成同一组状态之间的三份同构迁移：`Idle → Braking`、`Braking → Clamping`、`Clamping → Idle` 各被声明三次。⭐ 更准的落点措辞是「跨兄弟复合态复用同名状态」，三条重复边只是它的后果 —— 顺带的后果还有：这三个区并不是真正独立的三条回路，三处 `[*] --> Idle` 也都落到同一个 `Frontend.Idle` 上，与 NL 第 1、3 条要求的「三个正交区各自并发」并不相符。
