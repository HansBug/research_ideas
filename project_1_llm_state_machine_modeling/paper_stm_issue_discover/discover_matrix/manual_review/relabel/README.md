# 人工全量重标工作区

54 份逐 pair 的工作单 + 生成 / 回收 / 校验工具。目标是让作者**逐 pair 人工裁决**三件事：现有 expected issue 是否成立、是否偏浅、以及台账遗漏了什么。

⛔ **本目录不修改台账。** [expected_issue_set.json](../expected_issue_set.json) 保持冻结 —— 它是 v46 与 X1 两轮判定所依据的 ground truth，事后改它比改结果更严重。重标产物只落在本目录内；合并回台账是另一件事，需要单独的裁定与 PR。

## 一、为什么要重标

现有台账 98 条 `REPORTABLE`（原 126 条，扣 `00x8` 越界 27 条与 `EIS-0043-02` 的逐条边界裁定）的来路是这样的：

| 项 | 现状 |
| :-- | :-- |
| 生成者 | ⛔ **5 个 LLM agent**（`<pair>-review.json` → `final_stratification.json` → `expected_issue_set.json`） |
| 人类校验 | ⛔ **0 条** |
| 双盲复审 | ⛔ 仅 12/60 = 20%，$\kappa = 0.750$，且是**二元 case 级** |
| 只过正则从未二读 | ⛔ **23 / 98**（`decided_by = lexical`；全 126 条口径下是 32 条） |
| 证据读了 fcstm 投影 | ⛔ **51 / 98** |
| 时序 | ⛔ 台账 07-31，**晚于**方法产出 07-27 |
| 谓词覆盖 | ⛔ 只用到 15/19；`variable_declared` / `variable_delta_after` / `response_within` / `invariant` **从未作为 primary**；**11 条无 primary 谓词** |

⭐ **核心怀疑：现有 expected issue 可能偏浅。** 文献也指出自动生成的断言容易偏浅。⭐ 若能挖出更深的问题，那**不一定是坏事** —— 它可能成为方法的新增长点。

支持这个怀疑的两组既有数字：X1 朴素基线有 **13 条真漏记**（台账没记但确实成立），主臂只有 2 条；主臂**完全漏掉**而 X1 命中的台账条目有 **22 条**，反向只有 3 条。

## 二、⛔ 三条硬边界（动手前先读）

### 1. 建模对象是 $M = (S, E, V, Tr, A)$

⛔ **无时钟变量 $C$、无不变式 $Inv$、无正交区并发。** 这是 [CLAUDE.md](../../../../../CLAUDE.md) 定死的 project_1 边界，不是本次可以放宽的口径。

具体到重标：

- ⛔ **不许记**：fork / join 伪状态、「两个区域是否同时活跃」、秒级 / 毫秒时间约束、计时器、不变式。
- ⭐ **仍要记**：NL 说「持续到 X 才离开」「先 A 后 B」这类**次序与保持**义务在模型上有没有**结构性**承载（缺边、守卫、层次）。那不需要时钟。
- ⚠️ 元素**名字**恰好叫 `fork` / `Timer` 的，仍在范围内 —— 判的是主张需不需要并发 / 时钟语义，不是名字。

[validate.py](./validate.py) 会对疑似越界的新增条目报 `W`，⚠️ 判据是词法关键词，**会误伤**，所以只提醒不删。

### 2. `00x8` 六个 pair 永久排除

`0008` `0018` `0028` `0038` `0048` `0058` 的 NL 要求 fork/join 与秒级时间约束，忠实模型在 $M$ 中无法表示。⛔ 它们**不生成工作单、不进网格、不进分母**，见 [nl_scope_rule.md](../../docs/protocol/nl_scope_rule.md)。

⛔ 这与「不设 hold-out」是**两件事**，不得混谈：前者说的是有些**规约**本就不是本方法要建模的对象，后者说的是**不许因样本表现改分母**。把后者套到前者上，会得出「排除 `00x8` = 剔除不利样本」这个错误结论 —— 事实相反，被排除集里 `0018` 的 `hit@1` 高于全量均值。

### 3. 判断锚在**作者源**，不锚在投影

工作单 §1.3 给的 PlantUML 是被测的作者源。⛔ `plantuml_source_lowering.py` 的投影会合成 `UnspecifiedInitial` / `InvalidInitial*` / `FinalWait*` / `R45RouteToken` —— **作者从没写过这些**。

⭐ 这不等于「读了投影的条目就无效」：缺陷在转换阶段暴露、中间表示如实反映、断言据此报出，**是方法按设计工作**，主张没有越界。⛔ 但重标时必须能回答一句：**「这条主张在作者源上怎么表述？」** 答不上来的，就是被投影带偏了。

⚠️ 附带一个已登记的事实缺口：台账多条 statement 把某些诊断归给了 pyfcstm，实际那是本仓库自己的表示层做的（见 [ground_truth_limitations.md](../../docs/protocol/ground_truth_limitations.md) §5）。看到「pyfcstm 报了 X」的措辞，⛔ 不要照抄。

## 三、怎么用

### 3.1 一份工作单长什么样

打开 `<pair>.md`（如 [0000.md](./0000.md)）即可开工，⛔ 不需要再翻别的文件。结构：

| 节 | 内容 | 要不要填 |
| :-- | :-- | :-- |
| §0 | 本 pair 结论 | ⭐ 做完再填 |
| §1 | 原料：结构摘要 / NL 全文（分段 + 行号）/ 作者源 PlantUML（行号）/ 参考模型 PlantUML | 只读 |
| §2 | 现有 expected issue 逐条 + ⛔ 自动风险标记 | ⭐ 逐条裁决 |
| §3 | 候选新增 issue（五个来源，见下） | ⭐ 逐条裁决 |
| §4 | ⭐ 深度检查清单（逐 pair 点名真实元素） | ⭐ 逐条勾选 + 写发现 |
| §5 | 新增 issue 登记 | ⭐ 按需填 |
| §9 | 孤儿填写区（材料变动时才出现） | 并回正文后删掉 |

**只有 `<!-- FILL:BEGIN -->` 与 `<!-- FILL:END -->` 之间的内容是给人填的。** 其余部分重跑生成器会被覆盖。填写用 `~~~` 围栏包着，⭐ 所以你可以在理由里自由粘贴 ``` 代码块。

### 3.2 §3 的五个候选来源

| 小节 | 来源 | 优先级 |
| :-- | :-- | :-- |
| §3.1 | 两臂多报侧判为 `VALID_UNRECORDED` 的「真漏记」 | ⭐ 最高 —— 已过一轮独立复核 |
| §3.2a | 审阅 agent 判为 `problem` / `extra` / `uncertain` 却没进台账的 diff | ⭐ 高 |
| §3.2b | 判为 `correct` / `similar` 的 diff | 备查，不设裁决区 |
| §3.3 | 两臂产出中机械未匹配任何台账条目的 issue | ⭐ 中 —— 量大，按出现格数排序 |
| §3.4 | 已被判为「非缺陷」的多报簇 | 备查 —— 避免与既有裁定撞车 |
| §3.5 | 与台账同根、但匹配器未归并的簇 | ⭐ **「台账偏浅」的直接证据** —— 对应条目适合走「修正」 |

⛔ **§3.2 的一个已知证据缺口**：当年**没有单独记录「为什么不收」**，只留下了该 diff 被判成什么。所以「排除理由」给的是它的 `verdict` 与判定者理由，不是一条真正的排除论证。

### 3.3 §4 清单怎么读

每条都是**待核问句**，不是结论；机械判据写在下一行。⭐ 判错了就在「发现:」里写「机械判错，理由 X」—— 那本身就是有用的记录。勾 `[x]` 表示**看过了**，「发现:」留空表示看过但无发现。

清单按八类组织，每类的标题下写着**台账在这一维有多空**，例如：`event` 方向全库只有 4 条、`variable_declared` 与 `variable_delta_after` 从未作为 primary、`response_within` / `invariant` 同样从未出现。⭐ 越空的维度越值得挖。

### 3.4 什么该记、什么不该记

⭐ **该记**：

1. 在 $M$ 内、在**作者源**上成立、且与 §2 已有条目不是同一缺陷的任何缺陷。
2. 现有条目**说浅了**的 —— 走「修正」并写出更强的 statement，⛔ 不要新开一条。
3. 现有条目**说错了**的 —— 走「删除」并写明理由。⛔ 台账错了就是错了，这正是重标的目的。
4. ⭐ 谓词写不出来的缺陷 —— `primary_predicate` 留空，在理由里写明词表缺口。**词表缺口本身是发现**。

⛔ **不该记**：

1. 越界的（§二.1）。
2. 只在投影上成立的（§二.3）。
3. 与 §2 已有条目同根的 —— 走「并入现有条目」。
4. 「模型没用 submachine 语法 / 没加方括号」这类**记法形态**主张 —— $M$ 里没有「子机引用」与「守卫槽位」的区分量。⚠️ 但若形态错误**导致**了语义后果（例如守卫写进 trigger 槽使该边永不触发），那记的是**后果**，在范围内。

### 3.5 深度三档

| 档 | 判据 | 例 |
| :-- | :-- | :-- |
| 表层 | 单点存在性 / 拼写 | 「`FinishState` 没有 `state` 声明」 |
| 中层 | 单点关系 | 「`InMotion` 有三个子态但没有区域初始边」 |
| 深层 | 跨状态推理 / 隐含冲突 / 运行时后果 | 「接管迁移只挂在一个子态上，自动模式的其余每一处都把接管信号静默丢弃」 |

⭐ **判据是「读懂它需要看几个地方」**：一处 = 表层，两处的关系 = 中层，需要沿执行路径推理或需要跨多个状态比对 = 深层。

## 四、命令

```bash
cd .../discover_matrix/manual_review/relabel

python3 generate.py                    # 生成 / 刷新全部 54 份（⭐ 幂等，保留已填内容）
python3 generate.py --pairs 0000 0044  # 只刷新指定 pair
python3 generate.py --check            # 只报告哪些会变，不写盘

python3 collect.py                     # 回收 → relabel_result.json
python3 collect.py --pairs 0000 --stdout

python3 validate.py                    # 校验完整性 / 边界 / 去重
python3 validate.py --write-progress   # 顺便刷新 PROGRESS.md
python3 validate.py --json             # 机器可读

python3 export_unmatched.py            # 重新导出 §3.3 的原始 issue 文本
```

**幂等保证**：`generate.py` 先把旧文件里所有 `key -> 填写内容` 抽出来，重新渲染骨架，再按 key 注回。若某个 key 在新材料里消失，旧内容会被搬到 §9「孤儿填写区」，⛔ 不会静默丢弃。

⚠️ `export_unmatched.py` 读 `runs/` 下的原始 run record，而 `runs/` 被 `.gitignore` 排除。X1 臂的记录在本 clone；⛔ **主臂 v46 的记录不在本 clone**，在姊妹目录 `research_ideas/runs/paper1/matrix-v46-full/`。已导出的结果落在 [unmatched_issues.json](./unmatched_issues.json)（**入库**），所以工作单本身是自包含的，⛔ 只有要重新导出时才需要那些原始记录。
