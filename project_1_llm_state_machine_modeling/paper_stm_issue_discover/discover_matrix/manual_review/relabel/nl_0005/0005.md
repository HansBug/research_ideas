### EIS-0005-02 🟡

**问题类型**：`element`（单元素） · `state`（状态） · `incorrect`（错值） · `requirement`（需求文本）
- 归类依据（原文逐字）：这三个 ID 首次出现在外层 state 块体内，PlantUML 前向引用规则把它们钉成子态

**问题描述**：这三个 ID 首次出现在外层 state 块体内，PlantUML 前向引用规则把它们钉成子态（R4.5 投影确认：DoorOpenWithItem { DoorShutWithItem {...} ReadytoCook { Cooking {...} WaitingToStart } DoorIdleWithItem }）。后果是 active(DoorShutWithItem) 蕴含 active(DoorOpenWithItem)——门开有物与门关有物同时成立，直接违反 NL 第 4/5/6/8 句把二者当互斥替代配置（由相反的开/关门事件到达）的处理；且 DoorOpen --Place Item--> DoorOpenWithItem 现在总落在自造的 DoorIdleWithItem 上。

- **补充证据（与本条是同一个问题）**：作者在 `state DoorOpenWithItem {` 块体内**前向引用**了尚未声明的 `DoorShutWithItem`（L14）与 `ReadytoCook`（L15）。PlantUML 的作用域规则据此把这两个态判为 `DoorOpenWithItem` 的**后代**而非兄弟；后面 L18 `state DoorShutWithItem {`、L25 `state ReadytoCook {` 只是给同一个已存在的状态补子态，并不把它提回顶层。`Cooking` 又经 L30 嵌进 `ReadytoCook`，于是也落在 `DoorOpenWithItem` 之下。后果：作者写成「回到兄弟态 DoorOpenWithItem」的三条边（L21 的 ItemInside、L29 的 WaitingToStart、L36 的 ActiveCooking）在层次语义下全部成为**后代 → 祖先**边——每次触发都退出并重新进入 `DoorOpenWithItem`，重跑它的默认入口 L11 `[*] --> DoorIdleWithItem`，把「门内已有物品」这个内部阶段清零。判读者要裁的是：这个包含关系是不是作者本意；若不是，这三条边的语义就与 NL 描述的「开门后回到有物品的开门态」不符。
