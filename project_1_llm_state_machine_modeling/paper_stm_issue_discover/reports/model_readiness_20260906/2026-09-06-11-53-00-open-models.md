## 推荐逻辑

- **优先讨论 Qwen3.8-27B，第二款在 Gemma4-31B-it 与 Muse-Glimmer-30B 之间权衡 [clm-open-selection]。** Gemma4 有独立模型族、256K 原生窗口和 32/16 并发证据，但真实 method 约 934s、contract-completion 预算耗尽后降级；Muse 的 method 在本格完成，窗口为 128K。两者的容量与工作流证据要一起看，不能根据本格发现问题数量选优。
- **替代候选：Qwen3.6-35B-A3B + Muse-Glimmer-30B。** Qwen3.6 的 active 参数很小，thinking 16 worker 通过；Muse 的 agentic benchmark 和长输入负载值得考虑，但 parser/服务配置更专用。
- **暂不进入主矩阵：Nemotron、GLM、gpt-oss、Llama。** 它们值得保留为候选，但本轮没有实际 H200 负载证据；在 E2 前若替换，必须先完成同一套部署、tunnel、context 和 16-worker 检查。

## 官方启动要点

Qwen3.8 官方卡同时给出 vLLM/SGLang 命令和 YaRN `rope_parameters`；Qwen3.6 官方卡给出 TP8 的 vLLM/SGLang 配方；Gemma4 官方卡给出 Transformers/vLLM 路径；Muse 官方卡要求其 parser/工具链；Nemotron 官方卡区分 H100 256K 与 B200 1M recipe；gpt-oss 官方 OpenAI Docs 提供 vLLM 服务器指南。E1 实测在 GPU 0-3 上为适应 H200 分配使用 TP2/TP4，记录为配置偏差，不能回写成官方默认命令。

## context 口径

本轮原生窗口已验证：Qwen3.8 262,144、Qwen3.6 262,144、Gemma4 256K、Muse 131,072 [clm-open-context]。每个边界请求达到声明值约 0.9 倍，并留出输出预算；Qwen3.8 的 1M YaRN 和 Qwen3.6 的 1.01M YaRN 已按官方 recipe 配置，分别用 900,036 和 909,035 输入 tokens 完成 2/2 边界请求。两款扩展配置还各通过 16K thinking 的 16-worker 32/32 测试。原生与扩展结果分开保留；长上下文容量通过不等于长距离语义能力已验证。

Muse 的窗口和并发结论以最终 `muse-high-tool-*` 为准；旧 response-format 记录只有 transport/schema 合格，内容含占位符，不能作为完整任务完成证据。详见[部署报告](./2026-09-06-11-53-00-serving-evidence.md)的协议差异和逐条检查。

## 发布时间与复现限制

日期优先采用官方明确的开放公告：[Qwen 官方仓库 News](https://github.com/QwenLM/Qwen3.8#news) 写 Qwen3.8-27B 为 2026-08-14、Qwen3.6-35B-A3B 为 2026-04-16、Qwen3.6-27B 为 2026-04-22；不能合并两个 3.6 型号的日期。Qwen 博客当前访问只返回 SPA 壳，不将页面更新时间当发布日。Gemma4 使用官方公告的 2026-04-02；Nemotron/Muse 使用卡片的 release 字段。HF `createdAt`/`lastModified` 不是统一发布日期。[clm-open-table]

开放模型吞吐来自固定合成输入，输出规模、reasoning 控制和 prefix caching 会影响结果。实验 16 workers 是 HTTP 并发承载证据，不是 16 个接近最大窗口请求同时驻留 GPU 的承诺。精确 checkpoint revision、服务参数与失败记录见 evidence bundle；未运行候选不因模型卡分数高而成为 ready。
