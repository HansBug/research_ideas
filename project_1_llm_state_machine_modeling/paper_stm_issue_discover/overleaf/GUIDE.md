# F1 Overleaf Engineering Guide

## Purpose and boundaries

This is a portable IEEE conference project for the SANER 2027 Research Track **double-anonymous submission manuscript**. `main.tex` is the only English submission entry and the authoritative language. `main-zh.tex` is an internal Chinese companion marked as not for submission. F1 contains only generic, visibly marked `PLACEHOLDER`/`TODO` text, layout fixtures, and placeholder bibliography records; it contains no Paper1 claim, definition, method, study design, result, contribution, research question, real citation, data assertion, or asset. The user-authorized fixture prose is ordinary paper-style text, with `(THIS IS PLACEHOLDER TEXT, PLZ FULFILL IT WHEN WRITING.)` at the start of each visible section/abstract; it is not scientific content and must be replaced or removed in a later, separately approved writing goal.

## Ownership and layout

`main.tex` and `main-zh.tex` are the two roots. `config/` contains shared packages, language switches, the future results interface, and manifest metadata. `sections/index.tex` is the sole chapter-order source; the two roots must never duplicate that order. Every abstract, section, appendix, placeholder figure, and placeholder table has a paired `.en.tex`/`.zh.tex` file with matching `SYNC-ID` comments; each visible fixture paragraph has its own paired block ID. Figures belong only in `figures/`; table sources belong only in `tables/`; `references.bib` is shared and currently contains only clearly marked placeholder records. No Paper1 content is placed in those directories during F1.

## Official template protection

The protected vendor tree is `template/official-original/`, extracted byte-for-byte from `template/source/IEEEtran-1.8b-ctan.zip`. The archive is the canonical IEEEtran distribution (version 1.8b, dated 2015-08-26) linked by the IEEE template page and distributed through CTAN. The provenance record documents the IEEE policy/template URLs, the Overleaf IEEE Official Template page, the CTAN download URL, retrieval date, archive SHA-256, license notices, and the WAF limitation encountered when retrieving the IEEE binary endpoint. `template/MANIFEST.sha256` inventories both the archive and every extracted file.

The vendor tree is read-only: do not delete, rename, reformat, patch, or add files. `IEEEtran.cls` and `IEEEtran.bst` at the project root are byte-identical work copies mapped to `official-original/IEEEtran/IEEEtran.cls` and `official-original/IEEEtran/bibtex/IEEEtran.bst`. `tools/validate-template-integrity` checks archive hash, extracted inventory, protected set, and both work-copy identities on every `make check`. To upgrade, add a new versioned archive/tree and provenance entry, review the diff, then switch the work-copy mapping; never overwrite historical vendor material. Our roots, sections, configs, scripts, and docs are separate self-owned files and never modify the official samples.

## Overleaf and local round trip

Upload this directory as one project without changing its paths. For the minimal upload archive, run `make zip` and upload `build/overleaf-upload.zip`; it contains only the two roots, byte-identical class/style work copies, CJK fallback, shared config/sections, and figure/table sources or assets. Documentation, validators, protected template archives, and generated files are excluded. In Overleaf set `main.tex` as the root for the submission PDF; select `main-zh.tex` only for the internal companion. Download the source zip, extract it into a new empty directory, and run `make clean && make all && make check` in the full repository project, or invoke `latexmk -pdf` explicitly in the minimal upload tree. Both roots use `\\documentclass[10pt,conference]{IEEEtran}` and standard Overleaf `pdfLaTeX`; no shell escape, system fonts, absolute paths, `../` imports, symlinks, external server, or repository-outside resource is permitted. Clean builds must not use pre-existing aux/bbl/toc caches. Cloud Overleaf execution is not a credential-free CI step; local clean source-zip validation is reported as `OVERLEAF_PORTABLE_LOCAL_VALIDATION` and must not be described as a cloud run.

## Bilingual synchronization

English controls later scientific content and page budget. Each semantic paragraph/claim block gets one stable `% SYNC-ID: id` in each language. The ID sets, order, labels, citation keys, equation identifiers, figure/table inputs, and numeric macro uses must match exactly. Chinese may use natural syntax but may not add or omit a claim, evidence item, number, citation, limitation, modality, or ordering. `config/results.tex` is the only future numeric interface; later macros require a canonical in-repository JSON/TSV path, field or JSON pointer, snapshot hash, and verification commit. Canonical facts outrank prose. `tools/validate-bilingual` is deterministic and provider-free; semantic equivalence and visual naturalness remain human review gates.

## Chinese terminology and language review

The Chinese companion is written primarily in Chinese. For a technical concept, introduce it as `中文（English）` at its first visible occurrence, then use the Chinese term thereafter. Keep English only where it is required for a proper name, venue name, author name, model or product name, LaTeX command, file path, citation key, label, equation identifier, or an established acronym that would be ambiguous in Chinese. When an acronym is needed, introduce `中文（English, ABC）` once and use the Chinese term afterwards. The fixed English placeholder marker at the start of each F1 unit is an explicit layout exception and must remain unchanged.

Every substantive bilingual PR must review this rule before editing and after rendering. Use `$shuorenhua:shuorenhua` (source: https://github.com/MrGeDiao/shuorenhua) to review Chinese clarity, naturalness, terminology stability, and unnecessary English; use `$academic-humanizer` (source: https://github.com/AIScientists-Dev/academic-humanizer) to review the English academic version. Read the complete relevant `SKILL.md` before each review, record the skill version/hash and input revision, and list accepted or rejected edits. Neither review may change facts, numbers, citations, claims, limitations, modality, causal strength, or responsibility. After both language reviews, rerun the per-`SYNC-ID` bilingual equivalence check and inspect the Chinese PDF for first-use terminology and residual unnecessary English. These local tools are review aids only and never Overleaf build dependencies. F1 contains layout placeholders, so the skills are not run to rewrite its scientific text.

## Writing-phase admission

After the user approves a section plan, freeze canonical fact/evidence sources before writing. Do not import talks, stories, issues, experiment archives, or old LaTeX drafts without explicit authorization and source verification. Every substantive block must record claim, evidence, number, citation, limitation, and epistemic strength against its `SYNC-ID`. Historical drafts remain references, never silent sources. F1 has no selected headline, title, abstract, contribution, or narrative.

## SANER/IEEE constraints (verified 2026-09-01)

The current SANER Research Track page requires original unpublished English PDF submissions, the IEEE Conference Proceedings format, a maximum of 10 pages with up to 2 additional pages for references only, electronic submission through EasyChair, and full double-anonymous review. The dates page lists abstract submission on Mon 21 Sep 2026 AoE and paper submission on Fri 25 Sep 2026 AoE. `Data Availability` is expected after Conclusions and before References. The section is counted in the 10-page body allowance; only references may use extra pages. Do not use `compsoc`/`compsocconf`, `geometry`, `titlesec`, `setspace`, margin/font/spacing overrides, compressed bibliography, negative spacing, or any other page-limit hack. Artifact sharing is encouraged but not mandatory and must be anonymous when used.

First-party sources: [SANER home](https://conf.researchr.org/home/saner-2027), [Research Track call](https://conf.researchr.org/track/saner-2027/saner-2027-papers), [dates](https://conf.researchr.org/dates/saner-2027), [SANER AI-generated text policy](https://conf.researchr.org/attending/saner-2027/Guidelines+for+Artificial+Intelligence+%28AI%29-Generated+Text), [IEEE templates](https://www.ieee.org/conferences/publishing/templates.html), [IEEE Author Center](https://conferences.ieeeauthorcenter.ieee.org/write-your-paper/authoring-tools-and-templates/), and [IEEE Overleaf template](https://www.overleaf.com/latex/templates/ieee-conference-template/grfzhhncsfqn). These pages were opened and recorded on 2026-09-01; the live call controls if requirements change.

## AI-use disclosure

The current SANER AI-generated text policy requires AI-generated paper content, including text, figures, images, and code, to be disclosed in `Acknowledgment`. The disclosure must identify the AI system, the affected paper sections, and the level of use. It says editing and grammar enhancement generally fall outside the policy's intent, so disclosure for that limited use is recommended rather than required. `sections/11-ai-use-disclosure.{en,zh}.tex` is the paired, disabled-by-default interface for this rule. F1 enables neither file and makes no claim about AI use. In a writing-phase PR, enable it only after the accurate disclosure has been agreed; do not invent a system, affected section, or use level, and rerun the bilingual, anonymity, and page-budget gates after doing so.

## Data Availability

`sections/10-data-availability.{en,zh}.tex` is a paired, normal section interface after Conclusions and before References. F1 contains only a deferred comment and no link, promise, or availability claim. In the writing phase, use the concise style common in recent SANER papers: one short paragraph named `Data Availability` (or a directly related replication-package sentence) that gives an anonymous repository and access instructions when materials can be shared; otherwise gives a concrete reason that sharing is not possible or suitable and, when applicable, states whether release is planned after acceptance. Do not add a long inventory, marketing language, unverifiable promise, or repository link before access and licensing are checked. Keep the English and Chinese paragraphs paired by `SYNC-ID`, and count this section, appendices, and all other body material within the 10-page limit.

This policy follows the practical pattern visible in SANER 2025/2026 papers: availability language is brief, operational, and placed near the end of the manuscript. It does not require an artifact, but it does require an honest status when the section is written. The exact status and wording remain a writing-phase decision based on the verified artifact record and the live SANER call.

For maintainers, the style check was grounded in public SANER examples including [Does the Tool Matter?](https://arxiv.org/abs/2501.15114), [Why Do Developers Engage with ChatGPT in Issue-Tracker?](https://arxiv.org/abs/2412.06757), [WakeMint](https://arxiv.org/abs/2502.19032), and [Coverage-Guided Road Selection](https://arxiv.org/abs/2601.08609). Their reusable pattern is a short operational sentence or paragraph pointing to a replication package and access instructions, with no lengthy catalog in the manuscript. These examples guide tone and placement only; they are not Paper1 sources and must not be copied into the paper.

## Review-stage minimal recomputation package

This is a policy for a possible later review-time artifact, not an artifact or release commitment. `tools/review-artifact-manifest.example.json` deliberately records `not_prepared`; F1 does not make an availability claim, select release contents, or redistribute anything.

SANER 2025, 2026, and the current 2027 call make artifacts encouraged rather than mandatory. A later `Data Availability` section may give an anonymous link and access instructions, or truthfully explain why sharing is not possible or suitable. The 2027 call permits small additional material through EasyChair, permits a tested anonymous link where needed, permits deferral to camera-ready when anonymization is infeasible, and asks PC members not to require full artifact availability at submission. Recheck the live call before submission.

If a package is ever legally and anonymously ready, it is a **minimal, frozen, review-time recomputation package**. Its only claim is provider-free regeneration of every paper-facing statistic, denominator, percentage, and final table from frozen records. It is neither a repository dump nor an end-to-end experiment rerun.

The five required, allowlisted roles are: (1) the exact FCSTM runtime revision and license notice; (2) a byte-manifested Paper1 method release; (3) the provider-free statistics evaluator; (4) the minimum manifest-bound input closure needed for the claimed scope; and (5) the frozen final-output closure required for arithmetic recomputation. Every role needs an in-package path, SHA-256, byte count, source snapshot, inclusion reason, and license/provenance record. A complete-universe rerun claim must contain every input in that universe; a smaller sample may be a smoke/audit sample only and must not claim full-paper statistic regeneration.

There is **no distributable Paper1 Judge**. All validity, relation, D/A, K/N/I, and grouping decisions are human-completed research records; the human Judge process itself is never an external artifact and has no rerun interface. The package may contain only a sanitized final human-decision snapshot as static, non-executable output data when that exact input is necessary for the statistics evaluator. It must not contain a `judge/` directory, Judge or adjudicator code, Judge prompts, reviewer identities or assignments, unblinding mappings, raw deliberation, LLM records, credentials, provider streams, or any mechanism that reruns or purports to automate human adjudication. Its README must say that it recomputes arithmetic from frozen human decisions and does not reproduce adjudication.

The review-ready manifest is checked by `tools/validate-review-artifact-manifest`. For a future real package, it must be package-local and inventory every regular file except the self-describing manifest. The validator compares the supplied SHA-256 values and byte counts with the actual clean package, rejects symlinks, paths outside the package, Judge/adjudicator/reviewer paths and command tokens, inventory drift, weak gate records, and an evaluator command not bound to the declared provider-free evaluator entry point. It never executes the command, builds a package, calls a provider, or alters research data. Human review still decides legal authorization, semantic adequacy, anonymity, and whether a given component is really non-Judge code.

Before a package can be marked `review_ready`, a rights holder must grant an explicit redistribution license for the method source (`method/NOTICE.md` currently records that no such external redistribution license exists); the selected frozen archive must pass its provider-free integrity validation; every included asset must have an approved license; clean extraction must pass; and the actual Data Availability wording must be true. The current path is therefore no review package plus an honest later writing-phase explanation, unless all gates pass. No F1 document or PR may claim a public artifact, a promised future release, or an automated/reproducible Judge.

## Anonymity and assets

Submission source and PDF must omit author names, affiliations, email, ORCID, ordinary identity-bearing acknowledgments, funding, identifying footnotes, personal/repository links, local paths, DOI/copyright/camera-ready blocks, and identifying PDF metadata. The requested camera-ready handoff values are kept only in the ignored `../author-info.private.md` file outside this project root and must never be copied into the double-anonymous source zip. Self-citations must remain third person or be anonymized when required by the live call. Do not claim that an artifact is public until redistribution licensing and an anonymous URL are verified. Figures should prefer language-neutral PDF/vector assets; raster assets use PNG; SVG shell conversion is not a dependency. Tables with text require language pairs, while purely numeric shared tables require the same frozen canonical values.

## Placeholder fixtures and enforcement

The F1 builds intentionally render roughly two to three pages of ordinary generic placeholder paragraphs plus paired single-column figure/table fixtures and two clearly marked `PLACEHOLDER` BibTeX records. These fixtures test layout, pairing, and bibliography plumbing only; their labels, rows, captions, prose, and records must be replaced before submission. `tools/validate-content-boundary` rejects non-placeholder citation keys, unmarked figure/table content, and cross-column placeholder floats; it permits an abstract only when the visible placeholder marker is present.

## Enforcement and review

Run `make clean && make check` before and after every change. The check invokes template-integrity, bilingual, anonymity, format-policy, portability, and clean English/Chinese builds, then verifies non-empty PDFs, extractable text, metadata, page count, and absence of unresolved references/citations. Validators never edit files, call a provider, or depend on private state. Generated PDFs and TeX auxiliaries belong only under ignored `build/` and must never be committed. Human gates remain: venue/source accuracy, bilingual semantic equivalence, Chinese first-use terminology and unnecessary-English review, anonymous-word false positives, natural layout, and future claim/evidence correctness. Substantive PRs must include the two language-skill review records described above.

Each F1 PR must report the branch/base, commit, source URLs and hashes, all gate commands/results, local source-zip boundary, and three independent reviews: template/venue, build/portability, and bilingual/scope. Reviewers inspect current files and command output rather than relying on summaries. Any P0/P1 is fixed and rechecked by the responsible reviewer. The PR remains unmerged. `NO_METHOD_RERUN`, `NO_JUDGE_RERUN`, and `NO_RESULT_MUTATION` are explicit F1 invariants.
