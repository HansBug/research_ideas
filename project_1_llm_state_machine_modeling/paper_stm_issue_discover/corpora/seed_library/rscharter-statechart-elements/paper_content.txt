Context: Theautomatedtranslationofdesignmodelsfromtherequirementswritteninnatural
language (NL) textual format is tedious. An NL is inherently ambiguous, whereas a formal
language is unambiguous.
Objective: In this paper, we propose a framework, Requirement Specification Charter
(RSCharter), for translating NL textual specifications into formal First-Order Predicate Logic
(FOPL) by identifying and representing them as state diagram elements.
Method: The framework used a classical NLP rule-based baseline model for identifying the
statechart diagram elements from the NL.
Results:We found that the proposed approach generates FOPL and develops a state diagram
with an average precision of 89% and a recall of 87%.
Conclusion: Our results depend on the complexity levels of the evaluation datasets, the
dependency parser accuracy, and the coverage of the FOPL conversion rules.
1. Background and Motivation
Manual derivation of behavioral modelsfrom natural language (NL) requirements is time-consuming, error-prone,
and typically performed by experienced analysts Arora et al. (2016), Bozyigit et al. (2024). Various methods have been
proposed for generating UML diagrams from NL specifications using rule-based NLP techniques, but these are manual
and rely on heuristic rules. Ahmed et al. Ahmed et al. (2022) reviewed systems for automatically transforming NL
intoUMLmodels,identifyinglimitationsduetoNLPcapabilitiesandheuristic-basedapproaches.Aroraetal.Arora
etal.(2016)notedthelaboriousnatureofmanualdomainmodelcreation,whileautomaticextractiontechniquesface
challenges in industrial settings. Bozyigit et al. Bozyigit et al. (2024) evaluated two text-to-model tools—ChatGPT and
txt2Model—both of which showed lower performance and high variance for relation types.
In this paper, we propose a framework called Requirement Specification Charter (RSCharter ) for automated
extractionofelementsofthestatechartdiagram(suchasconditions,events,actions,andstates)fromtheNLtextual
specifications. RSCharter converts an NL SRS document (RUPP or EARS compliant) into equivalent First Order
PredicateLogic(FOPL)expressionsbeforegeneratingthestatechartdiagramusinganyconventionalgenerator.The
motivation is to develop a framework for describing system behaviours and exhibit formalization with precisely defined
syntax and semantics by understanding the behavioural pattern through state variables and transitions.

2.1. Action & Trigger Extractor (ATE)
The ATE module uses a dependency parser-based algorithm for extracting conditional clauses (i.e., the antecedent )
andcorrespondingbodyclauses(i.e., consequent ).InthecontextofSRS,theconditionclauserepresentsthe trigger
clause, outlining preconditions for actions described in the body clause (i.e., action clause ). Dependency parsing
identifies the causal relationship between these clauses and clarifies inter-phrase associations, helping to identify
compound triggers/actions involving multiple sub-clauses (see Figure 1).
Trigger Clause: TherearetwotypesoftriggerclausesinaconditionalSRS:(i) existential ,whereatruthvalueis
assignedtotheexistenceofasystemstate,and(ii) comparative ,whereatruthvalueisassignedtoacomparisonbetween
states.In bothcases, ifthe conditionistrue, ittriggers systemactions. ATEextracts triggerclauses bytraversingleft
from the root token to find the start and right from the right token to find the end.
Action Clause: The action clause consists of what the system is supposed to perform, which amounts to the new state
in which the system should transition if the trigger occurs. The action clause is extracted by traversal to the right of the
token that denotes the termination of the trigger clause.
2.2. First-Order Predicate Logic Converter (FLC)
The FLC module converts the extracted action clause and associated trigger clauses (if any) into FOPL expressions.
Therearethreetypesof trigger rules-oneforcomparativetriggerclauseandtwofor existentialtriggerclause(one
for the case where the subject-object relation is " is-a" and the other for " non is-a" subject-object relation). We use
threereservedpredicates-(i) AGENT(∙)todenoteanysystemwhosenameidentityisunknown(orunresolved),(ii)
STATUS (∙) to denote a property that is a state-value of an agent (e.g.: " Database x is open" implies STATUS (open)),
and (iii)hasStatus( ∙,∙)to denote the relation between the agent and its state-value (see Table 1).
2.3. State Diagram Generator (SDG)
TheSDGmoduleprocessestheFOPLexpressionsoftheactionandtriggerclauses,convertingthemintoastatechart
diagram. States are represented as nodes, and actions (with their conditions) are represented as edges. Each action has
an initial state and a subsequent next state. If a trigger is present, the edge represents an implication (see Figure 2).

3.4. Preliminary Observations
We observe that RSCharter-R1 exhibits very high EP (best: 0.94; avg.: 0.89) and ER (best: 0.93; avg.: 0.87) on all
the SRS documents except esaand, to a certain extent, Home1.3. On further analysis, we find that the overall drop
inaccuracycanbeattributedtoalackofaccuracyindependencyparsingofmorecomplexstatementshavingmore
logical operands.
4. Discussions and Future Work
This paper presents RSCharter a framework for generating statechart diagrams from natural language require-
ment specifications by translating them into First-Order Predicate Logic (FOPL) expressions. The framework is
implementation-agnostic, with accuracy dependent on dataset complexity, parser accuracy, and FOPL conversion rules.
Futureworkaimstoimprove RSCharter withenhanceddatasets,advancedaugmentationtechniques,andabroader
metric suite for evaluating statechart diagram generators.
