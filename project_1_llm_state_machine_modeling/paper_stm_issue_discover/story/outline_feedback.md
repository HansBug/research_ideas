## 批注与正文的回收流程

1. 修改前读取飞书全文及 revision，再分页列出未解决评论；以外层 `has_more` 拉完评论页，以卡片内部 `has_more` 判断是否继续拉回复。`docs +fetch` 的紧凑评论只作定位提示，不能替代完整读取。已登记评论按 comment_id/reply_id 去重；需追溯已解决评论时显式选择包含已解决项。
2. 对每条批注记录原文、作者与日期、comment_id/reply_id、引用段落及读取 revision。把事实纠正、论证建议和措辞建议连到对应贡献、RQ 或段落；不把转述写成导师原话。正文直接编辑也与上次同步版本比较，先保留远端改动再合并。
3. 形成有来源的写作决定：采纳、部分采纳、暂缓或不采纳，并说明理由和证据。长期研究决定写在本页；review gate、CI、push、merge 等施工状态只进对应 PR。
4. 修改规范中文论文及必要的来源/术语/图表说明；数值回查 S0–S8，实质论证修改重新做证据和语言审查。需要新实验的建议先记录研究缺口，不能把期望写成结果。
5. 写回前重读远端 revision；如果变化，先合并新增内容。按已有段落或块局部更新，尽量保留被批注块的身份与锚点。不要整篇覆盖或删除评论来模拟同步；必须重组带批注段落时先保存原文和关联关系。
6. 写回后回读：核对段落顺序、全部正文、四表数值、引用和评论锚点；记录来源 revision 与对应 Git commit 到 PR。处理并核验后再决定是否解决评论，不能因已读取就自动标记解决。本流程在用户要求回收批注或继续写作时执行，不暗示后台持续监听。

批注记录每条包括：`来源链接 / comment_id / reply_id / 作者与时间 / 原文与选区 / 读取 revision / 处理决定及依据 / 修改节号 / 对应 commit`。尚无实际批注时不建立虚拟记录。批注含私人信息时，只将研究决定与必要引文纳入仓库。
