## 1. Thesis

【AI 建议·待确认】⚠️ 这段措辞是我方的，与导师定调不冲突，但没有一句导师逐字原话直接针对它，⛔ 因此不得升格为【导师原话背书】。

给定一份自然语言需求 `NL` 与一份由 LLM 从该需求生成的状态机模型 `STM_0`，**把「这个模型哪里不符合需求」变成一个可机械求值的问题**：先把需求全覆盖地拆成一条条义务，再把每条义务转换成一个受限谓词逻辑上的断言，在被评审模型上求值——为假者构成一条**带可执行判据与闭合证据链**的发现，为真者构成**回归防护**。

一句话：**本文贡献的是一套模型错误发现方法、支撑它的谓词逻辑断言体系、以及 issue 证据链体系，而不是「我们发现了多少问题」。** ⚠️ 这句的三个成分与 §7 已裁定的三条 contribution 一一对应（〔用户明确裁定 2026-08-11〕），⛔ 后续 PR 改这句时必须同步 §7，不得两处不一致。

**「可机械求值」在本文有确切含义，不是一个形容词。** ⚠️ 它是整篇论文的承重词——§7 三条 contribution 与 §8 的技术挑战都压在它上面。

【AI 建议·待确认】（措辞是我方的）**判据**：一条发现所依附的断言，能在**不看需求、不看参考模型、不问人**的前提下，仅由被评审模型本身决定真假；换一个人、换一次运行，得到同一个真值。⚠️ 这三条约束不是修辞，它们分别对应实现里的一个硬性安排：求值阶段的输入里没有 `NL`（§5.4 ⑥）、参考模型全程不是输入（§6.2）、断言以脚本形式落盘并可重放（§5.5）。

⛔ **它不意味着「一定求得出来」。** 谓词允许**拒答**——求不出可靠真值时返回第三种取值，而不是把求不出来当成假（§5.4、§6.6）。⛔ 也不意味着「求值为真 = 该处没有缺陷」，只等于「在这条义务的这个操作化下未观察到违反」（§6.3）。

## 2. 解决什么问题

【AI 建议·待确认】

LLM 已经能从自然语言需求生成状态机式制品，但生成出来的东西**不能直接用**——它可能漏掉需求点名的状态、把条件写成事件、把并列条件压成一个名字、留下进不去的状态或没有默认入口的复合态。于是问题从「能不能生成」变成 **「怎么知道生成的这一份哪里不对」**。

**场景是具体的，不是泛指。** 控制系统的功能需求以自然语言散文交付；据此产出一份状态机式制品（【v46 实测】本文语料里它是 **PlantUML** 状态图）；这份制品接下来要被喂给模型检查、测试生成或代码生成。所以「哪里不对」必须在制品**进入下游之前**被回答，而此刻回答它的人手上只有两样东西：**需求散文**与**这份图**。⛔【仓库裁定】**参考模型不在手上**（§6.2）——上游论文作者确实为每份需求写过参考模型，但它只在人工标注缺陷台账时使用；若允许方法对答案，要解的就不是这个问题了。

这不是一个「跑个检查器」的问题，原因有三层：

1. **判据从哪来**：需求是散文，模型是图；「模型是否满足需求」不是一个现成的形式化判定问题，得先把散文里的义务抽出来，再决定每条义务用什么可判定的形式表达。
2. **表达什么才算表达对了**：同一条义务有多种操作化，其中一部分是**伪代理**——「某条迁移是否存在」冒充「某个状态是否可达」就是典型：边存在不等于可达（守卫可能恒假、源态可能不可达），边不存在也不等于不可达（可经其它路径）。形式相似而实质不同。【仓库裁定】该替换已被明令禁止，见 [../discover_matrix/docs/protocol/hit_criterion.md](../discover_matrix/docs/protocol/hit_criterion.md)。
3. **行为性问题在图上没有定义**：PlantUML 是绘图记法，不定义执行语义——「从上电起 3 步内能否到达 X」在它上面不是难以回答，是问题本身没有定义。

**三层叠起来的后果是：这个问题要的判据，和检查器给的判据不是同一种东西。** 检查器查的是**制品自身**的性质——语法、引用完整性、可达性、是否有默认入口；而「不符合需求」要求一个**从需求那一侧长出来的判据**，它必须知道需求第几句要求了什么、这个要求落在模型的哪个元素上、以及用什么可判定的形式表达它。**本文构造的就是这样一个判据**，而不是再实现一个检查器。

## 3. 为什么这个问题有价值

【AI 建议·待确认】三条，按对审稿人的说服力排序：

1. **它是 LLM 建模落地的必经关口。** 控制系统的状态机模型下游要接模型检查、测试生成、代码生成；一个「看起来像状态机」的制品进入下游，错误会被放大而不是被发现——模型检查会在一个错的模型上给出正确的答案，测试会照着错的行为生成，代码会把错误固化。而人工逐份复核 LLM 生成的模型，成本与直接手写模型相当——那样 LLM 就没有意义了。**所以这道关口既不能省，也不能靠人力堆。**
2. **交付物的形态决定了这项工作能不能被用起来，而不只是被读一遍。** 同一个「模型有问题」的结论，可以写成三种东西，对使用者是三件不同的事：写成**一句自然语言评语**，使用者必须回读需求与模型才能确认它成不成立；写成**一条带定位的缺陷记录**，能确认了，但改完之后还得再人工确认一遍；写成**一条可以在制品上重新求值的断言**，改完直接重跑就知道。**所以「发现」这项任务的难点不止在于找得准，还在于产出物是什么形态**——这正是 §4 三条 gap 的来源，也是本文把「一条发现」定义成「一条可机械求值的断言 + 它的证据链」而不是「一段评语」的理由。
3. **它是可累积的。** 断言一旦成立就可以反复求值。模型改一次，整套断言重跑一次——这是「一次性评审」变成「持续防护」的分界。⚠️ 这一条与第 2 条是同一件事的两端：只有当交付物取了第三种形态，累积才是可能的；评语和缺陷记录都不能重放。

## 5. 我们的方法：核心洞察

### 5.1 受限谓词词表本身就是一次建模

【导师原话背书】**这是本文最核心的判断。** 措辞是我方的（[08-08 记录](../../talks/2026-08-08-导师-paper1收窄为issue-discover.md) §一「核心定调：discover 独立成篇」末段：「**受限谓词词表本身就是一次建模**——这正是导师所指」），背书用的导师逐字原话是「**这个逻辑进一步印证了业务建模在其中的重要性**」。

不给 LLM 一个通用工具箱让它自己摸索，而是**先把「一个状态机模型可能在哪些方面不符合需求」这件事建模一遍**，结果是一个 **19 个谓词的闭合词表**。【v46 实测】词表按求值机制分三族：

| 族 | 个数 | 回答什么 | 谓词 |
| :-- | --: | :-- | :-- |
| 结构 | **10** | 模型里写没写 | `state_declared`、`event_declared`、`variable_declared`、`edge_declared`、`containment`、`initial_target`、`effect_declared`、`action_declared`、`guard_distinguishable`、`cardinality` |
| 仿真 | **6** | 跑起来会怎样 | `reaches`、`occupancy_after`、`event_consumed`、`stays_in`、`terminates`、`variable_delta_after` |
| 有界模型检查 | **3** | 界内是否恒成立 | `invariant`、`response_within`、`persists_until` |

这个词表干了三件事，缺一不可【AI 建议·待确认】：

1. **它是一次领域建模**——把控制系统需求里反复出现的义务模式（可达、驻留、事件响应、效果方向、覆盖）固化成有限个可判定形式。
2. **它约束了 LLM 的输出空间**——LLM 不再自由发挥，只做「把这条义务映射到哪个谓词、绑哪些元素」这一件事。
3. **它让测不了的东西显式暴露**——义务无法用这 19 个谓词表达时，系统必须记为覆盖缺口，不许换个近似谓词蒙混过去。

### 5.2 ⚠️ 词表的由来：论文怎么写（承重结构）

【导师原话】

> 「**规则一定是从领域分析归纳出来的，应用在 54 个案例中**」
>
> 「**基于所归纳的规则，指导了 prompt 设计，这个逻辑能说通**」

【仓库裁定】由此确定的口径：**从领域分析、真实文献与技术资料调研归纳而来，应用于 54 个案例，并据此指导 prompt 设计。** ⛔ **不表述为「从这批 pair 归纳」。** ⛔ **不在论文里解释留出集**——「为什么不留出」在本方法的论证结构里根本不出现。工程侧四条配套要求见 [../discover_matrix/docs/protocol/method_provenance_policy.md](../discover_matrix/docs/protocol/method_provenance_policy.md)。

【v46 实测】v46 报告 §4.4 举出的两个示例可直接写进论文（⚠️ 这是**举例数**，不是实际标注数——实际有 **3 个**谓词挂了出处注释，见下）：

- **`stays_in`** ← UML 2.5.1 §14.2.3.9.1 的 run-to-completion 规则：一个在当前配置下不触发任何迁移的事件会被**丢弃**，而丢弃不改变配置。**所以「事件有没有被消费」与「机器有没有离开」是两个独立问题**——该谓词不能用前者近似后者。
- **`persists_until`** ← 时序逻辑中 until 的标准定义：`p U q` 只约束 `q` 首次成立**之前**的前缀；「整个区间上 `p` 或 `q` 恒成立」是一个严格更强的不同公式。有界情形取弱形式，界内既未释放也未违反的运行不算反例。

⚠️【v46 实测】**当前只有 15 处规则挂了出处注释，19 个谓词未逐条挂钩**——这是已登记的工程欠账。其中**落在具体谓词上的是 5 条注释、覆盖 3 个谓词**：`occupancy_after`、`stays_in`、`persists_until`（均在 `pipeline/feedback_loop/src/paper_stm_feedback_loop/assertions/predicate_api.py`，落在这三个 `def` 体内的 `provenance:` 注释上，条数依次为 1 / 2 / 2）。**其余 16 个谓词一处都没有。** 余下 10 条都不能算谓词的逐条挂钩：9 条在非谓词位置（`capability.py` 3、`nodes.py` 2、`schemas.py` 2、`renderer.py` 1、`predicates.py` 的 `presupposes()` 1），1 条在 `_require_well_formed_names` 这个辅助方法上（同一文件，`def _require_well_formed_names` 体内）。⚠️ **`5 + 9 + 1 = 15` 才闭合**——早先写成 `3 + 9 + 1` 是把「谓词数 3」当成了「注释数」，那 3 个谓词其实由 5 条注释覆盖（`stays_in` 与 `persists_until` 各占 2 条）。

### 5.3 断言由全覆盖的需求拆分转换而来，因而覆盖性的分母来自需求侧

〔我方提出 · 导师未反对〕流程不是「让 LLM 读模型找问题」，而是**先读需求**：把需求原文全覆盖地拆成义务，再逐条转换成断言。

> ⛔ **强度更正（2026-08-11）**：此前标为【导师原话背书】，但 [08-08 记录](../../talks/2026-08-08-导师-paper1收窄为issue-discover.md) §3.2「第一条 contribution：谓词元模型与断言体系本身」正文首句明写这条是「我方在讨论中提出（导师未反对，并以上面那句强化）」。按 [README.md](./README.md) §2，**「导师未反对」不等于背书**——背书要求有一句导师逐字原话直接针对该判断，而这里没有。已降档。

这条顺序有两个直接后果【AI 建议·待确认】：

1. **覆盖性来自构造，不来自运气**——分母是需求的义务集，不是模型的可疑点集。
   - ⚠️ **这一条必须与一道硬边界同时写出，否则整个论证是循环的**【AI 建议·待确认】：上面这句只说明**分母取自哪一侧**（需求侧，而不是「模型上看起来可疑的地方」），⛔ **它不等于需求被完整地拆分了**。「全覆盖」是 §5.4 ① **交给 LLM 的一条指令**，不是一条已被验证的性质；审查它的 ② 也是 LLM。**两端都是 LLM，而这条拆分的完整性本轮未测量。** ⛔ 因此不得由「分母来自需求侧」推出「分母是完整的」，也不得把 §9 的命中率读成「相对需求全集的覆盖率」。⚠️ 本轮测不了的原因是两个分母候选都不干净：取「拆出的义务条数」，那是**方法自己产出的**，用它做覆盖率是自证；取「NL 的句子数」，则需要一份人工的句子级义务清单，那是又一个未经一致性检验的人工判定源。口径见 [paper_outline.md](./paper_outline.md) 的 `TODO-O7`。
2. **每条发现天生带上下文**——它知道自己来自需求哪一句、绑在模型哪个元素、用哪个谓词以什么参数求值为假。§4 的三条 gap 由此同时被填。

### 5.4 阶段化 + 定向反馈的循环

【v46 实测】八个阶段，每个产出阶段配一个审查者，不合格带**定向反馈**打回重写：

```
需求 + 模型 → ① 需求拆分 → ② 需求审查 ⟲ ①
            → ③ 断言转换 → ④ 静态预检 ⟲ ③ → ⑤ 断言审查 ⟲ ③
            → ⑥ 求值发布 → ⑦ 归因绑定 → ⑧ 结果裁决 → 发布 issue
```

【v46 实测】逐阶段的职责如下（⚠️ 这里只给职责与交接物，实现见 [../pipeline/feedback_loop/](../pipeline/feedback_loop/) 的 `discover/graph.py` 与 `discover/nodes.py`；「LLM / 确定性」一列说的是**这一步的判断由谁做**）：

| 阶段 | LLM / 确定性 | 输入 | 干什么 | 交出什么 |
| :-- | :-- | :-- | :-- | :-- |
| ① 需求拆分 | LLM | `NL` 原文 | 把散文**全覆盖地**切成一条条**需求义务**，每条记下它出自原文哪一句、属哪种 `verification_kind`、量词 / 触发 / 结果 / 覆盖义务各是什么 | 义务集 |
| ② 需求审查 | LLM | 义务集 + `NL` | 查覆盖（有没有句子没被认领）、查切分（有没有把两条义务压成一条）、查忠实（有没有加需求里没有的东西）；不合格带**定向反馈**打回 ① | 通过审查的义务集 |
| ③ 断言转换 | LLM | 义务集 + 被评审模型的元素表 | 每条义务映射成闭合词表上的**断言**：选谓词、绑模型元素、定角色（`primary` / `precondition` / `supporting`）与依赖；表达不了的**记为覆盖缺口**，⛔ 不许换近似谓词 | 断言脚本 |
| ④ 静态预检 | 确定性 | 断言脚本 + 被评审模型 | 不依赖 LLM 的检查：引用的元素在不在、参数形状对不对、有没有恒真恒假；**并在此按依赖拓扑序真正执行断言**，把结果**封存**起来。形状不合法的带定位打回 ③ | 可执行性状态（公开）+ **封存的真值**（不公开） |
| ⑤ 断言审查 | LLM | 断言脚本 + 义务集 + ④ 的**公开部分** | 查操作化是否忠于义务、有没有伪代理（§2 第 2 条）、角色与依赖是否自洽；不合格带定向反馈打回 ③ | 通过审查的断言脚本 |
| ⑥ 求值发布 | 确定性 | ④ 封存的真值 | 校验脚本哈希与工具环境哈希未变，然后**解封**真值 | 每条断言的真 / 假 / 拒答 |
| ⑦ 归因绑定 | 确定性 | 为假的断言 | 把每条为假的断言绑回它的需求义务、`NL` 原句与模型元素；绑不到作者写的元素上的（编译器自己造的元素）在此被识别出来 | 候选发现 + 归因状态 |
| ⑧ 结果裁决 | LLM | 候选发现 + 义务集 + 覆盖缺口 | 合并同源、剔除不成立的、决定哪些成为发布的 issue。⚠️ **issue 集合对 ⑥ 的结果闭合**——裁决者能改的只是分组与措辞，不能凭空增删一条为假的断言 | 已发布 issue 清单 |

⚠️ 图上的「需求 + 模型 →」与「→ 发布 issue」在实现里各自还对应一个确定性节点（`prepare` / `publish`），它们只做输入冻结与产物落盘、不产出任何主张，故不计入八阶段。

⚠️ **④ 与 ⑤ / ⑥ 的这个拆法不是工程细节，是方法的一部分**【v46 实测】：断言在 ④ 就已经跑完，但真值被**封存**，⑤ 的审查者只看得到「这条能不能执行」，**看不到它是真是假**。所以审查者无法朝着某个想要的结论去调断言——它只能就「这条断言忠不忠于那条义务」发表意见。⑥ 解封前还要校验脚本哈希与工具环境哈希，确保被审查的脚本与被求值的脚本是同一份。

⚠️ **循环发生在审查者与被审查者之间，不是重试**：审查者说清哪一条不合格、缺什么、期望什么形状，被审查者据此修订。**这一点必须与「换个随机数再跑一次」明确区分**，否则整个循环的贡献会被读成「多采样几次」。⚠️ 图上三条 `⟲` 各自打回的对象也不同：② 打回 ①（义务切错了）、④ 与 ⑤ 都打回 ③（断言写错了，但一个是形状错、一个是语义错）。

⚠️ **求值不看需求也不看参考模型，只看被评审模型本身**，所以它的真值是客观的、可复算的。求值层允许**拒答**：谓词无法给出可靠真值时返回拒答而不猜真假。

### 5.5 为真的那部分不是废料

求值为真的断言构成**回归防护**：它们记录了「这份模型在这些义务上是对的」。模型改动后重跑，为真变为假即为回归。

**这一条之所以成立，靠的是前面几节已经付过的代价，而不是额外做了什么**：断言以脚本形式落盘、绑定的元素是显式的、求值只依赖被评审模型且不需要人参与（§5.4 ⑥）——三者齐备，「重放」才是一个按钮而不是一次重新评审。⛔ 反过来说，若发现只是一段评语，这一节根本不存在（§3 第 2 条）。

⚠️ **它的读法有一条硬边界**【仓库裁定】：求值为真**不等于**「该处无缺陷」，只等于「在这条义务的这个操作化下**未观察到违反**」（§6.3）。所以防护面挡住的是**回归**，不是**遗漏**——一条从来没被表达出来的义务，不会因为别的断言为真而被覆盖。

⚠️【待定】这条目前是**方法性质的主张，不是实测结论**——【v46 实测】本轮未统计防护面规模。⛔ 因此在正文里它只能写成性质，不能写成结果，也不得给任何规模数字。口径见 [claim_evidence_map.md](./claim_evidence_map.md) **C3**（⛔ 此处此前误引为 C13，C13 说的是有界模型检查那一族，与本条无关，已更正）。

## 6. 任务边界

> 本节吸收了上一版独立的 `task_boundary.md`，去向说明见 [README.md](./README.md) §3.1。

### 6.1 任务定义

```text
输入：<NL, STM_0>
      NL    自然语言需求原文
      STM_0 一份由 LLM 从该需求生成的状态机模型（PlantUML）

产出：<已发布的 issue 清单,
       支撑每条 issue 的可执行断言,
       一条可回溯到 NL 原句与模型元素的证据链,
       求值为真的断言构成的回归防护面,
       未能表达的义务所对应的覆盖缺口>
```

**任务是发现，不是修复。**【导师原话】

### 6.2 输入与两条硬约束

| 输入 | 说明 | 纪律 |
| :-- | :-- | :-- |
| `NL` | 控制系统自然语言需求原文 | **义务的唯一来源**。需求层主张必须能引到具体哪一句 |
| `STM_0` | 被评审模型，PlantUML | **唯一的求值对象**。判定表示债务时必须回读它，不读编译产物 |
| 溯源元数据 | 取自上游数据表的哪一行哪一列、生成它的是哪个 LLM、原始文件 SHA-256 | 支撑可复现性 |

⛔【仓库裁定】**参考模型不是输入。** 上游论文作者为每份需求人工撰写的参考模型，**只在人工标注缺陷台账时使用**；方法全程不接触它。这保证方法不是在「对答案」。

⛔【仓库裁定】**缺陷台账不是输入。** 台账只在评测侧使用，且只在图终止之后用于审计；运行时不得进入任何 prompt、schema 或门。

### 6.3 产出

| 产出 | 不能做什么 |
| :-- | :-- |
| 已发布 issue | 不得发布无断言支撑的自然语言判断 |
| 可执行断言 | 不得自造谓词；不得用近似谓词替代无法表达的义务 |
| 证据链 | 不得只留结论不留调用原文 |
| 回归防护面 | 不得把「求值为真」读作「该处无缺陷」，只等于「在该操作化下未观察到违反」 |
| 覆盖缺口 | 不得静默换谓词蒙混过去 |
| 降级诊断 | 不得因配额耗尽而整格失败、丢弃产物 |

### 6.4 方法外

| 不做 | 归属 |
| :-- | :-- |
| 模型修复、多轮修复-确认、修复后回归确认 | 后续论文【导师原话】 |
| 一轮式 `NL -> STM` 初始生成 | 语料的来源方式，属上游论文；本文只作 related work |
| 证明某种建模语言 / DSL 更好 | 不是本文命题；中间表示是介质 |
| 完整 PlantUML / SysML round-trip 转换器 | 工程问题，且我们只需单向编译 |
| 时钟、不变式、正交区语义的验证 | 研究内容三 |
| 缺陷台账的自动构造 | 台账是人工标注的评测分母，不是方法产物 |

### 6.5 人类角色

| 环节 | 人类做什么 |
| :-- | :-- |
| 问题定义与范围 | 冻结建模对象 $M$、闭合谓词词表、claim 边界 |
| 缺陷台账标注 | 逐 pair 通读需求原文、被评审模型、参考模型三份材料 |
| 命中判定 | 逐位人工判定，并写下判据文字 |
| 多报侧裁定 | 逐簇按五类判定流程裁定；「回读作者源」一步**按定义不可机械复核** |
| **方法运行** | **无人在回路。** 不得在 run 中替换输入、干预中间产物或补写发现 |

⚠️【v46 实测】**判定层是独立误差源**：588 位与 288 簇全部由单一判定者人工裁定，**无第二判定者、无一致性系数**。这是 §Threats 的必写项。

### 6.6 失败与不确定状态

【仓库裁定】方法不允许整格崩溃，只允许降级。以下状态都必须显式落盘并进入分析：**拒答**（谓词无法给出可靠真值）、**覆盖缺口**（义务无法用闭合词表表达）、**隔离项**、**降级**（内部配额耗尽时封存产物）、**不可判定**（判定侧证据不足）。

⚠️ **降级不是失败，是设计。** 反过来做（配额耗尽即整格失败）会让最难的样本系统性地从数据里消失——而最容易耗尽配额的，恰恰是缺陷最硬的那些格。【v46 实测】v46 有 **9 个降级格**（claude 1 / gpt 8），它们仍有产物、仍进统计。

⚠️【v46 实测】**拒答有一个已知副作用**：拒答文案会回灌进生产者的下一轮上下文，其中包含极性与「把它发布出去」的指示。这是 `hit@1` 上界性的第二条通道，**尚未量化**。同一机制在方法一节是设计优点、在结果一节是上界成因，**两处必须都写**。

#### C-② 基于归纳后的谓词逻辑的断言体系（即谓词逻辑元模型）

**这一条立的是「用什么语言说出一条发现」。** 它是一套面向状态机问题发现的**谓词逻辑元模型**：19 个谓词构成的**闭合词表**，分结构 10 / 仿真 6 / 有界模型检查 3 三族（全表见 §5.1），**从领域分析、文献与技术资料调研归纳而来**，据此指导 prompt 设计，并应用于 54 个案例。

**「闭合」是这条的关键词，它有确定的操作含义**，三条一起才叫闭合：

1. **不许自造谓词**——LLM 只能从这 19 个里挑，它做的是「这条义务落哪个谓词、绑哪些元素」的映射，不是自由发挥（§5.1 第 2 点）。
2. **不许近似替代**——义务表达不了时必须**记为覆盖缺口**，⛔ 不许换一个形状相似的谓词蒙混过去（伪代理，§2 第 2 条、§8）。
3. **边界因此是显式的**——测不了的东西被逼着显形，而不是悄悄消失在一句「未发现问题」里（§5.1 第 3 点）。

**元模型之上是断言体系**：NL 全覆盖拆分出的需求条目**全量**转换成该词表上的断言，每条断言带角色（`primary` / `precondition` / `supporting`）、模型元素绑定与依赖关系。由此得到三条性质：

1. **覆盖性来自构造**，不来自运气——分母是需求的义务集；⚠️ **这只说明分母取自需求侧，⛔ 不等于需求被完整拆分**：拆分由 §5.4 ① 产出、由 ② 审查，两者都是 LLM，其完整性本轮**未测量**（硬边界与两个分母候选的问题见 §5.3 条 1，口径见 [paper_outline.md](./paper_outline.md) 的 `TODO-O7`）。⛔ 因此这条性质不得被写成「本方法覆盖了需求的全部义务」。
2. 求值为**假**的子集构成 issue；
3. **整个集合是一套回归套件**——为真者构成防护面，模型改动后重放。

⚠️ 这条 contribution 的合法性**完全挂在 §5.2 的领域分析上**（`TODO-S3`）：「从领域分析归纳」这句话若挂不住，剩下的就只是「我们选了 19 个谓词」。⛔ 这是三条里**唯一一条其根基本身还是欠账**的，也因此是 R2 必须交给导师拍板的议题之一。

##### ⭐ 断言不是规约，是回归防护 —— ⛔ 它只在演化线上有意义

〔用户明确裁定 2026-08-12〕**「对同一个 NL 的建模本身就没有唯一答案，而断言本身就得是依赖于建模方式的，哪怕这个方式可能并不一定都对都完整，所以不具备可迁移性，只在当前 stm 的演化线上是有意义的。」**

⭐ **这条论断决定 C-② 的主张边界，⛔ 必须写进论文而不是留在讨论里。** 展开是三句：

1. ⛔ **断言不可跨模型迁移。** 一条断言绑定的是**这一个模型的结构**（元素路径、层次、迁移）。同一份 NL 的另一个合法建模可能有完全不同的结构——⭐ 于是「该断言在另一个模型上为 True」**什么也不说明**，⛔ 既不证明断言对、也不证明那个模型好。
2. ⭐ **因此断言不是规约（specification）。** 规约的性质是**建模无关**——它约束一切满足它的实现。⛔ 我们的断言做不到这一点，⭐ 也不主张做到。
3. ⭐ **它是回归防护（regression guard）**：在**同一个模型的演化线上**，它能确定性地回答「这个缺陷还在不在」。⭐ 这正是它对下游的价值所在，⛔ 也正是它的作用域上限。

⚠️ **两条导出的纪律**：⛔ 论文中不得把断言表述为「从需求导出的规约」或「可复用的性质库」；⭐ 而 ref 翻转率一类实验**必须在同一模型上做**——⛔ 不得用同 NL 的另一个生成模型充当「已修复实例」，⚠️ 那个设计 2026-08-12 提出后当场被否决，理由就是上面第 1 条。


#### C-③ issue 证据链体系

**这一条立的是「一条发现交付出去时带着什么」。** 每条 issue 可沿 `issue → 断言 → 需求条目 → NL 原句 / PlantUML 元素` 完整回溯，四段链接各自是一个**可以被第三方独立检查的对象**，而不是一句出处说明：

| 链接 | 它是什么 | 拿到它的人能做什么 |
| :-- | :-- | :-- |
| issue → 断言 | 一条可重新执行的断言：谓词、参数、绑定的模型元素、以及它这次的真值 | 不信就自己再跑一遍；模型改了就重跑，直接知道这个问题还在不在 |
| 断言 → 需求条目 | 该断言由哪条需求义务转换而来，以及它在这条义务里的角色 | 判断这个操作化忠不忠于那条义务——即「你测的是不是我要的」 |
| 需求条目 → `NL` 原句 | 该义务出自需求原文的哪一句 | 回到需求侧确认这条要求**确实存在**，而不是方法自己想出来的 |
| 断言 → PlantUML 元素 | 它绑在被评审模型的哪个状态 / 事件 / 迁移 / 动作上 | 知道该改哪里；也能判断这条主张有没有落在**编译器自己造出来的元素**上（表示债务，§5.5） |

**这四段的价值不在于「记录得全」，而在于它们各自封死了一种「说不清」**：没有第一段，读者只能选择相信结论；没有第二段，无法判断操作化是否走样；没有第三段，无法排除方法在需求里无中生有；没有第四段，无法区分「模型错了」与「我们自己的转换环节错了」。

⛔ **所以它不是簿记。** 簿记是把已经发生的事记下来，而这四段是发现**在被生产时就必须满足的结构约束**——凑不齐这四段的东西在 §5.4 ⑦⑧ 根本走不到发布。⚠️ 与之相符的一条纪律已写在 §6.3：**不得发布无断言支撑的自然语言判断**。⚠️ 也正因如此，§7 末「不能写成主贡献的」里那条「run record 与证据簿记」与本条**不冲突**：簿记是可复现纪律，本条是发现的构造约束。

【导师原话】这正对着「现有的很多 detection 方法报告错误，缺少错误的上下文信息」那条差异化叙述。

###### ⭐ 最强的一条：**锚定位置改变处置率，而准确率不变**

⭐⭐ **Infer 自然实验**（Distefano, Fähndrich, Logozzo, O'Hearn，**CACM 62(8)**:62–70, 2019，DOI [10.1145/3338112](https://doi.org/10.1145/3338112)）—— ⭐ **全库唯一把「锚定」从「准确率」中分离出来的证据**。逐字：

> *"We assigned 20–30 issues to developers, and **almost none of them were acted on**. We had worked hard to get the false positive rate down to what we thought was less than 20%, and yet the fix rate… was **near zero**."*
>
> 改到 diff time 后：*"the fix rate **rocketed to over 70%**. **The same program analysis, with same false positive rate**, had much greater impact when deployed at diff time."*

⭐ **分析不变、误报率不变，只改变发现挂在哪里 → 处置率从 ≈0 到 &gt;70%。**

## 11. 可以说的话

【v46 实测】（+ 仓库裁定）

- 我们研究「给定需求与一份从它生成的状态机模型，自动发现不符合之处」这一任务。
- 我们给出一条完整的发现链路：需求拆成义务、模型转换到带形式语义的中间表示、在其上以结构检查 / 仿真 / 有界模型检查求值、再归因收束成 issue（对应 §7 C-①）。
- 我们给出一个 19 谓词的闭合词表与一套需求义务到断言的转换方法，使每条发现都可机械求值、可回溯到需求原句与模型元素。
- 断言由需求拆分转换而来，因而**覆盖性的分母来自需求侧**，不是模型的可疑点集；求值为真者构成回归防护。⚠️ ⛔ **这句只能说到「分母来自哪一侧」为止**：拆分的完整性由两个 LLM 阶段（§5.4 ①②）保证而本轮未测量，⛔ 不得写成「覆盖了需求的全部义务」「天然具备覆盖性」或任何暗示分母完整的说法（见 §5.3 条 1 的硬边界）。
- 可执行语义是必要的：按台账断言组的族构成，**26%–43%** 的已知缺陷需要行为证据表达（两口径）。
- 未被台账认领的产出逐条可裁定，其中最大一块（按条目 **46.5%**）不是模型缺陷也不是方法误判，而是评审入口的编译损失——这使「有些多报不是被评审对象的错」从一句 threats 变成一个**可扣除的量**。

## 12. 要小心的话

- ⛔ **三条 contribution 的强度一律未定。** 在 L1 / L2 的文献结论回来之前，⛔ 不得写「首个」「据我们所知未见」「显著优于」「远超」这类强度词，也不得用「填补了空白」一类同义变体绕过去。⚠️ 强度档的判据与每档要什么证据，定义在伞 PR [#179](https://github.com/HansBug/research_ideas/pull/179) §4.6 Q3，落笔在 **R1**。
- 「覆盖率」必须带 $\le$，且必须与算力代价一起给。
- 「必要性」只到这个强度：可执行语义必要；**有界模型检查的必要性本实验无法判定**——不是被证伪，而是这批语料没有提供足够深度的案例。
- 「回归防护」目前是方法性质，不是实测结论。
- 「表示债务占 46.5%」**不宜外推**——一条链、一个语料、一个检测器。论文里主张的应当是**审查动作**（评审入口若是中间表示，就必须做这项扣除），不是这个数字。

## 13. 不能说的话

【仓库裁定】

| 禁止 | 为什么 |
| :-- | :-- |
| 本文做模型修复 / 修复效果如何 | 修复是后续论文；导师明确 discover 单独成篇 |
| 贡献是 feedback loop + verification feedback | 已被 2026-08-07 / 08-08 定调取代 |
| 贡献是 `fcstm` / `pyfcstm` / 某种建模语言 | 中间表示是介质 |
| 贡献是 ledger / audit / 证据簿记 | 属评价与可复现纪律 |
| 贡献是「发现了 N 个新缺陷」 | 相对台账的净增量只有 **2 条**，且都不稳定 |
| `hit@1 = 60.4%`（不带 $\le$） | 已知扣除项只给上界方向 |
| 多报侧的「误报率」 | 分母不同质，且最大一块不是误判 |
| 某个执行模型更适合这项任务 | 两模型差 4.4pp，小于可解读量级，且能力边界高度重合 |
| 谓词选型建议 | 谓词与缺陷类型共线，须先做词表消融 |
| 这些模型没有并发 / 时间问题 | 我们排除的是无法判断的部分 |
| 台账即缺陷全集 | 台账有已知缺口，24 个 case 有外部记录的语义问题而台账无对应条目 |
| 「我们调查了 N 篇文献归纳出词表」 | 报锚定关系比报数量有说服力，且报数量会招来 SLR 方法论质询 |
