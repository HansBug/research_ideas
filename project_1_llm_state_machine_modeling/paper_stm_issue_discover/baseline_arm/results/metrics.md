## 2. ⭐ 逐位分解：两臂**互有胜负**，⛔ 不是一边宽松

588 位逐位并列（两臂键格式逐字相同，可直接对拍）：

| | 位数 | 占比 |
| :-- | --: | --: |
| 两臂都命中 | 269 | 45.7% |
| **仅主臂命中** | **86** | 14.6% |
| **仅 X1 命中** | **174** | 29.6% |
| 两臂都未命中 | 59 | 10.0% |
| 净差 | $+88$ | $= 15.0$pp ✅ 与 `hit@1` 的 Δ 闭合（差 0.1pp 为取整）|

⭐⭐ **「仅主臂命中 86 位」是排除「X1 判定普遍宽松」的关键证据**：若 X1 判得松，我们会看到 `x1_only` 很大而 `main_only` 趋近 0。实际两臂各有 14.6% 与 29.6% 的独有命中——**这是能力正交的形状，⛔ 不是一边放宽的形状。**

### 2.1 ⚠️ 按主臂四池分布：X1 的命中与主臂**几乎不相关**

| 主臂池 | 位数 | X1 在该池的命中率 |
| :-- | --: | --: |
| 满格 6/6 | 222 | $171/222 = 77.0\%$ |
| 近满格 5/6 | 78 | $64/78 = 82.1\%$ |
| 不稳定 1–4/6 | 150 | $101/150 = 67.3\%$ |
| 零命中 0/6 | 138 | $107/138 = \mathbf{77.5\%}$ |

⭐⭐ **满格池 77.0% 与零命中池 77.5% 几乎相同。** 即：主臂能否稳定命中某条缺陷，与 X1 能否命中它**基本无关**。⛔ 这直接反驳「基线只是把容易的那些捡了一遍」。

⚠️ **一处必须纠正的诊断逻辑**：`cross_arm.py` 的 `diagnose()` 曾把「满格池上 X1 独有命中 = 0」当作判定标准未放松的证据。⛔ **那是错的**：满格池按定义主臂全命中，`x1_only` 恒为 0，不含任何信息。⭐ 有信息的是上表的**池内命中率**与 §2 的 `main_only` 计数。

## 9. ⛔⛔ 一处已撤回的解释：「转换擦掉了缺陷所以主臂先天不利」——**那是错的**

⚠️ 本文件 §4.1 第 1 条与我先前的口头解释都暗示：主臂读编译产物、台账按作者源标，所以转换会擦掉缺陷、使主臂先天不利。⛔ **独立逐条核查（98 条 REPORTABLE × 42 对 `plantuml.puml` / `fcstm.fcstm`）推翻了这个解释。**

| 类 | 条数 | 判据 |
| :-- | --: | :-- |
| A · 完全可见 | **79** | fcstm 上有与台账 `generated_side` 实质同形的声明 / 边 / 缺失 |
| B · 形态改变但仍可见 | **19** | 缺陷仍在，但表现为编译器注入的**自申报标记态**或 route-token 改写 |
| **C · 被转换擦掉** | **0** | — |
| **D · 转换新造** | **0** | — |

⭐ **机制**：R4.5 转换把自由文本压成标识符时，**同时用 `named "<原文>"` 把原文原样带过去**——所以以名字或标签为载体的缺陷一条都没丢。全量词法对拍：42 对里作者源的每个状态名、每条迁移标签都逐字出现在 fcstm 里。

⛔ **我举的 pair 0000 那个例子（`state HumanDrivingMode { }` 空复合括号）根本不在 98 条里。** 全语料只有 4 处空复合括号（`0000` / `0009` / `0030` / `0050`），而 **126 条台账记录没有任何一条以它为对象**。⭐ 所以 X1 在 0000 上报出它是一条**台账外发现**，⛔ 不是「主臂漏掉的台账条目」。

⭐ **B 类没有系统性压低主臂**：B 类 19 条的主臂命中率 $70/114 = 61.4\%$，与整体 $60.4\%$ 几乎一样。⚠️ 编译器注入的标记态（如 `named "Unspecified initial"`、`"PlantUML initial target outside child scope: DoorsClosing"`）反而把异常**写进了名字**，使缺陷更容易被读出。

⛔ **因此不存在正当的分母剔除理由。** 判据是「一个方法能否被要求发现它按设计看不到的东西」——对这 98 条，**没有一条是主臂在其输入上看不到的**。任何扣减都会变成 `CLAUDE.md` §3.5 条款 4 的「更改分母」。⛔ **$\Delta = -14.9$pp 站得住，不能靠口径修正减小。**

### 9.1 ⭐ 但真正的不对称是另一件事，且它更重要

> 台账按作者源标注（`hit_criterion.md` §4.2 逐字「在 `stm0.puml` 里数引用次数」），而**被编译擦除的缺陷类在标注时根本无从与「正常」区分**——标注者读作者源时看到 `state HumanDrivingMode { }`，但它在 98 条里一条都没有。⛔ 这不是分母被压低，⭐ 是**可测缺陷空间被截断**：这 98 条系统性偏向「**能扛过编译的缺陷**」。
>
> ⭐ 后果：`hit@k` 作为**已知缺陷集覆盖率**依然有效，⛔ 但它对「编译会擦掉的那一类缺陷」**完全无信息**，而 X1 因为读作者源恰好对这一类有信息。⚠️ **两臂在这一类上不可比。**

⚠️ 这个截断的规模**未量化**（需按作者源重做一遍标注，本轮范围外）。⭐ 可确认的下界是 **4 处空复合括号、台账 0 条覆盖**。
