# 可断言性判定指令（发给每个判定组的**物理同一份**文本）

> ⭐ 本判定与「这条发现对不对」**完全无关**。命中判定已经做完并冻结，⛔ 你不复核它。
>
> ⛔⛔ **本口径是在看到 `hit` 结果之后提出的**，这一点必须公开记录，⛔ 不得隐瞒。⭐ 它之所以仍然正当，是因为它操作化的是论文 §1 早已声明的承重词「**可机械求值**」——⛔ 不是为了这次结果新造的概念。⭐ 且它**可证伪**：若判定结果显示绝大多数条目都可断言，这条论证线就不成立，⭐ **那也必须如实报出**。

---

## 一、你要判什么

给你一批**已被判为命中**的条目。每条含：判定者当时的论证（仅供你定位是哪条 issue）、那条 issue 的三段文本（`issue` / `where` / `reason`）、以及该 pair 的 PlantUML 作者源全文。

⭐ **对每一条，回答一个问题**：

> **这条发现能否被转写成一个「对给定模型可确定性求值」的命题？**

即：是否存在一个可判定的谓词 $P$ 与一组模型元素 $E$，使得「这条发现成立」等价于 $P(E) = \mathrm{False}$，且 $E$ 中每个元素都能在模型里**唯一定位**。

⛔⛔ **判据刻意不绑定任何特定的谓词词表。** ⚠️ 若用「能不能用某套现成谓词表达」当判据，那是循环论证——用一方的能力定义什么算发现。⭐ 下面三条要件是**任何**形式化框架都需要的。

---

## 二、三条要件（⭐ 三条全中才算 `assertable`）

### 要件 1 · 可定位

发现点名的元素必须能在模型里**唯一确定**：某个具体的状态、事件、变量、迁移、或它们的确定组合。

| ✅ 满足 | ⛔ 不满足 |
| :-- | :-- |
| 「`AutonomousMode --> HumanDrivingMode` 这条边」 | 「相关的迁移」「某处」「模型的这一部分」 |
| 「状态 `FinalState`」 | 「终止相关的状态」 |
| 「`HighwayMode` 内的三个子状态」（若模型里恰好可枚举） | 「若干子状态」 |

⚠️ **判据是「读完这条发现，我能不能在 PlantUML 里指出唯一的那处」**，⛔ 不是「它有没有提到一个名字」。

### 要件 2 · 可判定

命题必须有**确定真值**——给定这份模型，它要么真要么假，⛔ 不依赖读者的品味、经验或语境判断。

| ✅ 满足 | ⛔ 不满足 |
| :-- | :-- |
| 「该边的目标应是 X 而模型写的是 Y」 | 「这个命名不够清晰」 |
| 「模型未声明事件 `Power_On`」 | 「这里的语义可能造成歧义」 |
| 「`Idle` 从初始态不可达」 | 「建议改用子机状态以提高可读性」 |
| 「三个条件被写在一个标签里」 | 「这种写法不是最佳实践」 |

⚠️ **含「可能」「建议」「不够」「更好」「通常应」「可读性」「最佳实践」这类词的主张，默认落在⛔ 不满足**——⭐ 除非去掉这些词之后仍剩下一个确定命题（那时按剩下的那个判）。

### 要件 3 · 单一方向

发现必须指向**一件确定的事**，⛔ 不是若干可能性的并列。

| ✅ 满足 | ⛔ 不满足 |
| :-- | :-- |
| 「缺少从 `A` 到 `B` 的迁移」 | 「应该加一条迁移，或者改成子机状态」 |
| 「`X` 不应是 `Y` 的子状态」 | 「`X` 的层级归属存疑」 |

⚠️ 若一条 issue 同时含**一个可断言主张**与**一些不可断言的附带议论**，⭐ **按可断言的那部分判 `assertable`**——⛔ 附带议论不构成减分。⚠️ 但若**唯一**的主张本身是多选或模糊的，则不满足。

---

## 三、⛔ 三条必须守的纪律

1. ⛔ **不要复核命中对错。** 一条发现可以既命中又不可断言，也可以既不可断言又命中——⭐ 两个维度正交。
2. ⛔ **不要因为「它说的是对的」就判可断言。** ⚠️ 正确性与可形式化是两回事，⭐ 这正是本轮要量化的东西。
3. ⛔ **不要偏向任何一侧。** ⚠️ 若这批条目大多可断言，⭐ **如实报出** —— 那意味着提出这条口径的论证线不成立，⛔ 而那是必须知道的结果。

---

## 四、输出格式

写一个 JSON 文件（路径见分工消息），结构：

```json
{
  "judged_by": "<你的组号，如 A1>",
  "positions": {
    "EIS-9999-99|run1/9999-gpt": {
      "assertable": true,
      "locatable": true,
      "decidable": true,
      "single_direction": true,
      "sketch": "state_declared(<某状态>) = False",
      "note": "可选"
    },
    "EIS-9999-98|run2/9999-claude": {
      "assertable": false,
      "locatable": true,
      "decidable": false,
      "single_direction": true,
      "failing_requirement": "decidable",
      "quote": "「命名可能造成引用歧义」",
      "note": "唯一主张是可读性judgement，去掉「可能」后不剩确定命题"
    }
  }
}
```

| 字段 | 要求 |
| :-- | :-- |
| `assertable` | ⭐ 三条要件全中才为 `true` |
| `locatable` / `decidable` / `single_direction` | 逐条给，⭐ 便于事后按要件拆分统计 |
| `sketch` | ⭐ `assertable=true` 时**必填**：写出那个命题的形状（⛔ 伪代码即可，⛔ 不要求用任何特定谓词表）。⚠️ 写不出 sketch 就说明它其实不可断言 |
| `failing_requirement` | ⭐ `assertable=false` 时**必填**：哪一条要件先失败 |
| `quote` | ⭐ `assertable=false` 时**必填**：从 issue 原文里**逐字**摘出使它失败的那句 |

⚠️ **`sketch` 与 `quote` 是这份判定唯一的可复核凭据。** ⛔ 缺了它们，判定就无法被独立审查。

⛔ **位数必须齐**，分工消息会告诉你应有多少条。
