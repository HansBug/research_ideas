# 基线 prompt 的设计说明与审查记录

本目录的 [naive_v1.txt](./naive_v1.txt) 是**基线 prompt 的唯一真源**。代码从这个文件读取，⛔ 不在 `.py` 里内联副本。

⭐ **为什么单独放一个文件而不是内联进代码**：这份 prompt 是事前登记锁定的对象，审查时要能回答「它有没有在跑格之后被改过」。单独成文件时，`git log -p prompt/naive_v1.txt` 一条命令就能给出答案；内联进 `.py` 之后，prompt 的改动与实现的改动混在同一批 diff 里，那条审计线就断了。

## 1. 判据：一个称职的实践者会怎么做

伞 PR [#179](https://github.com/HansBug/research_ideas/pull/179) §4B.2 给出的可判定下限是：**对照臂必须是「一个称职的实践者手上只有一个 LLM、没有我们的方法时，会真的这么做」的那个东西。**

这份 prompt 就是那个形态：告诉它有一份需求、有一份模型、请找出模型相对需求的不符之处，然后让它自由决定报几条、按什么维度报。⛔ 它没有检查清单，⛔ 没有缺陷类型分类，⛔ 没有示例——因为一个称职的实践者手上本来就没有这些。

## 2. 给了什么 / 省了什么 / 没省什么

按 §4B.2 的三栏表，逐格对照：

| ✅ 给了（给了才说得通） | ⭐ 省了（省了仍说得通，这是低配的合法空间） | ⛔ 没省（省了就是稻草人） |
| :-- | :-- | :-- |
| 同两个执行模型（`gpt-5.5` / `claude-opus-4-7`）、同 54 pair、同 3 轮 = 324 格 | 迭代 / 反馈 / 多轮修订（= C-①） | **完整输入**：`nl.txt` 与 `plantuml.puml` 全文，未截断 |
| 完整、未截断的 `nl.txt` 与 `plantuml.puml` | 需求审查 / 断言审查 / 结果裁决三个审查阶段（= C-①） | **任务陈述的诚意**：明确说「找出模型相对需求的不符之处」 |
| 一次诚意的任务陈述 + 输出格式说明 | 静态预检 / 工具反馈 / pyfcstm 的任何输出（= C-①） | **推理空间**：见 §3 的 `analysis` 字段 |
| 允许它自由决定报几条、按什么维度报 | 19 条闭合谓词词表 / 断言 schema（= C-②） | **模型档位**：与主臂完全相同的两个模型，⛔ 不降级 |
| schema 解析失败的原地重试（带定向反馈） | 证据链字段：`named_elements` / 需求条目绑定 / 定位 trace（= C-③） | **温度与采样参数**：不显式设置，用 profile 默认，与主臂一致 |
| 最小结构化输出（transport 层能力，主臂也用它） | 多样性采样 / best-of-n / 自一致 | **`max_output_tokens`**：不设上限，用 profile 默认（⛔ 不压） |

### 2.1 ⚠️ worked example 这一格为什么落在「可以省」

这是三栏里唯一需要单独论证的格子，因为它两个方向都沾一点：

- 若**给** example，就在示范「该找哪一类问题」——那是 §4B.7 的泄漏方向 1（**给对照臂放水**），会高估朴素臂
- 若**因为怕放水而故意不给它任何格式说明**，输出会无法稳定切分——那是做弱

正确的落点是：**给格式说明，不给内容示范**。而「一个称职的实践者手上没有 example」这条判据本身也支持不给。所以省它既不放水也不做弱，它落在两个方向之间的干净空间里。

## 3. `reason` 字段：为实验可分析而给，⛔ 不为公平性而给

〔用户明确裁定 2026-08-12〕「**你也得让模型输出一些 reason 之类的信息，不然到时候对结果进行解释和分类都没法解释了**」「**这个的设置目的不是为了可追踪性，纯粹只是为了让结果到时候变得可以在 paper 里面被解释和分析而已，你得注意边界，不需要可追踪性，只需要能实验分析即可**」。

⛔ **它不构成 C-③ 的证据链能力**，边界如下：

| | C-③ 证据链（⛔ 不给） | `reason`（✅ 给） |
| :-- | :-- | :-- |
| 形态 | 结构化、可机械消费的四段链 | 一段自然语言 |
| 锚定 | 绑定到 `REQ-xxx` 需求条目 ID、`named_elements` 结构化元素表、定位 trace | ⛔ 不锚定任何东西 |
| 用途 | **交付时带着**，供下游自动消费 | 供**我们**做实验分析时读 |
| 提问方式 | 「依据需求的哪一条」 | 「你为什么认为这是问题」 |
| 归因由谁做 | 机制（可逐条自动归因） | ⭐ **人工**（判定者读完自己分类） |

⭐ **分界线是「谁来做归因」，不是「有没有理由」。** 给基线一段散文理由，它的多报仍然要由判定者人工读、人工分类；给它四段链，才是把归因能力送出去。

⭐ **而这个字段是必需的，不是锦上添花**：主臂做了五类多报分类。要对基线的多报做**同口径**分类并并排，判定者必须知道它**为什么**认为那是问题——否则一条多报无法区分它属于「过度规定」、「事实读错」还是「误解需求」，X1 的多报侧就只能给一个总数，与主臂的分类分布无法并列。

⚠️ **成本影响**：`reason` 使基线 output token 上升约 300k（324 格 × 约 5 条 × 约 200 token），仍是主臂 17.2M 的约 1.7%，⛔ 不影响「低配」论证。

## 4. ⛔ 泄漏审查：两个方向都查过

按 §4B.7，泄漏可以往两个方向走，两个都是学术问题。

### 4.1 方向一：给对照臂放水（会高估基线 → 低估我们的优势）

⛔ 本 prompt 与 `Field(description=...)` 中不含以下任何一类：

| 不得含 | 实际检查 |
| :-- | :-- |
| 台账（expected issue）的任何内容、ID、措辞 | 由 [../tests/test_prompt_no_leakage.py](../tests/test_prompt_no_leakage.py) 机械钉住 |
| 19 条谓词的任何名字或其措辞 | 同上 |
| 缺陷类型清单 / 检查清单 / 分类学 | 通读，无 |
| worked example 或任何具体缺陷的示范 | 通读，无（论证见 §2.1） |
| 诱饵对照、「注意检查 X」式引导 | 通读，无 |

⚠️ **审查范围是全部进入模型的文本**，不止这个文件：还包括 `schema.py` 的 `Field(description=...)`（它进 `model_json_schema()`，所以进 prompt）与**运行时生成**的文本（schema 解析失败后的重试反馈）。⛔ 静态 grep prompt 常量抓不到后者，所以重试反馈的措辞单独审查：它只报告 pydantic 的校验错误位置与期望类型，⛔ 不含任何内容引导。

### 4.2 方向二：把对照臂做弱（会低估基线 → 虚高我们的优势，⚠️ 且一旦被审稿人看出来，主臂的数字会被连带否掉）

⛔ 本实现不含以下任何一项：

| 不得有 | 实际状态 |
| :-- | :-- |
| 截断 NL 或模型 | ⛔ 无。全文注入，且 record 里存输入的 sha256 可复核 |
| 压 `max_output_tokens` | ⛔ 无。不显式设置，用 profile 默认（record 里记录该值） |
| 禁止或压缩逐步思考 | ⛔ 无。反而**专门加了** `analysis` 字段提供全局推理落脚点（理由见 §5） |
| 降模型档 | ⛔ 无。与主臂同两个 profile |
| 任务陈述含糊或误导 | ⛔ 无。逐字「identify the places where the model does not conform to the specification」 |
| ⚠️ **保守措辞压召回** | ⛔ 无。**特别警惕过**：诸如 "only report issues you are confident about" / "report at most N" / "be conservative" 这类措辞看起来像合理工程约束，实际会显著压低召回率，属做弱。本 prompt 一个都没有，反而写的是「Report as many or as few issues as you actually find」 |

## 5. `analysis` 字段：推理空间的对等

主臂是八阶段循环，每阶段都有 rationale 字段，推理有大量落脚点。X1 是单次调用；若它必须直接填 `issues` 列表，**跨 issue 的全局比对**（通读需求 → 通读模型 → 逐处对照）就没有落脚点，那会在 §4B.2 的「⛔ 不许禁止它逐步思考」这一栏上形成不对等。

所以 `analysis` 是**可选**字段，存在理由是推理空间对等，⛔ 不是为了分析（那是 `reason` 的职责）。两个字段目的不同，都要。
