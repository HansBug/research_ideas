# `baselines/` 操作规范

本文档用于固定 `project_1_llm_state_machine_modeling/baselines/` 与 [SUMMARY.md](./SUMMARY.md) 的后续维护方式，作为 `project_1` 中 baseline 论文持续收集、整理、比较与回填的统一工作规范。

## 0. 文档关系与使用顺序

`baselines/` 下几个核心文档的职责如下：

1. [README.md](./README.md)
   - 解释论文集定位、纳入/排除标准与单论文目录要求。
   - 是进入本论文集时的首个入口文档。
2. [GUIDE.md](./GUIDE.md)
   - 规定检索、筛选、目录维护、`DESC.md` 生产与 [SUMMARY.md](./SUMMARY.md) 回填规范。
3. [SUMMARY.md](./SUMMARY.md)
   - 记录当前正式收录范围、统计口径、论文清单、数据集/benchmark 盘点、待补充候选与更新日志。
4. [DESC_GUIDE.md](./DESC_GUIDE.md)
   - 规定单篇 `DESC.md` 的写法、章节结构、比较维度和证据要求。

默认推荐顺序如下：

1. 先读 [README.md](./README.md)，理解收录边界。
2. 再读 [GUIDE.md](./GUIDE.md)，确认本轮工作流程。
3. 再读 [SUMMARY.md](./SUMMARY.md)，确认当前总账和待补充缺口。
4. 若任务涉及单篇分析，再读 [DESC_GUIDE.md](./DESC_GUIDE.md)。
5. 最后进入具体论文目录，按 `bibtex.bib -> paper_content.txt -> paper.pdf（必要时） -> DESC.md` 的顺序工作。

## 1. 目标与任务边界

`baselines/` 不是一般性的“相关工作收纳箱”，而是为 `project_1` 建设可反复引用的 LLM 状态机建模 baseline 集合。它主要服务以下任务：

1. 固定“可与本研究横向比较”的论文集。
2. 提取统一可比字段，为后续论文写作和实验设计服务。
3. 沉淀对控制系统状态机建模真正有指导价值的研究观察和空白。
4. 在 LLM 论文稀缺时，允许补充少量**任务定义高度一致**的经典非 LLM 直接前身工作，但必须在 `DESC.md` 与 [SUMMARY.md](./SUMMARY.md) 中显式标明其“经典 baseline/前身 baseline”定位。

以下工作不属于本论文集的主任务，应避免混入：

1. `sources/` 中那类控制系统样本论文的收集与 `STM.md` 提取。
2. 泛形式化方法背景收集、传统方法综述、非 LLM 工具普查。
3. FSM 只作为提示范式、规划控制或多智能体编排机制的论文。
4. 输出不是状态机族模型的论文；这类论文即使暂时保留，也只能按弱相关处理，不能当成主线 baseline。

## 2. 检索策略

### 2.1 主线关键词簇

基于 `BASELINE.md`、`BASELINE_TO_EXPLORE.md`、`DIR_1_llm_direct_state_machine_generation.md` 和 `LITERATURE_SEARCH_RESULTS.md` 的现有经验，后续检索应优先围绕以下主线：

1. `LLM/GPT/ChatGPT/Claude/Gemini` + `state machine/statechart/state diagram/FSM`
2. `requirements` + `statechart/state machine` + `automotive/industrial/control`
3. `LLM` + `model refinement/model completion/model repair` + `state machine/FSM`
4. `multimodal/diagram recognition/vision-language` + `state diagram/FSM`
5. `state machine` + `formal verification/model checking/constraint repair`

### 2.2 检索方向优先级

优先级按以下顺序执行：

1. 直接生成状态机模型的论文。
2. 基于已有状态图/FSM 的精化、扩展、修复、测试生成论文。
3. 泛 UML/SysML 论文只有在明确包含状态机输出时才考虑。
4. 邻近任务论文，例如状态图识别到代码、FSM 推理 benchmark，仅在其方法对本研究有直接借鉴价值时纳入，且默认只能评为 `🟠`。

### 2.3 去偏与跳过规则

为避免把时间耗在低命中方向，后续应主动降权以下候选：

1. `FSM` 仅用于智能体控制、规划或对话流，而非建模工件生成。
2. 纯机器人操作流水线、纯协议推理、纯智能合约生成等与 `project_1` 对比关系较弱的方向。
3. 输出是类图、顺序图、goal model、一般 domain model 等非状态机工件的论文。
4. 纯综述、纯位置论文、纯经验报告，若缺少可比较实验与方法细节。

### 2.4 批量规模与排序 override

本论文集领域相对窄，默认采用以下 override：

1. 每轮实际筛查的候选论文尽量不少于 `12` 篇。
2. 每轮最终正式入库若少于 `2` 篇，需要在 [SUMMARY.md](./SUMMARY.md) 的更新日志中说明原因。
3. 论文清单排序不沿用仓库根级默认年份升序；本论文集按 Project 1 baseline 相关性、任务链条和维护优先级组织，具体写法见 [§6.6](#66-论文清单-的写法)。

## 3. 筛选标准

### 3.1 收录条件

一篇论文进入 `baselines/`，至少应满足以下条件：

1. 论文核心任务与 LLM 建模工件生成、精化、扩展、修复或识别直接相关；
   或者虽然不是 LLM，但任务定义与“需求/设计描述 -> 状态机族模型”高度一致，足以作为经典前身 baseline。
   且目标工件应是状态机族模型，或必须明确说明为何仍值得保留。
2. 输入、输出、方法流程、实验设置和主要结果可从原文稳定提取。
3. 对 `project_1` 的研究设计、baseline 选择或比较维度有明确价值。
4. PDF 原文和 `paper_content.txt` 可获得并质量可用。

### 3.2 降优先级条件

以下论文可暂存为候选，但不应优先入库：

1. 任务更偏代码生成、协议推理或图样识别，只有一部分可迁移到 `project_1`。
2. 输出不是状态机族模型，但方法思路对状态机任务仍有有限借鉴价值。
3. 原文信息不完整，例如公开性、评测细节或输入输出定义不清。

### 3.3 排除条件

以下论文原则上不纳入：

1. 非 LLM 方法，且仅作为背景对比。
2. 不产生可比较建模工件，或 `FSM` 只是内部控制结构。
3. 输出与状态机任务无关的类图、顺序图、目标模型或一般概念模型，且无法证明对 `project_1` 有直接借鉴价值。
4. 只有抽象观点，没有足够实验或方法证据。

### 3.4 去重规则

去重按以下优先级执行：

1. 优先按 DOI 去重。
2. DOI 缺失时按标准化标题去重。
3. 标题存在轻微差异时，再结合作者、年份和会议/期刊综合判断。

### 3.5 BASELINE评估口径

为避免把“相关工作”与“可直接对比 baseline”混在一起，`baselines/` 中每篇正式收录论文都必须给出一个 `BASELINE评估` emoji，统一使用以下口径：

| Emoji | 含义 |
|---|---|
| 🟢 | 直接构成 baseline：输入是自然语言系统设计/描述/需求，允许附带轻量补充规格；输出必须是状态机、Statechart、SysML 状态机或与本研究目标高度等价的状态机族模型，与 `project_1` 的“自然语言自动生成状态机模型”任务直接可比 |
| 🟡 | 相关但非直接 baseline：仍然围绕状态机模型，但输入不是纯自然语言，或任务本质是已有状态机的精化/扩展/修复/测试生成，而非从零建模 |
| 🟠 | 弱相关/可比性有限：输出不是状态机族模型，或任务只是有限状态推理、多模态识别、泛 UML/SysML/goal/domain 建模，只适合补充说明或方法借鉴 |
| ⚪ | 背景资料：只适合当背景文献，不建议纳入 baseline 对比表 |

说明：`⏳` 不是 baseline 强度等级，而是处理状态；它只用于合法 PDF / 全文或 `DESC.md` 暂缺时的阻塞记录。若 `SUMMARY.md` 主表中暂时保留 `⏳` 行，必须排在 completed rows 之后，并且不得计入已完成 `DESC.md` 数。

### 3.6 四条件证据编码口径

从 PR #82 起，[SUMMARY.md](./SUMMARY.md) 的论文清单必须同时维护以下四个 evidence-signal 列，用于把 LLM4MDE 候选的匹配证据拆开审计：

| 条件 | 定义 | 🟢 | 🟡 | 🟠 | ⚪ |
|---|---|---|---|---|---|
| `LLM4Modeling` | 论文核心是否是用 LLM 做建模工件生成 / 抽取 / 精化 / 修复 / 评估 | 核心贡献就是 LLM4Modeling | 建模链路重要但不唯一 | 只作辅助或评估 | 不相关 |
| `NL输入` | 输入是否含自然语言需求、文本描述、user story、访谈 transcript、文档等 | 主输入是 NL | NL + 结构化输入混合 | NL 只作提示/说明 | 无 NL 输入证据 |
| `LLM方法` | LLM 是否是方法核心组件 | LLM 是核心流程组件 | LLM 是重要模块 | LLM 仅辅助 | 无 LLM |
| `STM族输出` | 输出是否是 STM-family 或强状态 / 行为语义模型 | 明确 UML/SysML State Machine / Statechart / FSM / EFSM / LTS / 近同构状态-迁移模型 | Event-B / PAT(CSP#) / symbolic protocol / process/activity / Rebeca actor-based formal model 等强行为近邻 | Simulink block/data-flow slice、领域模型 / use case / 类图 / 目标模型 / 规约等间接相关 | 不满足或未见证据 |

执行规则：

1. `评估` 列是 Project 1 baseline 的综合 verdict；四条件列只是 evidence signals，不得用四条件机械派生或替代 `评估`。
2. 经典非 LLM 前身工作可出现 `评估=🟢/🟡` 且 `LLM4Modeling=⚪`，因为其价值来自任务定义高度一致。
3. LLM4MDE 近邻工作可出现 `STM族输出=🟡` 且 `评估=🟠`，因为强行为近邻不等于 exact STM direct baseline。
4. `STM族输出=🟢` 但 `NL输入=🟠/⚪` 的论文只能说明存在状态机工件信号，不能写成 `NL -> STM` direct baseline。
5. 对 BPMN、Petri net、POWL、UML activity diagram、Rebeca、Simulink slice、SysML UCD/BD consistency 等近邻，必须写清“为何可借鉴”以及“为何不能评为 `🟢` direct STM baseline”。

### 3.7 PDF gate 与 `⏳` 阻塞规则

候选进入正式 completed baseline 计数，必须同时满足以下条件：

1. 有合法可用 PDF 或等价全文原文。
2. 已使用 `tools/pdf_extractor.py` 生成可读 `paper_content.txt`；若 text 模式异常，应切 OCR 或记录失败。
3. 已补齐可用于学术写作的 `bibtex.bib`。
4. 已按 `bibtex.bib -> paper_content.txt -> paper.pdf（必要时）` 的顺序生成 `DESC.md`。
5. `DESC.md` 明确输入、输出、输出模型类型、LLM / agent 设置、反馈/验证机制、数据集/benchmark、代码/数据获取方式，以及与 Project 1 的 direct / near / related-work 关系。

若 PDF gate 未通过：

1. 不生成 `paper.pdf`、`paper_content.txt`、`DESC.md`，也不计入 completed `DESC.md` 数。
2. 只允许在“待补候选/阻塞记录”中保留最小信息，如标题、来源、当前价值、阻塞原因和下一步获取路径。
3. 不得用 CSV 初筛、网页摘要、issue 表格或搜索结果直接写最终四条件；只能写“CSV 初筛信号，待 PDF 精读确认”。
4. `needs_pdf`、`⏳` 或“待补”都是处理状态，不是 baseline 强度，不得冒充 `🟢/🟡/🟠/⚪` 结论。

### 3.8 #81 LLM4MDE seed-source 使用边界

Issue #81 的 CSV / 表格 / 评论适合做候选入口，但不能替代论文精读。后续从 #81 或类似批量 census 中导入候选时，必须遵守：

1. 明确本轮处理集合来自哪一个评论、小节或筛选子集，避免把 228 篇全量、70 篇 high-fit 与少量优先精读候选混为一谈。
2. 对已入库条目只更新总账字段，不重复建目录、不改 slug，避免反向链接失效。
3. 对新候选先做 PDF gate；gate 未通过者只列入待补，不进入主表 completed rows。
4. CSV 初筛的四条件只能作为检索排序线索；最终 `评估` 与四条件必须来自论文全文、artifact、publisher/DOI 或作者提供材料。
5. 若本轮发现“初筛信号很强但全文不可得”的坑，必须把阻塞原因和后续获取策略回写到 [SUMMARY.md](./SUMMARY.md) 的待补候选或更新日志，并在必要时补充本 [GUIDE.md](./GUIDE.md)。

## 4. 目录与文件规范

`baselines/` 下每篇论文必须独占一个子目录。目录名应保持简洁、稳定、可读，通常用标题关键词或已有 slug。

每个单论文目录至少应包含：

1. `paper.pdf`
2. `paper_content.txt`
3. `bibtex.bib`
4. `DESC.md`

若论文在 [SUMMARY.md](./SUMMARY.md) 的“直接 baseline：评估与四条件五绿”表中同时满足 `评估=🟢` 且 `LLM4Modeling / NL输入 / LLM方法 / STM族输出` 四条件全部为 `🟢`，则该单论文目录还必须包含：

5. `ASSETS.md`

其中：

1. `paper_content.txt` 必须由 PDF 自动提取获得。
2. `DESC.md` 是本论文集的核心派生文件，统一遵循 [DESC_GUIDE.md](./DESC_GUIDE.md)。
3. `ASSETS.md` 是五绿 direct baseline 的资源与复现实验资产清单，只对这类最高优先级直接 baseline 强制要求；其他论文可在确有公开 artifact 时自愿补充，但不得把“有无 `ASSETS.md`”误解为 baseline 强度。
4. 若目录中已有代码仓库、数据集链接或补充材料信息，应优先写入 `DESC.md`；若该论文属于五绿 direct baseline，还必须同步写入 `ASSETS.md`，不能只留在零散笔记里。

## 5. 内容整理策略

### 5.1 单篇论文需要提取什么

每篇 baseline 的 `DESC.md` 至少应抽取以下可比较信息：

1. 输入工件、输入形态和输入模态。
2. 输出工件、输出模型类型和最终产物形态。
3. 所用 LLM、提示工程、反馈机制、验证或修复闭环。
4. 数据集/benchmark 来源、规模、构造方式、开放性。
5. 主要实验结果、局限性和与 `project_1` 的关系。
6. `BASELINE评估` emoji 与评估理由。

这里必须明确区分：

1. 输入是否是纯自然语言。
2. 若不是，额外输入到底是已有模型、图像、代码、约束、标准文档还是其他工件。
3. 输出到底是状态机模型、状态图代码、状态图图像识别结果、代码/测试工件，还是其他非状态机工件。
4. 若输出不是状态机族模型，必须明确说明它为何仍被保留，以及为什么不能评为 `🟢`。

### 5.2 必须进入汇总表的字段

后续写 [SUMMARY.md](./SUMMARY.md) 的论文总表时，每篇论文必须至少包含以下列：

1. `BASELINE评估`
2. `LLM4Modeling`
3. `NL输入`
4. `LLM方法`
5. `STM族输出`
6. `类别`
7. `标题`
8. `年份`
9. `输入`
10. `输出`
11. `输出模型类型`
12. `使用的LLM`
13. `主要方法`
14. `需求词工程`
15. `运行仿真`
16. `形式化验证`
17. `目录`

其中：

1. `输入` 不得只写“文本”或“模型”，要尽量写清是“自然语言需求”“自然语言 + I/O 规格”“初始 FSM + 约束”“状态图图像”等。
2. `输出` 不得只写“模型”，要尽量写清是“SysML 状态机”“Mermaid Statechart”“Umple 状态机”“SystemVerilog FSM 代码”“扩展状态图 + 测试用例”等；若不是状态机工件，也必须直说。
3. `主要方法` 只用一句话概括核心 pipeline，避免写成长段。
4. 四条件列必须只写单个 emoji，不在单元格里重复中文解释；中文解释统一放在口径说明中。
5. `需求词工程 / 运行仿真 / 形式化验证` 三列按“程度｜技术｜角色”填写，不能把普通 prompt 或语法检查夸大成高强度 formal verification。

### 5.3 数据集/benchmark 汇总表字段

后续 [SUMMARY.md](./SUMMARY.md) 中还必须维护单独的“数据集与 benchmark 清单”表。每条至少包含：

1. `论文`
2. `BASELINE评估`
3. `数据集/Benchmark`
4. `来源类型`
5. `制作方法`
6. `输入`
7. `输出`
8. `规模`
9. `可获取性`
10. `获取方式/链接`
11. `简述来源`

其中：

1. `可获取性` 统一只用 emoji 表示，不写自由文本，固定口径如下：

| Emoji | 含义 |
|---|---|
| 🟢 | 可直接获取：论文给出了可直接下载、浏览或通过清晰公开渠道直接取得完整内容的链接/入口 |
| 🟡 | 需联系申请：论文明确说明需要联系作者团队、项目方或维护方申请获取 |
| 🟠 | 信息不清：论文只提到制作方式、来源或使用过该数据，但没有给出足够清晰的获取路径 |
| 🔒 | 难以取得：数据依赖企业/团队内部资料、付费标准、受限工业资产或其他现实上很难取得的来源 |

2. 这四类不是偏序等级，不应用“比谁更开放”去硬排；它们只是四种不同的获取状态。
3. `获取方式/链接` 一列只要原文或作者工件中存在明确 URL，就必须写成 Markdown 链接。
4. 若只有仓库、Zenodo、项目页、补充材料页等间接入口，也应优先给出该入口链接，而不是只写“见 DESC”。
5. 若没有清晰链接，必须明确写“原文未提供公开下载链接”或等价表述，不能留空。

### 5.3.1 五绿 direct baseline 的 `ASSETS.md` 资产记录

五绿 direct baseline 是后续 Project 1 对比实验最可能真正复用的对象。凡进入 [SUMMARY.md](./SUMMARY.md) 第一张表的论文，必须额外维护 `ASSETS.md`，并按“可复现实验资产”而不是普通论文摘要来写。

`ASSETS.md` 至少包含以下信息：

1. 论文入口、DOI / arXiv / publisher page、本地 PDF 路径。
2. Venue 与 CCF 口径；CCF 列沿用 `ccf_venues` 的 `🏆 / 🥈 / 🥉 / ⚪ / ❓` 口径。
3. 实验代码 URL 与状态，必须区分：
   - 公开可运行代码。
   - paper-specific artifact repo。
   - 只有 README / 占位符的仓库壳。
   - 相关工具链仓库但非论文专属代码。
   - 原文未提供或未找到。
4. 实验结果细则 URL 与状态，必须区分：
   - 可下载 workbook / CSV / ODS / JSON / parquet / raw output。
   - 仓库内零散结果文件。
   - 只有论文内表格。
   - 无结果细则。
5. 数据集 / benchmark URL 与状态，必须区分：
   - 公开可下载标注数据 / ground truth。
   - 公开输入文档但无 ground truth。
   - 作者内部 / 工业私有数据。
   - 可从标准、手册或公开示例重建但未打包的样本。
   - 未公开。
6. Artifact / replication package URL 与状态，说明是否足以支撑端到端复现实验。
7. 仓库或数据集的大体结构说明，例如主要目录、输入文件、输出模型、结果表和可运行入口。
8. 对 Project 1 对比实验的可用性判断：可直接用、需重建、只适合方法论参考、或暂不可用。
9. 非 GitHub 资源深挖结果：publisher supplementary / download tab、arXiv ancillary、DOI landing page、Zenodo / OSF / Figshare、Google Drive、学校 repository metadata、匿名 artifact、项目主页、README 内 zip / release / raw 文件、作者声明的申请路径等。
10. 可复查快照：核验日期、GitHub default branch / HEAD commit、raw 文件 ETag 或 content-length、本地冻结派生物路径与 hash、访问失败状态码或 WAF / 权限异常。
11. 风险与待复查项：访问异常、匿名评审 artifact、WAF/权限、provider drift、版本漂移、license 不明、工业数据不可公开等。

执行要求：

1. `ASSETS.md` 中的外部事实必须给出可点击 URL；访问失败也要给出入口 URL 和失败状态。
2. 不得把“公开输入文档”写成“公开 benchmark”，除非 ground truth / expected output 同时公开。
3. 不得把“论文内表格”写成“可下载结果细则”；可下载结果必须有独立文件、仓库路径或本地冻结派生物。
4. 不得把“相关工具仓库”写成“论文专属代码”；例如工具链公开但 thesis pipeline 未公开时，必须显式说明。
5. 若本仓库已把公开数据解析成 parquet / JSONL / CSV 等冻结派生物，应在 `ASSETS.md` 同时链接原始公开入口和本地派生物路径，并说明派生时间、来源、行数和 hash。
6. 在写“未发现公开代码 / 数据 / 结果”之前，必须先完成非 GitHub 深挖：至少检查论文 PDF 与 `paper_content.txt` 中的 `artifact / supplementary / code / data / repository / GitHub / Zenodo / OSF / Figshare / Drive / contact / email` 等线索，检查 publisher / arXiv / DOI / 学校 repository 页面是否有附件、download tab、source package、supplementary package 或 ancillary file，并检查项目页、匿名 artifact、仓库 release / zip / raw 结果文件。
7. 对所有可下载资源不得只停留在“页面可达”：若是 zip / xlsx / ods / csv / json / parquet / source tarball / supplementary PDF / Drive 文件夹 / publisher download package，应尽量列出实际文件名、文件角色、是否包含实验代码、逐样本输出、prompt、评分细则、ground truth 或脚本；若无法逐文件打开，应明确写“入口可达但未逐文件审计”，不能把入口可达升级为代码或数据已核验。
8. 邮件 / 申请路径必须保守处理：只有原文、artifact、仓库 README、publisher 页面或数据可用性声明明确给出 `available on request`、`contact us`、数据申请表、artifact contact、作者邮箱等正式渠道时，才把“可邮件 / 可申请”写成建议动作，并且只顺着该渠道联系。若只是“没有公开”但没有明确申请渠道，必须写“未提供公开申请入口，先放着 / 不主动打扰”，不得擅自从学校主页、LinkedIn、社交媒体或其他非原文渠道外扩打扰。论文首页作者邮箱可作为正式论文联系渠道记录，但不等于所有未公开数据都应主动索取；只有复现实验确实需要且没有公开替代时才使用。
9. 对 GitHub 或其他活仓库，不得只写 URL；若它影响复现实验，应记录 default branch、HEAD commit、license / release / dependency lock 状态和主要目录。对 Google Drive / 匿名 artifact 这类入口，只能把 HTTP 可达写成“入口可达”，不能据此宣称逐文件下载已审计。
10. [SUMMARY.md](./SUMMARY.md) 的五绿 direct baseline 表只保留紧凑资源列；完整资源说明以对应 `ASSETS.md` 为准，避免 [SUMMARY.md](./SUMMARY.md) 成为第二事实真源。
11. 对 Anonymous Github / 4open 这类匿名 artifact，必须优先寻找可由浏览器直接访问的前端入口；若平台使用 `#!/r/<repo>/...` hashbang 路由，应把该路由作为人类浏览主入口。普通 `/r/<repo>/...` 或 `/repository/<repo>/...` 若重定向到 `/api/repo/...` 并返回 `401 not_connected`，不能直接判定 artifact 不存在，只能记录为入口踩坑。
12. 对 Anonymous Github / 4open 这类匿名 artifact，资源记录应区分三类 URL：浏览器入口用于人工复核，`/api/repo/<repo>/file/...` 与 `/files/?path=...` 用于 raw 文件 / 目录 fallback，`/api/repo/<repo>/zip` 用于正式冻结。冻结时不要只依赖整包 ZIP SHA-256，因为 ZIP 元数据可能让整包 hash 随请求变化；应优先保存文件清单、关键文件大小和逐文件 hash。

### 5.4 什么内容进入 `DESC.md`

应写入 `DESC.md` 的内容：

1. 对单篇论文本身可追溯的事实和分析。
2. 后续论文写作时需要直接引用的关键信息。
3. 原文支持的相关工作脉络与论文定位。

不应塞进 `DESC.md` 的内容：

1. 纯粹跨论文的关键词簇经验。
2. 大量尚未核实的候选论文名单。
3. 只有 collection 维度才有意义的统计和宏观观察。

这些内容应进入 [SUMMARY.md](./SUMMARY.md)。

### 5.5 `DESC.md` 写作硬约束

虽然单篇写法的详细模板由 [DESC_GUIDE.md](./DESC_GUIDE.md) 规定，但本 collection 还额外固定以下硬约束；后续生成或重写任何 `DESC.md` 时都必须满足。

先决阅读顺序固定为：

1. 先读 `bibtex.bib`，确认标题、作者、年份、会议/期刊、DOI、链接等元信息。
2. 再尽可能完整阅读 `paper_content.txt`，至少覆盖摘要、引言、方法、实验/案例、结论、相关工作/参考文献。
3. 只有在提取文本存在歧义、图表缺失、公式断裂或版式问题时，才回到 `paper.pdf` 核对。

禁止的做法包括：

1. 只看标题、摘要或关键词就直接写 `DESC.md`。
2. 只在 `paper_content.txt` 中搜索几个命中词后就跳过其余正文。
3. 不读取 `bibtex.bib`，直接凭 PDF 首页手动拼元信息。
4. 没有生成 `paper_content.txt` 就直接从 PDF 零散摘录。

### 5.6 `DESC.md` 必备章节与信息

每篇 `DESC.md` 至少应包含以下部分，并与 [DESC_GUIDE.md](./DESC_GUIDE.md) 的固定顺序保持一致：

1. `基本信息`
2. `简报`
3. `研究问题与动机`
4. `核心方法`
5. `实验与评估`
6. `与本研究的关系`
7. `重要的相关工作`
8. `文献分类总结`

其中有几项是本 collection 的硬要求：

1. `基本信息` 中除了常规元信息，还必须明确写出：
   - 代码/仓库获取方式。
   - 数据集获取方式。
   - 若原文未提供公开入口，必须如实写“原文未提供公开代码/数据集获取链接”，并补充当前可行获取方式。
2. `简报` 必须紧跟在 `基本信息` 之后，必须回答五个问题：
   - 解决的问题。
   - 研究动机。
   - 方法创新。
   - 实验设计。
   - 结论与不足。
3. `简报` 中的“解决的问题”必须同时说清输入、方法、输出，并附字符示意图，展示 `输入层 -> 方法层 -> 输出层` 的完整黑箱流程。
4. `与本研究的关系` 中必须给出该论文的 `BASELINE评估` emoji，并解释为什么属于该类。
5. `实验与评估` 中若出现数据集、benchmark、代码仓库、补充材料链接，必须与 [SUMMARY.md](./SUMMARY.md) 的汇总口径保持一致。

### 5.7 `重要的相关工作` 的分类提取规则

`重要的相关工作` 是 `DESC.md` 中的核心章节，必须从论文原文的 related work、方法、实验和 references 中提取，不能编造或凭印象补齐。

统一按以下五类组织：

1. `重要的前身类工作`
   - 本论文明确基于其继续发展、扩展或改进的工作。
   - 包括作者团队自己的前期工作，也包括原文明说 `build upon / based on / extending / improving upon / inspired by` 的外部工作。
2. `直接参与实验的 baseline`
   - 在实验中被明确当作 baseline 或对比对象，并出现具体结果对照。
3. `提供了重要论证的工作`
   - 用于支撑研究动机、问题定义、现有不足或研究必要性的工作。
4. `在技术上提供了支持的工作`
   - 被论文直接采用、受其启发或作为技术组成部分使用的方法、框架、模型、工具。
5. `其他重要工作`
   - 提供背景知识、理论基础、评估方法或标准支撑，但不直接参与本论文的方法或实验。

每条相关工作至少要写清：

1. 基本信息：作者、年份、标题、会议/期刊。
2. 主要内容：研究对象、方法、关键特点。
3. 原文中的引用证据：章节、表格或尽可能具体的行号/位置。
4. 主要发现或局限性：只在原文有依据时填写。
5. 与本论文的关系：说明它在本论文里扮演什么角色。
6. 佐证内容/技术使用/作用：按所属类别说明它如何支撑当前论文。

编写要求固定如下：

1. 必须基于原文，不能编造未出现的关系或评价。
2. 分类按“在本论文中实际起到的作用”判定，而不是按我们主观觉得它重要。
3. 若同一篇文献横跨多个类别，应在主类别详细写，在其他类别简短交叉引用，避免重复。
4. 第 1-4 类通常详细写，第 5 类可相对简写，但仍要保留可追溯证据。
5. 所有内容统一用中文写，保持客观、准确、可回溯。

## 6. `SUMMARY.md` 撰写规范

[SUMMARY.md](./SUMMARY.md) 必须稳定维护以下章节：

1. 文档定位与使用方式。
2. 当前收录统计。
3. `BASELINE评估` emoji 口径。
4. 检索关键词簇。
5. 论文清单。
6. 数据集与 benchmark 清单。
7. 初步归类/覆盖盘点。
8. 待补充候选或必要阻塞。
9. 更新日志。

### 6.1 章节顺序与标题固定

后续维护 [SUMMARY.md](./SUMMARY.md) 时，默认应尽量保持与当前版本一致的章节顺序，不随每轮工作任意改名或重排。推荐固定为：

1. 文档定位说明 + 推荐使用顺序。
2. `## 当前收录统计`
3. `## BASELINE评估口径`
4. `## 检索关键词簇`
5. `## 论文清单`
6. `## 数据集与 Benchmark 清单`
7. `## 初步归类与覆盖盘点`
8. `## 待补充高优先级候选`
9. `## 更新日志`

其中：

1. 若未来确有必要新增章节，应优先插入到相邻语义区块中，而不是打乱上述主骨架。
2. 除非 collection 目标发生明显变化，否则不建议把“论文清单”和“数据集与 Benchmark 清单”拆成多套并列表。
3. “待补充高优先级候选”可以按实际情况改为“待补充候选/阻塞记录”，但应保持它位于“覆盖盘点”之后、“更新日志”之前。

### 6.2 开头说明的写法

`SUMMARY.md` 开头不应只是标题，建议保持如下功能：

1. 用一小段说明本文件是该 collection 的总账。
2. 明确它负责记录哪些内容，例如 baseline 论文、比较口径、数据集/benchmark 盘点、待补充候选和更新日志。
3. 紧接着给出推荐使用顺序，至少包含：
   - 先读 [README.md](./README.md)
   - 再读 [GUIDE.md](./GUIDE.md)
   - 再读本文件
   - 如需重写单篇分析，再读 [DESC_GUIDE.md](./DESC_GUIDE.md)

### 6.3 当前收录统计的写法

`## 当前收录统计` 默认使用短列表，不写成长段。至少应包含：

1. 已收录 baseline 论文数。
2. 本轮新增论文数。
3. 已完成 `DESC.md` 数。
4. `⏳ 尚未提取` 数。
5. 若本轮有命名规范化、字段口径变更、结构调整等维护动作，可加一条“本轮规范化工作”。

统计规则如下：

1. 所有数字必须与当前目录和表格真实内容一致。
2. 如果本轮没有新增论文，但进行了结构整理，也应如实写 `0`，不要省略。
3. `DESC.md` 的数量应按当前目录中已完成且正式入账的单篇分析计算。

### 6.4 `BASELINE评估口径` 的写法

`## BASELINE评估口径` 默认使用 emoji 对照表，不改成自然段说明。表格至少包含两列：

1. `Emoji`
2. `含义`

要求如下：

1. 与第 `3.5` 节完全保持一致，不允许在 [SUMMARY.md](./SUMMARY.md) 内另发明一套不同定义。
2. 这里写的是“collection 级比较口径”，不在这一节夹带单篇论文评价。

### 6.5 `检索关键词簇` 的写法

`## 检索关键词簇` 默认拆成以下四个三级小节：

1. `### 当前推荐关键词簇`
2. `### 已观察到的高命中特征`
3. `### 已观察到的低命中特征`
4. `### 检索倾向调整`

写法要求如下：

1. 每个小节优先使用短 bullet 列表。
2. 每节原则上不超过 `10` 行，只保留当前最有指导意义的经验。
3. 更新方式应是整合改写，不是每轮机械追加旧观察。
4. 关键词簇要偏向可执行检索语义，如“模型名/任务词/领域词”的组合，而不是零碎长句。
5. 这里必须按“压缩式维护”执行，而不是“日志式累积”执行；后续回写时，默认应先删除、合并、替换旧观察，再决定是否保留极少数仍然有效的要点。
6. 只要某条关键词经验没有持续命中价值，或只是某一轮偶然命中的细碎词、长查询、网站名、作者名、临时检索绕路，就应直接删掉，而不是继续堆在 `SUMMARY.md` 里。
7. 如果某一小节已经接近 `10` 行，默认动作不是放宽长度，而是继续压缩、归并和淘汰旧项；除非存在极强的 collection 级理由，否则不要 override 这一限制。
8. 任何把关键词簇小节写成“逐轮追加的检索日志”“命中记录流水账”“候选词仓库”的做法，都视为不符合本 collection 规范。

### 6.6 `论文清单` 的写法

`## 论文清单` 必须使用统一表格，不应在表格外再额外维护一套重复清单。固定列顺序如下：

1. `#`
2. `评估`
3. `LLM4Modeling`
4. `NL输入`
5. `LLM方法`
6. `STM族输出`
7. `类别`
8. `标题`
9. `年份`
10. `输入`
11. `输出`
12. `输出模型类型`
13. `使用的LLM`
14. `主要方法`
15. `需求词工程`
16. `运行仿真`
17. `形式化验证`
18. `目录`

表格写法要求如下：

1. `评估` 列直接使用 emoji，不重复文字标签。
2. `类别` 是 collection 内部工作类型，如“直接生成”“精化/修复”“泛建模”“多模态邻近”等；其中“直接生成”默认只用于状态机族模型。
3. `标题` 用论文原始英文标题，不在表格中额外塞入中文译名。
4. `年份` 统一用纯年份数字。
5. `目录` 必须链接到对应单论文目录，而不是只写 slug 文本。
6. `目录` 列统一使用显示文本 `paper`，链接目标写对应单论文目录（形如 `./slug/`），不要直接显示子目录名。
7. 一篇论文在表里只出现一次；不要按“本轮新增”“历史论文”拆成多张正式表。
8. `#` 是当前排序视图编号，不作为稳定引用 ID；重排后应重新连续编号。
9. 论文清单排序固定为：`评估rank(🟢, 🟡, 🟠, ⚪, ⏳) -> 年份降序 -> STM族输出rank -> NL输入rank -> LLM4Modelingrank -> LLM方法rank -> 标题升序`。
10. `⏳` 只作为处理状态排在 completed rows 之后，不与 `🟢/🟡/🟠/⚪` 共享 baseline 强度语义。
11. 若某篇论文的四条件与 `评估` 看起来不一致，应优先补充说明，而不是强行把颜色调成一致；例如非 LLM 经典 direct baseline、BPMN/Petri 近邻、已有状态图到形式模型转换都允许出现这种差异。
12. “直接 baseline：评估与四条件五绿”表是第 5.3.1 节所述资源资产的总入口，除上述默认列外，必须在 `年份` 后追加 `Venue / CCF`、`论文链接`、`实验代码`、`实验结果`、`数据集 / Benchmark`、`资源说明` 六列；其他三张论文清单表维持默认列，避免表格过宽。
13. 五绿 direct baseline 表的 `资源说明` 列必须链接到对应单论文目录的 `ASSETS.md`；若该文件缺失，应视为本论文集的 I 级维护问题。

### 6.7 `数据集与 Benchmark 清单` 的写法

`## 数据集与 Benchmark 清单` 应保持两层结构：

1. 先给 `### 数据集可获取性口径`
2. 再给正式的数据集表

`### 数据集可获取性口径` 默认使用 emoji 对照表，字段至少为：

1. `Emoji`
2. `含义`

正式数据集表的固定列顺序如下：

1. `#`
2. `论文`
3. `评估`
4. `数据集/Benchmark`
5. `来源类型`
6. `制作方法`
7. `输入`
8. `输出`
9. `规模`
10. `可获取性`
11. `获取方式/链接`
12. `简述来源`

表格写法要求如下：

1. `可获取性` 只写 emoji，定义与第 `5.3` 节一致。
2. `获取方式/链接` 只要存在明确 URL，就必须写成 Markdown 链接。
3. 若只有间接入口，例如 GitHub、Zenodo、项目主页、演示视频，也应写出该入口。
4. 若无公开入口，应明确写“原文未提供公开下载链接”或等价表述。
5. 本表的 `#` 必须与“论文清单”中的 `#` 严格一一对应，保持单篇论文一行。
6. `论文` 列统一使用显示文本 `paper`，链接目标写对应单论文目录（形如 `./slug/`），不再显示 slug 文本。
7. 若一篇论文涉及多个数据集、benchmark 或案例来源，应合并写入同一行的对应单元格，而不是拆成多行。
8. 若论文没有单独数据集，但有实验案例集、公开工件或标准裁剪样本，也应如实入表，而不是因为“不像标准 benchmark”就漏掉。

### 6.8 `初步归类与覆盖盘点` 的写法

`## 初步归类与覆盖盘点` 默认至少包含以下内容：

1. `### 类别分布`
2. `### BASELINE评估分布`
3. `### 当前最有价值的整体观察`

写法要求如下：

1. `类别分布` 和 `BASELINE评估分布` 优先用三列表格：类别/评估、篇数、说明。
2. `当前最有价值的整体观察` 优先用编号列表，控制在 `3-6` 条。
3. 这里写的是跨论文观察，不重复单篇摘要。
4. 若某个观察直接依赖数据开放性、输入模态、输出模型类型等汇总特征，应确保能从上面的表中追溯出来。

### 6.9 `待补充高优先级候选` 的写法

`## 待补充高优先级候选` 用于记录已经在历史工作中出现、但尚未正式收录的高价值候选。默认表格字段为：

1. `优先级`
2. `标题`
3. `来源文档`
4. `当前价值`

写法要求如下：

1. `来源文档` 应尽量指向当前仓库内已经出现该候选的历史文档来源。
2. `当前价值` 要说明为什么值得补入，而且应优先围绕状态机任务本身，不要再把非状态机方向当高优先级主线。
3. 这里记录的是待正式收录对象，不是随手堆放的大候选池；数量应保持克制。
4. 因 PDF gate 未通过而保留的候选，必须写清“已尝试过的获取入口”“失败原因”“下一步可行获取路径”，不得把它们塞进 completed 主表。
5. 若后续获得合法 PDF，应先补齐四件套，再从待补候选移入主表，并同步更新统计、数据集表和更新日志。

### 6.10 `更新日志` 的写法

`## 更新日志` 默认使用三列表格：

1. `时间`
2. `更新内容`
3. `说明`

写法要求如下：

1. 时间统一写 `yyyy-mm-dd hh:mm:ss`，保留到秒。
2. 更新日志必须按时间降序排列；新记录插入表格顶部，方便读者第一眼看到最近修改。
3. 一行只记录一类相对完整的动作，不要把过细碎的命令级操作逐条入账。
4. 若某轮工作既有新增论文，也有结构调整，可以拆成多行记录，但仍按每行时间降序组织。
5. 若一轮检索收获很少或存在失败/阻塞，应在说明列里简明写出原因。
6. 若从踩坑中产生新的可复用纪律，例如 PDF gate、CSV 初筛不能替代精读、DOI 尚未激活、artifact 入口需复核等，应同步回写到本 [GUIDE.md](./GUIDE.md) 的相应规则，而不只写在一次性 PR comment 里。

维护要求如下：

1. “当前推荐关键词簇”“高命中特征”“低命中特征”“检索倾向调整”四个小节默认每节不超过 `10` 行。
2. 关键词簇相关小节必须优先做压缩式重写，不允许因为新一轮检索就机械累加旧 bullet；若发现内容在膨胀，必须主动删减到只剩当前最有效的核心模式。
3. 论文清单必须使用第 5.2 / 6.6 节规定的固定字段，不因每轮新增而换列口径；若 PR body 明确升级 schema，应同步更新本 [GUIDE.md](./GUIDE.md)。
4. 数据集与 benchmark 清单必须使用第 5.3 节规定的固定字段。
5. 统计数字必须与当前表格真实内容一致。
6. 已正式入库但尚未完成 `DESC.md` 的论文必须显式标为 `⏳ 尚未提取`。
7. 如果 [SUMMARY.md](./SUMMARY.md) 当前版本已经形成了更细的稳定写法，后续原则上应向当前版本收敛，而不是重新发明结构。

### 6.11 四条件与 PDF gate dry-run 样例

后续遇到 LLM4MDE 候选时，至少按以下样例先做 dry-run，再决定是否正式入库：

1. `modeling-like-peeling-an-onion`
   - gate：用户于 2026-06-08 提供本地原文 PDF，已提取 `paper_content.txt`，因此可从 `⏳` 转为 completed。
   - 编码：`评估=🟠`，`LLM4Modeling=🟢`，`NL输入=🟢`，`LLM方法=🟢`，`STM族输出=🟡`。
   - 理由：输入和 LLM 方法高度贴近 Project 1，但输出是 UML activity diagram / PlantUML activity diagram，不是 exact STM。
2. #81 ID 14 `Model-based test execution from high-level natural language instructions using GPT-4`
   - gate：若只有 Springer 页面或摘要、PDF 需购买/权限，则不得生成四件套，不得写最终四条件。
   - 记录：只写入待补候选，说明“CSV 初筛信号强，待合法 PDF 精读确认”。
3. #81 ID 9 `UML State Diagrams to Rebeca`
   - gate：PDF 和可读文本可得时可入库。
   - 编码：可为 `评估=🟠`，`LLM4Modeling=🟢`，`NL输入=🟠`，`LLM方法=🟢`，`STM族输出=🟡`。
   - 理由：它处理已有 UML state diagrams 到 Rebeca actor-based formal model 的转换，不是自然语言需求到状态机；Rebeca 是强行为近邻和形式验证模型，但不是 STM-family 近同构输出。
4. #81 ID 17 `Automated Generation of BPMN Processes from Textual Requirements`
   - gate：PDF 和可读文本可得时可入库。
   - 编码：可为 `评估=🟠`，`LLM4Modeling=🟢`，`NL输入=🟢`，`LLM方法=🟢`，`STM族输出=🟡`。
   - 理由：`NL -> BPMN` 是强行为近邻，但 BPMN/process model 不是 Project 1 的 exact STM 输出。
5. #81 `Requirements-Driven Slicing of Simulink Models using LLMs`
   - gate：PDF 和可读文本可得时可入库。
   - 编码：可为 `评估=🟠`，`LLM4Modeling=🟢`，`NL输入=🟢`，`LLM方法=🟢`，`STM族输出=🟠`。
   - 理由：它由自然语言需求驱动定位 Simulink block，并输出 Simulink block/data-flow slice；该输出不是 Stateflow、状态机或强行为近邻，只能作为模型理解 / trace / slicing 支撑证据。

这些 dry-run 的作用是防止两类常见错误：一是把 CSV 初筛当成全文终审；二是把 BPMN、Petri、POWL、Activity、Rebeca、Simulink、SysML UCD/BD 等近邻工件误标为 direct STM baseline。

## 7. 工作流程

一轮完整工作默认按以下顺序执行：

1. 先读 [README.md](./README.md)、[GUIDE.md](./GUIDE.md)、[SUMMARY.md](./SUMMARY.md)。
2. 先补历史欠账，优先修复缺失 `DESC.md`、命名不一致、表格未回填等问题。
3. 再进行候选检索与筛选，并明确 seed-source、候选集合和去重依据。
4. 对候选先执行 PDF gate；未通过者只入待补候选/阻塞记录，不生成 `DESC.md`。
5. 对确认收录的论文建立或补齐 `paper.pdf`、`paper_content.txt`、`bibtex.bib`。
6. 按 [DESC_GUIDE.md](./DESC_GUIDE.md) 完成 `DESC.md`。
7. 最后统一回写 [SUMMARY.md](./SUMMARY.md)，包括论文主表、数据集表、统计、待补候选和更新日志。

一轮结束前必须做以下一致性检查：

1. 目录中文件是否齐全。
2. `SUMMARY.md` 的论文数与实际目录数是否一致。
3. `BASELINE评估`、类别标签和统计数字是否一致。
4. 数据集表是否与论文总表口径一致。
5. 关键词簇是否仍保持简洁有效，没有变成冗长检索日志、历史追加清单或机械累积的关键词仓库。
6. 论文主表是否按 `评估 -> 年份降序 -> 四条件 tie-break -> 标题` 排序，编号是否连续。
7. 四条件列是否全部为单个 emoji，且是否与 `DESC.md` 中的证据说明一致。
8. 更新日志是否按 `yyyy-mm-dd hh:mm:ss` 降序排列。

## 8. 质量与可追溯性要求

后续维护时，以下要求必须满足：

1. 所有结论、数字、标签和分类都应能回溯到原文。
2. 若原文未提供代码、数据集、benchmark 链接，必须如实标注“未提供”，不能臆测补齐。
3. 若某篇论文与 `project_1` 的关系较弱，但仍决定收录，需在 `DESC.md` 和 [SUMMARY.md](./SUMMARY.md) 中明确说明“为何仍保留”。
4. 对 PDF 暂缺、DOI 尚未激活、artifact 入口只由原文声明但未逐文件复核等情况，必须显式保留不确定性，不得为了让表格完整而伪造公开来源或复现能力。
5. 每次踩坑后若形成稳定规则，应优先沉淀到本 [GUIDE.md](./GUIDE.md)，让后续 agent 能复用；不要只把经验留在临时 PR 评论、聊天记录或本地脚本里。

## 9. 与 `DESC_GUIDE.md` 的关系

只要任务涉及单篇 `DESC.md`，必须再读 [DESC_GUIDE.md](./DESC_GUIDE.md)。

冲突处理规则如下：

1. collection 边界、目录回填和汇总口径，以 [GUIDE.md](./GUIDE.md) 为准。
2. 单篇 `DESC.md` 的章节结构、写法和证据要求，以本文件第 `5.5-5.7` 节和 [DESC_GUIDE.md](./DESC_GUIDE.md) 共同为准。
