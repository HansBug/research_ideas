# 主支路交通灯 FPGA 控制分析 / Traffic Light Controller System Analysis Based on FPGA

## 论文在讲什么

这篇论文讨论的是一个基于 FPGA 的交叉口交通灯控制系统。作者并不是只给一个固定周期的灯色轮转，而是把主路、支路、应急车辆、无车道空置和高峰时段这些工况都压进同一套控制器里，用 Verilog 和 Quartus II 做模块化实现、仿真和板级验证。

文中把系统拆成状态机模块、计时模块和交通灯输出模块三块来写。这样读起来很直接：先看到这个路口要面对哪些 traffic scenarios，再看到 `S1-S4` 四个状态如何切换，最后才是 `mcount / scount` 倒计时和数码管显示这些工程实现细节。

## 控制系统在文中的位置

这里的控制系统就是论文主体，不是外围案例。论文第二章先定义了四种运行场景，第四章再把状态机转移逻辑、倒计时逻辑和灯色输出逻辑逐块展开，说明这是一个典型的“控制逻辑先行、硬件实现跟进”的控制器设计文。

对我们最有价值的部分在于，它不是只有“主路绿、支路红”这种薄流程，而是明确给出 `urgent_m / urgent_s`、`mhas_car / shas_car`、`mcount / scount` 这些 guard 和状态变量，说明在什么条件下保持现态、提早切换、进入黄灯、进入对向绿灯。这让它比很多单纯展示波形图的 FPGA 交通灯短文更适合整理成 `STM.md`。

## 对我们为什么有用

这篇论文补的是一个比较标准、但细节足够厚的 `EFSM + T1` 交通灯样本。当前库里虽然已经有不少 traffic light controller，但很多样本只覆盖普通相位切换，或者只写 emergency priority；这篇则把应急优先、无车跳转和 rush-hour 配时放在同一控制器里，表达更完整。

它对后续数据集构建还有一个好处：文中的变量命名和逻辑关系都很工程化，像 `urgent_s`、`mcount`、`scount`、`is_busytime` 这种词，在自然语言恢复状态机时很容易对应成 guard、timer 和 state variable。对于想做“从工程描述恢复可执行 EFSM”的任务，这种文本非常友好。

## 如果需要人工细读，建议怎么读

人工重读时，建议先看第 `2-3` 页，把四种运行场景和主路/支路的基本配时读清楚，尤其要先确认正常工况与高峰工况的时间差异，以及 emergency case 究竟覆盖主路还是支路。这里能先定下整个控制对象的边界。

然后直接跳到第 `8-10` 页集中读 `4.1.1` 到 `4.1.3`。先抓 `S1-S4` 和 `urgent_m / urgent_s / mhas_car / shas_car` 这套状态转移，再看 `mcount / scount` 如何倒计时、何时归零、怎样驱动下一状态。硬件外围电路、供电、滤波和晶振模块可以放到第二轮再看；如果只是为了重做 `STM.md`，优先级最高的始终是场景定义、状态转移和计时逻辑。
