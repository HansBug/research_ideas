# FPGA 应急优先交通灯控制器 / Design and implementation of smart traffic light controller with emergency vehicle detection on FPGA

## 论文在讲什么

这篇论文讨论的是一个四向路口智能交通灯控制器，重点不在城市交通大数据或优化算法，而在一个可直接部署到 FPGA 上的离散控制器如何根据 `RFID + IR` 输入切换灯相。作者想解决的是两个现实问题：普通定时交通灯无法根据车流密度灵活分配绿灯时长，而且也无法可靠地给应急车辆让行。

为此，论文把控制器写成 `clock division + counter + FSM operation` 三个子模块。RFID 用来检测应急车辆，IR 用来判断车流密度，FSM 则据此决定当前处于应急优先、低密度放行还是高密度放行，以及何时插入黄灯过渡。整体结构是典型的工程时序控制器，而不是“智能交通”外壳下的黑箱模型。

## 控制系统在文中的位置

我们关心的交通灯控制系统是这篇文章的绝对主角。摘要里就直接说明系统的输入、子模块和应急优先目标，后面正文也持续围绕四向路口、RFID 读卡、IR 传感器和相位时长映射展开，没有把控制器降格成方法验证附属物。

尤其重要的是，论文把控制逻辑从“交通灯应该智能一些”压成了很具体的时序链。比如：检测到应急车辆时给该车道至少 `50 s` 绿灯；没有应急车辆时按 `IR` 传感器激活数量给 `15 s / 30 s` 绿灯；每次结束后都插入 `5 s` 黄灯，并在绿灯期间持续监听应急请求。这些信息对 `STM.md` 来说几乎就是可直接复写的控制链。

## 对我们为什么有用

这篇论文对 `sources/` 的价值，在于它补的是 `🚦` 领域里非常典型的 `EFSM + T1` 样本。文库里已经有一些交通灯论文，但有些偏 PLC 固定周期，有些偏图像/密度策略；这篇则把“应急优先 + 密度配时 + FPGA 定时器”三者放到了同一条状态链里，结构更完整。

此外，它对后续数据集的帮助不只在于“有几个状态”。真正有用的是：它清楚保住了输入设备、定时常数、相位过渡和抢占逻辑，也就是后续自然语言到状态机建模最难丢失的那部分信息。用这篇去训练模型，能够逼着模型同时识别 guard、timer 和 priority preemption，而不只是灯色序列。

## 如果需要人工细读，建议怎么读

人工细读时，建议先看第 1 页摘要和第 4-5 页。先把 `RFID`、`IR sensors`、`clock division / counter / FSM` 三个子模块关系理顺，再把 `50 s / 30 s / 15 s / 5 s` 这些关键时长摘出来。对于 `STM.md` 首轮提取来说，这部分已经足够支撑主要状态链。

之后再看 Figure 3 和 Figure 4 对应的文字说明，重点确认 `check RFID -> check IR -> green/yellow -> back to check RFID` 这条主循环，以及应急车辆在普通绿灯期间到达时如何抢占当前相位。硬件搭建和板级实现可以放到第二轮再看，因为它们对理解控制骨架的重要性低于状态切换本身。
