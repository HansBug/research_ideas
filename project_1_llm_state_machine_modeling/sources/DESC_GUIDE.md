# `sources/` 的 `DESC.md` 编写规范

## 1. 文件定位

`DESC.md` 的作用不是替代 [STM.md](./STM_GUIDE.md)，也不是把单篇论文再写成一篇冗长综述。它只负责一件事：让后来者在较低阅读成本下知道**这篇论文大体在讲什么、设计了什么系统，以及我们关心的控制系统描述在文中扮演什么角色**。

换句话说，`DESC.md` 是面向样本库维护者的“中等篇幅定向说明”。它要明显充实于一两句话备注，让读者对论文对象、系统设计和控制角色形成比较具体的感性认识；但它仍然服务于后续做数据集、回看论文、挑选代表样本时的快速理解，而不是服务于领域内的深度技术复现。

## 2. 它应该回答什么

一份合格的 `DESC.md` 默认要回答以下四个问题：

1. 这篇论文主要在解决什么问题，系统大概长什么样。
2. 我们关心的控制系统描述在文中是主角、案例、方法载体，还是教学/实现示例。
3. 这篇论文为什么值得留在 `sources/` 里，后续做样本整理时大概能从中期待什么。
4. 如果后续确实需要人工细读原文来重做 `STM.md`、校正案例边界或补数据集样本，应优先读哪些章节、哪些页，以及每一段阅读的目标是什么。

## 3. 它不应该做什么

`DESC.md` 默认不承担以下职责：

1. 不展开逐状态、逐转移、逐 guard 的证据抽取；这些属于 `STM.md`。
2. 不重复维护 `🟢/🟡/⚪/⏳`、`A/B/C/D`、`T0-T3`、`FSM/EFSM/HSM` 等总账口径；这些属于 [SUMMARY.md](./SUMMARY.md) 与 `STM.md`。
3. 不再保留长篇 `基本信息 / 代码获取 / 数据集获取 / 控制证据 / 分类总结` 大纲式综述。
4. 不为了“完整”而抄很多细节、参数表、公式或长链路清单；只保留帮助快速建立整体印象的核心信息。
5. 不把“人工导读”写成对 `STM.md` 证据摘录的复读；导读必须能在 `STM.md` 暂时失效、过时或质量不足时，仍然指导人直接回原文把状态机相关内容重新读出来。

## 4. 默认结构

除非用户明确要求更详细，`DESC.md` 默认固定为四段式中等篇幅说明：

1. `## 论文在讲什么`
   - 用 `2` 段左右自然语言说明论文的问题背景、目标系统、大致控制思路，以及输入/模式/结果的大体轮廓。
2. `## 控制系统在文中的位置`
   - 用 `2` 段左右自然语言说明我们关注的控制系统描述在文中到底是什么角色。
   - 例如：它是论文的核心系统设计对象、被分析/被验证的代表性案例、方法落地的主要载体，或是用于教学/实现展示的工程样例。
3. `## 对我们为什么有用`
   - 用 `2` 段左右自然语言说明它对 `sources/` 样本收集的意义。
   - 强调“它能帮我们补哪类样本、后续回看时大概该关注什么、哪些细节可以第二层再看”即可。
4. `## 如果需要人工细读，建议怎么读`
   - 用 `2` 段左右自然语言给出一条可执行的人工阅读路线。
   - 第一段优先写“先看哪些章节/页确认系统边界，再跳到哪些章节/页抽状态、转移、时间条件、状态动作和异常分支，最后用哪些实验/案例页做一致性核对”。
   - 第二段优先写“哪些章节/页主要是连续模型、数学推导、识别/估计算法、背景综述或性能指标，适合第二轮再看”，并明确这条路线在 `STM.md` 不可靠时仍可直接指导人工重读原文。

文件标题行仍保留：

```markdown
# 中文标题 / English Title
```

除此之外，默认不再追加大块元信息表，也不恢复旧版那种分节过细的长综述框架。

## 5. 篇幅与风格要求

默认按以下硬约束维护：

1. 全文以四段式自然语言说明为主，优先 `4` 个二级标题，每节通常 `2` 段左右。
2. 总长度默认控制在当前极短版的约 `5` 倍左右，通常可写到约 `1200-2200` 字；原则上应明显充实于一句话说明，但也不应回到旧版 `80-100` 行长综述。
3. 以自然语言解释为主，不要再堆很多项目符号、字段表或分类标签。
4. 允许点名若干代表性的状态、模式、任务阶段、输入或输出，用来帮助读者建立直觉；但不要把 `DESC.md` 写成压缩版 `STM.md`。
5. 语气应克制、说明性强，不写夸张评价，不写“强样本”“完美样本”之类口号式结论；只说清楚其样本价值来自哪里。
6. 所有 `#` / `##` / `###` 标题行后面必须保留一个空行，不要让标题和正文首段直接粘连。

## 6. 写作判断原则

写 `DESC.md` 时，优先强调以下信息：

1. 控制对象是什么。
2. 系统是在解决真实工程任务，还是主要在展示一种方法。
3. 控制描述是论文主体，还是为了论证方法而引入的案例。
4. 读这篇论文时，我们后续最值得先回看的部分在哪里。
5. 如果要人工重读原文，哪些章节/页最该先看，哪些数学推导、背景材料或连续控制细节可以后看。

如果论文整体偏方法或偏工具，但其中有一个明确控制案例值得保留，也应如实写出来，例如：

1. “论文整体偏方法，但其中的某个控制系统案例是承载方法验证的主要对象。”
2. “交通灯/机器人/外骨骼控制器在文中更像实现示例，但示例本身足够具体，仍值得保留。”

不要把所有论文都写成“系统设计核心论文”。角色必须如实区分。

## 7. 与 `STM.md` 的关系

两者分工必须明确：

1. `STM.md` 负责证据级抽取，回答“原文里到底有哪些状态、事件、guard、时序和控制链”。
2. `DESC.md` 负责中等篇幅的快速定向和人工重读导读，回答“这篇论文大体是什么，这套控制描述在文里是什么地位，以及如果要人工回原文重做样本应怎样读”。

因此：

1. `DESC.md` 不应复制 `STM.md` 的长证据链。
2. `STM.md` 也不需要复制 `DESC.md` 的感性导读段落。
3. 如果同一轮同时重写两者，建议先完成 `STM.md`，再回到原文和 `STM.md` 一起写中等篇幅的 `DESC.md`；但 `## 如果需要人工细读，建议怎么读` 这一节必须优先面向“即使 `STM.md` 失效，人也能直接按它重读原文”来组织。

## 8. 编写顺序

生成或重写单篇 `DESC.md` 时，默认按以下顺序工作：

1. 先读 `bibtex.bib`，确认标题与元信息。
2. 再读 `paper_content.txt`，理解论文主体。
3. 必要时回到 `paper.pdf` 核对图、表和版式。
4. 若该论文已有 `STM.md`，可以再读一遍以保持口径一致，但不能反过来只靠 `STM.md` 代替原文阅读。

## 9. 维护原则

后续维护时，默认采用“中等篇幅整合更新”而不是不断追加新段落：

1. 若旧版 `DESC.md` 过长，应整体压缩重写。
2. 若对论文角色判断改变，应直接改写对应段落，不保留历史层层追加痕迹。
3. `DESC.md` 的目标是始终好读、信息足够、又不会失控膨胀，而不是积累历史备注。
