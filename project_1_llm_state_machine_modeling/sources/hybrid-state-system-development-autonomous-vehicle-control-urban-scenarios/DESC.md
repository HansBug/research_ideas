# 城市场景自动驾驶 HSS 元状态与 Road 子机开发链 / Hybrid State System Development for Autonomous Vehicle Control in Urban Scenarios

## 论文在讲什么

这篇论文围绕 `OSU-ACT` 参加 `DARPA Urban Challenge` 时所采用的控制架构展开，主轴是怎样把城市自动驾驶系统写成一个 `Hybrid State System (HSS)`。作者并不满足于只给一个“高层做决策、低层做控制”的常见口号，而是明确把高层写成离散 `FSM`，把底层写成连续的横纵向控制器，并说明两者通过接口交换事件与连续命令。

更有价值的是，文章进一步展示了高层控制器不是一次性拍脑袋设计出来的，而是通过一串 capability graft 的方式逐步扩展。作者从最基础的道路 waypoint 跟踪开始，接着加入阻塞车辆等待、双车道借道绕行、以及根据车道分隔规则决定“停车后绕行”还是“不断速换道”的能力。这种写法让论文不仅有宏观元状态，还有一个非常可追溯的 `Road` 子状态机演化链。

## 控制系统在文中的位置

这里的控制系统描述属于论文主体本身，而不是挂在方法论末尾的案例插图。`HSS` 不是为了展示形式化术语而引入的壳，而是作者解释车辆怎样在 `Road / Intersection / U-Turn / Parking Zone` 等场景间切换、以及怎样把连续控制和离散决策耦合起来的核心结构。换句话说，我们关心的控制器恰恰就是作者想说明的东西。

需要如实指出的是，这篇与文库里已有的 urban-challenge 自动驾驶条目是邻近的，但并不只是换个标题重复讲 mission states。现有不少条目更强调顶层 driving states、异常恢复和行为监督器，而这篇的独特性在于它公开解释了 `HSS` 接口、元状态层、`Road` 子机内部 `S1-S7` 的 graft 逻辑，以及 extension / insertion 两类结构对可达性和系统鲁棒性的影响。

## 对我们为什么有用

这篇对 `sources/` 的直接价值，是补进了一个更偏“层次状态机如何和连续控制耦合”的城市自动驾驶样本。它不只提供一组 mission mode 名称，还明确保留了 `HC` 离散控制器与 `LC` 连续控制器之间的关系，因此非常适合被标成 `HSM + T0 + 连续耦合`，用来区分那些只在高层做符号决策的自动驾驶论文。

它也提供了一种很少见但很有建模价值的叙述方式：不是一次性给最终状态图，而是按能力嫁接的顺序解释 `Road` 子机怎样从 `S1 -> S2 -> S3` 扩展到带 `S4 / S5 / S6 / S7` 的更复杂结构。这使得后续如果要研究“自然语言如何逐步增量生成状态机”或“新增需求如何修改现有状态图”，这篇会比单纯给最终大图的论文更有参考价值。

## 如果需要人工细读，建议怎么读

人工重读时，建议先看第 `1-2` 页摘要和 `2.1 The HSS layout`，先把 `HC` 和 `LC` 的职责边界、`Phi / Psi` 接口、以及为什么作者选 `HSS` 而不是一般统一模型读清楚。这样后面再看状态机时，就知道哪些是高层离散决策，哪些是底层连续执行，不会把两层混在一起。

随后直接跳到第 `3.2 Development Stages`，重点读 `Road` meta-state 的四个阶段和 Figure `8-18` 周围的文字说明。第一轮重建样本时，优先圈出元状态总表、`S1-S7` 的扩展顺序、`blocking obstacle`、`complete stop and pass`、`non-stop lane change` 这些决策语义；至于更形式化的系统方程、Dubins 车辆模型和其他连续控制细节，可以放到第二轮再补。
