# `sources/` 操作规范

本文档用于固定 `project_1_llm_state_machine_modeling/sources/` 的后续维护方式，重点约束 [SUMMARY.md](./SUMMARY.md) 的总账结构、回填顺序与统计口径，避免论文级与案例级信息再次混写。

## 0. 文档关系与使用顺序

`sources/` 下的核心文档分工如下：

1. [README.md](./README.md)
   - 负责解释论文集定位、收录边界、目录职责与推荐阅读顺序。
2. [GUIDE.md](./GUIDE.md)
   - 负责规定检索、筛选、目录维护、[SUMMARY.md](./SUMMARY.md) 回填与一致性检查的操作规范。
3. [SUMMARY.md](./SUMMARY.md)
   - 是唯一总账，记录前部关键词簇与当前统计、论文总账、失败记录、案例总账，以及文末统一更新日志。
4. [STM_GUIDE.md](./STM_GUIDE.md)
   - 负责单篇 `STM.md` 的抽取标准、证据组织与未收获口径。
5. [DESC_GUIDE.md](./DESC_GUIDE.md)
   - 负责单篇 `DESC.md` 的中等篇幅说明写法，强调“快速定向 + 人工重读导读”，而不是“长综述”。

默认阅读顺序如下：

1. 先读 [README.md](./README.md)，确认为什么建这个论文集、收什么、不收什么。
2. 再读 [GUIDE.md](./GUIDE.md)，确认本轮操作规范。
3. 再读 [SUMMARY.md](./SUMMARY.md)，确认当前总账、失败历史与下一步续做位置。
4. 若任务涉及 `STM.md`，再读 [STM_GUIDE.md](./STM_GUIDE.md)。
5. 若任务涉及 `DESC.md`，再读 [DESC_GUIDE.md](./DESC_GUIDE.md)。
6. 最后进入具体论文目录，按 `bibtex.bib -> paper_content.txt -> paper.pdf（必要时） -> 派生文件` 的顺序工作。

## 1. 目标与范围

`sources/` 不是一般性的相关工作收藏夹，而是面向 `project_1` 数据集构建的样本库。收集它们的直接目标如下：

1. 为“控制系统状态机自动生成”任务积累可追溯的原始论文样本。
2. 从真实控制系统论文中提取可写成 `STM.md` 的自然语言控制逻辑、模式切换、故障恢复、门控与时间约束描述。
3. 让后续总账能够稳定区分“论文级是否成账”和“案例级是否可入数据集”。

### 1.1 收录条件

1. 研究对象是具体控制系统、控制器或控制子系统，而不是开发流程、工具流程或抽象方法流程。
2. 原文能够支持提取运行模式、状态切换、输入触发、输出动作、定时规则、异常/恢复链等内容。
3. 能获取 PDF，并生成质量可用的 `paper_content.txt`。
4. 原文至少有希望形成可追溯 `STM.md`，哪怕最终只得到 `🟡 可整理` 或 `⚪ 未收获` 结果。

### 1.2 降优先级条件

1. 研究对象真实存在，但论文主体更偏算法、优化、诊断、仿真或工具演示，离可直接整理成 `STM.md` 还差一层。
2. 状态信息主要散落在图、图注或多个段落，需要较高整理成本。
3. 论文更偏 `Hybrid / T2 / T3` 或连续控制，又缺明确离散模式链、局部 timer 或 guard/输出映射。

### 1.3 排除条件

1. 研究对象不是控制系统运行客体，而是工具、流程、工作流、架构或方法论。
2. 论文只有连续控制性能、参数调优、轨迹优化、感知估计，没有离散行为逻辑。
3. 无法取得可用 PDF，或文本提取后仍不足以支撑可追溯整理。

### 1.4 非目标任务边界

以下工作与 `project_1` 整体研究有关，但不属于 `sources/` 的日常维护主线：

1. 泛 LLM 生成 UML/SysML baseline 的比较与综述，这类内容应主要留在 `baselines/` 或其他 baseline 文档中。
2. 把单篇 `DESC.md` 再写成长综述；本论文集里的 `DESC.md` 只承担中等篇幅的快速定向说明，不承担深度综述职责。
3. 纯形式化工具、元模型、建模流程背景文献的扩张式收集，如果它们不能产出具体控制对象样本，不应挤占本论文集配额。

## 2. 目录与文件规范

`sources/` 下每篇论文必须独占一个子目录。每个目录至少应包含：

1. PDF 原文。
2. `bibtex.bib`
   - 需要尽可能完整，达到可直接用于论文写作的程度。
3. `paper_content.txt`
   - 必须优先使用 `tools/pdf_extractor.py` 生成。
   - 默认先用 `text` 模式；若提取异常，立即改用 `ocr` 模式。
4. `STM.md`
   - 必须基于 `paper_content.txt` 生成。
   - 其抽取口径统一遵循 [STM_GUIDE.md](./STM_GUIDE.md)。
5. `DESC.md`
   - 不是每篇必备文件，但若目录下已存在，或任务明确要求生成/重写，就必须遵循 [DESC_GUIDE.md](./DESC_GUIDE.md)。
   - 其定位是“用中等篇幅说明论文在讲什么、系统是什么、控制系统在文中的角色是什么，以及人工回原文时该怎样读”，不是证据抽取文件。

## 3. 单篇论文处理流程

处理一篇新论文时，默认按以下顺序执行：

1. 创建论文目录并放入 PDF。
2. 完成 `bibtex.bib`。
3. 生成并检查 `paper_content.txt`。
4. 阅读 `paper_content.txt`，必要时回 `paper.pdf` 核对。
5. 依据 [STM_GUIDE.md](./STM_GUIDE.md) 编写 `STM.md`。
6. 若该论文需要 `DESC.md`，则依据 [DESC_GUIDE.md](./DESC_GUIDE.md) 编写或重写 `DESC.md`。
7. 最后统一回填 [SUMMARY.md](./SUMMARY.md)。

执行时还应遵守以下约束：

1. `STM.md` 只提取真实控制系统、控制器或控制子系统的设计/描述/需求内容。
2. 所有写入 `STM.md` 的信息都必须能在原文中追溯到证据。
3. 若论文最终没有收获，也必须留下 `⚪ 未收获` 的 `STM.md`，不能留空不记。
4. 只要本轮新纳入或重写了 `STM.md`，就必须在**同一轮**同步回填 `SUMMARY.md` 的论文表、案例表和相关统计。
5. 如果论文已经收录但暂时还没有 `STM.md`，必须在论文总账中显式记为 `⏳ 尚未提取`，并把 `案例数` 记为 `0`。

### 3.1 `DESC.md` 的默认定位

`DESC.md` 只用于帮助维护者快速建立感性认识，但默认不再压成极短备注。它主要回答三件事：

1. 论文主要在讲什么，系统大概是什么。
2. 我们关心的控制系统描述在文中扮演什么角色。
3. 这篇论文对样本收集为什么有用。
4. 如果需要人工重读原文，应该优先看哪些章节/页以及为了解决什么问题去看。

维护要求如下：

1. 不再写成 `基本信息 / 代码 / 数据集 / 证据 / 分类总结` 的长综述。
2. 默认使用四段式中等篇幅结构，具体口径以 [DESC_GUIDE.md](./DESC_GUIDE.md) 为准。
3. 不把 `DESC.md` 写成压缩版 `STM.md`；逐状态、逐转移、逐 guard 证据仍应留在 `STM.md`。
4. `DESC.md` 中必须保留“如果需要人工细读，建议怎么读”一节，且该节要在 `STM.md` 不可靠时仍然能够独立指导人工重读论文。
5. 如果同一轮同时改 `STM.md` 和 `DESC.md`，优先先改 `STM.md`，再写中等篇幅的 `DESC.md`。

## 4. [SUMMARY.md](./SUMMARY.md) 的固定结构

[SUMMARY.md](./SUMMARY.md) 是 `sources/` 的唯一总账，不再允许把论文级与案例级信息分散到多套并行表中。

### 4.1 必备章节

后续维护时，[SUMMARY.md](./SUMMARY.md) 必须稳定包含以下章节：

1. 文档定位与使用方式。
2. 收录边界回顾。
3. 检索关键词簇。
4. 当前收录统计。
5. `## 领域 Emoji 口径`
6. `## 论文总账`
7. `## 本轮下载失败记录`
8. `## 案例总账（按新口径维护）`
9. `## 统一更新日志`

### 4.2 统一更新日志

`SUMMARY.md` 中只保留**一套**更新日志，固定放在全文最后，也就是“案例总账（按新口径维护）”之后；表格必须按时间降序排列，最新记录始终置顶。使用以下列：

1. `时间`
2. `论文总账更新`
3. `案例总账更新`
4. `说明`

维护要求如下：

1. 不再在“论文总账”内部维护单独日志。
2. 不再在“案例总账”内部维护第二套日志。
3. 同一轮若同时发生论文新增与案例回填，应合并到同一时间行。
4. 时间统一使用绝对时间 `yyyy-mm-dd hh:mm:ss`。
5. `论文总账更新` 只写论文级变化，例如新增论文数、累计论文数、是否出现 `⏳` 或 `⚪` 变化。
6. `案例总账更新` 只写案例级变化，例如新增案例、回刷区间、统计口径调整。
7. 新增日志时默认插入表格顶部，除非是在补录历史时间点；即使补录历史，也必须在补录后恢复整体降序。

### 4.3 论文总账维护规则

论文层只回答“这篇论文当前是什么状态、关联多少案例”，不再承载案例级细节。

#### 4.3.1 论文级统计表

`### 按领域统计的论文状态分布` 必须满足：

1. 行固定是领域。
2. 列固定是 `🟢 直接可用 / 🟡 可整理 / ⚪ 未收获 / ⏳ 尚未提取 / 总计`。
3. 统计对象是论文，不是案例。
4. 不允许把 `A/B/C/D`、`时间级别`、`状态机类型` 这类案例字段搬到论文统计表中。

#### 4.3.2 论文清单

`### 论文清单` 是 `sources/` 唯一的论文级主表，默认至少维护以下列：

1. `#`
2. `领域`
3. `STM状态`
4. `案例数`
5. `标题`
6. `年份`
7. `主题`
8. `关键词`
9. `跳转`

维护要求如下：

1. 不再保留第二套文件级论文表。
2. `STM状态` 只允许使用 `🟢 直接可用 / 🟡 可整理 / ⚪ 未收获 / ⏳ 尚未提取`。
3. `案例数` 只用于把论文与案例总账关联起来；如果论文还没有可入账案例，应记 `0`。
4. 若论文尚未提取 `STM.md`，必须显式写成 `⏳ 尚未提取`，不能留空。
5. `跳转` 列统一只保留 `[STM](./xxx/STM.md) / [DESC](./xxx/DESC.md)` 两个 Markdown 链接，不再使用目录链接，也不再混入 `TXT / Bib`。
6. 论文排序与编号原则上稳定，不因局部补写就频繁重排。

#### 4.3.3 `⚪ 未收获` 论文管理

论文总账中应稳定保留：

1. `### `⚪ 未收获` 论文成因分布`
2. `### `⚪ 未收获` 论文专表（便于 hard negative 回收）`

默认原因类别如下：

1. `📉 连续控制/估计/优化主导`
2. `🛠️ 方法/工具/流程主导`
3. `📚 综述/标准/架构主导`
4. `🔍 目标控制链证据不足`

### 4.4 案例总账维护规则

案例层负责承载所有细粒度建模口径。`状态机类型 / 时间级别 / 结构标签 / 数据集角色 / 原文细节充实度 / 描述细节充实度` 一律只在案例层维护。

#### 4.4.1 案例级统计表

案例总账至少要维护以下分布表，且行统一是领域：

1. `各领域案例角色分布`
   - 列固定为 `💎 核心保留 / 🧰 清洗后保留 / 🪫 降采样保留 / 总计`
2. `各领域原文细节充实度分布`
   - 列固定为 `🟢 A / 🟡 B / 🟠 C / 🔴 D / 总计`
3. `各领域描述细节充实度分布`
   - 列固定为 `🟢 A / 🟡 B / 🟠 C / 🔴 D / 总计`
4. `各领域时间级别分布`
   - 列固定为 `T0 / T1 / T2 / T3 / N/A / 总计`
5. `各领域状态机类型分布`
   - 列固定为 `FSM / EFSM / HSM / Protocol / Resource-flow / Hybrid / N/A / 总计`

需要补充的案例级章节还包括：

1. `案例总体统计`
2. `结构标签覆盖率（多标签口径）`
3. `强趋同簇汇总`
4. `面向状态机自动生成数据集的整体判断`
5. `案例清单`

#### 4.4.2 案例清单

`### 案例清单` 默认至少维护以下列：

1. `#`
2. `论文#`
3. `领域`
4. `案例`
5. `控制对象`
6. `状态机类型`
7. `时间级别`
8. `结构标签`
9. `数据集角色`
10. `原文细节`
11. `描述细节`
12. `跳转`

维护要求如下：

1. 用 `论文#` 把案例和论文总账关联起来，避免在案例表里再重复维护一整套论文级信息。
2. `跳转` 列统一只保留 `[STM](./xxx/STM.md) / [DESC](./xxx/DESC.md)` 两个 Markdown 链接，不再混入 `TXT / Bib`。
3. 不再给案例清单单独维护长段 `条目级判断` 列；更长的解释应留在单篇 `STM.md` 与 `DESC.md`。
4. 若论文当前没有可入账案例，不要臆造案例行。
5. 只要新增、删除、回刷或重判案例，就必须同步重算所有案例级统计表。

### 4.5 当前收录统计与失败记录

`## 当前收录统计` 与 `## 本轮下载失败记录` 也必须持续维护。

当前收录统计至少应覆盖：

1. 已收录论文数。
2. 本轮新增论文数。
3. 下载失败记录数。
4. 已完成 `STM.md` 的论文数。
5. `⏳ 尚未提取` 的论文数。
6. 必要时可补充“含正例案例的论文数”与“正例案例数”，但这两项仍以总表真实内容为准。

失败记录维护要求如下：

1. 使用单一失败表，不要为不同轮次再开多套失败表。
2. 记录标题、失败时间、失败原因，必要时保留尝试链接与失败现象。
3. 若后续下载成功，旧失败记录可保留为历史，不要求回删。

### 4.6 领域与 Emoji 复用原则

1. 后续新增论文与案例时，默认复用 [SUMMARY.md](./SUMMARY.md) 现有领域框架与 emoji。
2. 只要现有框架可以覆盖，就不要随意新增 emoji 或临时改名。
3. 若确需新增领域，必须先更新 `领域 Emoji 口径`，再在正文其他表中使用。

## 5. 回填顺序与章节级约束

每轮完成后，推荐按以下顺序回填 [SUMMARY.md](./SUMMARY.md)：

1. 先更新论文总账：论文清单、论文状态统计、`⚪ 未收获` 成因分布与专表。
2. 若本轮有下载失败，再更新失败记录表。
3. 再更新案例总账：案例清单、案例总体统计、领域分布表、结构标签覆盖率、强趋同簇与整体判断。
4. 再更新顶部的“当前收录统计”。
5. 再回填前部的“检索关键词簇”；这一节必须按“整合式维护”回写，不能只新增不删减。
6. 最后回填文末“统一更新日志”，并复核是否仍按时间降序排列。

章节级硬约束如下：

1. 禁止重新引入第二套论文级总表。
2. 禁止重新引入论文区日志和案例区日志两套并行日志。
3. 论文级统计表只统计论文状态，不统计案例级 `A/B/C/D`、`T0/T1/T2/T3`、`FSM/EFSM/HSM/...`。
4. 案例级细粒度统计只放在案例总账，不回抬到论文层。
5. 所有统计数字必须由当前真实表格重算，不能凭记忆手填。
6. 已收录但未完成 `STM.md` 的论文必须如实写为 `⏳ 尚未提取`。
7. 只要案例清单变化了，对应的案例分布表与整体判断就必须同轮更新。
8. `统一更新日志` 必须始终位于全文最后，不允许再插回前部章节之间。

## 6. 案例判定口径

### 6.1 判定顺序

所有案例级回填默认按以下顺序判定：

1. 先读对应论文目录下的 `paper_content.txt` 全文。
2. 如遇图表、公式、版式或提取异常，再回 `paper.pdf` 核对。
3. 先判 `状态机类型 / 时间级别 / 结构标签`。
4. 再分别判 `原文细节充实度 / 描述细节充实度`。
5. 最后再给 `💎 / 🧰 / 🪫`，并在强趋同簇层做采样治理。

### 6.2 字段固定集合

1. `状态机类型`
   - 固定集合：`FSM / EFSM / HSM / Protocol / Resource-flow / Hybrid / N/A`
2. `时间级别`
   - 固定集合：`T0 / T1 / T2 / T3 / N/A`
3. `结构标签`
   - 固定集合：`层次 / 并行 / 协议交互 / 资源互斥 / 显式时钟 / 连续耦合`
   - 多标签时允许并列；没有额外结构特征时记 `-`
4. `原文细节充实度 / 描述细节充实度`
   - 固定口径：`🟢 A / 🟡 B / 🟠 C / 🔴 D`
5. `数据集角色`
   - 固定口径：`💎 核心保留 / 🧰 清洗后保留 / 🪫 降采样保留`
   - `⛔` 不再作为案例行角色使用；无正例案例的论文直接留在论文层的 `⚪ 未收获` 管理中

### 6.3 论文级与案例级的边界

1. 论文级 `🟢/🟡/⚪/⏳` 只表示 `STM.md` 的整体成账状态。
2. 案例级 `💎/🧰/🪫` 才表示数据集去留与清洗优先级。
3. 不允许用案例级细节评级替代论文级状态，也不允许反过来用论文级状态替代案例级判型。

## 7. 检索关键词簇的持续更新规则

`## 检索关键词簇` 不是静态列表，必须在每轮维护中持续写回、持续校正、持续压缩整合；禁止只做单向追加式更新，也不允许机械累积旧 bullet，避免关键词簇内容无限膨胀。

维护时至少要做四件事：

1. 保留仍有效的基础检索组合。
2. 从当前高质量案例里反推对象词、行为词、输入词、输出词与时间词。
3. 根据本轮新增的高质量论文，补充更高命中的标题词与对象词。
4. 根据本轮 `⚪ 未收获` 或低命中候选，明确哪些词应降权。
5. 同步合并同义/近义词簇，删除已经过时、低价值、偶然命中或重复表达的旧项。

默认约束如下：

1. `当前推荐关键词簇`、`高命中特征`、`低命中特征`、`检索倾向调整` 四个小节都应压缩式整合更新。
2. 每个小节默认不超过 `10` 行。
3. 每次写回时都必须同时做“新增 + 合并 + 替换 + 删减”四类动作中的必要部分，不能只单方面追加新词而不清理旧内容。
4. 接近篇幅上限时，优先压缩、合并、替换旧内容，而不是放宽长度限制。
5. 不要把一轮偶然命中的细碎词长期堆在总账里。
6. 当多个方向都可能命中时，优先补当前样本更稀缺但仍高价值的领域。
7. 这里的“更稀缺”不是凭记忆口头判断，而是每轮都要先回看 [SUMMARY.md](./SUMMARY.md) 里的 `各领域原文细节充实度分布`、`各领域描述细节充实度分布`、`各领域时间级别分布` 与 `各领域状态机类型分布`，动态找出**当前** `🟢 A` 数量最少、`A` 级占比最低或类型/时间/结构覆盖最薄的领域。
8. 某个领域一旦在后续轮次里补起来，就必须自动降权；新的检索重点应随总账统计变化而变化，不能把某一批“曾经稀缺”的领域长期固定成永久优先项。

## 7.1 用户筛选条件的刚性执行

如果用户对新增论文或案例提出了硬条件，这些条件必须被当成真正的筛选规则，而不是事后回填时的装饰标签。默认要求如下：

1. 用户若要求 `原文细节 = 🟢 A`、`描述细节 >= 🟡 B`、`只收 T1`、`只收 HSM`、`只收某领域`、`只收含异常恢复链` 等条件，必须先检索候选，再逐篇回原文如实判定。
2. 不得先决定“这篇想收”，再把 `A/B/C/D`、`T0-T3`、`FSM/EFSM/HSM`、`💎/🧰/🪫` 这些字段反向写成目标值去迎合用户要求。
3. 若候选论文不满足条件，就直接排除；若最终满足条件的样本很少，或某一轮根本没有满足项，也必须如实返回少量结果或空结果，并说明原因。
4. 若用户条件与当前领域平衡原则冲突，以“如实满足用户硬条件”优先；但在满足用户条件的候选集合内部，仍应优先补当前更稀缺的领域。

## 8. 去重与跳过规则

后续处理时，以下对象默认直接跳过：

1. 已经存在于 `sources/` 且已在 [SUMMARY.md](./SUMMARY.md) 入账的论文。
2. 最近 `5` 天内已经明确记录失败的候选论文。

去重优先级如下：

1. 先按 DOI 去重。
2. DOI 缺失时按标准化标题去重。
3. 标题仍有轻微差异时，再结合作者、年份、会议/期刊综合判断。

对失败重试的默认规则如下：

1. 以失败表中记录的时间为准。
2. 若当前日期距离失败记录不超过 `5` 天，默认跳过，不再重复下载。
3. 超过 `5` 天后可重新尝试；若再次失败，则继续追加新的失败记录。

## 9. 推荐的实际执行顺序

一次完整增量整理任务，默认按以下顺序推进：

1. 先读 [SUMMARY.md](./SUMMARY.md)，确认现有论文总账、案例总账、失败记录与关键词簇，并先根据最新案例统计判断本轮最缺的领域在哪里。
2. 若用户给了硬性筛选条件，先把这些条件写成明确的候选判定标准，再开始检索，不允许边搜边偷偷放宽。
3. 再扫 `sources/` 目录，确认哪些论文缺 `STM.md`、哪些条目需要补账。
4. 对候选新论文做去重与“5 天失败跳过”检查。
5. 完成新论文的 PDF、BibTeX、文本提取与 `STM.md`；若该论文需要 `DESC.md`，则在同一轮按 [DESC_GUIDE.md](./DESC_GUIDE.md) 补写或重写。
6. 统一回填论文总账、失败记录、案例总账、当前统计、统一更新日志与关键词簇。
7. 最后执行一致性检查，确认表格、统计与目录状态一致，并复核本轮是否确实遵守了用户筛选条件与领域平衡原则。

## 10. 与专项 GUIDE 的关系

本规范只负责 `sources/` 与 [SUMMARY.md](./SUMMARY.md) 的组织和汇总。

1. `STM.md` 的具体抽取标准仍以 [STM_GUIDE.md](./STM_GUIDE.md) 为准。
2. `DESC.md` 的具体写法、篇幅和定位仍以 [DESC_GUIDE.md](./DESC_GUIDE.md) 为准。

如果本文件与单篇派生文件的具体写法发生冲突，优先级如下：

1. `STM.md` 相关冲突：以 [STM_GUIDE.md](./STM_GUIDE.md) 为准。
2. `DESC.md` 相关冲突：以 [DESC_GUIDE.md](./DESC_GUIDE.md) 为准。

## 11. 质量与可追溯性要求

后续 AI 至少应满足以下最低质量线：

1. 所有纳入/排除判断都应有原文依据，不能只凭标题或摘要猜测。
2. `bibtex.bib` 必须尽量补齐到可直接用于论文写作的程度。
3. `paper_content.txt` 若质量异常，应优先重提取，而不是在明显乱码文本上强行写 `STM.md`。
4. 论文总账、案例总账、失败记录和当前统计中的数字必须前后一致。
5. 如果证据不足，应明确写成 `⚪ 未收获` 或 `⏳ 尚未提取`，而不是用主观推断把条目补圆。
6. 新增或回刷案例后，必须同步更新其所属领域的案例统计表，不能只改案例清单不改统计。
7. 若生成或重写 `DESC.md`，必须把篇幅控制在“中等篇幅的快速定向说明”范围内，不得再次膨胀成长综述。
8. 无论用户提出什么筛选要求，都严禁弄虚作假；如果用户要求 `🟢 A`，就必须逐篇核实哪些真的是 `🟢 A`，而不是为了凑结果把 `🟡 B / 🟠 C / 🔴 D` 改写成 `🟢 A`。
9. 如果真实满足条件的样本数不足，必须如实返回不足的结果，并说明缺口来自哪里；不允许通过放宽条件但不声明、或篡改标签的方式“补足数量”。
