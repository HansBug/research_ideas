# 联锁表精度验证论文 / Verifying the accuracy of interlocking tables for railway signalling systems using abstract state machines

## 论文在讲什么

这篇论文讨论的是铁路信号系统设计阶段的一个很具体的问题：联锁表如果在设计时就写错，后面的验证与调试成本会非常高，因此作者尝试在设计阶段就把联锁表转成形式模型并做一致性检查。文中的形式手段是 `abstract state machines` 与 `NuSMV`，但真正的核心输入并不是抽象 benchmark，而是地铁车站联锁表中对进路、区段、道岔、信号机和反向进路的工程约束。

对我们更有用的是，论文没有停留在“用 ASM 做验证”的方法口号，而是把联锁表里每一列各自负责什么写清楚了。它说明了某条进路包含哪些 block、哪些 point 应该处于什么位置、哪些 signal 应显示什么颜色、哪些 counter route 必须被锁死，同时还给出了列车在满足信号和道岔位置条件后如何从一个 track circuit 进入下一个 track circuit 的规则。

## 控制系统在文中的位置

这里的控制系统描述不是陪衬，而是整篇验证工作的前提模型。作者要想证明联锁表是否正确，必须先把“请求进路后系统怎么锁闭、怎么排道岔、什么时候改变信号显示、列车何时能继续前进”这条控制链落成明确的状态更新规则，因此文中的联锁逻辑本身就是主要分析对象。

同时，这篇论文不是把列车运行抽成很空泛的事件序列，而是把真实联锁里最关键的互斥资源关系保留了下来。进路是否可开通取决于区段是否空闲、反向进路是否已锁、道岔是否摆到位；列车能否进入下一段又取决于信号颜色与道岔位置。这种“资源互斥 + guard 驱动运动”的写法，对状态机数据集尤其重要，因为它保住了比普通顺序控制更强的约束语义。

## 对我们为什么有用

对 `sources/` 来说，这篇论文补的是 `🚆 + EFSM + T0 + 资源互斥` 方向的一类高细节样本。它和单纯把 interlocking 当成资源分配问题的论文相比，更进一步保住了“信号显示如何影响列车能否推进”的动作侧描述；和只讲形式验证流程的论文相比，它又保住了联锁表字段和故障注入结果，因此既能作为正样本，也能为以后设计 hard negative 提供边界参照。

它还有一个实际价值：论文把错误情形写得很直白。反向进路同时锁闭失败会导致碰撞，道岔位置错误会导向脱轨，这些都不是抽象安全性质，而是能直接映射回控制 guard 失效后果的工程语义。对后续做“从自然语言恢复状态机”或“从模型到验证场景”的任务，这类带失效后果的控制描述比单纯 nominal 流程更有用。

## 如果需要人工细读，建议怎么读

如果后续要人工重写或细化 `STM.md`，建议先看介绍车站布局和联锁表的部分，再直接读 `Table 1` 附近关于 `Route / Blocks / Points / Signals / Counter routes` 各列含义的解释。读这一段的目标不是理解 ASM 语法，而是先锁定控制对象边界：系统到底在控制哪些资源、哪些颜色和道岔位置会被当成 guard、初始状态是什么。

然后应继续读进路开放与列车移动规则的正文，以及后面碰撞、脱轨 fault injection 的分析段。前者用于抽“请求进路 -> 锁进路 -> 锁道岔 -> 改信号 -> 允许运动”的主链，后者用于补“guard 失效会产生什么异常后果”。至于 ASM 与 NuSMV 对应关系、CTL 公式写法和验证工具细节，可以放到第二轮再看；那部分对理解验证框架有价值，但不是当前抽取控制状态链的第一优先级。
