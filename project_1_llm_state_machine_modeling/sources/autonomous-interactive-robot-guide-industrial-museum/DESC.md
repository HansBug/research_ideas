# 工业博物馆导览机器人任务编排器 / Development of an Autonomous and Interactive Robot Guide for Industrial Museum Environments Using IoT and AI Technologies

## 论文在讲什么

这篇论文讲的是一个部署在摩托车装配厂工业博物馆环境中的自主导览机器人。系统整体融合了导航传感器、`mmWave`、`LiDAR`、`RGB-D`、本地大语言模型和云侧通信，目标是让机器人能够在真实参观环境中完成路线导航、展品讲解和与访客的自然语言交互。

从 `sources/` 的角度看，最值得保留的是它没有把机器人控制只埋在系统框图里，而是公开给出一个五态 `FSM`：`Idle / Undock / Navigate / Dock / Done`。同时，作者还把 `goal_status`、retry 上限、停靠/脱离底座服务、动态避障和实地导览结果串在一起，因此这不是“有一个状态图配图就算数”的薄链样本，而是一条可以真正回写到数据集里的任务编排控制链。

## 控制系统在文中的位置

这里的控制系统描述属于软件系统主体的一部分。论文虽然也讨论传感融合、工业环境部署和人机交互，但 `ROS 2 Orchestrator` 里的状态机就是把这些模块联结成可运行导览任务的核心决策器。换句话说，它不是附属示例，而是机器人能否完成导览任务的主逻辑载体。

更具体地说，这篇不是单纯的机器人平台介绍。它把高层控制器写成“根据任务起点、剩余目标、成功失败反馈和 docking 服务结果做状态迁移”的形式，因此在 `sources/` 里更像一个任务级 `EFSM` 样本，而不只是一个“移动机器人系统综述”。

## 对我们为什么有用

这篇能补一类过去相对不足的服务机器人样本，即带明确任务编排和失败回退的导览机器人控制器。它和纯工业机器人顺序控制、飞行器任务管理、停车或门控系统都不一样，能提供一条“服务调用 + 导航反馈 + retry 计数 + 完成/中止分支”式的文本模板。

对 `project_1` 来说，这种样本特别适合研究如何从面向软件接口的工程描述中恢复状态机。因为它的状态并不靠传统传感器阈值切换，而更多依赖 `goal_status`、service client、topic 和异步模块协同，这有助于扩展数据集对现代机器人控制描述的覆盖面。

## 如果需要人工细读，建议怎么读

人工重读时，先直接看第 `9-10` 页 `Robot control` 和 Orchestrator 段落，把五个状态、各自的进入条件、`goal_status` 反馈、retry 逻辑和 `Dock/Undock` 服务链先整理出来。随后再补看第 `14` 页和第 `17` 页的实地实验总结，确认这套状态机确实在真实导览场景里跑通了完整的 undock、导航、dock 主链。

第一次回读时，不必把大量篇幅放在大模型交互、`mmWave` 感知原理或馆内硬件部署细节上。那些信息有助于理解系统背景，但如果目标是重做 `STM.md` 或复核案例边界，最优先的仍然是高层状态机、成功/失败分支和实地执行结果。
