# 航空航天与空管控制 / Formal Specification and Verification of a Coordination Protocol for an Automated Air Traffic Control System

## 论文在讲什么

这篇论文围绕航空航天与空管控制展开，当前 `STM.md` 抽到的核心对象是“自动空中交通控制系统中的冲突协调协议”。如果只抓一句话理解它的主体，可以先把它看成：这是航空交通控制领域的 AAC coordination protocol，用于在不同冲突时间窗下在 controller、AutoResolver、TSAFE 和 TCAS 之间分配与回收控制责任。

从现有条目看，文中的离散控制链主要以 `Protocol（协议/交互状态机）` 的方式出现，时间语义属于 `T2（强实时 / 显式时钟时间窗口）`。虽然主要样本集中在一条主链上，但原文对这条链的输入条件、执行动作和阶段衔接已有较明确交代。原文细节和可描述性目前分别被评为“🟡 B（细节较充实）”与“🟡 B（细节较充实）”，因此它更适合作为中等篇幅的系统说明材料，而不是只看题名或摘要就结束。

## 控制系统在文中的位置

它更接近论文的主控制对象或主案例载体，作者不是顺手举例，而是靠这套系统把设计、实现、验证或实验结果真正落到地上。

更具体地说，这篇论文里我们关心的控制系统描述，承担的是“把系统目标落成可观察控制流程”的角色。作者通常会把它写成若干状态、阶段、模式、顺序段或功能链，并把感知输入、执行输出、阈值条件、切换规则和异常/恢复路径交代出来；如果论文同时带有建模、验证或实验框架，这套控制逻辑也是连接那些方法章节与结果章节的中心骨架。

## 对我们为什么有用

对 `sources/` 来说，它的价值不只是“又多一篇相关论文”，而是补进了 `航空航天与飞行/空管控制` 方向的一类具体样本。它至少提供了一条可以和总表案例统计直接对应的主控制链，便于后续把论文级总账和案例级表格重新关联起来。

后续做数据集时，第一轮最值得盯住的不是所有工程背景，而是 `Protocol（协议/交互状态机）` + `T2（强实时 / 显式时钟时间窗口）` 这条主控制骨架本身：先把状态/阶段名、关键输入、输出动作、门控条件、时间阈值和异常分支抽稳，再决定是否补硬件接线、连续控制、性能曲线或实现细节。这样做能避免把 `DESC.md` 写成压缩版 `STM.md`，同时也能保住样本最核心的可复用部分。

## 如果需要人工细读，建议怎么读

如果后续需要人工细读，建议先看第 1-2 页 的摘要与引言，只确认系统边界、控制目标和论文到底是在讲系统设计、方法落地还是实验评估；然后直接跳到第 5-6、8 页 中和 `Section 3，对 AAC layered design 与责任分层的说明、Figure 4，对 `TSAFE_Alert` 变量取值的说明` 相关的部分，优先圈出状态/阶段名、输入感知、输出执行、guard、时间条件以及异常或回退链；最后再用第 9、11-12 页 的实验、仿真、验证或结果部分，核对这些控制步骤在完整场景里是怎样串起来的。

像第 2-4 页 里更偏飞行器动力学、导航估计、控制律推导和仿真性能的内容，通常可以放到第二轮再看。除非你是在追某个阈值、定时常量或切换条件的出处，否则第一次人工复核只需要先把主控制链读稳；即使 `STM.md` 之后需要重做，这条阅读路线也足够支撑人工重新把案例抽出来。
