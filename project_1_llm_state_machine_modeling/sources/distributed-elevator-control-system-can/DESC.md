# 基于 CAN 的分布式电梯状态机控制 / Development of the State Machine for the Distributed Elevator Control System Implementing Controller Area Network (CAN)

## 论文在讲什么

这篇论文研究的是一个没有中央 `CPU` 的多电梯控制系统。作者把楼层侧请求单元抽象成 `Stair-Object`，把每台电梯抽象成 `Lift-Object`，所有对象通过 `CAN` 总线互联；系统的关键不是集中式调度，而是让每台电梯都在本地运行同一套 `Elevator State Machine`，然后依据全网广播过来的状态决定自己要不要接单。

论文的写法很直接。它先介绍分布式电梯控制系统 `DECS` 的构成，再展开 `ESM` 的三状态模型和 `rank()` 逻辑，之后补充单梯 `PSM`、多梯时的服务优先判断，以及广播状态如何被编码到 `CAN` 消息里。也就是说，这不是一篇只讲通信或仿真平台的文章，而是一篇明确把调度逻辑和运动状态机写出来的控制案例文。

## 控制系统在文中的位置

我们关心的控制系统描述在文中是绝对核心。通信库、仿真库和可视化窗口只是为了支持作者验证 `DECS` 的运行，而真正要解决的问题是：当多个电梯共享同一批楼层请求时，每台电梯该如何在本地根据网络同步状态做出一致决策。

最有价值的部分是 `ESM` 和 `rank()`。前者把每台电梯压缩成 `UP / DOWN / STOP` 三个模式，同时把 `fr / cd / cf / rank()` 写成转移 guard；后者则说明为什么一个楼层请求虽然会被所有电梯接收到，但最后只能由一台最合适的电梯服务。这种“局部状态机 + 分布式仲裁”的组合在文库里辨识度很高。

## 对我们为什么有用

对 `sources/` 来说，这篇论文补的是楼宇电梯方向里比较少见的分布式样本。库里已有不少 `PLC` 单梯或群控电梯案例，但像这样把每台电梯做成自治对象、再用网络同步和 rank 计算来决定服务归属的条目并不多，能明显增加同领域内部的结构差异。

它也适合做 `EFSM` 样本。因为这里的状态不是单纯的“上下停”流程图，而是带有 `rank / fr / cd / cf` 这些扩展变量的条件转移；后续无论做自然语言建模还是做离散控制语义抽取，都能直接利用这组变量和 guard，而不需要额外从实现代码逆推。

## 如果需要人工细读，建议怎么读

如果后续要人工复核 `STM.md` 或重做样本，建议先看摘要和 `Elevator State Machine (ESM)` 段落，先确认三状态模型、四个核心变量以及 `STOP` 如何作为方向切换的中心节点。随后再看 `rank()` 一节，重点标出“请求广播给所有电梯”“只有 rank 为真者接单”“位置/方向/目的层向量如何参与比较”这几个判断点。

至于 `WinEL.exe` 可视化、`ELLib.dll`/`CanBusServer.dll` 软件封装和测试案例细节，可以放到第二轮再看。它们有助于理解作者怎样验证系统，但如果目标是抽取状态机样本，第一轮更值得优先锁定的是本地 `ESM`、分布式 `rank()` 和 `CAN` 广播后的同步决策链。
