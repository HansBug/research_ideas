# 铁路平交口 PLC 与 IoT 控制仿真 / Design and Simulation of a PLC and IoT-based Railway Level Crossing Gate Control and Track Monitoring System using LOGO

## 论文在讲什么

这篇论文讨论的是一个面向铁路平交口的自动门控与轨道监测系统。作者关心的核心问题不是抽象的“智慧交通平台”，而是怎样把来车检测、道口栏杆动作、道路信号灯、列车放行信号以及轨道故障提示整合进一套 PLC 控制链，并通过 LOGO 软件先做可运行仿真。

从正文组织看，论文把重点放在一条很工程化的控制路径上：轨道侧传感器检测列车到来，PLC 接收输入后驱动蜂鸣预警、栏杆闭合和道路信号灯切换；当列车离开后，再由另一侧传感器触发开门与信号恢复。也就是说，这里不是只给硬件框图，而是给了完整的“输入条件如何推动门控状态变化”的顺序描述。

## 控制系统在文中的位置

这个铁路道口控制器就是论文主体。`Hardware Design`、`System Operation` 和后面的仿真展示，都是围绕 PLC 如何接收轨旁传感器、如何驱动栏杆电机与交通信号展开，而不是把控制逻辑藏在外围平台或通信框架里。

对 `sources/` 来说，这一点很关键，因为不少铁路方向论文虽然也会出现 interlocking、monitoring、IoT 这些词，但真正能直接抽成状态机文本的往往只有几句概括。此文相对可用的原因，在于它明确写出了“来车检测 -> 预警 -> 关门 -> 道路转红/列车转绿 -> 列车离开 -> 开门复位”的主控制链，并补充了轨道故障与障碍检测如何接入同一 PLC。

## 对我们为什么有用

这篇论文补的是 `🚆` 方向里偏工程实现型的 `PLC + level crossing` 样本位。仓库中已经有较多联锁表、进路锁闭和形式化 route lifecycle 样本，但这篇的价值不在资源互斥，而在典型的道口执行控制链，它更接近“传感器触发门控和信号动作”的离散控制叙述。

它对后续数据集的帮助主要有两点。第一，控制对象、输入、输出和动作顺序都比较直白，适合做 `EFSM + T0` 的工程型样本；第二，论文还把轨道故障检测与移动端监测挂接在同一系统里，使样本不只是简单两态栏杆门，而是一个带扩展监测接口的门控控制器。

## 如果需要人工细读，建议怎么读

人工重读时，建议优先看第 `3-7` 页的 `Hardware Design using PLC and IoT` 与 `System Operation`。第一轮先抓稳三件事：哪几个传感器是状态切换输入；PLC 在来车与离车两个方向上分别输出哪些动作；道路灯、列车灯、蜂鸣器和栏杆电机之间的联动顺序是什么。只要这三点确认清楚，道口控制器的主状态链就已经足够稳定。

第二轮再回看图 `4` 附近关于 ultrasonic、RF、IR 传感器和 track fault 展示的文字，确认哪些是已经纳入 PLC 逻辑的输入，哪些更偏监测扩展功能。至于前言里关于铁路事故背景、自动化意义和 IoT 一般性介绍，可以放到最后补读，因为它们对恢复状态机主链帮助不大。
