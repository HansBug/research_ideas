# 铁路道口联锁五态状态机与安全性质 / Formal Verification of a Dependable State Machine-Based Hardware Architecture for Safety-Critical Cyber-Physical Systems: Analysis, Design, and Implementation

## 论文在讲什么

这篇论文研究的是一个安全关键铁路道口联锁系统，并把它同时放在状态机建模、形式化验证和硬件实现的语境里来讨论。作者选用铁路 crossing/interlocking 作为案例，持续监视 `sensor1`、`sensor2` 和主开关，然后根据列车是否接近、是否进入危险区、是否离开危险区，去驱动双栏杆、警示灯和 whistle 的输出。

从我们的角度看，最重要的不是 NuSMV 或硬件架构本身，而是论文把控制逻辑写成了很完整的五态有限状态机：`N / T / C / P / Q`。它不仅讲了列车到达 `sensor1` 时发生什么、穿越 `sensor1-sensor2` 危险区时发生什么、到达 `sensor2` 后又怎么变化，还把这些状态进一步翻译成 CTL/LTL 性质去检验。因此它是一篇“状态机与形式化验证都比较明确”的铁路执行层样本。

## 控制系统在文中的位置

控制系统描述在这篇论文里是核心案例。作者当然也关心“怎样验证”和“怎样映射到硬件”，但这一切都建立在前面的铁路联锁行为模型已经写清楚的前提上。也就是说，这篇论文不是先有一个抽象验证框架，然后随便挂一个铁路名词；相反，是先把 crossing controller 的输入、状态和输出组织出来，再用形式化性质去证明它满足要求。

这使它和很多偏 route-table、偏资源锁闭的铁路联锁文献形成了互补。后者常常更像资源生命周期或进路约束，而这篇文章则更接近“列车触发式执行机构控制器”，对象粒度更靠近实际道口设备，因此对状态机数据集来说是另一类很有价值的铁路样本。

## 对我们为什么有用

对 `sources/` 来说，它最大的意义是补了一条 `🚆` 领域中比较清晰的 `FSM + T0` 样本。当前铁路类文献里不少都偏 `Resource-flow`、进路锁闭或 Petri net/HCPN 风格，而这篇文章的状态机更加直白：输入是两个传感器和一个开关，输出是栏杆、灯光、蜂鸣器，中间则是清楚的状态切换与安全性质。

此外，这篇论文还能帮助我们保留“控制逻辑 + 形式化性质”同时可追溯的写法。它不是只给操作流程，也不是只给 CTL/LTL 公式，而是把两者一一挂接起来。后续如果需要构造“自然语言控制链 + 可验证性质”配对数据，这种样本会比只有流程图、没有性质约束的工程论文更有延展价值。

## 如果需要人工细读，建议怎么读

人工细读时，建议先从第 `6-7` 页的 `Section 3.1 / 3.2` 和 `Figure 5 / Figure 7` 开始。第一轮只确认四件事：列车到 `sensor1`、位于危险区、到 `sensor2`、以及两传感器都失效时，各自对应哪些输出动作；五个状态分别叫什么；哪几个输入和输出在状态机里被建模成布尔变量；主链是怎样从 `N` 走到 `Q` 再回安全态的。

之后再看第 `8-9` 页的 `CTL/LTL` 性质表与相关说明，主要目的是核对这些性质到底对应主链中的哪一段安全要求，尤其是 `sensor1` 触发后最终进入 `C`、`C` 如何保持到 `Q`、以及 `sensor1` 和 `sensor2` 不能同时有效这些约束。硬件综合与更一般的 verification workflow 可以放到第二轮再看，不必抢在控制链之前。
