# 应急车辆优先放行交通灯控制器 / FPGA - Based Emergency Traffic Light Controller System with IoT Application

## 论文在讲什么

这篇论文讨论的是一个基于 `FPGA + IoT` 的应急车辆优先交通灯控制器。核心问题不是普通固定配时，而是在救护车接近路口时，怎样利用声音和图像传感器及时切换信号灯，使目标方向得到绿灯通行，并把当前信号状态同步通知给驾驶员。

论文的控制对象是一个双向路口的 `NS / EW` 交通灯。作者把控制逻辑明确拆成两部分：一个状态机负责跟踪当前和下一交通状态，一个计数器负责实现不同状态之间的延时切换。这样一来，正文里不仅有“应急优先”的功能目标，还有足够明确的离散状态和时间规则可供抽取。

## 控制系统在文中的位置

这里的控制系统描述处于论文主体，而不是硬件陪衬。虽然文中也写了 `ESP8266`、`Blynk`、`DE-10 Nano` 等实现细节，但这些都是为交通灯状态机服务的。作者真正解释的是：两路传感器如何形成四种输入状态、这些输入状态如何决定 `NS / EW` 的灯色输出，以及黄灯和红灯延时如何帮助系统安全切换到应急优先模式。

对 `sources/` 来说，这一点很关键，因为它说明我们抽到的不是“IoT 通知 demo”，而是完整的路口交通信号控制器。状态机、计数器、灯色编码和恢复到初始流的逻辑都在原文里直接出现，后续可很自然地整理成状态机自然语言描述。

## 对我们为什么有用

这篇论文补的是 `🚦` 方向里一个很典型但又不只是普通配时控制的样本：它把应急优先、双传感器触发、显式计时和恢复主流程串到了一起。相比只有“哪个方向绿灯更久”的交通灯论文，这篇更适合用来训练或评估模型是否能同时保住输入分支、时间语义和恢复链。

后续做数据集时，最值得优先保留的是三部分信息：第一，`00 / 01 / 10 / 11` 四种输入状态；第二，`3 s` 黄灯与 `10 s` 红灯的工程定时；第三，应急车辆通过后恢复初始控制流。这三件事结合起来，刚好构成了一个典型的 `FSM + T1` 控制样本。

## 如果需要人工细读，建议怎么读

如果后续要人工复核 `STM.md` 或重抽案例，建议先读第 1 页摘要和引言，确认系统目标是“为 emergency vehicle 开辟绿灯通道”；然后直接跳到第 2-3 页 `3.2 Flow chart of the TLC system` 和 `Table 2`，把四种输入状态、`NS / EW` 输出变化以及 `3 s / 10 s` 的定时关系圈出来。

之后再看第 3-4 页的 simulation / hardware implementation 结果页，用波形和 LED 行为核对这些状态是否真的按正文所述执行。至于 `ESP8266`、`Blynk`、图像与声音识别算法这些内容，可以放到第二轮再看；第一次阅读只需要先把交通灯主状态链和恢复逻辑读稳。
