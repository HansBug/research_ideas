# STM.md 撰写规范

本文档用于固定 `project_1_llm_state_machine_modeling/sources/*/STM.md` 的当前写法、内容要求和判定逻辑。凡是从给定文献中提取“带有状态机要素的控制系统设计/描述/需求等自然语言内容”，都应遵循本规范。

> 说明：本规范只负责单篇 `STM.md`。进入具体论文目录前，应先阅读本论文集的 [README.md](./README.md)、[GUIDE.md](./GUIDE.md) 和 [SUMMARY.md](./SUMMARY.md)。

## 0. 与论文集级文档的关系

`STM.md` 不是孤立文件，默认位于 `sources/` 论文集中。后续 AI 在生成、补写或重写 `STM.md` 时，应按以下关系理解：

1. [README.md](./README.md)
   - 负责说明这个论文集为什么存在、该收什么、不该收什么。
   - 用于避免在方向层面误收不相关论文。
2. [GUIDE.md](./GUIDE.md)
   - 负责规定目录维护、筛选规则、[SUMMARY.md](./SUMMARY.md) 回填和整体工作流程。
   - 用于决定什么时候该补 `STM.md`，以及补完后怎么回写总账。
3. [SUMMARY.md](./SUMMARY.md)
   - 负责记录本论文集里每篇论文的实时状态、盘点结果和统计。
   - `STM.md` 的评级、条目数和备注最终都要回流到这里。
4. [STM_GUIDE.md](./STM_GUIDE.md)
   - 负责当前文件的判定标准、结构模板和证据写法。
   - 一旦涉及单篇抽取细节，以本文件为直接规范。

## 1. 目标与适用范围

`STM.md` 的目标不是复述整篇论文，也不是泛泛总结“论文用了状态机”。它的目标是：

1. 从论文原文中找出**真实控制系统**的设计描述、功能描述或需求描述。
2. 这些内容应当能够支撑后续构建**状态机自然语言需求/描述数据集**。
3. 每一条内容都必须能回溯到论文中的**具体页码、章节/图名、摘录原文**。

本规范适用于两种情况：

1. 论文中找到了可用的控制系统描述，此时需要写出一个或多个“条目”。
2. 论文中没有找到可用内容，此时也要留下“未收获”的检查记录。

## 2. 什么算目标对象，什么不算

### 2.1 算目标对象

优先提取以下对象：

1. 实际控制系统，如输液泵、起搏器、恒温器、自动变速器、刹车系统、飞机轮刹系统、分拣机、PLC 设备模块等。
2. 实际控制系统中的子系统、控制器、功能块、执行单元，只要它们确实承担控制职责。
3. 具有明确运行模式、阶段推进、条件切换、故障降级、恢复路径、时序约束的控制逻辑。
4. 用自然语言、状态图、自动机、TA/EFSM/ECC/Petri Net 等形式表达，但能够整理成控制系统自然语言描述的内容。

### 2.2 不算目标对象

以下内容通常不应提取为条目：

1. 开发流程、需求分析流程、验证流程、建模流程、代码生成流程。
2. 工具自身的模式、界面状态、工作流状态。
3. 纯方法论、纯架构分层、纯元模型说明，但没有实际控制对象行为描述。
4. “论文/实验/教学流程”的阶段，不是被控系统或控制器本身的运行逻辑。
5. 只能看出“有状态”但状态属于文档处理、需求管理、工具使用，而不是控制系统。

### 2.3 判定口径

判断“算不算我们关注的具有状态机属性的控制系统”时，至少同时检查以下三点：

1. **对象真实性**：对象必须是控制系统、控制器或控制子系统，而不是流程或工具。
2. **行为可组织性**：原文中要能看出模式切换、条件驱动、阶段推进、故障处理、时序约束或类似状态机属性。
3. **证据可追溯**：最终写入 `STM.md` 的每句话都必须能在原文里找到依据。

## 3. 提取前的阅读与证据原则

### 3.1 阅读顺序

推荐顺序如下：

1. 先读同目录下的 `bibtex.bib`，确认标题、作者、年份、会议/期刊、DOI、URL 等元信息。
2. 若目录下额外存在 `DESC.md`，可以快速浏览以建立主题印象，但不能替代原文阅读。
3. 再精读 `paper_content.txt`，以此作为 `STM.md` 的主要证据来源。
4. 如 `paper_content.txt` 提取质量差，优先用 `tools/pdf_extractor.py` 重新提取；必要时改用 OCR。
5. 如文本仍明显异常，应回到 PDF 原文核对，不得在证据不足时硬写。

补充要求如下：

1. 不推荐只看标题、摘要或少量关键词后直接开始写 `STM.md`。
2. 不推荐跳过 `bibtex.bib`，直接凭 PDF 首页手工拼元信息。
3. 若 `DESC.md` 与原文有出入，以 `paper_content.txt` / PDF 原文为准，而不是以 `DESC.md` 为准。

### 3.2 证据原则

1. `STM.md` 中所有判断、摘录、整理后的自然语言内容都必须以原文为依据。
2. 可以做**合理转接**，把原文中分散的句子整理成连续描述，但不能加入找不到原文依据的新信息。
3. 如果原文有 OCR 噪声，摘录时允许保留噪声；不要为了“更顺”而擅自改写引文内容。
4. 如果控制逻辑只出现在图题、图注、变量表、公式说明中，这些也可以作为证据，但仍需写清出处。

### 3.3 统一底线要求

无论具体论文写法如何，凡是提取控制系统状态机自然语言内容，至少都要满足以下底线：

1. 只提取真实控制客体。
   - 目标必须是实际控制系统、控制器或控制子系统。
   - 不得把开发流程、验证流程、建模流程、工具模式、需求管理状态或实验流程误当成状态机样本。
2. 所有内容必须可追溯。
   - 写入 `STM.md` 的每一条判断、摘录和整理描述，都必须能回到 `paper_content.txt` 或 PDF 原文。
   - 证据不足时宁可降级为 `🟡 可整理` 或 `⚪ 未收获`，不要硬补结论。
3. 文本质量异常时必须先修复提取。
   - 若 `paper_content.txt` 出现乱码、缺页、断裂严重或段落错乱，应先重新提取。
   - 默认先用 `text` 模式，不可用时改用 `ocr` 模式。
4. 整理后的自然语言要尽量贴近原文。
   - 允许做最小必要的连接、压缩和转述。
   - 不得编造原文中不存在的行为、状态、条件、时序或结论。
5. 必须明确区分“有收获”和“未收获”。
   - 找到可靠控制逻辑时，按正例条目写清证据、整理描述和逐句溯源。
   - 找不到时，也必须形成 `⚪ 未收获` 记录，不能留空不记。
6. 至少满足最低判定标准。
   - 至少应能识别出具体控制对象。
   - 至少应能识别出状态、阶段、模式、切换条件、触发事件、守卫条件、动作输出中的一部分。
   - 若内容只涉及连续控制性能、优化算法、诊断方法或系统架构，而没有明确离散行为逻辑，应谨慎判为 `⚪ 未收获` 或 `🟡 可整理`。

### 3.4 与新口径回填的关系

当前仓库已经把 `状态机类型 / 时间级别 / 结构标签 / 原文细节充实度 / 描述细节充实度 / 数据集角色 / 趋同标签` 直接写进每个正例条目，也把 `文件级角色 / 代表状态机类型 / 代表时间级别 / 结构标签概况` 写进 `## 盘点结论`。这些字段不是脱离原文额外脑补的标签，而是从论文原文阅读、条目判断和 [SUMMARY.md](./SUMMARY.md) 回刷结果中同步回填下来的固定参数。

后续回填的固定顺序是：

1. 先读 `paper_content.txt` 全文，必要时回 `paper.pdf`。
2. 先判 `状态机类型 / 时间级别 / 结构标签`。
3. 再判 `原文细节充实度 / 描述细节充实度`。
4. 最后才给 `💎 / 🧰 / 🪫 / ⛔` 与 `🔁 / 🪞 / ✨`。

这对当前 `STM.md` 写法有三个直接要求：

1. 每个正例条目都应让读者看得出它更像 `FSM / EFSM / HSM / Protocol / Resource-flow / Hybrid` 里的哪一类。
2. 若条目带关键时间语义、层次/并行/协议/资源互斥/连续耦合等结构信号，应在摘录和描述里保住这些事实，不要只留下平面流程感。
3. `### 2. 基于原文整理后的自然语言描述` 会被单独拿出来判“描述细节充实度”；因此**描述是否够丰富，只看这段描述文本本身**，不能拿原文摘录更丰富来替它补分。
4. 一旦 `状态机类型 / 时间级别 / 结构标签` 判定完成，它们就不只是“统计标签”，还应反过来约束第 `2` 节描述稿必须保住哪些建模关键件。
5. 对后续**每一篇新纳入文献**，若原文按当前规则可判到 `🟢 A` 或 `🟡 B`，则当前描述稿默认也应尽量做到不降级；如果因为抽取或改写把该类型/时间/结构所要求的关键要素压没了，这条 `STM` 就应视为“待重写”，不能算完成。
6. 更细的“类型化关键要素 / 降级条件”以 [2026-04-02-14-17-AI-讨论-sources文库STM数据集可用性与趋同问题系统分析.md](../discussions/2026-04-02-14-17-AI-讨论-sources文库STM数据集可用性与趋同问题系统分析.md) 第 `3.3` 节为准；本规范这里只保留最直接的执行提示。
7. 这套字段不是历史回刷专用动作；后续**每一篇新纳入文献**只要开始正式写 `STM.md`，就应在该文件中把文件级参数和条目级参数一次性补齐，不允许先写一个没有这些指标的临时版、再等以后统一补标签。

## 5. 各部分的具体写法

### 5.1 `## 盘点结论`

这是文件级的总判断，不是单条目的判断。

字段含义如下：

1. `评级`
   - 这是**文件级历史提取状态**，不是条目级数据集角色。
   - `🟢 直接可用`：控制对象明确，原文证据充分，能直接整理成高质量自然语言描述。
   - `🟡 可整理`：控制对象大体明确，但证据分散、图中文字较多、状态名不完整或摘录质量一般，仍可整理。
   - `⚪ 未收获`：没有找到符合要求的控制系统自然语言设计/描述/需求内容。
2. `文件级角色`
   - 这是条目级结果在单篇文件上的聚合结论。
   - `💎 含核心样本`：文件内至少有 `1` 条 `💎 核心保留` 条目。
   - `🧰 需清洗样本`：文件内暂无 `💎`，但仍有需补抽、重写或清洗的正例条目。
   - `🪫 主要用于降采样池`：文件内正例条目都已过线，但属于 `🔁` 强趋同采样池。
   - `⛔ 不作正样本`：整篇文件没有可入账正例。
3. `代表状态机类型 / 代表时间级别 / 结构标签概况`
   - 用于在单篇入口快速提示这篇 `STM.md` 当前最值得关注的建模画像。
   - 如果文件内部存在两个同等重要且性质不同的条目，允许用 `/` 并列表示。
4. `未收获原因类别`
   - 仅 `⚪ 未收获` 文件填写。
   - 当前固定类别为 `📉 连续控制/估计/优化主导`、`🛠️ 方法/工具/流程主导`、`📚 综述/标准/架构主导`、`🔍 目标控制链证据不足`。
5. `是否计入 SUMMARY.md 盘点`
   - 有实质条目时通常写“是”。
   - 未收获时写“否”。
6. `提取条目数`
   - 等于本文件中 `## 条目 n` 的数量。
7. `简要判断`
   - 1 句话概括整篇论文的提取价值或失败原因。

对后续新纳入文献，还要额外执行一条硬约束：

1. 只要该论文在本轮已经正式产出 `STM.md`，本节里的文件级参数也必须在本轮一并写好。
2. 如果当前是 `⚪ 未收获`，也不能因为“没有正例条目”就跳过文件级参数；`文件级角色 / 代表状态机类型 / 代表时间级别 / 结构标签概况 / 未收获原因类别` 仍然必须完整给出。

### 5.2 条目级参数条

每个正例条目在 `控制对象` 后面必须紧跟一组固定参数，字段顺序如下：

1. `状态机类型`
   - 必须写成 `英文标签 + 中文全称`，例如 `EFSM（扩展状态机）`、`HSM（层次状态机）`。
2. `时间级别`
   - 必须写成 `英文标签 + 中文全称`，例如 `T1（工程定时 / 局部定时）`、`T2（强实时 / 显式时钟时间窗口）`。
3. `结构标签`
   - 用中文标签列出；多个标签之间用 `、` 连接；没有额外标签时写 `-（无额外结构标签）`。
4. `原文细节充实度`
   - 必须写成 `emoji + 字母 + 中文全称`，例如 `🟡 B（细节较充实）`。
5. `描述细节充实度`
   - 同样必须写成 `emoji + 字母 + 中文全称`。
6. `数据集角色`
   - 必须写成 `emoji + 中文全称`，例如 `💎 核心保留`、`🧰 清洗后保留`。
7. `趋同标签`
   - `✨ 未见强趋同`、`🪞 邻近相似` 或 `🔁 强趋同（具体簇名）`。

这里要特别强调两点：

1. `原文细节充实度` 与 `描述细节充实度` 不是一回事，不能因为原文很强就把描述也写高。
2. 这些参数不是装饰；它们会直接被 [SUMMARY.md](./SUMMARY.md) 复用，所以命名和顺序都不能乱。
3. 对后续新纳入文献，这组参数默认必须在**首次完成该条目**时就写入，而不是留待以后由别的回刷任务补齐。

### 5.3 `### 0. 条目识别与判定`

这是每个条目必须具备的入口说明。

要求如下：

1. `一句话说明` 必须写清楚：
   - 所属领域；
   - 具体系统/子系统/控制器是什么；
   - 该对象在系统中负责什么控制任务。
2. `判断` 必须明确：
   - 这个对象到底算不算我们关注的控制系统；
   - 为什么算，或为什么只是“构件级样本”；
   - 为什么不算的情况，一般应放在“未收获”文件中，而不是正例条目里。

推荐写法：

1. “这是汽车底盘控制领域的自动变速器控制器，用于……”
2. “这是医疗设备领域的双腔起搏器控制系统，用于……”
3. “算。对象是实际控制系统，原文给出了……”
4. “算，但属于控制软件构件级样本……”

### 5.4 `### 1. 原文摘录`

这是最关键的证据区。

要求如下：

1. 每个摘录块必须有编号，如 `摘录 A / B / C`。
2. 每个摘录块必须写清出处：
   - 第几页；
   - 什么章节、图、表或段落；
   - `paper_content.txt` 中的行号范围。
3. 摘录内容使用 Markdown 引用块，即 `> ...`。
4. 摘录应尽量**完整、长一些、多一些**，宁可稍长，不要只摘一个关键词。
5. 摘录时优先保留原文上下文，以便后面的自然语言整理和逐句溯源有足够依据。
6. 若不同句子的依据分散在多个位置，应保留多个摘录块，不要强行拼成一段伪引文。

#### 高频补摘 checklist

结合前期降级条目回刷与最近前 `10` 条重写，以下几类信息被证明最容易在摘录阶段漏掉；后续凡是原文里出现，就应默认补进 `### 1. 原文摘录`：

1. **显式状态名与阶段名**
   - 例如 `idle / Entry / CalcSlipRate / Exit`、`idle / commanded / proved / occupied`、`LRI / AVI / URI / PVARP / VRP`。
   - 若状态名承载行为语义，不要只摘“系统经历若干阶段”这种概括句。
2. **精确 guard、比较式、阈值区间与赋值**
   - 例如 `v<5*(v-w*R)`、`v==0 [torqueABS=0]`、`0-30% -> 90 seconds`。
   - 对 `EFSM / Hybrid` 条目，这类内容通常必须有至少一段原文直引支撑。
3. **clock / timer / 周期触发 / timing-constraint 名称与边界**
   - 例如 `clk`、`clk_AnSw`、`exec = 2`、`period = 10 ms`、`event function T`、`BrakeDelayAtMasterNode = 130 ms`、`TLRI-TAVI / TAVI / TURI`。
   - 不能只摘“存在时间约束”，还要摘“谁触发计时、何时开始计时、何时复位、上界/下界是多少、超时后做什么”。
4. **异常、降级、恢复与 fallback 链**
   - 例如 retry 计数、priority tier、alarm、manual fallback、mode switch、释放条件。
   - 这类内容常散落在 requirement list、图注和正文段落中，必要时应多摘几块。
5. **接口读写节拍、端口映射与同步开始/停止**
   - 对构件级 TA / FunctionPrototype / block behavior，若原文区分 `read / execute / write`、`behstart / behstop`、`READ(Pin) / WRITE(Pout)`、输入/输出端口映射、更新阶段、`committed/urgent` 位置，应把这些执行节拍和接口语义单独摘出来。
6. **层次 / 并行 / 子模块 / 调度顺序 / 资源关系**
   - 例如四个 sibling movement machines、父子职责边界、`Thread A / Thread B`、`D1 / D2`、`mc=<ac,ts>`、printer 子模块、资源锁闭/释放条件、共享锁变量。
   - 不能只摘顶层摘要，而把真正决定结构的子机名、并发分支、调度顺序和资源规则漏掉。
7. **离散映射表**
   - 若控制逻辑是“输入区间/模式 -> 输出动作/持续时间”，要把整张映射补齐，不要只摘其中一两个 bucket。

### 5.5 `### 2. 基于原文整理后的自然语言描述`

这是最终要服务数据集构建的核心内容。

要求如下：

1. **默认用英文撰写**，因为目标通常是尽量保留原始论文的表达方式。
2. 必须基于第 1 节摘录内容整理，不得越界扩写。
3. 在允许的情况下，尽量直接使用原文或原描述的措辞。
4. 允许的改写仅限于：
   - 增加必要连接词；
   - 把分散在不同段落中的原文句子串起来；
   - 对明显重复的表达做轻微去重。
5. 不允许：
   - 引入原文没有的功能、变量、条件、阈值、模式名称；
   - 加入自己的解释性假设；
   - 把图中没出现的状态数量、迁移数量硬写出来。
6. 必须尽量把建模关键件直接写进这段描述，而不是只留在摘录里。
   - 若原文里的关键 guard、阈值、timer、异常回退、控制权交接、层次关系、资源互斥或连续耦合点对建模很关键，描述里就应尽量保住。
   - 否则后续在 [SUMMARY.md](./SUMMARY.md) 中很容易出现“原文细节充实度够，但描述细节充实度降级”的问题。
7. 正式写描述前，应先把当前条目的 `状态机类型 / 时间级别 / 结构标签` 当作一张保真 checklist，至少补核以下项目：
   - `FSM`：阶段划分、触发事件、阶段动作。
   - `EFSM`：关键变量、阈值、guard 比较关系、变量更新或控制动作。
   - `HSM`：高层模式、低层子状态/子机、父子关系、跨层触发或层间职责边界。
   - `Protocol`：参与角色、消息/命令、请求-授权-确认-返还的顺序，以及控制权变化。
   - `Resource-flow`：资源对象、占用/释放条件、冲突互斥关系、阻塞原因或使能条件。
   - `Hybrid`：连续变量、连续量物理含义、离散切换与连续侧的耦合关系，必要时保住控制律或演化方向。
   - `T1`：timer 的存在、启动/复位时点、时长、超时后的迁移影响。
   - `T2`：显式时间窗口、最小/最大持续时间、deadline / refractory、clock reset 点、多个 timer 的比较关系。
   - `T3`：连续时间演化本身，以及它与离散迁移共同决定系统语义这一事实。
   - `层次 / 并行 / 协议交互 / 资源互斥 / 显式时钟 / 连续耦合`：若条目带这些标签，描述里必须显式保住对应结构事实，不能在改写时压平成普通顺序流程。
8. 压缩时优先压缩修辞、背景说明和重复表达，不要优先压掉建模关键件。
9. 对后续新纳入文献，如果原文可判到 `🟢 A / 🟡 B`，则当前描述稿原则上也应维持在同级，至少不能因抽取过程丢掉关键要素；若出现描述降级，应继续补摘录或重写，而不是直接收口。
10. 行文上应写成“系统设计/功能/需求/描述”式自然语言，不要过于直白地写成：
   - “该状态机有 4 个状态”
   - “发生事件 e1 后从 s1 转到 s2”
11. 但如果论文原文本身就以这种方式表述，而且这是必要事实，则可以谨慎保留。

#### 高频降级点 checklist

结合降级条目回刷与最近前 `10` 条重写，描述稿最常见的降级方式不是“完全写错”，而是把原文中真正决定建模质量的细节压没。后续写第 `2` 节时，默认额外检查下面几类问题：

1. **状态名被压没**
   - 若状态名本身承载语义，应直接保留，而不是改写成“进入某阶段”“完成计算后退出”。
   - 特别是 lifecycle state、timing cycle、父子子机名、read/write stage。
2. **guard 被压成模糊条件**
   - 若原文给了精确 guard、阈值、区间边界或变量赋值，描述中也应尽量保留数值、比较方向和动作结果。
   - 不要把 `v<5*(v-w*R)` 写成“滑移过大时”，也不要把 `0-30% -> 90s` 写成“低密度时延长绿灯”。
3. **时间语义只剩“带定时器”**
   - 若原文给了 clock 名、周期触发参数、delayConstraint 名称与边界、reset 点、hold/restart 规则、deadline / refractory / execution time，描述中必须写清这些时间事实如何影响迁移。
4. **异常/降级/恢复链缺失**
   - 若原文有 retry、priority tier、alarm、manual fallback、release condition、mode switch、恢复返回路径，描述里不能只保 nominal path。
5. **结构被压平成单线流程**
   - 对 `HSM / 并行 / Resource-flow / Protocol` 条目，描述里应保住子机、角色、资源或并发事实。
   - 不要把四个 sibling 子机、共享资源锁闭、请求-授权-确认链压成一句“系统执行相应动作”。
6. **接口节拍与更新阶段缺失**
   - 对构件级 `EFSM / Hybrid`，若原文有 `read / execute / write` 节拍、输入/输出端口、变量映射、同步开始/停止、`committed/urgent` 位置或专门的变量更新阶段，应在描述中保住。
7. **并行链与调度顺序被压扁**
   - 对带 `并行` 标签的条目，若原文区分线程名、子模块名、局部调度表、时间戳命令或分支并发推进关系，描述里不能只写成“系统随后执行若干动作”。
8. **离散映射被压成“自适应调整”**
   - 对 bucket-to-action / bucket-to-duration 逻辑，描述中应保住完整映射或至少保住全部关键 bucket，不能只剩泛泛结论。

如果原文按当前口径可达 `🟢 A / 🟡 B`，但描述中仍丢了上述任一关键件，默认应视为**待继续补摘录或重写**，不应直接把该条目标成完成。

推荐标准：

1. 读起来像一段系统设计说明或功能需求说明。
2. 句子之间连续自然。
3. 每一句都能在前面的摘录里找到依据。

### 5.6 `### 3. 逐句溯源`

这一节用于保证最终描述是“句句可追溯”的。

要求如下：

1. 将第 2 节中的每一句话**完整复写**出来。
2. 对每一句标注其对应的摘录编号，如 `A`、`A, B`、`B, C`。
3. 这里的对应关系必须能回到第 1 节的原文摘录块。
4. 如果一句话依赖多个摘录，必须全部列出。
5. 如果某一句无法找到对应摘录，说明该句不应留在第 2 节。

## 6. 内容组织逻辑

实际提取时，建议按下面逻辑走：

1. 先确定论文里出现的候选对象是不是控制系统。
2. 再判断这个对象是否具有可整理的状态机属性。
3. 再收集原文证据，不要先凭印象写结论。
4. 最后基于原文写连续自然语言描述，并逐句回溯。

换言之，逻辑顺序是：

`对象识别 -> 目标判定 -> 原文摘录 -> 整理描述 -> 逐句溯源`

而不是：

`先脑补一个控制逻辑 -> 再去找相似原文`

## 7. 什么时候应判定为“未收获”

出现以下情况时，应直接写成 `⚪ 未收获`：

1. 找到的“状态”属于开发流程、需求生命周期、工具模式、工作流步骤，而不是控制系统。
2. 论文只有架构层面的模块关系，没有行为、模式、切换、时序或故障处理描述。
3. 文中虽然提到 automata / state machine，但对象只是形式化框架说明，没有实际控制对象的设计内容。
4. 只有图，没有足够正文或图注支撑，无法形成可追溯自然语言描述。
5. `paper_content.txt` 质量太差，而重新提取或 OCR 后仍不足以支撑可靠摘录。

## 8. 与 [SUMMARY.md](./SUMMARY.md) 的关系

当任务要求汇总时，`STM.md` 应作为 [SUMMARY.md](./SUMMARY.md) 盘点的直接依据。

通常需要从 `STM.md` 中汇总的信息包括：

1. 该论文是否有收获；
2. 文件级历史评级；
3. 提取条目数；
4. 每个正例条目的控制对象、结构特点与建模类型信号；
5. 每个正例条目的原文细节与当前描述细节是否足够支撑建模。

### 8.1 与 [SUMMARY.md](./SUMMARY.md) 字段的映射

后续回填时，至少要把 `STM.md` 中的以下信息映射回 [SUMMARY.md](./SUMMARY.md)：

1. `## 盘点结论` 中的 `评级`
   - 对应 [SUMMARY.md](./SUMMARY.md) 文件级总表中的 `原始评级` 列。
2. `提取条目数`
   - 对应 [SUMMARY.md](./SUMMARY.md) 文件级总表中的 `条目数` 列。
3. `简要判断`
   - 对应 [SUMMARY.md](./SUMMARY.md) 文件级总表中的 `文件级判断` 列，可压缩但不能改变结论。
4. 是否存在有效条目
   - 影响文件级 `💎 / 🧰 / 🪫 / ⛔` 聚合结果，以及 `⚪ 未收获` 专表。
5. 每个 `## 条目 n`
   - 对应 [SUMMARY.md](./SUMMARY.md) 条目级总表中的一行，不能漏账。
6. `控制对象` 与 `### 0. 条目识别与判定`
   - 影响条目级总表中的 `控制对象`、领域归类和是否属于目标控制系统。
7. `### 1. 原文摘录` 与对应论文原文
   - 共同支撑 `状态机类型 / 时间级别 / 结构标签 / 原文细节充实度` 的判定。
8. `### 2. 基于原文整理后的自然语言描述`
   - 是 `描述细节充实度` 的直接判定对象。
   - 如果这段描述把关键 guard、timer、异常链、层次关系或协议交接压没了，后续会被直接判为描述降级。
9. `### 3. 逐句溯源`
   - 用于证明描述没有越界扩写，也用于后续定位“是原文薄，还是抽取过程抽薄了”。
10. 文件级角色
   - 不是 `STM.md` 里直接填写的字段，而是由条目级结果聚合出来；但 `STM.md` 的条目质量会直接决定它最终落成 `💎 / 🧰 / 🪫 / ⛔` 中的哪一种。

这里再明确一条流程要求：

1. 对任何新纳入文献，上述映射关系都应在**同一轮**完成回写。
2. 也就是说，不能只把新参数写进单篇 `STM.md`，却不更新 [SUMMARY.md](./SUMMARY.md)；反过来也不能只改总表，不改单篇 `STM.md`。

### 8.2 半成品与异常情况处理

如果在写 `STM.md` 时出现以下情况，应如实记录，不要硬补：

1. 文本提取质量差但仍可判定无有效内容
   - 正常写 `⚪ 未收获`，并在 `## 检查说明` 或 `## 备注` 中说明文本质量问题。
2. 已确认论文应收录，但本轮没有足够时间完成 `STM.md`
   - 不要伪造结论；应在 [SUMMARY.md](./SUMMARY.md) 中记为 `⏳ 尚未提取`。
3. 图中信息丰富、正文不足
   - 允许依赖图题、图注和变量说明，但必须写清出处；若仍不能逐句溯源，则宁可判为 `🟡 可整理` 或 `⚪ 未收获`。
4. 存在多个候选控制对象
   - 只提取那些确实承担控制职责、证据充分、能形成可追溯自然语言描述的对象；不要为了凑条目数强行全收。

## 9. 当前仓库采用的风格总结

当前 `STM.md` 的写法固定为：

1. 标题、盘点结论、判定说明、出处说明用中文。
2. 条目标题通常用英文短语，便于快速概括控制逻辑。
3. `控制对象` 用中文写，强调对象是什么。
4. 原文摘录尽量保留英文原文。
5. 整理后的自然语言描述默认使用英文。
6. 逐句溯源用中文框架配英文句子。

后续新增或重写 `STM.md` 时，应保持这一风格一致。

## 10. 常见错误与最低完成标准

后续写 `STM.md` 时，至少要避免以下常见错误：

1. 把“开发/验证/实验流程”误当成控制系统状态机。
2. 只摘一个状态名或几个关键词，却没有足够上下文支持后续自然语言整理。
3. 在第 2 节“整理后的自然语言描述”里加入原文没有的模式名、阈值、守卫条件或控制动作。
4. 第 3 节“逐句溯源”没有把第 2 节中的句子完整复写，导致无法逐句核对。
5. 论文其实没有有效控制对象，却因为“出现了 automaton/FSM/statechart”几个词就误判为正例。

一个合格的 `STM.md`，最低应满足以下标准：

1. 能明确回答“控制对象是谁，为什么算控制系统样本”。
2. 至少给出足够支撑结论的原文摘录和出处。
3. 最终整理出的自然语言描述句句可溯源。
4. 能直接支撑 [SUMMARY.md](./SUMMARY.md) 中 `状态机类型 / 时间级别 / 结构标签 / 原文细节充实度 / 描述细节充实度 / 数据集角色` 的后续回填。
5. 对于原文可达 `🟢 A / 🟡 B` 的新条目，当前描述稿不得因为抽取过程丢掉当前 `状态机类型 / 时间级别 / 结构标签` 所要求的关键要素；否则只能算“待重写”，不算真正完成。
