## 1. 这次调研是干什么的，为什么现在做

**起点是导师 2026-08-13 给的两句话**：

> 实际工业应用是不可能把真实项目材料放到商业大模型上去用的
>
> 而工业应用场景中，很难去部署大规模的模型，没有专业的算力基础设施

**背景**：导师此前给了两条论文路线，第二条是「强调工业应用背景，使用私域部署的小规模模型，达到的效果能和最新的全量 llm 相当」。我方向导师报告说这条路线**说圆有困难**——「工业背景本身并不意味着要私域，而且 stm 这些事是软件设计阶段的事不是运行时的事，即便说清楚了私域，reviewer 也会立刻问你怎么不私域部署一个 600B 的模型」。上面两句是导师对此的**直接反驳**。

**本轮的职责因此被明确为一件事**：把这两句话**写成可引、可辩护的学术表述**——用什么措辞、引谁、放论文哪一节、审稿人会问什么、不能说什么。

⛔ **不在职责内**：判断这条路线能不能赢、方法有没有效果、该选哪个模型。用户 2026-08-13 明确「⛔ 不是让你非得教我做事告诉我我这个路不行」「至于是不是我能打得赢那不是你该考虑的问题」。

## 4. 学术口径：两句话怎么写

### 4.1 前提一「不外发」

**可用的英文表述**：

> In industrial settings, project artifacts such as requirements documents and design models are typically **not permitted to leave the organization's boundary** for processing by third-party hosted models.

**依据形态是产业实践，不是法规**——这决定了怎么引：

| 可引证据 | 内容 | 谁在用 |
| :-- | :-- | :-- |
| 三星禁用 ChatGPT 事件（CNBC） | 企业级禁令的公开事例 | **TOSEM 2025**（CCF A 刊）就是引它 |
| ABB Spec2Control | 自陈 "we cannot publish them" | 同域（NL → PLC 控制逻辑）自述实践 |
| CCS 2024（arXiv:2405.06371，27 人访谈，CCF A） | 记录「因保密改用本地 Llama」 | 唯一的访谈级实证 |

**放论文哪一节**：Introduction 的 motivation 段（一到两句）+ Threats to Validity 里显式承认它是 **assumption**。

⛔ **不得写成法规强制。** 法条层能支撑的只有「不能用**未获授权的**商用端点」（DFARS 252.204-7012 (a) 的 `Technical information` 定义逐字含 "engineering data… data sets" + NIST SP 800-171 Rev 2 §3.1.20 DISCUSSION 逐字点名 "software as a service"），**推不出「不外发」这条更强的实践**。

⚠️ **必须主动交代的同域反例**：ABB 那篇**同时用了 Azure AI Foundry 上的 GPT-5**。处置是限定场景（设备厂商内部工具链 ≠ 型号研制单位涉密制品）。**藏着不说比说出来更危险——它就在同一篇里。**

### 4.2 前提二「算力有限」

**这句最容易写坏。关键是：私域部署不等于「没有算力」，而是「有限、固定、不可弹性扩展」。**

> On-premise deployment implies a **fixed, dedicated compute budget** rather than elastic cloud capacity: capacity is procured once for a specific environment, cannot be shared across isolated segments, and cannot be scaled on demand.

| 可引证据 | 支撑什么 | 限定 |
| :-- | :-- | :-- |
| 工信部工信厅通信〔2026〕14 号逐字「针对**中小企业**在算力获取、应用落地和能力提升中的难点」，并推荐「训推一体机」「整合本地闲置、分散算力」 | 官方承认算力获取存在难点 | ⛔ 口径是**中小企业**，引用必须带此限定 |
| NVIDIA 10-Q（期止 2026-04-26，SEC EDGAR）逐字「No shipments of Data Center Hopper products to China occurred during the quarter」「effectively foreclosed from competing in China's data center compute market」 | 高端数据中心 GPU 可得性受限，是「算力有限」的**成因** | ⛔ 只作成因，**不得用来论证具体显存天花板** |
| **Weyssow et al., TOSEM 2025** 把「单卡 24 GB」写进 §3 独立成节、§4 方法论开篇、模型池筛选、直到结论句（逐字「QLoRA enables the fine-tuning of LLMs up to 34B parameters for less than 24GB of GPU memory」） | **固定算力预算可作承重前提**——最强形态先例 | — |
| REFSQ 2026 把预算收到 **6 GB** | 同上，更窄 | — |

⛔ **不得写「工业单位没有算力基础设施」**：有官方级反证——**浪潮 NF5868G8 官方页 1536 GB、可单机部署 DeepSeek 671B**；新华三一体机官方页覆盖 14B–671B。⚠️ 而这类一体机**正是工信部文件推荐给「算力有难点」群体的形态**。

### 4.3 合起来的研究问题形态

> 在一个**不外发**、**算力固定**的部署条件下，开源模型能否达到商业 SOTA 的水平？

**三个好处**：**不需要「必须小模型」**（只需包络固定，具体多大由实验设置给定）· **不需要论证任何具体天花板** · **反例不构成反驳**（它是部署条件而非全称断言，某单位有大算力不影响「存在这一条件」）。

⛔ **一条硬条件：不得同时兼享「工业界普遍状况」的修辞。** 工业单位实际算力**查无严谨来源**——四大中文库全部不可用（CNKI curl 返 000 · 万方仅 SPA 壳 · 百度学术 403 · 维普 404+登录墙）· 国产一体机官方材料**不公布显存与卡数** · 军工方向**零篇可引学术文献**。

⭐⭐ **而这个空白是结构性的，不是等更多调查能填上的**——本轮找到的三条真实分布（MLPerf 送测侧 · HuggingFace 297,135 人自报 · 公网暴露面）**采样机制都系统性排除企业内网**。**这正是「为什么陈述条件而非调查现状」的方法论正当理由。**（级别 **I**：机制解释为我方推断，三条来源本身为 M）

### 4.4 术语选择

**on-premise deployment** 首选（文献通用、不预设规模）· `self-hosted` 可用 · 中文用「私域部署」但**英文慎用 private**（易与 privacy-preserving 混淆）· ⛔ **`air-gapped` 只在真气隙时用**（强断言，我方无证据支撑其普遍存在）· ⛔ **避免 `local LLM`**（歧义，可能被读成跑在笔记本上）。

⚠️ **实证**：MDE/RE 侧 **1,029 份摘要**里，`self-hosted` / `air-gapped` / `locally deploy` / `data never leaves` / `sovereign` / `open-weight` **六类说法一次都没出现**——**这些术语在目标社区尚未成为惯用语，首次使用需给定义**。（**M**）

### 4.5 文献先例

**承重样板 3 篇**：**Weyssow et al., TOSEM 2025**（最强，见 §4.2）· **REFSQ 2026**（6 GB）· **ICSR 2025**（arXiv:2504.07907，真实工业伙伴，逐字「We had no available resources to fine-tune the larger model」「there was no need for a large scale compute cluster」「consumer GPUs as affordable business hardware」，**唯一落在单位级的证据**，判半承重；⛔ 通篇不给 GPU 型号与显存）。

⚠️ **对目标社区的冷判断**：MODELS / RE / REFSQ / SoSyM / REJ 共 **1,455 条题录、31 venue-年份**，只有 2 篇写出「因保密所以用本地模型」这条因果，**三篇全文到手全部判装饰、承重 0 条**。相对地 SE 期刊侧（TSE / TOSEM / EMSE）有 7 篇承重（⚠️ 其中 5 篇仅摘要级判定）。**故审稿人不会默认接受这条动机。**（**M**，除摘要级那 5 篇为 **S**）

### 4.6 审稿人会问什么

| 问题 | 答法 |
| :-- | :-- |
| 「Azure OpenAI 有 DISA IL6、Bedrock 有 IL5，公有云已合规」 | 那是**可用性**论证，不是**可接受性**论证；工业决策依据是甲方合同、内部审批与责任归属。并主动交代 ABB 反例 |
| **「你为什么不私域部署一个 600B 的模型」** | **正面接受**：可部署规模由**本文声明的算力预算**决定，本文在该预算下评估。⛔ **不要论证「大模型部署不了」**——有官方级反证 |
| 「你怎么知道工业单位是这个算力水平」 | **不声称知道**。这是**声明的部署条件**，不是对工业界现状的断言；理由见 §4.3 末 |
| 「小模型半年就被取代」 | 反手引 **Angermeir et al., ICSE 2026** 逐字「The only factor directly linked to LLMs was the usage of deprecated models, an issue **exclusive to commercial models**」。⛔ 这是**比较性事实陈述不是建议句**；且其 DOI 是死链（错源在上游预印本版权块），只引 arXiv 不写 DOI |
| 「换个模型还成立吗」 | 不存在「≥3 模型」的成文要求；EMSE guideline G6 是 `should`，只要求「用商业模型时加一个开放基线」——用开放权重本来就满足 |
| 「为什么不微调／蒸馏」 | 可驳回（四步全有 M 级引用），⚠️ 但须主动承认边界：**NL2TL 770M 微调 95%+ vs GPT-4 prompting 77.7%** 就在形式化侧 |

### 5.2 本项目的实验平台落在 T3

本项目可用 **4×H200**（141 GB/卡 = **564 GB 标称**）做实验。⛔ **这只是我们能跑多大模型的上限，不是论文叙事的一部分。**

**权重预算**（可复算）：$564 \times 0.92 - 20 - 12 \approx 487$ GB——其中 0.92 是 vLLM 默认 `gpu_memory_utilization`、20 GB 是 30K 上下文 KV 上界、12 GB 是激活 + CUDA graph + NCCL。对应 4-bit 可容约 **854B 总参**。（**I**，公式已给可复算）

⛔ **一条格式判据卡掉三个容量上的赢家**：**NVFP4 / MXFP8 内核是 Blackwell 原生，而 H200 是 Hopper**。vLLM 源码逐字 `SM90 falls through to … Marlin`、`the fallback dequantizes only the weights`，act dtype 硬返回 BF16 ⇒ **能跑、省显存、不省算力**。⚠️ 但「Hopper 无 FP4 张量核」这句**在 NVIDIA 官方文档里找不到显式否定句**，依据只有引擎行为侧——**引用时须如此表述**。（**M** 源码 / **I** 硬件断言）

⭐ **而这条判据几乎不打 2025 世代**：2025 世代 NVFP4 官方件**仅 1 个**、MXFP8 **0 个**、MXFP4 4 个（gpt-oss 四型）。它打掉的是 2026 世代容量排序的前三名。（**M**）

## 6. 实验可行性：能跑 ≠ 跑得动

### 6.1 权重与 KV 是零和的

| 候选 | KV/token | KV 预算 | 最大并发@30K |
| :-- | --: | --: | --: |
| `DeepSeek V4-Flash`（MLA-like，L=43） | **48.4 KiB** | 340 GB | **228.8** |
| `MiniMax M2.7`（**纯 GQA**，L=62，Hkv=8） | 248.0 KiB | 277 GB | 36.4 |
| `GLM-4.7-FP8`（GQA，**L=92**，Hkv=8） | **368.0 KiB** | 77 GB | **6.8** |
| `GLM-5.2`（MLA+DSA，L=78） | 87.8 KiB | 42 GB | 15.6 |

⭐ 两件只有读 `config.json` 才能发现的事：`M2.7` 的 `attn_type_list` **62 项全为 1**（全 softmax，**不能打混合注意力折扣**）；`nvidia/GLM-5.2-NVFP4` 的量化块**自带** `kv_cache_scheme: 8-bit float`。（**M**）

### 6.2 判据是激活参数，不是总参数

按 config 推算：`M2.7` **9.8B**（官方 10B ✓）· `V4-Flash` 16.0B · `GLM-4.7` **~32B** · `GLM-5.2` **~39B**。

⭐⭐ **文献里「大 MoE 低并发慢」的自变量是激活参数**，⛔ **而这四个里总参数与激活参数的排序是反的**——所以按「模型大 → 慢」的直觉会判错。`GLM-4.7` 是并发（6.8）与激活（3.3 倍）**两项同时最差**。（**I**，判据来自文献 + config 推算）

### 6.3 真实编排并发 = 6

`launch_cells_serial.sh` 的并发是命令行参数 `MAX`，闸门为 `while [ "$(jobs -rp|wc -l)" -ge "$MAX" ]`；**每格内部是顺序多阶段**，故在飞 LLM 请求数 ≈ 运行中的格数。**从 run record 实读：峰值在飞 = 6，21 次记录全为 6。**（**M**）

⭐ 推论：**并发 6 对除 `GLM-4.7` 外的所有候选都远未触及 KV 上限**，故瓶颈是**单序列 decode 吞吐**而非 KV 容量——与 §6.2 的判据一致。

### 6.4 端到端墙钟与两条前提纠正

**墙钟**：`V4-Flash` **4.05 / 7.13 h** · `GLM-4.7` **9.66 / 23.99 h** · `M2.7` **11.75 / 12.89 h** · `GLM-5.2` **拒绝估算**。朴素基线臂一律 ≤0.22 h（占主臂 7%），不是约束。

⭐ **唯一卡数完全对齐的实测**：MiniMax-M2.5 FP8 on **4×H200 SXM**，32K 档 TTFT **1.3 s**（1 req）→ 5.2 s（8 req）；单用户生成 **81 / 47 / 25 tok/s**（1/8/18 req）；`Capacity: 18 requests`。**且是关闭 prompt caching、关闭投机、满精度 KV 测的，即下界。**（**M**）

⛔ **两条对我方前提的纠正**（从 3637 份 run record 全量聚合，非估算）：

1. **输入被低估**——实测均值 **36.4K tok/次**、总 **132.4M**（我方此前按 108.6M 估）。
2. **「prefill 是主要成本」是错的**——**decode 占墙钟 51%–89%**（六档里五档 >68%）。故优化顺序是**投机解码 > 提并发（= 省 KV）> prefix caching > prefill 算力**。

⭐ **prefix caching 的真实收益（实测而非估算）**：3637 次调用里每个角色的 `system_prompt_sha256` **只有唯一取值**（逐字节相同），全实验**只有 5 个前缀**，合计 **48.9M tok = 总输入的 36.9%**。但乘上 prefill 只占墙钟 11%–49% ⇒ **端到端只省 4.2%–17.4%（0.5–0.7 h）**。⛔ 常被引的「TTFT 降 7 倍」是**单请求冷热对比，不适用**；受控并发 A/B 的真实数是 vLLM **+13.3% 吞吐**。**该开，但不是成败关键。**（**M**）
