## 一、核心定调：discover 独立成篇

我方原本的设想是 paper1 = issue discover + issue repair 两部分、两个独立子 loop，
并担心「repair 可能没有 discover 复杂，如果 repair 太简单的话怕不足以单独发、
还得和 discover 拼一个论文」。

导师两句话直接否掉了这个顾虑：

> **「discover 部分单独成一篇文章」**
>
> **「repair 不会简单的，特别是要高质量 repair」**

由此确定：

1. **paper1 收窄到 issue discover，单独成篇。**
2. **repair 另立后续论文**，不进这篇。本文只在讨论一节**捎带提及**可用于修复：
   > **「可以捎带提一下用于修复，但不宜多提，这篇文章毕竟不做这个。」**

导师还就方法本身给了一句判断：

> **「这个逻辑进一步印证了业务建模在其中的重要性」**

这句针对的是我方汇报的反面立论——**无脑自主 agent 不可靠且很吃基础设施；
把 pyfcstm 的裸工具直接给 agent 效果很差，AI 会乱用工具、一个劲乱摸索**。
最终解法是针对常见问题类型与性质类型定义十几种简单直白的谓词逻辑，
只准 agent 用这些写断言。**受限谓词词表本身就是一次建模**——这正是导师所指。

## 二、论文结构：那条「大逻辑」

> **「还是那个大逻辑：解决什么问题 == 为什么这个问题有价值 == 现有方法存在的问题
> == 你的方法 == 验证必须扣住问题特征和要 claim 的 contribution
> == 结果分析来支撑 contribution，并回到问题部分」**

`story/paper_outline.md` 的章节顺序按此排布，每节都要能回答「它服务哪条 contribution」。

## 三、Contribution 口径

### 3.1 导师点名的差异化叙述（直接用于 Intro motivation）

> **「这是个比较重要的 contribution，在论述时就要指出来：现有的很多 detection 方法
> 报告错误，缺少错误的上下文信息，一方面需要人工进行繁重的复核，
> 另一方面也不便于进行错误修复后的回归确认。」**

### 3.2 第一条 contribution：谓词元模型与断言体系本身

我方在讨论中提出（导师未反对，并以上面那句强化）：核心贡献不在于**发现了多少问题**，
而在于**定义了一套谓词逻辑元模型**，且最终产出不只是 issue，还包含**一条闭合的证据链**
与**一整套针对 NL 与 STM 的可执行断言体系**。断言由 NL 全覆盖拆分出的需求条目转换而来，
因此天然具备覆盖性；求值为假的那部分挂钩 issue，**为真的那部分构成回归防护**。

## 四、谓词词表的由来：论文怎么写

我方的顾虑是：谓词其实是在这批 pair 上归纳、并在代表性 pair 上调过 prompt，
担心被 challenge；曾考虑「不声称这个」。

导师给出的合法叙述是：

> **「规则一定是从领域分析归纳出来的，应用在 54 个案例中」**
>
> **「基于所归纳的规则，指导了 prompt 设计，这个逻辑能说通」**

由此确定的写法：**从领域分析、真实文献与技术资料调研归纳而来，应用于 54 个案例，
并据此指导 prompt 设计。**
⛔ 不表述为「从这批 pair 归纳」。工程侧的配套要求见
[../paper_stm_issue_discover/discover_matrix/docs/protocol/method_provenance_policy.md](../paper_stm_issue_discover/discover_matrix/docs/protocol/method_provenance_policy.md)。

📌 这部分是**后续论文要重点展开的内容之一**——需要把文献与技术资料的调研补齐，
把「这十几条谓词语义各自的领域出处」说通。

## 五、实验设计

### 5.1 模型数量：不追数量

> **「为什么一定要跑那么多 llm 呢？我觉得选择几个代表性的就可以了。
> 核心还是围绕论文的 motivation 和 contribution 来设计实验，并定义 RQ 来进行论述」**

由此：多执行模型的目的**只是证明方法对 LLM 的泛化性**，能证明即可，不追求覆盖面。
当前用 `claude-opus-4-7` 与 `gpt-5.5` 两个前沿模型。

### 5.2 fork / join：讨论中的建议与最终处置

导师当时的建议是：

> **「fork/join 这种效果差，是不是因为并发引起的问题，恰恰可以在 RQ 中进行专门的分析，
> 也是重要的 finding」**

我方当时的回应是：这东西 pyfcstm 不支持，也不好定义谓词逻辑，定义了也做不了判定，
处在落不了地的状态。

**最终采取的处置（2026-08-11 定）**：**不展开、不单开 RQ**。
改为在**问题定义阶段**就把建模对象的边界讲清——本研究锚定
$M = (S, E, V, Tr, A)$，不含时钟变量与正交区并发语义；那份要求 fork / join 与
秒级时间约束的需求，其忠实模型在 $M$ 中无法表达，因此它派生的 6 个 pair
**自然落在研究对象之外**，选语料时被自然排除，一句话带过即可。

理由是这样更干净：**根本不需要「这不是剔除不利样本」那套辩护，因为它压根不在对象内。**
⚠️ 但边界必须在论文里如实写明，且**不得反过来说「这些模型没有并发问题」**——
上游论文记录的最大一类语义问题恰恰是缺正交区。判据与证据见
[../paper_stm_issue_discover/discover_matrix/docs/protocol/nl_scope_rule.md](../paper_stm_issue_discover/discover_matrix/docs/protocol/nl_scope_rule.md)。

### 5.3 指标口径

`hit@1`（全部判定位的命中比例）/ `hit@3`（每个 pair 三轮中至少命中一次）/
`hit@all`（三轮全中）。三者必须同时报。

## 六、由此作废的旧口径

| 作废项 | 被什么取代 |
| :-- | :-- |
| paper1 = discover + repair 合成一篇 | discover 独立成篇；repair 另立后续论文 |
| 「repair 可能太简单、不足以单独发」 | 导师直接否定：「repair 不会简单的」 |
| 以 issue closure、regression audit、discover-and-refine loop 为核心贡献 | 谓词元模型与断言体系本身 + 缺上下文信息那条差异化叙述 |
| 「谓词表是从 60/54 pair 归纳出来的」 | 从领域分析 / 文献与技术资料调研归纳，应用于 54 案例 |
| 「多 LLM 越多越好」 | 选代表性的即可，围绕 motivation / contribution 设计 RQ |
| 把 fork / join 只当作「排除不利样本」并为之辩护 | 在问题定义阶段给出建模对象边界，语料自然落在界外 |
