# 状态机缺陷发现实验：设计、证据链与双侧结果

> 本文汇报一次完整实验的设计与结果。**自包含**：读完不需要跳转即可理解全部内容；
> 正文的 `[n]` 只在需要追溯原始材料时使用，条目见文末。
>
> 文中标 **【推论】** 的，是从测量结果推出的判断，尚未经导师确认。

---

## 一、这个实验在问什么

我们做的是一套**自动发现状态机模型缺陷**的方法：给定一份自然语言需求（NL）和一份由 LLM
从该需求生成的状态机模型，方法要自己读出「这个模型哪里不符合需求」，并把每一条发现
落成可机械求值的断言。

要回答的问题只有两个：

1. **它能找到多少已知缺陷？**（覆盖侧）
2. **它额外报出来的那些东西，是什么？**（多报侧）

第二个问题通常被简单处理成「误报率」。我们逐条读完了每一条额外产出，结论是
**这个简单处理是错的**——占比最大的一块既不是模型的缺陷，也不是方法的误判。

### 计数单位对照表

全文有若干个不同的计数单位，先一次说清，后面不再解释：

| 名词 | 是什么 | 本次的数量 |
| :-- | :-- | --: |
| **pair** | 一组「一份需求 + 一份待评审的状态机模型」，是实验的基本输入单元 | 54 |
| **格** | 一次完整运行 = 一个 pair × 一个执行模型 × 一轮 | 324 |
| **台账记录** | 人工标注出的一条已知缺陷，是覆盖率的分母单元 | 98 |
| **判定位** | 一条台账记录在一个格里判命中 / 未命中，= 记录 × 执行模型 × 轮 | 588 |
| **issue** | 方法发布的一条发现，逐格计数 | 1105 |
| **簇** | 把同一条发现在多个格里的重复出现合并后的单位 | 304 |
| **去重组** | 把同一 pair 内根因相同的多个簇再合并一层 | 124 |

⚠️ 「台账记录」与「簇」是**两侧各自的单位，不可互相换算**：前者是我们事先标注的已知缺陷，
后者是方法额外报出、事先没有对应记录的产出。

### 「作者」指谁

全文出现的**「作者」一律指生成被评审模型的那个 LLM**，即语料里那 6 个生成方之一。
上游论文的人类作者一律称**「上游论文作者」**。
这个区分在 §7 的判定链路里是关键：一条额外产出算「表示债务」还是「真漏记」，
取决于**生成该模型的 LLM 在它写的 PlantUML 原文里究竟写没写那个东西**。

## 二、实验语料：60 个 pair 从哪来

### 2.1 来源

语料来自一篇已发表的实证研究 [1]。该论文用两阶段框架（提示生成 + 模型检查反馈修复）
让多个 LLM 从自然语言需求生成 SysML 行为模型，并公开了完整的实验数据表 [2]。
我们只取其中的**状态机（STM）**部分：

- **10 份自然语言需求**，来自真实控制系统的需求描述（高层驾驶模块、制动子系统、
  泵控制、混合动力 SUV、列车控制、微波炉控制、无人机集群、避撞子状态机、
  数码相机、自动驾驶模式）；
- 每份需求**交由 6 个不同的 LLM 各生成一份状态机**——GPT-4o、GPT-4、Claude、
  DeepSeek、Kimi、Llama，取其**经模型检查反馈修复后的最终输出**，PlantUML 格式；
- 合计 $10 \times 6 = 60$ 个 pair，每个 pair 是一组「需求 + 待评审模型」；
- 论文作者还为每份需求**人工撰写了一份参考模型**（reference model，同为 PlantUML），
  并逐 case 记录了三类问题。

⚠️ **这里有两条容易混淆的模型轴，全文请区分**：

| 轴 | 是谁 | 数量 |
| :-- | :-- | --: |
| **生成方** | 写出被评审模型的 LLM，属于语料，我们不控制 | 6 |
| **执行方** | 跑我们这套发现方法的 LLM（§5.1） | 2 |

**pair 的编号约定**（后文大量出现）：四位数字，**十位标识生成方、个位大体标识需求**。
例如 `0000` 是 GPT-4o 为「高层驾驶模块」写的那份，`0010` 是 GPT-4 为同一份需求写的。
⚠️ **个位不是可靠的需求索引**：上游编号里「泵控制」与「混合动力 SUV」两份需求在
`0002`/`0003` 与 `0013`/`0012` 之间互换了位置。需求归属一律以每个 pair 的需求原文为准，
不要按个位推算。后文出现的 `0000-2` 这种带后缀的，指该 pair 上的第 2 条产出。

我们完整取用这 60 个 pair，不做筛选或改写。每个 pair 在我们这边保存为一个目录，含原始需求
`nl.txt`、作者提供的生成模型 `stm0.puml`，以及溯源元数据——记录它取自数据表的哪一行哪一列、
原始文件的 SHA-256 [3]。

**为什么用它**：这份语料有三个我们自己造不出来的性质——生成方是真实 LLM 而非人工注入缺陷；
缺陷分布是自然发生的；而且它带一个**独立的外部对照**（论文自己记录的问题清单），
可以用来检查我们的缺陷台账是否系统性漏掉了某一类。

### 2.2 为什么排除其中 6 个

10 份需求中有 1 份（数码相机）要求 **fork / join 并发结构与秒级时间约束**。
它对应的 6 个 pair——即 6 个生成方各自为这份需求写的那一份——被**先验排除**，
不进入本轮实验。

理由是**建模对象的边界**，不是样本取舍。本研究锚定的状态机形式为

$$
M = (S, E, V, Tr, A)
$$

即状态、事件、变量、迁移、动作五元组。它**既没有时钟变量，也没有正交区并发语义**。
那份需求所要求的东西，其**忠实模型**在 $M$ 里根本无法表达——我们无论如何都不可能对它
做出正确判断，留在分母里只会制造无意义的失败。

四点保证这不是「剔除不利样本」：

1. **判据先验**：只扫需求文本里是否出现并发 / 计时要求，在任何运行之前即可判定，
   与结果无关 [4]。
2. **按需求整体排除，不按格排除**：一份需求派生的 6 个 pair 同进同出。
   逐 pair 判定会留下「挑掉某几格」的空间，按需求判定没有。
3. **分布双峰且间隔极大**：那份需求有 11 处并发提及、17 处计时提及；
   其余 9 份中 8 份两项**均为 0**，剩下 1 份只有 3 处计时提及。
   不存在需要「调阈值」的中间地带。
4. **阈值不敏感（可复算）**：遍历阈值组合，**154 / 187 组给出完全相同的 6 个 pair**。
   唯一断点在计时阈值 3 与 4 之间——取 ≤ 3 会把那份只有 3 处计时提及的需求也拉进来。

另一个旁证：这个排除规则确立之前，曾有一轮把 60 个 pair 全跑过。在那一轮里，
`0018`（GPT-4 为数码相机需求写的那份）的命中率是 **12/18 = 66.7%**
（该 pair 有 3 条台账记录 × 2 个执行模型 × 3 轮 = 18 个判定位，命中 12 位），
**高于那一轮的全量均值 53.9%**。若目的是挑数字，不会把它一起排掉。
⚠️ 那一轮用的是更早的流程版本与更宽的判定口径，53.9% 与 §6.1 表中的两个数**都不可比**，
此处只用它做同轮内的相对比较。

⚠️ **这个排除有代价，必须一并写明。** 逐条回读被排除的 27 条台账记录，
**没有一条的主张真正需要并发语义**——它们多是「元素恰好叫 fork / join」的结构缺陷
（边声明、包含关系、守卫位置、命名作用域、数量断言）。也就是说，
**我们排除的是「规约」（因其要求 $M$ 表达不了的特性），不是「发现」**：
被排除的是那份需求，而它连带带走了 27 条本可判定的结构主张。

**换个排除口径会怎样？** 若改为「按记录逐条排除」，即只剔除那些**主张本身需要并发语义**的
记录，则符合该条件的记录数是 **0**——这 27 条会全部留在分母里，可判记录变成 125 条。
两种口径的差别因此是实的，不是零：**我们选的是更保守的那个**（分母更小，
但排除规则只依赖需求文本、不依赖任何记录的内容或表现）。
选它的理由是可审计性——按记录排除需要逐条判断「这条主张要不要并发语义」，
而那个判断发生在已经看过记录之后。

⚠️ 这条边界必须在论文里如实写明，并且**不能反过来说「这些模型没有并发问题」**：
恰恰相反，上游论文记录的最大一类语义问题正是「缺正交区」（18 条）[1]。
我们排除的是**我们无法判断的那部分**，不是不存在的那部分。

剩下 **54 个 pair** 构成本轮实验语料。

## 三、缺陷台账：expected issue 怎么来的

### 3.1 标注方式

台账是本实验的**能力分母**——它回答「这些模型里到底有哪些缺陷」。

标注是**全人工**的，对三份材料做三方对照：

| 材料 | 作用 |
| :-- | :-- |
| **需求原文** `nl.txt` | 义务的来源：需求要求了什么 |
| **被评审模型** `stm0.puml`（LLM 生成，上游作者提供） | 被检查的对象 |
| **参考模型**（上游作者人工撰写，同一份需求） | 对照：一个正确实现长什么样 |

标注者逐 pair 通读三份材料，把每一处「参考模型这样写、生成模型那样写、且需求支持前者」
记为一条 expected issue。每条记录保存**双侧原文**，例如：

> **参考侧**：`human_mode --> [*] : power_off` 与 `autonomous_mode --> [*] : power_off`
> **生成侧**：`[*] --> FinalState : Power Off`（唯一的 Power Off 边，源端是伪初始状态；
> 且 FinalState 是普通状态而非终态伪状态）

这样任何人只看这两行就能判断该条是否成立，不必重读整个模型。

### 3.2 每条记录带什么

一条 expected issue 至少含：缺陷的自然语言陈述、双侧原文、它属于 $M$ 的哪个元素、
归因层，以及一组**可机械求值的断言**。

**归因层**记录「凭什么说这是缺陷」，四类。
⚠️ 注意其中的 `over_specification` 说的是**被评审模型**多写了；
§7.6 里还会出现一个方向相反的「过度规定」，指的是**我们的断言**要得比需求多。
两者主体相反，不要混。

| 层 | 含义 | 条数 |
| :-- | :-- | --: |
| `nl_named` | 需求**逐字点名**了这个缺失或错位的元素 | 52 |
| `nl_contradiction` | 模型与需求直接冲突 | 13 |
| `wellformedness` | 合式性缺陷——不可达、缺省入口、命名塌缩等。**不从任何需求句子推出，看模型本身即可判定** | 27 |
| `over_specification` | 被评审模型比需求多要求了东西 | 6 |

**断言组**分三种角色：`primary` 陈述缺陷本身；`corroborating` 补第二个后果；
`negative_control` 证明 primary 不是恒为假（否则它对任何模型都「成立」，等于什么都没测）。

⚠️ **台账在这一点上远未达到理想状态，必须如实说明。** 98 条可判记录的实际断言构成是：

**按记录计**（分母 98 条）：

| | 记录数 |
| :-- | --: |
| 完全没有断言的 | 11 |
| 被标为不可自动化的 | 12 |
| 带 `negative_control` 的 | **2** |

**按断言个数计**（同一条记录可带多个）：

| 角色 | 个数 |
| :-- | --: |
| `primary` | 86 |
| `recovered_unverified`（从散文陈述恢复、本身不可求值） | 95 |
| `corroborating` | 14 |
| `negative_control` | **2** |

也就是说：**负控只覆盖 2 条记录**，而不可求值的散文恢复项比 `primary` 还多。
负控是设计上的要求，不是台账的现状。这意味着**绝大多数台账条目没有「primary 不恒假」
的独立保证**——判定时靠人工逐位复核补上，但这是人力保证而非机械保证。

### 3.3 分母

| | 条数 |
| :-- | --: |
| 台账全部 | 126 |
| − 落在被排除那 6 个 pair 上的 | 27 |
| − 逐条边界裁定剔除的 | 1 |
| **可判记录** | **98** |

台账全量 126 条的逐条内容（双侧原文、归因层、断言组）见 [5]。

那 1 条经独立裁定判为**表示层产物而非作者缺陷**——它反映的是我们中间表示的损失，
不是被评审模型写错了。判据只读模型与台账，与运行结果无关。两个口径的数字都给：
99 条口径下 `hit@1` = 60.8%，98 条口径下 = 60.4%。

⚠️ **54 个 pair 里有 12 个没有台账记录**：它们跑了，但不产生判定位，只用于多报侧统计。
**覆盖侧实际压在 42 个 pair 上。**
这 12 个为什么没有条目，台账本身不区分两种可能——标注时未认定缺陷，或标注欠账。
考虑到 §3.4 所述的整体缺口，**不应把它们读作「这些模型无缺陷」**。

**98 条记录在这 42 个 pair 上的分布**（回答「结论会不会被少数 pair 支配」）：

| | |
| :-- | --: |
| 单个 pair 最多的记录数 | 6 |
| 中位数 | 2 |
| 最集中的 5 个 pair 合计 | 24 条（24%） |

分布相当平——没有任何一个 pair 超过 6 条，前五名合起来才占四分之一。
**因此 §6 的分层结论不是由一两个 pair 支配的。**
按需求分组则不均：最多的一份需求有 17 条，最少的 5 条。

### 3.4 台账的已知缺口

台账不是缺陷全集。用上游论文自己记录的问题清单做外部对照 [1][6]：论文记录的语义类问题
共 50 条、散布 41 个 case，其中**有 24 个 case 我们的台账没有对应条目**。缺口最大的是
「缺正交区」（覆盖率 39%）与「缺状态/迁移」（14%）。

前者是 §2.2 说的建模对象边界；后者是**待补欠账**。因此本文所有覆盖率数字都应读作
「**在一个已知不完整的分母上的覆盖率**」。

## 四、方法：feedback loop 的结构

### 4.1 为什么要有循环

直接让 LLM「读模型报缺陷」会得到大量无法验证的自然语言断言。我们要的是**每一条发现都挂在
一个可机械求值的谓词上**，于是把过程拆成若干阶段，每阶段配一个审查者，不合格就打回重写。

**循环发生在审查者与被审查者之间**，不是简单重试：审查者给出**定向反馈**——哪一条不合格、
缺什么、期望什么形状——被审查者据此修订，而不是换个随机数重来。

### 4.2 流程

```
                  ┌────────────────────────────────────────┐
                  │                                        │ 定向打回
                  ▼                                        │
  需求 + 模型 → ① 需求拆分 ──────→ ② 需求审查 ─────────────┘
                                      │ 通过
                                      ▼
                  ┌────────────────────────────────────────┐
                  │                                        │ 定向打回
                  ▼                                        │
                 ③ 断言转换 → ④ 静态预检 → ⑤ 断言审查 ─────┘
                                              │ 通过
                                              ▼
                                          ⑥ 求值发布
                                              │
                                              ▼
                                          ⑦ 归因绑定
                                              │
                                              ▼
                                          ⑧ 结果裁决 ──→ 发布 issue
```

| 阶段 | 做什么 |
| :-- | :-- |
| ① **需求拆分** | 把需求原文切成一条条**义务**：「NL 第 4 句要求接管迁移存在」 |
| ② **需求审查** | 检查每条义务是否真有需求依据、是否可落成断言；不合格打回 ① |
| ③ **断言转换** | 把义务落成**闭合谓词词表**里的调用，如 `reaches(源, 目标, 步数)` |
| ④ **静态预检** | 机械检查：绑定的元素是否存在、参数是否合法；不合格打回 ③ |
| ⑤ **断言审查** | 检查断言是否真表达了那条义务、是否恒真恒假；不合格打回 ③ |
| ⑥ **求值发布** | 在模型上真正求值（结构查询 / 仿真 / 有界模型检查） |
| ⑦ **归因绑定** | 把每个 False 挂回它所依赖的模型元素 |
| ⑧ **结果裁决** | 决定哪些 False 够格发布成 issue |

⑥ 的求值不看需求也不看参考模型，只看被评审模型本身，所以它的真值是客观的。

⚠️ **⑥ 里的谓词可以「拒绝作答」。** 当一个谓词无法在给定模型上给出可靠真值时
（所需的形式化查询在该模型上不可判定、或超出求解预算），它返回**拒答**，
而不是猜一个真或假。拒答连同原因一并记录，并回灌给生产者作为改写依据。
这条设计避免了「求不出来就当成假、于是报一条假发现」——但它有一个副作用，见 §6.2。

### 4.3 关键约束：闭合谓词词表

断言只能用 **19 个预先定义的谓词**，不能自造。全表如下，按**求值机制**分三组
（实现里细分为五族，这里把只查静态结构的三族合并成一组）：

| 族 | 谓词 | 问什么 |
| :-- | :-- | :-- |
| **结构**（10 个）<br>纯结构查询，不执行模型 | `state_declared` | 该路径上是否声明了这个状态、是叶态还是复合态 |
| | `event_declared` | 是否声明了这个事件 |
| | `variable_declared` | 是否声明了这个变量 |
| | `edge_declared` | 是否存在这条（源, 触发, 目标）迁移 |
| | `containment` | A 是否被 B 包含 |
| | `initial_target` | 复合态的默认入口指向谁 |
| | `effect_declared` | 这条迁移上是否挂了这个效果 |
| | `action_declared` | 这个状态上是否挂了这个进入 / 持续 / 退出动作 |
| | `guard_distinguishable` | 同源同触发的几条边，守卫是否互相可区分 |
| | `cardinality` | 某复合态的子态数量 |
| **仿真**（6 个）<br>从上电开始执行 | `reaches` | 若干步内能否从 A 到达 B |
| | `occupancy_after` | 给定事件序列后，系统停在哪个状态 |
| | `event_consumed` | 这个事件在该状态下会不会被消费 |
| | `stays_in` | 给定触发到来时，是否仍停留在原状态 |
| | `terminates` | 给定前提下是否必然进入终态 |
| | `variable_delta_after` | 给定序列后某变量的增量 |
| **有界模型检查**（3 个）<br>在有界范围内穷举 | `invariant` | 界内某条件是否恒成立 |
| | `response_within` | 每次触发是否都在界内得到响应 |
| | `persists_until` | 某状态是否一直保持到给定事件到来 |

三族的证据强度不同：结构族给出的是「模型里写没写」，仿真族给出的是「跑起来会怎样」，
有界模型检查族给出的是「在有界范围内是否恒成立」。**只有后两族能回答行为性问题**，
而它们都要求模型具有可执行语义——这一点在 §7.5 会再次用到。

这条约束是刻意的：

- 它让每条发现**可复算**——任何人拿到模型和断言，能自己跑出同一个真值；
- 它让**测不了的东西显式暴露**——某条义务无法用这 19 个谓词表达时，系统必须记为
  「覆盖缺口」，而不是换个近似谓词蒙混过去。

代价是词表的表达力边界会限制能测什么，这一点在结果里有体现（§6.3 的变量类）。

⛔ **求值只在被评审模型上进行，全程不使用参考模型。** 参考模型只在人工标注台账时用过。
这保证方法不是在「对答案」。

## 五、实验结构与证据链

### 5.1 网格

$$
54\ \text{pair} \times 2\ \text{模型} \times 3\ \text{轮} = 324\ \text{格}
$$

- **2 个执行模型**：`claude-opus-4-7` 与 `gpt-5.5`，同一套流程、同一批输入，只换执行 LLM。
  用两个前沿模型是为了区分「方法的能力边界」与「某个执行模型的能力边界」。
  ⚠️ 这两个是**跑我们方法**的模型，与语料里那 6 个**写出被评审模型**的 LLM 是两回事（§2.1）。
- **3 轮**：同一格重复三次。LLM 有采样随机性，单轮结果无法区分「能找到」与「碰巧找到」。

一个「格」= 一次完整的 feedback loop 运行。

判定位 = (台账记录, 模型, 轮) 三元组，共 $98 \times 2 \times 3 = 588$ 个，每位判命中或未命中。
覆盖侧的另一个口径按 (记录, 模型) 计，共 $98 \times 2 = 196$ 对。

**这次运行的规模**：324 格全部跑完，累计 3621 次 LLM 调用，
输出 17.18M token、输入 163.4M token，节点累计机时约 88 小时（并发执行，墙钟约 7 小时）。
方法总共发布了 **1105 条 issue**（逐格计数，同一条发现在 6 个格里算 6 条）。
这 1105 条兵分两路：一部分被命中判定认领为「对应某条台账记录」，
其余的进入多报侧分析（§7）。

**降级格 9 个（claude 1 / gpt 8）**。「降级」指一格在内部配额（修订次数、审查轮次）
耗尽时，**不中止、不丢弃**，而是把已经拿到的产物封存落盘，并记下「哪条义务没走完、卡在哪」。
这样该格仍有产物、仍进统计，未完成的部分以结构化诊断的形式可分析。
反过来做（配额耗尽即整格失败）会让最难的样本系统性地从数据里消失——
而最容易耗尽配额的，恰恰是缺陷最硬的那些格。

三个指标各回答一个不同的问题：

| 指标 | 定义 | 回答 |
| :-- | :-- | :-- |
| `hit@1` | 命中位 / 588 | **一次运行的期望产出** |
| `hit@3` | 三轮至少命中一次的 (记录, 模型) / 196 | **该缺陷是否在能力范围内** |
| `hit@all` | 三轮全部命中的 (记录, 模型) / 196 | **稳定性** |

`hit@3` 高而 `hit@all` 低 = 能力够、稳定性不足；两者都低才是能力问题。**三者必须同时报。**

### 5.2 证据链：每一格留下什么

每一格是一个自包含的目录：

| 产物 | 内容 |
| :-- | :-- |
| **逐节点记录** | 循环的每一步一条：输入哈希、输出哈希、耗时、状态、失败原因 |
| **逐次 LLM 调用记录** | 完整 prompt、原始响应、token 用量、重试次数 |
| **最终产物** | 发布的 issue 清单、被排除的观察、覆盖缺口、降级诊断 |

**可关联性靠三样东西保持**：

1. **稳定 ID 贯穿全链**。一条需求有 id，由它派生的断言带该 id，发布的 issue 记录它依赖
   哪些需求与断言。任何一条 issue 都能反查到「它从需求哪一句来、经过哪些审查轮次、
   最后求值了什么」。
2. **内容哈希**。每个阶段的输入输出都记哈希，可验证中途没有被改动。
3. **判定与产物分离**。命中判定是一张独立的表（记录 × 模型 × 轮 → 1/0），每一位都带一段
   判据文字，说明凭哪条 issue、按哪种等价形态判的命中。判定表不改动产物，产物也不影响判定表。

于是对任意一个数字，追溯路径完整：

```
hit@1 = 355/588
   └→ 判定表某一位 = 1
        └→ 判据文字：「该 issue 陈述的命题与台账那条指向同一处作者源缺陷」
             └→ 该格的 issue #3 原文
                  └→ 它依赖的断言 id 与需求 id
                       └→ 该断言的求值记录与 LLM 调用原文
```

### 5.3 命中怎么判

**唯一标准**：我们的断言所表达的命题，与台账那条记录所表达的命题，**是否指向同一个作者源缺陷**。

不看谓词是否相同——台账建立于当前谓词体系之前，标签有代差。四种形态都算命中：
直接对应、合取项之一、负向命题的正向对偶、蕴含更根本的原因。

**明确禁止一种替换**：用「某条迁移是否存在」冒充「某个状态是否可达」。边存在不等于状态可达
（守卫可能恒假、源态可能不可达），边不存在也不等于不可达（可经其它路径）。两者形式相似
而实质不同 [7]。

588 位中 **568 位有逐位人工判据**，每位写明凭哪条产出、按哪种形态判的。
⚠️ 余下 **20 位只有判定结果、没有判据文字**（15 位判命中、5 位判未命中），
**不可逐格复核**——这是本次实验的一处诚实缺口，且其中 15 位落在命中侧，
方向对我们有利。

## 六、覆盖侧结果

### 6.1 总体

对照组是**同一套方法的上一个版本**，跑的是同一批语料、同一个网格。

⚠️ **这个对照是弱对照，两处必须先讲清楚，否则下表的差值会被高估。**

**其一，两版之间的差异不是单点改动。** 流程源码有二十余处修改，按影响面归为四类：

| 类 | 内容 |
| :-- | :-- |
| **运行语义** | 内部配额耗尽从「整格中止、无产物」改为「封存已有产物、带诊断落盘」——这**直接改变有多少格能产出结果**，是差值里最不像「方法变强」的一项 |
| **审查门之间的可满足性** | 消解了若干道门互斥的情形（存在「按门 A 改就违反门 B」的无解形状）；放宽一道门，允许已拒答的谓词换用替代主断言 |
| **证据形态约束** | 关系缺失类主张强制用结构谓词取证；撤销一条只看词法的校验（它会误伤合法写法） |
| **需求拆分的输出形态** | 「需求点名、模型未声明」的差集从散文表述升级为结构化槽位；谓词表增加「句子形状 → 谓词」的正向索引 |

**本次没有做逐项消融，因此不能把差值归给其中任何一项。**

**其二，两版的判定不同质。** 上一版有相当比例的判定来自自动匹配，本版几乎全部为人工逐位判定；
且上一版存在过宽判定——同一条产出被同时记给多条台账记录，包括它并未陈述其命题的那条。
按本版口径重判，上一版基线会从 274 降到 256。**下表用的是上一版的已发布值 274，
即对自己不利的那个取法。**

| 指标 | 上一版 | **本轮** | 差 |
| :-- | --: | --: | --: |
| `hit@1` | 274/588 = 46.6% | **355/588 = 60.4%** | **+13.8pp** |
| `hit@3` | 106/196 = 54.1% | **139/196 = 70.9%** | **+16.8pp** |
| `hit@all` | 77/196 = 39.3% | **95/196 = 48.5%** | **+9.2pp** |
| claude | 132/294 = 44.9% | 184/294 = 62.6% | +17.7pp |
| gpt | 142/294 = 48.3% | 171/294 = 58.2% | +9.9pp |

**采样噪声底**：逐轮 `hit@1` 为 59.2% / 60.7% / 61.2%，三轮极差 2.0pp。提升远大于它，
不太可能由轮间采样波动单独解释；但 $n = 3$ 且未计入需求族聚类，**这不是一个方差检验**。

⚠️ **算力必须一起说**：output token 从 9.91M 涨到 **17.18M（1.73×）**，
每百万 token 的命中位数从 27.6 降到 **20.7（−25%）**。
**单位算力的效率是下降的**，`+13.8pp` 不能整体归因于方法改进。

### 6.2 ⛔ 这个数字只能作为上界读

两条通道会让命中率虚高，方向都朝上：

**其一，一个不具判别力的谓词。** PlantUML **没有变量声明语法**，因此全部 60 份模型里，
作者自己声明的变量数是 **0**。于是「模型未声明变量 X」这个断言对**任何**模型都为真——
它区分不了有缺陷的模型与忠实的模型。筛查在**带逐位判据的那 340 个命中位**上做
（见本节末的构成说明），其中 **51 位（15.0%）** 的判据引用了它，
**10 位（2.9%）** 不依赖任何其它事实。另外 15 个无判据文字的命中位未被筛查到，
所以 51 是下界。

| 扣除 | `hit@1` |
| :-- | --: |
| 报告值 | 355/588 = **60.4%** |
| 扣掉仅靠该谓词成立的 10 位 | 345/588 = 58.7% |
| 扣掉引用了它的全部 51 位 | 304/588 = 51.7% |

**其二，求值层的拒答文案会回灌进生成侧的上下文**，其中包含极性与「把它发布出去」的指示。
这条尚未量化。

再加上 §5.3 那 20 位不可复核（其中 15 位是命中），**结论是：可写的只有
$\mathrm{hit@1} \le 60.4\%$，真实下界未知。** 论文里不得出现不带 ≤ 的 60.4%。

📌 **355 的构成**：人工判定表 574 条中 346 条判为命中；其中 6 条属被剔出分母的那条记录，
故分母内带逐位判据的命中为 340；另有 15 个命中位无人工条目。`340 + 15 = 355`。
上界筛查只覆盖那 340 条。

### 6.3 分层：哪类缺陷找得到，哪类找不到

**按归因层**

| 层 | 记录 | `hit@1` | `hit@3` | `hit@all` |
| :-- | --: | --: | --: | --: |
| `nl_named` | 52 | **70.5%** | 80.8% | 59.6% |
| `nl_contradiction` | 13 | 51.3% | 69.2% | 34.6% |
| `wellformedness` | 27 | **48.1%** | 57.4% | 35.2% |
| `over_specification` | 6 | 47.2% | 50.0% | 41.7% |

**【推论】** 需求点名的缺陷比合式性缺陷高 **22.4pp**。一个可能的机制是：**当前流程是需求
驱动的**——从需求句子形成义务，再落成断言。需求点了名的缺陷自然形成得了义务；而合式性缺陷
（不可达、缺省入口、命名塌缩）**不从任何需求句子推出**，要靠看模型本身发现，
而流程里没有这样一个入口。

⚠️ 但这个解释与另一个解释**在本数据上不可分离**：也可能只是合式性缺陷本身更难。
能分离两者的实验是明确的：**加装一条模型驱动的巡检入口后重测该层**。
另：分层样本量只有 6–52 条，未单独估计层内方差。

**按 $M$ 元素**

| 元素 | 记录 | `hit@1` |
| :-- | --: | --: |
| 事件 `E` | 6 | 77.8% |
| 状态 `S` | 26 | 72.4% |
| 动作 `A` | 18 | 67.6% |
| 迁移 `Tr` | 45 | **51.9%** |
| 变量 `V` | 2 | **8.3%** |
| 跨多个元素 | 1 | 0% |

迁移是最大的一类（45/98）也偏弱。变量几乎全灭，与 §6.2 同源：PlantUML 无变量声明语法，
变量类义务在这条链上本就难以成立。

**按谓词**（仅在**记录数 ≥ 5** 的谓词中取最高三个与最低三个；样本更小的谓词波动过大，未列）

| 谓词 | 记录 | `hit@1` |
| :-- | --: | --: |
| `containment`（包含关系） | 10 | 78.3% |
| `cardinality`（子状态计数） | 5 | 73.3% |
| `initial_target`（默认入口指向） | 14 | 69.0% |
| `guard_distinguishable`（守卫可区分） | 5 | 36.7% |
| `reaches`（可达性） | 8 | **31.2%** |
| `edge_declared`（边声明） | 7 | **31.0%** |

⚠️ **不要读成谓词选型建议。** 谓词与缺陷类型高度共线：`reaches` 主要用于合式性层的可达性
缺陷，它低不是因为「这个谓词不好用」，而是因为它承载的那类缺陷本身难。
要变成选型建议必须先做词表消融。

### 6.4 稳定性：一个双峰分布

98 条记录按命中格数（满分 6）分布：

| 格数 | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
| :-- | --: | --: | --: | --: | --: | --: | --: |
| 记录数 | **23** | 4 | 6 | 8 | 7 | 13 | **37** |

**明显双峰**：37 条满格、23 条零命中，中间四档合计仅 25 条。

**【推论】** 方法的行为不是「大部分缺陷有六成把握」，而是「一部分稳定找得到、另一部分完全
找不到、中间少量不稳定」。三个池子该做的事完全不同：

| 池 | 条数 | 状态 | 该做什么 |
| :-- | --: | :-- | :-- |
| 满格 6/6 | 37 | 能力已覆盖且稳定 | 无需投入 |
| 近满格 5/6 | 13 | 基本覆盖 | 低优先级观察 |
| 不稳定 1–4/6 | 25 | 能力够、稳定性不足 | 降低方差 |
| 零命中 0/6 | 23 | 能力缺口 | 补入口 |

零命中 23 条的层构成：`wellformedness` **10**、`nl_named` **7**、`nl_contradiction` 3、
`over_specification` 3。

⚠️ **其中 7 条在需求驱动层**，占零命中的 30%。**这是对「缺的只是模型驱动入口」这一读法的
反证**——补入口解决不了这 7 条。真实图景是两块缺口并存，后者的成因本次未定位。

⚠️ 本节与 §6.3 是**同一份数据的两个切面**，因此不构成独立佐证；但两者在同一方向上收敛。

### 6.5 两个模型的能力边界高度重合

| | 记录数 |
| :-- | --: |
| 两个模型都至少命中一次 | 64 |
| 仅 claude | 9 |
| 仅 gpt | 2 |
| 两个都未命中 | 23 |

只有 11/98（11.2%）是单模型专属。
（末行的「两个都未命中 23」与 §6.4 的零命中 23 条是同一批记录，非独立观察。）

⚠️ 但样本只有两个模型：对更强的模型能否解决，本实验不提供证据。

## 七、多报侧结果

📌 提醒：本节大量出现的**「作者」指生成被评审模型的那个 LLM**（见 §一 的说明），
不是上游论文的人类作者。


### 7.1 这一侧在问什么

方法发布的 issue 里，未被任何台账记录认领的那些，是什么？

朴素读法是「误报」。逐条读完之后，这个读法是错的。

我们先把这些产出合并成**同质簇**。合并判据是：**同一个 pair 内，指向同一个模型元素、
且陈述同一个命题**的产出算一簇——同一条发现在 6 个格（2 模型 × 3 轮）里的重复出现自然
落入同一簇，措辞不同不影响归并。方法在 324 格里共发布 1105 条 issue，其中未被任何台账记录认领的部分归并为 **304 簇**。

⚠️ 1105 与 304 不能直接相除算「误报率」：1105 是逐格计数（同一条发现在 6 个格里算 6 条），
304 是跨格合并后的簇数，两者分母不同质。下面所有比例都在 288 簇的内部计算。

去向：

| 去向 | 簇数 | 含义 |
| :-- | --: | :-- |
| 进入分析 | **288** | 下面五类裁定的对象 |
| 台账已承载 | 14 | 命中判定没把它认领给任何记录，但逐条回读后发现其内容已被某条台账记录覆盖——属判定层的漏认领，不是额外发现 |
| 真阴性 | 2 | 断言求值为真——模型满足了该义务，方法正确地没有报 issue |

### 7.2 五类裁定

每一簇必须落入且只落入五类之一，**没有第六类，也不设「待定」**：

| 类 | 定义 | 判据 |
| :-- | :-- | :-- |
| ✅ **真漏记** | 事实为真、作者确实没写、义务有出处、台账没记 | 四条**全中** |
| ⚙️ **表示债务** | 事实为真，但**作者在原始 PlantUML 里已经写了**——是我们的中间表示丢的 | 必须回读作者源并给行号 |
| 📄 **无需求依据** | 事实为真、作者也确实没写，但**需求没有要求它** | 属过度规定 |
| ❌ **假阳性** | **事实为假**——主张与模型相反 | 与上一类的唯一分界就是事实真假 |
| 🚫 **越界** | 主张的对象超出 $M = (S, E, V, Tr, A)$ | 时钟、不变式、正交区 |

### 7.3 判定链路

顺序不能颠倒，颠倒会系统性判错。每一步排在那个位置都有理由：

```
零步  内容已被台账记录承载？
      → 是：不属额外发现，移出（14 簇）

①    事实在被评审模型上客观为真吗（含动作，须读全文）？
      → 否：❌ 假阳性
      ▸ 排第一：事实为假时，后面所有问题都没有意义

②    主张的对象在 M = (S, E, V, Tr, A) 内吗？
      → 否：🚫 越界
      ▸ 排在归属之前：越界主张不必再去回读作者源

③    断言索要的**范畴**对吗？
      （需求称之为条件却索要事件、称之为动作却索要事件、
        合取项被索要成三个独立触发）
      → 错：📄 无需求依据
      ▸ ⛔ 这一步最容易被省略，而省略它的代价最大——见下

④    同一缺口已由本 pair 另一簇以**正确范畴**承载了吗？
      → 是：📄 无需求依据（只计一次，注明由哪一簇承载）

⑤    作者在原始 PlantUML 里表达过**这条需求义务**吗？
      → 是：⚙️ 表示债务      ← 必须给作者源行号
      ▸ 排在 ⑥ 前：作者写过，就不必再问需求有没有依据

⑥    需求真的要求这件事吗？
      （需求层主张要逐字需求；合式性主张的义务来自形式化本身）
      → 否：📄 无需求依据
      → 是：✅ 真漏记
```

⚠️ **③④ 必须前置于 ⑤，否则范畴错置与合取拆分会被短路成表示债务。**
这两类合计 41 条目，占「无需求依据」的 34%——若把归属判断提到范畴之前，
它们会整批流入表示债务，46.5% 与 41.3% 这两个数字随之改变。

⚠️ **⑤ 问的是「这条需求义务」，不是「断言字面索要的那个标识符」。**
两者不同：作者写了 `extra_lane=true`（义务已表达），但没写一个名叫 `extra_lane_true`
的事件（断言字面所求）。按后者读，几乎所有簇都会被判成「作者没写」。

**③ 的关键子判据是逻辑连接词**——事实为真、且作者源含该文本时，看作者用的是什么连接：

| 作者写法 | 拆开是不是正确修法 | 落点 |
| :-- | :-- | :-- |
| **析取**（`\|` / `\|\|`），且各支逐字写出 | 是——融合后无法只凭其一激活 | ⚙️ 表示债务 |
| **散文 "or"**，需求未给标识符 | 否——报告者必须自造分型名，造名空间无上界 | 📄 无需求依据 |
| **合取**（`&&` / 散文 "and"） | 否——拆开会把 AND 变成 OR | 📄 无需求依据 |

**这条子判据优先于 ⑤。** 不写死它，同一份需求下 6 个模型的同形簇会按判定人分裂——
作者的守卫写法六份完全同形，判定却可能一半落债务、一半落无需求依据。

### 7.5 ⚙️ 表示债务：46.5% 的那一块是什么

这是本次实验中占比最大、且此前未被识别的一块，需要解释清楚。

**先讲清楚这块的前提：什么是「中间表示」。**

作者交付的模型是 **PlantUML**。PlantUML 是一种**绘图记法**——它规定图怎么画，但**不定义
执行语义**：没有「一步」的概念，没有事件消费规则，没有守卫求值次序。因此
「从上电起 3 步内能否到达状态 X」「某状态是否在事件 e 到来前一直保持」这类问题，
**在 PlantUML 上无法回答**，不是难以回答，是问题本身没有定义。

而我们的方法要求每条发现都可机械求值（§4.3），其中相当一部分谓词需要仿真或有界模型检查。
所以流程先把 PlantUML **编译成一个带形式语义的状态机 DSL**，谓词在这个 DSL 模型上求值。

这次编译**不是无损的**——两种记法的表达力不重合，作者能在 PlantUML 里写出的一些东西，
DSL 装不下，只能压缩或改写。典型有三种压缩和一种注入：

| 子类 | 编译时发生了什么 | 条目 | 去重 |
| :-- | :-- | --: | --: |
| `D1` **析取备选融合** | 作者写 `A or B` 作为触发，编译压成**单一原子事件名**（如 `A_or_B_detected`），两个备选各自不再作为独立事件存在 | 61 | 9 |
| `D2` **原子子表达式不可寻址** | 作者写了带量的守卫（如 `dist < 15`），编译后**该量无法被单独指涉**——只能整体判断守卫，不能问「那个变量声明了吗」 | 50 | 12 |
| `D3` **槽位焊死** | 触发与效果两段被压进一个名字，之后无法区分「谁触发」与「做了什么」 | 18 | 4 |
| `D5` **跨通道打包** | 一条产出同时跨越上面多种情形（如既有融合事件、又涉及边声明），无法归到单一子类 | 4 | 4 |
| `D4` **结构注入** | 与上面相反：编译**加入了作者没写的结构**。该 pair 里作者写了两个并发区，编译把它们摊平成顺序嵌套，并在外层注入一个伪初始状态与它的初始边——于是「进入外层后首先落到哪」变了，冷启动可达性随之改变 | 1 | 1 |

**于是发生的事情是**：断言在 DSL 模型上求值，看到「模型里没有事件 `A`」——
这个求值结果**是真的**，DSL 模型里确实没有；但作者的 PlantUML 里写了 `A or B`。
所以**方法没有误判，被评审模型也没有缺陷，出问题的是中间那次编译**。

**为什么不直接在 PlantUML 上求值？** 因为那样就只能做词法与结构匹配，
仿真与有界模型检查两组（§4.3 表中的后 9 个谓词）全部做不了。这两族在覆盖侧的分量可以算：
**按主谓词计，355 个命中位中 85 位（23.9%）由这两族承载**；
**按「该台账记录的断言组里含任一这两族谓词」计，为 150 位（42.3%）**。
两个口径都不算小，且它们对应的正是可达性、保持性、终止性这类**只能靠执行语义回答**的义务。
换言之，这 46.5% 不是可以简单绕开的：**它是「要形式化求值」这个选择的伴生代价。**

⚠️ **这块的归属需要导师裁定。** 它既不是被评审模型的缺陷，也不是方法的误报，
而是工具链的损失。三种处置各有后果：

1. 从多报侧分母中扣除——但那等于把工具链缺陷藏起来，且扣除后 precision 会显著虚高；
2. 计入误报——但会低估方法在**作者原文**层面的准确性；
3. **单独成类报告**（本文的做法）——代价是读者必须理解中间表示的存在。

**判定这一类靠一条硬规则**：⛔ **回读作者写的 PlantUML 原文，不读编译产物。**
只读编译产物会把编译损失当成模型缺陷。

**案例一（`D1`，6 格全中）**

作者写的是（`stm0.puml` 第 13 行）：

```
AutonomousMode --> HumanDrivingMode : Human Steering Cmd, Brake Pressed, in (AutoFinal)
```

三个并列项。编译产物里只剩一个事件：

```
event Human_Steering_Cmd_Brake_Pressed_in_AutoFinal
      named "Human Steering Cmd, Brake Pressed, in (AutoFinal)"
```

方法报「`Human_Steering_Cmd` 未作为独立事件声明」——**事实为真，且作者确实写了**。

**案例二（`D2`，6 格全中）**

作者在三处写着 `Front Distance <= 10` 与 `Front Distance > 10`，这是一个被比较的**量**。
编译把它改建成了两个事件，而该模型的中间表示里**一个变量声明都没有**。
需求逐字写 `when front_distance > 10`。方法报「未声明变量 `front_distance`」——同样是真的。

📌 这个案例还给出一条方法论提示：按 `front_distance` 去检索作者源会**零命中**，
因为作者实写的是 `Front Distance`（大写、有空格）。**词法检索会漏，第 ③ 步必须逐行读。**

**【推论】** 这一发现的价值不在数字本身，而在于它把「有些多报不是模型的错」
**从一句 threats 段落变成了一个可扣除的量**：给定一条评审链、一个语料、一个检测器，
能算出多报里有多大比例应归因于中间表示。

⚠️ **现象本身不是新的**，既有文献已有名字：CEGAR 的 spurious counterexample [9]、
静态分析框架的 program representation fault [10]、模型驱动工程里的 semantics preservation。
我们的新处只在把它做成**评测归因侧的可扣除量**。三点限定：它不是过近似造成的伪反例；
不是工具 bug；落点在评测归因这一环，不在建模或验证环节。

⚠️ 这个比例**不宜外推**——一条链、一个语料、一个检测器。论文里应当主张的是**审查动作**
（评审入口若是中间表示，就必须做这项扣除），不是这个具体数字。

### 7.6 📄 无需求依据：**我们的断言**要得比需求多

（方向与 §3.2 台账里的 `over_specification` 相反：那条说被评审模型多写了，这里说我们多要了。）

| 子类 | 含义 | 条目 | 去重 |
| :-- | :-- | --: | --: |
| `N-SPLIT` | 要求把**合取**条件拆成独立元素 | 33 | 13 |
| `N-CTX` | 语境/状语措辞被抬成同名元素 | 18 | 13 |
| `N-FORM` | 义务已兑现，只是换个形态实现 | 16 | 8 |
| `N-SPLIT-PROSE` | 散文并列，需求未给标识符，报告者须自造名字 | 16 | 2 |
| `N-ANCHOR` | 义务被锚到错误的元素上 | 13 | 9 |
| `N-FUSE` | 融合类主张但不满足债务条件 | 8 | 8 |
| `N-KIND` | 范畴错置：把被比较的量当事件、把输出动作当输入事件 | 8 | 7 |
| `N-META` / `N-CLOSED` / `N-MODAL` | 元层要求 / 闭词表边界 / 情态误读 | 7 | 7 |

**案例（`N-SPLIT`，5/6 格）**：模型里的事件名是
`front_inactive && rear_inactive && pedestrian_inactive`——作者写的是一条**合法的合取守卫**。
需求原文 `as indicated by the conditions front_inactive, rear_inactive, and pedestrian_inactive`
**是合取**，一条合取守卫就是忠实编码。方法要求拆成三个独立事件——**拆开反而错了**，
因为那会把 AND 变成 OR。

**案例二（`N-CTX`，跨 4 个生成方同形）**：需求第 4 句是
`During flight, ...`——`During flight` 是个**语境状语**，交代后面那句话发生在什么时段，
需求并没有把「飞行」命名为一个可占据的状态；该需求点名的状态只有搜索、编队调整、攻击三个。
方法把这个状语字面抽成了一个状态名，于是报「模型缺 `Flight` 状态」。
事实成立（模型里确实没有），但需求没要求过它。
⚠️ **这一条的同形出现在同一份需求的 4 个不同生成方上**——说明它不是某份模型的偶然，
而是「散文状语 → 具名元素」这条抽取路径的系统性倾向。

**案例三（`N-FORM`）**：需求要求某状态「持续执行目标搜索」。模型用**驻留在该状态本身**
表达了这件事，而方法要求它落成一个显式的 `during` 动作声明。义务已兑现，只是形态不同。
⚠️ 这一条还暴露了另一个问题：**送给断言的证据包只有状态 / 事件 / 变量的路径表，
不含进入 / 持续 / 退出动作的声明清单**，所以断言即便想核也核不了——
这不是提示措辞问题，是证据包的字段缺失。

**【推论】** 这一类去重后占 54.0%，是**真正需要整改的地方**。
从上面三个案例看，它至少含两种成因：**提示侧的抽取倾向**（案例一的合取拆分、
案例二的状语抽名）与**证据包的字段缺失**（案例三）。前者可通过提示与评审条款收敛，
后者必须补字段。⚠️ 两者各占多少尚未拆分，这是下一轮要做的。

### 7.7 ❌ 假阳性只占 8.0%

子类按**断言的四个槽位**中哪一个出错来分：一条断言要指定「用哪个谓词、
指向哪个元素、该元素属哪个类别（状态 / 事件 / 动作 / 变量）、锚在哪个位置」。

| 子类 | 含义 | 条目 | 去重 |
| :-- | :-- | --: | --: |
| `FP-N` 名字槽差 | 同类别承载者在场，只是标识符字面不同 | 15 | 12 |
| `FP-K` 类别槽差 | 承载者以动作存在，断言按事件索要 | 5 | 5 |
| `FP-0` 零槽差 | 四槽全对、属性实际成立，断言仍判假 | 2 | 2 |
| `FP-A` 锚点错置 | 触发只能锚在源态，断言锚到了目标态 | 1 | 1 |

**案例**：方法报「无 `power_on` 事件」。模型确有 `event start` 与
`PoweredOff -> Operate : /start`，而需求逐字规定的信号名就是 `start`——需求另一句里的
`powered on` 是同一刺激的散文表述。**主张与模型相反。**

条目/去重比 1.15——**不在同一处反复出现**，故不是某个 pair 的固定偏差；
但失效**形态**是系统性的：四类可命名，65%（15/23）落在「名字槽差」。

### 7.8 🚫 越界只占 3.5%

这一类是**主张本身落在建模对象 $M$ 之外**——不是模型错了，也不是我们判错了，
而是那条主张问的东西 $M$ 根本不表达（§2.2）。三个子类：

| 子类 | 含义 | 条 |
| :-- | :-- | --: |
| **扁平化读法** | 主张成立与否取决于「把并发区拍平成一条链」这种读法，换成区感知读法就不成立 | 6 |
| **区计数** | 主张是对状态数量的断言，但计数结果依赖如何看待并发区的划分 | 2 |
| **不变式** | 主张需要「在所有时刻恒成立」这一形式，而 $M$ 不含不变式 | 2 |

10 条越界簇落在 5 个 pair 上，其中 3 个属同一份需求。

⚠️ **这个数字不能用来论证语料已经扫干净。** 两个理由：
其一，它是**用方法自己的产出去衡量语料的范围**——方法不擅长表达的东西本来就不会被它
报成越界，属自证；其二，这 10 条的分布明显不均（一个 pair 独占 6 条）。
能说的只有：**方法在剩余语料上没有再报出成规模的越界主张。**

⚠️ 这也**不构成**对 §2.2 那次排除本身的检验——被排除的 6 个 pair 不进网格，
按构造不产出任何簇。

### 7.9 ✅ 真漏记：全部净增量只有 2 条

**案例一**：某模型的 `EmergencyStopping` 状态里**没有任何进入/持续动作**，而需求第 3 句
要求「进入该状态并**发出** `Obstacle Detected` 信号」；模型里唯一的 `Obstacle_Detected`
是**输入触发**，用在几条终止边上。要求发出的输出信号被吞进了状态名的描述串。

⚠️ **它为什么不是表示债务？** 第 ③ 步问的是「作者**表达过这个义务**吗」，不是「字面
**出现过**这几个字吗」。作者写的 `EmergencyStopping: Obstacle Detected` 是状态的**描述性
标注**，不是动作槽位——义务从未被表达，只是文本恰好同名。作为对照：另一份模型里作者写的是
`/ UAV Count Decreased`——斜杠开头，那是 PlantUML 的标准效果槽位，义务确实被表达了，
所以那条判表示债务，而本条判真漏记。

**案例二**：接管迁移只挂在一个子状态上，而模式一级本身与另一个子状态都不消费该事件。
需求第 4 句整句是 `transit to human driving mode when receive human steering cmd,
brake pressed, in (auto final)`——⚠️ 句末确有 `in (auto final)`，引用时不得截断。
裁定成立的依据是把三项读作**并列的触发条件**而非作用域限定：同一份需求下另有两位生成方
分别把它写成 `||` 与 `or`（这两位也在下面说的「挂在模式一级」的 4 位之内），
即他们自己就把第三项当成第三个析取触发。按这个读法，
该句未对接管迁移施加源态限定；参考模型也挂在模式一级，同需求 6 个作者里有 4 个挂在模式一级。

⚠️ 若改读作「仅在 auto final 时接管」，本条不成立。**该读法之争应在论文里写明。**
⚠️ 另外，本条与一条已有台账记录在某一半上有交叠，净增量应只记不交叠的那一半。
⚠️ **两条净增量本身都不稳定**（2/6 与 3/6）。

### 7.10 稳定性

**174/288（60%）的簇只出现在 6 个格中的 1 个**，多报的长尾以单次采样噪声为主。

⚠️ 但重复要分两个层面看，结论只在其中一个层面成立：

| 层面 | 表示债务 | 无需求依据 | 说明 |
| :-- | --: | --: | :-- |
| **跨格重复**（出现在 >1 个格的簇数） | 52 | 50 | **几乎持平**——两类都有稳定复现的部分 |
| **同根因重述**（条目/去重比） | **4.47** | 1.78 | **相差 2.5 倍** |

也就是说：**不是「表示债务更容易跨格复现」，而是「同一处编译损失会被拆成更多条不同的
产出反复陈述」**——同一行 PlantUML 的一处融合，会以不同分支名、不同 roll-up 形态
被报好几遍。长尾是采样噪声，而这种同根因重述是系统性的。

## 八、这个实验证明了什么

### 8.1 三条可写进论文的主张

| 主张 | 证据 | 强度 |
| :-- | :-- | :-- |
| 方法在 98 条已知缺陷上取得 `hit@1` 60.4%、`hit@3` 70.9% | 588 位人工判定，其中 568 位带逐位判据、20 位无（15 位在命中侧） | 强，但**必须标为上界**，且算力涨 1.73× 需同时说明 |
| 未匹配产出中，**按条目计**最大的一块（46.5%）是评审入口的编译损失；**按去重计**为 24.2%，去重后最大的是断言侧过度规定 | 逐条回读作者源并给行号 | 强，但判定**不可机械复现**——第 ③ 步需人工回读 |
| 相对已知缺陷的净增量只有 2 条 | 288 簇过四条判据 | 中，一条部分交叠，且两条都只有 2/6 与 3/6 |

### 8.2 能力与稳定性是两个独立问题，且体量相当

23 条零命中（能力缺口）、25 条 1–4/6（稳定性缺口）。`hit@3` 与 `hit@all` 相差 22.4pp。
（⚠️ 这个 22.4pp 与 §6.3 里归因层之间的 22.4pp 是**两个无关的量，数值巧合**。）
**双峰分布说明方法不是「普遍有六成把握」，而是「会的很会、不会的完全不会」。**

### 8.3 必须一起说的局限

1. **`hit@k` 是上界**（§6.2），命中侧的对称审计未做。
2. **54 个 pair 不是 54 个独立样本**，是 9 份需求 × 6 份模型；族间离散度大，
   报到 0.1pp 不代表该精度。
3. **两版的判定构成不同质**（详见 §6.1）：上一版未做多报侧裁定，
   因此两版的 precision 不可比，只有覆盖率可比，且覆盖率的可比性本身也是弱的。
4. **判定层是独立误差源**：588 位与 288 簇全部由单一判定者人工裁定，**无第二判定者、
   无一致性系数**；多报侧第 ③ 步按定义不可机械复核。
5. **20 位不可逐格复核**，其中 15 位是命中。
6. **台账本身有已知缺口**（§3.4）：24 个 case 有外部记录的语义问题而台账无对应条目。

## 九、下一步【推论】

**应做**

- **补一条模型驱动的巡检入口**。合式性层低 22.4pp，零命中里 10 条在该层。
  ⚠️ 但另有 7 条零命中在需求驱动层，补入口解决不了它们，需另行定位。
- **收断言侧的过度规定**。去重后占比最大（54.0%），`N-SPLIT` / `N-CTX` / `N-FORM`
  三个子类合计 67 条目。⚠️ 但据 §7.6 案例三，其中至少一部分不是提示问题而是
  **证据包字段缺失**（动作声明未下发），先拆开成因再动手。
- **补中间表示的损失**。表示债务按条目占 46.5%，而 `D1`/`D2`/`D3` 三类合计 129 条目
  看起来是**可修的编译实现问题**（析取触发可保留成多个事件、守卫里的量可保留成变量声明），
  不是记法表达力的鸿沟。⚠️ 全文占比最大的一块此前没有对应行动项，这是个疏漏。
- **降低方差**。25 条处在「能找到但找不稳」。
- **收需求集规模**。中位 15 条、最大 99；超 60 条的 13 格里 4 格降级，且全部落在 gpt 一侧。
  断言转换与需求拆分两个阶段合计占节点耗时 88%，且随需求条数线性增长——这既是算力涨
  1.73× 的主因，也是降级的主要来源。

**必须补的对照与审计**（下列每一项缺失都会被审稿人直接问到，且都不需要重跑 324 格）

| 项 | 为什么必须做 | 代价 |
| :-- | :-- | :-- |
| **朴素基线** | 全文唯一对照是自己的上一版。同样两个执行模型、同样 54 个 pair，**不走这 8 阶段循环，一个提示直接让它列出不符之处**，在这 98 条上是多少？没有这个数，60.4% 没有参照系，无法说明这套循环换来了什么 | 一次小规模运行 |
| **上一版零产物格的影响** | §6.1 已承认「配额耗尽从整格中止改为降级落盘」直接改变有多少格能产出，却只作定性描述。这一项**不需要消融就能算**：数出上一版零产物的格，扣掉本版对应格的命中，重算差值 | 纯统计，无需运行 |
| **表示债务的第二判定者** | 46.5% 这一整块靠「人工回读作者源」认定，而该步不可机械复现、目前单人判定。抽 30 簇给第二人盲判、报一致率 | 一人半天 |
| **台账撰写过程的交代** | 台账是能力分母。必须写清：谁标的、什么时候标的、**是否在看过方法产出之后标的**、与命中判定是否同一人。若时序上晚于方法产出，60.4% 就不是覆盖率 | 文字交代 |
| **命中形态的构成** | 四种等价形态中「蕴含更根本的原因」最宽。355 位按四形态拆开各多少？若相当比例靠最宽那一档，这个数的性质就变了 | 纯统计 |
| **拒答文案的回灌量** | 同一机制在 §4 是设计优点、在 §6.2 是上界成因，且尚未量化。从逐次调用记录里数：多少条已发布 issue 的断言是在收到拒答反馈之后才改成现在形状的 | 纯统计 |

**暂缓**

- **不要据 §6.3 的谓词表做词表选型**。谓词与缺陷类型共线，要做必须先做消融。
- **不要把净增量 2 条当卖点**。当前价值在覆盖已知缺陷，不在扩充缺陷集。

**不要做**

- 不要只给一套多报侧分母。**理由**：两套给出不同的主要矛盾，只报一套会把整改资源投错地方。
- 不要把 `hit@k` 写成点估计或区间估计。**理由**：已知扣除项只给出上界方向，
  下界取决于尚未做的对称审计，写成区间等于宣称了一个并不掌握的下界。
