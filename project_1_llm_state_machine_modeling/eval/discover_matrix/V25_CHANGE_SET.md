## 改动 1（已实施）：L379 的两个选项补上适用条件

### 诊断（比我最初的判断更准）

我最初写「`REQUIREMENT_REVIEWER`(L379) 允许要求拆开而断言阶段禁止，两者矛盾」。**读完整原文后这个说法
不准确** —— L379 逐字是：

> otherwise require distinct coverage obligations **or an explicit limitation**

它给了**两个**选项，而「explicit limitation」正是断言阶段允许的做法。所以严格说它与断言阶段**不矛盾**，
只是把「要求拆开」列在前，**顺序暗示了优先级**，而适用条件没写。

### 改法：只补适用条件，不删任何一方的能力

新增的判据是**可执行的**（不依赖偏好）：

> 要求 distinct coverage obligations 只在**模型已声明可分离的原子事件**时可行。模型只声明一个合并标签
> 而无更细粒度时，唯一可用的结果是 explicit limitation —— 在那里要求拆开会产生一条**断言阶段被禁止表达**
> 的需求（它不得臆造原子事件名），于是该需求要么落在合并事件上而**平凡为真**，要么被打回。

同时明确限制写在 `requirement` 本身而非 `source_context`（后者会被所有 gate 与 review 规则当作不存在）。

**验证**：`make test` 1599 passed / 4 skipped。

## 改动 2（**降为 follow-up**）：谓词把「绑错名字」与「元素缺失」压成同一个 False

### 缺陷是真的，且比 prompt 措辞更根本

    state_declared('...0018.join2')            = True     ← 模型真名
    state_declared('...0018.Join2')            = False
    state_declared('...0018.Nonexistent_XYZ')  = False    ← **同一个信号**

两者含义截然不同：前者是**绑定错误**，后者是**正确发现**。而下游把 False 当发现发布，**于是绑定错误
变成虚构**。

`prompt` 再怎么写都不解决它 —— **一个错拼的名字总会得到一个看起来正常的 False。**

### 但按「先算上限」，本轮不改

| 代次 | 绑定总数 | 仅大小写不符 |
| :-- | --: | --: |
| v23 | 25,946 | **30**（全在 `0018-gpt` 一格，全是 `Join2`/`join2`） |
| **v24** | 23,782 | **0** |

**v24 已零例**，所以改它在本轮的收益上界是 **0 条**。为一个当前零发生的情形改 pipeline src、并占用本轮
双 review 额度，收益不成比例。

**登记为条件触发 follow-up**（与 `initial_target` 的「≥2 条无条件入口」同类）：一旦某代次再次出现
仅大小写/拼写不符的绑定，即实施。

修法方向已定：让谓词区分「未声明」与「疑似拼写/大小写不符」，后者**拒答**（`UnsupportedEvidence`）而非
返回 False —— 理由与 `_require_well_formed_names` 拒绝形状不合法的名字完全一致。

## 顺带纠正我自己的一处混淆

我曾把两处不一致并列为「名字大小写不一致」，实际它们性质不同：

| 格 | 现象 | 判定 |
| :-- | :-- | :-- |
| `0032` | 模型 `OperateState`，`nl_parent` 记 `Operate` | **不是缺陷** —— NL 与模型的命名本就该不同，断言绑模型真名是对的 |
| `0018` | 模型 `join2`，断言绑 `Join2` | **真缺陷** —— 会得到静默 False |

**只有后者是问题。** 前者被我误列，是因为我按"字符串不等"归类，而没问"哪个才该是断言的绑定对象"。
