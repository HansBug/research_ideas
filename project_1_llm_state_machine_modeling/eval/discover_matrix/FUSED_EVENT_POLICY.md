**否则要求 distinct coverage obligations 或显式限制**。

| 行 | 逐字 |
| --: | :-- |

| 146 | use it as one transparent representation proxy, **state that the alternatives cannot be separated** |

**L379 给了两条出路，断言阶段实现第二条。这是分工，不是矛盾。**

## 二、~~矛盾的实际后果~~ —— 本节结论已被否证，保留供追溯

⛔ **下面的推理链是错的**：它假设 L379 只有「拆开」一条出路，而 L379 明写「或显式限制」，
断言阶段实现的正是后者。真实流水线里需求可以形成**且**断言可以落成（落成为表示限制见证）。

~~需求形成阶段允许要求拆开，断言阶段禁止拆开。~~ 原推理：

    需求评审通过一条「区分三个接管条件」的需求（L379 允许）
        ↓
    断言转换器被禁止为它写区分性断言（L77 / L146）
        ↓
    该需求要么落成合并事件的断言（**必然为 True**，因为断言的是模型自己的编码）
    要么被打回

⚠️ **`EIS-0000-02` 的实测事实仍然有效，但它不支持「矛盾」这个解释。** NL 第 5 句要求三个接管条件，
模型压成一个跨行自由文本标签（`Human_Steering_Cmd_Brake_Pressed_in_AutoFinal`），断言逐字绑定了那个
融合事件因而必然为 True。**这是「表示限制被如实记录、但记录本身不构成发现」**，而非「断言不能表达」——
后者要求存在一个被禁止的表达，实测中不存在。真正缺的是承载事件粒度的谓词（见 §四）。

实测确认：该格的断言逐字绑定了那个融合事件

    AST-REQ-M005-2  edge_declared(source="...AutonomousMode.AutoFinal",
                                  trigger="...Human_Steering_Cmd_Brake_Pressed_in_AutoFinal", ...)

即断言了**模型自己的编码**，必然为 True，发现自然不存在。

## 三、⛔ 为什么不能加第 6 句

按 [记忆纪律「一条策略只能有一个归属地 / 禁止加法式补丁修复」]，加一句「但你可以报告融合本身是缺陷」会
让**五方矛盾变成六方矛盾**。

而且加法式补丁在这里有一个具体的失败模式：新句子会与 L77 的「do not invent separate atomic events」
**在同一个 prompt 里相隔数行**共存，模型面对「不得臆造原子事件」与「可以报告融合是缺陷」时，无法判断
「报告融合是缺陷」是否等于「臆造原子事件」—— **而那正是它们的实质区别所在**。

## 四、原设计的修法（**已被 §四末的可表达性核查否决，保留以便追溯**）

⚠️ 下表是我在做可表达性核查**之前**设计的。核查结论（本节末）表明它的 `ASSERTION_CONVERTER` 那一格
**无法实施** —— 没有谓词能承载「事件粒度断言」。表格保留是为了记录设计路径，**不是待办**。

四个阶段对「合并事件」各有一件**不重叠**的事要做：

| 阶段 | 唯一职责 | 不做什么 |
| :-- | :-- | :-- |
| `REQUIREMENT_SPLITTER` | 按 NL **原样**形成义务（NL 说三个条件就是三个） | 不看模型、不预判可表达性 |
| `REQUIREMENT_REVIEWER` | 判义务是否忠实于 NL | **不**因模型只有合并事件就削弱义务 |
| `ASSERTION_CONVERTER` | 两类断言**并列**产出：<br>① 用合并事件的可执行断言（**必然 True**，作为表示限制的见证）<br>② ⛔ **事件粒度断言** —— **核查后确认无谓词可承载，此格作废** | **不**臆造 N 个原子事件名（那是幻觉） |
| `ASSERTION_REVIEWER` | 检查 ① ② 都在 | **不**因 ② 存在而打回；**不**因 ① 必然 True 而打回 |

### 关键区分：报告融合 ≠ 臆造原子事件

| | 做法 | 是否允许 |
| :-- | :-- | :-- |
| **臆造** | 断言 `event_declared('Brake_Pressed')` 存在 —— 那个名字模型里没有、NL 里也没有 | ⛔ 禁止（幻觉） |
| **报告粒度** | 断言「NL 点名 3 个条件，而 `declared_model_vocabulary` 里对应位置只有 1 个事件」 | ✅ 应当 |

后者**不需要任何不存在的名字** —— 它断言的是**计数关系**，两侧都可从已有材料读出。

⛔ **但「应当」不等于「能」** —— 见下。这个区分我原以为足以支撑修法，实际它只说明了修法**在语义上**
正当，没有说明它**可执行**。

### ⛔ 可表达性已核查：需要**词表扩张**，本通路 v25 不实施

第 1 步的结论（实测）：

| 检查 | 结果 |
| :-- | :-- |
| `cardinality` 能否数事件 | **不能** —— docstring 逐字「declares exactly this many non-pseudo **direct substates**」，只数状态 |
| `event_declared` 能否数 | **不能** —— 存在性谓词（某具名事件在不在），非计数 |
| 数据层面可数吗 | **可以** —— `structure.events()` 实测返回 `0000` 的 5 个事件 |

**关键区分**：`structure` 是 API facade，**不是谓词**。断言脚本能调的是那 19 个谓词；`structure.events()`
是谓词**内部**用的。让断言脚本直接调 facade 会绕过谓词层的全部纪律（`_note` 记账、
`_require_well_formed_names`、attribution 引用记录）—— 而那些正是让发现**可归因**的机制。

所以准确结论是：**数据可数，但没有谓词把它暴露为可断言的命题。** 要支持事件粒度断言需**新增谓词**
（如 `event_cardinality(scope, count)`），那是**词表扩张** —— 远超「收窄一句禁令」的范围，需要独立的
可表达性设计与双 review。

📌 **这个区分把结论从「不可能」改成了「需要词表扩张」，两者的后续动作完全不同。**

### v25 的处置

**本通路不实施。** 记录为「已知不可表达 + 已定位所需扩张」，与 `PAIR-G-REC-06`（join/junction 类型错配）
同类。

⚠️ **裁定建议的「收窄禁令」若照做会更糟**：模型被允许报告融合是缺陷，但没有谓词能承载那个断言 ——
它要么臆造一个谓词调用（幻觉），要么落成 `unsupported`。**现状至少产出一个诚实的 True。**
