# talks 工作指南

本文档规定 `talks/` 下人类讨论纪要的维护方式。

## 1. 目标与边界

`talks/` 的目标是把“原始回忆碎片 -> AI 扩写 -> 人工纠偏 -> 纪要定稿”这条链路稳定下来。

它不是论文集，不服务于 PDF 收录、`paper_content.txt` 提取或 `desc.md`/`STM.md` 生产。遇到论文类任务，应回到对应论文集或单论文目录处理，而不是混入这里。

## 2. 命名规则

每次讨论使用一个单独目录，默认命名为：

1. `yyyy-mm-dd-hh-mm-对象-主题`
2. 若无具体时间，可退化为 `yyyy-mm-dd-对象-主题`

其中：

1. `对象` 尽量稳定，如 `导师`、`组会`、`同门`、`合作者`。
2. `主题` 只保留短关键词，避免写成长句。
3. 若同一天有多次相近讨论，优先保留时分，避免目录名碰撞。

## 3. 文件职责

### 3.1 `raw.md`

`raw.md` 是原始输入层，默认用于保存：

1. 片段化回忆。
2. 当时记下的关键词。
3. 不完整判断。
4. 明确标有问号或待确认的模糊点。

默认要求：

1. 优先保留原始语气和顺序。
2. 可以很短，可以不成句。
3. 不要求写成完整段落。
4. 不要为了“好看”提前抹平不确定性。

### 3.2 `minutes.md`

`minutes.md` 是结构化输出层，默认用于保存：

1. 本次讨论的背景。
2. 明确形成的判断、共识或建议。
3. 仍有争议或待确认的点。
4. 对后续研究、写作或整理工作的影响。

推荐章节可采用：

```markdown
# 标题

## 1. 讨论背景
## 2. 主要结论
## 3. 展开说明
## 4. 待确认点
## 5. 后续动作
```

这不是强制模板，但默认应有“已确认内容”和“未确认内容”的清晰区分。

### 3.3 `todo.md`

只有当讨论直接产生了待办事项时才创建 `todo.md`。典型内容包括：

1. 需要回查的论文、目录或文档。
2. 需要补写的章节、图表或实验。
3. 需要后续向导师或他人再次确认的问题。

## 4. 扩写规则

AI 根据 `raw.md` 扩写 `minutes.md` 时，必须遵守以下规则：

1. 先忠实恢复原始意思，再考虑文字组织，不要为了流畅度改写掉原意。
2. 遇到明显依赖上下文才能成立的句子时，可以做最小必要补全，但不能无依据发明新结论。
3. 如果某个判断只是从零散片段推出来的，应明确标注为“待确认”或“根据上下文推测”。
4. 用户后续口头或书面纠正一旦出现，应以最新纠正为准，回写到 `minutes.md`。
5. `raw.md` 原则上不替换成扩写版，除非用户明确要求把原稿也一并整理。

## 5. 修订规则

多轮修订时，默认采用“**覆盖式重写 `minutes.md` + 保留 `raw.md` 原始证据**”的策略，而不是把不同版本机械堆叠。

具体要求：

1. 若只是文字顺序或表述精度调整，直接更新 `minutes.md` 正文。
2. 若用户推翻了先前某条判断，应在新版本中删除或改写旧判断，不要把互相冲突的说法并列保留为正文。
3. 若确有必要保留版本痕迹，可在 `minutes.md` 末尾加一个简短的“修订记录”小节，但不要把正文写成聊天记录。
4. 若讨论中出现新的任务拆分，应同步补写或更新 `todo.md`。

## 6. 工作顺序

一轮完整工作建议按以下顺序执行：

1. 先读 [README.md](./README.md)。
2. 再读 [GUIDE.md](./GUIDE.md)。
3. 创建或进入目标讨论目录。
4. 若目录刚建立，先写 `raw.md`。
5. 基于 `raw.md` 生成或重写 `minutes.md`。
6. 若形成行动项，再生成或更新 `todo.md`。
7. 最后检查 `minutes.md` 是否把“共识”和“待确认点”明确分开。

## 7. 质量要求

在 `talks/` 下，质量判断标准不是“写得像正式论文”，而是：

1. 是否忠实反映了原始讨论意思。
2. 是否清楚区分了已确认内容与待确认内容。
3. 是否便于后续继续修订，而不是一轮写死。
4. 是否把真正需要落地的后续动作写清楚了。
