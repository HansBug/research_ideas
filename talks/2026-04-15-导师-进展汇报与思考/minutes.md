## 2. 已确认结论

- 这学期的第一优先级是尽快把 `project_1` 的第一篇论文推出来，不要继续让主线发散。投稿形式可以是期刊或长文，不必死盯某一个近期会议窗口；更关键的是做扎实，并给后续几个月的写作与修改留出缓冲。

- 第一篇论文优先讲 `LLM agent + 仿真 + 形式化验证` 形成闭环的方法本身。这里真正的贡献点在闭环方法、多智能体系统和全流程反馈，而不在 `DSL` 本身。
- 因此，第一篇论文里不应过度强调“我们自研了一个 `DSL`”；若 `Umple` 这样的现成文本状态机载体足够承载实验和闭环，就可以直接拿来用。

- 需要持续关注 `LLM-based 软件开发` 这个方向，因为其中很多 workflow、agent orchestration、traceability 和 specification 管理思路，可以直接迁移到 `LLM-based modeling`。

### 3.2 关于 `project_1` 为什么要拆成两条论文线

- 这次讨论最关键的结构性收束，是把“方法闭环”与“`DSL/pyfcstm` 本体”分开。
- 第一篇论文应当优先回答的问题是：面向控制系统建模，`LLM` 如何在 agent 化工作流中，与仿真、形式化验证和结构化反馈结合，形成一个可反复迭代的闭环。
- 在这个叙事里，`DSL` 只是闭环里的一个承载对象，重要的是它是否足够稳定、可解析、可执行、可反馈，而不是它是不是我们自己发明的。

### 3.3 关于两类控制系统状态机对象的边界

- 讨论中提到的 $0 \\le x - y \\le n$，并不是一个孤立公式，而是在提醒：一部分甲方场景的模型和验证剖面本来就带明显时间性质，语义气质更接近 `timed automata`。
- 这类对象更自然地会落到 `project_3` 那条 timed/profile-based verification 线上，或者至少会强烈依赖那条线。
- 与之对应，另一部分对象更像离散控制、模式切换、周期执行、事件-守卫-动作、层次状态机这一侧，更接近 `HSM` / `EFSM` / `pyfcstm`。
- 这次讨论给出的方向很明确：第一篇论文不要试图同时吃掉这两类对象，而应该优先在离散控制状态层站稳。
- 换句话说，第一篇论文先把“控制系统的离散控制状态层如何被 `LLM` 闭环建模”讲清；强时间语义那一侧可以保留为后续延展或对照背景，而不是当前主问题本体。

### 3.4 关于 `Umple` 在当前叙事里的角色

- 这次讨论里提到的 `Umple`，不是随便举的一个工具名，而是一个相对合适的文本状态机承载对象。
- 我补查了一下官方资料，`Umple` 是一个把 `UML` 中的 association、attribute、state machine 等建模抽象加入到主流面向对象语言中的建模工具 / 语言家族，也支持文本方式编写状态机并生成可执行代码。官方页面还明确提到，可以直接让 `AI` 根据需求生成 `Umple` 数据模型或状态模型。
- 因此，把 `Umple` 放进第一篇论文的意义，不是把它当成我们的理论贡献，而是把它当成一个现成、可执行、可接反馈链的文本状态机载体。
- 这样一来，第一篇论文就能更干净地聚焦在“闭环方法”上，而不是被拖进“自研 `DSL` 是否足够新颖”的论证泥潭。
- 外部参考：<https://cruise.umple.org/umple/>

### 3.5 关于 `spec-driven` 的当前可操作理解

- 这一部分不是我对导师原话的机械复述，而是我根据今天讨论上下文，再结合外部资料形成的当前理解。
- 我查到的较新一手资料里，`spec-driven` 在当下 `AI-native` 软件开发语境里，通常不是指“直接从一句需求跳到代码”，而是指先把自然语言需求转成一组明确、结构化、可追踪的规格工件，再让 agent/LLM 围绕这些规格继续推进。
- 例如 `Kiro/AWS` 官方文档给出的典型流程就是 `Requirements -> Design -> Tasks -> Implementation`：先形成 `requirements.md`，再生成 `design.md`，再拆成可执行任务；并且在面向特定目标架构时，规格生成过程还要显式对齐架构目标、服务边界、数据归属和组织规范。
- 另一篇更贴近控制系统设计场景的 `Design-OS` 论文，则把 `specification-driven` 描述为一种让 specification 成为“人类设计者与 AI agent 共享契约”的流程：每一阶段都沉淀结构化工件，并保持从意图到设计参数的可追踪性。
- 如果把这些资料和今天的讨论放在一起，我当前更倾向把“控制系统开发的 `spec-driven` 方法”理解为：从顶层需求出发，不直接跳到 `DSL`、代码或模型，而是先经过架构设计与系统分解，把需求转成一组结构化 specification，再让 `LLM/agent` 围绕这些 specification 去做建模、生成、仿真、验证和修复。
- 这里的关键中间层就是“架构设计”。因为只有经过架构设计，顶层需求才会被进一步拆成组件边界、责任划分、接口与交互、状态与模式、守卫与约束、时间窗口或周期语义，以及可验证的局部 specification。
- 也正因为这一层存在，`spec-driven` 才不是一句“把 requirement 换个名字叫 spec”的空话，而是把高层需求转化为可由 agent 消化、可由工具检查、可继续进入闭环的中间工件。
- 放回 `project_1` 的语境里，这意味着第一篇论文里的 `spec-driven LLM`，未必非要理解成“生成 spec 的 LLM”，而更可以理解成“由 specification 驱动、并围绕 specification 组织工作流的 LLM/agent 系统”。
- 这样看，今天笔记里“顶层需求 -> spec-driven，中间的关键点在于架构设计”这句话就比较顺了：顶层需求先经架构与设计层落成结构化 specification，随后 agent 再据此去生成状态机、跑仿真、接形式化验证反馈，并继续修正。
- 这也是为什么 `spec-driven` 比单纯的 `requirements-driven` 更强：前者强调结构化 specification、设计分解、traceability 和后续执行；后者往往只强调“需求是出发点”，但不一定把需求中间态做成足够清晰、足够可操作的规格层。
- 外部参考：<https://kiro.dev/docs/specs/feature-specs/requirements-first/>、<https://docs.aws.amazon.com/zh_tw/govcloud-us/latest/UserGuide/govcloud-kiro.html>、<https://arxiv.org/abs/2603.20151>

### 3.6 为什么要关注 `LLM-based 软件开发`

- 导师专门提醒关注 `LLM-based 软件开发`，核心意思不是换方向，而是借方法。
- 这一方向中已经积累了不少关于多 agent 协作、需求到设计再到任务拆解、自动测试、可追踪工作流、架构感知生成的经验。
- 这些经验对 `LLM-based modeling` 非常有价值，因为后者如果继续停留在“prompt 一次出模型”，就很难讲清可信度、可回放性和可维护性。
- 因此后续在写第一篇论文时，应主动把 `LLM-based 软件开发` 这条线里的方法学语言吸收进来，尤其是 specification 管理、架构设计中间层、traceability、agent orchestration 和结构化反馈闭环。
