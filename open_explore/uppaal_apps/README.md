# `uppaal_apps/` 论文集 README

## 1. 论文集定位

`open_explore/uppaal_apps/` 是面向 `UPPAAL` 应用验证工作的专题论文集，当前主线聚焦于：

1. 使用 `UPPAAL` 方法或 `UPPAAL` 软件，对**具体系统、具体协议、具体控制器或具体软件对象**进行形式化建模与形式化验证的论文。
2. 能清楚交代“被验证系统 - 模型抽象 - 待验证性质 - 查询/分析流程 - 验证结果”的案例型工作。
3. 能为后续博士研究中的状态机建模、性质构造、验证剖面和修复闭环提供可复用案例证据的验证文献。

它与同级的 [uppaal_tech/README.md](../uppaal_tech/README.md) 分工如下：

1. [uppaal_tech/README.md](../uppaal_tech/README.md)
   - 负责 `UPPAAL` 本体技术、算法、数据结构、扩展能力和工具工程主线。
2. [uppaal_apps/README.md](./README.md)
   - 负责 `UPPAAL` 被用于验证协议、控制器、嵌入式系统、工业系统、软件系统等**具体对象**的应用案例主线。

换言之，这里不是“凡是提到 `UPPAAL` 的应用都收”，而是优先收“**以形式化验证为中心的 `UPPAAL` 应用论文**”。

## 2. 设立宗旨与期望收获

单独建立本论文集，是为了把“工具技术本体”和“工具如何真正用于验证实际对象”拆开维护，避免两类材料在后续扩库时互相稀释。

这里希望持续沉淀的内容主要包括：

1. 具有正式学术或工程贡献的 `UPPAAL` 应用验证论文。
2. 由官方案例页、官方教程、核心团队论文或稳定学术脉络支撑的可追溯验证案例。
3. 可复用的应用抽象模式，例如：
   - 现实系统如何映射为 `UPPAAL` 模型；
   - 性质如何写成查询；
   - 环境假设、时序约束和同步规则如何组织；
   - 验证结果如何回到工程解释层。
4. 对后续博士研究有直接价值的结构化信息，例如：
   - 被验证系统到底是什么系统；
   - 它有什么关键特点；
   - 案例规模多大；
   - 模型、案例文件、补充材料是否公开可得；
   - 哪些工业案例虽然经典，但材料现实上难以取得。

## 3. 收录范围

本论文集优先收录以下条目：

1. 使用 `UPPAAL`、`UPPAAL SMC`、`UPPAAL Tiga`、`UPPAAL CORA`、`UPPAAL Stratego`、`ECDAR` 等 `UPPAAL` 谱系方法，对具体系统或模型执行形式化验证的论文。
2. 面向协议、控制器、嵌入式系统、工业系统、软件组件或安全关键场景的 `UPPAAL` case study / industrial case / application paper。
3. 官方案例页、官方教程或官方文档中可追溯到正式论文、技术报告或稳定案例来源的材料。
4. 在被验证系统、建模方式、性质表达、实验或案例结果上提供了足够细节，能支撑 `desc.md` 深度整理的条目。

本论文集当前**不应作为重点**收录以下条目：

1. 主贡献是 `UPPAAL` 本体算法、抽象、数据结构、引擎或工具工程的论文，这些应进入 [uppaal_tech/README.md](../uppaal_tech/README.md)。
2. 只是在 related work 或实验中顺带提到 `UPPAAL`，但没有形成真实验证案例主线的论文。
3. 主要目标是调度、优化、控制合成、测试或仿真，但正文没有给出清晰形式化验证任务、性质或验证结论的论文。
4. 没有合法 PDF、没有可用正文提取物、无法支撑可靠整理的条目。

说明：

1. 若一篇论文同时包含“应用案例”和“技术扩展”，默认按**主要贡献中心**归类。
2. 若一篇论文主要是调度/测试/控制合成，但验证部分仍非常完整、并且对博士研究的“模型-性质-验证”主线有明显价值，可暂时保留为 `🟡 可整理`，但必须在 [SUMMARY.md](./SUMMARY.md) 中如实写清边界。

## 4. 纳入与排除判定标准

后续筛选时，至少从以下维度判断：

1. 研究对象
   - 纳入：具体系统、协议、控制器、软件组件、工业场景。
   - 排除：工具本体、纯技术机制、泛 timed automata 背景。
2. 任务类型
   - 纳入：形式化建模、模型检查、时序性质验证、安全/活性/死锁/调度/一致性分析等明确验证任务。
   - 降优先级：虽然使用 `UPPAAL`，但正文主线更偏优化、测试或调度，验证只占较弱位置。
3. 证据形态
   - 纳入：正文明确讲了被验证系统、模型、性质、查询或结果。
   - 排除：只有一句“我们用 `UPPAAL` 做过分析”。
4. 可提取性
   - 纳入：可获得 PDF 原文并生成质量可用的 `paper_content.txt`。
   - 排除：无法稳定获取正文，或提取结果不足以支撑可靠整理。
5. 与博士研究相关性
   - 纳入：能为状态机建模、性质构造、验证剖面或修复研究提供案例参照。
   - 降优先级：案例真实，但与控制系统、形式化验证或状态机表示关系较弱。

当前优先级最高的方向包括：

1. 控制系统、嵌入式系统和工业 `CPS` 的 `UPPAAL` 验证案例。
2. 协议、通信系统和并发组件的 `UPPAAL` 形式化验证案例。
3. 明确涉及时序约束、安全性质、活性性质、资源约束或环境建模的工作。

关于“领域类型”还应额外遵守以下规则：

1. 当前文档中的领域分类只是**当前版本的工作骨架**，不是封闭不变的固定枚举。
2. 后续若实际收录中稳定出现新的高频应用簇，或现有类别已经明显过宽，应按实际情况动态新增、拆分或合并领域类型。
3. 一旦调整领域类型，必须在同一轮内同步回写 [README.md](./README.md)、[GUIDE.md](./GUIDE.md) 与 [SUMMARY.md](./SUMMARY.md)，保持口径一致。

## 5. 本论文集下文件说明

本论文集默认包含以下核心文件：

1. [README.md](./README.md)
   - 入口说明与边界定义。
2. [GUIDE.md](./GUIDE.md)
   - AI 检索、筛选、分流、回填和一致性检查规范。
   - 同时规定 `desc.md` 默认必写、统一论文表字段和“案例/模型/数据公开性”维护方式。
3. [SUMMARY.md](./SUMMARY.md)
   - 当前总账、分类口径、论文表、材料公开性清单、更新日志和失败记录。
4. [DESC_GUIDE.md](./DESC_GUIDE.md)
   - 单篇 `desc.md` 的专项规范。
   - 固定“被验证系统 / 系统特点 / 系统规模 / 模型 / 性质 / 流程 / 结果 / 公开性”的写法。

推荐阅读顺序如下：

1. [README.md](./README.md)
2. [GUIDE.md](./GUIDE.md)
3. [SUMMARY.md](./SUMMARY.md)
4. 若任务涉及新建或重写单篇分析，再读 [DESC_GUIDE.md](./DESC_GUIDE.md)
5. 具体论文目录下的 `bibtex.bib`
6. 具体论文目录下的 `paper_content.txt`
7. 必要时核对 `paper.pdf`

## 6. 单论文路径约束

本论文集下每个单论文目录默认至少应包含：

1. `paper.pdf`
2. `paper_content.txt`
3. `bibtex.bib`
4. `desc.md`

其中：

1. `paper_content.txt` 必须用 `tools/pdf_extractor.py` 生成。
2. `desc.md` 是本论文集的默认必备派生文件，必须遵循 [DESC_GUIDE.md](./DESC_GUIDE.md)。
3. `desc.md` 中必须显式写出：
   - 被验证系统是什么；
   - 系统有什么关键特点；
   - 系统规模有多大；
   - 模型、案例、数据或补充材料是否公开；
   - 若有公开入口，具体链接是什么。

本论文集对“是否允许不写 `desc.md`”采取如下 collection 级 override：

1. **默认规则**：只要用户没有明确说“这轮先不要写 `desc.md`”，则正式入账时必须同时补齐 `desc.md`。
2. **允许暂缺的唯一情形**：
   - 用户明确要求“先批量收录、暂不写 `desc.md`”；
   - 或用户明确要求“本轮只补三件套”。
3. 只要没有上面这种明确豁免，后续 AI 一律不得把“仅有三件套、没有 `desc.md`”当作本 collection 的常态完成态。

## 7. AI 工作入口提示

进入本论文集时，默认按以下方式工作：

1. 先判断该条目是不是“应用验证主贡献”，若不是则转去 [uppaal_tech/README.md](../uppaal_tech/README.md)。
2. 再判断该条目是不是“以形式化验证为中心”，不要机械把所有 `UPPAAL` 应用都收进来。
3. 按 `README.md -> GUIDE.md -> SUMMARY.md` 的顺序理解现有口径。
4. 处理单篇论文时，按 `bibtex.bib -> paper_content.txt -> paper.pdf（必要时） -> desc.md` 的顺序工作。
5. 新条目入库后，必须同步回写 [SUMMARY.md](./SUMMARY.md)。
6. 若用户没有明确要求“本轮不写 `desc.md`”，则该条目只有在 `desc.md` 补齐后才算完成。

## 8. 后续 AI 应优先做什么、避免做什么

优先做的事：

1. 补齐当前已入账条目的 `desc.md` 与总账字段一致性。
2. 优先收录那些能把“被验证系统 / 性质 / 流程 / 结果 / 公开性”讲清楚的案例。
3. 在 [SUMMARY.md](./SUMMARY.md) 中持续维护系统对象、系统特点、系统规模与材料公开性，而不是只记一行标题。

应避免的事：

1. 把所有“`UPPAAL` + application”论文机械收进来。
2. 新增单论文目录却不写 `desc.md`，然后默认当作完成。
3. 用“详度”“实现”这类难以长期稳定维护的主观列替代更可执行的“公开材料是否可获取”信息。
4. 只写泛泛综述，不回到原文提取系统对象、规模、性质和公开材料线索。
