问题一句话：本文验证的是已划分多处理器实时系统的可调度性，核心问题是带任务依赖、抢占和跨处理器总线通信的任务集，是否总能在截止时间前完成。
方法一句话：作者把任务、总线、处理器、依赖管理器和调度策略统一建模为 `UPPAAL` 时间自动机模板，并联合使用符号模型检查和统计模型检查做可调度性分析。
验证收获一句话：论文在 `21` 任务 `GSM` 实例上证明模型可给出完整可调度结论，又在 `103` 任务 `GSM+MP3` 大系统上用 `SMC` 快速证明其高概率不可调度，并顺带输出响应时间和处理器利用率等性能信息。

## 简报

这篇论文的重点不是某个具体控制器，而是一个可配置的多处理器实时系统可调度性分析模板。它把任务集、处理器平台、总线和依赖关系统一压进 `UPPAAL`，让“任务是否会错过 deadline”变成模型检查问题。

- 系统：已划分到固定处理器上的多处理器实时任务集，任务间可存在跨处理器依赖。
- 特点：同时考虑抢占、依赖、总线延迟、不确定执行时间和多种调度策略。
- 规模：主实验为 `4` 个处理器上的 `21` 任务 `GSM` 系统；扩展实验达到 `103` 任务 `GSM+MP3`。
- 模型：`Task`、`DependencyManager`、`Bus`、`Scheduler`、`Policy` 等模板组成的时间自动机网络。
- 性质：任务不进入 `Error`、不可调度概率估计、最坏响应时间期望和处理器利用率。
- 方法：符号 `MC` 给出可调度证明，`SMC` 负责不可调度概率估计与反例/性能分析。
- 结果：`21` 任务系统被证明可调度；`103` 任务系统在 `SMC` 下显示高概率不可调度。

`任务集与平台配置 -> 时间自动机模板实例化 -> A[] not error / Pr / E / simulate 查询 -> 可调度结论 + 反例 + 性能统计`

## 论文定位

本文属于 `⏱️ + 🌐` 的分析框架型应用论文。它确实有具体任务系统案例，但主贡献仍然是把多处理器实时系统可调度性分析沉淀为一个可复用 `UPPAAL` 模板，因此更偏“应用驱动的验证框架”，而不是单一行业对象的案例论文。

## 验证对象与问题背景

### 系统与场景

对象是多处理器实时系统，多个周期性任务被固定映射到不同处理器上执行，任务之间允许存在依赖关系，依赖消息可以通过总线跨处理器传播。

### 系统组成与运行机制

论文建模的核心组成包括：

1. 应用任务集合 `Application`
2. 处理器与总线构成的 `Infrastructure`
3. 调度器与策略模块 `Scheduler`
4. 专门管理静态/动态依赖关系的 `DependencyManager`

任务每个周期都会经历释放、等待依赖满足、执行、完成等阶段；调度器再依据 `EDF`、`RMS` 等策略把 ready task 插入对应处理器队列。

### 验证边界

本文主要面向已划分的多处理器实时系统，不处理任务在多个处理器之间自由迁移的情况，也不覆盖更底层缓存、总线协议实现等硬件细节。

### 核心问题

传统利用率上界或响应时间分析在多处理器、依赖和不确定执行时间场景下往往过保守或不完备。作者希望用模型检查替代“过于保守”和“只靠仿真”的两难处境。

## 模型与形式化建模

### 抽象对象

论文把系统分成三层：

1. 任务层：每个任务由一个 `Task(id)` 自动机和属性结构共同表示。
2. 平台层：处理器队列与总线模型表示运行环境。
3. 调度层：调度器模型和策略模型负责插入/选择就绪任务。

### 建模形式

任务用三个时钟记录执行时间、响应时间和周期内时间；依赖关系用静态矩阵 `staDap` 与动态矩阵 `dynDap` 管理；总线负责跨处理器依赖消息传递；秒表用于表示暂停和恢复执行。

### 关键抽象与取舍

关键点包括：

1. 用队列而不是独立处理器自动机来表示 CPU 使用状态。
2. 用依赖矩阵统一表示任务图和运行时依赖满足情况。
3. 用 `UPPAAL-SMC` 补足符号验证无法“证明不可调度”的缺口。

## 验证目标与性质

### 待验证问题

论文围绕以下性质展开：

1. 符号性质：任务不会进入 `Error`
2. 统计性质：在给定时间边界内存在任务超期的概率
3. 性能性质：任务响应时间上界期望、处理器利用率

### 查询表达

文中典型查询包括：

1. `A[] not error`
2. `Pr[<= t](<> exists(i:tid_t) Task(i).Error)`
3. `Pr[<=20000](<> exists(i:tid_t) Task(i).Error) <= 0.01`
4. `E[<=20000;1000](max: Task(16).respt)`
5. `simulate 10 [<=200] {cpuUsed[0], cpuUsed[1], cpuUsed[2], cpuUsed[3]}`

这些查询分别对应 deadline 满足、不可调度风险、最坏响应时间和资源利用率评估。

## 核心方法与验证流程

1. 先配置任务属性数组、依赖矩阵、处理器属性和总线时延。
2. 用符号模型检查验证 `A[] not error` 是否成立。
3. 若符号分析确认可调度，再用 `SMC` 估计不可调度概率是否趋近于 `0`。
4. 对关注任务进一步用 `E[...]` 查询响应时间统计特征。
5. 用 `simulate` 输出处理器时间占用曲线，辅助性能分析。

## 案例与结果

论文给出两个代表性结果：

1. `21` 任务 `GSM` 系统在 `2335 s` 左右完成符号验证，被证明可调度。
2. 同一实例的统计分析中，不可调度概率区间随置信参数收紧而进一步逼近 `0`。
3. `Task(16).respt` 的统计最坏响应时间期望约为 `12.4942 ± 0.0532254`。
4. `4` 个处理器的利用率约为 `48%/45%/41%/50%`。
5. 扩展到 `103` 任务 `GSM+MP3` 后，符号验证内存耗尽，而 `SMC` 在约 `40` 分钟后给出不可调度概率区间 `[0.98004, 1]`。

## 与本研究的关系

### 相关性分析

它与博士研究中的“时间约束 + 状态机验证 + 反例辅助修复”直接相关，尤其适合作为“如何把时序调度问题转写成性质查询”的参考。

### 可借鉴之处

1. 把依赖、总线和调度策略统一进一个可配置模板。
2. 用符号 `MC` 与 `SMC` 形成“可证明 + 可估计”的组合流程。
3. 把性能统计和可调度性验证放在同一模型上完成。

### 存在的不足与改进空间

具体应用对象仍偏任务集级抽象，行业语义较弱；原文也未公开模板工程，后续复用仍需按论文重建。

### 对本研究的启发

这篇论文说明，对控制系统状态机研究而言，除了安全/活性，还可以把“可调度性”“响应时间”“资源利用率”沉淀成稳定的待验证性质簇。
