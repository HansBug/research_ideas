# `uppaal_apps/` 的 `desc.md` 编写规范

本文档用于规范 `open_explore/uppaal_apps/*/desc.md` 的写法。它不是泛泛的读书笔记模板，而是面向 `UPPAAL` 应用验证文库的专项整理规范。

本规范吸收两类已有经验：

1. 同级 `uppaal_tech/` 中“问题 / 方法 / 解决点”三条主线的写法。
2. `baselines/` 中对单篇材料做结构化字段抽取和比较口径固定的做法。

因此，`uppaal_apps/` 下的 `desc.md` 默认既要有技术主线，也要有结构化字段，不允许只写一段泛泛摘要。

## 1. 使用场景

以下任务默认必须遵守本文件：

1. 新建某篇应用论文的 `desc.md`
2. 重写或大幅修订既有 `desc.md`
3. 审阅某篇 `desc.md` 是否抓住了应用对象、模型、性质和验证流程的关键内容

如果任务只是扩库、补 `paper_content.txt`、补 `bibtex.bib` 或回填 [SUMMARY.md](./SUMMARY.md) 而不生成单篇 `desc.md`，则不必强制进入本文件；但仍应保持本文件定义的字段和口径与 [SUMMARY.md](./SUMMARY.md) 一致。

## 2. 写作前的必读顺序

生成任何单篇 `desc.md` 前，默认按以下顺序阅读：

1. [README.md](./README.md)
2. [GUIDE.md](./GUIDE.md)
3. [SUMMARY.md](./SUMMARY.md)
4. [DESC_GUIDE.md](./DESC_GUIDE.md)
5. 目标论文目录下的 `bibtex.bib`
6. 目标论文目录下的 `paper_content.txt`
7. 必要时核对 `paper.pdf`

## 3. 本文库下 `desc.md` 的核心目标

对 `UPPAAL` 应用验证论文，单篇 `desc.md` 至少要把以下问题说清楚：

1. 这篇论文验证的**具体对象**是什么。
2. 为什么这个对象需要被形式化建模和形式化验证。
3. 作者如何把现实对象抽象为 `UPPAAL` 模型，抽象边界在哪里。
4. 待验证性质是什么，它们如何被写成查询、约束或判定目标。
5. 验证流程怎样运行，最终发现了什么问题、证明了什么结论，或者暴露了什么边界。
6. 对当前博士研究而言，可复用的对象模式、性质模式和验证流程模式是什么。

这里额外固定几条 collection 级硬约束：

1. 如果论文没有清晰给出验证对象、性质或验证结果，就不应把它写成高质量应用 `desc.md`；必要时应在文中明确写“原文未充分说明”。
2. 如果论文主贡献其实是 `UPPAAL` 本体技术，而应用只是例子，则应优先转去 [uppaal_tech/README.md](../uppaal_tech/README.md)，不要在这里硬写应用分析。
3. 如果论文主要是调度、优化、测试或控制合成，而验证部分较弱，则必须在 `desc.md` 中显式说明边界，不能假装它是纯验证论文。

## 4. 详细度基线

`uppaal_apps/` 下的 `desc.md` 默认不是“扩写摘要”，而是**单篇应用验证解剖**。最低要求如下：

1. 默认必须逐篇人工阅读 `bibtex.bib` 与 `paper_content.txt`，必要时回看 `paper.pdf`，再独立写 `desc.md`。
2. 不允许只看标题、摘要、关键词、现有 [SUMMARY.md](./SUMMARY.md) 或旧版 `desc.md` 就草率改写。
3. `desc.md` 的重点不是“这篇论文大概做了什么”，而是“这个应用对象如何被建模、验证、解释”。
4. 对应用论文而言，最需要展开的通常不是背景，而是：
   - 对象如何抽象；
   - 性质如何表达；
   - 验证流程怎样执行；
   - 结果如何被解释回工程对象。
5. 不允许把多篇论文套同一段模板式表述后仅替换对象名；每篇都必须保留自己的对象边界、性质组织、案例规模和验证难点。
6. 若原文确实没有把某个模型、性质或流程细节展开到更细层级，应明确写“原文未展开到该层”，而不是用空话糊过去。

换言之，默认目标不是“让读者知道这篇论文属于哪个领域”，而是“让读者顺着 `desc.md` 就能看懂：它验证什么、怎样建模、怎样验证、验证出了什么、对后续研究能借什么”。

## 5. `desc.md` 必要结构

后续单篇 `desc.md` 默认至少包含以下结构；除非原文材料极端特殊，否则不建议删减主干章节。

### 5.1 开头三条一句话简述

`desc.md` 最开头必须先给出三条一句话简述：

1. **问题一句话**
2. **方法一句话**
3. **验证收获一句话**

这三条必须足够短，能让读者在不通读全文的情况下迅速知道：

1. 验证对象和核心痛点是什么；
2. 作者是怎样用 `UPPAAL` 做建模与验证的；
3. 最终验证结果或方法价值是什么。

### 5.2 `## 基本信息`

该章节默认使用短条目列表，至少包含以下字段，顺序尽量固定：

1. `标题`
2. `中文标题`
3. `作者`
4. `单位`
5. `发表`
6. `DOI`
7. `链接`
8. `应用领域`
9. `验证对象`
10. `UPPAAL线`

紧接着必须显式写出两类获取信息：

1. `代码/模型/仓库获取方式`
2. `案例/数据获取方式`

写法约束如下：

1. 若原文未提供公开代码、模型、仓库或案例文件链接，必须明确写“原文未提供公开获取链接”。
2. 若只能通过论文正文、附录、官网、案例页、GitHub、Zenodo、补充材料或联系作者获取，也要写清楚。
3. 这里强调的是“如何获取”，不是“如何构建”。

### 5.3 `## 简报`

简报是高密度概览区，必须至少回答以下五个问题：

1. 验证对象是什么。
2. 现实对象被抽象成什么模型。
3. 验证了哪些性质。
4. 用了哪条 `UPPAAL` 工具/方法线。
5. 得到了什么主要结论。

推荐在该章节中固定写出：

1. 一段总述。
2. `- 对象：`
3. `- 模型：`
4. `- 性质：`
5. `- 方法：`
6. `- 结果：`

若论文材料足够，建议附一个字符示意图，展示：

`现实对象/需求 -> 抽象模型 -> UPPAAL 查询/分析 -> 验证结果/反例/结论`

### 5.4 `## 论文定位`

这一节要说明：

1. 这篇论文属于哪个应用领域。
2. 它更偏经典 `UPPAAL`、`SMC`、`Tiga`、`CORA`、`Stratego`、`ECDAR` 还是其他谱系分支。
3. 它是工具展示型案例、工程案例型论文，还是对象驱动的验证论文。
4. 它与 [uppaal_tech/README.md](../uppaal_tech/README.md) 中哪条技术线直接相关。

### 5.5 `## 验证对象与问题背景`

该章节默认至少回答：

1. 现实对象是什么，属于什么系统或场景。
2. 为什么这个对象需要形式化验证。
3. 作者面对的核心问题、风险、需求或错误模式是什么。
4. 为什么选择 `UPPAAL`，而不是只做非形式化分析或只做仿真。

推荐二级标题：

1. `### 对象与场景`
2. `### 核心问题`
3. `### 研究动机`

### 5.6 `## 模型与形式化建模`

这是应用论文的核心章节之一，必须把“现实对象如何进入 `UPPAAL`”说清楚。

至少应回答：

1. 抽象对象是什么，抽象边界在哪里。
2. 使用了哪种 `UPPAAL` 模型形式：
   - 普通 timed automata
   - network of timed automata
   - priced / stochastic / game / I/O / component-based 变体
3. 关键状态、时钟、变量、同步、守卫、不变式、环境假设分别如何组织。
4. 有哪些关键抽象取舍、简化或限制。

强约束如下：

1. 不允许只写“作者用 `UPPAAL` 建了模型”就结束。
2. 默认要比摘要更细，至少让读者知道模型由哪些主要部件、模板或交互关系构成。
3. 若论文明确给出自动机元组、组件关系、同步机制或环境模型，应尽量保留。
4. 若论文没有完全展开模型细节，也要说明“原文只给了哪些层级的信息，缺了哪些层级”。

### 5.7 `## 验证目标与性质`

该章节必须明确：

1. 待验证性质是什么。
2. 这些性质属于：
   - 安全性质
   - 活性性质
   - 有界响应/截止期限
   - 死锁/可达性
   - 一致性/精化
   - 调度/资源/性能
   - 统计或概率性质
3. 性质来自原始需求、领域约束、设计规范，还是作者自行构造的分析目标。
4. 性质如何写成查询、断言或判定目标。

推荐二级标题：

1. `### 待验证问题`
2. `### 性质类型`
3. `### 查询表达`
4. `### 判定边界与前提`

如果原文给出了典型查询，建议尽量保留，例如：

1. `A[] not deadlock`
2. `E<> error`
3. `Pr[<=T](<> goal) >= p`

### 5.8 `## 核心方法与验证流程`

这是 `desc.md` 的重心之一，必须比“背景”更细。

至少应回答：

1. 整体验证流程怎样运行。
2. 从现实对象到模型的输入、处理中间层和输出分别是什么。
3. 使用了哪些关键 `UPPAAL` 功能、变体、组合方式或配置。
4. 它和“直接建一个普通模型然后跑查询”相比，多做了什么。

推荐优先按下面四层展开：

1. **对象层**
   - 被建模的系统部件、控制逻辑、协议角色、环境进程是什么。
2. **规则层**
   - 这些对象如何通过时钟、同步、守卫、更新、概率、成本或博弈角色发生演化。
3. **过程层**
   - 怎样生成模型、组合模型、执行查询、筛选反例、解释结果。
4. **差异层**
   - 与已有案例、已有工具用法或已有方法相比，真正不同在哪里。

对这一节的额外要求如下：

1. 若论文里同时有建模流程和验证流程，默认两边都要交代。
2. 若论文的核心难点在环境建模、状态爆炸控制、抽象简化、统计采样或结果解释，应把这些点展开。
3. 若论文本身更偏教程、经验论文或工程案例，也要写清它的方法性贡献体现在哪个工作流环节。

### 5.9 `## 案例与结果`

这一节至少应回答：

1. 案例规模如何。
2. 跑了哪些验证任务、多少性质或多少查询。
3. 验证得到的主要结论是什么。
4. 是否找到了错误、反例、违例场景或性能瓶颈。
5. 作者如何解释这些结果对现实对象的意义。

推荐尽量保留关键数字，例如：

1. 模型规模
2. 状态数、模板数、时钟数、变量数
3. 性质条数
4. 验证时间、资源消耗、命中错误数
5. 工业或工程收益

不要只写“实验结果良好”“验证有效”，而应尽量写成可追溯的具体结论。

### 5.10 `## 与本研究的关系`

该章节默认至少包含：

1. `### 相关性分析`
2. `### 可借鉴之处`
3. `### 存在的不足与改进空间`
4. `### 对本研究的启发`

这里必须显式回答：

1. 这篇论文和当前博士研究的哪一部分最相关：
   - 状态机建模
   - 验证场景/性质生成
   - 验证剖面
   - 缺陷修复
2. 可复用的是：
   - 对象抽象方式；
   - 性质组织方式；
   - 工具流程；
   - 案例分析方式；
   - 还是错误解释方式。
3. 真正的不足是什么，不要只写礼貌性缺点。

### 5.11 `## 重要的相关工作`

这是单篇 `desc.md` 的重要章节之一，必须基于原文的相关工作与参考文献来写，不能编造。

默认可按以下四类组织：

1. `### 1. 直接前身类工作`
2. `### 2. 同类应用或对照案例`
3. `### 3. 提供技术支撑的工作`
4. `### 4. 其他重要工作`

对每篇重要文献，建议尽量包含：

1. 标题或作者/年份
2. 主要内容
3. 在当前论文中的作用
4. 与当前论文的关系

### 5.12 `## 实现与材料`

默认至少说明：

1. 论文材料够不够细。
2. 模型、代码、脚本、案例文件或工具入口是否可得。
3. 若不可得，只有什么层级的材料可得：
   - 论文正文
   - 官方案例页
   - 工具二进制
   - 公开模型
   - 补充材料

建议在这一节显式给出两个判断：

1. **内容详细程度**
2. **实现可获取程度**

写法应与 [SUMMARY.md](./SUMMARY.md) 中的 `详度`、`实现` 两列保持一致。

## 6. 必须显式抽取的比较字段

为便于后续汇总，`desc.md` 中必须尽量显式回答以下字段：

1. `应用领域`
2. `验证对象`
3. `对象层级`
4. `UPPAAL线`
5. `模型类型`
6. `关键对象`
7. `环境假设`
8. `验证任务`
9. `性质类型`
10. `查询表达`
11. `主要结果`
12. `代码/模型是否公开`
13. `案例/数据是否公开`

其中对 `验证对象 / 模型 / 性质` 的要求尤其严格：

1. 不得只写“系统”“模型”“约束”“性质”。
2. 要尽量写成“列车控制器”“工业气候控制系统”“仲裁协议”“控制器网络”等具体对象。
3. 模型要尽量写成“network of timed automata”“priced timed automata”“timed I/O specification”等具体形式。
4. 性质要尽量写成“死锁自由”“有界响应”“最坏响应时间”“时序一致性”“安全约束满足”等具体类型。

## 7. 数学公式与符号规范

对应用论文，若原文中模型定义、查询表达或判定条件依赖正式定义，默认应适度保留数学表达，而不是全部翻译成口语。

执行规则如下：

1. 行内公式统一写成 `$...$`。
2. 独立定义、关键查询、关键构造、复杂度结果统一写成：

$$
a = b
$$

这样的单独成行公式块。
3. `$$` 与 `$$` 之间必须刚好只有一行公式内容。
4. 默认避免使用 GitHub 容易出问题的复杂排版宏。
5. 文件名、工具名、路径名、命令行参数仍然用反引号，如 `desc.md`、`UPPAAL`、`paper_content.txt`。
6. 当以下场景出现时，建议保留至少一个公式或查询：
   - 模型对象的正式定义很关键；
   - 性质表达离开正式符号会明显失真；
   - 查询语句本身就是论文贡献的一部分。

## 8. 与 `SUMMARY.md` 的对齐关系

后续单篇 `desc.md` 与 [SUMMARY.md](./SUMMARY.md) 的关系固定如下：

1. `desc.md` 中的 `应用领域` 对应 [SUMMARY.md](./SUMMARY.md) 统一总表中的 `领域`。
2. `desc.md` 中的 `验证对象` 对应统一总表中的 `验证对象`。
3. `desc.md` 中的 `UPPAAL线` 对应统一总表中的 `UPPAAL线`。
4. `desc.md` 中的 `验证任务` 与 `性质类型` 对应统一总表中的同名字段。
5. `desc.md` 中的实现与材料判断，对应统一总表中的 `详度`、`实现` 与 `状态`。
6. `desc.md` 开头三条一句话简述，是统一总表 `一句话简介` 的上游压缩来源。

换言之：

1. [SUMMARY.md](./SUMMARY.md) 负责让人快速扫全局。
2. `desc.md` 负责把单篇“对象 / 模型 / 性质 / 流程 / 结果”讲清楚。

## 9. 证据与写作约束

1. 所有判断都应来自 `bibtex.bib`、`paper_content.txt` 和必要时的 `paper.pdf`。
2. 若提取文本有歧义、图表缺失或公式断裂，应回到 PDF 核对。
3. 若论文对模型或性质写得不够细，应如实写“原文未展开到该层细节”，不要脑补。
4. 对关键数字、性质类型、模型结构和结果结论，尽量给出可追溯证据。
5. 可做综合分析，但不能凭常识补写原文没有的事实。

## 10. 缺失信息的处理

1. 验证对象不清楚：回到摘要、引言、系统描述和案例部分补证。
2. 模型不清楚：优先重读方法、建模、系统架构、形式化定义部分。
3. 性质不清楚：优先重读查询、需求、实验设置和结果分析部分。
4. 验证流程不清楚：优先重读方法流程图、工具配置、实验步骤和结论。
5. 若仍证据不足，在 `desc.md` 中显式标“原文未充分说明”，不要臆测补齐。
