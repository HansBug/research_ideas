# `uppaal_apps/` 的 `desc.md` 编写规范

本文档用于规范 `open_explore/uppaal_apps/*/desc.md` 的写法。它不是泛泛的读书笔记模板，而是面向 `UPPAAL` 应用验证文库的专项整理规范。

本规范吸收两类已有经验：

1. 同级 `uppaal_tech/` 中“问题 / 方法 / 解决点”三条主线的写法。
2. `baselines/` 中对单篇材料做结构化字段抽取和公开性盘点的做法。

因此，`uppaal_apps/` 下的 `desc.md` 默认既要有技术主线，也要有结构化字段，不允许只写一段泛泛摘要。

## 1. 使用场景

以下任务默认必须遵守本文件：

1. 新建某篇应用论文的 `desc.md`
2. 重写或大幅修订既有 `desc.md`
3. 审阅某篇 `desc.md` 是否抓住了被验证系统、系统特点、系统规模、模型、性质和验证流程的关键内容

本 collection 的默认规则还包括：

1. 只要用户没有明确说“这轮不要写 `desc.md`”，正式入账时就必须写 `desc.md`。
2. 因此，大多数新增论文任务都会同时触发本文件。

## 2. 写作前的必读顺序

生成任何单篇 `desc.md` 前，默认按以下顺序阅读：

1. [README.md](./README.md)
2. [GUIDE.md](./GUIDE.md)
3. [SUMMARY.md](./SUMMARY.md)
4. [DESC_GUIDE.md](./DESC_GUIDE.md)
5. 目标论文目录下的 `bibtex.bib`
6. 目标论文目录下的 `paper_content.txt`
7. 必要时核对 `paper.pdf`

## 3. 本文库下 `desc.md` 的核心目标

对 `UPPAAL` 应用验证论文，单篇 `desc.md` 至少要把以下问题说清楚：

1. 这篇论文验证的**具体系统**是什么。
2. 该系统由哪些核心部件、角色、进程、控制环节或通信实体构成。
3. 这些部件在现实中如何运行、如何交互，以及哪一层才是论文真正验证的边界。
4. 该系统有什么关键特点，为什么值得做形式化验证。
5. 系统规模大概多大，至少要写清论文给出的关键量纲。
6. 作者如何把现实对象抽象为 `UPPAAL` 模型，抽象边界在哪里。
7. 待验证性质是什么，它们如何被写成查询、约束或判定目标。
8. 这些性质在现实系统里分别对应什么风险、需求或正确性承诺。
9. 验证流程怎样运行，最终发现了什么问题、证明了什么结论，或者暴露了什么边界。
10. 模型、案例、数据或补充材料是否公开，以及现实上能否取得。
11. 对当前博士研究而言，可复用的对象模式、性质模式和验证流程模式是什么。

这里额外固定几条 collection 级硬约束：

1. 如果论文没有清晰给出被验证系统、性质或验证结果，就不应把它写成高质量应用 `desc.md`；必要时应在文中明确写“原文未充分说明”。
2. 如果论文主贡献其实是 `UPPAAL` 本体技术，而应用只是例子，则应优先转去 [uppaal_tech/README.md](../uppaal_tech/README.md)，不要在这里硬写应用分析。
3. 如果论文主要是调度、优化、测试或控制合成，而验证部分较弱，则必须在 `desc.md` 中显式说明边界，不能假装它是纯验证论文。

## 4. 展开基线

`uppaal_apps/` 下的 `desc.md` 默认不是“扩写摘要”，而是**单篇应用验证解剖**。最低要求如下：

1. 默认必须逐篇人工阅读 `bibtex.bib` 与 `paper_content.txt`，必要时回看 `paper.pdf`，再独立写 `desc.md`。
2. 不允许只看标题、摘要、关键词、现有 [SUMMARY.md](./SUMMARY.md) 或旧版 `desc.md` 就草率改写。
3. `desc.md` 的重点不是“这篇论文大概做了什么”，而是“这个系统如何被建模、验证、解释”。
4. 对应用论文而言，最需要展开的通常不是背景，而是：
   - 系统是什么；
   - 系统由哪些关键部件组成、怎么运行；
   - 此次验证到底覆盖了系统的哪一层或哪一段场景；
   - 系统特点与规模是什么；
   - 对象如何抽象；
   - 性质如何表达；
   - 验证流程怎样执行；
   - 结果如何被解释回工程对象；
   - 材料现实上能否取得。
5. 不允许把多篇论文套同一段模板式表述后仅替换对象名；每篇都必须保留自己的系统边界、性质组织、案例规模和验证难点。
6. 若原文确实没有把某个模型、性质、规模或公开性细节展开到更细层级，应明确写“原文未展开到该层”或“原文未提供公开入口”，而不是用空话糊过去。

## 5. `desc.md` 必要结构

后续单篇 `desc.md` 默认至少包含以下结构；除非原文材料极端特殊，否则不建议删减主干章节。

### 5.1 开头三条一句话简述

`desc.md` 最开头必须先给出三条一句话简述：

1. **问题一句话**
2. **方法一句话**
3. **验证收获一句话**

### 5.2 `## 基本信息`

该章节默认使用短条目列表，至少包含以下字段，顺序尽量固定：

1. `标题`
2. `中文标题`
3. `作者`
4. `单位`
5. `发表`
6. `DOI`
7. `链接`
8. `主轴分类`
9. `次轴场景`
10. `被验证系统`
11. `UPPAAL线`

紧接着必须显式写出两类获取信息：

1. `代码/模型/仓库获取方式`
2. `案例/数据获取方式`

写法约束如下：

1. 若原文未提供公开代码、模型、仓库或案例文件链接，必须明确写“原文未提供公开获取链接”。
2. 若只有官网案例页、benchmark 页、历史入口或 DOI，也要如实写清楚，不要伪装成“可直接下载”。

### 5.3 `## 简报`

简报是高密度概览区，必须至少回答以下六个问题：

1. 被验证系统是什么。
2. 系统有什么关键特点。
3. 系统怎样被抽象成模型。
4. 验证了哪些性质。
5. 用了哪条 `UPPAAL` 工具/方法线。
6. 得到了什么主要结论。

推荐在该章节中固定写出：

1. 一段总述。
2. `- 系统：`
3. `- 特点：`
4. `- 规模：`
5. `- 模型：`
6. `- 性质：`
7. `- 方法：`
8. `- 结果：`

若论文材料足够，建议附一个字符示意图，展示：

`现实系统/需求 -> 抽象模型 -> UPPAAL 查询/分析 -> 验证结果/反例/结论`

### 5.4 `## 论文定位`

这一节要说明：

1. 这篇论文在 `主轴分类` 上属于哪类验证对象，在 `次轴场景` 上属于哪类现实应用。
2. 它更偏经典 `UPPAAL`、`SMC`、`Tiga`、`CORA`、`Stratego`、`ECDAR` 还是其他谱系分支。
3. 它是工具展示型案例、工程案例型论文，还是对象驱动的验证论文。
4. 它与 [uppaal_tech/README.md](../uppaal_tech/README.md) 中哪条技术线直接相关。

### 5.5 `## 验证对象与问题背景`

该章节默认至少回答：

1. 现实系统是什么，属于什么场景。
2. 这个系统由哪些关键部件、角色、进程或控制环节构成。
3. 这些部件怎样协同工作，系统的基本运行机制是什么。
4. 论文真正验证的边界在哪里，是整个系统还是其中的某个协议层、控制器、启动阶段或子机制。
5. 这个系统为什么需要形式化验证。
6. 作者面对的核心问题、风险、需求或错误模式是什么。
7. 为什么选择 `UPPAAL`，而不是只做非形式化分析或只做仿真。

推荐二级标题：

1. `### 系统与场景`
2. `### 系统组成与运行机制`
3. `### 验证边界`
4. `### 核心问题`
5. `### 研究动机`

这里增加一个硬约束：

1. 不允许只写“这是一个工业协议/控制器/软件协议”，必须进一步说明它具体控制什么、与谁交互、系统内部至少有哪些关键组成。
2. 若论文本身只验证系统的一部分，也必须明确写“验证对象是整个系统中的哪一层”，不能让读者误以为论文覆盖了全部实现。

### 5.6 `## 模型与形式化建模`

这是应用论文的核心章节之一，必须把“现实系统如何进入 `UPPAAL`”说清楚。

至少应回答：

1. 抽象对象是什么，抽象边界在哪里。
2. 使用了哪种 `UPPAAL` 模型形式：
   - 普通 timed automata
   - network of timed automata
   - priced / stochastic / game / I/O / component-based 变体
3. 关键状态、时钟、变量、同步、守卫、不变式、环境假设分别如何组织。
4. 有哪些关键抽象取舍、简化或限制。

### 5.7 `## 验证目标与性质`

该章节必须明确：

1. 待验证性质是什么。
2. 这些性质属于：
   - 安全性质
   - 活性性质
   - 有界响应/截止期限
   - 死锁/可达性
   - 一致性/精化
   - 调度/资源/性能
   - 统计或概率性质
3. 性质来自原始需求、领域约束、设计规范，还是作者自行构造的分析目标。
4. 性质如何写成查询、断言或判定目标。
5. 每类性质在现实系统里对应什么风险、错误模式、正确性承诺或工程需求。

推荐二级标题：

1. `### 待验证问题`
2. `### 性质类型`
3. `### 性质分组与实际含义`
4. `### 查询表达`
5. `### 判定边界与前提`

如果原文给出了典型查询，建议尽量保留，例如：

1. `A[] not deadlock`
2. `E<> error`
3. `Pr[<=T](<> goal) >= p`

这里增加两个硬约束：

1. 不允许只写“安全性、活性、时序约束”而不解释这些词在该论文里具体指什么。
2. 若论文存在多条性质或多组公式，默认应按“性质簇”归纳解释，例如“消息接收正确性”“错误状态不可达”“截止时间满足”“结果一致性”等，而不是只给一个总标签。

### 5.8 `## 核心方法与验证流程`

这是 `desc.md` 的重心之一，必须比“背景”更细。

至少应回答：

1. 整体验证流程怎样运行。
2. 从现实系统到模型的输入、处理中间层和输出分别是什么。
3. 使用了哪些关键 `UPPAAL` 功能、变体、组合方式或配置。
4. 它和“直接建一个普通模型然后跑查询”相比，多做了什么。

### 5.9 `## 案例与结果`

这一节至少应回答：

1. 案例规模如何。
2. 跑了哪些验证任务、多少性质或多少查询。
3. 验证得到的主要结论是什么。
4. 是否找到了错误、反例、违例场景或性能瓶颈。
5. 作者如何解释这些结果对现实系统的意义。

不要只写“实验结果良好”，而应尽量写成可追溯的数字或明确结论。

### 5.10 `## 与本研究的关系`

该章节默认至少包含：

1. `### 相关性分析`
2. `### 可借鉴之处`
3. `### 存在的不足与改进空间`
4. `### 对本研究的启发`

### 5.11 `## 重要的相关工作`

这是单篇 `desc.md` 的重要章节之一，必须基于原文的相关工作与参考文献来写，不能编造。

默认可按以下四类组织：

1. `### 1. 直接前身类工作`
2. `### 2. 同类应用或对照案例`
3. `### 3. 提供技术支撑的工作`
4. `### 4. 其他重要工作`

### 5.12 `## 案例、模型与数据公开情况`

默认至少说明：

1. 论文对应的模型、代码、脚本、案例文件或 benchmark 是否公开。
2. 若存在公开入口，当前是否真的可访问。
3. 若不存在直达链接，至少有哪些间接入口：
   - 论文正文
   - DOI
   - 官方案例页
   - benchmark 页
   - 作者主页
   - 历史链接
4. 若案例依赖工业内部资产，也要明确写出来。

建议在这一节显式给出以下四项：

1. **可获取性判断**：`🟢 / 🟡 / 🟠 / 🔒`
2. **判断依据**
3. **获取方式/链接**
4. **对后续复用的现实影响**

## 6. 必须显式抽取的比较字段

为便于后续汇总，`desc.md` 中必须尽量显式回答以下字段：

1. `主轴分类`
2. `次轴场景`
3. `被验证系统`
4. `系统组成`
5. `系统运行机制`
6. `验证边界`
7. `系统特点`
8. `系统规模`
9. `UPPAAL线`
10. `模型类型`
11. `关键对象`
12. `环境假设`
13. `验证任务`
14. `性质类型`
15. `性质来源`
16. `查询表达`
17. `主要结果`
18. `模型/案例/数据是否公开`
19. `获取方式/链接`

其中对 `被验证系统 / 系统特点 / 系统规模 / 模型 / 性质` 的要求尤其严格：

1. 不得只写“系统”“模型”“约束”“性质”。
2. 系统要尽量写成“Bang & Olufsen 音视频控制协议”“车辆换挡控制器”“WS-AT 分布式事务协议”这类具体对象。
3. 系统特点要尽量写成“单总线冲突检测”“多任务优先级中断控制”“四站 TDMA 启动同步”。
4. 系统规模要尽量写清模板数、性质数、参与方数量、时间界、工业文档规模或其他原文给出的关键量纲。

## 7. 数学公式与符号规范

对应用论文，若原文中模型定义、查询表达或判定条件依赖正式定义，默认应适度保留数学表达，而不是全部翻译成口语。

执行规则如下：

1. 行内公式统一写成 `$...$`。
2. 独立定义、关键查询、关键构造、复杂度结果统一写成：

$$
a = b
$$

这样的单独成行公式块。
3. `$$` 与 `$$` 之间必须刚好只有一行公式内容。
4. 默认避免使用 GitHub 容易出问题的复杂排版宏。
5. 文件名、工具名、路径名、命令行参数仍然用反引号，如 `desc.md`、`UPPAAL`、`paper_content.txt`。
6. 当以下场景出现时，建议保留至少一个公式或查询：
   - 模型对象的正式定义很关键；
   - 性质表达离开正式符号会明显失真；
   - 查询语句本身就是论文贡献的一部分。

## 8. 与 `SUMMARY.md` 的对齐关系

后续单篇 `desc.md` 与 [SUMMARY.md](./SUMMARY.md) 的关系固定如下：

1. `desc.md` 中的 `主轴分类` 与 `次轴场景`，分别对应 [SUMMARY.md](./SUMMARY.md) 统一总表中的 `主轴` 与 `次轴`。
2. `desc.md` 中的 `被验证系统` 对应统一总表中的 `被验证系统`。
3. `desc.md` 中的 `系统特点` 与 `系统规模` 对应统一总表中的同名字段。
4. `desc.md` 中的 `UPPAAL线` 对应统一总表中的 `UPPAAL线`。
5. `desc.md` 中的 `验证任务` 与 `性质类型` 对应统一总表中的同名字段。
6. `desc.md` 中的公开性判断，对应 [SUMMARY.md](./SUMMARY.md) 的“案例/模型/数据公开性清单”。
7. `desc.md` 开头三条一句话简述，是统一总表 `一句话简介` 的上游压缩来源。

## 9. 证据与写作约束

1. 所有判断都应来自 `bibtex.bib`、`paper_content.txt` 和必要时的 `paper.pdf`。
2. 若提取文本有歧义、图表缺失或公式断裂，应回到 PDF 核对。
3. 若论文对模型、性质、规模或公开性写得不够细，应如实写“原文未展开到该层细节”，不要脑补。
4. 对关键数字、性质类型、模型结构和结果结论，尽量给出可追溯证据。
5. 可做综合分析，但不能凭常识补写原文没有的事实。

## 10. 缺失信息的处理

1. 被验证系统不清楚：回到摘要、引言、系统描述和案例部分补证。
2. 系统规模不清楚：优先重读实验、案例、结果和图表说明部分。
3. 模型不清楚：优先重读方法、建模、系统架构、形式化定义部分。
4. 性质不清楚：优先重读查询、需求、实验设置和结果分析部分。
5. 验证流程不清楚：优先重读方法流程图、工具配置、实验步骤和结论。
6. 公开性不清楚：优先核对原文、官方案例页、benchmark 页和作者提供的链接；若仍不足，明确写“公开性信息不清”。
