问题一句话：本文验证的是水务 `SCADA` 系统的运行日志，核心问题是如何把水箱液位日志转成 timed automata 模型，并据此实时识别 overflow、underflow 和 reply 三类攻击。
方法一句话：作者将水务日志离散化后构造成 timed automata 网络，并使用时序逻辑性质在 `UPPAAL` 中检查某类异常模式是否可达。
验证收获一句话：在 `40` 天日志数据上，论文给出的三类性质恰好区分出 `10` 天 overflow、`10` 天 underflow、`10` 天 reply 攻击和 `10` 天正常行为，四项指标 `Precision/Recall/F-Measure/Accuracy` 全为 `1`。

## 简报

这篇论文不是去验证控制器设计，而是把运行中的 `SCADA` 日志转成 formal model，用模型检查做实时攻击识别。它更接近“监测分析”而不是“离线设计验证”，因此很适合放在 `📊` 主轴下。

- 系统：水分配系统两个水箱 `ct1`、`ct2` 的液位日志。
- 特点：基于日志而非设计图，目标是识别 `overflow`、`underflow` 和 `reply` 三类攻击模式。
- 规模：`40` 天日志，其中 `10` 天正常、`10` 天 `OF`、`10` 天 `UF`、`10` 天 `R`。
- 模型：日志先离散化，再转成 timed automata 网络。
- 性质：`Eφ`、`Eχ`、`Eψ` 三类 reachability 检测公式，以及它们的并集。
- 方法：领域专家先给出攻击模式判据，再写成 `UPPAAL` 可验证的时序性质。
- 结果：三类攻击和正常日志全部被正确区分，四个评估指标都为 `1`。

`水务 SCADA 日志 -> 特征离散化 -> timed automata 网络 -> 攻击模式性质 -> UPPAAL 验证 -> 实时异常识别`

## 论文定位

这篇论文和传统 `UPPAAL` 应用论文最大的不同，是它验证的对象不是设计模型，而是从日志在线/准在线重建的行为模型。因此它非常适合作为“监测分析类应用”案例。

## 验证对象与问题背景

### 系统与场景

对象是水分配系统中的两个 cistern 水位日志。论文设定的背景是：系统引入新的远程数据采集与远程控制能力后，出现了异常水位，领域专家怀疑存在恶意控制执行器的攻击。

### 系统组成与运行机制

实验所用日志主要关注两个水箱：

1. `ct1`
2. `ct2`

论文把这些水位时间序列离散成特征片段，再转成 timed automata，使日志中的演化模式能被逻辑公式捕捉。

### 验证边界

论文并不重建完整物理水务系统，而是围绕日志中能观测到的水位行为做形式化监测。它因此更像 anomaly detection，而不是控制设计验证。

### 核心问题

1. 如何把日志片段变成可供模型检查的正式模型；
2. 如何把攻击模式写成领域专家可接受的时间逻辑公式；
3. 这类性质对真实日志是否足够有区分力。

## 模型与形式化建模

### 抽象对象

模型输入是按小时采样的一天日志。每个一天的日志都会被构造成一个 formal model，用于检查当日是否出现某类异常行为。

### 建模形式

作者使用 timed automata 网络来表示离散化后的行为序列，并在其上验证 reachability / safety / liveness 相关性质。

### 关键抽象与取舍

1. 重点只看液位行为特征，不建模完整控制拓扑；
2. 先做特征离散化，再进入 automata；
3. 攻击定义是领域知识驱动的，而非纯统计学习。

## 验证目标与性质

### 待验证问题

三类主要性质对应三类攻击：

1. `φ`
   - `overflow (OF)`：`ct1` 的上升值至少出现 `11` 次；
2. `χ`
   - `underflow (UF)`：`ct2` 的下降值至少出现 `9` 次；
3. `ψ`
   - `reply (R)`：`ct1` 和 `ct2` 同时保持 basal values 至少 `12` 次。

最终查询是：

1. `Eφ`
2. `Eχ`
3. `Eψ`
4. `E(φ ∨ χ ∨ ψ)`

### 性质类型

这些性质主要属于：

1. reachability；
2. 行为模式检测；
3. 监测型安全性质。

### 性质分组与实际含义

1. `OF`
   - 水箱被恶意灌满或无法及时排水；
2. `UF`
   - 水位异常下降；
3. `R`
   - 两个 cistern 读数被异常回复/冻结，表现出同步不自然模式。

## 核心方法与验证流程

1. 采集一日日志；
2. 做特征离散化；
3. 生成对应 timed automata 网络；
4. 让领域专家把攻击经验转成逻辑性质；
5. 在 `UPPAAL` 中验证这些性质是否可达；
6. 把验证结果映射回日志标签。

## 案例与结果

### 数据集

实验使用 `BATADAL` 数据，覆盖 `40` 天：

1. `10` 天 `OF`；
2. `10` 天 `UF`；
3. `10` 天 `R`；
4. `10` 天正常。

### 检测结果

表 5 显示：

1. 所有 `OF` 日志都只命中 `φ`；
2. 所有 `UF` 日志都只命中 `χ`；
3. 所有 `R` 日志都只命中 `ψ`；
4. 所有正常日志对三者都为 false。

因此最终：

1. `Precision = 1`
2. `Recall = 1`
3. `F-Measure = 1`
4. `Accuracy = 1`

### 结果边界

论文同时指出，这些性质是与领域专家共同构造的，因此成功并不意味着“任何水务攻击都能被识别”，而是说明这组 formalized domain rules 对当前三类攻击非常有效。

## 与本研究的关系

### 相关性分析

这篇论文和博士研究第二部分“验证场景与待验证性质生成”尤其相关，因为这里的性质几乎完全是从领域经验中反推出来的。

### 可借鉴之处

1. 把运行日志当作模型输入，而不是只验证设计期模型。
2. 让领域专家直接参与性质阈值构造。
3. 用 reachability 性质做异常检测，而不是只做离线正确性证明。

### 存在的不足与改进空间

1. 只覆盖三类异常；
2. 模型和性质强依赖离散化规则；
3. 缺少公开 `UPPAAL` 模型仓库，难以直接复跑。

### 对本研究的启发

它证明 `UPPAAL` 不只适用于“设计期验证”，也可以进入“日志驱动监测分析”场景。对博士研究而言，这种从运行日志回推 formal property 的方法很值得关注。
