## 简报

本文不是验证纯协议，而是验证一个真正的安全关键嵌入式控制器。作者把换挡控制器及其环境抽象为 timed automata，并围绕 `46` 条逻辑公式检查控制正确性与响应时间要求。论文的另一项贡献是提出了一个不修改模型检查器实现、只靠语法变换就能检查有界响应性质的方法。

- 系统：车辆换挡控制器。
- 特点：控制 clutch、engine、gearbox，依赖环境假设，安全关键。
- 规模：`46` 条逻辑公式；完整换挡应在 `1.5 s` 内完成，正常情况在 `1 s` 内完成；验证耗时约 `2.99 s`。
- 模型：gear controller + surrounding environment 的 timed automata 网络。
- 性质：安全性、响应时间、换挡完成性。
- 方法：控制器建模 + 环境建模 + 有界响应性质的可达性化转换。
- 结果：`46` 条性质全部自动检查，通过数秒内完成。

`工业控制需求 -> 控制器/环境 timed automata -> UPPAAL 可达性化响应时间验证 -> 安全与时间界证明`

## 论文定位

这篇论文是 `UPPAAL` 在控制器/嵌入式系统方向的代表案例。它不仅给出具体工业控制器验证，还展示了如何把“bounded response time”这类需求变成现有工具可检查的问题。

## 验证对象与问题背景

### 系统与场景

被验证系统是现代车辆中的换挡控制器。它通过通信网络接收驾驶员换挡请求，再驱动 clutch、engine 与 gearbox 完成实际换挡。

### 系统组成与运行机制

这不是一个抽象的“控制器状态机”例子，而是一个有明确执行链条的车辆控制子系统：

1. **驾驶员请求入口**
   - 驾驶员的 gear request 通过通信网络送达控制器。
2. **中心控制器**
   - gear controller 决定何时释放、结合、等待、切换以及在什么条件下继续下一步。
3. **执行部件**
   - clutch、engine、gearbox 是真正完成换挡动作的物理/逻辑执行端。
4. **环境模型**
   - 环境并不是背景噪声，而是控制器正确性的前提，因为换挡时间、零扭矩条件、同步速度等都依赖外部部件行为。

它的运行机制可以概括为：控制器接收换挡请求后，按一定先后关系协调 clutch、engine 和 gearbox 的动作，在满足同步与时间界条件后完成一次完整换挡。因此论文真正验证的是**控制器与环境共同组成的闭环换挡过程**，而不是单独一张控制逻辑图。

### 验证边界

本文验证的边界是**gear controller 设计及其 surrounding environment 假设下的行为正确性**。也就是说，作者不是验证整车所有控制逻辑，而是在“给定环境约束成立”的前提下验证换挡子系统。

### 核心问题

换挡过程既要正确又要及时。若控制序列、时序假设或环境交互处理不当，就可能导致车辆行为不安全。因此，仅靠测试和仿真并不足够，需要系统地验证控制逻辑及其时间边界。

### 研究动机

论文来自 Mecel AB 与 Uppsala University 的联合项目，目标是在设计早期就用形式化方法描述草案，并用符号仿真和模型检查帮助调试和验证控制逻辑。

## 模型与形式化建模

论文明确说明，模型不仅包含 gear controller 本身，还包含 surrounding environment。环境中保留了 clutch、engine、gearbox 等低层部件与通信交互，从而使控制器性质可以在“给定环境假设”下被解释。

文中给出的关键时间界包括：

1. gearbox release：`100-200 ms`
2. gearbox set：`100-300 ms`
3. clutch：`100-150 ms`
4. engine zero torque：`400 ms`
5. engine synchronization speed：`500 ms`

这些环境参数不是附带说明，而是模型的一部分。

## 验证目标与性质

论文把非形式化工业需求整理成 `46` 条逻辑公式，主要覆盖：

1. 控制序列的安全性。
2. 换挡动作最终完成。
3. 响应时间受界。
4. 不同子部件之间的协调顺序与时序约束。

由于当时 `UPPAAL` 主要提供可达性分析，作者特别处理了 bounded response time 性质，使其能被转写为可达性问题。

### 性质分组与实际含义

把 `46` 条公式按系统语义理解，可以分成几类：

1. **动作顺序与互锁安全性**
   - 哪些部件必须先动作、哪些条件未满足时绝不能继续下一步，这决定换挡是否安全。
2. **子部件时间界**
   - clutch、gearbox、engine 各自的动作必须在给定时间窗口内完成，否则后续控制决策就失去依据。
3. **整次换挡的完成性**
   - 换挡不仅要“最终能完成”，还要在 `1 s` 或 `1.5 s` 这类工程上可接受的时间内完成。
4. **有界响应性质**
   - 这类性质最接近现实控制需求，例如“某请求出现后，某响应必须在给定时间内成立”。

### 性质来源与表达方式

这些性质直接来自 Mecel AB 提供的非形式化工业需求。论文的重要贡献之一，就是把这些需求系统化地转成 `46` 条逻辑公式；因此这里的“性质”不是抽象分类，而是对真实控制需求的逐条形式化。

## 核心方法与验证流程

论文的方法可以概括为：

1. 从工业需求文档抽取控制器需求与环境假设。
2. 建立 gear controller 及环境的 timed automata 模型。
3. 用简单逻辑表达安全和响应时间性质。
4. 对有界响应性质做语法变换，使之适配 `UPPAAL` 的可达性分析框架。
5. 借助符号仿真先调试，再做自动验证。

这条方法线对今天依然有价值，因为很多工程需求仍然要先被“转写”成现有工具能吃下去的形式。

## 案例与结果

论文给出的结果相当扎实：

1. 控制器正确性被形式化为 `46` 条逻辑公式。
2. 完整换挡应在 `1.5 s` 内完成，正常情况约束在 `1 s` 内。
3. 在 Pentium `75 MHz`、`24 MB` 内存机器上，全部 `46` 条性质验证耗时约 `2.99 s`。

对早期工业控制案例而言，这说明 `UPPAAL` 已不仅能处理小教学例子，而是能支撑结构化的嵌入式控制验证。
