# `uppaal_apps/` 操作规范

本文档用于固定 [SUMMARY.md](./SUMMARY.md) 与 `open_explore/uppaal_apps/` 的后续维护方式，作为后续 AI 在该专题下持续扩张 `UPPAAL` 应用文库时的统一操作规范。

## 0. 文档关系与使用顺序

`uppaal_apps/` 下的核心文档分工如下：

1. [README.md](./README.md)
   - 负责解释应用文库定位、纳入/排除标准和与 `uppaal_tech/` 的边界。
2. [GUIDE.md](./GUIDE.md)
   - 负责规定检索、筛选、目录维护、[SUMMARY.md](./SUMMARY.md) 回填和一致性检查规范。
3. [SUMMARY.md](./SUMMARY.md)
   - 负责记录当前总账、应用分类、条目清单、更新日志与失败历史。

默认推荐顺序如下：

1. 先读 [README.md](./README.md)。
2. 再读 [GUIDE.md](./GUIDE.md)。
3. 再读 [SUMMARY.md](./SUMMARY.md)。
4. 最后进入具体论文目录，按 `bibtex.bib -> paper_content.txt -> paper.pdf（必要时）` 的顺序工作。

## 1. 目标与范围

`uppaal_apps/` 只负责收录 `UPPAAL` 的应用与案例工作，不负责维护 `UPPAAL` 本体技术。

本论文集的直接目标如下：

1. 沉淀 `UPPAAL` 在协议、控制系统、嵌入式系统、软件系统和工业场景中的实际使用模式。
2. 梳理不同案例里常见的建模对象、性质类型、验证目标和结果表达方式。
3. 为博士研究后续案例设计、场景生成和性质整理提供可对照的应用素材。

以下内容不属于本论文集目标：

1. `UPPAAL` 核心算法、数据结构、扩展能力和工具工程论文。
2. 泛 timed automata 案例，但与 `UPPAAL` 没有稳定直接关系的工作。
3. 只有工具提及、没有实质案例贡献的条目。

## 2. 检索策略

### 2.1 应用关键词簇

默认按“`UPPAAL + 应用对象 + 任务类型`”构造关键词簇，例如：

1. `UPPAAL + protocol/controller/embedded system/industrial case study`
2. `UPPAAL + verification/testing/scheduling + 具体系统名`
3. `UPPAAL + official case study`

### 2.2 与技术文库的分流规则

遇到候选条目时先做一次强制分流：

1. 若主贡献是新算法、新抽象、新数据结构、新引擎能力，转入 [uppaal_tech/README.md](../uppaal_tech/README.md)。
2. 若主贡献是利用 `UPPAAL` 验证某个对象、展示某种建模方法或积累工程案例，保留在本应用文库。

### 2.3 关键词簇维护约束

1. [SUMMARY.md](./SUMMARY.md) 中关键词簇相关章节默认每节不超过 `10` 行。
2. 必须做压缩式整合更新，禁止把搜索过程机械堆积成流水账。
3. 如果某类应用对象长期低命中，应降权，而不是无限继续堆词。

## 3. 筛选、去重与失败规则

### 3.1 收录条件

默认至少满足以下全部条件：

1. 论文正文以具体应用对象为中心，而不是以工具本体技术为中心。
2. `UPPAAL` 在正文里承担了实质建模、验证、测试或分析作用。
3. 能获得合法 PDF，并生成可用 `paper_content.txt`。

### 3.2 降优先级条件

1. 案例本身太薄，只有简单演示意义。
2. 与控制系统或形式化验证研究目标相关性较弱。
3. 主要价值只是“用过 `UPPAAL`”，而不是提供可复用案例模式。

### 3.3 排除条件

1. 主贡献其实是技术本体，应转入 [uppaal_tech/README.md](../uppaal_tech/README.md)。
2. 无法取得合法可用 PDF。
3. 提取结果严重异常且短期内无法补齐。

### 3.4 去重规则

1. 先按 DOI 去重。
2. DOI 缺失时按标准化标题去重。
3. 标题近似时，再结合作者、年份、会议/期刊综合判断。

### 3.5 失败重试规则

1. 最近 `5` 天内已明确失败的候选，默认跳过。
2. 超过 `5` 天可重试；若再次失败，继续追加失败记录。

## 4. 目录与文件规范

`uppaal_apps/` 下每篇论文必须独占一个子目录。目录名默认沿用稳定 slug。

每个论文目录至少应包含：

1. `paper.pdf`
2. `paper_content.txt`
3. `bibtex.bib`

后续若开始做案例抽取，建议逐步补以下派生文件：

1. `desc.md`
2. 应用对象与建模摘要
3. 验证性质与结果摘要

## 5. 内容整理策略

当前 `uppaal_apps/` 处于初始化阶段，因此默认先保证：

1. PDF 原文在库。
2. BibTeX 元信息可用。
3. `paper_content.txt` 可检索可追溯。

当后续开始做单篇深度整理时，优先提取：

1. 应用对象是什么。
2. 为什么选择 `UPPAAL`。
3. 模型和性质是怎样组织的。
4. 结果能给博士研究带来什么启发。

## 6. [SUMMARY.md](./SUMMARY.md) 撰写规范

[SUMMARY.md](./SUMMARY.md) 必须持续维护以下章节：

1. 文档定位与使用方式。
2. 收录边界回顾。
3. 检索关键词簇。
4. 当前收录统计。
5. 应用分类。
6. 论文清单。
7. 更新日志。
8. 失败与阻塞记录。

维护约束如下：

1. 论文清单必须按年份升序维护。
2. 统计数字必须与表格真实内容一致。
3. 命中技术本体论文时，不在本文件正式入账，而是转去 `uppaal_tech/`。

## 7. 工作流程

一轮完整工作默认按以下顺序进行：

1. 先读 [README.md](./README.md)、[GUIDE.md](./GUIDE.md)、[SUMMARY.md](./SUMMARY.md)。
2. 先做“应用/技术”分流判断。
3. 先补历史欠账，再扩新条目。
4. 完成单论文目录必要文件后，再统一回填 [SUMMARY.md](./SUMMARY.md)。
5. 回填后检查统计、年份顺序、分类和链接一致性。

## 8. 质量与可追溯性要求

1. 所有收录判断都应有原文依据。
2. 若证据不足，必须如实写入失败或待补证记录。
3. 不得在仓库文档中写入外部本地绝对路径。
