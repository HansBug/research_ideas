# `uppaal_apps/` 操作规范

本文档用于固定 [SUMMARY.md](./SUMMARY.md) 与 `open_explore/uppaal_apps/` 的后续维护方式，作为后续 AI 在该专题下持续扩张 `UPPAAL` 应用验证文库时的统一操作规范。

## 0. 文档关系与使用顺序

`uppaal_apps/` 下的核心文档分工如下：

1. [README.md](./README.md)
   - 负责解释本论文集为什么存在、收什么、不收什么，以及与 [uppaal_tech/README.md](../uppaal_tech/README.md) 的边界。
2. [GUIDE.md](./GUIDE.md)
   - 负责规定检索、筛选、目录维护、[SUMMARY.md](./SUMMARY.md) 回填和一致性检查规范。
3. [SUMMARY.md](./SUMMARY.md)
   - 负责记录当前总账、分类口径、统一论文表、材料公开性清单、更新日志和失败历史。
4. [DESC_GUIDE.md](./DESC_GUIDE.md)
   - 负责单篇 `desc.md` 的专项结构和写法，尤其约束被验证系统、系统特点、系统规模、模型、性质、验证流程和公开性信息的展开方式。

默认推荐顺序如下：

1. 先读 [README.md](./README.md)。
2. 再读 [GUIDE.md](./GUIDE.md)。
3. 再读 [SUMMARY.md](./SUMMARY.md)。
4. 若任务涉及生成或重写单篇 `desc.md`，再读 [DESC_GUIDE.md](./DESC_GUIDE.md)。
5. 最后进入具体论文目录，按 `bibtex.bib -> paper_content.txt -> paper.pdf（必要时） -> desc.md` 的顺序工作。

## 1. 目标、范围与当前主攻方向

`uppaal_apps/` 不是一般性的“`UPPAAL` 应用收藏夹”，而是一个面向**形式化验证案例**的专题文库。当前直接目标如下：

1. 沉淀 `UPPAAL` 在具体系统或模型上的验证应用主线。
2. 稳定抽取跨论文可复用的信息：
   - 被验证系统是什么；
   - 它有什么关键特点；
   - 规模有多大；
   - 如何抽象成 `UPPAAL` 模型；
   - 待验证性质是什么；
   - 查询或分析流程如何组织；
   - 模型、案例、数据或补充材料是否公开。
3. 为博士研究后续的状态机建模、性质整理、验证剖面与修复闭环提供案例支撑。

### 1.1 一级领域口径

后续在 [SUMMARY.md](./SUMMARY.md) 中，默认按以下一级领域维护应用分类：

| Emoji | 领域 | 含义 |
|---|---|---|
| 🛰️ | 协议与通信系统 | 网络协议、通信协议、分布式交互、消息同步等 |
| 🎛️ | 控制器与嵌入式系统 | 控制逻辑、嵌入式控制器、实时控制软件等 |
| 🏭 | 工业系统与 `CPS` | 工厂、制造、工业控制、混合系统、工业案例等 |
| 🚦 | 交通、调度与资源系统 | 交通控制、调度、资源分配、实时任务系统等 |
| 🧩 | 软件、架构与组件系统 | 软件组件、软件架构、并发程序、服务组合等 |

原则上每篇论文只给一个一级主领域；若确有跨域性，在 `关键词` 或 `一句话简介` 中补充，不要在主分类上重复贴多个领域。

这里还必须明确：

1. 上表是**当前版本**的默认领域骨架，不是后续不可变更的固定分类。
2. 若实际扩库中稳定出现新的应用簇，或现有某一类已经过宽、影响检索与汇总，应按实际情况动态扩充、拆分或合并领域类型。
3. 一旦调整领域类型，必须在同一轮同步更新：
   - [README.md](./README.md) 中的领域说明；
   - [GUIDE.md](./GUIDE.md) 中的一级领域口径；
   - [SUMMARY.md](./SUMMARY.md) 中的分类统计与统一论文表对应字段。

### 1.2 `UPPAAL` 线口径

统一论文表中的 `UPPAAL线` 列默认按以下口径填写：

1. `UPPAAL`
2. `UPPAAL SMC`
3. `UPPAAL Tiga`
4. `UPPAAL CORA`
5. `UPPAAL Stratego`
6. `UPPAAL PORT`
7. `ECDAR`
8. `其他 UPPAAL 谱系变体`

### 1.3 非目标边界

以下内容即使和 `UPPAAL` 有关联，也不属于本论文集的主任务：

1. 主要贡献是 `UPPAAL` 本体算法、引擎、抽象、数据结构或实现架构的论文，应转入 [uppaal_tech/README.md](../uppaal_tech/README.md)。
2. 泛 timed automata / 泛 model checking 案例，但与 `UPPAAL` 没有稳定直接关系的工作。
3. 只有调度、优化、测试、控制合成或仿真结论，而没有清晰形式化验证问题、性质或查询的论文。
4. 只是在正文中顺带提到 `UPPAAL`，没有形成可复用应用案例的条目。
5. 没有合法 PDF、没有可靠提取文本且短期内无法补齐的条目。

## 2. 检索策略

### 2.1 以验证为中心的关键词簇

默认按“`UPPAAL + 验证任务 + 应用对象`”构造关键词簇，而不是只搜索“`UPPAAL + application`”。

推荐优先使用以下几类词簇：

1. 对象驱动
   - `UPPAAL + formal verification/model checking + protocol/controller/embedded system/industrial system/software component`
2. 任务驱动
   - `UPPAAL + safety/liveness/deadlock/schedulability/reachability/consistency + case study`
3. 变体驱动
   - `UPPAAL SMC/Tiga/CORA/Stratego/ECDAR + case study/industrial/application`
4. 领域驱动
   - `UPPAAL + automotive/railway/avionics/medical/manufacturing/network protocol`
5. 官方入口反推
   - 先看 [uppaal_tech/README.md](../uppaal_tech/README.md) 中的官网、案例页与作者主线，再反向追具体应用论文。

### 2.2 扩词逻辑

命中某篇高质量论文后，默认从以下四个方向继续扩：

1. **对象扩词**
   - 从系统名、协议名、控制器名继续追同类案例。
2. **性质扩词**
   - 从 `safety / liveness / deadline / schedulability / refinement` 继续追同类验证任务。
3. **变体扩词**
   - 从 `UPPAAL SMC / Tiga / CORA / Stratego / ECDAR` 继续追同一工具线的应用文献。
4. **作者扩词**
   - 从 [uppaal_tech/README.md](../uppaal_tech/README.md) 与 [uppaal_tech/SUMMARY.md](../uppaal_tech/SUMMARY.md) 中的核心作者和技术分支，反向追其应用论文。

### 2.3 低命中方向的降权规则

以下检索方式命中率通常偏低，后续应降权而不是持续堆词：

1. 只搜 `UPPAAL + application`。
2. 只搜 `UPPAAL + optimization/scheduling/testing`，但没有同时限定 `formal verification/model checking`。
3. 只搜泛 timed automata 领域词，没有同时限定 `UPPAAL`。
4. 只搜过宽的行业词，如 `system`、`industry`、`controller`，但没有加验证任务词。

### 2.4 与技术文库的分流规则

遇到候选条目时，先做一次强制分流：

1. 若主贡献是新算法、新抽象、新数据结构、新引擎能力，转入 [uppaal_tech/README.md](../uppaal_tech/README.md)。
2. 若主贡献是利用 `UPPAAL` 验证某个具体对象、展示建模方式、分析性质或积累工程案例，保留在本应用文库。
3. 若技术与应用都很强：
   - 优先根据摘要、引言、贡献列表和结论判断主要贡献中心；
   - 必要时在两边互相交叉引用，但正式入账只放一边。

### 2.5 关键词簇维护约束

1. [SUMMARY.md](./SUMMARY.md) 中关键词簇相关章节默认每节不超过 `10` 行。
2. 必须做压缩式整合更新，禁止把搜索过程机械堆积成流水账。
3. 若某类对象、性质或变体连续多轮低命中，应在 [SUMMARY.md](./SUMMARY.md) 中明确降权。
4. 新增关键词簇后，应优先整合或替换旧观察，而不是简单累加旧 bullet。

### 2.6 批量规模要求

若本轮任务是“扩库”，默认采用以下批量下限：

1. 一轮实际筛查候选论文数原则上不应少于 `20` 篇。
2. 一轮最终正式入库论文数原则上不应少于 `10` 篇。
3. 若因领域过窄、开放获取受限或资料稀缺达不到该规模，应在更新日志中如实说明。

## 3. 筛选、去重与失败规则

### 3.1 收录条件

默认至少满足以下全部条件：

1. 论文正文以具体验证对象为中心，而不是以工具本体技术为中心。
2. `UPPAAL` 在正文里承担了实质建模、验证、分析或性质检查作用。
3. 能获得合法 PDF，并生成质量可用的 `paper_content.txt`。
4. 能从正文中稳定提取以下至少四类信息：
   - 被验证系统；
   - 模型抽象；
   - 待验证性质；
   - 查询/流程；
   - 结果或案例结论。

### 3.2 降优先级条件

1. 应用对象真实，但性质表达、查询或验证流程交代很弱。
2. 主要价值在调度、测试或优化，验证只是配套存在。
3. 与控制系统、状态机表示或形式化验证主线的相关性偏弱。
4. 论文适合做“补充背景”，但不适合做代表案例。

### 3.3 排除条件

1. 主贡献其实是技术本体，应转入 [uppaal_tech/README.md](../uppaal_tech/README.md)。
2. 无法取得合法可用 PDF。
3. 文本提取严重异常且短期内无法补齐。
4. 正文没有清晰被验证系统、性质或结果，无法支持高质量 `desc.md`。

### 3.4 去重规则

1. 先按 DOI 去重。
2. DOI 缺失时按标准化标题去重。
3. 标题近似时，再结合作者、年份、会议/期刊综合判断。

### 3.5 失败重试规则

1. 最近 `5` 天内已明确失败的候选，默认跳过。
2. 超过 `5` 天可重试；若再次失败，继续追加失败记录。

## 4. 目录与文件规范

`uppaal_apps/` 下每篇论文必须独占一个子目录。目录名默认沿用稳定 slug。

每个论文目录至少应包含：

1. `paper.pdf`
2. `paper_content.txt`
3. `bibtex.bib`
4. `desc.md`

### 4.1 完成度规则

本论文集采用如下 collection 级默认规则：

1. **默认完成态**
   - `paper.pdf + paper_content.txt + bibtex.bib + desc.md` 四件套齐全；
   - 已正式记入 [SUMMARY.md](./SUMMARY.md)；
   - 统一论文表、材料公开性表和统计均已回填。
2. **临时待补态**
   - 只有在用户明确要求“先收录、不写 `desc.md`”或“本轮只补三件套”时，才允许出现；
   - 必须在 [SUMMARY.md](./SUMMARY.md) 中明确标成 `⏳ 尚未提取`。

换言之：**只要用户没明确说不写 `desc.md`，本 collection 默认不允许把“缺 `desc.md`”当作已完成。**

### 4.2 `paper_content.txt` 生成规则

1. 默认优先使用 `python -m tools.pdf_extractor -m text` 生成。
2. 若提取结果显著异常，应立即切换 `ocr` 模式。
3. 不得跳过 `paper_content.txt` 直接只看 PDF 零散片段后开始写 `desc.md`。

### 4.3 `desc.md` 触发规则

在本论文集内，以下情况默认都必须补齐 `desc.md`：

1. 论文被正式纳入本 collection。
2. 论文被用于跨论文比较或研究启发归纳。
3. 论文被视为某个领域、某种性质或某条 `UPPAAL` 变体线的代表案例。
4. 论文被用来支撑博士研究中的具体论证。

只有当用户明确要求“本轮先不要写 `desc.md`”时，才允许暂缓。

## 5. 内容整理策略

### 5.1 统一论文表必须抽取的字段

后续正式入账时，至少应为每篇论文抽取以下字段：

1. `年份`
2. `Key`
3. `标题`
4. `关键词`
5. `领域`
6. `被验证系统`
7. `系统特点`
8. `系统规模`
9. `UPPAAL线`
10. `验证任务`
11. `性质类型`
12. `状态`
13. `一句话简介`
14. `链接`

### 5.2 单篇 `desc.md` 应优先提取的内容

对正式入账的条目，优先提取以下信息：

1. 被验证系统到底是什么，处于什么应用场景。
2. 系统的关键特点是什么，为什么值得形式化验证。
3. 系统由哪些核心部件、角色、进程、控制环节或通信实体构成。
4. 这些部件如何交互，系统的基本运行机制是什么。
5. 验证边界在哪里：论文实际验证的是整个系统、某个控制器、某个协议层、某个启动阶段，还是某个子机制。
6. 规模信息是什么，例如模板数、性质数、参与方数量、时间界、工业文档规模等。
7. 它怎样被抽象为 `UPPAAL` 模型，模型边界和环境假设是什么。
8. 待验证性质是什么，如何写成查询。
9. 性质应尽量按“性质簇”解释清楚，而不是只写类别名。
10. 验证流程怎样运行，是否用了特定变体、抽象、组合或统计配置。
11. 结果是什么，发现了什么问题，或证明了什么结论。
12. 模型、案例、数据、脚本、benchmark 或官方案例入口是否公开，以及如何获取。

这里额外增加 collection 级硬要求：

1. `desc.md` 中“验证对象与问题背景”一节，默认必须把“系统是什么样的系统、由哪些关键部件组成、系统怎么运行、此次验证覆盖哪一层边界”讲清楚。
2. `desc.md` 中“验证目标与性质”一节，默认必须把“验证的是哪几类性质、每类性质在现实系统里对应什么风险或需求、若原文给出典型查询或性质族则应尽量保留”讲清楚。
3. 只写“安全性、活性、时序约束”这种标签而不解释其在该系统中的具体含义，视为信息不足。

### 5.3 案例/模型/数据公开性表

后续 [SUMMARY.md](./SUMMARY.md) 中必须维护单独的“案例/模型/数据公开性清单”表。每条至少包含：

1. `论文`
2. `状态`
3. `案例/模型/数据`
4. `来源类型`
5. `制作/来源方式`
6. `可获取性`
7. `获取方式/链接`
8. `简述`

其中：

1. `可获取性` 统一只用 emoji，固定口径如下：

| Emoji | 含义 |
|---|---|
| 🟢 | 可直接获取：存在当前可访问的公开下载链接、仓库、补充材料页或官方案例入口，能够直接拿到相应材料 |
| 🟡 | 需联系申请：原文明确说明需要联系作者、团队或项目方申请 |
| 🟠 | 信息不清：原文或官网说明存在相关材料，但没有稳定、清晰、当前可用的公开获取路径，或历史链接已失效 |
| 🔒 | 难以取得：案例强依赖企业内部资产、工业实现、受限规格或现实上难以公开的材料 |

2. 这四类不是“质量高低”，只是四种不同的获取状态。
3. `获取方式/链接` 一列只要存在明确 URL，就必须写成 Markdown 链接。
4. 若只有官网案例页、benchmark 页、作者主页或 DOI 这类间接入口，也应优先给出该入口链接，而不是留空。
5. 若没有清晰链接，必须明确写“原文未提供公开下载链接”或等价表述。

### 5.4 `SUMMARY.md` 与 `desc.md` 的分工

默认规则如下：

1. [SUMMARY.md](./SUMMARY.md) 负责统一字段、分类、状态和材料公开性总账。
2. 单篇系统背景、建模细节、性质细节和结果解释应尽量写入 `desc.md`。
3. 若某个观察只对单篇有效，写在 `desc.md`；只有跨论文可复用的观察才写回 [SUMMARY.md](./SUMMARY.md)。

## 6. [SUMMARY.md](./SUMMARY.md) 撰写规范

[SUMMARY.md](./SUMMARY.md) 必须持续维护以下章节：

1. 文档定位与使用方式。
2. 当前关注边界。
3. 检索关键词簇。
4. 当前收录统计。
5. 按年份分布统计。
6. 应用分类口径。
7. 状态与公开性口径。
8. 统一论文总表。
9. 案例/模型/数据公开性清单。
10. 更新日志。
11. 失败与阻塞记录。

维护约束如下：

1. 关键词簇相关小节默认每节最多 `10` 行，必须整合更新而不是持续累加。
2. 统一论文总表第一列固定为 `领域`，但全表仍必须按年份从低到高排列；同年按 `Key` 字典序稳定排序。
3. 统计数字必须与统一论文表和公开性清单真实内容一致。
4. 正式入账的论文必须进入统一论文总表，不要为“本轮新增”反复新开临时表。
5. 命中技术型论文时，不在本文件正式入账，而是转去 `uppaal_tech/`。
6. 若用户明确允许暂缓 `desc.md`，则必须明确写 `⏳ 尚未提取`，不能默默留在目录里不入账。
7. 不再维护 `详度` 与 `实现` 两列；改为维护“被验证系统 / 系统特点 / 系统规模”和单独的公开性清单。
8. `状态` 列默认只使用：
   - `🟢 直接可用`
   - `🟡 可整理`
   - `⚪ 未收获`
   - `⏳ 尚未提取`
9. 统一论文总表最后一列固定命名为 `链接`，默认使用短链接格式 `[paper](相对路径)`。
10. “当前收录统计”与“按年份分布统计”都必须显式维护年份信息，不能只给总数而完全不写时间维度。

## 7. 工作流程

一轮完整工作默认按以下顺序进行：

1. 先读 [README.md](./README.md)、[GUIDE.md](./GUIDE.md)、[SUMMARY.md](./SUMMARY.md)。
2. 若本轮涉及 `desc.md`，再读 [DESC_GUIDE.md](./DESC_GUIDE.md)。
3. 先做“技术/应用”分流，再做“验证主线/非验证主线”判断。
4. 先补历史欠账，再扩新条目。
5. 新条目入库时，先补齐 `paper.pdf + paper_content.txt + bibtex.bib`。
6. 若用户没有明确豁免，再立即补齐 `desc.md`。
7. 单篇四件套齐全后，再统一回写 [SUMMARY.md](./SUMMARY.md) 的总表、公开性表和统计。
8. 一轮结束前，复核统计、排序、字段口径、链接和失败记录。

## 8. 质量与可追溯性要求

1. 所有字段、结论、标签、统计和公开性判断都应有原文或官方入口依据。
2. 若证据不足，必须如实写“原文未充分说明”或“官方仅给历史入口但当前链接失效”，不能主观补齐。
3. 对工业案例尤其要区分：
   - 论文是否公开；
   - 案例是否公开；
   - 模型文件是否公开；
   - 当前公开链接是否仍然有效。
4. `desc.md` 与 [SUMMARY.md](./SUMMARY.md) 中的被验证系统、系统特点、系统规模、验证任务和公开性口径必须保持一致。
