## 简报

这篇论文是典型铁路联锁案例。作者没有停留在抽象规则层，而是围绕 Rawalpindi Cantt 车站的真实客运股道，提取了进路冲突关系、道岔定位、信号开放和取消进路逻辑，并把这些规则转成可由 `UPPAAL` 检查的 timed automata 模块。

- 系统：Rawalpindi Cantt 车站客运股道联锁系统。
- 特点：固定闭塞、两显示臂板信号机、道岔机械联锁向软件联锁升级。
- 规模：`5` 条客运线、`25` 架信号机、`27` 组道岔、`18` 条进路。
- 模型：由 route selection、point driver、light driver、route automaton、watchdog 等模板组成。
- 性质：碰撞避免、脱轨避免、超时错误检测、取消进路安全、点机故障时不开放信号。
- 方法：从联锁表提取冲突关系和点位要求，再构造成模块化 timed automata 并执行 `CTL` 查询。
- 结果：所检验的代表性进路均满足安全性质，且模型可通过增加布尔冲突变量适应线路扩展。

`站场联锁表/平面图 -> 模块化 timed automata -> CTL 安全查询 -> 进路冲突/点位/信号/取消逻辑验证`

## 论文定位

本文属于 `🎛️ + 🚦`。它验证的是具体车站联锁控制系统的设备控制逻辑，而不是协议规范或抽象安全框架。与 `uppaal_tech` 类工作不同，这里真正的验证对象是实际站场的进路与信号控制。

## 验证对象与问题背景

### 系统与场景

被验证对象是巴基斯坦 Rawalpindi Cantt 车站的客运股道联锁系统。原站场采用分布式机械杠杆室控制，作者的目标是给该站设计一套软件化自动联锁方案。

### 系统组成与运行机制

论文重点涉及的现场元素包括：

1. `Track circuit`
   - 检测股道占用；
2. `Signal`
   - 授权列车进入闭塞分区；
3. `Points`
   - 决定列车走向；
4. `Traffic control center / interface layer`
   - 发出选路请求；
5. `Interlocking layer`
   - 检查请求是否与既有进路冲突、股道是否空闲、点机与信号是否反馈正确。

### 验证边界

论文验证的是**站内进路建立、道岔定位、信号开放、列车通过和取消进路**这条控制链，不覆盖调车作业、`ATS` 或更高层列车运行图优化。

### 核心问题

1. 冲突进路是否可能同时开放，导致碰撞；
2. 列车经过道岔时，道岔是否可能被切换而导致脱轨；
3. 点机或信号机超时无反馈时，系统是否会正确进入错误处理；
4. 取消进路时，锁闭是否会在不安全时刻过早释放。

### 研究动机

铁路联锁是典型 safety-critical real-time system，仅靠测试、仿真和同行评审无法穷尽错误，因此需要形式化验证。

## 模型与形式化建模

### 模块划分

作者在 `UPPAAL` 中采用模块化建模：

1. **Route automaton**
   - 模拟进路占用、列车进入/离开、停站占用。
2. **Route selection automaton**
   - 核心选路逻辑，检查冲突进路、股道占用并协调后续模块。
3. **Point driver automaton**
   - 控制道岔动作并等待反馈，带 watchdog 超时错误分支。
4. **Light driver automaton**
   - 控制信号开放与回红，也支持取消进路时的延迟释放。
5. **Watchdog automata**
   - 对现场设备反馈超时进行 fail-safe 处理。

### 关键抽象

1. 用布尔变量编码冲突进路是否已被锁闭；
2. 用 `urgent` channel 处理某些必须立即发生的反馈；
3. 点机和信号机都引入“超时即错误”的 fail-safe 分支；
4. 取消进路后，信号立即回红，但道岔和进路锁闭要在缓冲时间后释放。

### 环境假设

论文明确假设：

1. 司机总是遵守信号显示；
2. 不包含调车和部分附属信号；
3. 使用两显示信号；
4. 验证重点在客运股道。

## 验证目标与性质

### 待验证问题

论文给出了至少六类关键性质，其中代表性的是：

1. 碰撞避免；
2. 脱轨避免；
3. 道岔/信号的超时错误状态判定；
4. 取消进路安全；
5. 点机故障时不得开放信号。

### 性质类型

1. 安全性质；
2. 有界响应/超时性质；
3. 设备故障处理正确性；
4. 锁闭/解锁时序性质。

### 性质分组与实际含义

1. **Collision avoidance**
   - 一条进路被建立时，所有冲突进路必须保持在初始不可用状态。
2. **No derailment**
   - 列车在进路内运行时，道岔位置必须保持为该进路要求的位置。
3. **Timeout correctness**
   - 超过规定时间必须到达错误状态；未超时则不能误报错误。
4. **Cancel-signal safety**
   - 取消进路后只有在缓冲时间过去后才能释放锁闭。
5. **No signal after point error**
   - 道岔设置失败时，后续信号绝不允许开放。

### 查询表达

论文给出了典型 `CTL` 形式，例如：

$$
AG[\lnot a.start \Rightarrow (b.start \land c.start \land d.start)]
$$

用于表达“当进路 `a` 被建立时，其冲突进路 `b/c/d` 必须始终保持在初始状态”。取消进路安全则写成：

$$
AG[\psi \Rightarrow AF \, \phi]
$$

其中 `\psi` 表示收到取消命令，`\phi` 表示延迟满足后清空并释放进路。

## 核心方法与验证流程

1. 从车站 interlocking tables 提取 route dependencies 和 conflicting routes；
2. 按功能拆分为选路、点机、信号机、股道占用等自动机模块；
3. 为设备反馈引入 watchdog 定时器；
4. 对每条代表性进路组合其相关冲突进路并做并行验证；
5. 在 `UPPAAL` 中对每条性质运行 `CTL` 查询，并在 simulator 中查看消息序列图。

论文特别强调：由于完整站场状态空间较大，实际验证时只把目标进路和与其冲突或共享道岔的进路组成并行系统，而不是一次性把全站所有进路整体展开。

## 案例与结果

### 案例规模

1. `5` 条客运线；
2. `25` 架 semaphore signals；
3. `27` 组 mechanically operated points；
4. `18` 条定义好的 routes。

### 主要验证任务

论文对每条进路都检查死锁自由和若干安全性质。表 4 给出代表性进路 “Down Home to Number 2 Platform” 的结果。

### 主要结果

1. 冲突进路互斥性质满足；
2. 脱轨避免性质满足；
3. 点机与信号超时错误性质满足；
4. 取消进路后 `60 s` 缓冲后再释放锁闭的性质满足；
5. 点机出错时不会进入 `signal_order` 开放信号状态。

对代表性进路，文中给出的资源消耗也很具体：

1. 冲突进路碰撞自由性质需要 `>25 GB` 内存、`>5 h`；
2. 脱轨性质约 `>500 MB`、`>1 h`；
3. 点机和信号超时性质约 `>2 MB`、`>10 min`。

### 结果解释

这些结果说明模型不只是“纸面安全”，而是能够把联锁表中的核心工程规则形式化为自动检查的安全条件，并保留对未来站场扩展的适配性。

## 与本研究的关系

### 相关性分析

该文非常适合作为“从真实控制表与现场规则抽取状态机”的案例，对博士研究中的需求到模型转换尤其重要。

### 可借鉴之处

1. 以实际联锁表为基础抽取状态机条件；
2. 通过模块化模板抑制状态爆炸；
3. 把故障处理路径也纳入正式性质，而不是只验证正常流。

### 存在的不足与改进空间

1. 完整站场整体验证仍很昂贵；
2. 不覆盖调车和更高层调度功能；
3. 原文未提供独立 `UPPAAL` 工程和联锁表数据文件。

### 对本研究的启发

论文说明控制系统的很多关键性质并不来自抽象安全口号，而是来自“冲突表、锁闭条件、释放条件、超时条件”这类结构化规则，非常适合作为自动化性质生成的来源。
