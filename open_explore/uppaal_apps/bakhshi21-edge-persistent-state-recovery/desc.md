## 简报

本文验证的不是单个协议报文，而是一整套边缘容器架构中的“应用 + 存储 + 复制 + 恢复”闭环。作者关心的核心是：状态化应用如果依赖本地卷，一旦容器或节点故障就会丢状态，那么能否通过存储容器和复制数据结构把状态保住并恢复出来。

- 系统：运行在 fog/edge 节点上的有状态应用、存储容器与复制数据结构。
- 特点：同时考虑应用级故障、节点级故障、容器重启和副本一致性。
- 规模：代表性模型含多个 `App`、`SC`、`Node Failure` 自动机以及复制数组。
- 模型：`UPPAAL` 自动机网络，显式表示 `rep_data_struct`、`l_rep_data_struct` 等状态。
- 性质：卷的易失性、故障恢复、数据可用性、最终一致性、无死锁。
- 方法：把性质分成 `MP/FTP/CP` 三组，用查询逐项验证。
- 结果：所有性质均满足，说明方案既能恢复，又能保持副本一致。

`边缘有状态容器问题 -> App/SC/NodeFailure 模型 -> MP/FTP/CP 查询 -> 恢复与一致性结论`

## 论文定位

本文属于 `🧩 + 🌐` 的边缘软件服务案例。虽然底层用到了 `RAFT`，但论文真正验证的是容器化恢复机制和存储一致性流程，因此更像软件架构与运行时容错验证，而不是单纯协议论文。

## 验证对象与问题背景

### 系统与场景

对象是部署在边缘或雾层上的有状态容器化应用。现有 Kubernetes 对无状态应用恢复较友好，但对依赖本地卷的有状态应用来说，容器或节点失败后状态容易丢失。

### 系统组成与运行机制

论文中的关键组成包括：

1. `App`：负责执行业务任务并更新内部状态
2. `SC`：负责维护复制数据结构和状态落盘
3. `Replicated Data Structure`：每个节点上的本地复制状态
4. `Node Failure` 自动机：驱动节点失败与恢复
5. `RAFT` 共识机制：保证多个副本之间的最终一致

应用每次执行后先把状态写入本地卷，再复制到本地 replicated data structure，随后通过副本同步机制传播到其他节点。

### 验证边界

论文验证的是恢复与一致性机制本身，不覆盖完整云边协同调度、业务负载模型或更复杂应用逻辑。

### 核心问题

作者要回答：

1. 卷的易失性是否被正确建模
2. 应用故障后是否能自动重启
3. 节点故障后应用是否会被迁移并恢复
4. 副本状态是否最终和 leader 一致

## 模型与形式化建模

### 抽象对象

模型显式表示：

1. 应用的部署、执行、失败、恢复状态
2. 存储容器负责的复制动作
3. 本地和 leader 两份复制结构数组
4. 节点故障及恢复动作链

### 建模形式

故障和恢复通过 committed locations 触发，应用和存储容器在不同通道上被依次故障和恢复。复制状态用数组记录，例如 `rep_data_struct` 与 `l_rep_data_struct`。

### 关键抽象与取舍

1. 重点建模故障后状态是否可取回，而不细化真实 Kubernetes 全部行为。
2. `RAFT` 被抽象为能够保证同步点上一致性的复制机制。
3. 把应用故障和节点故障拆成不同自动机，再在查询层统一表达恢复要求。

## 验证目标与性质

### 待验证问题

论文把性质分为三组：

1. `Model Properties`
2. `Fault-tolerance Properties`
3. `Consistency Properties`

### 查询表达

代表性查询包括：

1. `A[] A0.App_deployment imply internal_value[0]==0`
2. `A[] NF.Node_Failure imply(rep_data_struct[0]==0 && ...)`
3. `A0.Failure --> A0.App_deployment`
4. `NF.Node_Failure --> NF.All_recovered`
5. `A[] S.Sync imply (rep_data_struct == l_rep_data_struct)`
6. `A[] not deadlock`

这些查询分别对应卷易失性、节点故障后本地状态丢失、应用恢复、节点恢复、一致性和死锁自由。

## 核心方法与验证流程

1. 先把应用执行、状态写入和复制过程建模。
2. 再加入应用故障与节点故障自动机。
3. 用三组查询分别检查“模型有没有按设计工作”“故障后能不能恢复”“副本是不是最终一致”。

## 案例与结果

论文报告所有定义的性质都被 `UPPAAL` 验证通过，主要结论包括：

1. 应用每次重新部署后，其本地卷确实为空，符合易失性假设。
2. 节点故障会导致本地复制结构清零。
3. 应用故障和节点故障之后，系统都能把应用恢复回部署状态。
4. 当存储容器进入同步状态时，局部复制结构与 leader 复制结构保持一致。
5. 模型整体满足 `A[] not deadlock`。

## 与本研究的关系

### 相关性分析

它与博士研究中的“状态机 + 容错恢复 + 已知缺陷修复”非常接近，尤其适合参考其如何把故障恢复链条编码成可验证状态机。

### 可借鉴之处

1. 将恢复性质按“应用故障”“节点故障”“数据一致性”分层组织。
2. 先验证平台性质，再验证容错性质，最后验证一致性性质。
3. 把复制状态直接做成显式变量，便于性质表达。

### 存在的不足与改进空间

真实 Kubernetes 行为被较强抽象，论文也未公开模型工件；对大规模集群与更复杂应用负载的适用性仍有限。

### 对本研究的启发

它说明“恢复成功”不能只写成单条活性公式，而应拆成部署、数据可用、同步一致等多个可追溯性质簇。
