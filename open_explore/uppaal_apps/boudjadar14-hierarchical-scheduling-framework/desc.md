问题一句话：本文验证的是层次化航电任务系统的可调度性，核心问题是如何在组件级分析中估计每个子系统所需的最小 CPU 预算，并判断整机是否还能在单核上排得下。
方法一句话：作者用参数化 timed automata/stopwatch 模型表示任务、共享资源和非确定性 supplier，再结合 `UPPAAL` 与 `UPPAAL SMC` 分别做精确证明和预算候选估计。
验证收获一句话：论文在 `15` 任务、`3` 组件的航电案例上算出了各组件最小预算需求，并证明顶层因预算总和超过 `100%` 而不可调度。

## 简报

这篇论文把层次化调度问题真正做成了“组件接口 + 子系统验证 + 顶层合成”的形式化流程。作者不是直接把整机一次性扔给 `UPPAAL`，而是先估计每个组件至少需要多少预算，再把组件接口当成父层抽象任务来分析。

- 系统：一个由 `15` 个任务组成的 avionics 应用，被划分为 `3` 个组件。
- 特点：组件级预算合同、具体 timed action 行为、共享输入/输出总线、可切换局部调度策略。
- 规模：`3` 个组件；每个组件 `5` 个任务；共享 I/O bus 作为处理器实例；最小预算分别为 `89/100`、`90/100`、`67/100`。
- 模型：任务、supplier、CPU 和调度策略分别建模；supplier 非确定性地分片供应资源。
- 性质：组件局部 deadline 满足、预算候选下的错误概率、顶层整机是否仍可调度。
- 方法：先用 `SMC` 为 supplier 试探预算，再用经典 `UPPAAL` 验证 `A[] error!=1`。
- 结果：三个子组件各自可调度，但顶层预算总和超过单核可用资源，因此整机不可调度。

`航电任务集 -> 组件划分与 supplier 接口 -> 子组件预算估计/证明 -> 顶层接口合成 -> 整机可调度性结论`

## 论文定位

本文属于典型 `⏱️ + 🚀` 案例，重心是航电任务系统的层次化调度，而不是 `UPPAAL` 引擎本身。与纯解析调度论文相比，它更强调如何把具体任务行为和共享资源真正放进模型检查流程。

## 验证对象与问题背景

### 系统与场景

对象是一个航电实时系统，任务被按功能分为火控、导航和基础显示等子系统，各子系统都要争用 CPU 与 I/O 资源。

### 系统组成与运行机制

论文把应用组织成 `3` 个组件：

1. Component 1：火控相关任务。
2. Component 2：导航相关任务。
3. Component 3：基础显示与 auto-toggle 等任务。

组件内部有本地调度器，组件外部则通过 supplier 接口从父层获得周期/预算形式的 CPU 供应。共享 I/O 总线被建模成一个特殊处理器实例。

### 验证边界

作者验证的是任务层与资源层的 schedulability，不展开更细的飞控算法语义或外部物理环境。

### 核心问题

关键问题有两个：

1. 每个组件至少需要多少预算才不丢 deadline。
2. 即使各组件都能独立满足预算合同，顶层是否还能在单核平台上整体排得下。

## 模型与形式化建模

### 抽象对象

任务由一串 timed actions 描述，动作可以是计算、资源锁定和解锁。组件由本地调度策略和一组任务/子组件组成。

### 建模形式

框架以参数化 timed automata 与 stopwatch 自动机实现，关键模板包括：

1. 任务模板。
2. 非确定性 supplier 模板。
3. CPU/共享资源模板。
4. 调度策略模板，如 `EDF/FPS/RM`。

### 关键抽象与取舍

1. supplier 不是固定时隙表，而是在周期和预算约束内非确定性供给资源。
2. 这样做能保守覆盖“其它组件何时打断当前组件”的全部情形。
3. 共享总线不单独建协议，而作为资源实例并入 schedulability 分析。

## 验证目标与性质

### 待验证问题

论文主要验证：

1. 单个组件在给定 supplier 预算下是否会 miss deadline。
2. 不同预算候选的错误概率有多大。
3. 顶层组件合成后是否还能在单核上可调度。

### 查询表达

文中典型查询包括：

1. `A[] error != 1`
2. `Pr[<=10000](<> error)`
3. `E[globalTime <= 100000;100](max: tWCET[i])`

第一个做严格证明，第二个用来快速否定过小预算，第三个用来观察 worst-case execution time 分布。

### 性质分组与实际含义

1. 组件安全性：任何任务都不应进入 deadline miss。
2. 预算可接受性：给定预算下是否仍可能出现错误轨迹。
3. 顶层资源充足性：所有子组件接口之和是否超出单核可供给上限。

## 核心方法与验证流程

1. 根据任务功能把系统切成多个组件。
2. 给每个组件关联一个非确定性 supplier。
3. 先用 `UPPAAL SMC` 试不同预算候选，若错误概率下界大于 `0`，说明预算过小。
4. 对候选可行预算再用经典 `UPPAAL` 验证 `A[] error != 1`。
5. 将各组件预算接口提升到父层，继续分析顶层组合。

## 案例与结果

### 案例规模

1. 航电应用含 `15` 个任务。
2. 划分为 `3` 个组件，每个组件 `5` 个任务。
3. 共享 I/O bus 建模为处理器实例。

### 关键结果

1. Component 1 至少需要 `89/100` 的系统资源。
2. Component 2 至少需要 `90/100` 的系统资源。
3. Component 3 至少需要 `67/100` 的系统资源。
4. 三者预算总和显著超过 `100%`，因此顶层在单核平台上不可调度。

作者还利用 `SMC` 图形结果观察到：预算过低时，任务 deadline miss 的概率区间下界会明显大于 `0`；预算提高后，worst-case execution time 分布向安全侧收缩。

## 与本研究的关系

### 相关性分析

这篇论文非常贴近博士研究里的“模型-验证-修复”闭环，因为它不仅告诉你系统是否不满足，还告诉你是哪一级预算合同不足。

### 可借鉴之处

1. 用 supplier 接口把高层影响压缩成可验证合同。
2. 先 `SMC` 再 `MC` 的组合策略适合预算搜索。
3. 共享总线这类资源可以直接并入组件级 schedulability，而不必分裂为完全独立的问题。

### 存在的不足与改进空间

案例没有公开稳定模型包；另外顶层不可调度的结论更偏资源容量层，不涉及功能需求层的修复策略。

### 对本研究的启发

对控制系统状态机研究来说，组件级接口和顶层组合之间的“合同式验证”很值得借鉴，尤其适合把 LLM 生成的局部模型放进增量式验证流程。
