方法一句话：作者把 supplicant、authenticator、server 以及攻击者分别建成 `UPPAAL` 模型，用 `CTL` 风格查询检查端口开闭、死锁自由、`MIC/PTK/GTK` 生成与重认证行为。
验证收获一句话：论文证明核心协议在理想前提下满足无死锁和密钥建立要求，同时也指出 `4-way handshake` 对伪造 `ANonce` 和持续 `DoS` 攻击敏感，攻击次数超过阈值后握手会崩溃。

## 简报

这篇论文把无线网络安全协议拆成三个子流程分别验证。它并不试图覆盖完整密码学细节，而是关注状态机层面最直接的安全承诺：协议是否会卡死、端口是否会按预期开闭、`MIC/PTK/GTK` 是否最终建立，以及简单攻击是否会破坏这些性质。

- 系统：`802.1X` 认证流程、`4-way handshake`、`group-key handshake` 三个子协议。
- 特点：带重认证、端口控制、攻击者消息注入和超时重试。
- 规模：supplicant、authenticator、server、hacker/DoS attacker 等若干自动机模板。
- 模型：基于 timed automata 的多角色同步模型。
- 性质：端口开闭可达、死锁自由、`MIC` 最终可验证、重认证可触发。
- 方法：分别建模三个子协议，再用查询检查正常与攻击场景。
- 结果：基本协议满足预期；`4-way handshake` 对错误 `ANonce` 和大规模 `DoS` 攻击脆弱。

`802.11i 认证规范 -> 多角色自动机模型 -> 端口/死锁/密钥查询 -> 暴露握手阶段 DoS 脆弱性`

## 论文定位

本文是 `🛰️ + 🌐` 的网络安全协议案例。它的贡献主要在于把 `802.11i` 的几个关键状态机流程落到 `UPPAAL` 上做行为级验证，因此更适合作为“协议状态机 + 攻击通道 + 时间重试”样本，而不是密码学严格证明。

## 验证对象与问题背景

### 系统与场景

`IEEE 802.11i` 为无线网络提供更强的 `MAC` 层安全机制，广泛用于无线网络与物联网环境。它引入 `802.1X` 认证、`4-way handshake` 和 `group-key handshake` 来建立和更新密钥。

### 系统组成与运行机制

论文建模的关键角色包括：

1. supplicant
2. authenticator
3. authentication server
4. 攻击者或 `DoS` 模块

运行过程大致是先完成 `802.1X` 认证并生成 `PMK`，再通过 `4-way handshake` 生成 `PTK`，最后在组播场景中通过 `group-key handshake` 下发 `GTK`。

### 验证边界

本文主要验证握手控制流程与时间逻辑，不深入密码学运算细节，也没有完全建模 `MIC` 计算和密钥派生全过程。

### 核心问题

作者关心的是：

1. 认证和握手过程会不会死锁
2. 端口是否会按认证结果正确开闭
3. `MIC/PTK/GTK` 是否最终建立
4. `DoS` 或伪造消息会否让协议停滞或崩溃

## 模型与形式化建模

### 抽象对象

论文分别为 `802.1X`、`4-way handshake` 和 `group-key handshake` 构建自动机模板，并通过同步通道表示消息收发，例如 `Msg1! / Msg1?`。

### 建模形式

角色状态、超时变量、攻击计数器和端口状态都被表示为离散状态与时钟变量。攻击者通过 `FakeEAPoStart`、`FakeMsg1` 等通道模拟伪造消息。

### 关键抽象与取舍

1. 把 `MIC`、`PTK`、`GTK` 是否建立压缩成关键布尔量。
2. 主要分析握手状态机，而不展开密码学证明。
3. 攻击效果通过“错误消息导致阻塞/无法恢复初始状态”来近似刻画。

## 验证目标与性质

### 待验证问题

论文为不同子协议设置了代表性查询：

1. 端口最终可打开或关闭
2. 协议无死锁
3. 重认证能够发生
4. `MIC` 最终可验证，进而完成 `PTK` 安装
5. `GTK` 成功下发后组播握手可继续推进

### 查询表达

文中典型查询包括：

1. `E<> port==1`
2. `E<> port==0`
3. `A[] not deadlock`
4. `authenticator.A10 -> port==0`
5. `E<> x==ReCertificationTIME`
6. `E<> MIC==1`

这些查询分别对应端口控制、死锁自由、重新认证和密钥安装等要求。

## 核心方法与验证流程

1. 先单独建模 `802.1X` 认证流程并验证端口和重认证行为。
2. 再为 `4-way handshake` 建模，并加入 `Hacker` 自动机模拟错误 `Msg1` 注入。
3. 最后把 `group-key handshake` 作为两步协议单独建模，验证 `GTK` 成功下发后的继续执行性。

## 案例与结果

论文报告了以下主要结论：

1. `802.1X` 模型满足端口开闭和 `A[] not deadlock` 等基本性质。
2. `4-way handshake` 在理想场景中满足无死锁且 `MIC` 最终可验证。
3. 若攻击者反复发送伪造 `Msg1`，当攻击次数超过约 `100` 次时，supplicant 无法正常拒绝错误信息并恢复到初始状态。
4. `group-key handshake` 满足 `A[] not deadlock`，表明一旦 `GTK` 成功接收，后续流程可正常推进。

## 与本研究的关系

### 相关性分析

它可作为“通信协议状态机 + 时间约束 + 攻击场景”的直接样本，适合支撑博士研究中待验证性质与验证场景的自动生成。

### 可借鉴之处

1. 把复杂标准拆成多个较小子协议逐一验证。
2. 用单独攻击者自动机注入错误消息，而不是混入主协议。
3. 把“可达/不可达 + 无死锁 + 最终建立关键变量”组合成基础性质簇。

### 存在的不足与改进空间

论文明确承认尚未完整建模 `MIC` 验证和完整密钥派生过程，因此更适合行为级验证，而非密码学级安全证明。

### 对本研究的启发

这篇论文提醒本研究：对安全协议类对象，性质往往需要同时覆盖“正常完成”“错误恢复”“攻击下退化”三类路径。
