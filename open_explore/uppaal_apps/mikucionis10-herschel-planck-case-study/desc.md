问题一句话：本文验证的是 Herschel-Planck 卫星控制软件的可调度性，核心问题是 32 个任务在单处理器和混合资源共享协议下是否都能赶在截止时间前完成。
方法一句话：作者把卫星任务集、CPU 调度与资源协议建成 `UPPAAL` 停表自动机模型，并用模型检查替代更保守的经典响应时间分析。
验证收获一句话：`UPPAAL` 证明了全部任务可调度，且给出的最坏响应时间普遍低于传统分析，其中最关键的 `PrimaryF` 任务也被证明仍在截止期内。

## 简报

本文分析的是航天软件调度问题。虽然平台是单 CPU，但任务之间存在固定优先级抢占、优先级继承/优先级上限两种资源共享协议，以及任务挂起等复杂行为，使得经典响应时间分析过于保守。

- 系统：Herschel 与 Planck 卫星共享的单处理器飞控软件架构。
- 特点：固定优先级抢占、混合资源协议、任务挂起、扩展截止时间。
- 规模：`32` 个任务、`6` 类共享资源、`4` 个运行实例（两颗卫星各含 nominal/event 模式）。
- 模型：CPU 调度器 + 任务模板 + 资源模板 + 全局不变式的 `UPPAAL` 网络。
- 性质：可调度性、最坏响应时间、CPU 利用率、阻塞时间。
- 方法：工业任务参数 -> 停表自动机模型 -> reachability/sup 查询 -> 与 Terma 响应时间分析对照。
- 结果：整套系统被证明可调度，`PrimaryF` 任务的 `WCRT` 低于截止时间，且 CPU 利用率约 `63.65%`。

`卫星任务参数/资源协议 -> UPPAAL 调度模型 -> deadline 不可达查询 + WCRT 上界 -> 与经典 RTA 对照`

## 论文定位

这篇论文是 `UPPAAL` 在安全关键嵌入式调度分析中的代表案例。它验证的不是通信协议，而是一个真实卫星软件栈的任务调度与资源竞争行为，因此非常接近“控制系统软件状态机 + 时间约束”的博士主线。

## 验证对象与问题背景

### 系统与场景

被验证对象是 Herschel-Planck 卫星的软件执行架构。两颗卫星传感器和执行机构不同，但共用同一套计算架构：单处理器、RTEMS、基础软件层和应用软件层。

### 系统组成与运行机制

运行机制可概括为：

1. 多个 ASW/BSW 任务在单处理器上按固定优先级抢占调度。
2. 任务通过优先级继承与优先级上限两类协议共享资源。
3. 部分任务在持锁期间会因硬件服务而挂起，使单处理器调度问题呈现出近似多处理器阻塞特征。

这使得系统虽然硬件简单，但时间行为非常复杂。

### 验证边界

论文验证的是**任务调度、资源竞争与响应时间边界**，不是卫星控制算法的业务语义正确性，也不是底层硬件物理环境本身。

### 核心问题

Terma 既有响应时间分析得到的结论是：至少有一个关键任务可能违背截止期，但这种违例在压力测试和部署中从未观察到。作者要判断这是系统真的不安全，还是传统分析太保守。

### 研究动机

模型检查可以显式保留任务依赖、挂起与资源共享结构，因此有机会得到比递推式响应时间分析更少保守、但仍然安全的上界。

## 模型与形式化建模

作者用 `UPPAAL` 扩展的 timed automata/stopwatch automata 建模：

1. **CPU scheduler 模板**
   - 表示单 CPU、固定优先级抢占队列。
2. **任务模板**
   - 周期任务、依赖任务、ASW/BSW 不同控制流。
3. **资源模板**
   - 显式编码优先级继承与优先级上限协议。
4. **全局不变式**
   - 控制 job/WCRT 等停表变量何时推进。

模型边界的关键在于：它保留了任务执行、挂起、锁持有与抢占关系，但不展开应用任务的业务计算内容。

## 验证目标与性质

### 待验证问题

核心问题是所有任务是否都能在各自 deadline 前完成，并进一步给出最坏响应时间和 CPU 使用率。

### 性质分组与实际含义

1. **截止期满足**
   - `error` 状态是否不可达，现实含义是任何任务都不会发生 deadline miss。
2. **最坏响应时间上界**
   - 各任务 `WCRT` 的 `sup` 查询，现实含义是设计时序余量。
3. **阻塞与资源竞争**
   - 量化资源锁和挂起造成的最坏阻塞。
4. **CPU 利用率**
   - 判断平台是否整体过载。

### 性质来源与表达方式

这些性质直接来自工业任务规格：`Period`、`WCET`、`Deadline`、资源使用模式。论文通过 reachability 和 `sup` 查询把这些工程参数转成形式化可检验目标。

## 核心方法与验证流程

1. 从 Terma 的任务与时序文档中读取任务参数。
2. 为 CPU、任务和资源协议实例化 `UPPAAL` 模板。
3. 先检查系统是否存在 deadline violation。
4. 再计算各任务 WCRT 和 CPU 利用率。
5. 最后把结果与 Terma 传统响应时间分析逐项对照。

方法优势在于：不仅能回答“是否可调度”，还能给出更细的可视化排程与阻塞解释。

## 案例与结果

论文给出的主要结果包括：

1. `UPPAAL` 用约 `112s` 即可证明系统可调度。
2. 对整个最坏周期估计的 CPU 利用率约为 `63.65%`。
3. 对 `32` 个任务给出的 `WCRT` 普遍低于 Terma 传统分析结果。
4. 最关键的 `PrimaryF`（任务 `21`）在 `UPPAAL` 中 `WCRT` 约为 `54.115/56.382/58.586`，均低于 `59.6` 的截止时间。

因此，这篇论文最重要的结论不是“算出更小数字”，而是证明原先看似会超时的关键任务其实仍然可调度。

## 与本研究的关系

### 相关性分析

这篇论文直接对应博士研究里的“控制系统软件需求 -> 状态机/自动机 -> 时间性质验证”链条。

### 可借鉴之处

1. 用模板化方式组织调度器、任务、资源三类模型。
2. 把工程文档中的 period/WCET/deadline 直接映射为形式化参数。
3. 用可视化排程与 WCRT 比较支撑工程解释。

### 存在的不足与改进空间

模型依赖大量工业先验参数和人工整理的任务流，自动化程度有限；原始工业文档也无法完全公开复核。

### 对本研究的启发

对于后续博士工作，这篇案例说明：只要把“任务/资源/环境假设”提纯成结构化模型，`UPPAAL` 很适合承接需求到验证剖面的中间层。
