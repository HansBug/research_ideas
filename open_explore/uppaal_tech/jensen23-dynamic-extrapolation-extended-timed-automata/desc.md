# Dynamic Extrapolation in Extended Timed Automata

- 问题一句话：现代 `Uppaal` 实际处理的不是经典 timed automata，而是带整数变量、表达式和 C-like 更新的 `XTA`，继续沿用静态 `M/LU` 外推会因为只看类型上界而变得过粗。
- 方法一句话：先用静态分析找出每个 location-clock 对真正相关的路径和表达式，再在验证时依据当前数据状态动态计算更紧的 extrapolation bound。
- 解决点一句话：让 `UPPAAL` 的 zone abstraction 从“只会看常数”升级到“能看当前程序状态”，从而把 `XTA` 上的外推精度显著收紧。

## 论文定位

这篇论文在 `uppaal_tech/` 技术线上非常关键，因为它正面回答了一个容易被忽略的问题：`UPPAAL` 的输入语言早就不是 Alur-Dill 时代那种纯 clocks + constants 的 timed automata 了，而是 extended timed automata (`XTA`)。

也就是说，现代 `UPPAAL` 用户在模型里经常写的是：

1. clock guard 里带整数表达式；
2. edge 上有更新语句；
3. 约束值会随着当前数据状态变化。

如果外推算法还沿用“先看所有常数上界，再统一外推”的思路，就会越来越不适配实际输入语言。本文正是在这个意义上，属于 `🧱 核心算法/数据结构` 与 `⚡ 改进与扩展` 的交叉条目：它不是发明新建模形式，而是在修补 `UPPAAL` 抽象引擎，使其继续跟得上现代语言层。

## 立足问题

文章立足的问题很具体：经典 extrapolation 在 `XTA` 上不是不能用，而是通常会粗得离谱。

### 1. 经典外推只会看比较常数

在普通 timed automata 里，一个 clock `x` 如果只和常数 `k` 比较，那么当 `x > k` 时，精确值往往已不重要。这正是经典 `M`/`LU` 外推的基础。

### 2. 但 `XTA` 里的 bound 往往是表达式

本文举的例子非常典型：某个 clock `x` 的相关上界可能不是固定 `10`，而是：

1. `a`
2. `a + b`
3. `foo()`

而这些表达式的值又取决于路径上做过哪些更新。若仍然只从变量类型信息里取一个巨大上界，那就会把外推界限放得很松，导致：

1. zone graph 变大；
2. 探索更慢；
3. 内存消耗上升。

### 3. 朴素动态化也不行，因为路径可能有环

最直接的想法是：既然当前数据状态已知，那就临时把表达式算出来不就好了？问题在于，某个 location-clock 对真正受哪些表达式影响，需要回溯到“从当前点到下一次 reset 前”的路径；而路径里可能有环，更新也可能重复多次。

因此作者要解决的核心不是“表达式求值”这么简单，而是：

1. 哪些表达式真的和某个 `(q, x)` 相关；
2. 哪些路径必须考虑；
3. 遇到环时如何保持可计算性；
4. 最终如何仍回到 DBM 可处理的 zone 形式。

## 核心方法

这篇论文的关键贡献是构造 `PDynM` 与对应 `Extra^+_{PDynM}` 外推，它结合了：

1. **离线静态分析**
   - 提前找相关路径；
2. **在线动态求值**
   - 依据当前 data state 算真正的 bound；
3. **保守回退**
   - 遇到难处理环路时退回传统 `M` 外推。

### 1. 先回顾 `XTA` 语义

文章把 `XTA` 建成：

1. location
2. clock valuation `\nu`
3. discrete data state `\sigma`
4. guards `g`
5. data condition `b`
6. update `u`
7. reset set `r`

也就是说，一个配置实际上是：

$$
(q, \sigma, \nu)
$$

这比经典 timed automata 多了一个显式 data state。本文所有“动态外推”的核心，就是把这个 `\sigma` 充分利用起来。

### 2. 传统 `M` 外推在 `XTA` 上的扩展仍然太粗

论文先定义了面向 `XTA` 的 `M(q, x)`。其基本做法是：

1. 看 location invariant 中和 `x` 有关的表达式。
2. 看 outgoing edge guard 里和 `x` 有关的表达式。
3. 沿着不 reset `x` 的边继续往后看。
4. 最终取这些表达式在其域 `D_A(e)` 上的最大值。

这已经比经典 timed automata 更进一步，因为它允许 bound 是表达式而非单个常数。但问题仍在于：`D_A(e)` 只是一个静态近似域。对于当前具体状态 `\sigma`，很多表达式根本不会取到那么大的值。

于是这个 `M` 仍然偏保守。

### 3. 目标是定义真正依赖当前状态的 `DynM`

理想情况下，作者想为每个 location-clock 对 `(q, x)` 和当前数据状态 `\sigma` 计算一个真正精确的动态 bound：

$$
\mathrm{DynM}(q, \sigma, x)
$$

它应当等于：从 `q` 出发，在下一次 reset `x` 之前，所有真正相关约束在当前状态及其后续更新下可能产生的最大比较值。

但这个理想定义直接算会碰到路径环问题，因此作者没有直接实现 `DynM`，而是先构造一个可计算的近似 `PDynM`。

### 4. 用 `Paths_M` 静态收集“相关路径”

作者观察到，对某个 `(q, x)` 来说，真正相关的只是这样一些 path-expression 对：

1. path 从 `q` 开始；
2. path 上没有 reset `x`；
3. path 终点处存在一个和 `x` 相关的局部约束表达式；
4. 这个表达式才可能影响 `x` 的外推界。

于是定义了 `Paths_M(q, x)`：为每个 location-clock 对收集所有这类相关路径及其终点表达式。

关键点在于，这一步是在**验证前**做的静态分析。也就是说：

1. 动态外推不会在探索过程中反复做图搜索；
2. 所有“哪条路径 relevant”都提前算好并缓存下来。

### 5. 用 DFS + 颜色标记检测环，并在环上回退到 `M`

论文给出了两个核心算法 `ComputePaths` 和 `ComputePathsRecursive`。它们用 DFS 和四种颜色：

1. white
2. gray
3. black
4. red

来遍历每个 `(q, x)` 的相关路径。

其目的有两个：

1. 收集所有 acyclic relevant paths。
2. 一旦发现 relevant cycle，就把该 `(q, x)` 标成 `⊥`，表示这里不能精确动态化，后续直接回退到 `M(q, x)`。

这一步非常漂亮，因为它承认“完全动态精确化”在有环时不现实，但又不因此放弃整个方法，而是只在局部回退。

### 6. 在验证时按当前状态执行路径上的更新，再求表达式值

当 `Paths_M(q, x)` 不是 `⊥` 时，论文就定义：

$$
\mathrm{PDynM}(q, \sigma, x) = \max_{(w,e) \in Paths_M(q,x)} \mathrm{eval}(w, e, \sigma)
$$

其中 `eval(w, e, σ)` 的意思是：

1. 沿 path `w` 上的更新依次作用到当前 data state `\sigma`；
2. 若途中某条边的 data condition 在当前状态下不成立，则该 path 作废；
3. 否则在 path 终点把表达式 `e` 真正算出来。

这一步正是“动态外推”的实质：不是靠类型域猜一个大上界，而是顺着当前具体程序状态把相关 bound 算出来。

### 7. 直接的 `a_{≡PDynM}` 抽象可能非凸，所以还要回到 DBM 外推算子

如果只根据 `PDynM` 定义等价关系，然后取对应抽象，得到的值集可能不是 convex zone，于是不能直接用 DBM 表示。

因此作者没有止步于“语义上定义更细的抽象”，而是继续定义一个 DBM 层的外推算子：

$$
\mathrm{Extra}^+_{PDynM,q,\sigma}(D)
$$

它完全仿照 `Extra^+_M` 的风格，只是把里面使用的界值换成了 `PDynM(q,\sigma,x)`。这样做有几个效果：

1. 仍然保持 zone convexity。
2. 仍然能在 DBM 上高效执行。
3. 同时获得更紧的 bound。

这一步很关键，因为它表明本文不是只停在语义证明，而是真的把动态信息压回了现有 `Uppaal` DBM 基础设施。

### 8. 再加两类进一步优化：SCC 与冗余路径删除

论文随后又给了两个非常实用的改进。

#### 8.1 SCC 改进

若一个 relevant cycle 上所有 update 都是 identity update，那它其实不会改变数据状态。此时没必要悲观地回退到 `M`。作者通过 SCC 分析识别这类无害环，减少回退发生的机会。

#### 8.2 基于表达式域的冗余路径删除

若某条路径终点表达式的可能取值域总是被另一条路径的表达式域压住，那么前者永远不可能贡献最大 bound。于是可以预先删掉这类冗余 path。

这说明作者非常关心验证时开销，努力把动态求值需要执行的 path 数量压到更少。

### 9. 推广到 `PDynLU`

论文还指出，这套想法可以自然推广到区分 lower/upper bound 的 `LU` 外推，只需分别维护 `Paths_L` 与 `Paths_U`。虽然正文没完全展开全部细节，但这说明本文不是只对 `M` 外推有效，而是对现代 `Uppaal` 中更常见的 `LU` 思路也兼容。

## 解决了什么问题

这篇论文解决的是一个非常“内核级”的问题：`UPPAAL` 语言能力升级了，但抽象内核如果不升级，就会越来越失配。

### 1. 它把外推从“常数导向”推进到“状态导向”

过去 extrapolation 看的是模型里可能出现的最大常数；本文则把当前 data state 拉进了外推界的计算。这样一来，外推终于能真正感知程序上下文。

### 2. 它用静态分析 + 动态求值的组合，避免了纯动态法过慢

如果完全在线分析相关路径，开销会很大；如果完全离线静态近似，又太粗。本文的混合方法正好卡在两者之间：

1. 结构依赖离线分析。
2. 数值依赖在线求值。

这是一种非常典型、也非常成功的 program-analysis 风格设计。

### 3. 它在大多数有动态约束的模型上显著缩小了 zone graph

实验结果非常明确：

1. 总体上 zone graph 数量减少约 `34.7%`。
2. 时间总体减少约 `3.3%`。
3. 最佳案例能把 zone graph 压到原来的约 `17.3%`，也就是超过 `80%` 的减少。
4. 最坏情况也会有小幅退化，作者没有回避这一点。

这说明本文不是理论上“也许更细”，而是在真实模型上确实有明显收益。

## 与 UPPAAL 技术线的关系

这篇论文的重要性在于：它证明 `UPPAAL` 近年的演化不只是往上层加新 operator、新查询，而是仍在深挖最底层的 symbolic abstraction engine。

从时间线上看，它大致接在：

1. 早期 `DBM / zone / extrapolation` 奠基工作之后；
2. 现代 `XTA` 语言能力扩张之后；
3. 并为更复杂 `Uppaal` 模型继续提供可扩展验证能力。

因此它是“老内核在新语言下如何继续活下去”的代表条目。

## 对本研究的启发

这篇论文对当前博士研究最值得迁移的启发，是：**语言一旦变丰富，抽象规则也必须一起升级**。

1. **不能只把 richer modeling language 当输入层装饰**
   - 如果底层验证/抽象不跟上，语言越丰富，分析越粗。
2. **静态分析与动态分析应当组合使用**
   - 纯静态会过粗，纯动态会过慢；本文的折中方式很值得借鉴。
3. **内核优化会直接决定上层工作流是否可用**
   - 你的闭环研究若想支持更丰富状态机元素，可能同样需要在抽象和状态压缩层做对应升级。

总的来说，这篇论文让人看到：即便在 2023 年，`UPPAAL` 的核心竞争力仍然有一大部分来自它不断更新自己的 symbolic engine，而不是只堆应用层功能。
