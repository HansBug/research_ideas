# Time for Statistical Model Checking of Real-Time Systems

- 问题一句话：大量实时与混杂时间系统问题因复杂度或不可判定性超出经典 timed model checking 能力。
- 方法一句话：为 `CSTA` 网络赋予自然随机语义，用随机运行生成 + Wald 序贯检验 + Monte Carlo 估计，在 `UPPAAL` 中实现 `SMC` 查询与可视化。
- 解决点一句话：把 `UPPAAL` 从纯符号最坏情形验证推进到可处理复杂实时系统概率估计的 `SMC` 路线。

## 论文定位

这篇论文在 `uppaal_tech/` 里属于 `⚡ 改进与扩展`，而且是 `UPPAAL SMC` 技术线非常早的标志性起点之一。它不是把 `UPPAAL` 简单接上一个 Monte Carlo 脚本，而是第一次系统说明：对经典 timed model checking 做不了、甚至不可判定的问题，`UPPAAL` 可以换一条路，通过统计模型检查给出有置信度的近似判断。

如果把它放回 `UPPAAL` 总时间线，这篇工作承接了两类前史：

1. 一边是经典 `UPPAAL` 的符号验证传统，擅长 hard real-time guarantee。
2. 另一边是统计模型检查在概率系统、黑盒系统中的既有方法。

这篇论文的关键作用，是把两者在 `UPPAAL` 环境里第一次真正接起来，明确形成后续 `UPPAAL SMC` 分支的核心方向。

其最核心的对象不是普通 timed automata，而是带更一般连续演化速率的模型，并配合统计查询：

$$
\Pr[\mathrm{bound}](\Diamond \varphi) \ge p, \qquad \Pr[\mathrm{bound}](\Diamond \varphi) \ ? 
$$

## 立足问题

这篇论文立足的问题很明确：经典 timed model checking 虽然已经能在工业规模上处理不少实时验证任务，但它擅长的主要是**穷尽式、符号式、最坏情形**分析。一旦模型更复杂，尤其出现以下几类因素时，传统路线会迅速吃力：

1. 时钟/连续变量在不同位置具有不同演化速率。
2. 模型带有复杂随机或近似随机行为。
3. 问题本身是不可判定的，或者虽然可判定但代价高到不再实用。

论文提到的典型对象是 `Constant Slope Timed Automata`，其中 clocks 在不同 location 的速率可以不同，甚至可能为负。这类模型的表达能力已经逼近甚至达到更一般的 hybrid model 范围，因此很多问题不能再指望用传统 symbolic reachability 直接穷举解决。

作者并不满足于说“那就退回仿真”。他们真正盯住的瓶颈是：

1. 如果只做 simulation，那么缺少形式化查询语义与统计置信界。
2. 如果仍坚持 classical model checking，那么很多问题根本算不动。
3. 即便引入随机语义，也必须保证并行组件组合后得到的仍是纯随机系统，而不是又退化成带非确定性的 MDP，否则统计模型检查就无法直接施展。

所以这篇论文要解决的不是“如何让 `UPPAAL` 也能随机跑几次”，而是更具体的三件事：

1. 给复杂实时网络定义一个**自然的 stochastic semantics**。
2. 设计一个能在此语义下生成随机运行、监测性质并做统计判定的引擎。
3. 把这些能力嵌回 `UPPAAL`，使用户可以像写普通查询那样写概率/比较/估计类查询，并获得可视化反馈。

## 核心方法

这篇论文的方法主线，可以拆成“模型语义层、运行生成层、统计判定层、工具交互层”四层。

### 1. 模型语义层：给复杂 timed system 一个可用于 SMC 的随机语义

论文承接作者团队关于 `CSTA` 的工作，把系统看成一组带常斜率连续变量的实时组件。关键不是再加一个外部随机标签，而是直接对“下一次延时多久、什么时候触发迁移”赋予随机分布。

其设计非常克制：

1. 若某状态允许的延时是有界的，则延时按 uniform distribution 选择。
2. 若延时上界不存在，则按 exponential distribution 选择。
3. 组件并行组合时，通过 race 机制决定谁先发生。

这一步的意义很大。因为组合结果若仍含外部非确定性，统计模型检查就没有明确采样对象；而论文的语义设计正是为了让组合后的系统仍然是“纯随机过程”，而不是 MDP。

### 2. 运行生成层：用专门的 simulation engine 按随机语义抽样运行

任何 SMC 工具都至少要做三件事：

1. 生成随机运行。
2. 在线监测运行是否满足性质。
3. 汇总样本并给出统计结论。

论文为此实现了一个新的运行生成引擎。它不是沿用经典 `UPPAAL` 的 symbolic zone 操作，而是直接在离散时钟取值状态上做更便宜的仿真推进。运行可以按以下几种边界截断：

1. 时间上界
2. cost 上界
3. 离散步数上界

引擎在推进过程中还需要计算：

1. 从当前状态到 invariant 上界还剩多少可延时空间。
2. 某 guard 或谓词何时第一次变为可满足。
3. 一旦监测到目标性质已经成立，是否立即停止该条 run。

换句话说，这里不是“盲目随机走”，而是一个**受时间/代价边界约束、带在线监测的随机运行生成器**。

### 3. 统计判定层：把查询分成 qualitative / quantitative / comparison 三类

论文把工具支持的查询组织成三种典型问题。

第一类是**定性判断**：

$$
\Pr[\mathrm{time} \le b](\Diamond expr) \ge p
$$

这类问题对应“某成功事件在给定边界内发生的概率是否至少达到阈值 `p`”。作者使用 Wald 的 sequential hypothesis testing 来做，优点是：

1. 不一定要预先固定样本数。
2. 当证据已经足够偏向某一边时可以提前停止。
3. 用户可以通过误判概率参数控制精度。

第二类是**定量估计**：

$$
\Pr[\mathrm{time} \le b](\Diamond expr) \ ?
$$

这类问题直接估计概率区间，论文使用基于 Monte Carlo 的方法给出置信区间。

第三类是**概率比较**：

$$
\Pr[\mathrm{time}_1 \le b_1](\Diamond expr_1) \ge \Pr[\mathrm{time}_2 \le b_2](\Diamond expr_2)
$$

这一类很有意思，因为它不是先分别估计两个概率再做人为比较，而是直接使用扩展的序贯假设检验，在统一统计框架下比较两个概率。这样可以避免“两个估计区间各自有误差，却很难统一比较”的问题。

### 4. 工具交互层：把 SMC 结果做成可读的概率分布与趋势图

这篇论文还有一个常被轻视但实际很重要的方法点：作者并没有把结果停留在“输出一个概率区间”。他们专门强调可视化与交互：

1. 概率估计区间可直接显示。
2. 可画出随时间边界增长的累积分布。
3. 可画出成功概率或资源消耗分布。
4. 可比较不同实验配置在各个 bound 下的走势。

这让 `UPPAAL SMC` 的定位从“验证器补充模式”变成了“分析工具”，适合看性能、概率、代价随 bound 的变化，而不是只看一个布尔真值。

## 解决了什么问题

这篇论文解决的，是 `UPPAAL` 在 2011 年前后面对复杂实时随机系统时的一条关键能力缺口。

第一，它给出了一种现实可用的替代路径：当经典 timed model checking 因复杂度或不可判定性失效时，不必彻底放弃形式分析，而可以退到有明确语义和置信界的 `SMC`。

第二，它把“实时系统的统计模型检查”真正做进了 `UPPAAL`。这不是独立原型，而是延续 `UPPAAL` 的建模语言、查询语言风格和交互方式，因此技术线是连续的。

第三，它把查询结果从“硬实时是否满足”扩展到“在给定时间/代价边界内达到目标的概率是多少、两个设计哪个更可能成功、代价分布如何”。这使 `UPPAAL` 不再只做 worst-case verification，还能做 performance-oriented analysis。

当然，这篇论文也没有解决一切：

1. 它给的是近似与置信结论，不是经典 model checking 的完备真值判定。
2. 当事件极罕见时，样本复杂度仍会很高。
3. 论文中的查询仍主要是 bounded、非嵌套概率性质。

## 对本研究的启发

对当前博士研究，这篇论文最直接的启发是：面对复杂实时系统，形式分析不必只剩“全证明”与“全放弃”两种选择，中间还有一层可度量置信度的统计验证。

第一，这对我们后续做状态机生成与验证场景生成很重要。许多由 LLM 生成的模型，早期不一定适合直接上最严格的穷尽式验证；先做 bounded / probabilistic / sampled 分析，反而能更快暴露薄弱点。

第二，论文展示了“查询语言 + 样本执行 + 统计判定 + 可视化反馈”的一体化路径。对自动建模系统而言，验证反馈如果只是 `false` 很难用于修复；但若能像本文这样产出概率曲线、成功分布、能耗走势，就更适合指导模型迭代。

第三，这篇工作提醒我们：在状态机验证里，最坏情形和常见情形是两类不同证据。博士研究若要服务实际控制系统建模，后者往往也很重要。
