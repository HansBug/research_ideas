# Checking & Distributing Statistical Model Checking

- 问题一句话：高置信度 `SMC` 往往需要海量运行，单机生成样本会成为 `UPPAAL SMC` 的吞吐瓶颈。
- 方法一句话：在主从架构下分发 `SMC`，并为序贯假设检验设计无偏分布式算法，利用 batch 与 buffer 同时降低通信和同步开销。
- 解决点一句话：把 `UPPAAL SMC` 从单机统计验证推进到可扩展的分布式统计验证。

## 论文定位

这篇论文在 `uppaal_tech/` 里属于 `🛠️ 工程与工具链`，是 `UPPAAL SMC` 技术线中非常典型的“扩展计算能力而不改动核心语义”的工作。它不是重新发明新的模型或新的逻辑，而是解决 `SMC` 走向大规模时最现实的一道门槛：**采样太慢**。

在时间线上，这篇工作接在 [david11-smc-priced-timed-automata](./../david11-smc-priced-timed-automata/) 与 [david12-statistical-model-checking-stochastic-hybrid-systems](./../david12-statistical-model-checking-stochastic-hybrid-systems/) 之后。前者已经把 `UPPAAL SMC` 的模型与查询语义讲清楚，后者继续扩展到 hybrid systems；而本文转向另一个现实问题：当你已经有正确的 `SMC` 算法后，如何让它在 PC cluster 或 GRID 上真正扩起来，而且不引入统计偏差。

因此，这篇论文的核心价值在于：它把 `UPPAAL SMC` 从“理论上可采样”推进到“工程上可以大规模并行采样”。

## 立足问题

这篇论文面对的问题，不是 `SMC` 能不能做，而是 `SMC` 做得越认真，越容易被自身样本复杂度拖死。

原因很直接：

1. 高置信度意味着要更多样本。
2. 极小 indifferent region 或极高置信要求会进一步抬高样本数。
3. 单次运行本身在复杂模型上也可能很慢。

因此，哪怕 `SMC` 相比穷尽式验证已经便宜很多，面对大规模模型和高精度要求时，还是会遭遇“confidence explosion”。最自然的想法是分布到多个节点并行跑，但问题没有这么简单。

若只是做固定样本数的 Monte Carlo 估计，分布式很容易：预先算出总共要 `N` 次运行，然后平均切给多个 worker 即可。真正麻烦的是**序贯假设检验**：

1. 它不知道总样本数会是多少。
2. master 会根据当前累计证据提前停机。
3. 不同运行耗时可能和结果本身相关。

这就带来一个潜在偏差：如果“短运行”更容易较早返回某一类结论，而 master 又总是优先收到这类结果，那么分布式收集顺序就可能扭曲原本无偏的 Wald 检验。

所以这篇论文真正盯住的是一个很细但很关键的问题：**如何在分布式收集异步样本的同时，不破坏序贯假设检验的统计正确性。**

## 核心方法

这篇论文的方法可以拆成“问题分层、无偏顺序控制、工程参数化、系统自分析”四层。

### 1. 先区分两类 SMC：估计型容易分发，序贯检验型难分发

作者首先明确区分两类 `SMC` 算法：

1. **估计型**
   - 样本数预先已知。
   - 典型是 Monte Carlo 概率估计。
   - 分发策略近乎平凡，直接把样本任务平均分配。
2. **序贯检验型**
   - 样本数动态决定。
   - 典型是 Wald sequential hypothesis testing。
   - 若异步收集方式不当，会引入偏差。

这一分层很重要，因为论文并没有把“分布式 `SMC`”当成一个统一问题，而是指出真正困难之处只在后一类。

### 2. 无偏核心：用 round 思路推广出 batch + buffer 机制

已有工作曾提出 round-robin 式方案，要求按轮同步收集结果以避免偏差，但同步得太死，吞吐就上不去。作者的改进思路是：在保证无偏的前提下，尽量放松同步。

他们引入了两个关键参数：

1. **batch**
   - 每个 worker 不逐条返回单次运行结果，而是累计 `B` 条后再回传一个聚合值。
   - 这可以显著降低通信频率。
2. **buffer**
   - master 允许各 worker 在结果队列中领先若干批次，记作 `K`。
   - 这样较快节点不必每次都被最慢节点完全卡住。

直观上，作者不是要求“所有节点每次都严格一起提交一条结果”，而是允许它们在安全范围内异步前进，但 master 只在足够保守的条件下做判定。这样既降低偏差风险，又提高并行利用率。

### 3. 统计规则层：维护保守上下界而不是直接过早判定

论文的关键算法思想，是对 Wald ratio 的更新维护两个安全近似，而不是在消息到达顺序上盲目即时更新。某些结果尚未返回时，master 通过保守计数形成：

1. 一个偏向接受的下界估计
2. 一个偏向拒绝的上界估计

然后只有当这些保守界已经足够越过阈值时，才允许提前判定。这样一来，即便部分批次尚未抵达，也不会因为“谁先返回”而破坏统计正确性。

这里的关键不是复杂数学新定理，而是把序贯检验从“逐条同步更新”改造成“允许异步、但界定上仍安全”的可执行工程版本。

### 4. 工程实现层：OpenMPI 主从架构 + 参数调优

论文把算法落到了 `UPPAAL` 分布式实现里：

1. 一个 master 负责维护统计状态与决策。
2. 多个 slave 负责生成随机运行。
3. slave 异步发送批量结果。
4. master 依据 buffer 中最低层或早期结果部分更新统计量。

实现上还特别注意：

1. 通信阻塞会在 buffer 满时自然回压。
2. 小批量虽然更灵活，但通信开销高。
3. 大批量虽然减少通信，但又可能让 master 拿到太多“已经没必要”的过量样本。

因此，`B` 与 `K` 都不是拍脑袋参数，而是需要调优的性能控制点。

### 5. 一个很有 `UPPAAL` 味道的方法：用 `UPPAAL SMC` 分析分布式 `SMC` 自己

这篇论文非常漂亮的一点，是作者不只实验跑分布式框架，还把**分布式算法自身**建成 `UPPAAL` 模型，然后再用 `SMC` 去分析它。

也就是说，他们不仅做：

1. 真实 cluster 上的实验 benchmark，

还做：

2. master/slave timed automata 模型，
3. 对不同 `B/K/N` 参数配置做概率与性能估计，
4. 用模型分析来解释实验现象。

这种“工具分析自己”的闭环很 `UPPAAL`，也让论文不只是工程 report，而是具有方法论价值。

## 解决了什么问题

这篇论文解决的是 `UPPAAL SMC` 在走向大规模时一个非常现实且关键的问题。

第一，它证明了：分布式 `SMC` 并不等于“多开几个 worker 就完事”，尤其对 sequential hypothesis testing，必须显式控制样本到达顺序造成的偏差。

第二，它提出的 batch + buffer 机制在统计正确性与并行吞吐之间找到了一个很实用的折中。相较简单同步轮次方法，它减少了不必要阻塞；相较完全异步天真收集，它又保住了无偏性。

第三，它给出了实证和模型双重证据，说明恰当设置 `B` 与 `K` 可以让分布式 `UPPAAL SMC` 近线性扩展，并显著加速大规模案例。

第四，它在 LMAC 这类先前只能小规模分析的协议上，实现了前所未有规模的统计实验，说明分布式 `SMC` 不是纸面优化，而是真能拓展可分析问题边界。

1. 先回顾 `UPPAAL SMC` 的 NPTA 与 Wald 检验基础。

从内容详细程度看，它已经足以让读者重建核心分布式方案和参数作用机制。代码级网络通信细节当然没有完全铺开，但 master/slave 协议、统计状态和实验口径都讲得很清楚。

从实现可获取角度看，这篇论文明确对应 `UPPAAL` 的分布式实现扩展，并依赖 OpenMPI。也就是说，工具层实现明确存在；若要完整复现，则还需结合具体源码与集群环境配置。

## 对本研究的启发

对当前博士研究，这篇论文最大的启发是：一旦验证流程依赖大量样本或大量候选模型，**扩展性问题本身会反过来决定研究方法是否可落地**。

第一，我们未来若让 LLM 生成大量状态机候选，再逐个验证或采样分析，那么分布式执行与结果聚合很可能不是附属问题，而是主问题。

第二，论文提醒我们：并行化不能只看吞吐，还要看统计或逻辑正确性是否被破坏。尤其当验证过程是自适应停止的，异步收集会引入非常隐蔽的偏差。

第三，“用形式方法分析自己的验证框架”这一思路很值得借鉴。对于自动建模与验证流水线，未来完全可以把调度器、采样器、修复循环本身也形式化，反过来分析其性能与正确性。
