# `DESC_GUIDE.md`

本文档用于规范 `open_explore/uppaal_tech/` 下单篇 `desc.md` 的写法。它不是泛泛的“论文摘要模板”，而是面向 `UPPAAL` 理论与技术文库的专项整理规范。

## 1. 使用场景

以下任务默认必须遵守本文件：

1. 新建某篇技术论文的 `desc.md`
2. 重写或大幅修订既有 `desc.md`
3. 审阅某篇 `desc.md` 是否抓住了 `UPPAAL` 技术线的关键问题

如果任务只是扩库、补 `paper_content.txt`、补 `bibtex.bib` 或回填 [SUMMARY.md](./SUMMARY.md) 而不生成单篇 `desc.md`，则不必强制进入本文件；但仍应保持本文件定义的问题/方法/解决点口径与 [SUMMARY.md](./SUMMARY.md) 一致。

## 2. 写作前的必读顺序

生成任何单篇 `desc.md` 前，默认按以下顺序阅读：

1. [README.md](./README.md)
2. [GUIDE.md](./GUIDE.md)
3. [SUMMARY.md](./SUMMARY.md)
4. [DESC_GUIDE.md](./DESC_GUIDE.md)
5. 目标论文目录下的 `bibtex.bib`
6. 目标论文目录下的 `paper_content.txt`
7. 必要时核对 `paper.pdf`

如果条目是 thesis/合集型父路径，先读该父路径自己的 `README.md`，再决定是否进入其 `paper-*` 子目录。

## 3. 本文库下 `desc.md` 的核心关注点

对 `UPPAAL` 技术线论文，单篇 `desc.md` 最优先回答以下三个问题：

1. 这篇工作**立足于什么问题**
2. 它**用了什么方法**
3. 它**解决了什么问题**

其中：

1. “问题”不是只抄一句背景口号，而是要写清它当时卡在什么技术瓶颈、已有方法哪里不够。
2. “方法”不能只列算法名、工具名或术语缩写，而要稍微展开说明它到底怎么做，关键机制是什么。
3. “解决了什么问题”要写清它真正推进了哪一段技术线、把什么从“做不到/做不好”推进到“可以做/做得更好”，同时不要夸大边界。

## 4. `desc.md` 必要结构

后续单篇 `desc.md` 默认至少包含以下结构：

### 4.1 开头三条一句话简述

`desc.md` 最开头必须先给出这三条一句话简述：

1. **问题一句话**
2. **方法一句话**
3. **解决点一句话**

这三条必须足够短，能直接压缩映射到 [SUMMARY.md](./SUMMARY.md) 的对应列。

### 4.2 论文定位

说明这篇论文在 `UPPAAL` 技术线中的位置，例如：

1. 它属于 `🧱 / ⚡ / 🛠️` 哪一类
2. 它处在哪段时间线
3. 它和哪些前后条目直接相连

### 4.3 立足问题

这一节必须回答：

1. 论文面对的具体技术问题是什么
2. 这个问题为什么在当时重要
3. 既有 `UPPAAL`/timed automata 方法哪里不够

推荐写法：

1. 先交代背景与瓶颈
2. 再说明论文具体盯住哪一层问题
3. 最后点明问题边界，不要把所有背景都写成它自己的贡献

### 4.4 核心方法

这是 `desc.md` 的重心之一，必须比“问题”更细。

至少应回答：

1. 它采用了什么核心思想
2. 它依赖哪些关键数据结构、语义对象、搜索策略、抽象规则或工程机制
3. 它和已有方法相比，真正改动了哪里

强约束如下：

1. 不允许只写“提出了某某算法/框架/工具”就结束。
2. 必须稍微展开说明方法机制，例如：
   - 是改了状态表示
   - 改了抽象/外推
   - 改了搜索/剪枝
   - 改了组合规则
   - 改了测试/博弈/统计语义
   - 改了工具架构或用户工作流
3. 如果论文本身是 tutorial / survey / engineering retrospective，也要写清它的方法性贡献体现在“如何组织语言、查询、流程、工具链”。

### 4.5 解决了什么问题

这一节要回答：

1. 它最终让什么变得可做、可扩展、可实现或更高效
2. 它解决到什么程度
3. 还有哪些问题其实没有解决

推荐把“解决点”写成对技术线的推进，而不是泛泛写“提高了性能”“很有意义”。

### 4.6 与 `UPPAAL` 技术线的关系

建议明确写出：

1. 它接在谁之后
2. 它往后影响了谁
3. 它更靠近 `DBM / zone / Tiga / SMC / ECDAR / Stratego / randomized / Coshy` 中哪条主线

### 4.7 实现与材料

默认至少说明：

1. 论文材料够不够细
2. 源码是否可得
3. 若不可得，只有什么层级的实现或运行版本

### 4.8 对本研究的启发

只保留和当前博士研究直接相关的启发，例如：

1. 对状态机建模的启发
2. 对验证场景/性质组织的启发
3. 对工具链设计或验证工作流的启发

## 5. 与 `SUMMARY.md` 的对齐关系

后续单篇 `desc.md` 与 [SUMMARY.md](./SUMMARY.md) 的关系固定如下：

1. `desc.md` 开头三条一句话简述，分别对应 [SUMMARY.md](./SUMMARY.md) 统一总表中的：
   - `问题简述`
   - `方法简述`
   - `解决点简述`
2. `SUMMARY.md` 是压缩版总账。
3. `desc.md` 是单篇展开版解释。

换言之：

1. `SUMMARY.md` 负责让人快速扫全局。
2. `desc.md` 负责把单篇“问题/方法/解决点”讲清楚。

## 6. 证据与写作约束

1. 所有判断都应来自 `bibtex.bib`、`paper_content.txt` 和必要时的 `paper.pdf`。
2. 若论文对方法写得不够细，应如实写“论文未展开到某层细节”，不要脑补。
3. 若论文是 tutorial / survey / retrospective，不要硬套成算法论文；但仍要回答其面向的问题、组织方法和推进结果。
4. 对 thesis/合集型父路径，默认以父条目为主写；若只想写其中一篇 `paper-*` 子论文，应明确说明范围。

## 7. 缺失信息的处理

1. 问题不清楚：回到引言、相关工作和贡献列表补证。
2. 方法不清楚：优先重读方法、算法、语义、实验设置部分。
3. 解决点不清楚：优先重读结论、实验/案例结果和作者对比叙述。
4. 若仍证据不足，在 `desc.md` 中显式标“原文未充分说明”，不要臆测补齐。
