# `DESC_GUIDE.md`

本文档用于规范 `open_explore/uppaal_tech/` 下单篇 `desc.md` 的写法。它不是泛泛的“论文摘要模板”，而是面向 `UPPAAL` 理论与技术文库的专项整理规范。

## 1. 使用场景

以下任务默认必须遵守本文件：

1. 新建某篇技术论文的 `desc.md`
2. 重写或大幅修订既有 `desc.md`
3. 审阅某篇 `desc.md` 是否抓住了 `UPPAAL` 技术线的关键问题

如果任务只是扩库、补 `paper_content.txt`、补 `bibtex.bib` 或回填 [SUMMARY.md](./SUMMARY.md) 而不生成单篇 `desc.md`，则不必强制进入本文件；但仍应保持本文件定义的问题/方法/解决点口径与 [SUMMARY.md](./SUMMARY.md) 一致。

## 2. 写作前的必读顺序

生成任何单篇 `desc.md` 前，默认按以下顺序阅读：

1. [README.md](./README.md)
2. [GUIDE.md](./GUIDE.md)
3. [SUMMARY.md](./SUMMARY.md)
4. [DESC_GUIDE.md](./DESC_GUIDE.md)
5. 目标论文目录下的 `bibtex.bib`
6. 目标论文目录下的 `paper_content.txt`
7. 必要时核对 `paper.pdf`

如果条目是 thesis/合集型父路径，先读该父路径自己的 `README.md`，再决定是否进入其 `paper-*` 子目录。

## 3. 本文库下 `desc.md` 的核心关注点

对 `UPPAAL` 技术线论文，单篇 `desc.md` 最优先回答以下三个问题：

1. 这篇工作**立足于什么问题**
2. 它**用了什么方法**
3. 它**解决了什么问题**

其中：

1. “问题”不是只抄一句背景口号，而是要写清它当时卡在什么技术瓶颈、已有方法哪里不够。
2. “方法”不能只列算法名、工具名或术语缩写，而要**详细展开说明它到底怎么做**，关键机制是什么，最好能让读者看完就知道“这个方法是如何运转起来的”。
3. “解决了什么问题”要写清它真正推进了哪一段技术线、把什么从“做不到/做不好”推进到“可以做/做得更好”，同时不要夸大边界。

## 3.1 详细度基线

`open_explore/uppaal_tech/` 下的 `desc.md` 默认不是“扩写摘要”，而是**单篇技术解剖**。后续写作时，详细度默认以 [ad90-timed-automata/desc.md](./ad90-timed-automata/desc.md) 为基准参照。

硬约束如下：

1. 默认必须逐篇人工阅读该条目的 `bibtex.bib` 与 `paper_content.txt`，必要时回看 `paper.pdf`，再独立写 `desc.md`；不允许只看标题、摘要、现有 `SUMMARY.md` 或旧版 `desc.md` 就草率改写。
2. 默认应把“立足问题 / 核心方法 / 解决了什么问题”三节写成正文主体，而不是每节只写一小段泛泛而谈。
3. 其中“核心方法”通常应是全文最详细的部分之一；如果读完后仍然不知道对象是什么、规则怎么推进、过程如何执行、比前人改了哪里，则说明详细度不达标。
4. 不允许把多篇论文套同一段模板式表述后仅替换名词；每篇都必须保留其自己的技术瓶颈、方法结构、边界条件与时间线位置。
5. 即便是 tutorial、survey、retrospective 或 invited paper，也不能偷换成短摘要；仍需交代它如何组织方法、统一概念、重排工作流或澄清技术路线。
6. 若原文确实没有把某个机制展开到更细层级，应明确写“原文未展开到该层”，而不是用空话糊过去。

换言之，默认目标不是“让读者知道这篇论文大概讲什么”，而是“让读者沿着 `desc.md` 就能看懂：它针对什么技术缺口、靠什么机制推进、推进到什么程度、和 `UPPAAL` 技术线如何衔接”。

## 4. `desc.md` 必要结构

后续单篇 `desc.md` 默认至少包含以下结构：

### 4.1 开头三条一句话简述

`desc.md` 最开头必须先给出这三条一句话简述：

1. **问题一句话**
2. **方法一句话**
3. **解决点一句话**

这三条必须足够短，能直接压缩映射到 [SUMMARY.md](./SUMMARY.md) 的对应列。

### 4.2 论文定位

说明这篇论文在 `UPPAAL` 技术线中的位置，例如：

1. 它属于 `🧱 / ⚡ / 🛠️` 哪一类
2. 它处在哪段时间线
3. 它和哪些前后条目直接相连

### 4.3 立足问题

这一节必须回答：

1. 论文面对的具体技术问题是什么
2. 这个问题为什么在当时重要
3. 既有 `UPPAAL`/timed automata 方法哪里不够

推荐写法：

1. 先交代背景与瓶颈
2. 再说明论文具体盯住哪一层问题
3. 最后点明问题边界，不要把所有背景都写成它自己的贡献

### 4.4 核心方法

这是 `desc.md` 的重心之一，必须比“问题”更细。

至少应回答：

1. 它采用了什么核心思想
2. 它依赖哪些关键数据结构、语义对象、搜索策略、抽象规则或工程机制
3. 它和已有方法相比，真正改动了哪里

强约束如下：

1. 不允许只写“提出了某某算法/框架/工具”就结束。
2. 默认应把“方法”写成全文最扎实的部分之一，通常不应比“立足问题”更短。
3. 必须把方法机制往下展开一层，至少让读者知道它**靠什么对象表达、按什么规则演化、通过什么过程完成分析或验证**。
4. 推荐优先按下面四层去拆方法；如果论文不适合四层全写，也至少写出其中最关键的三层：
   - **对象层**：它引入了什么关键对象，例如 clocks、zones、DBM、game states、queries、templates、components、strategies。
   - **规则层**：这些对象如何变化，例如 reset/guard、抽象/外推、组合/投影、搜索/剪枝、随机采样、策略更新。
   - **过程层**：它怎样完成判定、验证、合成、优化或工程执行，例如 product construction、region graph、symbolic search、simulation loop、query evaluation、tool workflow。
   - **差异层**：它比前一代方法具体多做了什么、少做了什么、换掉了什么。
5. 必须稍微展开说明方法机制，例如：
   - 是改了状态表示
   - 改了抽象/外推
   - 改了搜索/剪枝
   - 改了组合规则
   - 改了测试/博弈/统计语义
   - 改了工具架构或用户工作流
6. 如果论文里同时有“正向方法”和“负结果/边界证明”，默认两边都要交代：
   - 正向方法是怎么让某件事变得可做的；
   - 负结果又是通过什么编码、归约或反例思路证明某件事做不到的。
7. 如果论文本身是 tutorial / survey / engineering retrospective，也要写清它的方法性贡献体现在“如何组织语言、查询、流程、工具链”。

详细度要求再强调一次：

1. “核心方法”默认不应只停留在名词解释层，而要落实到“怎么表示、怎么推进、怎么判定、怎么实现”。
2. 对理论/算法论文，优先补齐关键定义、迁移规则、抽象关系、判定目标、复杂度或可判定性边界。
3. 对工具/工程论文，优先补齐系统架构、数据流、接口关系、执行流程、性能瓶颈与版本集成点。
4. 对综述/教程论文，优先补齐其重新组织技术线的方法，而不是只抄一份目录式概览。
5. 若某篇 `desc.md` 的方法部分明显短于问题部分，或读完仍无法复述“该方法到底如何运作”，则应继续补写，不算完成。

建议在写“方法”时优先补齐以下追问：

1. 它的输入、状态和输出分别是什么。
2. 状态如何推进，或者分析如何一步步展开。
3. 哪些约束、判定条件或 acceptance 条件在真正起作用。
4. 它的 finite abstraction / symbolic representation / executable workflow 到底落在哪一层。
5. 它与前一代方法相比，关键变化是在语义层、算法层、数据结构层，还是工程层。

如果论文本身材料足够细，方法部分还应尽量点出：

1. 关键定义或构造是什么。
2. 重要证明或判定过程依赖什么思路。
3. 复杂度、可判定性或表达能力边界是怎么得到的。

### 4.5 解决了什么问题

这一节要回答：

1. 它最终让什么变得可做、可扩展、可实现或更高效
2. 它解决到什么程度
3. 还有哪些问题其实没有解决

推荐把“解决点”写成对技术线的推进，而不是泛泛写“提高了性能”“很有意义”。

### 4.6 与 `UPPAAL` 技术线的关系

建议明确写出：

1. 它接在谁之后
2. 它往后影响了谁
3. 它更靠近 `DBM / zone / Tiga / SMC / ECDAR / Stratego / randomized / Coshy` 中哪条主线

### 4.7 实现与材料

默认至少说明：

1. 论文材料够不够细
2. 源码是否可得
3. 若不可得，只有什么层级的实现或运行版本

### 4.8 对本研究的启发

只保留和当前博士研究直接相关的启发，例如：

1. 对状态机建模的启发
2. 对验证场景/性质组织的启发
3. 对工具链设计或验证工作流的启发

### 4.9 数学公式与符号规范

对 `UPPAAL` 理论与技术线论文，尤其是 `timed automata / DBM / zone / specification theory / games / SMC` 这类理论或算法成分较强的条目，默认应适度保留原文中的数学表达，而不是全部翻译成口语。

执行规则如下：

1. 行内公式统一写成 `$...$`。
2. 独立定义、关键构造、判定问题、复杂度结果统一写成：

$$
a = b
$$

这样的单独成行公式块。注意中间只能有**一行公式正文**，不能插空行、不能拆成多行推导。
3. `$$` 与 `$$` 之间必须刚好只有一行公式内容；不要写成多行 `aligned` 风格大块推导，以避免 GitHub 渲染炸掉。
4. 默认避免使用 GitHub 上容易出问题的宏或写法，例如：
   - `\left` / `\right`
   - `\operatorname`
   - 多行 `$$` 公式体
   - 其他未经验证的复杂排版宏
5. 推荐替代方式：
   - 花括号直接写 `\{` 与 `\}`
   - 自定义函数名优先写成 `\mathrm{fract}` 这类保守形式
   - 需要“或/且”时优先写 `\lor` / `\land`
6. 不要用反引号包裹纯数学对象；例如应写 `$M = (\Sigma, S, S_0, C, E)$`、`$L(M) \subseteq L(M')$`，而不是代码样式。
7. 文件名、工具名、路径名、命令行参数仍然用反引号，如 `desc.md`、`UPPAAL`、`paper_content.txt`。
8. 对理论论文，若原文材料支持，建议至少保留以下两类公式中的各一类：
   - 一个**关键对象定义**，例如自动机元组、语义对象、约束形式、状态表示。
   - 一个**关键过程或结论**，例如迁移规则、抽象关系、判定问题、复杂度、可判定性边界。
9. 公式不要求越多越好；原则是“该用公式的地方就用公式”，尤其是在以下场景：
   - 口头改述会显著损失精度
   - 论文的方法机制依赖正式定义
   - 判定问题、闭包性质或复杂度结果需要精确表达
10. 若展示公式无法压成单行，应优先改写成正文解释 + 一个单行关键公式，而不是硬塞多行公式块。

## 5. 与 `SUMMARY.md` 的对齐关系

后续单篇 `desc.md` 与 [SUMMARY.md](./SUMMARY.md) 的关系固定如下：

1. `desc.md` 开头三条一句话简述，分别对应 [SUMMARY.md](./SUMMARY.md) 统一总表中的：
   - `问题简述`
   - `方法简述`
   - `解决点简述`
2. `SUMMARY.md` 是压缩版总账。
3. `desc.md` 是单篇展开版解释。
4. 其中 `方法简述` 只是入口，不是终点；单篇 `desc.md` 必须在正文里把该方法简述具体展开成“对象 / 规则 / 过程 / 差异”中的若干层。

换言之：

1. `SUMMARY.md` 负责让人快速扫全局。
2. `desc.md` 负责把单篇“问题/方法/解决点”讲清楚。

## 6. 证据与写作约束

1. 所有判断都应来自 `bibtex.bib`、`paper_content.txt` 和必要时的 `paper.pdf`。
2. 若论文对方法写得不够细，应如实写“论文未展开到某层细节”，不要脑补。
3. 若论文是 tutorial / survey / retrospective，不要硬套成算法论文；但仍要回答其面向的问题、组织方法和推进结果。
4. 对 thesis/合集型父路径，默认以父条目为主写；若只想写其中一篇 `paper-*` 子论文，应明确说明范围。

## 7. 缺失信息的处理

1. 问题不清楚：回到引言、相关工作和贡献列表补证。
2. 方法不清楚：优先重读方法、算法、语义、实验设置部分。
3. 解决点不清楚：优先重读结论、实验/案例结果和作者对比叙述。
4. 若仍证据不足，在 `desc.md` 中显式标“原文未充分说明”，不要臆测补齐。
